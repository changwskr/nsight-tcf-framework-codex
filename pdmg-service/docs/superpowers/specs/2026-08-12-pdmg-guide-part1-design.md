# PDMG 애플리케이션 아키텍처와 개발 가이드 제1부 집필 설계

## 1. 목적

`zz.PDMG 애플리케이션 아키텍처와 개발 가이드 목차.md`의 제1부를 개발자와 애플리케이션 아키텍트가 함께 사용할 수 있는 상세 본문으로 작성한다. 설명은 현재 저장소에서 확인되는 AS-IS 구현만 대상으로 하며, 목표 구조나 미구현 제안은 본문에 섞지 않는다.

## 2. 결과물

다음 디렉터리에 장별 Markdown 파일을 생성한다.

```text
pdmg-service/docs/PDMG 애플리케이션 아키텍처와 개발 가이드/
├─ 01장.PDMG 시스템 개요.md
├─ 02장.전체 온라인 거래 빅픽처.md
└─ 03장.레이어드 아키텍처와 컴포넌트.md
```

## 3. 대상 독자

- PDMG에 처음 참여하는 Java·Spring 업무 개발자
- Handler, Facade, Service, DAO의 책임과 호출 경계를 판단해야 하는 애플리케이션 아키텍트
- TCF ON/OFF 요청 흐름과 공통 프레임워크의 책임을 이해해야 하는 프레임워크 개발자
- 장애 발생 시 요청 흐름과 계층 경계를 추적해야 하는 운영 담당자

## 4. 집필 범위

### 4.1 1장. PDMG 시스템 개요

- PDMG의 목적과 온라인 거래 시스템으로서의 역할
- `pdmg-ui`, `pdmg-service`, `pdmg-fw`, `pdmg-jwt`의 책임
- 모듈 간 빌드·런타임 의존 관계
- Java, Spring Boot, Gradle, MyBatis, JWT 등 실제 기술 스택
- 실제 설정에서 확인되는 실행 포트와 HTTP 호출 관계
- TCF ON/OFF 진입 경로
- Service ID, GUID, ServiceContext, TransactionContext, STF, ETF, 이미지로그 등 핵심 용어

### 4.2 2장. 전체 온라인 거래 빅픽처

- UI에서 업무 DB까지의 전체 요청 흐름
- Filter, Interceptor, TCF, Handler, Facade, Service, DAO, Mapper의 호출 순서
- 시스템 선처리, 업무 처리, 시스템 후처리의 경계
- 정상·업무 실패·시스템 실패 흐름
- 온라인 요청 생명주기와 DB 트랜잭션 생명주기의 차이
- 요청 Thread와 Worker Thread가 실제로 분리되는 조건
- GUID, Context, 로그, 예외, 트랜잭션이 만나는 지점

### 4.3 3장. 레이어드 아키텍처와 컴포넌트

- Framework, Entry, Application, Rule, DTO, Persistence, Client, Config, Support 계층
- 각 계층의 책임, 입력, 출력, 의존 대상
- 허용되는 호출 방향과 금지되는 역방향 의존
- 실제 패키지와 대표 클래스 매핑
- PDMG 구조와 클린 아키텍처 개념의 대응 관계
- 현재 구현이 표준 계층 구조와 다른 지점은 사실로 명시

## 5. 장별 공통 구성

각 장은 주제에 맞게 다음 순서를 적용한다.

1. 장의 목적과 학습 목표
2. 핵심 구조 다이어그램
3. 주요 개념과 책임
4. AS-IS 실제 구현
5. 실행 또는 의존 흐름
6. 설정과 소스의 연결
7. 경계와 주의사항
8. 개발자·아키텍트 점검 체크리스트
9. 장 요약과 다음 장 연결

## 6. 표현 원칙

- 텍스트 다이어그램과 표를 우선 사용한다.
- 클래스, 설정 키, 파일 경로는 저장소에서 확인된 정확한 이름을 사용한다.
- 문서보다 실행 코드와 설정을 우선 근거로 삼는다.
- TCF ON과 OFF를 섞지 않고 각각의 실제 경로를 구분한다.
- 온라인 거래 범위와 Spring DB 트랜잭션 범위를 동일한 개념처럼 표현하지 않는다.
- 구현되지 않았거나 확인되지 않은 기능은 AS-IS인 것처럼 서술하지 않는다.
- 로컬 개인 경로, 계정, Secret과 Token 값은 본문에 넣지 않는다.
- 중복 원문을 그대로 복사하지 않고 하나의 설명으로 통합한다.

## 7. 근거 우선순위

1. `pdmg-service`, `pdmg-fw`, `pdmg-ui`, `pdmg-jwt` 실행 코드
2. 각 모듈의 `build.gradle`과 Spring YAML
3. 테스트 코드
4. 모듈 README
5. 제1부 관련 기본 문서와 `-1.md` 재분석 문서
6. `46~75`번 아키텍처 다이어그램 문서

## 8. 검증 기준

- 목차의 제1부 1~3장 절이 빠짐없이 포함되어야 한다.
- 본문에서 참조한 저장소 상대 경로가 실제로 존재해야 한다.
- 모듈 버전, 포트, 설정 키와 주요 클래스가 현재 코드와 일치해야 한다.
- TCF ON/OFF, 트랜잭션, Thread 설명이 실제 조건부 구성과 일치해야 한다.
- 세 장 사이에 같은 설명이 불필요하게 반복되지 않아야 한다.
- Markdown 제목 계층, 표, 코드 블록과 내부 링크가 정상이어야 한다.
