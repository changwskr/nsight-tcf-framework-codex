# PDMG 애플리케이션 아키텍처와 개발 가이드 제2부 집필 설계

## 1. 목적

`zz.PDMG 애플리케이션 아키텍처와 개발 가이드 목차.md`의 제2부를 개발자·아키텍트용 상세 본문으로 작성한다. 목차의 장·절 번호와 제목을 최대한 그대로 유지하고, 현재 저장소에서 확인되는 AS-IS 식별체계와 개발 구조를 설명한다.

## 2. 결과물

```text
pdmg-service/docs/PDMG 애플리케이션 아키텍처와 개발 가이드/
├─ 04장.애플리케이션 분류와 Service ID.md
├─ 05장.네이밍 규칙.md
├─ 06장.패키지와 프로젝트 구조.md
└─ 07장.도메인 정의와 호출 방식.md
```

## 3. 목차 보존 원칙

- 4장은 `4.1`부터 `4.15`까지 원래 절 번호와 제목을 유지한다.
- 5장은 `5.1`부터 `5.17`까지 원래 절 번호와 제목을 유지한다.
- 6장은 `6.1`부터 `6.16`까지 원래 절 번호와 제목을 유지한다.
- 7장은 `7.1`부터 `7.13`까지 원래 절 번호와 제목을 유지한다.
- 장 도입, 체크리스트, 장 요약, 근거 문서는 번호 없는 보조 절로 둔다.
- 목차에 없는 설명은 기존 절의 하위 제목으로만 추가한다.

## 4. 장별 내용

### 4장. 애플리케이션 분류와 Service ID

애플리케이션 코드 분류표를 기준으로 대구분, 업무구분, 세부업무, 프로그램 식별번호, 거래구분을 해석한다. 화면번호·프로그램 ID·Service ID·URL·Handler Registry·거래 통제·타임아웃의 연결을 실제 `mgcoa*` 거래와 TCF 코드로 설명한다. 신규 Service ID의 생성·등록·검증 절차와 미등록·중복 오류를 포함한다.

### 5장. 네이밍 규칙

`MG-NAMING_CONVENTION.md`를 최우선 기준 문서로 사용한다. 프로그램 접두어, Service ID, Java 패키지, 클래스, Handler, Controller, Facade, Service, Rule, DTO, DAO, Mapper 파일과 Statement ID, Java 필드·DB 컬럼, 오류 코드 규칙을 실제 코드와 대조한다. 문서 규칙과 현행 예외를 구분하고 금지 이름과 신규 프로그램 체크리스트를 제시한다.

### 6장. 패키지와 프로젝트 구조

`pdmg-service`와 연관 모듈의 실제 디렉터리·패키지 구조를 기준으로 `entry`, `application`, `dto`, `persistence`, `client`, `config`, `support`의 책임을 설명한다. Mapper 리소스 경로, Component Scan, Mapper Scan, Aspect Pointcut, 신규 업무축, 테스트 패키지와 금지 패턴을 실제 Annotation·설정과 연결한다.

### 7장. 도메인 정의와 호출 방식

시스템, 업무·세부업무, 프로그램, 거래 도메인의 경계를 정의하고 의존 관계를 설명한다. TCF ON/OFF, UI 직접 호출, UI Relay, 외부 시스템, 동기·비동기 호출을 별개의 흐름으로 기술한다. 신규 도메인 추가 시 식별자, 패키지, Handler/Controller, Facade, Service, DAO·Mapper와 UI 연결까지 확인할 절차를 제시한다.

## 5. 근거 우선순위

1. `pdmg-service`, `pdmg-fw`, `pdmg-ui`, `pdmg-jwt`의 현재 실행 코드
2. `build.gradle`, Spring YAML, Mapper XML
3. 테스트 코드
4. `MG-NAMING_CONVENTION.md`
5. 목차가 지정한 기본 문서
6. `-1.md` 재분석 문서와 다이어그램 문서

## 6. 표현 원칙

- AS-IS와 저장소 표준 규칙을 구분한다.
- 식별자를 분해할 때 각 자리와 코드의 의미를 텍스트 다이어그램으로 표현한다.
- 화면번호와 Service ID가 항상 일대일이라고 가정하지 않는다.
- URL, Header와 path의 Service ID 결정 우선순위를 실제 Controller 코드에 맞춘다.
- Handler Registry는 `TransactionDispatcher` 생성 시점의 등록 구조로 설명한다.
- 거래 통제와 타임아웃은 Service ID를 키로 사용하는 연계 지점까지만 설명하고 상세 알고리즘은 후속 장으로 넘긴다.
- 개인 경로, 계정, Secret, Token 값은 기록하지 않는다.
- 구현되지 않은 Rule이나 Client를 현행 구현처럼 만들지 않는다.

## 7. 검증 기준

- 목차의 61개 절이 모두 한 번씩 존재해야 한다.
- 장별 절 번호가 오름차순이며 제목이 원래 목차와 일치해야 한다.
- 본문의 대표 클래스, 설정 키, URL, 패키지와 리소스 경로가 실제 저장소와 일치해야 한다.
- 모든 로컬 Markdown 링크가 실제 파일로 해석되어야 한다.
- 네 장 사이의 용어와 예시가 일관되어야 한다.
- Markdown 공백 오류, 미완성 표시와 민감정보가 없어야 한다.

## 7.1 상세 품질 기준

- 각 장은 제1부와 같은 수준의 도입, 학습 목표, 핵심 다이어그램, 본문, AS-IS 분석, 예제, 주의사항, 체크리스트와 요약을 갖춘다.
- 각 번호 절은 최소한 `개념/목적`, `실제 구현 또는 규칙`, `개발 시 영향`을 설명한다.
- 소스가 있는 절은 대표 클래스·메서드·Annotation·설정 키를 제시한다.
- 흐름이 있는 절은 텍스트 다이어그램 또는 단계 표를 제공한다.
- 단순 정의를 반복하지 않고 `mgcoa9000` 등 하나 이상의 실제 프로그램을 끝까지 추적한다.
- 분량 자체를 목표로 삼지는 않지만 장당 최소 250줄 상당의 설명 밀도를 확보한다.
