## 1. 전문과 DTO의 구분

전문은 HTTP로 전달되는 전체 JSON이고, DTO는 그 안의 업무 데이터입니다.

### 요청 전문

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "202608100001",
      "rms_svc_c": "mgcoa9000S0",
      "optr_eno": "user01",
      "tr_trm_ipadr": "127.0.0.1"
    }
  },
  "dto": {
    "keyword": "거래",
    "pageNo": 1,
    "pageSize": 20
  }
}
```

Java 타입 대응은 다음과 같습니다.

| JSON 영역   | Java 타입          | 소유 모듈      |
| ----------- | ------------------ | -------------- |
| `hdr_nhnis` | `hdr_nhnis`        | `pdmg-fw`      |
| `sys_comm`  | `sys_comm`         | `pdmg-fw`      |
| `dto`       | `mgcoa9000S0DTOin` | `pdmg-service` |

`DTOin`에는 `hdr_nhnis`가 들어가지 않습니다. 공통 헤더는 `ServiceContext`에서 관리합니다.

## 2. 요청 DTO 변환 과정

현재 Controller는 처음부터 DTO 타입으로 받지 않고 전체 JSON을 `Map`으로 받습니다.

```java
@PostMapping("/{serviceId}")
public Object handleByServiceId(
        @PathVariable String serviceId,
        @RequestBody Map<String, Object> request,
        HttpServletRequest servletRequest) throws Exception {
    return handle(serviceId, request, servletRequest);
}
```

Controller는 `dto` 노드만 꺼냅니다.

```java
Object dtoBody =
        request == null ? null : request.get("dto");
```

이 시점의 `dtoBody`는 일반적으로 `LinkedHashMap`입니다.

이후 처리 흐름은 다음과 같습니다.

```text
HTTP JSON
→ Controller: Map<String, Object>
→ request.get("dto"): Object/Map
→ Handler
→ Facade
→ ObjectMapper.convertValue()
→ 거래별 DTOin
→ Service
```

Facade의 변환 코드:

```java
private <T> T convert(Object dtoBody, Class<T> type) {
    Object source = dtoBody == null
            ? Collections.emptyMap()
            : dtoBody;

    return objectMapper.convertValue(source, type);
}
```

예:

```java
mgcoa9000S0DTOin input =
    convert(dtoBody, mgcoa9000S0DTOin.class);
```

### `dto`가 없을 때

`dtoBody == null`이면 빈 Map을 DTO로 변환합니다.

```text
dto 없음
→ emptyMap()
→ 모든 필드가 null/0/기본값인 DTOin
```

따라서 `dto`가 없다는 이유만으로 Controller나 Facade에서 즉시 오류가 발생하지 않습니다. 필수값 검증은 현재 주로 Service에서 수행합니다.

## 3. DTO 종류

### `*DTOin`

거래 요청 데이터를 표현합니다.

```text
mgcoa9000S0DTOin   거래 파라미터 조회 조건
mgcoa9000C0DTOin   거래 파라미터 등록 데이터
mgcoa9000U0DTOin   거래 파라미터 수정 데이터
mgcoa9000D0DTOin   거래 파라미터 삭제 키
```

목록 조회 DTO에는 일반적으로 다음 값이 들어갑니다.

```java
private String keyword;
private Integer pageNo;
private Integer pageSize;
```

`offset`은 외부 전문에서 받지 않고 Service가 계산합니다.

```java
int offset = (pageNo - 1) * pageSize;
```

이는 사용자가 임의의 SQL Offset 값을 직접 지정하는 것을 막고 페이징 정책을 Service에서 통제한다는 의미입니다.

### `*DTOout`

Service가 반환하는 업무 결과입니다.

조회형:

```java
private List<mgcoa9000S0DTOSub0> mgcoa9000S0DTOSub0;
private int size;
private int pageNo;
private int pageSize;
private long totalCount;
private int totalPages;
```

쓰기형:

```java
private Integer PROC_CNT;
private String RSLT_CD;
private String RSLT_MSG;
```

### `*DTOSub0`

조회 결과 한 행을 표현합니다.

```text
DB 조회 Map 한 건
→ DTOSub0 한 개
→ DTOout 목록에 추가
```

예:

```java
mgcoa9000S0DTOSub0 sub =
        new mgcoa9000S0DTOSub0();

sub.setTxId(asString(row, "TX_ID", "txId"));
sub.setTxName(asString(row, "TX_NAME", "txName"));

output.addmgcoa9000S0DTOSub0(sub);
```

### `*MsgJson`

`mgcoa9999`에만 별도 MsgJson 클래스가 있습니다.

```text
mgcoa9999S0DTOinMsgJson
mgcoa9999S0DTOoutMsgJson
mgcoa9999S0DTOSub0MsgJson
```

이 클래스는 SuperSpring의 `JsonMessage` 기반 marshal/unmarshal을 지원합니다.

일반적인 온라인 요청에서는 Facade의 Jackson `convertValue()`가 사용되므로 MsgJson이 필수는 아닙니다.

```text
일반 온라인 요청
→ ObjectMapper.convertValue
→ DTOin

특수 marshal 엔진
→ DTOinMsgJson / DTOoutMsgJson
```

## 5. `DataObject`의 역할

PDMG DTO는 일반 Java Bean 기능 외에도 다음 메타 정보를 가집니다.

```java
private static final Map<String, FieldProperty>
        fieldPropertyMap;
```

예:

```java
fieldPropertyMap.put(
    "txId",
    FieldProperty.builder()
        .setPhysicalName("txId")
        .setLogicalName("txId")
        .setType(FieldProperty.TYPE_OBJECT_STRING)
        .setIsNullable(true)
        .setIsEncrypt(false)
        .build()
);
```

`FieldProperty`에는 다음과 같은 DTO 설계 정보가 들어갑니다.

```text
물리 필드명
논리 필드명
데이터 타입
Decimal 정보
Nullable 여부
암호화 여부
```

이 정보는 DTO 엔진에는 필요하지만 HTTP 응답에는 불필요합니다. 그래서 시스템 후처리에서 제거합니다.

## 6. 목록 DTO의 특수 Getter

목록형 DTO에는 동일한 내부 목록에 접근하는 여러 Getter가 있습니다.

```java
getmgcoa8888S0DTOSub0()
getmgcoa8888S0DTOSub0List()
getmgcoa8888S0DTOSub0Array()
getmgcoa8888S0DTOSub0(int index)
```

Jackson이 그대로 직렬화하면 유사한 목록 필드가 여러 개 만들어질 가능성이 있습니다.

개념적으로:

```json
{
  "mgcoa8888S0DTOSub0": [],
  "mgcoa8888S0DTOSub0List": [],
  "mgcoa8888S0DTOSub0Array": []
}
```

시스템 후처리는 이름이 `List`나 `Array`로 끝나는 보조 필드를 제거합니다.

최종 응답:

```json
{
  "mgcoa8888S0DTOSub0": [
    {
      "guid": "...",
      "serviceId": "mgcoa8888S0"
    }
  ],
  "size": 1,
  "pageNo": 1,
  "pageSize": 20,
  "totalCount": 1,
  "totalPages": 1
}
```

현재 생성형 목록 DTO 구조에서는 중복 Getter 정리라는 목적에 맞습니다.

## 7. `*List/*Array` 삭제 규칙의 위험

현재 삭제 로직은 해당 필드가 메타 Getter에서 생성된 것인지 확인하지 않고 이름만 검사합니다.

```java
if (fieldName.endsWith("List")
        || fieldName.endsWith("Array")) {
    fieldsToRemove.add(fieldName);
}
```

따라서 정상 업무 응답 필드를 다음처럼 정의하면 데이터가 실제 HTTP 응답에서 제거됩니다.

```java
private List<String> customerList;
private String[] resultArray;
```

```text
Service DTOout에는 존재
→ 업무 후처리 로그에서 제거
→ HTTP 응답에서도 제거
→ ImageLog 응답 전문에서도 제거
```

권장 기준은 다음과 같습니다.

- `DTOin`에는 `guidList`, `txIdList` 같은 이름을 사용할 수 있음
- `DTOout`에서 실제 업무 필드 이름을 `*List`, `*Array`로 끝내면 안 됨
- 장기적으로는 필드명 일괄 삭제 대신 보조 Getter에 `@JsonIgnore`를 선언하는 것이 안전함

예:

```java
@JsonIgnore
public List<Row> getRowsList() {
    return rows;
}

@JsonIgnore
public Row[] getRowsArray() {
    return ...
}
```

이렇게 하면 응답 후처리에서 이름 기반 삭제가 필요 없어집니다.

## 8. 삭제 요청 DTO의 호환성

`mgcoa8888D0DTOin`은 여러 JSON 필드명을 허용합니다.

```java
@JsonProperty("guidList")
@JsonAlias({
    "GUID_LIST",
    "guid_LIST",
    "guid_list"
})
private List<String> guidList;
```

따라서 다음 요청이 모두 바인딩됩니다.

```json
{ "guidList": ["A", "B"] }
```

```json
{ "GUID_LIST": ["A", "B"] }
```

```json
{ "guid_list": ["A", "B"] }
```

Java API 호환을 위한 기존 Getter는 JSON 직렬화에서 제외했습니다.

```java
@JsonIgnore
public List<String> getGUID_LIST() {
    return getGuidList();
}
```

`mgcoa9000D0DTOin.txIdList`도 같은 방식입니다.

이 구조는 기존 전문과 camelCase 신규 전문을 함께 지원하기 위한 호환 처리로 적절합니다.

## 9. 출력 결과 코드 DTO

쓰기 DTOout은 대문자 필드 계약을 사용합니다.

```java
private Integer PROC_CNT;
private String RSLT_CD;
private String RSLT_MSG;
```

응답 예:

```json
{
  "PROC_CNT": 1,
  "RSLT_CD": "0000",
  "RSLT_MSG": "OK"
}
```

현재 코드 의미는 업무별 Service 구현에 들어 있습니다.

```text
0000 = 정상
0001 = 필수값 누락 또는 입력 데이터 없음
0002 = 중복
0003 = 대상 없음
```

주의할 점은 이 값들이 공통 `exceptionCode.yml`의 시스템 예외 코드가 아니라 Service가 정상 반환하는 업무 결과 코드라는 것입니다.

```text
RSLT_CD 실패
→ Java 예외 없음
→ 업무 후처리 실행
→ 트랜잭션 정상 커밋 가능
→ HTTP 상태도 보통 200
```

반면 `BizException`, Timeout 등은 오류 DTO인 `NH_NIS_ERR_DTO`로 변환됩니다.

## 10. 성공 응답과 오류 응답

### 성공

Service가 `DTOout`을 반환하면 시스템 후처리가 `dto`에 넣습니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "...",
      "rms_svc_c": "mgcoa9000C0"
    }
  },
  "dto": {
    "PROC_CNT": 1,
    "RSLT_CD": "0000",
    "RSLT_MSG": "OK"
  }
}
```

### 오류

예외는 `NH_NIS_ERR_DTO`로 변환되어 `result`에 들어갑니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "...",
      "rms_svc_c": "mgcoa9000C0"
    }
  },
  "result": {
    "stdErrCode": "FW_TIMEOUT",

    "errType": "COMMON"
  }

```

따라서 전문 계약은 정확히 다음과 같습니다.

| 결과                     | 본문 키  | 타입             |
| ------------------------ | -------- | ---------------- |
| 정상 또는 업무 결과 코드 | `dto`    | 업무 `*DTOout`   |
| 프레임워크·업무 예외     | `result` | `NH_NIS_ERR_DTO` |

## 11. 오류 DTO 보안 문제

`NH_NIS_ERR_DTO`에는 다음 내부 정보 필드가 존재합니다.

```text
errClassName
errFileName
errMethodName
errLineNo
stackTrace
```

`NhBaseException` 처리 경로에서는 상위 15개 Stack Trace를 DTO에 넣습니다.

이 값이 클라이언트 응답으로 전달되면 내부 클래스, 파일명, 메서드와 소스 위치가 노출될 수 있습니다.

운영 응답에는 다음 정도만 포함하는 것이 적절합니다.

```json
{
  "stdErrCode": "E9999",
  "stdErrMsgCntn": "처리 중 오류가 발생했습니다.",
  "errType": "SYSTEM"
}
```

상세 예외 정보는 서버 로그와 ImageLog에만 남기는 것이 안전합니다.

## 12. 입력 검증 관점

현재 DTO에는 Bean Validation이 적용되어 있지 않습니다.

검색 결과 다음 형태의 제약 조건은 발견되지 않았습니다.

```java
@NotNull
@NotBlank
@Size
@Pattern
@Valid
```

따라서 현재 입력 검증은 다음처럼 Service 코드에서 직접 수행합니다.

```java
String txId = trimToNull(input.getTxId());

if (txId == null) {
    output.setRSLT_CD("0001");
    output.setRSLT_MSG("REQUIRED: txId");
    return output;
}
```

현재 방식의 특징:

- 검증 시점이 Service 진입 이후
- 실패를 예외가 아닌 결과 DTO로 반환할 수 있음
- 거래마다 검증 로직이 중복될 수 있음
- 필드 길이와 형식 검증 누락 가능

신규 DTO에서는 필드 필수 여부, 최대 길이, 허용 형식을 명시하는 것이 필요합니다.

## 13. 문서 현행화가 필요한 부분

27번 문서는 대부분 현행 구현과 일치합니다. 다음 표현은 보완이 필요합니다.

| 문서 내용                    | 현행 분석                                       |
| ---------------------------- | ----------------------------------------------- |
| DTO는 보통 `DataObject` 상속 | 현재 업무 DTO는 전부 상속                       |
| `*List/*Array`는 메타 필드   | 이름 기반 삭제이므로 정상 업무 필드도 삭제 가능 |
| 실패 `NH_NIS_ERR_DTO`        | HTTP에서는 `result` 키에 들어감                 |
| UI JSON 필드명 = Java 필드명 | `@JsonAlias`가 있으면 레거시 이름도 허용        |
| `dto`가 요청 DTO로 변환      | 실제로는 Controller Map → Facade `convertValue` |
| DTO 필수값 계약              | Bean Validation 없이 Service가 직접 처리        |

## 최종 평가

| 영역                            | 평가                           |
| ------------------------------- | ------------------------------ |
| 헤더와 업무 DTO 분리            | 정상                           |
| 거래별 DTO 분리                 | 정상                           |
| DTO 패키지 위치                 | 정상                           |
| `DTOin → Service → DTOout` 흐름 | 정상                           |
| DataObject 메타 관리            | 구현됨                         |
| 목록 DTO 중복 Getter 정리       | 구현됨                         |
| `*List/*Array` 제거 안정성      | 개선 필요                      |
| 레거시 요청 필드 호환           | 일부 DTO에 구현                |
| 입력 Bean Validation            | 없음                           |
| 오류 DTO 내부정보 노출          | 개선 필요                      |
| DTO 바인딩 테스트               | `mgcoa8888D0DTOin` 일부만 존재 |

핵심적으로는 다음 구조입니다.

```text
DTOin
= 외부 dto 입력을 업무 타입으로 변환

DTOout
= Service의 정상 반환 데이터

DTOSub0
= 목록 응답의 한 행

NH_NIS_ERR_DTO
= 예외 응답이며 dto가 아니라 result에 포함

hdr_nhnis
= 업무 DTO가 아니라 FW ServiceContext의 공통 헤더
```

이번 분석은 소스와 문서를 읽은 정적 점검이며 파일 수정과 테스트 실행은 하지 않았습니다.
