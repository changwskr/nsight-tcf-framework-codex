## 12. HTTP 요청 분석 결과

[12.http요청.md](./12.http요청.md)의 서버 요청 구조는 대체로 맞지만 UI 호출 방식이 현재 소스와 반대로 설명되어 있습니다.

또한 non-local JWT 요청, `/{businessCode}/online`, 서비스 ID 불일치 검증에 중요한 제약이 있습니다.

## 1. 현재 온라인 HTTP 계약

TCF ON 기준 실제 계약은 다음과 같습니다.

```text
Method       POST
Content-Type application/json
Body         JSON Object
서비스 식별  rms_svc_c 우선, URL path 보조
```

대표 요청:

```http
POST /mgcoa8888S0
Content-Type: application/json;charset=UTF-8
Accept: application/json
```

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa8888S0",
      "std_gbl_id": "..."
    }
  },
  "dto": {
    "pageNo": 1,
    "pageSize": 20
  }
}
```

서버 내부 흐름 (현행: `tcf.enabled=true`, `timeout.enabled=true`):

```text
POST
  ↓
DefaultFilter
  ↓
ServicePreventionInterceptor
  ↓
OnlineTransactionController
  ↓
TcfFacade
  ↓
OnlineTimeoutExecutor   ← Worker + TransactionTemplate (Commit/Rollback 주체)
  ↓
TransactionDispatcher
  ↓
Handler
  ↓
Facade                  ← @Transactional(REQUIRED) 로 기존 TX 참여
  ↓
Service
  ↓
DAO
  ↓
ResponseBodyAdvice      ← 성공 dto / 실패 result
```

`timeout.enabled=false` 이면 Executor는 `SyncOnlineTimeoutExecutor`(동기 통과)이고, 이 경우 Commit/Rollback 주체는 Facade `@Transactional` 쪽이 됩니다.

## 2. 문서의 가장 큰 오류: UI Relay가 현행이 아님

문서에는 UI 호출을 다음처럼 설명합니다.

```text
브라우저
  → pdmg-ui /api/relay/{serviceId}
  → pdmg-service
```

하지만 현재 화면은 Relay를 사용하지 않고 브라우저가 `pdmg-service`를 직접 호출합니다.

[`service-client.js`](../../pdmg-ui/src/main/resources/static/_shared/service-client.js)

```javascript
const response = await fetch(targetUrl, {
  method: "POST",
  headers: {
    "Content-Type": "application/json;charset=UTF-8",
    Accept: "application/json",
  },
  body: JSON.stringify(body),
});
```

실제 흐름:

```text
브라우저 :8090
  ↓ 직접 fetch + CORS
pdmg-service :8080/{serviceId}
```

Relay API는 하위 호환으로 남아 있지만 현재 일반 거래 화면에서는 사용하지 않습니다.

따라서 문서의 다음 부분을 수정해야 합니다.

```text
5.1 UI Relay (화면)
→ UI 브라우저 직접 호출

9.4 UI에서 service URL 직접 호출 금지
→ 현재는 직접 호출이 기본이므로 삭제 또는 정책 변경
```

현재 문서는 [11.Http CORS적용.md](./11.Http%20CORS적용.md) 및 실제 UI 코드와 모순됩니다.

## 3. 지원 URL 세 가지

[`OnlineTransactionController.java`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/web/OnlineTransactionController.java)는 다음 경로를 지원합니다.

| URL                           | 서비스 ID                |
| ----------------------------- | ------------------------ |
| `POST /{serviceId}`           | Header 우선, 없으면 path |
| `POST /online`                | Header 필수에 가까움     |
| `POST /{businessCode}/online` | Header 필수에 가까움     |

### PDMG 기본

```http
POST /mgcoa8888S0
```

이 경로는 local에서 헤더가 없어도 작동할 수 있습니다.

```json
{
  "dto": {
    "pageNo": 1
  }
}
```

`DefaultFilter`가 URL 마지막 경로인 `mgcoa8888S0`를 사용해 합성 헤더를 만듭니다.

### `/online`

```http
POST /online
```

이 경로에서 헤더가 없으면 Filter가 서비스 ID를 URL 마지막 값인 `online`으로 합성할 수 있습니다.

```text
rms_svc_c = online
```

그러면 Dispatcher에는 다음 값이 전달됩니다.

```text
serviceId = online
```

등록된 Handler가 없으므로 실패합니다.

따라서 `/online`에서는 다음 헤더가 사실상 필수입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa8888S0"
    }
  }
}
```

### `/{businessCode}/online`

```http
POST /mg/online
```

이 경로도 Filter 관점에서 URL 마지막 값은 `online`입니다. Header가 없으면 마찬가지로 `online`을 서비스 ID로 사용할 수 있습니다.

또한 Controller가 받는 `businessCode` 값은 별도로 검증하거나 사용하지 않습니다.

```java
return handle(businessCode, request, servletRequest);
```

Header나 Context에 서비스 ID가 없을 때만 fallback으로 사용되므로 현재 `businessCode`는 실질적인 업무코드 검증 기능이 없습니다.

문서에는 다음처럼 명확히 적어야 합니다.

```text
/online 및 /{businessCode}/online 요청에는
hdr_nhnis.sys_comm.rms_svc_c가 반드시 필요하다.
```

## 4. 서비스 ID 우선순위

실제 우선순위는 다음과 같습니다.

```text
1. ServiceContext.header.sys_comm.rms_svc_c
2. 요청 JSON hdr_nhnis.sys_comm.rms_svc_c
3. URL path 변수
```

따라서 다음 요청은 URL과 다른 거래를 실행할 수 있습니다.

```http
POST /mgcoa8888S0
```

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa8888D0"
    }
  },
  "dto": {
    "guidList": ["..."]
  }
}
```

실제 라우팅:

```text
URL           mgcoa8888S0
전문 Header   mgcoa8888D0
실행 거래     mgcoa8888D0
```

문서에는 “동일하게 맞춘다”고만 되어 있지만 현재 서버가 일치를 검증하지 않는다는 사실을 추가해야 합니다.

권장 검증:

```java
if (StringUtils.hasText(pathServiceId)
        && StringUtils.hasText(headerServiceId)
        && !pathServiceId.equals(headerServiceId)) {
    throw new BizException(
        "FW0001",
        "URL과 전문의 서비스 ID가 일치하지 않습니다."
    );
}
```

## 5. UI도 서비스 ID 일치를 강제하지 않음

[`online-single.js`](../../pdmg-ui/src/main/resources/static/_shared/online-single.js)는 전송 전에 헤더와 GUID를 보강하지만 선택한 거래 ID를 `rms_svc_c`에 강제로 설정하지 않습니다.

```javascript
payload = ensureHdrNhnis(payload, true);
```

`ensureHdrNhnis()`가 하는 일:

- `hdr_nhnis` 생성
- `sys_comm` 생성
- GUID 생성
- `dto` 생성

하지만 다음 보장은 없습니다.

```text
payload.hdr_nhnis.sys_comm.rms_svc_c
    =
현재 선택한 transactionId
```

샘플을 그대로 쓰면 일치하지만 사용자가 JSON을 편집하거나 다른 거래의 전문을 복사하면 불일치할 수 있습니다.

전송 전에 다음 보정 또는 검증이 필요합니다.

```javascript
const selectedId = transactionIdEl.value;
const headerId = payload.hdr_nhnis.sys_comm.rms_svc_c;

if (headerId && headerId !== selectedId) {
  throw new Error("URL 거래와 전문 서비스 ID가 다릅니다.");
}

payload.hdr_nhnis.sys_comm.rms_svc_c = selectedId;
```

삭제·등록 거래에서는 안전상 자동 덮어쓰기보다 사용자에게 불일치를 알리고 전송을 막는 방법이 좋습니다.

## 6. non-local에서는 현재 UI 직접 호출이 실패함

문서에는 다음 요청 헤더가 기술되어 있습니다.

```http
Authorization: Bearer {accessToken}
```

`DefaultFilter`는 local이 아니면 반드시 이 헤더를 검사합니다.

```java
if (!"local".equalsIgnoreCase(active)) {
    String authorization =
        request.getHeader(HttpHeaders.AUTHORIZATION);

    if (authorization == null
            || !authorization.startsWith("Bearer ")) {
        response.sendError(401, ...);
        return;
    }
}
```

하지만 UI의 `service-client.js`는 Authorization 헤더를 보내지 않습니다.

```javascript
headers: {
  'Content-Type': 'application/json;charset=UTF-8',
  Accept: 'application/json'
}
```

따라서 현재 화면은:

```text
local 환경     → 호출 가능
dev/prod 환경  → 항상 401 가능
```

현재 `jwt.enabled=false`(예: local/dev yml)여부와 관계없이, `DefaultFilter`는 **프로파일이 local이 아니면** 토큰 검증 로직을 실행합니다. `jwt.enabled` 플래그를 Filter가 읽지는 않습니다.

해결하려면 UI에 토큰 공급 구조가 필요합니다.

```javascript
headers: {
  'Content-Type': 'application/json;charset=UTF-8',
  Accept: 'application/json',
  Authorization: `Bearer ${accessToken}`
}
```

하지만 브라우저 저장소에 토큰을 보관할 경우 XSS 위험을 함께 고려해야 합니다. 운영에서는 Gateway 또는 UI 서버 Relay가 인증정보를 관리하는 방식이 더 안전할 수 있습니다.

---

## 7. Relay도 Authorization을 전달하지 않음

서버 Relay도 현재 다음 헤더만 설정합니다.

```java
.defaultHeader(
    "Content-Type",
    "application/json;charset=UTF-8"
)
.defaultHeader(
    "Accept",
    "application/json;charset=UTF-8"
)
```

따라서 Relay 방식으로 전환해도 non-local `DefaultFilter` 인증을 자동 통과하지 않습니다.

운영 Relay를 사용할 계획이라면 다음 중 하나가 필요합니다.

- 사용자 Authorization 헤더를 안전하게 전달
- UI 서버가 서비스 호출용 토큰을 발급받아 전달
- Gateway를 통한 인증
- 신뢰된 내부 호출 계약

단순히 Relay로 바꾼다고 인증 문제가 해결되지는 않습니다.

## 8. Body 필수 여부

문서에는 `hdr_nhnis + dto` 전체가 필수처럼 표현되어 있지만 실제로는 환경별로 다릅니다.

### 요청 Body 자체

Body가 비어 있으면 Filter가 400을 반환합니다.

```text
Request Body 입력 전문이 비어있습니다.
```

따라서 Body 자체는 필수입니다.

### `hdr_nhnis`

```text
local     선택 가능, Filter 합성
non-local 필수
```

### `dto`

Controller는 다음처럼 가져옵니다.

```java
Object dtoBody =
    request == null ? null : request.get("dto");
```

`dto`가 없으면 `null`이 Handler로 전달됩니다. Facade는 일부 거래에서 null을 빈 Map으로 변환합니다.

```java
Object source =
    dtoBody == null
        ? Collections.emptyMap()
        : dtoBody;
```

따라서 현재 구현은 `dto` 누락을 공통 Controller에서 차단하지 않습니다.

문서의 “dto 필수”는 표준 계약으로는 맞지만 실제 검증은 없습니다.

## 9. Body 최상위 타입

공통 Controller는 다음 타입을 받습니다.

```java
@RequestBody Map<String, Object> request
```

따라서 최상위 JSON은 Object여야 합니다.

정상:

```json
{
  "dto": {}
}
```

잘못된 형태:

```json
[
  {
    "dto": {}
  }
]
```

또는:

```json
"mgcoa8888S0"
```

배열이나 단순 문자열은 `Map<String,Object>`로 변환할 수 없어 MVC 단계에서 역직렬화 오류가 발생합니다.

현재 일반 시스템 예외 Handler가 완전하지 않아 이 오류가 표준 `result` 전문으로 내려간다는 보장도 없습니다.

## 10. 응답 처리

현재 TCF 응답은 다음과 같습니다.

### 성공

```json
{
  "hdr_nhnis": {...},
  "dto": {...}
}
```

### 알려진 예외

```json
{
  "hdr_nhnis": {...},
  "result": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "...",
    "errType": "COMMON"
  }
}
```

문서의 다음 표현:

```text
NH_NIS_ERR_DTO 또는 Advice가 감싼 형태
```

은 현재 구현 기준으로 더 명확히 수정할 수 있습니다.

```text
TCF ON + legacy-web 활성:
hdr_nhnis + result(NH_NIS_ERR_DTO)
```

다만 Filter 오류와 일반 미처리 예외는 이 형식이 보장되지 않습니다.

UI는 HTTP 상태뿐 아니라 서비스 오류 본문의 `result` 존재 여부도 확인합니다(`error-popup.js`의 `errorPayload`). 브라우저 Abort/네트워크 실패 시에는 `service-client.js`가 합성한 상위 `stdErrCode`(UI_TIMEOUT/UI_NETWORK)를 볼 수 있습니다. 이 방향은 적절합니다.

## 11. 클라이언트 Timeout과 서버 Timeout

UI:

```yaml
pdmg.ui.timeout-ms: 10000
```

서버:

```yaml
nhnis.fw.timeout.milliseconds: 5000
```

현재 기본값은 다음 순서입니다.

```text
서버 Timeout 5초
  ↓
서버가 HTTP 504 반환
  ↓
UI는 10초 안에 504 수신
```

이 순서가 적절합니다.

UI Timeout이 서버보다 짧으면:

```text
브라우저는 먼저 연결을 중단
서버 작업은 계속 실행될 수 있음
```

특히 브라우저의 `AbortController.abort()`는 클라이언트 대기를 중단하는 것이지 Java Worker Thread와 DB 트랜잭션을 직접 취소하는 기능이 아닙니다.

## 12. X-Forwarded-For 신뢰 문제

Controller와 Filter는 `X-Forwarded-For`의 첫 번째 값을 클라이언트 IP로 사용합니다.

```java
String forwardedFor =
    request.getHeader("X-Forwarded-For");
```

서비스를 브라우저가 직접 호출할 수 있으면 사용자가 이 헤더를 위조할 수 있습니다.

따라서 사용자별·IP별 거래통제에 사용할 경우 다음이 필요합니다.

```text
외부 Client
  ↓
신뢰된 Gateway/Proxy가 기존 XFF 제거
  ↓
Gateway가 검증된 Client IP 기록
  ↓
pdmg-service는 신뢰된 Proxy 요청만 허용
```

서비스가 모든 클라이언트의 `X-Forwarded-For`를 그대로 신뢰하면 IP 기반 거래통제를 우회할 수 있습니다.

## 13. TCF OFF 요청

TCF OFF에서는 개별 업무 Controller가 활성화됩니다.

```java
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "false",
    matchIfMissing = true
)
```

개별 Controller는 Spring의 기본 `@RequestBody`가 아니라 PDMG 전용 annotation을 사용합니다.

```java
import nhnis.fw.commons.resolver.RequestBody;
```

`RequestBodyArgumentResolver`가 전체 전문에서 `dto`를 추출해 업무 DTO로 변환합니다.

따라서 TCF OFF에서도 요청 구조는 다음과 같습니다.

```json
{
  "hdr_nhnis": {...},
  "dto": {...}
}
```

다만 TCF OFF에서는 다음 기능이 달라질 수 있습니다.

- Handler 라우팅 없음
- 공통 TimeoutExecutor 미사용
- Facade를 거치지 않고 Controller가 Service 직접 호출
- Facade 트랜잭션 미사용
- GlobalExceptionHandler 비활성
- 오류 응답 정책 차이

따라서 TCF OFF는 HTTP URL만 동일할 뿐 처리 계약 전체가 동일하지 않습니다.

## 최종 평가

문서 정확도는 약 60~70%입니다.

서버의 POST 전문과 내부 처리 흐름은 맞지만, 가장 중요한 UI 호출 경로가 현재 구현과 반대로 기록되어 있습니다.

현재 실제 흐름은 다음과 같습니다.

```text
브라우저 pdmg-ui:8090
  ↓ 직접 POST + CORS (주 경로)
pdmg-service:8080/{serviceId}
```
