대상: `pdmg-service` / `pdmg-fw`  
관련 소스:

| 역할          | 패키지 / 클래스                                               |
| ------------- | ------------------------------------------------------------- |
| 업무 선후처리 | `nhnis.mg.co.a.entry.aspect.BizPrePostAspect`                 |

## 결론

`BizPrePostAspect` Pointcut을 **Service**(`application.service`)로 두면, 업무 선처리·후처리가 **Facade `@Transactional` 안**에서 실행된다.

```text
TX BEGIN   ← Facade 프록시 진입 (application.facade)
├─ 업무 선처리          ← Service 프록시 @Before (entry.aspect)
├─ Service              ← application.service
├─ DAO / SQL            ← persistence.dao
└─ 업무 후처리          ← Service 프록시 @AfterReturning
TX COMMIT  ← Facade 반환
```

검증 로그 키:

```text
[업무 선처리] 호출: mgcoa5530Service.mgcoa5530S0
```

---

## 패키지 관점에서의 책임 분리

트랜잭션·선후처리 위치는 **컴포넌트 타입 → 패키지**로 고정한다.

| 관심사                  | 컴포넌트   | 패키지                   | 이유                        |
| ----------------------- | ---------- | ------------------------ | --------------------------- |
| serviceId 라우팅        | Handler    | `entry.handler`          | TCF 진입만. TX·업무 없음    |
| 요청 횡단 로그/선후처리 | Aspect     | `entry.aspect`           | 배선. 업무 로직 없음        |
| DB commit/rollback      | Facade     | `application.facade`     | 업무 TX 경계                |
| 업무 절차               | Service    | `application.service`    | Aspect 대상. TX 미보유      |
| HTTP(TCF OFF)           | Controller | `application.controller` | 호환 진입. TCF ON 시 비활성 |
| SQL                     | DAO        | `persistence.dao`        | 영속만                      |

```text
entry.handler ──► application.facade ──► application.service ──► persistence.dao
                      │                        ▲
                      │                   entry.aspect
                      │              (BizPrePost on Service)
                      └── @Transactional(rdwTransactionManager)
```

## 변경 전 / 후

### 변경 전 (Controller ‖ Facade Pointcut)

Advisor `@Order`에 따라 업무 후처리가 TX **밖**에 있을 수 있었다.

```text
업무 선처리
→ TX 시작
→ Facade / Service / DAO
→ TX Commit
→ 업무 후처리          ← Commit 이후일 수 있음
```

### 변경 후 (Service Pointcut) — 현재

Facade TX가 먼저 열리고, 그 안에서 Service Aspect가 돈다. TX Advisor와 Biz Aspect의 순서 경쟁을 피한다.

```text
Handler (entry.handler)
→ Facade 프록시 (application.facade)
   → @Transactional 시작
   → Service 프록시 (application.service)
      → 업무 선처리 (entry.aspect.BizPrePostAspect)
      → Service
      → DAO / SQL (persistence.dao)
      → 업무 후처리
   → Service 반환
→ Facade 반환
→ Commit
```

## 현재 Pointcut / TX 선언

### BizPrePostAspect

파일: `nhnis.mg.co.a.entry.aspect.BizPrePostAspect`

```java
@Pointcut("execution(public * nhnis.mg.co.a.application.service..*(..))")
public void mgBizBoundary() {
}
```

### PdmgBizTxFlowAspect (참고)

파일: `nhnis.mg.co.a.entry.aspect.PdmgBizTxFlowAspect`  
Handler / Facade / Controller / Service / DAO 메서드 시작·종료 TX-FLOW 로그 (`@Order(50)`).

### Facade `@Transactional`

```java
// nhnis.mg.co.a.application.facade.*
@Transactional(transactionManager = "rdwTransactionManager", readOnly = true)
public mgcoa8888S0DTOout mgcoa8888S0(Object dtoBody) { ... }
```

| 항목             | 위치                                                                |
| ---------------- | ------------------------------------------------------------------- |
| `@Transactional` | **Business Facade** (`application.facade`, `rdwTransactionManager`) |
| 업무 선후처리    | **Service** (`application.service` ← `BizPrePostAspect`)            |

## 런타임 전체 흐름

### TCF ON (`nhnis.fw.tcf.enabled=true`)

상세: [pdmg-service 트랜잭션흐름.md](./pdmg-service%20트랜잭션흐름.md)

```text
Filter → 시스템 선처리(ImageLog INSERT)
  → OnlineTransactionController (pdmg-fw)
  → TcfFacade → Handler (entry.handler)
  → Facade (application.facade, @Transactional)
       → [업무 선처리] → Service (application.service)
       → DAO (persistence.dao) → [업무 후처리]
  → 시스템 후처리(응답 봉투) → ImageLog UPDATE
```

공통 Controller 1개(`OnlineTransactionController`) + Handler / Facade / Service.  
거래별 Controller(`application.controller`)는 TCF ON일 때 `@ConditionalOnProperty(..., false)` 로 비활성.

### TCF OFF (호환)

```text
Filter → Controller (application.controller)
  → Service (application.service)   ← 현재 구현은 Service 직호출
  → DAO
```

TCF ON과 TX 경계를 맞추려면 Controller → Facade 호출이 더 일관되지만,  
현재 샘플 Controller는 Service를 직접 호출한다. (호환 경로)

## Service Pointcut 부작용

| 항목                            | 내용                              |
| ------------------------------- | --------------------------------- |
| Facade가 Service를 N회 호출     | 선후처리 로그 N회                 |
| 배치/스케줄이 Service 직접 호출 | 선후처리 실행됨                   |
| Facade DTO 변환 실패            | Service 미도달 → 업무 선처리 없음 |
| Service → Service 호출          | 중첩 선후처리 가능                |
| self-invocation                 | 프록시 미통과 → Aspect 미실행     |

거래당 선후처리를 **정확히 1회**만 보장하려면 Facade Pointcut + TX Advisor 순서 조정이 개념적으로 더 맞다.  
**Service 실행을 같은 TX로 확실히 감싸는 것**이 우선이면 현재 Service Pointcut이 적절하다.

---

## 잔여 개선

- 로그 `BRC: null`: DTO에 지점코드가 없을 때 `ServiceContext` 헤더 `tr_brc`로 보완 가능
- TCF OFF Controller를 Facade 경유로 맞추면 TX·선후처리 경계가 ON과 동일해짐
- IDE 실행 시 `pdmg-service` 변경은 `classes` 재컴파일·재시작 필요. `pdmg-fw` 변경은 jar 재빌드 후 재시작
