## 13. Filter — DefaultFilter 분석 결과

`DefaultFilter`는 PDMG 요청이 Controller에 도착하기 전에 실행되는 공통 진입 필터입니다.

핵심 역할은 다음 네 가지입니다.

```text
요청 본문 캐싱
+ 비-local JWT 검증
+ hdr_nhnis 및 ServiceContext 생성
+ 로그 추적용 MDC 구성
```

소스 위치: [DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java:45>)

### 1. 전체 처리 위치

```text
HTTP 요청
  ↓
DefaultFilter
  ├─ JWT 검증
  ├─ 요청 Body 캐싱
  ├─ hdr_nhnis 파싱·보완
  ├─ ServiceContext 생성
  └─ MDC 설정
  ↓
Spring Security
  ↓
DispatcherServlet
  ↓
ServicePreventionInterceptor
  ↓
OnlineTransactionController
  ↓
Handler → Facade → Service → DAO
```

`DefaultFilter`는 트랜잭션을 시작하거나 업무 SQL을 실행하지 않습니다. 트랜잭션 시작 전, 요청 처리 환경을 준비하는 계층입니다.

## 3. 일반 JSON 요청 처리

### 3.1 serviceId 추출

요청 URI의 마지막 부분을 임시 serviceId로 사용합니다.

```java
String uri = request.getRequestURI();
String serviceId = uri.contains("/")
        ? uri.substring(uri.lastIndexOf("/") + 1)
        : "UNKNOWN";
```

예를 들면:

```text
POST /mgcoa5530S0
→ serviceId = mgcoa5530S0
```

이 값은 먼저 MDC의 `serviceId`에 저장되고, 전문의 `rms_svc_c`가 있으면 나중에 그 값으로 교체됩니다.

주의할 점은 URI가 `/online`이면 초기 serviceId가 단순히 `online`이 된다는 것입니다. 따라서 `/online` 방식에서는 전문의 `hdr_nhnis.sys_comm.rms_svc_c`가 사실상 필요합니다.

---

### 3.2 요청 Body 캐싱

필터가 요청 JSON을 먼저 읽기 때문에 원래 Servlet 요청을 그대로 사용하면 Controller에서 Body를 다시 읽을 수 없습니다.

따라서 다음 래퍼를 사용합니다.

```java
CachedBodyHttpServletRequest wrapper =
        new CachedBodyHttpServletRequest(request);
```

캐시 구현: [CachedBodyHttpServletRequest.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/CachedBodyHttpServletRequest.java:14>)

Body 전체를 `byte[]`로 메모리에 저장하고, 이후 Controller가 다시 읽을 수 있게 합니다.

이 방식의 특징은 다음과 같습니다.

- 일반 온라인 JSON에는 적합
- 요청 Body 전체가 메모리에 올라감
- 대용량 JSON에서는 메모리 사용량 증가
- 파일 업로드는 별도 multipart 경로 사용

## 4. JWT 검증

JWT 검증 여부는 `jwt.enabled`가 아니라 활성 프로파일로 결정됩니다.

```java
if (!"local".equalsIgnoreCase(active)) {
    // JWT 검증
}
```

| 환경                | JWT 처리                 |
| ------------------- | ------------------------ |
| `local`             | 검증 생략                |
| `dev`, `prod`, 기타 | Bearer Access Token 필수 |

### 검증 순서

```text
Authorization 헤더 존재
  ↓
"Bearer "로 시작
  ↓
공유 비밀키로 JWT 서명 검증
  ↓
type 클레임이 ACCESS인지 검사
  ↓
subject를 ssoId로 추출
  ↓
request attribute에 저장
```

성공하면 다음과 같이 저장합니다.

```java
String ssoId = jwtProvider.getSsoId(token);
request.setAttribute("ssoId", ssoId);
```

검증 구현: [JwtProvider.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/jwt/JwtProvider.java:52>)

### 현재 설정 불일치

`dev` 설정에는 다음 값이 있습니다.

```yaml
jwt:
  enabled: false
```

하지만 `DefaultFilter`는 이 값을 전혀 사용하지 않습니다.

따라서 실제 동작은:

```text
spring.profiles.active=dev
+ jwt.enabled=false
→ 그래도 JWT 필수
```

운영 전에 `jwt.enabled`를 실제 조건으로 사용할지, 프로파일 조건을 유지할지 정책을 통일해야 합니다.

## 5. 요청 전문 처리

정상 JSON 요청은 다음 구조를 기대합니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "GUID",
      "rms_svc_c": "mgcoa5530S0",
      "scid": "mgcoa5530",
      "tr_trm_ipadr": "127.0.0.1",
      "optr_eno": "USER01",
      "tr_sysid": "pdmg-ui"
    }
  },
  "dto": {}
}
```

### local 환경

`hdr_nhnis`가 없어도 허용됩니다.

```json
{
  "dto": {}
}
```

필터가 다음 값을 자동 생성합니다.

| 필드           | 자동값                                 |
| -------------- | -------------------------------------- |
| `std_gbl_id`   | UUID, 하이픈 제거                      |
| `rms_svc_c`    | URL 마지막 경로                        |
| `scid`         | serviceId의 `S0`, `D0` 등 제거         |
| `tr_trm_ipadr` | X-Forwarded-For 또는 remoteAddr        |
| `optr_eno`     | `LOCAL`                                |
| `tr_sysid`     | `spring.application.name`, 현재 `pdmg` |

### 비-local 환경

`hdr_nhnis`가 없으면 다음 응답으로 종료됩니다.

```text
HTTP 400
공통 Header 정보가 없습니다.
```

## 6. ServiceContext 생성

필터는 공통 정보를 `ServiceContext`에 담습니다.

```java
ServiceContext serviceContext = new ServiceContext(
        applicationName,
        guid,
        active,
        requestHeaders,
        wrapper,
        response,
        header
);

serviceContext.setRequestBody(requestBody);
ServiceContextHolder.setInstance(serviceContext);
```

관련 소스:

- [ServiceContext.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/context/ServiceContext.java:14>)
- [ServiceContextHolder.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/context/ServiceContextHolder.java:3>)

저장되는 정보는 다음과 같습니다.

```text

active profile

HttpServletResponse
hdr_nhnis
원본 requestBody
userContext

```

`ServiceContextHolder`는 `ThreadLocal` 방식이므로 동일 요청 스레드의 Interceptor, Controller, Aspect 등에서 접근할 수 있습니다.

## 7. MDC 로그 컨텍스트

다음 값이 Log4j `ThreadContext`에 저장됩니다.

| MDC 키      | 출처                    |
| ----------- | ----------------------- |
| `guid`      | `std_gbl_id`            |
| `ip`        | `tr_trm_ipadr`          |
| `userId`    | `optr_eno`              |
| `serviceId` | `rms_svc_c`, 없으면 URL |

이 값들이 로그 패턴에 사용되어 같은 거래의 로그를 추적할 수 있게 합니다.

요청 처리가 끝나면 반드시 제거합니다.

```java
ServiceContextHolder.removeInstance();
ThreadContext.clearAll();
```

이 정리는 `finally`에서 실행되므로 정상, 업무 예외, 시스템 예외 모두 정리 대상입니다.

## 8. multipart 처리

`Content-Type`이 `multipart/`로 시작하면 별도 경로로 처리합니다.

```text
X-GUID 추출
  ↓
최소 hdr_nhnis 생성
  ↓
ServiceContext 생성
  ↓
filterChain.doFilter
```

그런데 현재 구현에는 중요한 보안 문제가 있습니다.

### JWT 검증 우회 가능성

multipart 분기가 JWT 검증보다 먼저 실행됩니다.

```java
if (contentType.startsWith("multipart/")) {
    // 바로 chain.doFilter
} else {
    // 여기에서만 JWT 검증
}
```

따라서 현재 코드 기준으로는:

```text
비-local + multipart 요청
→ Authorization 없어도 DefaultFilter 통과
```

파일 업로드 URL이 존재하거나 multipart를 허용한다면 JWT 검증을 공통 분기 앞으로 이동해야 합니다. 현재 분석에서 가장 우선순위가 높은 개선 항목입니다.

## 9. OPTIONS와 CORS

OPTIONS 요청은 필터를 실행하지 않습니다.

```java
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    return "OPTIONS".equalsIgnoreCase(request.getMethod());
}
```

브라우저 preflight 요청은 Body와 JWT가 없기 때문에 올바른 처리입니다.

CORS 허용 출처는 현재 다음 두 개입니다.

```yaml
http://localhost:8090
http://127.0.0.1:8090
```

CORS 설정: [WebMvcConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/WebMvcConfig.java:20>)

다만 `DefaultFilter`가 Spring Security CORS 필터보다 앞에서 `sendError()`를 실행할 가능성이 있으므로, JWT·JSON 오류 응답에는 CORS 헤더가 붙지 않을 수 있습니다. 브라우저에서는 실제 401/400 내용 대신 CORS 오류처럼 보일 수 있습니다.

## 10. 오류 처리

| 조건                          | 상태 |
| ----------------------------- | ---: |
| Bearer Token 없음             |  401 |
| JWT 서명·만료 검증 실패       |  401 |
| Access Token이 아님           |  401 |
| Body 없음                     |  400 |
| JSON 파싱 실패                |  400 |
| 비-local에서 `hdr_nhnis` 없음 |  400 |
| 필터 내부 일반 예외           |  400 |

모든 오류는 `response.sendError()`로 처리합니다.

따라서 다음 경로를 거치지 않습니다.

```text
GlobalExceptionHandler
ResponseBodyArgumentResolver
NH_NIS_ERR_DTO 표준 오류 전문
```

즉, 필터 오류 응답과 업무 오류 응답의 JSON 구조가 다를 수 있습니다.

## 11. 추가 발견 사항

### P0 — multipart JWT 우회

비-local에서도 multipart 요청에는 JWT 검증이 적용되지 않습니다.

권장 방향:

```text
OPTIONS 제외
  ↓
비-local JWT 검증
  ↓
multipart / JSON 분기
```

### P1 — 기존 헤더의 GUID 누락 보완 안 됨

`hdr_nhnis` 자체가 없으면 local에서 GUID를 생성합니다. 하지만 헤더는 존재하고 `std_gbl_id`만 비어 있으면 `enrichMissingSysComm()`은 GUID를 생성하지 않습니다.

그 상태에서 다음 코드를 실행합니다.

```java
String guid = header.getSys_comm().getStd_gbl_id();
ThreadContext.put(GUID, guid);
```

따라서 null MDC 값 처리 과정에서 예외가 발생하거나, GUID 없는 거래가 진행될 가능성이 있습니다.

`fillSysCommFromRequest()`에서 다음 보완이 필요합니다.

```java
if (isBlank(sys.getStd_gbl_id())) {
    sys.setStd_gbl_id(UUID.randomUUID()
            .toString()
            .replace("-", ""));
}
```

### P1 — 모든 URL에 Body 강제

필터 매핑은 `/*`이며 OPTIONS 외의 모든 요청을 처리합니다.

따라서 다음 요청도 Body가 없으면 400이 될 수 있습니다.

```text
GET /actuator/health
GET /favicon.ico
GET /error
정적 리소스
```

온라인 거래 경로만 포함하거나 health/error/static 경로를 명시적으로 제외하는 것이 안전합니다.

### P1 — 필터 오류 응답 비표준

`sendError()` 대신 공통 오류 응답 Writer를 사용하면 UI가 동일한 오류 스키마로 처리할 수 있습니다.

### P2 — `X-Forwarded-For` 신뢰

필터는 `X-Forwarded-For`의 첫 번째 값을 그대로 신뢰합니다. 거래통제를 IP 기준으로 적용한다면 외부 클라이언트가 헤더를 위조하지 못하도록 신뢰할 프록시 구간을 정의해야 합니다.

### P2 — 요청 크기 제한 없음

`readAllBytes()`로 Body 전체를 메모리에 올립니다. 요청 크기 제한이 없으면 대용량 Body로 메모리 압박이 가능합니다.

### P3 — 미사용 의존성

`ClientHttpConnector connector`가 주입되지만 실제로 사용되지 않습니다. 현재는 향후 APIGW/OCR 연계 예약 필드입니다.

## 결론

현재 `DefaultFilter`는 다음 역할을 담당하는 핵심 시스템 선처리 계층입니다.

```text
DefaultFilter
= 요청 Body 보존
+ 인증
+ 공통 헤더 준비
+ 요청 컨텍스트 생성
+ 로그 추적값 설정
```

기본 JSON 거래 흐름은 정상적으로 구성되어 있습니다. 다만 운영 적용 전에는 최소한 다음 세 항목을 보완해야 합니다.

1. multipart 요청에도 JWT 검증 적용
2. 기존 헤더에서 GUID가 비어 있을 때 강제 채번
3. 필터 오류 응답의 CORS 및 표준 오류 전문 통일

현재 해당 기능을 직접 검증하는 `DefaultFilter` 테스트는 검색되지 않았습니다. 이번 요청은 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
