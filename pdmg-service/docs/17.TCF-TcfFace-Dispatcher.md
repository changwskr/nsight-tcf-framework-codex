# 17. TCF — TcfFacade · TransactionDispatcher (PDMG)

기준일: 2026-08-09  
대상: `pdmg-fw` `TcfFacade`, `TransactionDispatcher`, `TransactionContext`  
관련: [16.TCF-OnlineTransactionController.md](./16.TCF-OnlineTransactionController.md) · [18.Business-Handler.md](./18.Business-Handler.md) · [09.서비스ID.md](./09.서비스ID.md) · [11.예외처리.md](./11.예외처리.md)

> 파일명 `TcfFace`는 오기이며, 클래스명은 **`TcfFacade`** 이다.

---

## 1. 역할

OnlineController와 업무 Handler 사이의 **TCF 코어 연결층**이다.

```text
OnlineTransactionController
  → TcfFacade.process(serviceId, dtoBody)     ★
       → TransactionContext.fromCurrent(serviceId)
       → OnlineTimeoutExecutor.execute(() -> …)  ★ 공통 timeout
            → TransactionDispatcher.dispatch(…)
                 → TransactionHandler.handle(dtoBody, context)
                      → 업무 *Facade (@Transactional REQUIRED)
```

| 컴포넌트 | 한다 | 하지 않는다 |
|----------|------|-------------|
| **TcfFacade** | Context 생성, **TimeoutExecutor** 위임, 경과 로그 | SQL, ImageLog, 응답 봉투 |
| **OnlineTimeoutExecutor** | Worker 실행 · **외부 TX** · deadline · 504/503 | 업무 분기 |
| **TransactionDispatcher** | serviceId→Handler 맵, `handle` 호출 | 업무 분기(S0/D0 — Handler 몫) |
| **TransactionContext** | serviceId·ServiceContext·시작시각 | 시스템 선후처리 본체 |

활성: `nhnis.fw.tcf.enabled=true` (`@ConditionalOnProperty`).

---

## 2. TcfFacade

FQCN: `nhnis.fw.tcf.core.facade.TcfFacade`

```java
public Object process(String serviceId, Object dtoBody) throws Exception {
    TransactionContext context = TransactionContext.fromCurrent(serviceId);
    Object result = onlineTimeoutExecutor.execute(
        () -> dispatcher.dispatch(serviceId, dtoBody, context));
    // debug: elapsedMs
    return result;
}
```

timeout·TX 정책: [20.타임아웃.md](./20.타임아웃.md) · 설계 [2026-08-09-pdmg-online-timeout-executor-design.md](./2026-08-09-pdmg-online-timeout-executor-design.md)

| 입력 | 의미 |
|------|------|
| `serviceId` | 예: `mgcoa8888S0` (Controller가 확정) |
| `dtoBody` | 전문의 `dto` 노드만 (Map 등) |

| 출력 | 의미 |
|------|------|
| `Object` | 업무 Facade가 반환한 `*DTOout` |

tcf-core의 `TCF.process`를 PDMG에 맞게 단순화한 진입점이다.  
시스템 선후(Filter/Interceptor/Advice)는 **여기서 다시 하지 않는다**.

---

## 3. TransactionContext

FQCN: `nhnis.fw.tcf.core.context.TransactionContext`

Handler·(필요 시) 업무 쪽에서 쓰는 **거래 1건 최소 컨텍스트**.

| 필드/메서드 | 내용 |
|-------------|------|
| `serviceId` | 이번 호출 ID |
| `serviceContext` | `ServiceContextHolder` 스냅샷 (Filter가 만든 것) |
| `startedAtNanos` / `elapsedMs()` | TcfFacade 구간 소요 |
| `getHeader()` / `getGuid()` | ServiceContext 위임 |

```java
TransactionContext.fromCurrent(serviceId)
  // = new TransactionContext(serviceId, ServiceContextHolder.getInstance())
```

시스템 선후·MDC의 주인은 여전히 `ServiceContext` / Interceptor다.  
`TransactionContext`는 Handler가 `context.getServiceId()`로 분기할 때 주로 쓴다.

---

## 4. TransactionDispatcher

FQCN: `nhnis.fw.tcf.core.dispatch.TransactionDispatcher`

### 4.1 기동 시 등록

생성자에서 모든 `TransactionHandler` 빈을 주입받아 맵을 만든다.

```text
for each TransactionHandler:
  for each id in handler.serviceIds():
    handlerMap.put(id, handler)
    중복 id → IllegalStateException (기동 실패)
```

로그 예:

```text
Registered TCF handler. serviceId=mgcoa8888S0 handler=mgcoa8888Handler
TCF dispatcher ready. handlers=N
```

`serviceIds()`가 비면 해당 Handler는 skip + WARN.

### 4.2 `dispatch`

```java
public Object dispatch(String serviceId, Object dtoBody, TransactionContext context)
```

```text
1. serviceId 공백 → ServiceHandlerNotFound("serviceId가 없습니다.")
2. handlerMap.get(serviceId) == null
     → ServiceHandlerNotFound("등록되지 않은 serviceId입니다: …")
3. return handler.handle(dtoBody, context)
```

| 예외 | 이후 |
|------|------|
| `ServiceHandlerNotFound` | `GlobalExceptionHandler` → `NH_NIS_ERR_DTO` (E9999 등) |
| Handler/Facade 업무 예외 | 동일 Advice 경로 · 쓰기면 Facade TX rollback |

조회 API: `handlers()` → 등록 맵 불변 복사.

---

## 5. TransactionHandler (계약만)

인터페이스: `nhnis.fw.tcf.core.handler.TransactionHandler`  
구현체는 업무 모듈 `entry.handler.*` ([18](./18.Business-Handler.md)).

| 메서드 | 의미 |
|--------|------|
| `serviceId()` | 단일 거래용 (기본 null) |
| `serviceIds()` | 등록 키 목록 (기본은 serviceId 하나) |
| `handle(dtoBody, context)` | 업무 Facade 호출 |

Dispatcher는 **어느 Handler인지**만 고른다.  
같은 Handler 안 S0/D0 분기는 `context.getServiceId()` + `switch` (Handler 구현).

## 6. 흐름 한눈에

```text
Controller
  tcfFacade.process("mgcoa8888S0", dtoMap)
    │
    ├─ TransactionContext(serviceId, ServiceContext)
    │
    └─ dispatcher.dispatch
          handlerMap["mgcoa8888S0"] = mgcoa8888Handler
          │
          └─ mgcoa8888Handler.handle(dto, ctx)
                switch ctx.serviceId
                  S0 → mgcoa8888Facade.mgcoa8888S0(dto)  ★ @Transactional
                  D0 → …
```

---

## 7. 업무 Facade와의 이름 구분

| 이름 | 계층 | TX |
|------|------|-----|
| **TcfFacade** | FW TCF 코어 | 없음 — 라우팅만 |
| **mgcoa*Facade** | 업무 `application.facade` | **있음** — DB 경계 |

혼동 금지: “Facade”라도 TCF 쪽은 트랜잭션을 열지 않는다.

---

## 8. 신규 거래 시 이 계층에서 할 일

1. 업무 `*Handler`에 `serviceIds()` 추가 (또는 새 Handler)  
2. 기동 로그에 `Registered TCF handler. serviceId=…` 확인  
3. **Dispatcher/TcfFacade 코드 수정 불필요** (스프링이 Handler 빈을 자동 수집)

중복 serviceId로 두 Handler가 등록되면 **애플리케이션 기동 실패**.

---

## 9. 하지 말 것

1. TcfFacade/Dispatcher에 SQL·업무 if  
2. Dispatcher를 우회해 Controller→Service 직호출 (TCF ON)  
3. serviceId 미등록 상태로 UI/URL만 추가  
4. 동일 serviceId를 두 Handler에 등록  
5. TcfFacade에 `@Transactional`을 올려 업무 TX와 섞기

## 11. 요약

```text
TcfFacade     = process(serviceId, dto) → Context + dispatch
Dispatcher    = serviceId → Handler 맵 (기동 시 조립)
TransactionContext = serviceId + ServiceContext + 경과시각

다음: Handler → 업무 Facade(TX) → Service → DAO
```
