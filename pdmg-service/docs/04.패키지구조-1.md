## 분석 결론

[04.패키지구조.md](./04.패키지구조.md)는 현재 `nhnis.mg.co.a.*` 구조만 놓고 보면 대부분 일치합니다.

이전 점검 시점에는 구 패키지(`nhnis.mg.application.*` 등)와 신규 `co.a`가 공존해 AS-IS 문서로는 어긋났지만, **현재 소스에서는 구 패키지가 제거**되었고 업무 코드는 `nhnis.mg.co.a.*`로 통합되어 있습니다.

따라서 이 문서는 더 이상 “신규 목표만”이 아니라 **현재 전체 패키지 구조(AS-IS)** 에 가깝습니다.

다만 문서에 남아 있는 다음 차이는 보정하는 것이 좋습니다.

```text
문서와 다른 점:
  Mapper XML 패턴 표기 (실제는 classpath*:rdw.*/*.xml)
  persistence.file / client / support 를 실구현처럼 보이게 한 표현
  pdmg-fw 의 com.ims.superspring.* · tcf.timeout 루트 미언급
```

문서가 금지한 축 없는 패키지는 **현재 소스에 없습니다.**

```text
문서상 금지:
  nhnis.mg.application.*
  nhnis.mg.entry.*
  nhnis.mg.config.*

현재 실제:
  (없음 — 제거 완료)
  nhnis.mg 에는 Boot만
  업무는 nhnis.mg.co.a.*
```

## 1. 현재 실제 패키지 구조

현재 `pdmg-service` 업무 패키지는 **`nhnis.mg.co.a` 단일 축**입니다.

### 기존 패키지 구조 (제거됨)

다음 구조는 더 이상 소스에 없습니다.

```text
nhnis.mg
├─ application
│  ├─ dto
│  └─ service
├─ entry
│  ├─ controller
│  ├─ facade
│  ├─ handler
│  └─ aspect
├─ persistence
│  └─ dao
├─ config
├─ client
└─ support
```

### 현재 패키지 구조

```text
nhnis.mg                    ← Boot만 (PdmgApplication, ServletInitializer)
nhnis.mg.co.a
├─ entry
│  ├─ handler
│  └─ aspect
├─ application
│  ├─ controller
│  ├─ facade
│  └─ service
├─ dto
├─ persistence
│  └─ dao
├─ config
├─ client
└─ support
```

현재 문서에는 위 신규(현재) 구조가 기술되어 있습니다.

문서의 다음 설명은 **현재 소스와 일치**합니다.

> `nhnis.mg`에는 Boot만 직접 둔다.

실제로 `nhnis.mg` 바로 아래에는 Boot만 있고, 업무 코드는 다음만 존재합니다.

```text
nhnis.mg.co.a.entry.*
nhnis.mg.co.a.application.*
nhnis.mg.co.a.dto.*
nhnis.mg.co.a.persistence.*
nhnis.mg.co.a.config.*
nhnis.mg.co.a.client.*
nhnis.mg.co.a.support.*
```

## 2. Component Scan 영향

현재 Boot 설정은 다음과 같습니다.

```java
@SpringBootApplication(scanBasePackages = "nhnis")
@ConfigurationPropertiesScan("nhnis")
```

따라서 Spring은 다음을 스캔합니다.

```text
nhnis.fw.*
nhnis.mg.*          ← Boot + nhnis.mg.co.a.*
```

구 패키지가 없으므로 **동일 Bean 이름 이중 등록은 현재 발생하지 않습니다.**

예를 들어 Service는 다음만 존재합니다.

```text
nhnis.mg.co.a.application.service.mgcoa5530Service
```

기본 Spring Bean 이름:

```text
mgcoa5530Service
```

다만 **업무 축을 복제·병행**하거나 Config를 축마다 복사하면 같은 위험이 다시 생깁니다.

```text
mgcoa8888Service
mgcoa9999Service
BizPrePostAspect
PdmgBizTxFlowAspect
RdwDataSourceConfig
SecurityConfig
WebMvcConfig
MybatisLogInterceptor
```

문서에는 다음 내용을 추가하는 편이 좋습니다.

> 현재는 `co.a` 단일 축이라 Bean 충돌은 없다. 다만 `scanBasePackages="nhnis"`이므로 축·Config를 복제할 때는 동일한 기본 Bean 이름과 `rdwTransactionManager` 등 설정 Bean 충돌을 피해야 한다.

## 3. 문서의 루트 구분 분석

문서는 다음 네 개의 루트를 설명합니다.

| 루트                       | 판단                |
| -------------------------- | ------------------- |
| `nhnis.fw.*`               | 맞음                |
| `nhnis.mg` Boot만          | **맞음 (현재 AS-IS)** |
| `nhnis.mg.[업무].[세부].*` | 맞음 (`co.a`)       |
| `nhnis.mg.ui.*`            | `pdmg-ui` 기준 맞음 |

`pdmg-fw`에는 `nhnis.fw.*` 외에도 호환 DTO를 위한 다음 루트가 있습니다.

```text
com.ims.superspring.*
```

구체적으로 다음과 같은 타입이 존재합니다.

```text
com.ims.superspring.dto.DataObject
com.ims.superspring.dto.engine.base.JsonMessage
com.ims.superspring.dto.engine.exception.*
```

PDMG DTO가 이 타입들을 상속하므로 단순히 무관한 외부 패키지는 아닙니다.

정확한 루트 표는 다음처럼 구성해야 합니다.

| 루트                    | 모듈           | 역할                                         |
| ----------------------- | -------------- | -------------------------------------------- |
| `nhnis.fw.commons.*`    | `pdmg-fw`      | Filter, Context, ImageLog, 전문, 공통 유틸   |
| `nhnis.fw.tcf.*`        | `pdmg-fw`      | Controller, Dispatcher, Handler SPI, Timeout |
| `nhnis.fw.exception.*`  | `pdmg-fw`      | 예외 및 오류 응답 (`result` 전문 조립 포함)  |
| `com.ims.superspring.*` | `pdmg-fw`      | 레거시 전문 DTO 호환                         |
| `nhnis.mg`              | `pdmg-service` | Boot만                                       |
| `nhnis.mg.co.a.*`       | `pdmg-service` | 업무 축 구조 (현재 유일)                     |
| `nhnis.mg.ui.*`         | `pdmg-ui`      | UI                                           |

## 4. 패키지 경로 규칙

문서가 정의한 경로는 다음과 같습니다.

```text
nhnis.mg.[업무구분].[세부업무구분].[계층].[세부패키지]
```

예:

```text
nhnis.mg.co.a.entry.handler
nhnis.mg.co.a.application.service
nhnis.mg.co.a.persistence.dao
```

이 규칙은 **현재 소스에 실제로 적용**되어 있습니다.

서비스 ID, Java 패키지와 Mapper 디렉터리 대응도 현재 `co.a` 구조에서 일치합니다.

```text
서비스 ID 접두 : mgcoa
Java 업무 루트 : nhnis.mg.co.a
Mapper 경로    : rdw.mg.co.a/
```

정확한 상태는:

```text
현재 구조: co.a 업무·세부 축 적용 (단일)
구 구조(축 없음): 제거됨
```

입니다.

## 5. 현재 샘플 트리의 정확성

문서에 기술된 샘플 트리는 대부분 실제 파일과 일치합니다.

```text
co/a
├─ entry/handler
├─ entry/aspect
├─ application/controller
├─ application/facade
├─ application/service
├─ dto
├─ persistence/dao
├─ client
├─ config
└─ support
```

다만 다음 항목은 실제 구현과 다릅니다.

### `persistence.file`

문서에는 다음 패키지가 있다고 되어 있습니다.

```text
persistence/file
```

현재 확인되는 Java 소스에는 이 패키지의 클래스나 `package-info.java`가 없습니다. (빈 디렉터리만 있을 수 있음)

따라서 다음 중 하나로 표현해야 합니다.

```text
현재 구현:
  persistence.dao만 존재

확장 후보:
  persistence.file
```

`persistence.file`을 현재 패키지 트리에 실재하는 것처럼 표시하면 안 됩니다.

### Client와 Support

현재 패키지의 Client와 Support는 실질적인 구현이 아니라 `package-info.java` 수준입니다.

```text
nhnis.mg.co.a.client
nhnis.mg.co.a.support
```

따라서 문서에 다음 상태 표시가 필요합니다.

```text
client  : 확장 자리만 존재
support : 확장 자리만 존재
```

## 6. 패키지 배치와 저장소 표준 충돌

문서에서는 다음 패키지를 금지합니다.

```text
entry.facade
entry.controller
```

그리고 다음을 사용하도록 규정합니다.

```text
application.facade
application.controller
```

그러나 저장소 루트 `AGENTS.md`의 공식 아키텍처 규칙은 반대입니다.

```text
entry/handler
  → entry/facade
  → application/service
  → application/rule
  → persistence/dao 또는 persistence/mapper
```

Controller도 저장소 표준에서는 다음 위치입니다.

```text
entry.web
```

따라서 다음 문서 규칙은 저장소 공식 규칙과 충돌합니다.

| 컴포넌트   | 04 문서                  | 저장소 공식 규칙         |
| ---------- | ------------------------ | ------------------------ |
| Handler    | `entry.handler`          | `entry.handler`          |
| Facade     | `application.facade`     | `entry.facade`           |
| Controller | `application.controller` | `entry.web`              |
| Service    | `application.service`    | `application.service`    |
| Rule       | 없음                     | `application.rule`       |
| DAO/Mapper | `persistence.dao`        | `persistence.dao/mapper` |

현재 소스는 문서대로 `application.facade`, `application.controller`를 사용하고 있습니다. 즉:

```text
04 문서 = 현재 PDMG 소스 구조
저장소 표준 = 현재 소스와 다른 권장 구조
```

문서에서는 `entry.facade`와 `entry.controller`를 절대적인 금지 패키지로 쓰면 안 됩니다.

특히 `entry.facade`는 저장소에서 권장하는 패키지입니다.

정확한 표현은 다음과 같습니다.

> 현재 PDMG 소스는 `application.facade`와 `application.controller`를 사용한다. 다만 저장소 공통 아키텍처는 `entry.facade`와 `entry.web`을 권장하므로, 문서에는 “PDMG 배치 기준”임을 명시하는 것이 좋다.

## 7. Application Rule 누락

저장소 아키텍처에는 다음 계층이 있습니다.

```text
application.rule
```

현재 `co.a` 패키지에는 Rule이 없습니다.

업무 검증과 계산은 Service가 직접 수행합니다.

예:

```text
Service
  → 입력값 검증
  → 검색 조건 구성
  → 페이징 계산
  → DAO 호출
  → 응답 DTO 조립
```

따라서 문서에는 다음을 구분해야 합니다.

```text
AS-IS:
  application.rule 없음
  Service가 검증과 계산 담당

권장 구조:
  application.rule 추가 가능
  Service는 업무 흐름 조정
  Rule은 검증과 계산
```

## 8. Mapper Scan 분석

현재 `RdwDataSourceConfig`는 다음 DAO 패키지를 스캔합니다.

```java
@MapperScan(
    basePackages = "nhnis.mg.co.a.persistence.dao",
    sqlSessionTemplateRef = "rdwSqlSessionTemplate"
)
```

이 부분은 문서와 일치합니다.

구 패키지용 `@MapperScan(basePackages = "nhnis.mg.persistence.dao")` 설정은 **더 이상 없습니다.**

DataSource·TX Bean도 `co.a.config`의 다음 이름만 선언됩니다.

```text
rdwDataSource
rdwSqlSessionFactory
rdwSqlSessionTemplate
rdwTransactionManager
```

문서에는 현재 상태를 다음과 같이 표시하면 됩니다.

```text
현재 Mapper Scan:
  nhnis.mg.co.a.persistence.dao

현재 XML 디렉터리:
  rdw.mg.co.a/

업무 축 추가 시:
  @MapperScan basePackages 확장 또는 공통 Config 유지
  (Config 복제 시 Bean 이름 충돌 주의)
```

## 9. Mapper XML 경로 설명 오류

문서에는 Mapper XML 경로가 다음과 같이 기술되어 있습니다.

```text
classpath*:rdw.mg.co.a/**/*.xml
```

하지만 실제 `RdwDataSourceConfig`의 패턴은 다음입니다.

```java
private static final String MAPPER_LOCATION_PATTERN =
    "classpath*:rdw.*/*.xml";
```

즉, 현재 실제 패턴은 특정 `co.a` 축만 하드코딩하지 않습니다.

```text
classpath*:rdw.*/*.xml
```

이 패턴은 다음과 같은 디렉터리를 모두 대상으로 할 수 있습니다.

```text
rdw.mg.co.a/*.xml
rdw.mg.ic.b/*.xml
rdw.기타축/*.xml
```

또한 현재 패턴은 `**/*.xml` 재귀 패턴이 아니라 바로 아래의 `*.xml`입니다.

따라서 문서의 설정 표는 다음으로 수정해야 정확합니다.

| 항목                  | 실제 값                         |
| --------------------- | ------------------------------- |
| Mapper Interface Scan | `nhnis.mg.co.a.persistence.dao` |
| Mapper XML Scan       | `classpath*:rdw.*/*.xml`        |
| 현재 XML 디렉터리     | `rdw.mg.co.a/`                  |

## 12. 업무 축 추가 방식의 문제

문서는 새로운 업무 축 `ic.b`를 추가할 때 다음 구조를 제안합니다.

```text
nhnis.mg.ic.b
├─ entry
├─ application
├─ dto
├─ persistence
├─ config
└─ support
```

패키지 자체는 확장 가능합니다.

하지만 업무 축마다 `RdwDataSourceConfig`를 복제하면 다음 Bean 이름이 충돌합니다.

```text
rdwDataSource
rdwSqlSessionFactory
rdwSqlSessionTemplate
rdwTransactionManager
```

따라서 업무 축 추가 시 Config 전략을 먼저 결정해야 합니다.

### 같은 DB를 사용하는 경우

공통 DataSource 설정 하나를 사용하고 Mapper Scan 범위만 통합하는 것이 적절합니다.

```java
@MapperScan(
    basePackages = {
        "nhnis.mg.co.a.persistence.dao",
        "nhnis.mg.ic.b.persistence.dao"
    }
)
```

또는 공통 상위 marker package를 사용합니다.

### 서로 다른 DB를 사용하는 경우

각 축의 Bean 이름을 분리해야 합니다.

```text
coRdwDataSource
coRdwTransactionManager

icRdwDataSource
icRdwTransactionManager
```

그리고 `@Qualifier`와 `transactionManager` 이름도 맞춰야 합니다.

문서의:

> Config를 업무마다 둘지 팀 정책으로 정한다.

만으로는 부족합니다. 동일 Bean 이름 충돌 방지 기준이 필요합니다.

## 14. `pdmg-fw` 패키지 구조

`pdmg-fw`의 실제 핵심 구조는 다음과 같습니다.

```text
nhnis.fw
├─ commons
│  ├─ apigw
│  ├─ configuration
│  ├─ context
│  ├─ dto
│  ├─ exception
│  ├─ filter
│  ├─ imagelog
│  ├─ interceptor
│  ├─ jwt
│  ├─ log
│  ├─ message
│  ├─ resolver
│  ├─ transaction
│  └─ util
├─ exception
└─ tcf
   ├─ core
   │  ├─ context
   │  ├─ dispatch
   │  ├─ facade
   │  └─ handler
   ├─ timeout
   └─ web
```

그리고 레거시 DTO 호환 패키지가 별도로 있습니다.

```text
com.ims.superspring.dto.*
```

현재 `04` 문서는 `pdmg-service` 중심이기 때문에 `pdmg-fw` 구조를 자세히 설명하지 않습니다. 그러나 Boot가 두 모듈을 함께 스캔한다는 점을 설명하려면 최소한 다음 구분은 필요합니다.

```text
nhnis.fw.commons.* = 범용 공통 기능 (ImageLog 포함, 업무 TX와 별개)
nhnis.fw.tcf.*     = TCF 실행 기능 (timeout 포함)
nhnis.fw.exception = 공통 예외 응답 (오류는 result 키)
com.ims.*          = 전문 DTO 호환
```

## 15. 현재 패키지 구조의 핵심 이슈

우선순위대로 정리하면 다음과 같습니다.

### 해소됨 (이전 위험)

1. 구·신 패키지 동시 존재 → **제거 완료**
2. 동일 Service / Aspect / Config Bean 이중 등록 → **현재 없음**
3. 기존·신규 `RdwDataSourceConfig` 이중 선언 → **현재 없음**
4. 기존·신규 Mapper Scan 동시 활성 → **현재 없음**

### 아키텍처 정합성 (유지)

5. `application.facade`가 저장소 권장 `entry.facade`와 불일치
6. `application.controller`가 권장 `entry.web`과 불일치
7. `application.rule` 누락
8. `entry.facade`를 금지한 문서 규칙이 저장소 공통 규칙과 충돌 → “PDMG 배치”로 한정 표기 권장

### 문서 정확성 (보정 필요)

9. 실제 Mapper XML 패턴이 문서와 다름 (`classpath*:rdw.*/*.xml`)
10. `persistence.file`은 현재 구현이 아닌 확장 후보
11. `client` / `support`는 자리만 존재
12. `pdmg-fw`의 `com.ims.superspring.*` · `tcf.timeout` · `commons.imagelog` 호환/공통 루트 보강

### 확장 시 주의

13. 업무 축 추가 시 Config 복제로 인한 Bean 이름 충돌
14. `@MapperScan` / Pointcut / XML namespace 동기화

## 최종 평가

이 문서의 정확도는 관점에 따라 달라집니다.

```text
nhnis.mg.co.a 구조 설명: 약 90%
현재 pdmg-service 전체 AS-IS 설명: 약 85~90%
저장소 공식 권장 구조와의 일치: 약 60%
```

가장 먼저 바로잡아야 하는 부분은 다음입니다.

```text
Mapper XML 실제 패턴을 classpath*:rdw.*/*.xml 로 정정할 것
persistence.file / client / support 를 확장 자리로 명시할 것
entry.facade 금지를 “PDMG 배치 기준”으로 한정할 것
pdmg-fw 루트(commons.imagelog, tcf.timeout, com.ims.superspring)를 보강할 것
```

구·신 공존·이중 Config 충돌은 **현재 AS-IS 기준으로는 더 이상 핵심 위험이 아닙니다.**

이번 분석에서는 소스 트리와 설정을 대조했으며, 본 검증 문서의 문구 스타일은 유지한 채 잘못된 전제만 수정했습니다.
