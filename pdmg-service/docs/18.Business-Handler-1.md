## 18. Business Handler 분석 결과

Business Handler는 TCF가 선택한 serviceId를 해당 업무 Facade 메서드에 연결하는 업무 진입 라우터입니다.

핵심 역할은 다음 두 가지입니다.

```text
serviceIds() → 처리 가능한 거래 ID 등록
handle()     → serviceId에 맞는 업무 Facade 호출
```

전체 위치:

```text
OnlineTransactionController
  ↓
TcfFacade
  ↓
OnlineTimeoutExecutor
  ↓
TransactionDispatcher
  ↓
Business Handler                 ★ 현재 위치
  ↓
Business Facade
  ↓
Service
  ↓
DAO
```

---

## 1. Handler 인터페이스

공통 계약은 [TransactionHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/core/handler/TransactionHandler.java:22>)에 있습니다.

```java
public interface TransactionHandler {

    default String serviceId() {
        return null;
    }

    default Collection<String> serviceIds() {
        String id = serviceId();
        return id == null
                ? List.of()
                : List.of(id);
    }

    Object handle(
            Object dtoBody,
            TransactionContext context)
            throws Exception;
}
```

### 입력값

| 인자      | 내용                               |
| --------- | ---------------------------------- |
| `dtoBody` | 요청 전문의 `dto` 부분             |
| `context` | serviceId, GUID, ServiceContext 등 |
| 반환값    | 업무 Facade가 반환한 DTOout        |

Handler는 `hdr_nhnis`가 포함된 전체 전문을 받지 않습니다.

```json
{
  "hdr_nhnis": {},
  "dto": {
    "customerId": "10001"
  }
}
```

Handler가 받는 `dtoBody`는 다음 부분입니다.

```json
{
  "customerId": "10001"
}
```

## 2. 활성 조건

모든 PDMG Handler에는 다음 조건이 있습니다.

```java
@Component
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "true"
)
```

따라서:

| 설정                | Handler       |
| ------------------- | ------------- |
| `tcf.enabled=true`  | 생성          |
| `tcf.enabled=false` | 생성하지 않음 |

TCF OFF에서는 업무별 Controller가 Service를 직접 호출하므로 Handler가 사용되지 않습니다.

## 3. 현재 Handler 구성

패키지:

```text
nhnis.mg.co.a.entry.handler
```

현재 4개 Handler가 총 8개 serviceId를 등록합니다.

| Handler            | 등록 serviceId                                             |
| ------------------ | ---------------------------------------------------------- |
| `mgcoa5530Handler` | `mgcoa5530S0`                                              |
| `mgcoa8888Handler` | `mgcoa8888S0`, `mgcoa8888D0`                               |
| `mgcoa9999Handler` | `mgcoa9999S0`                                              |

구조는 “프로그램 식별번호 하나당 Handler 하나”입니다.

```text
mgcoa9000S0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
       ↓
mgcoa9000Handler 하나
```

거래마다 Handler를 따로 만들지 않는 현재 방식은 저장소 아키텍처 규칙과 일치합니다.

## 4. 기동 시 등록

Spring이 모든 `TransactionHandler` Bean을 Dispatcher에 주입합니다.

```java
public TransactionDispatcher(
        List<TransactionHandler> handlers)
```

Dispatcher는 Handler의 `serviceIds()`를 읽어 Map을 만듭니다.

```text
handlerMap

mgcoa5530S0 → mgcoa5530Handler
mgcoa8888S0 → mgcoa8888Handler
mgcoa8888D0 → mgcoa8888Handler
mgcoa9999S0 → mgcoa9999Handler
mgcoa9000S0 → mgcoa9000Handler
mgcoa9000C0 → mgcoa9000Handler
mgcoa9000U0 → mgcoa9000Handler
mgcoa9000D0 → mgcoa9000Handler
```

### 중복 등록

두 Handler가 같은 ID를 등록하면 기동이 실패합니다.

```text
Handler A → mgcoa9000S0
Handler B → mgcoa9000S0
→ IllegalStateException
```

실행 중 잘못된 Handler를 선택하지 않고 기동 단계에서 문제를 발견하는 것은 적절합니다.

## 7. Dispatcher와 Handler의 역할 차이

두 단계에서 serviceId를 확인합니다.

```text
TransactionDispatcher
  → serviceId에 해당하는 Handler 선택

Business Handler
  → Handler 내부에서 Facade 메서드 선택
```

예:

```text
serviceId = mgcoa9000U0

Dispatcher:
  mgcoa9000Handler 선택

mgcoa9000Handler:
  U0 case 선택

Facade:
  mgcoa9000Facade.mgcoa9000U0(dtoBody)
```

Dispatcher에 업무별 분기를 넣지 않고 Handler가 담당하는 현재 구조는 적절합니다.

---

## 8. Handler와 Facade 관계

Handler는 대응하는 업무 Facade 하나만 생성자 주입으로 받습니다.

```java
private final mgcoa9000Facade facade;

public mgcoa9000Handler(
        mgcoa9000Facade facade) {
    this.facade = facade;
}
```

권장 호출 방향:

```text
Handler → Facade → Service → DAO
```

현재 Handler는 다음 규칙을 지키고 있습니다.

- DAO 직접 호출 없음
- Mapper 직접 호출 없음
- Service 직접 호출 없음
- SQL 없음
- DTO 변환 없음
- 업무 계산 없음
- Facade 메서드만 호출

---

## 9. DTO 변환 위치

Handler는 `Object dtoBody`를 그대로 Facade에 전달합니다.

```java
facade.mgcoa9000C0(dtoBody);
```

실제 타입 변환은 업무 Facade에서 수행합니다.

```java
mgcoa9000C0DTOin input =
        objectMapper.convertValue(
            dtoBody,
            mgcoa9000C0DTOin.class);
```

현재 구조:

```text
Controller
  dto Map 추출
    ↓
Handler
  Object 그대로 전달
    ↓
Facade
  Object → DTOin 변환
    ↓
Service
  DTOin 사용
```

Handler를 단순 라우터로 유지한다는 점에서는 적절합니다.

다만 `Object` 기반 계약이므로 컴파일 시 타입 검증은 되지 않습니다. 잘못된 Map 구조는 Facade 실행 시점에야 발견됩니다.

장기적으로는 Handler에서 변환하지 않더라도 거래별 입력 타입 정보를 명시하는 계약을 고려할 수 있습니다.

## 10. 트랜잭션 범위

Handler 자체에는 `@Transactional`이 없습니다.

하지만 현재 timeout ON에서는 Handler가 이미 시작된 트랜잭션 안에서 실행됩니다.

```text
TransactionTemplate BEGIN
  ↓
TransactionDispatcher
  ↓
Business Handler                   TX 안
  ↓
Business Facade @Transactional     기존 TX 참여
  ↓
Service
  ↓
DAO
```

따라서 다음 표현이 정확합니다.

```text
Handler가 트랜잭션을 시작하지는 않는다.
하지만 Handler는 이미 열린 트랜잭션 안에서 실행된다.
```

### timeout OFF

```text
TcfFacade
  ↓
SyncOnlineTimeoutExecutor
  ↓
Dispatcher
  ↓
Handler                            TX 밖
  ↓
Facade @Transactional             여기서 TX 시작
  ↓
Service → DAO
```

이 경우 Handler의 Facade 호출 직전까지는 트랜잭션 밖입니다.

## 11. Handler 예외와 롤백

### 등록되지 않은 serviceId

Dispatcher 단계에서 실패합니다.

```java
throw new ServiceHandlerNotFound(
    "등록되지 않은 serviceId입니다: " + serviceId
);
```

Handler는 호출되지 않습니다.

### 등록됐지만 Handler 분기가 없는 경우

```java
serviceIds():
  mgcoa9000A0 등록

handle():
  A0 case 누락
```

이 경우 Dispatcher는 `mgcoa9000Handler`를 정상 선택하지만 Handler의 `default`에서 실패합니다.

```java
throw new ServiceHandlerNotFound(
    "mgcoa9000Handler 미지원 serviceId: ..."
);
```

timeout ON에서는 이 예외가 worker의 `TransactionTemplate` 밖으로 전달되어 rollback됩니다.

다만 Handler가 Facade를 호출하기 전에 발생한 예외이므로 실제 DB 변경은 시작되지 않았을 가능성이 큽니다.

## 12. serviceId 이중 관리 문제

현재 같은 ID가 두 군데에 선언됩니다.

```java
serviceIds():
    List.of(S0, C0, U0, D0)

handle():
    switch(context.getServiceId()) {
        case S0 ...
        case C0 ...
        case U0 ...
        case D0 ...
    }
```

따라서 다음 불일치가 생길 수 있습니다.

### 등록만 있고 분기 없음

```text
serviceIds에 A0 추가
switch에는 A0 누락

→ Dispatcher 등록 성공
→ 실행 시 Handler default 오류
```

### 분기는 있지만 등록 없음

```text
switch에 A0 추가
serviceIds에는 A0 누락

→ Dispatcher가 Handler를 찾지 못함
→ switch까지 도달하지 못함
```

테스트로 두 목록이 일치하는지 검증해야 합니다.

더 구조적으로는 serviceId와 실행 함수를 하나의 Map으로 관리할 수 있지만, 메서드 참조의 checked exception과 Bean 초기화 복잡도를 고려해야 합니다. 현재 거래 수에서는 상수+목록+switch도 충분히 읽기 쉽습니다.

## 13. Dispatcher serviceId와 Context serviceId

Dispatcher는 메서드 인자로 받은 serviceId로 Handler를 찾습니다.

```java
handlerMap.get(serviceId);
```

Handler는 `TransactionContext`의 serviceId로 다시 분기합니다.

```java
context.getServiceId();
```

현재 `TcfFacade`에서는 두 값이 동일하게 생성됩니다.

```java
TransactionContext context =
        TransactionContext.fromCurrent(serviceId);

dispatcher.dispatch(
        serviceId,
        dtoBody,
        context);
```

하지만 Dispatcher API 자체는 서로 다른 값을 받을 수 있습니다.

```text
dispatch serviceId = mgcoa9000S0
context serviceId  = mgcoa9000D0
```

이 경우 Dispatcher는 `mgcoa9000Handler`를 선택하고 Handler는 D0 삭제를 실행할 수 있습니다.

현재 정상 호출 경로에서는 발생하지 않지만 방어 검증이 필요합니다.

```java
if (!serviceId.equals(
        context.getServiceId())) {
    throw new IllegalArgumentException(
        "Dispatcher와 Context의 serviceId가 다릅니다."
    );
}
```

또는 Handler가 별도로 Context serviceId를 읽지 않도록 계약을 단순화할 수 있습니다.

## 15. 하지 않아야 할 구현

Handler에 다음 코드를 넣는 것은 현재 아키텍처와 맞지 않습니다.

```java
@Transactional
public Object handle(...) {
    dao.insert(...);
    mapper.select(...);
    validateBusinessRule(...);
}
```

Handler가 커지면 라우팅과 업무 책임이 섞입니다.

정상 구조:

```java
public Object handle(...) {
    return switch (context.getServiceId()) {
        case S0 -> facade.select(dtoBody);
        case C0 -> facade.create(dtoBody);
        default -> throw ...;
    };
}
```

## 16. 현재 점검 결과

| 우선순위 | 발견 사항                                 | 판단                      |
| -------- | ----------------------------------------- | ------------------------- |
| 정상     | 한 프로그램당 Handler 하나                | 아키텍처 규칙 준수        |
| 정상     | Handler가 Facade만 호출                   | 책임 분리 적절            |
| 정상     | 생성자 주입 사용                          | 적절                      |
| 정상     | TCF ON에서만 Handler 활성                 | Controller 모드와 일치    |
| 정상     | 중복 serviceId 기동 차단                  | 적절                      |
| P1       | `serviceIds()`와 `switch` 이중 관리       | 불일치 테스트 필요        |
| P1       | Dispatcher ID와 Context ID 일치 검증 없음 | 방어 검증 필요            |
| P1       | `Object dtoBody` 계약                     | 타입 안정성 부족          |
| P1       | serviceId 형식·공백 검증 없음             | Dispatcher 기동 검증 필요 |
| P2       | 단일 거래도 등록과 분기를 중복 확인       | 단순화 가능               |
| P2       | `ServiceHandlerNotFound`가 HTTP 500       | 400/404 검토              |
| 테스트   | Handler 전용 테스트 검색 안 됨            | 신규 테스트 필요          |

## 결론

현재 Business Handler는 다음 역할로 잘 제한되어 있습니다.

```text
Business Handler
  = 프로그램 단위 거래 목록 등록
  + serviceId별 Facade 메서드 선택
```

트랜잭션·DTO 변환·업무 처리·SQL은 Handler 책임이 아닙니다.

```text
Handler          라우팅
Facade           DTO 변환 + TX
Service          업무 흐름
DAO / Mapper     데이터 접근
```

운영 안정성을 위해 우선 추가할 검증은 다음입니다.

1. `serviceIds()`의 모든 ID가 `handle()` 분기에 존재하는지 테스트
2. Dispatcher serviceId와 Context serviceId 일치 검증
3. serviceId null·공백·형식 검증
4. Handler별 Facade 호출 테스트
5. 미지원 ID의 오류 상태를 400/404로 조정

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
