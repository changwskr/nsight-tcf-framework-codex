# 23. DAO 분석

## 1. 결론

현재 PDMG DAO는 MyBatis Mapper 인터페이스 방식으로 구현되어 있으며, Java 구현 클래스 없이 Mapper XML과 연결됩니다.

```text
Service
→ DAO 인터페이스
→ MyBatis Proxy
→ Mapper XML
→ RDW DataSource
→ DB
```

전체 구성은 정상입니다.

| 점검 항목                | 상태                        |
| ------------------------ | --------------------------- |
| DAO 인터페이스 4개       | 정상                        |
| `@RDWMapper` 등록        | 정상                        |
| Mapper Scan              | 정상                        |
| DAO namespace와 XML 연결 | 모두 일치                   |
| DAO 메서드와 XML ID      | 모두 일치                   |
| SQL 파라미터 바인딩      | `#{}` 사용, 정상            |
| RDW 트랜잭션 참여        | 정상                        |
| DAO 단위/통합 테스트     | 없음                        |
| SQL Statement Timeout    | 없음                        |
| 다건 IN 목록 상한        | 없음                        |
| 타입 안전성              | `Map<String,Object>`로 약함 |

핵심 위험은 다음 세 가지입니다.

- DAO 및 XML 통합 테스트가 없습니다.
- SQL별 실행 제한시간이 없습니다.
- 다건 삭제 목록 크기 제한이 없어 Oracle `IN` 1,000개 제한에 걸릴 수 있습니다.

# 2. DAO의 위치와 역할

패키지:

```text
nhnis.mg.co.a.persistence.dao
```

현재 DAO는 다음 네 개입니다.

| DAO            | 역할                 |
| -------------- | -------------------- |
| `mgcoa5530DAO` | 마케팅희망고객 조회  |
| `mgcoa8888DAO` | 이미지로그 조회·삭제 |
| `mgcoa9000DAO` | 거래 파라미터 CRUD   |
| `mgcoa9999DAO` | 영업팁 실적 조회     |

DAO의 역할은 다음과 같습니다.

```text
Service가 전달한 파라미터
→ MyBatis SQL Statement 실행
→ 조회 목록·건수·처리 건수 반환
```

DAO가 담당하지 않는 것:

- 업무값 검증
- 페이징 기본값 계산
- DTO 조립
- serviceId 라우팅
- HTTP 응답 생성
- 트랜잭션 시작·커밋
- 업무 결과 코드 결정

이 역할 분리는 적절합니다.

# 3. DAO 등록 방식

## `@RDWMapper`

DAO에는 다음 사용자 정의 Annotation이 붙습니다.

```java
@RDWMapper
public interface mgcoa9000DAO {
}
```

정의: [RDWMapper.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/RDWMapper.java:17>)

```java
@Target(ElementType.TYPE)
@Mapper
public @interface RDWMapper {
}
```

`@RDWMapper`는 MyBatis의 `@Mapper`를 포함한 합성 Annotation입니다.

현재 `@Inherited`도 선언되어 있지만 DAO는 인터페이스이고 `@Inherited`는 클래스 상속에만 의미가 있으므로 실질적인 효과는 없습니다. 기능상 문제는 아닙니다.

## `@MapperScan`

[RdwDataSourceConfig.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/RdwDataSourceConfig.java:27>)가 DAO 패키지를 스캔합니다.

```java
@MapperScan(
    basePackages =
        "nhnis.mg.co.a.persistence.dao",
    sqlSessionTemplateRef =
        "rdwSqlSessionTemplate"
)
```

따라서 실행 시 Spring/MyBatis가 DAO 인터페이스의 Proxy Bean을 만듭니다.

```text
mgcoa9000DAO 인터페이스
→ MyBatis MapperProxy 생성
→ Spring Bean 등록
→ Service에 주입
```

별도의 `mgcoa9000DAOImpl` 클래스는 필요하지 않습니다.

# 4. DataSource 연결

DAO는 다음 구성으로 연결됩니다.

```text
spring.datasource.rdw
→ rdwDataSource
→ rdwSqlSessionFactory
→ rdwSqlSessionTemplate
→ DAO Mapper Proxy
```

### DataSource

```java
@Bean
@Primary
@ConfigurationProperties("spring.datasource.rdw")
public DataSource rdwDataSource() {
    return DataSourceBuilder.create()
        .type(HikariDataSource.class)
        .build();
}
```

### SqlSessionFactory

```java
factory.setDataSource(rdwDataSource);
factory.setMapperLocations(...);
```

### SqlSessionTemplate

```java
@Bean
public SqlSessionTemplate rdwSqlSessionTemplate(
        SqlSessionFactory rdwSqlSessionFactory) {
    return new SqlSessionTemplate(
        rdwSqlSessionFactory);
}
```

### TransactionManager

```java
@Bean
@Primary
public PlatformTransactionManager
        rdwTransactionManager(
            DataSource rdwDataSource) {

    return new DataSourceTransactionManager(
        rdwDataSource);
}
```

MyBatis와 TransactionManager가 동일한 `rdwDataSource`를 사용하므로 DAO는 업무 트랜잭션에 정상 참여합니다.

# 5. Mapper XML 로딩

Mapper 위치 패턴은 다음과 같습니다.

```java
classpath*:rdw.*/*.xml
```

현재 실제 폴더:

```text
src/main/resources/
└─ rdw.mg.co.a/
   ├─ mgcoa5530-ORA.xml
   ├─ mgcoa8888-ORA.xml
   ├─ mgcoa9000-ORA.xml
   └─ mgcoa9999-ORA.xml
```

`classpath*:`이므로 프로젝트 클래스뿐 아니라 의존 JAR 안의 일치하는 XML도 함께 검색합니다.

장점:

- 여러 업무 Mapper를 자동으로 로딩 가능

위험:

- 의존 라이브러리에 같은 namespace와 statement ID가 있으면 충돌 가능
- 예상하지 않은 `rdw.*/*.xml`까지 로딩될 수 있음
- 중복 Mapper가 있으면 기동 단계에서 오류가 발생할 수 있음

현재 PDMG만 고려하면 정상 작동하는 구조입니다.

# 6. namespace 연결

MyBatis는 다음 두 값을 일치시켜 DAO를 찾습니다.

```text
DAO 인터페이스 FQCN
=
XML mapper namespace
```

## `mgcoa5530`

DAO:

```text
nhnis.mg.co.a.persistence.dao.mgcoa5530DAO
```

XML:

```xml
<mapper namespace=
  "nhnis.mg.co.a.persistence.dao.mgcoa5530DAO">
```

## `mgcoa8888`

```text
nhnis.mg.co.a.persistence.dao.mgcoa8888DAO
```

## `mgcoa9000`

```text
nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
```

## `mgcoa9999`

```text
nhnis.mg.co.a.persistence.dao.mgcoa9999DAO
```

네 개 모두 일치합니다.

namespace가 다르면 호출 시 일반적으로 다음 종류의 오류가 발생합니다.

```text
Invalid bound statement (not found)
```

# 8. DAO 메서드 네이밍

현재 형식은 다음과 같습니다.

```text
{서비스ID}_{SQL구분}{순번}
```

예:

```text
mgcoa9000C0_C0
│            │
│            └─ SQL 구분: Create 0번
└─ 서비스 ID
```

| 구분    | 의미                     |
| ------- | ------------------------ |
| `S0_S0` | 조회 거래의 첫 번째 조회 |
| `C0_C0` | 등록 거래의 첫 번째 등록 |
| `U0_U0` | 수정 거래의 첫 번째 수정 |
| `D0_D0` | 삭제 거래의 첫 번째 삭제 |

보조 SQL은 접미사를 사용합니다.

```text
mgcoa9000S0_S0_count
mgcoa9000S0_S0_exists
```

현재 문서와 구현이 일치합니다.

# 9. 입력과 반환 타입

## 입력

모든 DAO가 다음 타입을 받습니다.

```java
Map<String, Object>
```

예:

```java
Map<String, Object> param =
        new HashMap<>();

param.put("txId", txId);
param.put("txName", txName);

dao.mgcoa9000C0_C0(param);
```

XML에서는 Map 키를 그대로 사용합니다.

```xml
#{txId}
#{txName}
```

Map 키에 오타가 있어도 컴파일 오류가 발생하지 않습니다.

예:

```java
param.put("txID", txId);
```

XML:

```xml
#{txId}
```

이 경우 값이 null로 전달되거나 MyBatis 바인딩 오류가 발생할 수 있습니다.

## 반환

| SQL 유형  | 반환 타입                  |
| --------- | -------------------------- |
| 목록 조회 | `List<Map<String,Object>>` |
| count     | `int`                      |
| exists    | `int`                      |
| insert    | `int`                      |
| update    | `int`                      |
| delete    | `int`                      |

C/U/D의 `int`는 영향받은 행 수입니다.

```text
0 = 처리된 행 없음
1 = 한 건 처리
N = N건 처리
```

Service는 이 값을 근거로 최종 업무 결과를 판정해야 합니다.

# 10. 트랜잭션 참여

DAO 자체에는 `@Transactional`이 없습니다. 이 설계는 정상입니다.

### 타임아웃 ON

```text
OnlineTimeoutExecutor
→ TransactionTemplate BEGIN
  → Handler
  → Facade @Transactional(REQUIRED)
  → Service
  → DAO
  → MyBatis
  → SQL
→ COMMIT/ROLLBACK
```

### 타임아웃 OFF

```text
Facade @Transactional BEGIN
→ Service
→ DAO
→ SQL
→ COMMIT/ROLLBACK
```

`SqlSessionTemplate`은 Spring 트랜잭션에 연결된 Connection을 사용합니다.

```text
TransactionManager가 Connection 획득
→ Thread에 Connection 바인딩
→ DAO 호출
→ SqlSessionTemplate이 같은 Connection 사용
```

따라서 한 Service에서 DAO를 여러 번 호출해도 같은 트랜잭션에 참여합니다.

```text
BEGIN
→ exists SELECT
→ INSERT
→ 후처리
→ COMMIT
```

예외가 전파되면 전체가 롤백됩니다.

---

## 11. 트랜잭션이 없는 호출

DAO를 Facade/Executor 트랜잭션 밖에서 직접 호출하면 MyBatis는 SQL 실행을 위해 별도 Connection을 사용합니다.

```text
Controller
→ Service
→ DAO
→ SQL
```

TCF OFF에서 Controller가 Service를 직접 호출하는 현재 호환 경로가 여기에 해당할 수 있습니다.

조회는 상대적으로 영향이 적지만 쓰기 SQL은 자동 커밋될 수 있습니다.

```text
첫 번째 UPDATE 자동 커밋
→ 두 번째 INSERT 실패
→ 첫 번째 UPDATE 복구 불가
```

따라서 쓰기 DAO는 반드시 다음 경로로 호출해야 합니다.

```text
Controller/Handler
→ Facade @Transactional
→ Service
→ DAO
```

# 12. SQL 파라미터 바인딩 보안

현재 XML은 모두 MyBatis 바인딩을 사용합니다.

```xml
#{txId}
#{keyword}
#{guid}
```

`${...}` 문자열 치환은 확인되지 않았습니다.

따라서 현재 구조는 일반적인 SQL Injection에 대해 안전합니다.

```xml
AND T1.TX_ID = #{txId}
```

는 PreparedStatement의 바인딩 파라미터로 처리됩니다.

반면 다음 방식은 위험하지만 현재 사용하지 않습니다.

```xml
AND T1.TX_ID = '${txId}'
```

# 13. LIKE 검색의 의미

다음 검색은 SQL Injection에는 안전합니다.

```xml
LIKE '%' || #{serviceId} || '%'
```

하지만 사용자 입력의 `%`, `_`는 LIKE 와일드카드로 동작합니다.

예:

```text
serviceId = %
→ 사실상 모든 문자열과 일치
```

```text
serviceId = mgcoa____S0
→ _ 하나당 임의 문자 한 글자
```

이것이 고급 검색 기능으로 의도된 것이 아니라면 `%`와 `_`를 escape해야 합니다.

또한 앞뒤 `%` 검색은 일반 B-Tree 인덱스를 효율적으로 사용하기 어렵습니다.

```sql
LIKE '%검색어%'
```

데이터가 많아지면 Full Scan 가능성이 커집니다.

# 14. 페이징 SQL

5530, 8888, 9000은 Oracle ROWNUM 방식입니다.

```sql
SELECT *
FROM (
    SELECT a.*, ROWNUM rnum
    FROM (
        SELECT ...
        FROM ...
        ORDER BY ...
    ) a
    WHERE ROWNUM <= #{offset} + #{pageSize}
)
WHERE rnum > #{offset}
```

논리적으로는 다음 범위를 반환합니다.

```text
offset보다 큰 행
offset + pageSize 이하 행
```

예:

```text
pageNo   = 2
pageSize = 10
offset   = 10

반환 범위 = 11~20번
```

현재 Service 계산과 XML 조건은 일치합니다.

다만 offset이 매우 커지면 DB가 앞부분을 계속 읽어야 하므로 깊은 페이지에서 성능이 저하될 수 있습니다.

# 15. count와 select의 일관성

페이징 조회는 두 SQL로 나뉩니다.

```text
COUNT(*)
→ 목록 SELECT
```

두 SQL 사이에 다른 트랜잭션이 데이터를 추가·삭제하면 다음처럼 달라질 수 있습니다.

```text
COUNT 결과 = 100
다른 거래가 1건 삭제
목록 SELECT 기준 = 99건
```

현재 트랜잭션이 있다고 해도 DB 기본 격리 수준에 따라 두 SQL이 완전히 동일한 스냅샷을 보장한다고 단정할 수 없습니다.

보통 목록 화면에서는 허용 가능한 차이지만, 정확한 정합성이 필요한 거래라면 DB 격리 정책을 검토해야 합니다.

- 시간 컬럼이 문자열
- 길이가 14 이상이어도 잘못된 날짜값이면 `TO_DATE` 오류 가능
- 컬럼에 함수를 적용하므로 인덱스 사용이 어려움
- 대량 데이터에서 행마다 날짜 변환 비용 발생

장기적으로는 요청·응답 시각을 DB 날짜 타입이나 별도 소요시간 숫자 컬럼으로 관리하는 것이 유리합니다.

또한 요청·응답 전문 CLOB을 목록에서 같이 조회합니다.

```sql
REQUEST_MSG
RESPONSE_MSG
```

목록 화면이 전문을 즉시 사용하지 않는다면 목록 조회에서는 제외하고 상세 조회로 분리하는 것이 성능과 메모리에 유리합니다.

## 중복 확인

현재 등록은 다음 흐름입니다.

```text
SELECT COUNT(*) WHERE TX_ID = ?
→ 결과 0이면 INSERT
```

이 방식만으로 동시 요청의 중복을 방지할 수 없습니다.

DB에서 `TX_ID`에 PK 또는 UNIQUE 제약이 필요합니다.

## 수정

```sql
UPDATE TB_MG_TX_PARAM
SET ...
WHERE TX_ID = #{txId}
```

처리 건수가 0이면 수정 대상이 없다는 뜻입니다. Service에서 이를 성공으로 반환할지 `NOT_FOUND`로 반환할지 정책이 필요합니다.

## 키워드 검색

```sql
UPPER(column)
LIKE '%' || UPPER(#{keyword}) || '%'
```

대소문자 무시 검색이지만 일반 인덱스 사용은 어려울 수 있습니다. 데이터 증가 시 Function-Based Index나 검색 정책 변경을 검토해야 합니다.

# 20. 다건 삭제와 Oracle 1,000개 제한

8888과 9000은 `<foreach>`로 IN 조건을 생성합니다.

```xml
WHERE GUID IN (
    #{guid1},
    #{guid2},
    ...
)
```

```xml
WHERE TX_ID IN (
    #{txId1},
    #{txId2},
    ...
)
```

현재 Service에서는 blank 제거와 중복 제거만 하고 최대 개수는 제한하지 않습니다.

Oracle에서는 일반적으로 하나의 `IN` 목록에 1,000개를 초과하면 오류가 발생합니다.

```text
ORA-01795:
maximum number of expressions in a list is 1000
```

따라서 다음 중 하나가 필요합니다.

- 요청 목록 최대 1,000개 제한
- 500~900개 단위로 나눠 반복 실행
- 임시 테이블 활용
- Array Binding/Table Type 사용
- 다건 처리 전용 방식 도입

단순 구조에서는 요청 목록 상한을 500 또는 1,000 미만으로 제한하는 것이 현실적입니다.

# 21. SQL Timeout 부재

현재 Mapper XML에는 다음 설정이 없습니다.

```xml
timeout="4"
```

MyBatis 전역 설정에도 `defaultStatementTimeout`이 없습니다.

따라서 온라인 Executor가 5초 타임아웃을 발생시켜도 실행 중인 JDBC SQL이 즉시 중단된다고 보장할 수 없습니다.

```text
5초: HTTP 504
5초: Worker interrupt 요청
5~30초: SQL 계속 실행 가능
30초: SQL 종료
30초: 트랜잭션 ROLLBACK
```

보완 방법은 다음과 같습니다.

전역 설정:

```java
mybatisConfig.setDefaultStatementTimeout(4);
```

또는 SQL별 설정:

```xml
<select id="mgcoa5530S0_S0"
        timeout="4"
        ...>
```

공통 온라인 제한이 5초라면 DB SQL 제한은 일반적으로 5초보다 짧게 설정해야 합니다.

# 22. `throws Exception` 선언

현재 모든 DAO 메서드는 다음처럼 선언되어 있습니다.

```java
int mgcoa9000C0_C0(
        Map<String, Object> input)
        throws Exception;
```

MyBatis는 일반적으로 SQL 오류를 Spring의 `DataAccessException` 계열 RuntimeException으로 변환합니다. 따라서 Mapper 인터페이스에 광범위한 `throws Exception`은 필수는 아닙니다.

단점:

- Service와 Facade까지 불필요하게 `throws Exception` 전파
- 실제 발생 가능한 예외 유형이 모호함
- checked exception 롤백 정책을 복잡하게 만듦

운영 생성 코드 규약 때문에 유지하는 것이라면 가능하지만, 신규 표준에서는 제거 여부를 검토할 수 있습니다.

# 23. DAO Aspect와 로그

`PdmgBizTxFlowAspect`는 DAO 패키지도 감쌉니다.

```java
execution(
  * nhnis.mg.co.a.persistence.dao..*(..)
)
```

따라서 DAO 호출 시 다음 로그가 남습니다.

```text
[TX-FLOW][시작] mgcoa9000DAO.mgcoa9000C0_C0
SQL 실행 로그
[TX-FLOW][종료] mgcoa9000DAO.mgcoa9000C0_C0
```

하지만 이 로그는 트랜잭션 BEGIN이나 COMMIT을 증명하는 로그가 아닙니다.

실제 트랜잭션 여부는 다음으로 확인해야 합니다.

- Spring Transaction DEBUG/TRACE
- DataSourceTransactionManager 로그
- 실제 롤백 통합 테스트
- JDBC Connection autocommit 상태

# 24. 테스트 현황

현재 DAO/Mapper 전용 테스트는 확인되지 않았습니다.

현재 `mgcoa5530ServiceTest`는 DAO Mock을 사용하므로 다음을 검증하지 못합니다.

- Mapper XML 로딩
- namespace 일치
- statement ID 일치
- Map 파라미터 바인딩
- Oracle/H2 SQL 호환성
- 페이징 SQL
- INSERT/UPDATE/DELETE
- 트랜잭션 롤백
- timeout
- 다건 IN 처리

최소한 다음 통합 테스트가 필요합니다.

```text
H2 Mapper Context 기동
→ DAO Proxy 생성 확인
→ 5530 목록/count
→ 8888 목록/delete
→ 9000 create/update/delete
→ 9999 목록
→ 쓰기 후 예외 발생
→ 전체 rollback 확인
```

Oracle 전용 SQL은 H2 Oracle 모드에서 동작하더라도 실제 Oracle 실행계획과 완전한 호환성을 보장하지 않으므로 운영 전 Oracle 검증도 필요합니다.

# 25. 문서 현행성

[23.DAO.md](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/23.DAO.md:1>)는 현재 구조를 대체로 정확하게 설명합니다.

보정할 부분은 다음과 같습니다.

### “TX는 Facade”

정확한 표현:

```text
timeout ON:
OnlineTimeoutExecutor가 외곽 TX 시작
Facade REQUIRED 참여
DAO가 같은 TX 참여

timeout OFF:
Facade가 TX 시작
DAO가 같은 TX 참여
```

### “DAO = SQL 문만”

DAO 인터페이스에는 SQL 문이 없고 실행 계약만 있습니다.

```text
DAO 인터페이스 = SQL 실행 계약
Mapper XML     = 실제 SQL
```

### 누락된 운영 위험

문서에 다음 내용이 추가되는 것이 좋습니다.

- SQL Statement Timeout 없음
- Oracle IN 목록 1,000개 제한
- `Map<String,Object>` 타입 취약성
- Mapper 통합 테스트 부재
- `mgcoa9999` 페이징·정렬 없음
- LIKE 와일드카드와 인덱스 성능
- count와 목록의 시점 차이
