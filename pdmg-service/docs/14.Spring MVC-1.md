## 14. Spring MVC 분석 결과

현재 PDMG의 Spring MVC는 다음 역할을 담당합니다.

```text
URL과 Controller 매핑
→ 시스템 선처리 Interceptor 실행
→ 요청 파라미터 변환
→ 공통 OnlineTransactionController 실행
→ 응답 전문 조립
→ 예외 응답 처리
→ 시스템 후처리
```

현재 설정은 다음과 같습니다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    commons:
      legacy-web:
        enabled: true
      filter:
        enabled: true
```

따라서 현재 실행 구조는 `TCF ON + Legacy MVC ON`입니다.

## 1. 전체 요청 흐름

```text
HTTP 요청
  ↓
DefaultFilter                         Servlet 영역
  ├─ JWT 검증
  ├─ Body 캐싱
  ├─ hdr_nhnis 생성
  └─ ServiceContext 생성
  ↓
Spring SecurityFilterChain
  ↓
DispatcherServlet                    Spring MVC 시작
  ↓
HandlerMapping
  ├─ URL에 맞는 Controller 검색
  └─ 현재는 OnlineTransactionController 선택
  ↓
ServicePreventionInterceptor.preHandle
  ├─ GUID 확인·생성
  ├─ 요청 전문 로그
  └─ ImageLog INSERT
  ↓
HandlerMethodArgumentResolver
  └─ @RequestBody 변환
  ↓
OnlineTransactionController
  ↓
TcfFacade
  ↓
Handler → Facade(TX) → Service → DAO
  ↓
Controller 반환
  ↓
ResponseBodyArgumentResolver
  ├─ hdr_nhnis 추가
  ├─ 성공 dto / 실패 result 조립
  ├─ 응답 전문 로그
  └─ ServiceContext.responseBody 저장
  ↓
ServicePreventionInterceptor.afterCompletion
  └─ ImageLog UPDATE
  ↓
HTTP 응답
```

Spring MVC는 `DispatcherServlet`부터 시작합니다. `DefaultFilter`와 Spring Security는 MVC 진입 전에 실행됩니다.

## 4. HandlerMapping

Spring MVC의 `HandlerMapping`은 URL과 Controller 메서드를 연결합니다.

예를 들어:

```text
POST /mgcoa5530S0
```

현재 TCF ON에서는 다음 메서드로 연결됩니다.

```java
@PostMapping("/{serviceId}")
public Object handleByServiceId(
        @PathVariable String serviceId,
        @RequestBody Map<String, Object> request,
        HttpServletRequest servletRequest)
```

따라서:

```text
serviceId = "mgcoa5530S0"
request = 전체 JSON 전문
```

이후 Controller가 `dto`만 추출합니다.

```java
Object dtoBody = request == null ? null : request.get("dto");
return tcfFacade.process(serviceId, dtoBody);
```

## 7. ServicePreventionInterceptor

등록 설정은 다음과 같습니다.

```java
registry.addInterceptor(servicePreventionInterceptor)
        .addPathPatterns("/**")
        .excludePathPatterns("/error");
```

따라서 `/error`를 제외한 거의 모든 MVC 요청에 적용됩니다.

### preHandle

Controller 실행 전에 다음 작업을 합니다.

```text
ServiceContext 확인
→ hdr_nhnis 확인·보완
→ GUID 확인·생성
→ 요청 정보로 헤더 보완
→ 요청 전문 로그
→ ImageLog INSERT
→ Controller 실행 허용
```

중요한 점은 `DefaultFilter`에서 GUID가 누락되었더라도 Interceptor의 `ensureGuid()`가 다시 생성할 수 있다는 것입니다.

다만 Filter가 GUID null을 MDC에 저장하는 과정에서 먼저 오류가 발생하면 Interceptor까지 도달하지 못할 수 있습니다.

### postHandle

현재 실질적인 응답 후처리는 하지 않습니다.

```java
// 시스템 후처리 시작/종료·응답 전문은
// ResponseBodyAdvice에서 출력한다.
```

응답 조립은 `postHandle`보다 앞에서 일어나는 `ResponseBodyAdvice`에 맡겨져 있습니다.

### afterCompletion

요청 완료 후 다음 작업을 합니다.

```text
정상:
  ImageLog UPDATE

예외:
  exceptionImagelog
  ServiceContext 제거
  예외 재던지기
```

여기서 예외가 있을 때 `throw ex`를 다시 실행합니다.

```java
if (ex != null) {
    ...
    throw ex;
}
```

`afterCompletion`은 이미 MVC 예외 처리가 진행된 후 호출되는 완료 콜백이므로 여기서 예외를 다시 던지는 것은 불필요한 이중 예외 로그나 컨테이너 오류 처리를 유발할 수 있습니다. 후처리 로그만 수행하고 재던지지 않는 방향이 안전합니다.

## 8. RequestBodyArgumentResolver

소스: [RequestBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/RequestBodyArgumentResolver.java:26>)

의도는 표준 전문에서 `dto`만 추출해 Controller DTO로 변환하는 것입니다.

```java
JsonNode root = objectMapper.readTree(requestBody);
JsonNode bodyNode = root.get("dto");

return objectMapper.treeToValue(
        bodyNode,
        parameter.getParameterType()
);
```

예를 들어:

```json
{
  "hdr_nhnis": {},
  "dto": {
    "customerId": "10001"
  }
}
```

다음 Controller라면:

```java
public Output execute(
    @RequestBody CustomerInput input
)
```

`CustomerInput`에는 `dto` 내부만 바인딩하려는 구조입니다.

### 현재 TCF Controller와 관계

공통 Controller는 다음과 같이 전체 전문을 요구합니다.

```java
@RequestBody Map<String, Object> request
```

그런데 커스텀 Resolver가 이 파라미터를 처리하면 `dto`만 Map으로 반환하게 되고, Controller에서 다시 다음 작업을 합니다.

```java
request.get("dto")
```

그러면 `null`이 될 수 있습니다.

다만 Spring MVC 기본 Resolver인 `RequestResponseBodyMethodProcessor`도 `@RequestBody`를 지원하며 일반적으로 커스텀 Resolver보다 먼저 배치됩니다. 따라서 현재 실행에서는 기본 Resolver가 전체 JSON을 Map으로 변환하고, 커스텀 `RequestBodyArgumentResolver`가 실제로 호출되지 않을 가능성이 큽니다.

이 부분은 현재 구조상 설계가 명확하지 않습니다.

```text
업무별 typed Controller:
  dto만 추출하는 커스텀 Resolver가 필요할 수 있음

공통 OnlineTransactionController:
  전체 전문 Map이 필요함
```

권장 방향은 전용 어노테이션으로 구분하는 것입니다.

```java
@PdmgRequestBody
```

또는 공통 Controller에서는 `HttpServletRequest`나 전용 표준 요청 객체를 사용하여 커스텀 Resolver와 충돌하지 않게 해야 합니다.

## 9. ResponseBodyArgumentResolver

이름에는 `ArgumentResolver`가 들어가지만 실제 역할은 `ResponseBodyAdvice`입니다.

[ResponseBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java:45>)

```java
@ControllerAdvice
public class ResponseBodyArgumentResolver
        implements ResponseBodyAdvice<Object>
```

모든 MVC 응답을 대상으로 합니다.

```java
@Override
public boolean supports(...) {
    return true;
}
```

### 성공 응답

Controller가 업무 DTO를 반환하면:

```json
{
  "hdr_nhnis": {
    "sys_comm": {}
  },
  "dto": {
    "resultData": []
  }
}
```

### 실패 응답

ControllerAdvice가 `NH_NIS_ERR_DTO`를 반환하면:

```json
{
  "hdr_nhnis": {
    "sys_comm": {}
  },
  "result": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "온라인 거래 처리시간을 초과했습니다."
  }
}
```

즉:

```text
성공 → dto
실패 → result
```

### 부가 작업

응답 봉투 외에도 다음을 수행합니다.

```text
dtoLogicalName 제거
fieldPropertyMap 제거
*List 필드 제거
*Array 필드 제거
응답 전문 로그
ServiceContext.responseBody 저장
```

`*List`, `*Array`로 끝나는 필드를 모두 제거하므로 실제 업무 응답 필드가 이 명명 규칙을 사용하는 경우 필요한 데이터까지 사라질 수 있습니다. 생성 DTO의 내부 보조 필드만 제거하려는 목적이라면 필드 이름만으로 제거하기보다 타입 또는 명시적 직렬화 설정으로 제한해야 합니다.

### 예외 은폐 위험

응답 조립 중 예외가 발생하면:

```java
catch (Exception e) {
    e.printStackTrace();
}
```

예외를 다시 던지지 않고 비어 있거나 일부만 조립된 응답을 그대로 반환합니다. HTTP 상태도 성공 상태로 남을 수 있습니다.

운영에서는 다음 형태가 필요합니다.

```text
응답 조립 실패
→ 로거로 오류 기록
→ 표준 시스템 예외 발생
→ 500 + result 오류 전문
```

`printStackTrace()`는 운영 로그 정책에도 맞지 않습니다.

## 10. 예외 처리

TCF ON에서는 다음 Advice가 활성화됩니다.

[GlobalExceptionHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java:24>)

처리 대상은 다음과 같습니다.

| 예외                      | HTTP | 코드            |
| ------------------------- | ---: | --------------- |
| `ServiceHandlerNotFound`  |  500 | `E9999`         |
| `BizException`            |  500 | 업무 코드       |
| `OnlineTimeoutException`  |  504 | `FW_TIMEOUT`    |
| `OnlineOverloadException` |  503 | `FW_OVERLOADED` |

반환한 `NH_NIS_ERR_DTO`는 다시 `ResponseBodyAdvice`를 거쳐 `result`에 들어갑니다.

### 일반 Exception 미처리

현재 다음 핸들러는 없습니다.

```java
@ExceptionHandler(Exception.class)
```

따라서 `NullPointerException`, MyBatis 예외, 알 수 없는 RuntimeException 등은 표준 `result` 전문으로 변환된다는 보장이 없습니다.

일반 시스템 예외 핸들러가 필요합니다.

### Advice 중복 가능성

`ResponseBodyArgumentResolver`에도 다음 예외 핸들러가 있습니다.

```java
@ExceptionHandler(NhBaseException.class)
```

즉, 예외 Advice가 두 군데 있습니다.

```text
GlobalExceptionHandler
ResponseBodyArgumentResolver.errorProcessor
```

`BizException`의 상속 관계에 따라 둘 다 후보가 될 수 있으며 두 Advice에 `@Order`가 없습니다. 예외 처리 책임을 한 곳으로 통합하는 편이 명확합니다.

또한 레거시 처리기는 클라이언트 응답에 Stack Trace 상위 15개를 포함합니다. 보안 지침상 내부 클래스·파일·라인 정보가 외부로 노출되지 않도록 제거해야 합니다.

## 12. 트랜잭션과 Spring MVC의 관계

Spring MVC 자체는 업무 트랜잭션을 관리하지 않습니다.

```text
Spring MVC
  Controller 실행
    ↓
  TcfFacade
    ↓
  Handler
    ↓
  Facade @Transactional
```

타임아웃 기능이 활성화된 현재 구조에서는 실제 트랜잭션 경계가 worker thread의 `TransactionTemplate`에서 먼저 시작될 수 있고, Facade의 `@Transactional(REQUIRED)`가 그 트랜잭션에 참여합니다.

따라서 다음 위치에 업무 트랜잭션을 추가하는 것은 권장되지 않습니다.

```text
Filter
Interceptor
ResponseBodyAdvice
GlobalExceptionHandler
Controller
```

Spring MVC는 요청·응답 조정 계층이고, 업무 트랜잭션은 Facade/TCF 실행 경계가 담당하는 것이 맞습니다.

## 13. 현재 구조의 주요 점검 결과

| 우선순위  | 항목                                                    | 판단                      |
| --------- | ------------------------------------------------------- | ------------------------- |
| P0        | 일반 `Exception` 표준 처리 없음                         | 보완 필요                 |
| P1        | RequestBody 커스텀 Resolver와 기본 Resolver 역할 불명확 | 정리 필요                 |
| P1        | `afterCompletion`에서 예외 재던짐                       | 제거 검토                 |
| P1        | 응답 조립 예외를 `printStackTrace` 후 무시              | 표준 오류 처리 필요       |
| P1        | URL serviceId와 헤더 serviceId 불일치 미검증            | 검증 필요                 |
| P1        | 오류 Advice 두 곳, `@Order` 없음                        | 책임 통합 필요            |
| P1        | Stack Trace 클라이언트 노출                             | 제거 필요                 |
| P2        | `supports()`가 모든 응답에 true                         | 적용 Controller 제한 권장 |
| P2        | `*List`, `*Array` 필드 일괄 제거                        | 업무 데이터 손실 가능     |
| 문서 오류 | CORS `/api/**` 설명                                     | 실제는 `/**`              |

## 결론

현재 PDMG Spring MVC 구조의 핵심은 다음과 같습니다.

```text
DefaultFilter
  ↓
DispatcherServlet
  ↓
ServicePreventionInterceptor
  ↓
OnlineTransactionController
  ↓
TCF → Handler → Facade(TX) → Service → DAO
  ↓
ResponseBodyAdvice
  ↓
Interceptor.afterCompletion
```

전체 계층 분리는 적절하고, TCF ON/OFF에 따른 Controller 충돌도 방지되어 있습니다. 다만 운영 안정성을 위해 우선적으로 다음을 정리해야 합니다.

1. 일반 시스템 예외를 `result` 표준 전문으로 변환
2. `RequestBodyArgumentResolver`가 실제 어떤 Controller를 대상으로 하는지 명시
3. 응답 Advice의 예외 은폐와 `printStackTrace()` 제거
4. 두 예외 Advice의 책임과 우선순위 통합
5. URL과 전문 serviceId 일치 검증
6. `afterCompletion`의 예외 재던지기 제거 검토

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
