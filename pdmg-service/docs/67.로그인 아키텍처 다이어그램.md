## 3. 로그인 사용자 검증

```text
mgjwa1000Service
      │
      ▼
mgjwa1000DAO
      │
      ▼
사용자 테이블 조회
      │
      ├─ 사용자 없음
      │      └─ 로그인 실패
      │
      └─ 사용자 있음
             │
             ├─ 사용 여부 확인
             ├─ 잠금 상태 확인
             ├─ 비밀번호 Hash 존재 확인
             └─ 실패 횟수 확인
                    │
                    ▼
            BCrypt PasswordEncoder
                    │
                    ├─ matches = true
                    │      └─ 인증 성공
                    │
                    └─ matches = false
                           └─ 인증 실패
```

비밀번호 비교:

```text
사용자가 입력한 평문 비밀번호
             │
             ▼
BCryptPasswordEncoder.matches()
             │
             ▼
DB에 저장된 BCrypt Hash와 비교
             │
       ┌─────┴─────┐
       │           │
       ▼           ▼
     일치        불일치
       │           │
       ▼           ▼
   로그인 성공   로그인 실패
```

평문 비밀번호는 DB나 로그에 저장하면 안 됩니다.

```text

      │

      ├─ 최종 로그인 시각 갱신

      ├─ Access Token JTI 생성
      └─ Refresh Token ID 생성
      │
      ▼
JwtTokenIssuer
      │
      ├─ Access Token Claim 생성

      │
      ▼

      │

```

## 5. Access Token 구조

```text
Access Token
│
├─ Header
│   ├─ alg = RS256
│   ├─ typ = JWT
│   └─ kid = nsight-jwt-rs256
│
├─ Payload
│   ├─ iss = NSIGHT-AUTH
│   ├─ aud = NSIGHT-MP
│   ├─ sub = 사용자 ID
│   ├─ jti = 토큰 고유 ID
│   ├─ iat = 발급 시각
│   ├─ exp = 만료 시각
│   ├─ type = ACCESS
│   ├─ userId
│   ├─ userName
│   ├─ branchId
│   ├─ channelId
│   └─ authGroupId
│
└─ Signature
    └─ RSA Private Key를 이용한 RS256 서명
```

UI 저장:

```text
로그인 성공 응답
      │
      ▼
sessionStorage
      │
      └─ pdmg.jwt.session
           ├─ Access Token
           ├─ Refresh Token
           ├─ 사용자 정보
```

운영 환경에서는 Refresh Token을 JavaScript가 읽을 수 있는 `sessionStorage`보다 `HttpOnly + Secure + SameSite` 쿠키에 보관하는 것이 더 안전합니다.

```text

      ├─ 비밀번호 불일치
      ├─ 비활성 사용자
      ├─ 잠긴 계정
      └─ 사용 기간 만료
      │
      ▼

      │
      ├─ 실패 횟수 증가
      ├─ 실패 기준 초과 확인
      ├─ 필요 시 계정 잠금
      ├─ 로그인 실패 이력 저장
```

사용자 존재 여부를 노출하지 않도록 응답을 통일하는 것이 좋습니다.


## 9. SSO 로그인 권장 구조

현재 직접 로그인 방식에 SSO를 결합하면 다음과 같은 구조가 적절합니다.

```text
사용자
  │
  ▼
pdmg-ui
  │
  │ SSO 로그인
  ▼
SSO 인증 서버
  │
  ├─ 사용자 인증
  ├─ MFA
  ├─ 계정 상태 확인
  └─ SSO 인증 결과 또는 Authorization Code 반환
  │
  ▼
pdmg-ui 또는 Backend Callback
  │
  ▼
pdmg-jwt
  │
  ├─ SSO 응답의 전자서명 검증
  ├─ issuer 검증
  ├─ audience 검증
  ├─ nonce/state 검증
  ├─ 사용자 매핑
  └─ 내부 권한·영업점 조회
  │
  ▼
PDMG Access Token / Refresh Token 발급
  │
  ▼
pdmg-ui
```

중요한 구분:

```text
SSO Token
└─ 외부 SSO 인증 결과 확인용

PDMG Access Token
└─ pdmg-service 업무 호출용
```

SSO 인증이 성공했다고 자동으로 현재 PDMG 토큰이 생성되는 것은 아닙니다. SSO 결과를 받은 후 `pdmg-jwt`가 검증하고 PDMG용 토큰을 명시적으로 발급해야 합니다.

## 10. SSO 내부 호출 보호

```text
SSO 또는 내부 인증 연계 시스템
      │
      ├─ 호출 서비스 ID
      ├─ Timestamp
      ├─ 요청 Payload
      └─ HMAC Signature
      │
      ▼
pdmg-jwt InternalCallValidator
      │
      ├─ 허용 서비스 확인
      ├─ 허용 IP 확인
      ├─ Timestamp 오차 확인
      ├─ 공유 비밀키로 서명 재계산
      └─ 요청 서명 비교
      │
      ├─ 정상
      │      └─ 내부 인증 처리
      │
      └─ 실패
             └─ HTTP 401 또는 403
```

여기서 사용하는 내부 공유 비밀키는 JWT 서명용 RSA Private Key와 다른 값입니다.

```text
RSA Private Key
└─ JWT RS256 서명용

내부 shared-secret
└─ 내부 시스템 호출의 HMAC 검증용
```

## 13. 현재 구현상 주의사항

```text
로그인
  → pdmg-jwt가 RS256 Access Token 발급
  → pdmg-ui가 Token 저장
  → pdmg-service 호출
  → pdmg-fw가 HMAC jwt.secret으로 검증
  → 알고리즘 불일치로 검증 실패 가능
```

```text
발급
└─ RS256 + RSA Private Key

현재 검증
└─ HMAC + jwt.secret

필요한 변경
└─ pdmg-fw를 JWKS 기반 RS256 검증으로 전환
```

또한 일반 업무용 `service-client.js`에는 현재 `Authorization` 헤더 연결이 필요합니다.

## 14. 최종 권장 로그인 구조

```text
사용자
  │
  ▼
pdmg-ui
  │
  ├─ 직접 로그인 또는 SSO 이동
  ▼
SSO / pdmg-jwt
  │
  ├─ 사용자 인증
  ├─ 계정 상태 확인
  ├─ 권한·영업점 조회
  ├─ Access Token RS256 발급
  └─ Refresh Token 발급
  │
  ▼
pdmg-ui
  │
  ├─ Access Token은 메모리 또는 세션 보관
  └─ Refresh Token은 HttpOnly Cookie 권장
  │
  ▼
Authorization: Bearer {Access Token}
  │
  ▼
pdmg-service / pdmg-fw
  │
  ├─ JWKS Public Key 조회·캐시
  ├─ RS256 서명 검증
  ├─ Claim 검증
  ├─ Denylist 확인
  ├─ ServiceContext 생성
  └─ 거래 권한 확인
  │
  ▼
업무 처리
```
