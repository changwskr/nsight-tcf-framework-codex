## 분석 결론

[05.전체 빅픽처 흐름.md](./05.전체%20빅픽처%20흐름.md)는 앞의 01~04 문서보다 현재 TimeoutExecutor 구조를 훨씬 잘 반영하고 있습니다.

특히 다음 내용은 정확합니다.

- Timeout ON에서 별도 Worker Thread 사용
- Worker에서 외부 트랜잭션 시작
- Handler부터 DAO까지 외부 트랜잭션에 포함
- Facade의 `@Transactional(REQUIRED)`가 기존 TX에 참여
- 업무 Aspect가 Service 전후로 실행
- 시스템 선후처리와 업무 DB 작업을 분리
- 타임아웃 시 HTTP 504와 `FW_TIMEOUT` 응답

다만 문서 내부에서 구 구조의 설명이 일부 남아 있어 앞뒤가 충돌합니다.

가장 중요한 오류는 다음 두 부분입니다.

```text
성공 시퀀스:
  Facade에서 TX 시작
  Facade 반환 후 commit
```

```text
두 가지 트랜잭션:
  DB 트랜잭션 = Facade @Transactional
```

Timeout ON에서는 실제 트랜잭션을 시작하고 최종 Commit/Rollback하는 주체가 `DefaultOnlineTimeoutExecutor`입니다.

추가로 현재 AS-IS와 다른 문서 전제도 있습니다.

```text
문서: UI → /api/relay → pdmg-service
현재 화면: 브라우저가 pdmg-service 를 직접 호출 (CORS)
  (/api/relay 는 UI에 남아 있으나 샘플 화면의 주 경로가 아님)

문서: 실패 시 NH_NIS_ERR_DTO 를 dto 에 넣음
현재: 오류는 result 키로 조립 (dto 는 업무용)

문서: 구·신 패키지 공존으로 기동 위험
현재: nhnis.mg.co.a 로 통합 완료
```

## 1. 문서가 설명하는 전체 흐름

현재 문서의 기본 흐름은 다음입니다.

```text
브라우저
  → pdmg-ui
  → TransactionRelayService
  → pdmg-service
  → DefaultFilter
  → ServicePreventionInterceptor
  → OnlineTransactionController
  → TcfFacade
  → OnlineTimeoutExecutor
  → TransactionDispatcher
  → Handler
  → Facade
  → 업무 선처리
  → Service
  → DAO / Mapper XML / DB
  → 업무 후처리
  → ResponseBodyAdvice
  → ImageLog 후처리
  → 브라우저
```

큰 흐름은 현재 구현과 맞습니다.

다만 **현재 샘플 화면의 주 경로**는 UI 서버 중계가 아니라 다음입니다.

```text
브라우저
  → PdmgServiceClient (직접 POST pdmg-service/{serviceId})
  → DefaultFilter …
```

`pdmg-ui`의 `/api/relay/{id}` · `TransactionRelayService`는 여전히 있으나, mgcoa/imagelog 등 화면은 `_shared/service-client.js`로 서비스에 직접 붙습니다.

요청 스레드와 작업 스레드를 더 명확하게 분리해야 합니다.

## 2. 정확한 스레드 경계

### 요청 스레드

다음 구간은 Servlet 요청 스레드에서 실행됩니다.

```text
DefaultFilter
  → ServicePreventionInterceptor.preHandle
  → OnlineTransactionController
  → TcfFacade
  → OnlineTimeoutExecutor.execute
  → Future.get(timeout)
```

### 작업 스레드

Timeout이 활성화되면 다음 구간은 별도 Worker Thread에서 실행됩니다.

```text
ServiceContext 설치
  → TransactionTemplate BEGIN
  → TransactionDispatcher
  → Handler
  → Facade
  → 업무 선처리
  → Service
  → DAO
  → 업무 후처리
  → deadline 확인
  → Commit 또는 Rollback
  → ServiceContext 정리
```

### 요청 스레드 복귀

Worker가 끝나거나 요청 타임아웃이 발생하면 다시 요청 스레드에서 처리합니다.

```text
Controller 반환 또는 예외
  → GlobalExceptionHandler
  → ResponseBodyAdvice
  → ServicePreventionInterceptor.afterCompletion
  → DefaultFilter 종료 및 ServiceContext 정리
```

문서에서 이 세 구간을 명확히 분리하면 Timeout 동작을 훨씬 쉽게 이해할 수 있습니다.

## 3. TCF ON + Timeout ON 정확한 흐름

현재 구현 기준 전체 흐름은 다음과 같습니다.

```text
[요청 스레드]

브라우저
  → (주 경로) POST pdmg-service/{serviceId}   CORS
  → (대안) pdmg-ui /api/relay/{serviceId} → TransactionRelayService

DefaultFilter
  → 요청 Body 캐시
  → Header 역직렬화
  → ServiceContext 생성
  → GUID/MDC 준비

ServicePreventionInterceptor.preHandle
  → Header 보완
  → GUID 확인/생성
  → 요청 전문 로그
  → ImageLog INSERT

OnlineTransactionController
  → serviceId 결정
  → dto 노드 분리
  → TcfFacade.process

TcfFacade
  → TransactionContext 생성
  → OnlineTimeoutExecutor 호출

DefaultOnlineTimeoutExecutor
  → Worker Context 캡처
  → 작업 제출
  → Future.get(timeout)

                 ↓

[작업 스레드]

ServiceContext 설치
  → TransactionTemplate BEGIN
  → TransactionDispatcher
  → serviceId에 맞는 Handler 검색
  → Handler가 Facade 메서드 분기
  → Facade @Transactional(REQUIRED) 참여
  → Object dtoBody를 DTOin으로 변환
  → BizPrePostAspect @Before
  → Service
  → DAO(MyBatis Mapper)
  → Mapper XML / DB
  → BizPrePostAspect @AfterReturning
  → deadline/interrupted 재확인
  → Commit 또는 Rollback
  → Worker ServiceContext 정리

                 ↓

[요청 스레드]

Controller 반환 또는 예외 처리
  → ResponseBodyAdvice
  → 성공: {hdr_nhnis, dto}
  → 실패: {hdr_nhnis, result}   ← NH_NIS_ERR_DTO
  → 응답 전문 ServiceContext 저장
  → afterCompletion
  → ImageLog UPDATE (오류면 EXCEPTION_* 포함)
  → DefaultFilter finally
  → ServiceContext/MDC 정리
  → HTTP 응답
```

## 4. 시스템 선처리 분석

### DefaultFilter

문서의 다음 설명은 대체로 맞습니다.

```text
Body 캐시
ServiceContext 생성
GUID 준비
```

조금 더 정확하게는 다음 역할을 수행합니다.

```text
요청 Body 캐싱
hdr_nhnis 역직렬화
ServiceContext 생성 및 Holder 등록
요청 원문 저장
필터 체인 실행
최종 ServiceContextHolder 정리
```

`DefaultFilter`는 요청 전체의 Context 생명주기를 담당합니다.

### ServicePreventionInterceptor.preHandle

실제 역할은 다음과 같습니다.

```text
시스템 선처리 시작 로그
Header/sys_comm 생성 또는 보완
GUID 보장
serviceId, 화면 ID, 사용자, IP 보완
요청 전문 로그
ImageLog 사전 INSERT
시스템 선처리 종료 로그
```

따라서 문서의 “요청전문 로그 · ImageLog INSERT”는 정확합니다.

다만 ImageLog INSERT 실패는 거래 전체를 반드시 실패시키지 않습니다. `ImageLogHandler` 내부에서 일부 DB 예외를 로깅하고 계속 처리하는 방어 로직이 있습니다.

즉:

```text
ImageLog = 감사/관찰 기능
업무 성공 여부 = Service/DAO 결과
```

로 구분해야 합니다.

ImageLog `REQUEST_TIME`은 헤더 `tr_dtm`(업무일시)이 아니라 **서버 수신 시각**을 씁니다.

## 5. serviceId 결정 방식

문서는 다음처럼 표현합니다.

```text
serviceId = URL path = Handler 라우팅 키
```

기본적인 UI 호출에서는 맞지만, 실제 `OnlineTransactionController`는 다음 우선순위로 serviceId를 결정합니다.

```text
1. ServiceContext Header의 rms_svc_c
2. 요청 JSON hdr_nhnis.sys_comm.rms_svc_c
3. URL path의 serviceId
```

따라서 Header와 URL이 다르면 항상 URL이 사용되는 것이 아닙니다.

정확한 표현은 다음입니다.

> serviceId는 Header 값을 우선 사용하고, Header에 없으면 URL path를 사용하며 최종 결정된 값이 Dispatcher의 Handler 검색 키가 된다.

보안과 거래 정합성을 위해 Header와 URL의 값이 다를 때 차단할지 여부도 향후 명확히 정할 필요가 있습니다.

## 6. TransactionDispatcher 위치 오류

문서의 빅픽처에서 다음이 하나의 “업무 TX 밖 시스템 구간”으로 묶여 있습니다.

```text
TcfFacade
  → OnlineTimeoutExecutor
  → Dispatcher
```

하지만 Dispatcher는 외부 트랜잭션 안에서 실행됩니다.

실제 경계는 다음과 같습니다.

```text
TX 밖:
  TcfFacade
  OnlineTimeoutExecutor의 요청 스레드 부분

TX 경계:
  OnlineTimeoutExecutor 작업 스레드의 TransactionTemplate

TX 안:
  TransactionDispatcher
  Handler
  Facade
  Aspect
  Service
  DAO
```

따라서 Dispatcher를 업무 TX 밖 시스템 블록에 넣으면 안 됩니다.

---

## 7. Handler 트랜잭션 참여

문서의 다음 설명은 정확합니다.

```text
Handler
  → Executor TX 안
  → serviceId별 Facade 메서드 분기
```

Handler는 `@Transactional`을 선언하지 않으며 Commit/Rollback을 결정하지 않습니다.

하지만 Timeout ON에서는 이미 시작된 트랜잭션 안에서 실행됩니다.

```text
TX BEGIN
  → Dispatcher
  → Handler
  → Facade
```

Handler에서 DB 작업을 해도 기술적으로 같은 TX에 참여할 가능성이 있지만, 아키텍처 책임상 Handler에서 DB를 호출하면 안 됩니다.

## 8. Facade 역할과 문서 내부 충돌

빅픽처 본문에서는 다음과 같이 올바르게 설명합니다.

```text
Executor BEGIN
Facade @Transactional(REQUIRED)
같은 TX 참여
```

하지만 성공 시퀀스에는 다음과 같이 쓰여 있습니다.

```text
Facade: Object → DTOin 변환 후 TX 시작
Facade 반환 → TX commit
```

Timeout ON에서는 틀린 설명입니다.

정확한 성공 시퀀스는 다음과 같습니다.

```text
1. TimeoutExecutor가 Worker에서 TX 시작
2. Dispatcher와 Handler 실행
3. Facade가 기존 TX에 REQUIRED로 참여
4. Facade가 Object → DTOin 변환
5. Service와 DAO 실행
6. Facade 반환
7. TimeoutExecutor가 deadline 재검사
8. TransactionTemplate가 Commit
```

Facade는 업무 유스케이스와 기본 트랜잭션 선언 지점이지만 Timeout ON에서 물리 트랜잭션의 시작·종료 주체는 아닙니다.

## 9. 업무 선후처리 분석

현재 Pointcut은 Service 계층입니다.

```text
execution(
  public * nhnis.mg.co.a.application.service..*(..)
)
```

정상 흐름은 다음과 같습니다.

```text
TX BEGIN
  → 업무 선처리 @Before
  → Service
  → DAO
  → 업무 후처리 @AfterReturning
TX COMMIT
```

업무 선후처리에서 DB를 갱신하면 같은 트랜잭션에 참여합니다.

단, `@AfterReturning`이므로 Service에서 예외가 발생하면 업무 후처리는 실행되지 않습니다.

```text
Service 정상 반환
  → 업무 후처리 실행

Service 예외
  → 업무 후처리 미실행
  → Rollback
```

문서의 “업무 후처리” 옆에 정상 반환 조건을 표시해야 합니다.

## 10. 성공 처리 오류

현재 문서의 성공 시퀀스는 Facade가 트랜잭션을 시작하고 Commit한다고 설명합니다.

Timeout ON 기준 정확한 성공 시퀀스는 다음입니다.

```text
1. UI/브라우저가 serviceId와 전문 전달
2. Filter가 ServiceContext 생성
3. Interceptor가 Header/GUID 보완 및 ImageLog INSERT
4. Controller가 serviceId와 dto 분리
5. TcfFacade가 Worker 작업 요청
6. TimeoutExecutor가 Worker에서 TX 시작
7. Dispatcher가 Handler 검색
8. Handler가 Facade 메서드 선택
9. Facade가 DTOin 변환 후 기존 TX 참여
10. 업무 선처리
11. Service → DAO → SQL
12. 업무 후처리
13. deadline 재검사
14. TransactionTemplate Commit
15. ResponseBodyAdvice가 응답 봉투 조립 ({hdr_nhnis, dto})
16. afterCompletion이 ImageLog UPDATE
17. Filter가 Context 정리
18. UI가 결과 표시
```

## 11. 실패 처리 분석

문서에는 다음처럼 되어 있습니다.

```text
쓰기 Facade면
  → Spring TX ROLLBACK
```

Timeout ON에서는 조회/쓰기 구분과 관계없이 외부 TransactionTemplate가 전체 작업을 감쌉니다.

정확한 실패 흐름은 다음입니다.

```text
Service 또는 DAO 예외
  → 업무 후처리 @AfterReturning 미실행
  → Facade를 통과해 예외 전파
  → TransactionTemplate Rollback
  → Future가 요청 스레드에 예외 전달
  → GlobalExceptionHandler
  → NH_NIS_ERR_DTO
  → ResponseBodyAdvice가 {hdr_nhnis, result} 조립
  → ImageLog에 RESPONSE_MSG + EXCEPTION_* 갱신
```

체크 예외도 Executor 내부 래퍼를 통해 RuntimeException으로 전환하여 롤백되도록 처리되어 있습니다.

따라서 문서의 실패 조건은 다음처럼 써야 합니다.

```text
Timeout ON:
  Dispatcher 이하에서 예외가 전파되면 외부 TX Rollback

Timeout OFF:
  Facade의 rollbackFor와 Spring 기본 롤백 규칙에 따라 Rollback
```

Advice로 처리된 오류(`FW_TIMEOUT` 등)는 `afterCompletion`의 `ex`가 null이어도, 응답 JSON의 `result.stdErrCode`를 보고 **같은 ImageLog 테이블**에 예외 컬럼을 채웁니다.

## 12. 타임아웃 처리 분석

현재 구현은 요청 스레드에서 다음을 수행합니다.

```java
future.get(timeout)
```

시간이 초과되면:

```text
future.cancel(true)
OnlineTimeoutException 발생
GlobalExceptionHandler가 FW_TIMEOUT 생성
HTTP 504 Gateway Timeout 반환
```

문서의 다음 설명은 맞습니다.

```text
timeout → 요청 Thread 504 FW_TIMEOUT
```

하지만 중요한 시간 차이가 빠져 있습니다.

```text
요청 스레드
  → timeout 감지
  → Future 취소
  → 504 응답 처리 시작

작업 스레드
  → 인터럽트 또는 DB 작업 종료 대기
  → deadline 검사
  → Rollback
```

따라서 클라이언트가 504를 받은 순간에 DB Rollback이 이미 완료됐다고 보장할 수 없습니다.

문서에는 다음을 추가해야 합니다.

> 타임아웃 응답과 Worker 트랜잭션의 실제 롤백 완료는 동시에 일어나지 않을 수 있다.

또한 Worker가 interrupt를 받아도 업무 코드가 sleep/루프를 계속하면, 클라이언트·ImageLog는 실패인데 워커 로그는 성공처럼 이어질 수 있습니다.

## 13. Timeout 측정 범위

타임아웃 deadline은 Worker가 실행을 시작한 시점이 아니라 작업 제출 전에 계산됩니다.

따라서 다음 시간이 모두 timeout에 포함됩니다.

```text
Worker Pool Queue 대기
Dispatcher
Handler
Facade
업무 선처리
Service
DAO/SQL
업무 후처리
deadline 검사
```

문서의 “공통 timeout” 설명에는 Queue 대기 시간도 포함된다는 점을 추가하는 것이 좋습니다.

설정 키는 다음입니다.

```text
nhnis.fw.timeout.milliseconds   (기본 5000)
```

(`default-timeout-ms` 가 아님)

## 14. 시스템 후처리 분석

### ResponseBodyAdvice

현재 `ResponseBodyArgumentResolver`는 다음 조건에서 등록됩니다.

```text
nhnis.fw.commons.legacy-web.enabled=true
```

활성화되면 응답을 다음 구조로 감쌉니다.

```json
{
  "hdr_nhnis": {},
  "dto": {}
}
```

성공 시 업무 결과는 `dto`에 들어갑니다.

실패 시 `NH_NIS_ERR_DTO`는 **`dto`가 아니라 `result`** 에 들어갑니다.

```json
{
  "hdr_nhnis": {},
  "result": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "...",
    "errType": "COMMON"
  }
}
```

또한 응답 전문을 `ServiceContext.responseBody`에 저장합니다.

### afterCompletion

정상 완료에서는:

```text
ServiceContext의 응답 전문 조회
ImageLog 응답 시간/응답 전문 UPDATE
```

응답에 `result.stdErrCode`가 있으면:

```text
동일 TB_FW_IMAGE_LOG 에
RESPONSE_MSG + EXCEPTION_CODE/MSG/TYPE UPDATE
```

예외가 MVC까지 미처리 상태로 전달되면:

```text
exceptionImagelog
예외 정보 기록
```

이후 Filter가 ThreadLocal Context를 제거합니다.

문서의 시스템 후처리 순서는 전반적으로 맞습니다. 오류 키만 `result`로 정정하면 됩니다.

---

## 15. ImageLog와 업무 트랜잭션

문서의 다음 핵심 문장은 맞습니다.

> ImageLog·시스템 선후처리는 업무 Commit/Rollback과 분리된다.

ImageLog 선처리는 요청 스레드에서 업무 Worker TX가 시작되기 전에 실행됩니다.

```text
요청 스레드
  → ImageLog INSERT

작업 스레드
  → 업무 TX BEGIN
  → 업무 DB 처리
  → COMMIT/ROLLBACK

요청 스레드
  → ImageLog UPDATE
```

따라서 업무가 Rollback되어도 ImageLog는 남을 수 있습니다. 이것이 감사 로그 관점에서는 정상적인 구조입니다.

다만 Timeout 발생 시에는 요청 스레드의 시스템 후처리가 Worker의 실제 Rollback 완료보다 먼저 진행될 가능성이 있습니다.

---

## 16. TCF OFF 분석

문서의 TCF OFF 흐름은 현재 소스와 맞습니다.

```text
Filter / Interceptor
  → application.controller
  → Service
  → DAO
```

현재 Controller들은 Service를 직접 호출합니다.

따라서 다음 기능을 우회합니다.

```text
OnlineTransactionController
TcfFacade
TimeoutExecutor
Dispatcher
Handler
Facade @Transactional
```

업무 Aspect는 Service Pointcut이므로 실행되지만 명시적 트랜잭션은 없습니다.

문서의 다음 표현:

> Controller → Facade → Service가 더 일관적이다.

는 다음처럼 명확히 해야 합니다.

> TCF OFF에서도 트랜잭션을 보장하려면 Controller가 반드시 Facade를 호출해야 한다.

---

## 17. “두 가지 트랜잭션” 절의 오류

문서는 DB 트랜잭션 위치를 다음처럼 정의합니다.

```text
DB 트랜잭션
  → Facade @Transactional
```

이 정의는 Timeout OFF에만 맞습니다.

정확한 표는 다음과 같습니다.

| 구분                 | 의미                           | 범위/담당                    |
| -------------------- | ------------------------------ | ---------------------------- |
| 온라인 요청 흐름     | Filter부터 ImageLog 후처리까지 | 요청 전체                    |
| Timeout/SLA 실행     | Worker 실행과 제한 시간        | OnlineTimeoutExecutor        |
| DB TX—Timeout ON     | Commit/Rollback                | Worker의 TransactionTemplate |
| DB TX—Timeout OFF    | Commit/Rollback                | Facade `@Transactional`      |
| TCF OFF 직접 Service | 명시적 DB TX                   | 현재 없음                    |

## 18. 설정 조건도 빅픽처에 필요

전체 흐름은 다음 설정에 따라 달라집니다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    timeout:
      enabled: true
      milliseconds: 5000
      pool-size: 20
      queue-capacity: 100
    commons:
      filter:
        enabled: true
      legacy-web:
        enabled: true
```

각 설정의 의미는 다음과 같습니다.

| 설정                                  | 영향                                                          |
| ------------------------------------- | ------------------------------------------------------------- |
| `nhnis.fw.tcf.enabled`                | 공통 Controller/Handler 경로 또는 업무별 Controller 경로 선택 |
| `nhnis.fw.timeout.enabled`            | Worker+외부 TX 또는 동기 실행 선택                            |
| `nhnis.fw.timeout.milliseconds`       | Queue 대기 포함 온라인 제한 시간                              |
| `nhnis.fw.commons.filter.enabled`     | DefaultFilter 활성화                                          |
| `nhnis.fw.commons.legacy-web.enabled` | ResponseBodyAdvice와 일부 Aspect 활성화                       |

## 19. 현재 실행 가능성

문서는 신규 `nhnis.mg.co.a.*` 경로가 정상 실행되는 것처럼 설명합니다.

**현재 소스에서는 구 패키지(`nhnis.mg.application.*` 등)가 제거**되어 있고, 업무는 `nhnis.mg.co.a.*`만 존재합니다.

Boot는 다음과 같이 스캔합니다.

```java
@SpringBootApplication(scanBasePackages = "nhnis")
```

동일 Bean 이름 이중 등록(구·신 Service/Config 충돌)은 **현재 AS-IS에서 해소**되었습니다.

다만 업무 축을 복제하거나 `RdwDataSourceConfig`를 축마다 복사하면 다음 Bean 충돌이 다시 날 수 있습니다.

```text
rdwDataSource
rdwTransactionManager
mgcoa*Service
BizPrePostAspect
```

그러므로 이 문서는 다음으로 정의하면 정확합니다.

> 현재 `nhnis.mg.co.a` + TimeoutExecutor 기준으로 동작하는 AS-IS 흐름이다. 구·신 공존 기동 차단은 더 이상 전제가 아니다.

## 20. 문서 정확도 평가

| 영역                        |      평가 |
| --------------------------- | --------: |
| UI → 서비스 흐름            | 수정 필요 (직접 호출 반영) |
| Filter/Interceptor 선처리   |      높음 |
| Timeout Worker 구조         |      높음 |
| Handler/Facade/Service 흐름 |      높음 |
| 업무 Aspect 위치            |      높음 |
| 시스템 후처리               | 수정 필요 (`result`) |
| 성공 시 TX 설명             | 수정 필요 |
| 실패 시 TX 설명             | 수정 필요 |
| 두 가지 트랜잭션 절         | 수정 필요 |
| 현재 기동/패키지 전제       | **해소됨** (문서만 구전제 잔존) |

전체 정확도는 약 80~85%입니다. (Timeout·레이어 흐름은 높고, UI 경로·오류 봉투·설정 키·패키지 전제가 어긋남)

핵심적으로 다음을 수정하면 현재 구현과 상당히 정확하게 일치합니다.

1. 성공 시퀀스의 TX 시작·Commit 주체를 Facade에서 TimeoutExecutor로 변경
2. 실패 시퀀스를 외부 TransactionTemplate 기준으로 변경
3. “DB 트랜잭션 = Facade”를 Timeout ON/OFF 조건별 표로 변경
4. 오류 응답을 `{hdr_nhnis, result}` 로 정정 (`dto`는 업무 전용)
5. UI 주 경로를 브라우저 직접 호출(+CORS)로 정정 (relay는 대안)
6. 타임아웃 설정 키를 `milliseconds`로 정정
7. 구·신 패키지 충돌 전제는 삭제 (현재 단일 `co.a`)

이번 분석에서는 검증 문서의 형식·문체를 유지한 채 잘못된 전제만 수정했습니다.
