# 24. DAO-Mapper 분석

## 1. 결론

현재 PDMG Mapper XML은 DAO 인터페이스와 정상적으로 연결되어 있습니다.

```text
DAO 메서드
→ namespace + statement ID
→ Mapper XML
→ PreparedStatement
→ RDW DataSource
→ Oracle/H2
```

점검 결과:

| 항목                       | 상태                   |
| -------------------------- | ---------------------- |
| XML 4개 로딩 경로          | 정상                   |
| namespace와 DAO FQCN       | 모두 일치              |
| DAO 메서드와 statement ID  | 모두 일치              |
| 동적 조건과 Service Map 키 | 일치                   |
| SQL Injection 방어         | `#{}` 사용, 정상       |
| 페이징                     | 5530·8888·9000 적용    |
| count/list 조건 공유       | 적용                   |
| C/U/D SQL                  | 9000 적용              |
| 다건 삭제                  | 8888·9000 적용         |
| SQL Statement Timeout      | 없음                   |
| Mapper 통합 테스트         | 없음                   |
| H2 스키마 정합성           | `8888`에서 불일치 발견 |
| 대량 IN 방어               | 없음                   |

가장 직접적인 오류 가능성은 다음입니다.

> `mgcoa8888-ORA.xml`은 `REQUEST_MSG`, `RESPONSE_MSG`를 조회하지만 로컬 H2 `TB_FW_IMAGE_LOG` 테이블에는 두 컬럼이 없습니다. 따라서 로컬에서 `mgcoa8888S0` 실행 시 컬럼 없음 SQL 오류가 발생할 수 있습니다.


# 3. Mapper 등록 전체 흐름

```text
RdwDataSourceConfig
├─ rdwDataSource
├─ rdwSqlSessionFactory
│    ├─ Mapper XML 로딩
│    ├─ JdbcTypeForNull=NULL
│    ├─ callSettersOnNulls=true
│    └─ MybatisLogInterceptor
├─ rdwSqlSessionTemplate
└─ rdwTransactionManager

@MapperScan
└─ persistence.dao 인터페이스 Proxy 생성
```

DAO 호출 시 MyBatis는 다음 식별자로 SQL을 찾습니다.

```text
namespace + "." + statement id
```

예:

```text
nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
    .mgcoa9000C0_C0
```

# 6. 파라미터 바인딩

현재 모든 사용자 입력은 `#{}`로 바인딩됩니다.

```xml
AND T1.TX_ID = #{txId}
```

MyBatis는 이를 PreparedStatement 파라미터로 처리합니다.

```sql
AND T1.TX_ID = ?
```

따라서 SQL Injection 관점에서는 적절합니다.

위험한 `${}` 사용은 확인되지 않았습니다.

```xml
<!-- 현재 사용하지 않음 -->
AND T1.TX_ID = '${txId}'
```

## Service Map과 XML 키

| Mapper 키            | Service 입력 |
| -------------------- | ------------ |
| `trtBrc`             | 5530 Service |
| `basDt`              | 5530 Service |
| `guid`               | 8888 Service |
| `serviceId`          | 8888 Service |
| `requestTimeFrom/To` | 8888 Service |
| `minElapsedSeconds`  | 8888 Service |
| `keyword`            | 9000 Service |
| `txId`               | 9000 Service |
| `offset`             | 조회 Service |
| `pageSize`           | 조회 Service |
| `guidList`           | 8888 삭제    |
| `txIdList`           | 9000 삭제    |
| `salzTipKdc`         | 9999 Service |

현재 확인된 키는 서로 일치합니다.

다만 `Map<String,Object>` 기반이므로 키 오타를 컴파일러가 잡지 못합니다.

```java
param.put("txID", value);  // 컴파일 성공
```

```xml
#{txId}                    <!-- 런타임에서 문제 -->
```

# 7. 공통 동적 SQL

조회 Mapper는 `<sql>`과 `<include>`로 WHERE 조건을 재사용합니다.

```xml
<sql id="mgcoa9000Where">
    WHERE 1 = 1
    ...
</sql>
```

```xml
<include refid="mgcoa9000Where"/>
```

목록과 count가 같은 조건을 공유합니다.

```text
목록 SELECT
└─ mgcoa9000Where

COUNT SELECT
└─ mgcoa9000Where
```

장점:

- 목록과 전체 건수 조건 불일치 방지
- 조건 추가 시 한 곳만 수정
- 페이징 메타데이터 정확성 향상

5530, 8888, 9000에 정상 적용되어 있습니다.

9999는 count와 페이징 자체가 없어 공통 WHERE가 별도로 없습니다.

# 8. Oracle ROWNUM 페이징

5530, 8888, 9000은 같은 구조를 사용합니다.

```sql
SELECT *
FROM (
    SELECT a.*, ROWNUM rnum
    FROM (
        SELECT ...
        FROM ...
        WHERE ...
        ORDER BY ...
    ) a
    WHERE ROWNUM <= #{offset} + #{pageSize}
)
WHERE rnum > #{offset}
```

처리 예:

```text
pageNo   = 2
pageSize = 20
offset   = 20
```

SQL 범위:

```text
ROWNUM <= 40
rnum > 20
→ 21~40번 행 반환
```

현재 Service의 offset 계산과 일치합니다.

```java
offset = (pageNo - 1) * pageSize;
```

## 안정적인 정렬

페이징 SQL에는 고정 정렬이 필요합니다.

| Mapper | 정렬                           | 평가        |
| ------ | ------------------------------ | ----------- |
| 5530   | `L5101`                        | 일부 안정적 |
| 8888   | `REQUEST_TIME DESC, GUID DESC` | 안정적      |
| 9000   | `REG_DTM DESC, TX_ID ASC`      | 안정적      |
| 9999   | 없음                           | 불안정      |

5530의 `L5101`이 결과 집합에서 유일하지 않다면 같은 값 사이 순서는 보장되지 않습니다. PK가 `(L5101, L5103)`이므로 안정적인 페이징을 위해서는 다음처럼 고유 조합까지 정렬하는 편이 안전합니다.

```sql
ORDER BY T1.L5101, T1.L5103
```

# 9. `SELECT *`와 `rnum`

페이징 외곽 쿼리는 다음과 같습니다.

```sql
SELECT *
FROM (
    SELECT a.*, ROWNUM rnum
    ...
)
```

따라서 결과 Map에는 업무 컬럼 외에 `RNUM`도 포함될 수 있습니다.

```text
L5101
L5102
L5103
L5104
RNUM
```

현재 Service가 필요한 키만 읽기 때문에 기능상 문제는 없지만 결과 계약이 불필요하게 넓어집니다.

명시적으로 컬럼을 선택하면 더 명확합니다.

```sql
SELECT L5101, L5102, L5103, L5104
FROM (...)
```

# 10. `mgcoa5530` 분석

검색 조건:

```xml
AND T1.L5104 = #{trtBrc}
AND T1.L5103 = #{basDt}
```

조건 자체는 단순하고 바인딩도 안전합니다.

Index Hint:

```sql
/*+ INDEX(T1 TB_MK_CO_A_5530_PK) */
```

현재 H2 PK:

```text
TB_MK_CO_A_5530_PK
(L5101, L5103)
```

하지만 주요 조건은 `L5103`, `L5104`이고 정렬은 `L5101`입니다. PK의 선두 컬럼은 `L5101`이므로 검색 조건에 따라 Hint가 항상 유리하다고 단정할 수 없습니다.

운영 Oracle에서 다음 조건별 실행계획을 확인해야 합니다.

```text
L5103만 검색
L5104만 검색
L5103 + L5104 검색
조건 없이 페이징
```

# 11. `mgcoa8888` 분석

## 검색 조건

- GUID 정확히 일치
- 서비스 ID 부분 일치
- 화면 ID 부분 일치
- 사용자번호 일치
- 예외 거래만
- 요청시각 범위
- 최소 처리시간

### 부분 일치 검색

```xml
T1.SERVICE_ID LIKE '%' || #{serviceId} || '%'
```

파라미터 바인딩이라 SQL Injection은 방지되지만 사용자 입력의 `%`, `_`는 와일드카드로 동작합니다.

```text
serviceId = %
→ 대부분의 데이터와 일치
```

또한 선행 `%` 때문에 일반 인덱스 사용이 어렵습니다.

### 처리시간 계산

```sql
(
  TO_DATE(SUBSTR(RESPONSE_TIME, 1, 14), 'YYYYMMDDHH24MISS')
  -
  TO_DATE(SUBSTR(REQUEST_TIME, 1, 14), 'YYYYMMDDHH24MISS')
) * 86400
```

문제점:

- 문자열을 매 행 날짜로 변환
- 일반 인덱스 사용 어려움
- 잘못된 날짜 문자열이면 변환 오류 가능
- `LENGTH >= 14`만으로 날짜 유효성을 보장하지 못함
- SQL 조건 평가 순서는 보장되지 않으므로 길이 검사 후에만 `TO_DATE`가 실행된다고 단정할 수 없음

운영 데이터에 잘못된 일시값이 한 건만 있어도 전체 조회가 실패할 수 있습니다.

권장 구조는 저장할 때 별도 숫자 컬럼을 두는 것입니다.

```text
ELAPSED_MS
```

그러면 검색은 단순해집니다.

```sql
AND T1.ELAPSED_MS >= #{minElapsedMs}
```

# 12. H2 스키마 불일치

Mapper는 다음 컬럼을 조회합니다.

```xml
T1.REQUEST_MSG
T1.RESPONSE_MSG
```

하지만 로컬 [schema.sql](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/db/h2/schema.sql:10>)의 `TB_FW_IMAGE_LOG`에는 다음 컬럼까지만 있습니다.

```text
GUID
SERVICE_ID
SCREEN_ID
OPTR_ENO
CLIENT_IP
REQUEST_TIME
RESPONSE_TIME
EXCEPTION_TYPE
EXCEPTION_CODE
EXCEPTION_MSG
```

누락:

```text
REQUEST_MSG
RESPONSE_MSG
```

따라서 로컬 H2에서 이미지로그 목록을 실행하면 다음 종류의 오류가 발생할 가능성이 큽니다.

```text
Column "T1.REQUEST_MSG" not found
```

Mapper XML은 애플리케이션 기동 시 파싱되지만 실제 컬럼 유효성은 SQL 실행 시 확인됩니다. 따라서 애플리케이션이 기동됐다고 Mapper가 정상이라는 뜻은 아닙니다.

이 부분은 문서에 기록되지 않은 실제 정합성 문제입니다.

# 13. 이미지로그 전문 조회 비용

`mgcoa8888S0_S0` 목록 SQL이 요청·응답 전문까지 함께 조회합니다.

```sql
REQUEST_MSG
RESPONSE_MSG
```

전문이 크면 한 페이지 100건에서도 다음 비용이 커집니다.

- DB I/O
- 네트워크 전송량
- JVM 메모리
- CLOB→String 변환
- JSON 직렬화
- 업무 후처리 DTO 로그
- 브라우저 렌더링

권장 구조:

```text
목록 조회
→ GUID, serviceId, 시각, 오류코드 등 요약만

상세 조회
→ 특정 GUID의 REQUEST_MSG/RESPONSE_MSG 조회
```

전문 조회를 분리하면 목록 성능과 로그 안정성이 좋아집니다.

# 14. `mgcoa9000` 분석

## 키워드 검색

```sql
UPPER(TX_ID) LIKE '%' || UPPER(#{keyword}) || '%'
OR UPPER(TX_NAME) LIKE ...
OR UPPER(NVL(APP_ID, '')) LIKE ...
```

한 번에 다섯 컬럼을 부분 검색합니다.

데이터가 커지면:

- Full Scan 가능성
- 여러 `UPPER()` 연산
- 여러 OR 조건
- count와 목록에서 동일 비용 발생

관리성 소규모 테이블이면 허용 가능하지만 대량 거래 카탈로그로 성장하면 별도의 검색 인덱스나 검색 조건 제한이 필요합니다.

## EXISTS

```sql
SELECT COUNT(*)
FROM TB_MG_TX_PARAM
WHERE TX_ID = #{txId}
```

존재 여부만 필요하므로 Oracle에서는 다음 형태가 더 효율적일 수 있습니다.

```sql
SELECT COUNT(*)
FROM (
    SELECT 1
    FROM TB_MG_TX_PARAM
    WHERE TX_ID = #{txId}
      AND ROWNUM = 1
)
```

하지만 `TX_ID`가 PK라면 최대 한 건이므로 현재 COUNT도 큰 문제는 아닙니다.

## 중복 동시성

```text
EXISTS
→ INSERT
```

사이에 다른 거래가 INSERT할 수 있습니다. H2 스키마에는 `TX_ID` PK가 있으므로 최종 중복은 DB가 방어합니다.

운영 Oracle에도 동일한 PK/UNIQUE 제약이 있어야 합니다.

# 15. `mgcoa9999` 분석

현재 SQL은 조건 조회만 합니다.

```sql
SELECT ...
FROM TB_CR_AH_SALES_TIP_RACT
WHERE 1 = 1
  AND SALZ_TIP_KDC = ?
```

문제점:

- 페이징 없음
- count 없음
- ORDER BY 없음
- 조회 상한 없음

입력 조건도 없으면 전체 테이블을 조회합니다.

```text
salzTipKdc 없음
→ WHERE 1=1
→ 전체 조회
```

데이터가 증가하면 온라인 5초 타임아웃과 메모리 문제를 유발할 수 있습니다.

```text
필수 검색조건 지정
또는
pageNo/pageSize 적용
또는
최대 조회 건수 제한
```

그리고 결과 순서를 명확히 해야 합니다.

# 16. 다건 삭제 `<foreach>`

8888:

```xml
<foreach collection="guidList"
         item="guid"
         open="("
         separator=","
         close=")">
    #{guid}
</foreach>
```

9000:

```xml
<foreach collection="txIdList"
         item="txId"
         open="("
         separator=","
         close=")">
    #{txId}
</foreach>
```

Service가 빈 목록을 차단하므로 `IN ()` 생성은 방지됩니다.

하지만 최대 크기는 제한하지 않습니다.

Oracle은 일반적으로 IN 표현식 1,000개 제한이 있으므로 1,001개 이상이면 다음 오류가 발생할 수 있습니다.

```text
ORA-01795
```

권장 방식:

```text
단순 관리 화면 → 요청 최대 500건 제한
대량 처리       → Chunk 분할 또는 전용 배치
```

Chunk로 나눌 경우에도 같은 외곽 트랜잭션 안에서 모두 실행해야 중간 실패 시 전체 롤백됩니다.

# 17. NULL 처리 설정

MyBatis 설정:

```java
mybatisConfig.setJdbcTypeForNull(JdbcType.NULL);
mybatisConfig.setCallSettersOnNulls(true);
```

### `JdbcTypeForNull`

값이 null일 때 JDBC에 `NULL` 타입으로 전달합니다.

```xml
#{appId}
```

값이 null이면 JDBC 바인딩에서 null로 처리됩니다.

### `callSettersOnNulls`

조회 결과가 null이어도 결과 객체나 Map에 값을 반영하도록 돕습니다.

현재 결과 타입이 `HashMap`이므로 null 컬럼도 Map 키로 포함될 수 있습니다.

하지만 DB별 컬럼명 대소문자 차이는 해결하지 않습니다. Service에서 upper/camel/ignoreCase 보정을 별도로 하는 이유입니다.

# 18. Oracle/H2 방언

현재 파일명은 모두 `-ORA.xml`입니다.

사용 문법:

- `ROWNUM`
- `NVL`
- `||`
- `TO_DATE`
- Oracle Hint
- `SUBSTR`

로컬은 H2 Oracle 모드입니다.

```yaml
jdbc-url: jdbc:log4jdbc:h2:mem:pdmg;
  MODE=Oracle;
  DB_CLOSE_DELAY=-1;
  DB_CLOSE_ON_EXIT=FALSE
```

H2 Oracle 모드가 많은 문법을 지원하지만 Oracle과 완전히 같지는 않습니다.

특히 검증이 필요한 부분:

- `TO_DATE` 동작
- 날짜 뺄셈 결과 단위
- ROWNUM 중첩 페이징
- CLOB 반환 타입
- Hint 무시 여부
- 빈 문자열과 NULL 처리 차이
- 문자열 정렬과 대소문자

H2 성공은 Oracle 성공을 보장하지 않고, 반대도 마찬가지입니다.

# 19. SQL Timeout

현재 XML에는 다음 속성이 없습니다.

```xml
timeout="4"
```

SqlSessionFactory에도 다음 설정이 없습니다.

```java
setDefaultStatementTimeout(...)
```

따라서 공통 타임아웃 5초는 JDBC SQL 실행 제한시간이 아닙니다.

```text
온라인 요청 제한     5초
SQL Statement 제한   없음
```

발생 가능한 흐름:

```text
SQL 실행 시작
→ 5초 후 HTTP 504
→ Worker interrupt 요청
→ JDBC가 interrupt를 무시
→ SQL 계속 실행
→ SQL 반환 후 deadline 검사
→ ROLLBACK
```

권장 개념:

```text
SQL 제한       4초
업무 제한      5초
Gateway 제한   7초 이상
UI 제한        10초 이상
```

다만 특정 서비스만 10초로 운영한다면 SQL timeout도 서비스 특성에 맞게 설계해야 합니다. 전역 4초만 적용하면 해당 서비스도 SQL은 4초에 종료됩니다.

# 20. SQL 로그

[MybatisLogInterceptor.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/MybatisLogInterceptor.java:35>)는 query/update를 감쌉니다.

```java
MDC.put("sqlId", statement.getId());

long startedAt = System.currentTimeMillis();

try {
    return invocation.proceed();
} finally {
    log.debug(
        "{} | param={} | {}ms",
        sqlId,
        parameter,
        elapsed
    );

    MDC.remove("sqlId");
}
```

출력 예:

```text
[SQL] ... |
nhnis.mg.co.a.persistence.dao.mgcoa9000DAO.mgcoa9000C0_C0 |
param={txId=..., txName=...} |
12ms
```

`finally`에서 MDC를 제거하므로 Thread Pool 재사용 시 sqlId 오염은 방지됩니다.

## 보안 위험

파라미터 Map 전체를 DEBUG로 출력합니다.

```java
param={}
```

향후 DAO 파라미터에 다음 값이 들어가면 그대로 로그에 남을 수 있습니다.

- 고객번호
- 계좌번호
- 사번
- 개인정보
- 인증 토큰
- 전문 원문

현재 별도의 마스킹이나 최대 길이 제한이 없습니다.

log4jdbc `jdbc.sqltiming`도 DEBUG로 활성화되어 있어 바인딩값이 포함된 SQL이 기록될 수 있습니다.

운영 SQL 로그 정책에는 반드시 다음이 필요합니다.

- 민감 필드 마스킹
- 전문 필드 제외
- 최대 길이 제한
- 운영 DEBUG 활성 범위 제한
- 로그 접근권한 및 보존기간 관리

# 21. Mapper 테스트 현황

현재 Mapper XML을 실제로 실행하는 전용 테스트는 확인되지 않습니다.

Service 테스트는 DAO를 Mock으로 대체합니다.

```java
@Mock
private mgcoa5530DAO dao;
```

따라서 다음을 검증하지 못합니다.

- Mapper XML이 실제로 로딩되는지
- namespace/ID 연결
- H2 SQL 문법
- 컬럼 존재 여부
- 동적 `<if>` 처리
- ROWNUM 페이징
- `<foreach>` 삭제
- C/U/D 영향 행 수
- 실제 트랜잭션 롤백
- SQL timeout

특히 `REQUEST_MSG`, `RESPONSE_MSG` 컬럼 불일치는 Mapper 실행 테스트가 있었다면 바로 발견됐을 가능성이 높습니다.
