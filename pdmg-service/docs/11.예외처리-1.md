## 11. 예외처리 분석 결과

[11.예외처리.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/11.예외처리.md>)는 현재 변경된 `result` 오류 전문 구조를 대체로 정확히 반영합니다.

다만 일반 시스템 예외가 표준화되지 않은 점, 두 개의 `@ControllerAdvice`가 겹치는 점, 업무 오류 메시지 사전이 실제 응답에 적용되지 않는 점을 보완해야 합니다.

## 1. 현재 성공·실패 전문

현재 구현은 성공과 실패를 서로 다른 키에 담습니다.

### 성공

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000S0"
    }
  },
  "dto": {
    "totalCount": 10
  }
}
```

### 실패

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000C0"
    }
  },
  "result": {
    "stdErrCode": "MP0409",
    "stdErrMsgCntn": "MP0409",
    "errType": "BIZ"
  }
}
```

[ResponseBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java:117>)에서 명시적으로 구분합니다.

```java
if (body instanceof NH_NIS_ERR_DTO) {
    responseBody.set("result", errorJson);
} else {
    responseBody.set("dto", bodyNode);
}
```

따라서 문서의 다음 설명은 현재 구현과 일치합니다.

```text
성공 = hdr_nhnis + dto
실패 = hdr_nhnis + result
```

이 부분은 이전 `dto` 오류 봉투 구조에서 변경되었습니다.

---

## 2. 예외 처리 전체 흐름

```text
Service/Facade/Dispatcher
  ↓ 예외 발생
Facade @Transactional
  ↓ Rollback 판단
GlobalExceptionHandler 또는 레거시 Advice
  ↓ NH_NIS_ERR_DTO 생성
ResponseBodyArgumentResolver
  ↓ result에 오류 DTO 저장
HTTP 응답
  ↓
Interceptor.afterCompletion
  ↓
ImageLog 오류 결과 저장
```

쓰기 거래에서는 Facade를 벗어날 때 예외가 유지돼야 Rollback됩니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

```text
예외 전파
  → Facade TransactionInterceptor
  → Rollback
  → ControllerAdvice
  → 오류 응답
```

ControllerAdvice가 응답으로 변환하는 것은 트랜잭션 종료 이후이므로, 정상적으로 예외가 Facade 밖까지 전파됐다면 응답 변환 때문에 Rollback이 취소되지는 않습니다.

## 3. 현재 명시적으로 처리되는 예외

[GlobalExceptionHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java:30>)는 다음 네 종류만 처리합니다.

| 예외                      | 코드            | errType   | HTTP |
| ------------------------- | --------------- | --------- | ---: |
| `ServiceHandlerNotFound`  | `E9999`         | `SERVICE` |  500 |
| `BizException`            | 업무 코드       | `BIZ`     |  500 |
| `OnlineTimeoutException`  | `FW_TIMEOUT`    | `COMMON`  |  504 |
| `OnlineOverloadException` | `FW_OVERLOADED` | `COMMON`  |  503 |

문서의 예외 유형 구분은 맞습니다.

다만 문서 표에 있는 다음 표현은 현재 구현과 다릅니다.

```text
BizException → 보통 200 + ERR DTO
```

현재 코드는 명확히 HTTP 500을 반환합니다.

```java
return error(
    e.getCode(),
    e.getMessage(),
    TYPE.BIZ,
    HttpStatus.INTERNAL_SERVER_ERROR,
    null
);
```

따라서 문서 전체를 다음 중 하나로 통일해야 합니다.

```text
현행: 업무 예외도 HTTP 500
```

또는 정책 변경 시:

```text
업무 오류: HTTP 200 + result
시스템 오류: HTTP 5xx
```

일반적으로는 업무 오류도 의미에 따라 400, 404, 409 등으로 구분하는 방식이 더 명확합니다.

## 4. `BizException`은 아직 업무에서 사용되지 않음

[BizException.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/BizException.java:3>)는 구현되어 있습니다.

```java
public class BizException extends RuntimeException {

    private final String code;
    private final Object[] args;

    public BizException(String code, Object... args) {
        super(code);
        this.code = code;
        this.args = args;
    }
}
```

하지만 현재 `pdmg-service` 업무 코드에서는 다음 사용이 확인되지 않습니다.

```java
throw new BizException(...);
```

즉, 문서는 권장 설계를 설명하지만 현재 업무 구현에 실제 적용된 상태는 아닙니다.

`mgcoa9000` 등의 중복·미존재 검증에서 단순 결과 DTO나 다른 예외를 사용하고 있다면 표준 `BizException`으로 통일해야 합니다.

## 5. 메시지 사전이 응답에 연결되지 않음

[exceptionCode.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/exceptionCode.yml>)에는 메시지가 정의되어 있습니다.

```yaml
nhnis:
  exception:
    MP0404: "요청한 영업팁 실적을 찾을 수 없습니다."
    MP0409: "동일한 기본키의 영업팁 실적이 이미 존재합니다."
```

[ExceptionCodeProperties.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/ExceptionCodeProperties.java:16>)도 정상적으로 메시지를 조회할 수 있습니다.

```java
properties.message("MP0409")
```

그러나 `GlobalExceptionHandler`는 이를 사용하지 않습니다.

```java
return error(
    e.getCode(),
    e.getMessage(),
    TYPE.BIZ,
    ...
);
```

`BizException` 생성자는 `super(code)`를 호출하므로:

```java
throw new BizException("MP0409");
```

현재 응답은 다음처럼 될 수 있습니다.

```json
{
  "stdErrCode": "MP0409",
  "stdErrMsgCntn": "MP0409"
}
```

기대한 메시지는 나오지 않습니다.

권장 구현:

```java
private final ExceptionCodeProperties exceptionCodes;

@ExceptionHandler(BizException.class)
public ResponseEntity<NH_NIS_ERR_DTO> handleBizException(
        BizException e) {

    String message =
        exceptionCodes.message(e.getCode(), e.getArgs());

    return error(
        e.getCode(),
        message,
        TYPE.BIZ,
        HttpStatus.INTERNAL_SERVER_ERROR,
        null
    );
}
```

문서도 이 문제를 인지하고 있지만 “바람직하다” 수준이 아니라 현재 필수 보완사항에 가깝습니다.

## 6. 일반 시스템 예외 Handler가 없음

현재 `GlobalExceptionHandler`에는 다음 처리가 없습니다.

```java
@ExceptionHandler(Exception.class)
```

따라서 다음 예외는 표준 `NH_NIS_ERR_DTO`가 보장되지 않습니다.

- `NullPointerException`
- `IllegalArgumentException`
- DTO `convertValue()` 실패
- MyBatis 예외
- SQL 예외
- DataSource 접속 실패
- 기타 RuntimeException

이 예외들은 Spring Boot 기본 오류 처리로 전달될 수 있습니다.

예상 가능한 결과:

```json
{
  "timestamp": "...",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/mgcoa9000C0"
}
```

`ResponseBodyAdvice`가 이 Map을 다시 성공 DTO처럼 감싸면 다음처럼 보일 가능성도 있습니다.

```json
{
  "hdr_nhnis": {...},
  "dto": {
    "status": 500,
    "error": "Internal Server Error"
  }
}
```

즉, 시스템 오류인데 `result`가 아니라 `dto`에 들어갈 수 있습니다.

일반 시스템 예외 Handler가 필요합니다.

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<NH_NIS_ERR_DTO> handleException(
        Exception e) {

    log.error(
        "[GlobalExceptionHandler] unhandled exception",
        e
    );

    String message =
        exceptionCodes.message("FW9999");

    return error(
        "FW9999",
        message,
        TYPE.RUNTIME,
        HttpStatus.INTERNAL_SERVER_ERROR,
        null
    );
}
```

클라이언트에는 일반 메시지만 반환하고 상세 Stack Trace는 서버 로그에만 기록해야 합니다.

## 7. 두 개의 ControllerAdvice가 중첩됨

현재 예외를 처리하는 Advice가 두 개입니다.

### TCF Advice

```java
@RestControllerAdvice
public class GlobalExceptionHandler
```

처리:

- `ServiceHandlerNotFound`
- `BizException`
- Timeout
- Overload

### 레거시 Advice 겸 ResponseBodyAdvice

```java
@ControllerAdvice
public class ResponseBodyArgumentResolver
```

처리:

```java
@ExceptionHandler(NhBaseException.class)
```

문제는 `ServiceHandlerNotFound`가 `NhBaseException` 계열이라는 점입니다.

따라서 다음 두 Handler가 동시에 후보가 됩니다.

```text
GlobalExceptionHandler
  → ServiceHandlerNotFound 전용 Handler

ResponseBodyArgumentResolver
  → NhBaseException 포괄 Handler
```

두 Advice에 명시적인 `@Order`가 없어 어떤 Advice가 먼저 적용되는지 명확하지 않습니다.

이로 인해 동일 예외가 환경에 따라 다음 중 다른 경로로 처리될 위험이 있습니다.

```text
GlobalExceptionHandler → E9999 / SERVICE
레거시 errorProcessor → 예외 내부 코드와 MessageCache
```

권장:

```java
@RestControllerAdvice
@Order(Ordered.HIGHEST_PRECEDENCE)
public class GlobalExceptionHandler
```

레거시 Advice에는 더 낮은 우선순위를 부여합니다.

```java
@ControllerAdvice
@Order(Ordered.LOWEST_PRECEDENCE)
public class ResponseBodyArgumentResolver
```

장기적으로는 예외 Handler와 `ResponseBodyAdvice` 클래스를 분리하는 편이 안전합니다.

## 8. 레거시 `NhBaseException` Handler의 null 오류

[ResponseBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java:155>)에는 다음 흐름이 있습니다.

```java
if (e.getErrMsgType() == null) {
    errorDto.setErrType(TYPE.RUNTIME.name());
}
```

그런데 아래에서는 다시 원래 값을 switch 합니다.

```java
switch (e.getErrMsgType()) {
    case TYPE.RUNTIME, TYPE.COMMON, TYPE.AUTH -> ...
    case TYPE.SERVICE, TYPE.BIZ -> ...
}
```

`getErrMsgType()`이 null이고 `stdErrMsgContents`도 null이면 `switch(null)`로 인해 `NullPointerException`이 발생할 수 있습니다.

안전한 구조:

```java
TYPE type = e.getErrMsgType() == null
        ? TYPE.RUNTIME
        : e.getErrMsgType();

errorDto.setErrType(type.name());

switch (type) {
    // ...
}
```

## 9. Stack Trace 외부 노출

레거시 Handler는 Stack Trace 상위 15개를 응답 DTO에 넣습니다.

```java
errorDto.setStackTrace(
    getTop15StackTrace(e.getStackTrace())
);
```

이 정보에는 다음이 포함될 수 있습니다.

- 내부 패키지명
- 클래스명
- 메서드명
- 파일명
- 소스 라인
- 프레임워크 구조

이는 운영 응답에서 제거해야 합니다.

권장:

```text
서버 로그       → 전체 Stack Trace
ImageLog        → 오류 코드·안전한 메시지
클라이언트 응답 → 코드·사용자 메시지·GUID
```

클라이언트에는 GUID를 제공해 운영 로그를 조회할 수 있게 하는 편이 안전합니다.

## 10. ImageLog 오류 저장

현재 오류 전문은 `result`에 들어가며 ImageLog도 동일 구조를 파싱합니다.

[ImageLogHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/imagelog/ImageLogHandler.java:360>)

```java
JsonNode result = root.get("result");
JsonNode codeNode = result.get("stdErrCode");
JsonNode msgNode = result.get("stdErrMsgCntn");
JsonNode typeNode = result.get("errType");
```

따라서 다음 연결은 현재 일치합니다.

```text
ResponseBodyAdvice
  result.stdErrCode
       ↓
ImageLogHandler
  EXCEPTION_CODE
```

이 부분은 정상입니다.

또한 ControllerAdvice가 예외를 처리해 정상적인 응답으로 변환하면 `afterCompletion()`의 `ex`는 null이 될 수 있습니다. 이 경우 `postImagelog()`가 `result.stdErrCode`를 읽어 오류 컬럼을 기록합니다.

## 11. Interceptor에서 예외를 다시 던지는 문제

[ServicePreventionInterceptor.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/interceptor/ServicePreventionInterceptor.java:255>)는 `afterCompletion()`에서 다음과 같이 처리합니다.

```java
if (ex != null) {
    imageLogHandler.exceptionImagelog(...);
    ServiceContextHolder.removeInstance();
    throw ex;
}
```

`afterCompletion()`은 이미 요청 처리가 끝난 뒤 정리하는 단계입니다. 여기서 원래 예외를 다시 던질 필요가 없습니다.

가능한 문제:

- 완료 처리 중 추가 예외 로그
- Container의 중복 오류 처리
- 실제 원인과 후처리 오류 혼동
- 응답이 이미 작성된 후 예외 재발생

권장:

```java
if (ex != null) {
    imageLogHandler.exceptionImagelog(...);
    return;
}
```

원래 예외는 DispatcherServlet이 이미 관리하고 있습니다.

## 12. Filter 예외는 중앙 Handler 밖에 있음

`DefaultFilter`는 다음 오류를 `sendError()`로 직접 반환합니다.

| 오류              | HTTP |
| ----------------- | ---: |
| Access Token 없음 |  401 |
| Token 검증 실패   |  401 |
| Access Token 아님 |  401 |
| Body 없음         |  400 |
| 잘못된 JSON       |  400 |
| 공통 Header 없음  |  400 |
| Filter 내부 오류  |  400 |

이 오류는 Controller에 도달하지 않으므로 `GlobalExceptionHandler`를 거치지 않습니다.

따라서 다음 표준 오류 전문이 보장되지 않습니다.

```json
{
  "hdr_nhnis": {...},
  "result": {
    "stdErrCode": "FW0401"
  }
}
```

Servlet 기본 오류 JSON이나 HTML 응답이 내려갈 수 있습니다.

앞서 CORS 분석과 연결하면 Filter에서 조기 종료할 때 CORS 헤더도 누락될 수 있습니다.

장기적으로는 Filter 전용 오류 Writer가 필요합니다.

```text
FilterExceptionResponseWriter
  ├─ HTTP 상태 설정
  ├─ Content-Type application/json
  ├─ hdr_nhnis 구성
  ├─ result.stdErrCode
  └─ 안전한 오류 메시지
```

## 13. Timeout과 Rollback

Timeout 시 메인 요청 흐름은 다음과 같습니다.

```text
TimeoutExecutor
  ↓ 제한시간 초과
future.cancel(true)
  ↓
OnlineTimeoutException
  ↓
GlobalExceptionHandler
  ↓ HTTP 504 + result.FW_TIMEOUT
```

하지만 실제 Worker 작업 취소와 트랜잭션 Rollback은 Worker가 인터럽트를 제대로 전파해야 합니다.

현재 `mgcoa5530Service`는 `InterruptedException`을 잡은 뒤 다시 던지지 않고 업무를 계속합니다.

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    log.warn(...);
}
```

따라서 HTTP는 504가 반환돼도 Worker에서 DAO 작업이 계속될 수 있습니다.

예외 처리 문서에는 다음 조건을 추가해야 합니다.

```text
InterruptedException은 삼키지 않는다.
인터럽트 상태를 복구한 후 반드시 예외를 전파한다.
```

## 14. 현재 예외 처리 매트릭스

| 발생 위치            | 현재 처리             | 표준 `result` | 주요 문제               |
| -------------------- | --------------------- | ------------: | ----------------------- |
| `BizException`       | Global Handler        |            예 | 메시지가 코드로 나감    |
| Handler 미등록       | 두 Advice 후보        |        불확실 | Advice 우선순위 없음    |
| Timeout              | Global Handler        |            예 | Worker 취소 미완성      |
| Executor 과부하      | Global Handler        |            예 | 정상                    |
| `NhBaseException`    | 레거시 Handler        |            예 | null switch·Stack Trace |
| 일반 Runtime/DB 예외 | Spring 기본 처리 가능 |    보장 안 됨 | 일반 Handler 없음       |
| Filter 인증 오류     | `sendError()`         |        아니오 | CORS·전문 불일치        |
| 잘못된 JSON          | Filter `sendError()`  |        아니오 | 표준 오류 없음          |

| -------- | -------------------------------------------------------- |

## 최종 평가

문서 정확도는 약 75~80%입니다.

문서가 정확한 부분:

- 성공 `dto`, 실패 `result` 분리
- Facade 예외 전파와 Rollback 관계
- Timeout 504 및 Overload 503
- ImageLog의 `result.stdErrCode` 연계
- 업무 예외를 Service에서 발생시키는 방향

수정이 필요한 부분:

- 업무 예외 HTTP 200 설명과 실제 500의 모순
- `BizException`이 아직 업무에서 사용되지 않음
- 메시지 사전이 응답에 연결되지 않음
- 일반 시스템 예외의 표준 처리 부재
- 두 Advice의 처리 중첩
- Filter 오류가 표준 예외 처리 밖에 있음

핵심적으로 현재 구조는 다음 상태입니다.

```text
알려진 네 가지 예외
  → result 오류 전문으로 처리됨

일반 Runtime/DB/JSON/Filter 예외
  → 동일한 result 전문이 보장되지 않음

따라서 “모든 실패가 중앙 예외처리로 통일됐다”고 보기는 어렵다.
```
