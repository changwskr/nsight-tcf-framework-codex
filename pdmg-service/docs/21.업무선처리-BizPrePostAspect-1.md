# 21. 업무선처리 `BizPrePostAspect` 분석

## 1. 결론

현재 `BizPrePostAspect`는 업무 검증이나 데이터 변경을 수행하는 선처리기가 아니라, Service 호출 전후에 거래 진행 정보를 기록하는 로깅 Aspect입니다.

실제 적용 위치는 다음과 같습니다.

```text
Handler
  → Business Facade
    → DTO 변환
    → Service 프록시
        → PdmgBizTxFlowAspect 시작
        → BizPrePostAspect.before       업무 선처리 로그
        → Service
          → DAO / SQL
        → BizPrePostAspect.after        업무 후처리 로그
        → PdmgBizTxFlowAspect 종료
```

핵심 특성은 다음과 같습니다.

| 항목               | 현행                                     |
| ------------------ | ---------------------------------------- |
| 적용 대상          | `application.service` 아래 public 메서드 |
| 업무 선처리        | GUID, serviceId, 호출 메서드, BRC 로그   |
| 업무 후처리        | 정상 반환 결과 DTO 로그                  |
| DB 처리            | 없음                                     |
| 트랜잭션 시작·종료 | 하지 않음                                |
| 예외 후처리        | 없음                                     |
| 활성 조건          | `legacy-web.enabled=true`                |
| 실행 순서          | `@Order(100)`                            |

소스: [BizPrePostAspect.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/entry/aspect/BizPrePostAspect.java:28>)

## 2. 활성화 조건

클래스 선언은 다음과 같습니다.

```java
@Aspect
@Component
@Order(100)
@ConditionalOnProperty(
    name = "nhnis.fw.commons.legacy-web.enabled",
    havingValue = "true",
    matchIfMissing = true
)
public class BizPrePostAspect {
}
```

현재 [application.yml](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml:57>)에는 다음 설정이 있습니다.

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: true
```

따라서 현재는 활성화 상태입니다.

다음처럼 설정하면 Aspect Bean 자체가 생성되지 않습니다.

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: false
```

이 경우 없어진 것은 업무 자체가 아니라 다음 공통 로그입니다.

- 업무 선처리 시작·종료
- GUID, 서비스 ID, 호출 메서드, BRC
- 업무처리 시작·종료
- 업무 후처리 시작·종료
- 결과 DTO 로그

Service와 DAO는 정상 호출됩니다.

다만 업무 선후처리의 활성 조건이 `legacy-web`에 종속된 것은 구조적으로 다소 어색합니다. 장기적으로는 다음과 같이 독립 설정으로 분리하는 것이 명확합니다.

```yaml
nhnis:
  fw:
    biz-pre-post:
      enabled: true
```

## 3. 실제 포인트컷

현재 포인트컷은 다음과 같습니다.

```java
@Pointcut(
    "execution(public * " +
    "nhnis.mg.co.a.application.service..*(..))"
)
public void mgBizBoundary() {
}
```

의미를 분해하면 다음과 같습니다.

| 표현                    | 의미                              |
| ----------------------- | --------------------------------- |
| `execution`             | 메서드 실행 시점                  |
| `public *`              | 반환형과 관계없이 public 메서드   |
| `application.service..` | service 패키지와 모든 하위 패키지 |
| `*(..)`                 | 모든 메서드명과 모든 파라미터     |

예를 들어 다음 메서드는 적용됩니다.

```java
package nhnis.mg.co.a.application.service;

@Service
public class mgcoa9000Service {

    public mgcoa9000C0DTOout mgcoa9000C0(
            mgcoa9000C0DTOin input) {
        // Aspect 적용
    }
}
```

다음은 적용되지 않습니다.

```java
private void validate() { }       // public 아님
protected void calculate() { }    // public 아님
```

Service 패키지 밖이면 클래스 이름이 `Service`로 끝나도 적용되지 않습니다.

```java
package nhnis.mg.co.a.application.rule;

public class CustomerService {
    // 이름은 Service지만 패키지가 다르므로 적용되지 않음
}
```

즉, 클래스 이름이 아니라 패키지와 public 메서드 조건으로 적용됩니다.

## 4. 업무 선처리 내용

선처리는 `@Before`로 구현되어 있습니다.

```java
@Before("mgBizBoundary()")
public void before(JoinPoint joinPoint) {
    log.info(PdmgTxLog.bizPreStart());
    logBizPreProgress(joinPoint);
    log.info(PdmgTxLog.bizPreEnd());
    log.info(PdmgTxLog.bizProcessStart());
}
```

실행되는 위치는 Service 본문 직전입니다.

```text
Service 프록시 진입
→ 업무 선처리 시작
→ 거래 정보 출력
→ 업무 선처리 종료
→ 업무처리 시작
→ 실제 Service 메서드 실행
```

### 기록하는 정보

`logBizPreProgress()`는 다음 정보를 기록합니다.

```java
log.info(PdmgTxLog.bizPreProgress("GUID: " + guid));
log.info(PdmgTxLog.bizPreProgress("서비스: " + serviceId));
log.info(PdmgTxLog.bizPreProgress("호출: " + method));
log.info(PdmgTxLog.bizPreProgress("BRC: " + extractBrc(...)));
```

개념적인 로그는 다음과 같습니다.

```text
[업무 선처리] 시작 ===============================================
[업무 선처리] GUID: 20260810...
[업무 선처리] 서비스: mgcoa9000C0
[업무 선처리] 호출: mgcoa9000Service.mgcoa9000C0
[업무 선처리] BRC: 001
[업무 선처리] 종료 ===============================================
[업무처리] 시작 ===============================================
```

## 5. GUID와 서비스 ID 조회

GUID와 서비스 ID는 `ServiceContextHolder`에서 가져옵니다.

```java
ServiceContext ctx =
        ServiceContextHolder.getInstance();

String guid =
        ctx != null ? ctx.getGuid() : null;
```

서비스 ID는 표준 헤더에서 찾습니다.

```java
ctx.getHeader()
   .getSys_comm()
   .getRms_svc_c();
```

따라서 정상적인 온라인 거래에서는 다음 흐름으로 값이 전달됩니다.

```text
DefaultFilter
→ ServiceContext 생성
→ hdr_nhnis 설정
→ rms_svc_c 설정
→ Timeout Worker로 Context 전달
→ BizPrePostAspect에서 조회
```

Context가 없거나 헤더가 없더라도 예외는 발생하지 않습니다.

```text
GUID: null
서비스: null
```

로그만 `null`로 남고 Service는 계속 실행됩니다. 즉, 현재 Aspect는 Context 누락을 통제하지 않는 fail-open 방식입니다.

## 6. BRC 추출 방식

BRC는 Service 인자에서 Reflection으로 찾습니다.

검색 순서는 다음과 같습니다.

```java
getTrtBrc
getBrc
getBRC
getL5104
```

예를 들어 DTO가 다음 메서드를 제공하면:

```java
public String getTrtBrc() {
    return trtBrc;
}
```

Aspect가 자동으로 호출해 로그에 기록합니다.

### 현재 방식의 한계

DTO에 해당 getter가 없으면 다음처럼 처리됩니다.

```java
catch (ReflectiveOperationException ignored) {
    // 다음 이름 시도
}
```

따라서 다음 상황을 구분할 수 없습니다.

- DTO에 BRC가 원래 없는 경우
- getter 이름이 변경된 경우
- getter 접근 중 예외가 발생한 경우
- 예상 DTO가 아닌 객체가 전달된 경우

모두 최종적으로 다음 로그만 남습니다.

```text
[업무 선처리] BRC: null
```

또한 getter를 Reflection으로 호출하므로 이름이 문자열에 묶여 있습니다. 필드명이 바뀌어도 컴파일 오류가 발생하지 않습니다.

업무 통제에서 BRC가 필수라면 Reflection 로깅값을 사용하면 안 됩니다. 표준 인터페이스나 `ServiceContext.userContext`처럼 명확하게 검증된 값을 사용해야 합니다.

## 7. 트랜잭션과의 관계

### 타임아웃 활성 상태

현재는 `nhnis.fw.timeout.enabled=true`이므로 실제 최외곽 트랜잭션은 `OnlineTimeoutExecutor`가 시작합니다.

```text
Worker Thread
→ TransactionTemplate BEGIN
  → Dispatcher
    → Handler
      → Facade @Transactional(REQUIRED)
        → BizPrePostAspect.before
        → Service
        → DAO / SQL
        → BizPrePostAspect.afterReturning
  → 제한시간 검사
→ COMMIT 또는 ROLLBACK
```

이 경우:

- Executor가 실제 트랜잭션을 시작합니다.
- Facade는 기존 트랜잭션에 참여합니다.
- 업무 선후처리는 트랜잭션 안에서 실행됩니다.

### 타임아웃 비활성 상태

```text
Handler
→ Facade @Transactional BEGIN
  → BizPrePostAspect.before
  → Service / DAO
  → BizPrePostAspect.afterReturning
→ COMMIT
```

이 경우 Facade가 트랜잭션을 시작합니다.

### TCF 비활성 상태

현재 레거시 Controller가 Service를 직접 호출하면:

```text
Controller
→ BizPrePostAspect.before
→ Service / DAO
→ BizPrePostAspect.afterReturning
```

Aspect는 실행되지만 Facade를 통하지 않으므로 트랜잭션은 없을 수 있습니다.

따라서 다음 두 문장은 서로 다릅니다.

```text
“업무 선처리가 실행된다”       → TCF OFF에서도 가능
“업무 선처리가 TX 안에 있다”   → Facade/Executor TX가 있을 때만 가능
```

## 8. 선처리에서 DB 작업을 한다면

현재 선처리는 로그만 남깁니다.

만약 `before()`에서 DAO를 호출하여 한 건을 INSERT하면, TCF ON의 정상 Handler→Facade→Service 경로에서는 기존 트랜잭션에 참여합니다.

```text
Transaction BEGIN
  → BizPrePostAspect.before
       → 공통 이력 INSERT
  → Service
       → 업무 UPDATE
  → afterReturning
Transaction COMMIT
```

Service에서 예외가 발생하면 선처리 INSERT도 같이 롤백됩니다.

```text
선처리 INSERT
→ Service UPDATE
→ Service 예외
→ 전체 ROLLBACK
```

하지만 권장하지는 않습니다. 이유는 다음과 같습니다.

- 모든 Service public 메서드마다 실행됨
- 한 거래에서 Service를 두 번 호출하면 두 번 INSERT됨
- 내부 보조 Service에도 적용될 수 있음
- TCF OFF에서는 트랜잭션 없이 자동 커밋될 수 있음
- 로깅 Aspect가 업무 데이터 변경 책임까지 갖게 됨

트랜잭션에 묶이는 업무 공통 DB 처리가 필요하다면 Facade가 호출하는 명시적인 공통 컴포넌트가 더 안전합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
public Output execute(Object body) throws Exception {
    bizPreProcessor.process(context);
    Output output = service.execute(convert(body));
    bizPostProcessor.process(context, output);
    return output;
}
```

그러면 호출 횟수와 위치가 명시적으로 드러납니다.

## 9. 업무 후처리

같은 Aspect가 Service 정상 반환 후 업무 후처리도 수행합니다.

```java
@AfterReturning(
    pointcut = "mgBizBoundary()",
    returning = "result"
)
public void after(
        JoinPoint joinPoint,
        Object result) {

    log.info(PdmgTxLog.bizProcessEnd());
    log.info(PdmgTxLog.bizPostStart());

    if (log.isInfoEnabled()) {
        log.info(PdmgTxLog.bizResponseMessage());
        log.info(
            PdmgMessagePrinter.businessDto(result)
        );
    }

    log.info(PdmgTxLog.bizPostEnd());
}
```

중요한 점은 `@AfterReturning`이라는 것입니다.

| 상황                          | 후처리 실행                            |
| ----------------------------- | -------------------------------------- |
| Service 정상 반환             | 실행                                   |
| Service RuntimeException      | 미실행                                 |
| Service checked Exception     | 미실행                                 |
| DAO 예외                      | 미실행                                 |
| Service 호출 전 DTO 변환 실패 | 선·후처리 모두 미실행                  |
| 후속 Facade 처리에서 예외     | Service 후처리는 이미 실행됨           |
| 타임아웃 최종 검사에서 롤백   | Service 후처리는 이미 실행됐을 수 있음 |

따라서 업무 후처리 로그가 남았다고 해서 거래가 최종 커밋됐다는 의미는 아닙니다.

예를 들어:

```text
Service 정상 반환
→ @AfterReturning에서 성공 DTO 로그
→ Worker 최종 deadline 검사
→ 이미 5초 초과
→ ROLLBACK
→ HTTP 504
```

이 경우 업무 후처리에는 정상 DTO가 기록되지만 DB는 롤백되고 클라이언트는 타임아웃을 받습니다.

로그 해석 시 반드시 구분해야 합니다.

```text
업무 후처리 로그 = Service 정상 반환
COMMIT 로그       = 거래 최종 성공
HTTP 응답         = 클라이언트 처리 결과
```

## 10. 다른 Aspect와 실행 순서

`PdmgBizTxFlowAspect`는 `@Order(50)`입니다.

```java
@Order(50)
public class PdmgBizTxFlowAspect {
}
```

`BizPrePostAspect`는 `@Order(100)`입니다.

낮은 Order 값이 바깥쪽에서 감싸므로 실제 Service 로그 순서는 다음과 같습니다.

```text
PdmgBizTxFlowAspect @Around 시작       Order 50
  BizPrePostAspect @Before             Order 100
    Service 본문
  BizPrePostAspect @AfterReturning      Order 100
PdmgBizTxFlowAspect @Around 종료        Order 50
```

즉:

```text
[TX-FLOW][시작] mgcoa9000Service.mgcoa9000S0
[업무 선처리] 시작
[업무 선처리] ...
[업무 선처리] 종료
[업무처리] 시작
Service 본문
DAO/SQL
[업무처리] 종료
[업무 후처리] 시작
결과 DTO
[업무 후처리] 종료
[TX-FLOW][종료] mgcoa9000Service.mgcoa9000S0
```

현재 문서의 다음 표현은 순서가 반대로 읽힐 수 있습니다.

```text
BizPrePost @Before
→ (TxFlow around 등)
→ Service
```

정확한 순서는 `TxFlow 시작 → BizPrePost Before → Service`입니다.

## 11. 다중 Service 호출 시

포인트컷은 거래 단위가 아니라 Service 메서드 단위입니다.

Facade에서 Service를 두 번 호출하면:

```java
service.validate(input);
service.process(input);
```

프록시를 경유하는 호출이라면 선·후처리도 두 번 실행됩니다.

```text
업무 선처리 → validate → 업무 후처리
업무 선처리 → process  → 업무 후처리
```

따라서 `BizPrePostAspect` 로그 한 묶음을 거래 한 건으로 해석하면 안 됩니다.

거래 단위는 다음 값으로 묶어야 합니다.

- GUID
- serviceId
- TransactionContext
- 요청 시작·종료 로그

## 12. Self-invocation 제약

같은 Service 객체 내부에서 다른 메서드를 직접 호출하면 Spring 프록시를 다시 통과하지 않습니다.

```java
@Service
public class SampleService {

    public void mainProcess() {
        subProcess();
    }

    public void subProcess() {
    }
}
```

외부에서 `mainProcess()`를 호출한 경우:

```text
Aspect before(mainProcess)
→ mainProcess
   → subProcess 직접 호출
→ Aspect after(mainProcess)
```

`subProcess()`에는 별도의 Aspect가 실행되지 않습니다.

이는 Spring Proxy AOP의 일반적인 제약입니다.

## 13. 응답 DTO 로그의 보안 위험

후처리는 Service 결과 DTO 전체를 JSON으로 기록합니다.

```java
PdmgMessagePrinter.businessDto(result)
```

`PdmgMessagePrinter`는 다음 메타 필드를 제거합니다.

- `dtoLogicalName`
- `fieldPropertyMap`
- `*List`
- `*Array`

하지만 다음 민감정보를 마스킹하지는 않습니다.

- 고객번호
- 주민등록번호
- 계좌번호
- 전화번호
- 이메일
- 인증정보
- 업무상 민감정보

즉, sanitize는 DTO 생성기 메타 제거이지 개인정보 마스킹이 아닙니다.

운영 적용 전에는 다음 중 하나가 필요합니다.

```text
필드명 기반 마스킹
DTO별 로그 허용 필드
@Sensitive 같은 Annotation
응답 본문 로그 비활성화 설정
최대 길이 제한
```

또한 대용량 조회 결과를 전부 INFO 로그로 출력하면 로그량과 직렬화 비용이 커질 수 있습니다. 현재 `businessDto()`에는 최대 길이 제한이 없습니다.

## 14. 문서 현행성 점검

[21.업무선처리-BizPrePostAspect.md](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/21.업무선처리-BizPrePostAspect.md:1>)는 포인트컷 변경 내용을 대부분 올바르게 반영했습니다.

다만 다음 부분은 보정이 필요합니다.

### 트랜잭션 시작 주체

문서:

```text
DB BEGIN은 Facade가 연다.
```

정확한 표현:

```text
timeout ON  → OnlineTimeoutExecutor의 TransactionTemplate이 BEGIN
timeout OFF → Business Facade @Transactional이 BEGIN
```

### Aspect 실행 순서

문서의 호출 스택보다 실제 순서는 다음이 정확합니다.

```text
PdmgBizTxFlowAspect 시작
→ BizPrePostAspect.before
→ Service
→ BizPrePostAspect.afterReturning
→ PdmgBizTxFlowAspect 종료
```

### 후처리의 성공 의미

문서에는 정상 반환 DTO라고 되어 있지만 다음 설명이 추가되어야 합니다.

```text
Service 정상 반환을 의미할 뿐,
최종 COMMIT이나 HTTP 성공을 보장하지 않는다.
```

특히 타임아웃 최종 검사에서 이후 롤백될 수 있습니다.

## 15. 최종 평가

| 점검 항목                    | 평가                                         |
| ---------------------------- | -------------------------------------------- |
| Service 포인트컷 변경        | 정상 적용                                    |
| Facade DTO 변환 후 실행      | 정상                                         |
| 업무 선후처리와 TX 역할 분리 | 적절                                         |
| TCF ON 트랜잭션 참여         | 정상                                         |
| TCF OFF 실행                 | Aspect는 실행되나 TX 미보장                  |
| 예외 후처리                  | 없음                                         |
| BRC 추출                     | Reflection 기반으로 취약                     |
| Context 누락 통제            | 없음, fail-open                              |
| 개인정보 마스킹              | 없음                                         |
| 대용량 DTO 로그 제한         | 없음                                         |
| Aspect 전용 테스트           | 확인되지 않음                                |
| 문서 정확성                  | 대부분 정확, BEGIN 주체·Order 설명 보정 필요 |

쉽게 정리하면:

> `BizPrePostAspect`는 Service 실행 전 GUID·서비스·BRC를 기록하고, Service가 정상 반환하면 결과 DTO를 기록합니다. 트랜잭션을 만들거나 커밋하지 않지만 TCF ON에서는 이미 시작된 거래 트랜잭션 안에서 실행됩니다. 후처리 로그가 남아도 이후 타임아웃 검사나 Facade 오류로 롤백될 수 있으므로, 후처리 로그를 최종 거래 성공으로 판단해서는 안 됩니다.
