# Pdmk Service 네이밍 원칙

이 문서는 `pdmk-service`의 Java 코드와 아키텍처 구성요소에 적용하는 단일 네이밍 기준이다. 이름은 대상의 역할, 계층, 데이터 흐름과 외부 계약을 드러내야 한다.

## 1. 목적과 적용 범위

다음 항목에 적용한다.

- Java 패키지, 파일, 타입, 메서드, 변수, 상수
- Controller, Service, DAO, DTO, Config, Filter, Aspect
- TCF, STF, ETF, 표준 전문과 거래 식별자
- API, JSON, HTTP Header
- DB 객체, MyBatis XML과 SQL ID
- YAML, Spring Bean, 예외 코드, 로그와 MDC
- 테스트, 리소스, 스크립트와 문서

신규 코드에는 즉시 적용한다. 외부 연계나 DB·화면 프로그램과 결합된 기존 이름은 18장의 호환 예외를 따른다.

## 2. 규칙의 강도

| 구분 | 의미 |
|---|---|
| 필수 | 신규·변경 코드가 반드시 지킨다. |
| 권장 | 특별한 사유가 없다면 따른다. |
| 금지 | 신규 코드에 사용하지 않는다. |
| 호환 예외 | 외부 계약이나 기존 프레임워크 때문에 유지한다. |

우선순위는 `외부 계약 > 호환 예외 > 필수 > 권장`이다. 외부 계약과 연결된 이름은 영향 분석 없이 변경하지 않는다.

## 3. 공통 언어와 표기 원칙

- 코드 식별자는 영어, 설명 문서는 한국어를 사용할 수 있다.
- 같은 개념에는 같은 단어를 쓴다. 사용자 식별자는 `userId`로 통일한다.
- 의미가 분명한 완전한 단어를 우선하고 임의의 축약어를 만들지 않는다.
- 한 건은 단수, 컬렉션은 복수로 쓴다: `record`, `records`.
- 시간과 용량에는 단위를 붙인다: `elapsedMs`, `startedAtNanos`, `sizeBytes`.

### 약어

| 상황 | 원칙 | 예시 |
|---|---|---|
| 독립 프레임워크 컴포넌트 | 약어 전체 대문자 | `TCFAspect`, `STF`, `ETF` |
| 확립된 Java 타입 계열 | PascalCase 유지 | `TcfTransaction`, `TcfContext`, `JwtProperties` |
| 일반 역할 접미사 | Java 관례 사용 | `DtoIn`, `DtoOut`, `Dao` |
| 상수·DB 객체 | 대문자와 밑줄 | `DEFAULT_SYSTEM_ID`, `TRT_BRC` |
| 변수·JSON | camelCase | `traceId`, `clientIp`, `sqlId` |

## 4. Java 패키지 명명

### 필수

- 모두 소문자로 쓰고 점(`.`)으로 계층을 구분한다.
- 공통 프레임워크는 `nhnis.fw`, PDMK 업무 코드는 `nhnis.mk` 아래에 둔다.
- 업무 공통 Aspect는 `nhnis.mk.co.common.BizPrePostAspect`에 둔다.
- FW 시스템 선·후처리는 `nhnis.fw.commons.interceptor.ServicePreventionInterceptor`이다.
- 마지막 패키지는 실제 책임을 나타낸다.

```text
nhnis.fw.tcf.aspect
nhnis.fw.exception
nhnis.mk.co.a.controller
nhnis.mk.co.a.service
nhnis.mk.co.a.dao
nhnis.mk.co.a.dto
nhnis.mk.co.common
nhnis.mk.config
```

`common`, `misc`, `util`처럼 책임이 불분명한 패키지는 만들지 않는다.

## 5. Java 타입과 파일 명명

- 일반 타입은 PascalCase로 작성한다.
- public 최상위 타입과 파일명을 정확히 일치시킨다.
- 역할이 있는 타입은 역할 접미사를 사용한다.

```text
SecurityConfig.java              → SecurityConfig
StandardHeaderValidator.java     → StandardHeaderValidator
GlobalExceptionHandler.java      → GlobalExceptionHandler
TcfAuthenticationEntryPoint.java → TcfAuthenticationEntryPoint
```

- 인터페이스에 습관적으로 `I` 접두사를 붙이지 않는다.
- enum 타입은 PascalCase, enum 값은 UPPER_SNAKE_CASE로 작성한다: `ProcessingType.INQUIRY`.
- annotation은 선언 목적이 드러나는 PascalCase를 쓴다: `@TcfTransaction`.
- 예외는 `Exception`, 설정 바인딩 타입은 `Properties`로 끝낸다.

## 6. 메서드 명명

- camelCase 동사 또는 동사구로 시작한다.
- 이름으로 한 가지 책임을 설명할 수 있어야 한다.

| 목적 | 권장 이름 | 예시 |
|---|---|---|
| 조회 | `get`, `find`, `select` | `selectSalesTipDetail` |
| 목록 조회 | `find...List`, `select...List` | `selectSalesTipList` |
| 검증 | `validate`, `require` | `validate`, `require` |
| 변환·생성 | `to`, `from`, `of`, `copyOf`, `create` | `responseHeaderOf` |
| 등록·수정·삭제 | `save`, `insert`, `update`, `delete`, `remove` | `saveSalesTip` |
| 존재·상태 확인 | `exists`, `has`, `is` | `hasText` |

`doIt`, `proc`, `process1`, `handleData`처럼 대상을 설명하지 못하는 이름은 금지한다.

## 7. 변수·필드·상수 명명

- 변수와 필드는 camelCase를 사용한다.
- 컬렉션은 복수형을 사용한다: `records`, `headers`.
- 개수는 `count`, 크기는 `size`, 위치는 `offset`을 사용한다.
- boolean은 `is`, `has`, `can`, `should`, `enabled`로 질문처럼 읽히게 한다.
- `static final` 상수는 UPPER_SNAKE_CASE를 사용한다.

```java
String serviceId;
List<mpcoa9999DtoOut> records;
long totalCount;
long elapsedMs;
boolean clientSuppliedHeader;
static final String HEADER_REQUEST_ID = "X-Request-Id";
```

단순 제네릭은 `T`, `K`, `V`를 사용할 수 있다. 여러 도메인 타입이 섞이면 의미 있는 타입 매개변수명을 쓴다.

## 8. 계층별 컴포넌트 명명

```text
Filter/Security → Controller → Service → DAO/MyBatis → DB
                    ↑
            TCFAspect: STF before, ETF after
```

| 계층 | 접미사 | 책임 | 예시 |
|---|---|---|---|
| HTTP 진입 | `Controller` | 요청·응답 변환과 Service 호출 | `mpcoa9999Controller` |
| 업무 | `Service` | 업무 규칙과 Spring 트랜잭션 | `mpcoa9999Service` |
| 영속성 | `Dao` | MyBatis 메서드 계약 | `mpcoa9999Dao` |
| 데이터 | `Dto...` | 계층 간 데이터 전달 | `mpcoa9999DtoIn` |
| 설정 | `Config` | Bean과 프레임워크 조립 | `SecurityConfig` |
| 설정값 | `Properties` | 외부 설정 바인딩 | `JwtProperties` |
| 웹 체인 | `Filter` | 요청 전후 공통 처리 | `TcfTraceFilter` |
| 횡단 배선 | `Aspect` | 공통 처리 순서 제어 | `TCFAspect` |
| 예외 응답 | `Handler` | 예외를 응답으로 변환 | `GlobalExceptionHandler` |
| 인증 실패 | `EntryPoint` | 인증 실패 HTTP 응답 | `TcfAuthenticationEntryPoint` |
| 기술 관찰 | `Interceptor` | SQL 등 호출 가로채기 | `MybatisLogInterceptor` |
| 검증 | `Validator` | 입력 규칙 검사 | `StandardHeaderValidator` |

Controller는 SQL을 실행하지 않고, DAO는 업무 판단을 하지 않으며, DTO는 Service를 호출하지 않는다.

## 9. DTO와 표준 전문 명명

### 업무 DTO

```text
입력:      <프로그램ID>DtoIn
출력:      <프로그램ID>DtoOut
목록 응답: <프로그램ID>ListResponseDto

mpcoa9999DtoIn
mpcoa9999DtoOut
mpcoa9999ListResponseDto
```

### 표준 전문

```text
StandardHeaderDto
StandardRequestDto<T>
StandardResponseDto<T>
Result
```

DTO와 JSON 필드는 camelCase로 일치시킨다. DTO에는 DB 접근, 트랜잭션, 외부 호출 같은 업무 동작을 넣지 않는다. `Map<String, Object>`는 구조가 실제로 동적인 경우에만 쓴다.

## 10. TCF 아키텍처 명명

| 이름 | 책임 |
|---|---|
| `@TcfTransaction` | Controller 메서드를 TCF 거래로 선언 |
| `TCFAspect` | `STF → Controller → ETF` 순서를 배선 |
| `STF` | Header 보완·검증과 거래 시작 |
| `ETF` | 결과·오류 전문 조립과 거래 종료 |
| `TcfContext` | 한 거래의 상태와 시작 시각 |
| `TcfContextHolder` | 현재 스레드의 Context 보관 |
| `TcfTraceFilter` | 추적 ID와 HTTP 총 응답시간 기록 |

```text
serviceId:        MP.SalesTip.list
transactionCode: MP-INQ-0001
processingType:  INQUIRY
businessCode:    MP
```

- `serviceId`는 `<업무코드>.<도메인>.<동작>`을 사용한다.
- `transactionCode`는 `<업무코드>-<처리유형>-<일련번호>`를 사용한다.
- 처리유형은 `ProcessingType` enum 값과 일치시킨다.
- `@TcfTransaction`은 업무 거래 선언이며 DB commit/rollback은 `@Transactional`이 담당한다.

## 11. API·JSON·HTTP 명명

- API 경로는 소문자를 사용하고 계층을 `/`로 구분한다.
- 현재 RPC형 거래는 마지막 경로에 명확한 동사를 사용한다.

```text
/api/mp/co/a/9999/list
/api/mp/co/a/9999/detail
```

- JSON 필드는 camelCase를 사용한다.
- 표준 요청은 `header`, `body`, 응답은 `header`, `result`, `body`를 사용한다.
- 이전 JSON 이름 호환은 `@JsonAlias`로 제한한다.
- HTTP Header는 표준 하이픈 표기를 사용한다.

```text
X-Request-Id
X-Trace-Id
X-User-Id
X-Forwarded-For
Authorization
```

## 12. DB·MyBatis 명명

### DB

- 테이블, 컬럼, 제약조건은 UPPER_SNAKE_CASE를 사용한다.

```text
TB_CR_AH_SALES_TIP_RACT
TRT_BRC
SALZ_TIP_KDC
TB_CR_AH_SALES_TIP_RACT_PK
```

### MyBatis

- mapper `namespace`는 DAO 완전한 클래스명과 일치시킨다.
- statement `id`는 DAO 메서드명과 정확히 일치시킨다.
- `parameterType`, `resultType`은 실제 Java 타입과 일치시킨다.
- SQL alias는 DTO 필드의 camelCase와 일치시킨다.

```xml
<mapper namespace="nhnis.mp.co.a.dao.mpcoa9999Dao">
<select id="mpcoa9999S0_S0">
<sql id="salesTipColumns">
T1.TRT_BRC AS trtBrc
```

`mpcoa9999S0_S0` 같은 SQL ID는 외부·기존 계약이므로 임의로 바꾸지 않는다. mapper 파일은 현재 `rdw.<업무패키지>/<프로그램ID>-ORA.xml` 규칙을 사용한다.

```text
rdw.mp.co.a/mpcoa9999-ORA.xml
```

## 13. Spring 설정과 Bean 명명

- Bean 조립 클래스는 `Config`, 외부 설정 바인딩 클래스는 `Properties`로 끝낸다.
- Bean 이름은 lowerCamelCase를 사용한다.
- 같은 타입의 Bean이 여러 개면 데이터소스와 목적을 명시한다.

```text
RdwDataSourceConfig
CorsProperties
rdwDataSource
rdwSqlSessionFactory
rdwSqlSessionTemplate
rdwTransactionManager
securityFilterChain
```

YAML 키는 lowercase kebab-case를 사용하고 시간 값은 이름이나 값에 단위를 명시한다.

```yaml
nsight:
  tcf:
    slow-transaction-ms: 3000
```

비밀번호, JWT secret, 실제 접속정보를 예제 이름이나 문서에 노출하지 않는다.

## 14. 예외·결과 코드 명명

- 업무·시스템 오류 코드는 `FW`와 네 자리 숫자를 사용한다: `FW0001`, `FW0401`, `FW9999`.
- 하나의 코드는 하나의 의미에만 사용한다.
- 메시지는 `exceptionCode.yml`의 `nhnis.exception` 아래에서 관리한다.
- 예상하지 못한 시스템 오류의 기본 코드는 `FW9999`다.

```text
S0000: 정상 처리
E0001: 실패
```

업무 오류는 `BizException`, 미분류 오류는 일반 `Exception`으로 구분한다. 실패 응답 조립은 `ETF`가 담당하고 Controller별 오류 형식을 만들지 않는다.

```java
SUCCESS_CODE
FAIL_CODE
DEFAULT_CODE
CODE_REQUIRED
CODE_UNAUTHENTICATED
```

## 15. 로그·MDC·로그 파일 명명

### MDC

다음 lowerCamelCase 이름을 공통 사용한다.

```text
guid
traceId
userId
serviceId
ip
sqlId
ifId
errCode
```

같은 값을 `requestId`, `reqId`, `guid`처럼 중복 정의하지 않는다.

### 로그 태그

컴포넌트명과 일치시킨다: `[TCFAspect]`, `[STF]`, `[ETF]`, `[TRACE]`, `[SQL]`.

### 로그 파일

`<project>_<purpose>.log`를 사용한다.

```text
pk_framework.log
pk_service.log
pk_framework_yyyy-MM-dd.log.gz
pk_service_yyyy-MM-dd.log.gz
```

`pk_`는 `pdmk-service`의 권장 접두사다. 운영 로그 수집기가 기존 이름에 의존하면 수집 계약을 확인한 뒤 별도 변경한다.

## 16. 테스트 명명

- 단위 테스트 클래스는 `<대상타입>Test`로 끝낸다.
- 통합 테스트는 `<기능>IntegrationTest`를 사용할 수 있다.
- 테스트 메서드는 대상, 조건, 기대결과를 표현한다.

```java
class STFTest { }
class Mpcoa9999ServiceTest { }

void selectSalesTipDetail_missingBody_throwsBizException() { }
void preProcess_missingChannel_throwsBizException() { }
```

`test1`, `successTest`, `tempTest`처럼 실패 원인을 설명하지 못하는 이름은 사용하지 않는다.

## 17. 리소스와 문서 명명

- 기본 설정은 `application.yml`을 사용한다.
- 도구가 요구하는 표준 이름은 유지한다: `log4j2.xml`, `schema.sql`, `data.sql`.
- DB 종류가 계약에 포함되면 `-ORA.xml`처럼 접미사를 명시한다.
- 문서명은 내용을 바로 알 수 있게 작성하고 같은 주제의 기준 문서를 둘 이상 만들지 않는다.
- 설계·실행 기록은 `docs/superpowers/specs`, `docs/superpowers/plans`에 날짜와 영문 kebab-case를 사용한다.

```text
docs/네이밍원칙.md
docs/트랜잭션처리.md
docs/superpowers/specs/2026-08-01-naming-principles-design.md
```

## 18. 레거시 호환 예외

| 기존 이름 | 유지 이유 |
|---|---|
| `mpcoa9999Controller` | 프로그램 ID를 소문자 접두사로 결합하는 업무 규칙 |
| `mpcoa9999Service` | Controller·DAO·XML과 프로그램 ID 공유 |
| `mpcoa9999Dao` | MyBatis namespace 계약 |
| `mpcoa9999DtoIn/Out` | 전문·SQL 매핑 계약 |
| `TcfTransaction`, `TcfContext` | 이미 확립된 Java 타입 계열 |
| `JwtAuthenticationFilter` | 기존 PascalCase 약어 계열 |
| `mpcoa9999S0_S0` | 프로그램·SQL ID 계약 |

이 이름들은 일부만 독립적으로 바꾸지 않는다. 새 호환 예외가 필요하면 외부 계약, 영향 범위, 종료 조건을 문서화한다.

## 19. 금지 목록

### 금지 이름

```text
data
obj
temp
tmp
proc
doIt
value1
list2
commonUtil
misc
```

### 금지 구조

- public 타입과 Java 파일명을 다르게 작성한다.
- Controller에서 SQL을 실행하거나 DAO에서 HTTP 응답을 만든다.
- DTO에 Service 또는 DAO를 주입한다.
- 동일 개념에 여러 약어를 만든다.
- 시간·용량 변수에서 단위를 생략한다.
- DAO 메서드와 MyBatis statement ID를 다르게 작성한다.
- DB alias와 DTO 필드명을 불일치시킨다.
- 동일 주제의 별도 네이밍 기준 문서를 만든다.
- 비밀값이나 개인정보를 이름·로그·문서 예시에 넣는다.

| 좋은 이름 | 나쁜 이름 | 이유 |
|---|---|---|
| `elapsedMs` | `elapsed` | 단위가 명확함 |
| `salesTipRecords` | `dataList` | 도메인과 복수가 명확함 |
| `CODE_UNAUTHENTICATED` | `ERR1` | 오류 의미가 명확함 |
| `selectSalesTipDetail` | `procDetail` | 동작과 대상이 명확함 |
| `rdwTransactionManager` | `txManager2` | 데이터소스 목적이 명확함 |
| `StandardHeaderValidator` | `HeaderUtil` | 책임이 명확함 |

- [ ] 약어가 `TCF`·`STF`·`ETF` 또는 기존 `Tcf...`·`Jwt...` 계열과 일관되는가?
- [ ] 이름만 보고 Controller·Service·DAO·DTO 역할을 알 수 있는가?
- [ ] 메서드명이 동작과 대상을 함께 설명하는가?
- [ ] boolean은 질문처럼 읽히고 컬렉션은 복수형인가?
- [ ] 시간·용량 값에 `Ms`, `Nanos`, `Bytes` 단위가 있는가?
- [ ] DTO와 JSON 필드가 camelCase로 일치하는가?
- [ ] DAO 메서드, mapper ID, SQL alias가 Java 타입과 일치하는가?
- [ ] 거래·오류·로그 식별자가 정해진 형식을 따르는가?
- [ ] `guid`, `traceId`, `serviceId`, `sqlId`, `errCode`를 중복 정의하지 않았는가?
- [ ] `data`, `temp`, `proc`, `doIt` 같은 모호한 이름이 없는가?
- [ ] 기존 호환 예외를 근거 없이 확대하지 않았는가?
- [ ] 비밀값이나 개인정보가 이름과 예시에 없는가?
- [ ] 같은 주제의 별도 기준 문서를 만들지 않았는가?

체크리스트를 통과하지 못한 이름은 구현 내용이 맞더라도 수정한 뒤 병합한다.
