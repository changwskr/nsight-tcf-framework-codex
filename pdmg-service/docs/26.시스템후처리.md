# 26. 시스템 후처리 (PDMG)

기준일: 2026-08-09  
대상: `ResponseBodyArgumentResolver` · `ServicePreventionInterceptor.afterCompletion` · `ImageLogHandler.postImagelog`  
관련: [14.시스템 선후처리.md](./14.시스템%20선후처리.md) · [15.Interceptor-ServicePrevention.preHandle.md](./15.Interceptor-ServicePrevention.preHandle.md) · [25.업무후처리-BizPrePostAspect.md](./25.업무후처리-BizPrePostAspect.md) · [10.전문.md](./10.전문.md) · [11.예외처리.md](./11.예외처리.md)

## 1. 정의

업무(Facade TX · Service · 업무 후처리)가 끝난 뒤,  
**모든 온라인 거래에 공통**으로 적용하는 응답 조립·응답 로그·ImageLog 갱신이다.

```text
Facade COMMIT (또는 예외 경로)
  → Controller 반환 (*DTOout 또는 에러 body)
  → ResponseBodyAdvice.beforeBodyWrite     ★ 응답 봉투·응답전문 로그
  → HTTP 응답 기록
  → Interceptor.afterCompletion           ★ ImageLog UPDATE
```

| | **시스템 후처리 (여기)** | **업무 후처리 (25)** |
|--|-------------------------|---------------------|
| 시점 | Controller 반환 이후 | Service 정상 반환 직후 |
| TX | 업무 Facade TX **밖** (대개 COMMIT 이후) | Facade TX **안** |
| 내용 | `{ hdr_nhnis, dto }` · 응답 원문 · ImageLog | 업무 DTO 로그만 |
| 주체 | Advice + Interceptor.after | `BizPrePostAspect` |

활성: `nhnis.fw.commons.legacy-web.enabled=true`.

---

## 2. 왜 두 단계인가

`@ResponseBody`는 Interceptor `postHandle` **보다 먼저** 바디를 쓴다.  
그래서 응답 전문 로그·봉투 조립을 `postHandle`에 두면 **늦거나 비어 있다**.

| 단계 | 컴포넌트 | 하는 일 |
|------|----------|---------|
| A | `ResponseBodyArgumentResolver.beforeBodyWrite` | 봉투 · 응답 로그 · `ctx.setResponseBody` |
| B | `ServicePreventionInterceptor.afterCompletion` | `postImagelog` / `exceptionImagelog` |

`postHandle`은 의도적으로 시스템 후처리 로그를 **하지 않는다** (주석으로 Advice에 위임).

---

## 3. 전체 순서

```text
① [업무] Handler → Facade(TX) → BizPrePost → Service → DAO → 업무후처리
② Facade return → COMMIT
③ OnlineTransactionController 반환 (body = *DTOout)
④ ResponseBodyArgumentResolver.beforeBodyWrite
     [시스템 후처리] 시작
     hdr_nhnis + dto 조립 (메타 필드 제거)
     [온라인전문][응답][원문] + wire JSON
     [시스템 후처리] 종료
     ServiceContext.setResponseBody(pretty JSON)
     return ObjectNode → HTTP JSON
⑤ Dispatcher 응답 커밋
⑥ ServicePreventionInterceptor.afterCompletion
     정상: postImagelog(header, responseBody)
     예외: exceptionImagelog(+ Context remove)
```

선처리 대칭: [15](./15.Interceptor-ServicePrevention.preHandle.md) `preImagelog`(INSERT).

## 4. 단계 A — ResponseBodyAdvice

FQCN: `nhnis.fw.commons.resolver.ResponseBodyArgumentResolver`  
`@ControllerAdvice` + `ResponseBodyAdvice<Object>`  
`supports` → 항상 `true`.

### 4.1 `beforeBodyWrite` 절차

```text
1. [시스템 후처리] 시작
2. Content-Type multipart* ? → 후처리 종료 배너만 → body 그대로 반환
3. responseBody = {}
4. hdr_nhnis ← ServiceContext.header (valueToTree + removeUnwantedFields)
5. dto ←
     · body가 NH_NIS_ERR_DTO → marshal / fallback valueToTree
     · 그 외(업무 DTOout) → valueToTree + removeUnwantedFields
6. [온라인전문][응답][원문]
7. asIsWireJson(responseBody)
8. [시스템 후처리] 종료
9. ctx.setResponseBody(pretty string)   ← afterCompletion 입력
10. return responseBody  (= { "hdr_nhnis":…, "dto":… })
```

클라이언트가 받는 표준 계약([10](./10.전문.md)):

```json
{
  "hdr_nhnis": { … },
  "dto": { … }
}
```

### 4.2 메타 필드 제거 (`removeUnwantedFields`)

재귀적으로:

- `dtoLogicalName`, `fieldPropertyMap` 삭제  
- 이름이 `*List` / `*Array` 로 끝나는 필드 삭제  
- 하위 Object/Array 계속 순회  

와이어 JSON·ImageLog 응답 전문이 DataObject 메타로 오염되지 않게 한다.

### 4.3 같은 클래스의 `@ExceptionHandler(NhBaseException)`

`NhBaseException` → `NH_NIS_ERR_DTO` + HTTP 500.  
이 body도 다시 Advice `beforeBodyWrite`를 타면 `dto`에 에러 DTO가 실린다.

업무 `BizException` 등 다른 핸들러(`GlobalExceptionHandler`) 경로와 함께 [11](./11.예외처리.md)를 본다.  
Filter `sendError`는 Advice를 **안 탈 수** 있다.

## 5. 단계 B — afterCompletion · ImageLog

FQCN: `nhnis.fw.commons.interceptor.ServicePreventionInterceptor.afterCompletion`  
ImageLog: `nhnis.fw.commons.imagelog.ImageLogHandler`

### 5.1 정상 (`ex == null`)

```text
multipart 아니면:
  postImagelog(ctx.header, ctx.responseBody)
```

`postImagelog`:

- `RESPONSE_TIME` 설정  
- `RESPONSE_MSG` ← Advice가 넣은 응답 전문 원문  
- GUID 기준 **UPDATE** (pre INSERT 행)  
- 실패해도 업무 응답에는 영향 최소화(로그 error/warn)  
- updated=0 → pre 행 없음 WARN  

업무 Facade TX와 **커밋을 공유하지 않는** 별도 JDBC(ImageLog용 DS)다.  
업무 롤백되어도 선처리 INSERT·후처리 시도는 감사 관점에서 남길 수 있다.

### 5.2 예외 (`ex != null`)

```text
[ErrorProcessor] 로그
[시스템 후처리] 시작/종료 (배너만)
exceptionImagelog(header, null, ex)
ServiceContextHolder.removeInstance()
throw ex
```

예외 타입·코드·메시지 컬럼 갱신(없으면 INSERT).

### 5.3 Context

성공 경로 스니펫은 `afterCompletion`에서 Context를 반드시 지우지 않을 수 있다.  
요청 스레드 종료·Filter 측 정리와 맞춘다. 예외 경로는 **명시 remove**.

## 6. 로그 배너 (정상)

```text
[시스템 후처리] 시작 ===============================================
[온라인전문][응답][원문] ===============================================
{ "hdr_nhnis": …, "dto": … }
[시스템 후처리] 종료 ===============================================
```

(`PdmgTxLog` · `PdmgMessagePrinter.asIsWireJson`)

업무 후처리 로그(`[업무 후처리] 결과 DTO`)는 **그 이전·TX 안**에 이미 찍혀 있다.

## 7. 선처리와의 대칭

| | 선처리 [15] | 후처리 [26] |
|--|-------------|-------------|
| Interceptor | `preHandle` | `afterCompletion` |
| Advice | — | `beforeBodyWrite` |
| ImageLog | `preImagelog` INSERT | `postImagelog` UPDATE |
| 전문 | 요청 원문 | 응답 봉투 원문 |
| Context | GUID·헤더 보강 | `setResponseBody` |

multipart: 선·후 본문(전문/ImageLog) 스킵 가능.

---

## 8. 하지 말 것

1. 시스템 후처리에서 업무 SQL·Facade TX 재오픈  
2. 응답 봉투 로그를 `postHandle`에만 두기 (`@ResponseBody` 순서)  
3. ImageLog 실패를 업무 성공 API 실패로 바꾸기(현행은 격리)  
4. 업무 후처리(25)와 시스템 후처리를 한 Aspect로 합치기  
5. `setResponseBody` 없이 postImagelog만 호출해 응답전문 공백 유발

## 10. 요약

```text
시스템 후처리 = 응답 봉투 + 응답 전문 로그 + ImageLog UPDATE
  A. ResponseBodyAdvice.beforeBodyWrite  (COMMIT 이후, HTTP 직전)
  B. Interceptor.afterCompletion         (응답 기록 후 감사)
  ≠ 업무 후처리 (Service @AfterReturning, TX 안)
  ≠ postHandle (의도적 비움)

```
