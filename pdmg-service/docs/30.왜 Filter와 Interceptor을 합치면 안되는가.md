# 30. 왜 Filter와 Interceptor를 합치면 안 되는가 (PDMG)

기준일: 2026-08-09  
대상: `pdmg-fw` `DefaultFilter` · `ServicePreventionInterceptor` · (`ResponseBodyAdvice`)  
관련: [13.Filter-DefaultFilter.md](./13.Filter-DefaultFilter.md) · [15.Interceptor-ServicePrevention.preHandle.md](./15.Interceptor-ServicePrevention.preHandle.md) · [26.시스템후처리.md](./26.시스템후처리.md) · [16.Service Context.md](./16.Service%20Context.md) · [14.시스템 선후처리.md](./14.시스템%20선후처리.md)

---

## 0. 결론 (PDMG)

**기능을 “한 클래스”로 합치는 것이 목표가 아니다. 이미 나뉜 책임을 유지·정리하는 것이 목표다.**

| 계층 | PDMG 담당 | 책임 |
|------|-----------|------|
| **Filter** | `DefaultFilter` | HTTP 진입 — Body 캐시, JWT(비-local), `hdr_nhnis` 파싱, `ServiceContext`/MDC, Context 해제 |
| **Interceptor** | `ServicePreventionInterceptor` | **시스템 선처리** (요청전문 로그 · ImageLog INSERT) + **afterCompletion** ImageLog UPDATE |
| **Advice** | `ResponseBodyArgumentResolver` | **시스템 후처리(응답)** — `{ hdr_nhnis, dto }` · 응답 원문 · `setResponseBody` |
| **TCF** | `OnlineTransactionController` → `TcfFacade` → Dispatcher | serviceId 라우팅 (거래 공통 “실행”) |
| **Facade** | `application.facade` | DB `@Transactional` |
| **AOP** | `BizPrePostAspect` 등 | Service 메서드 단위 업무 선후·TX-FLOW |

구 NSIGHT 문서의 **STF / StandardHeader / `POST /{업무}/online` / Interceptor 최소화·제거** 권고는 **현행 PDMG에 그대로 적용하지 않는다.**  
PDMG는 STF가 없고, 시스템 선후·ImageLog가 **Interceptor + Advice**에 명시적으로 있다.

---

## 1. 왜 단순 통합하면 안 되는가

실행 위치가 다르다.

```text
Client / pdmg-ui relay
  ↓
DefaultFilter                         ★ Servlet Filter (DispatcherServlet 전)
  · CachedBody · JWT · hdr 파싱
  · ServiceContextHolder.setInstance
  ↓
DispatcherServlet · HandlerMapping
  ↓
ServicePreventionInterceptor.preHandle ★ MVC Interceptor
  · [시스템 선처리] 요청전문 · preImagelog
  ↓
OnlineTransactionController
  → TcfFacade → Handler → Facade(TX) → [BizPrePost] Service → DAO
  ↓
ResponseBodyAdvice.beforeBodyWrite    ★ 시스템 후처리(응답 봉투)
  · { hdr_nhnis, dto } · setResponseBody
  ↓
Interceptor.afterCompletion           ★ ImageLog post / exception
  ↓
Filter finally                        ★ Context remove · ThreadContext clear
  ↓
Response
```

| | Filter | Interceptor |
|--|--------|-------------|
| 시점 | MVC·Handler 결정 **전** | Handler 매핑 **후** |
| 요청 래핑 | `CachedBodyHttpServletRequest` 가능 | Body를 이미 읽힌 뒤면 늦음 |
| `sendError` 조기 종료 | 체인 중단 (Interceptor 미진입) | 해당 없음 |
| `@ResponseBody` 순서 | — | `postHandle`보다 Advice가 먼저 → 응답 로그는 Advice |

같은 “로깅/컨텍스트”로 보여도 **필요한 정보·실패 모드**가 다르다.  
완전 대체 관계가 아니다.

---

## 2. PDMG에서 각 계층이 실제로 하는 일

### 2.1 `DefaultFilter` (Filter)

설정: `nhnis.fw.commons.filter.enabled=true`

| 한다 | 하지 않는다 |
|------|-------------|
| Body 캐시 · `PDMG_REQUEST_BODY` | ImageLog INSERT/UPDATE |
| JWT Bearer (active ≠ local) | `[시스템 선처리]` 배너·요청전문 CORE 로그 |
| `hdr_nhnis` 파싱 / local 합성 | `{ hdr_nhnis, dto }` 응답 조립 |
| `ServiceContext` 생성 · MDC | `@Transactional` / 업무 SQL |
| `finally` Context·ThreadContext 정리 | serviceId → Handler 라우팅 |

HTTP가 깨졌거나 인증 실패면 **여기서 `sendError`** 하고 MVC에 안 들어간다.

### 2.2 `ServicePreventionInterceptor` (Interceptor)

설정: `nhnis.fw.commons.legacy-web.enabled=true` (WebConfiguration 등록)

| 시점 | 내용 |
|------|------|
| `preHandle` | GUID 보장 · 헤더 보강 · 요청전문 로그 · **`preImagelog`** |
| `postHandle` | 시스템 후처리 로그 **안 함** (Advice에 위임 — `@ResponseBody` 순서) |
| `afterCompletion` | 정상 **`postImagelog`** / 예외 **`exceptionImagelog`** |

업무 Facade TX **밖**. ImageLog가 업무 롤백에 같이 지워지지 않게 한다.

### 2.3 `ResponseBodyArgumentResolver` (Advice)

Interceptor가 아니지만 **시스템 후처리의 응답 절반**이다.

- 성공 body(`*DTOout`) → `{ hdr_nhnis, dto }`
- 응답 원문 로그 · `ServiceContext.setResponseBody` → afterCompletion 입력

Filter/Interceptor **한쪽에만** 합치면 Advice 순서·응답 전문 공백 문제가 다시 생긴다 ([26](./26.시스템후처리.md)).

### 2.4 TCF (거래 라우팅 — STF 아님)

```text
POST /{serviceId}  { hdr_nhnis, dto }
  → OnlineTransactionController
  → TcfFacade.process(serviceId, dto)
       → OnlineTimeoutExecutor (공통 SLA — Filter/Interceptor 밖)
  → Dispatcher → *Handler → *Facade(@Transactional) → *Service
```

| 구 Pdmk/NSIGHT 문서 | 현행 PDMG |
|---------------------|-----------|
| STF.preProcess (헤더검증·권한·Timeout·거래통제) | **없음** — 선후는 Filter/Interceptor/Advice. **Timeout은 TcfFacade의 OnlineTimeoutExecutor** ([20.타임아웃](./20.타임아웃.md)) |
| `StandardRequestDto` / ETF | **`hdr_nhnis` + `dto`** |
| Interceptor 제거 후 STF로 이관 | ImageLog·시스템 선후를 **Interceptor에 유지** |

거래 “실행·공통 timeout”은 TCF, 시스템 “감사·전문”은 Interceptor+Advice로 **이미 분리**되어 있다.  
Timeout을 Filter/Interceptor에 넣지 않는 이유: TX·Worker·504는 업무 실행 경계(`TcfFacade`) 책임이다.

## 3. “Filter로 다 합치면?” — PDMG에서 깨지는 것

| Filter에 옮기려는 것 | 문제 |
|----------------------|------|
| `preImagelog`만 Filter | 가능은 하나, Handler 매핑 전·Context 불완전·multipart/조기 `sendError`와 섞여 **선처리 구간 로그 위치가 흐려짐** |
| 응답 전문 로그 | 응답 body는 **Advice**에서 조립. Filter `doFilter` 안쪽만으로는 `@ResponseBody` 결과를 못 봄 |
| `postImagelog`를 Filter finally만 | Advice의 `setResponseBody` **이후**여야 함. 지금은 afterCompletion이 그 계약을 명시. Filter finally로 옮겨도 순서는 맞출 수 있으나, 예외 경로·`exceptionImagelog`·Context remove와 **한곳에 과부하** |
| JWT+ImageLog+봉투 조립 전부 | HTTP 실패와 업무/응답 조립이 한 클래스 → **거절 지점·로그 배너·TX 경계** 추적이 어려움 |

### Filter만으로 “시스템 선후”를 흡수하면

```text
DefaultFilter
  ├─ JWT · Body · Context
  ├─ 요청전문 · ImageLog INSERT
  ├─ (체인) Controller…Advice…
  └─ finally: ImageLog UPDATE · Context 제거
```

단기적으로는 동작 가능해 보여도:

1. **시스템 선처리 / 후처리 로그 배너**가 Filter 한 덩어리로 뭉개짐  
2. Advice·afterCompletion·Filter finally의 **순서 계약**이 문서·코드에서 사라짐  
3. TCF OFF 거래별 Controller·비온라인 MVC와 **선후 정책 공유**가 어려워짐  
4. “HTTP 문제”와 “감사 로그 문제”의 장애 분리가 안 됨  

---

## 4. “Interceptor로 다 합치면?” — PDMG에서 깨지는 것

| Interceptor에 옮기려는 것 | 문제 |
|---------------------------|------|
| `CachedBodyHttpServletRequest` | DispatcherServlet/메시지 컨버터가 Body를 쓰기 **전**에 래핑해야 함 → **Filter 몫** |
| JWT · 빈 Body · JSON 파싱 실패 `sendError` | MVC 진입 전 거절이 맞음. Interceptor까지 오면 이미 매핑·체인 비용 발생 |
| `ServiceContext` 최초 생성 | Filter가 Body에서 `hdr_nhnis`를 읽을 때 같이 만드는 것이 자연스러움 |
| 응답 봉투 조립 | `@ResponseBody` / `ResponseBodyAdvice`가 정석. Interceptor `postHandle`은 **늦다** |

Interceptor만으로 HTTP 진입을 흡수하면 **Body 재읽기·조기 401/400** 패턴이 깨진다.

## 5. 중복처럼 보이는 것과 실제 단일 책임

| 관심사 | 한 곳에서만 |
|--------|-------------|
| Body 캐시 · JWT · hdr 파싱 · Context **생성/해제** | **Filter** |
| `[시스템 선처리]` · 요청전문 로그 · **preImagelog** | **Interceptor.preHandle** |
| 응답 `{ hdr_nhnis, dto }` · 응답전문 로그 · **setResponseBody** | **Advice** |
| **postImagelog** / exceptionImagelog | **Interceptor.afterCompletion** |
| serviceId → Handler | **TCF** |
| DB commit/rollback | **Facade** |
| `[업무 선/후처리]` | **BizPrePostAspect** (Service) |

피해야 할 중복:

```text
Filter에서 요청전문+ImageLog
Interceptor에서 또 요청전문+ImageLog
Advice와 postHandle에서 둘 다 응답 원문
```

현행 PDMG는 위 표를 대체로 지키고 있다.  
합치기보다 **이 경계를 문서·코드에서 유지**하는 편이 맞다.

## 6. Interceptor를 없애도 되나? (PDMG 답)

**현재 구조에서는 권장하지 않는다.**

구 문서 조건(“STF가 거래 공통·ImageLog·전문 로그를 전부 가져간다”)이 PDMG에 **없다**.  
없애려면 동등 책임을 **명시적 다른 계층**으로 옮겨야 한다.

| Interceptor 제거 시 필수 이관 | 후보 | 비고 |
|------------------------------|------|------|
| preImagelog · 요청전문 로그 | Filter 또는 TCF 직전 컴포넌트 | TX 밖 유지 |
| postImagelog | Filter finally 또는 Advice 콜백 | `responseBody` 준비 후 |
| exceptionImagelog | `@ControllerAdvice` + Filter | 경로 누락 주의 |

이관 없이 삭제하면 **ImageLog·시스템 선후 로그가 빠진다.**

남겨 둘 추가 이유(선택):

- HandlerMethod/`@Annotation` 기반 MVC 전용 통제  
- TCF를 안 타는 `/actuator`, 내부 MVC 등  

다만 PDMG 온라인의 **주된 존재 이유**는 위 “시스템 선후·ImageLog”다.

## 7. 권장 구조 (현행 PDMG = 목표 형태)

```text
                         HTTP POST /{serviceId}
                         body: { hdr_nhnis, dto }
                                   │
                                   ▼
┌──────────────────────────────────────────────────┐
│ DefaultFilter                                      │
│  CachedBody · JWT(비-local) · hdr 파싱             │
│  ServiceContext / MDC · PDMG_REQUEST_BODY          │
│  finally: Holder.remove · ThreadContext.clear      │
└────────────────────────┬─────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────┐
│ ServicePreventionInterceptor.preHandle             │
│  [시스템 선처리] 요청전문 · preImagelog            │
└────────────────────────┬─────────────────────────┘
                         ▼
         OnlineTransactionController (TCF ON)
                         ▼
              TcfFacade → Dispatcher → Handler
                         ▼
         Facade @Transactional(rdwTransactionManager)
              → BizPrePost → Service → DAO
                         ▼
┌──────────────────────────────────────────────────┐
│ ResponseBodyAdvice                                 │
│  [시스템 후처리] { hdr_nhnis, dto } · setResponseBody │
└────────────────────────┬─────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────┐
│ Interceptor.afterCompletion                        │
│  postImagelog / exceptionImagelog                  │
└──────────────────────────────────────────────────┘
```

판단 기준:

```text
HTTP·인증·Body·Context 수명     → Filter
시스템 전문 감사(요청/ImageLog) → Interceptor (+ Advice 응답)
거래 라우팅                     → TCF
DB TX                           → Facade
업무 횡단 로그                  → BizPrePost AOP
```

## 8. 아키텍처 한 줄

> **Filter와 Interceptor를 하나로 합치지 말고, PDMG처럼 HTTP 진입(Filter) / 시스템 선후·ImageLog(Interceptor+Advice) / 거래 라우팅(TCF) / DB TX(Facade)를 유지하라.**

```text
합치기 ✗     Filter 전부 흡수 ✗     Interceptor 전부 흡수 ✗
중복 제거 ○  책임 표(§5) 지키기 ○   STF 없는 현행에 맞추기 ○
```
