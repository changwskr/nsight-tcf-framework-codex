# 03. 애플리케이션 레이어드 아키텍처 (PDMG)

## 1. 목적

PDMG는 **레이어드 아키텍처**다.  
레이어는 “호출이 위에서 아래로만 흐른다”는 **의존 방향**을 정의하고, 컴포넌트(Handler·Facade·Service…)는 그 레이어 안의 **역할 타입**이다.

| 구분 | 문서 | 답하는 질문 |
|------|------|-------------|
| 레이어 | **본 문서 (03)** | 계층을 어떻게 쌓고, 누가 누구를 호출해도 되는가? |
| 컴포넌트 | [02](./02.어플리케이션%20컴포넌트%20구조.md) | Handler/Facade/Service 각각의 책임·패키지·파일은? |

---

## 2. 레이어 스택 (한눈에)

```text
┌─────────────────────────────────────────────────────────────┐
│  0. 채널 / UI                                                │
│     pdmg-ui 브라우저 (직접 POST /{serviceId} + CORS)         │
└────────────────────────────┬────────────────────────────────┘
                             │ { hdr_nhnis, dto }
┌────────────────────────────▼────────────────────────────────┐
│  1. 프레임워크 인프라 (pdmg-fw)                              │
│     Filter · Interceptor · OnlineTransactionController       │
│     TcfFacade · ImageLog · GlobalExceptionHandler            │
└────────────────────────────┬────────────────────────────────┘
                             │ serviceId → Handler
┌────────────────────────────▼────────────────────────────────┐
│  2. Entry 레이어          nhnis.mg.co.a.entry.*              │
│     Handler (라우팅) · Aspect (업무 선·후처리 / TX-FLOW)      │
└────────────────────────────┬────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────┐
│  3. Application 레이어    nhnis.mg.co.a.application.*        │
│     Facade ★ DB TX  ·  Service (업무)                        │
│     Controller (TCF OFF 진입만)                              │
└────────────────────────────┬────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────┐
│  4. Contract 레이어       nhnis.mg.co.a.dto                  │
│     DTOin / DTOout / Sub  (계층 공통 입출력 계약)            │
└────────────────────────────┬────────────────────────────────┘
                             │ (Service·Facade가 사용)
┌────────────────────────────▼────────────────────────────────┐
│  5. Persistence 레이어    nhnis.mg.co.a.persistence.*        │
│     DAO  →  Mapper XML (rdw.mg.co.a/)  →  DB                 │
└─────────────────────────────────────────────────────────────┘

옆길(조립·연동, 수직 스택 밖):
  config / client / support
```

의존은 **위 → 아래**만 허용한다. 아래 레이어가 위를 알면 안 된다.

## 3. 레이어 정의

### 3.1 채널 / UI (pdmg-ui)

- 브라우저·화면. 업무 로직·SQL·TX 없음.
- 화면 JavaScript의 `PdmgServiceClient`가 `pdmg-service`를 직접 호출한다.
- `TransactionRelayService`와 `/api/relay/{id}`는 하위 호환으로 남아 있지만 현재 일반 화면 경로는 아니다.

### 3.2 프레임워크 인프라 (pdmg-fw)

| 역할 | 내용 |
|------|------|
| 요청 공통 | Body 캐시, GUID, `ServiceContext` |
| 시스템 선·후처리 | ImageLog, 요청/응답 전문 로그 |
| TCF 진입 | `OnlineTransactionController` → `TcfFacade` → Handler 탐색 |
| 예외 | 알려진 예외는 `GlobalExceptionHandler` → `result(NH_NIS_ERR_DTO)` |

업무 패키지(`nhnis.mg.co.a`)에 두지 않는다.  
Timeout ON에서는 `DefaultOnlineTimeoutExecutor` Worker의 `TransactionTemplate`이 외곽 DB TX를 연다. Facade의 `@Transactional(REQUIRED)`는 같은 TX에 참여한다. Timeout OFF에서는 Facade가 TX를 시작한다.

### 3.3 Entry 레이어 (`entry`)

| 패키지 | 역할 |
|--------|------|
| `entry.handler` | `serviceId` → Facade 메서드 라우팅 |
| `entry.aspect` | Service Pointcut 업무 선·후처리, TX-FLOW 로그 |

- TCF ON 시 **업무 쪽 최상위 진입**이다.
- Handler는 Facade만 호출한다. Service/DAO 직호출 금지.
- Aspect는 “배선”이지 업무 분기가 아니다.

### 3.4 Application 레이어 (`application`)

| 패키지 | 역할 | TX |
|--------|------|-----|
| `application.facade` | DTO 변환 + Service 호출 | **여기가 DB TX 경계** |
| `application.service` | 검증·절차·DAO 호출 | 기본 미보유 (Facade TX 안) |
| `application.controller` | TCF OFF HTTP 진입 | TX 없음(호환; Facade 경유 권장) |

Application은 “한 거래(유스케이스)를 수행하는 층”이다.  
Facade 1메서드 ≈ 온라인 거래 1건 ≈ 트랜잭션 1건.

### 3.5 Contract 레이어 (`dto`)

- 입출력 계약만. Bean 주입·SQL·TX 없음.
- Entry·Application·Persistence가 **같은 DTO 타입**을 공유한다.
- `application` 하위에 두지 않는 이유: 특정 레이어 소유가 아닌 공통 계약이기 때문.

### 3.6 Persistence 레이어 (`persistence` + Mapper)

- DAO 인터페이스 + `rdw.mg.co.a/*-ORA.xml`.
- SQL·바인딩만. 업무 판단·HTTP 조립 금지.
- DB 접근의 유일한 정상 경로다.

### 3.7 옆길: Config / Client / Support

수직 호출 스택에 끼워 넣지 않고 **조립·연동·유틸**로 둔다.

| 패키지 | 예 |
|--------|-----|
| `config` | DataSource, TM, Security, MyBatis interceptor |
| `client` | 외부 API |
| `support` | 순수 유틸 |

Config가 만든 Bean을 상위 레이어가 주입받아 쓴다. Config가 Handler/Service를 호출하지 않는다.

## 4. 레이어 간 의존 규칙

```text
허용 (↓):
  UI → FW → Entry → Application → (dto) → Persistence → DB

금지 (↑·횡단 위반):
  Persistence → Application / Entry / FW
  Application.service → Entry.handler / Controller
  Entry.handler → Application.service / Persistence   (Facade 우회)
  dto → 어떤 레이어든 주입·호출
```

```text
entry.handler ──► application.facade ──► application.service ──► persistence.dao
                         │                        ▲
                         │                   entry.aspect
                         │              (Service pointcut)
                         └── @Transactional
```

## 5. 트랜잭션과 레이어

레이어드에서 **TX는 Application(Facade)에만** 둔다.

```text
Entry (Handler)          ← TX 없음
    │
Application (Facade)     ← BEGIN / COMMIT / ROLLBACK
    │   ┌─ Aspect 선처리 (Service 진입 직전)
    │   Service
    │   Persistence
    │   └─ Aspect 후처리
    │
Entry로 반환 후 FW 후처리 ← 업무 TX 밖 (ImageLog 등)
```

상세: [01.트랜잭션처리 변경.md](./01.트랜잭션처리%20변경.md)

## 6. 진입 경로별 레이어 사용

### 6.1 TCF ON (`nhnis.fw.tcf.enabled=true`) — 기본

```text
FW(Filter→OnlineController→TcfFacade)
  → Entry(Handler)
    → Application(Facade → Service)
      → Persistence
```

Controller 레이어(`application.controller`)는 이 경로에 **끼지 않는다**.

### 6.2 TCF OFF — 호환

```text
FW(Interceptor)
  → Application(Controller → Service)
    → Persistence
```

Entry(Handler)를 건너뛴다. TX·업무 선후처리를 Facade와 맞추려면 `Controller → Facade → Service`가 더 일관적이다.

## 7. 패키지 ↔ 레이어 매핑

```text
nhnis.mg                          → Boot (레이어 밖 기동)
nhnis.mg.co.a.entry.*             → Entry
nhnis.mg.co.a.application.*       → Application
nhnis.mg.co.a.dto                 → Contract
nhnis.mg.co.a.persistence.*       → Persistence
nhnis.mg.co.a.config|client|support → 옆길
nhnis.fw.*                        → FW 인프라
rdw.mg.co.a/                      → Persistence 리소스
```

업무·세부 축(`co.a`)이 바뀌어도 **레이어 이름과 순서**는 동일하다.  
예: `nhnis.mg.ic.b.entry.handler` …

## 8. 레이어 vs 컴포넌트 (관계)

한 레이어 안에 여러 컴포넌트가 있다.

| 레이어 | 포함 컴포넌트 |
|--------|----------------|
| Entry | Handler, Aspect |
| Application | Facade, Service, Controller |
| Contract | DTO |
| Persistence | DAO (+ Mapper XML) |
| 옆길 | Config, Client, Support |

컴포넌트별 파일·네이밍·금지사항은 [02.어플리케이션 컴포넌트 구조.md](./02.어플리케이션%20컴포넌트%20구조.md)를 본다.

## 9. 설계 원칙 요약

1. **단방향 의존** — 상위만 하위를 안다.
2. **진입은 Entry(또는 TCF OFF Controller)** — 영속·업무를 HTTP에 붙이지 않는다.
3. **유스케이스 = Facade = TX 1건** — Service에 TX를 기본으로 두지 않는다.
4. **계약(DTO)은 공유, 소유권은 없음** — `dto` 패키지를 application에 넣지 않는다.
5. **영속은 Persistence만** — SQL은 DAO/Mapper에만.
6. **횡단은 Aspect/FW** — 업무 if 분기를 Aspect에 넣지 않는다.
7. **FW와 업무 분리** — ImageLog·공통 Controller는 `pdmg-fw`, 업무는 `nhnis.mg.*`.
