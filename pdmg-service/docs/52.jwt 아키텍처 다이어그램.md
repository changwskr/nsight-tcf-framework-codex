## 3. Access Token 생성

```text
mgjwa1000Service
      │
      ├─ 사용자 정보
      ├─ JTI 생성
      ├─ Channel ID
      ├─ Client IP
      └─ User-Agent
      │
      ▼
JwtTokenIssuer
      │
      ├─────────────────────────────────────────────────┐
      │ JWT Header                                      │
      │                                                 │
      │ alg = RS256                                     │
      │ typ = JWT                                       │
      │ kid = nsight-jwt-rs256                          │
      └─────────────────────────────────────────────────┘
      │
      ├─────────────────────────────────────────────────┐
      │ JWT Payload                                     │
      │                                                 │
      │ iss         = NSIGHT-AUTH                       │
      │ aud         = NSIGHT-MP                         │
      │ sub         = 사용자 ID                        │
      │ jti         = 토큰 고유번호                    │
      │ iat         = 발급 시각                         │
      │ exp         = 만료 시각                         │
      │ type        = ACCESS                            │
      │ userId      = 사용자 ID                        │
      │ userName    = 사용자명                          │
      │ branchId    = 영업점 ID                        │
      │ channelId   = 채널 ID                          │
      │ authGroupId = 권한 그룹                        │
      └─────────────────────────────────────────────────┘
      │
      ▼
RSA Private Key로 RS256 전자서명
      │
      ▼
Header.Payload.Signature
      │
      ▼
Access Token
```

Access Token의 개념적인 형태는 다음과 같습니다.

```text
eyJhbGciOiJSUzI1NiIsImtpZCI6Im5zaWdodC1qd3QtcnMyNTYifQ
.
eyJpc3MiOiJOU0lHSFQtQVVUSCIsInN1YiI6ImFkbWluMDEiLCJ0eXBlIjoiQUNDRVNTIn0
.
RSA_PRIVATE_KEY_SIGNATURE
```

## 4. RSA 키 관리

### 현재 구현

```text
pdmg-jwt 시작
    │
    ▼
JwtKeyConfiguration
    │
    ▼
RSA 2048 Key Pair 신규 생성
    │
    ├─────────────────────────────┐
    │                             │
    ▼                             ▼
RSA Private Key                RSA Public Key
    │                             │
    │ JVM 메모리에 보관           │ Public JWK 변환
    │                             │
    ▼                             ▼
JwtTokenIssuer                JWKSet
    │                             │
    │ Access Token 서명           ▼
    │                     JwkSetController
    │                             │
    │                             ▼
    │                 GET /.well-known/jwks.json
    │
    ▼
RS256 JWT 발급
```

현재 방식에서는 서버가 재기동되면 키가 바뀝니다.

```text
pdmg-jwt 재기동
    │
    ▼
새 RSA Key Pair 생성
    │
    ▼
기존 Public Key 폐기
    │
    ▼
기존 발급 토큰 검증 실패
```

### 운영 권장 방식

```text
Vault / KMS / KeyStore
        │
        │ Private Key 안전 보관
        ▼
pdmg-jwt
        │
        ├─ Private Key 로딩
        ├─ RS256 JWT 서명
        └─ Public Key만 JWKS로 공개
                 │
                 ▼
pdmg-service / pdmg-fw
        │
        └─ JWKS Public Key로 토큰 검증
```

Private Key는 `pdmg-jwt` 밖으로 전달하지 않습니다.

## 7. Access Token 검증 권장 흐름

```text
pdmg-service 요청
      │
      ▼
pdmg-fw DefaultFilter
      │
      ├─ Authorization Header 존재 확인
      │
      ├─ Bearer 접두어 확인
      │
      └─ JWT 문자열 추출
      │
      ▼
JWT Header 해석
      │
      ├─ alg = RS256 확인
      └─ kid = nsight-jwt-rs256 추출
      │
      ▼
JWKS Public Key 조회
      │
      │ GET http://pdmg-jwt:8110/.well-known/jwks.json
      ▼
JWKS 응답
      │
      └─ kid와 일치하는 RSA Public Key 선택
      │
      ▼
RS256 전자서명 검증
      │
      ├─ 성공
      │    └─ Claim 검증 진행
      │
      └─ 실패
           └─ HTTP 401 Unauthorized
```

Claim 검증은 다음 순서로 진행합니다.

```text
전자서명 검증 성공
      │
      ├─ iss = NSIGHT-AUTH인가?
      ├─ aud에 NSIGHT-MP가 포함되는가?
      ├─ exp가 현재 시각보다 이후인가?
      ├─ nbf 이전에 사용한 것은 아닌가?
      ├─ type = ACCESS인가?
      ├─ sub 또는 userId가 존재하는가?
      └─ 허용된 clock skew 범위인가?
      │
      ├─ 전부 정상
      │      └─ 인증 성공
      │
      └─ 하나라도 실패
             └─ HTTP 401 Unauthorized
```

## 9. 현재 실제 검증 구조

현재 `pdmg-fw`는 아직 JWKS 방식으로 검증하지 않습니다.

```text
pdmg-jwt
  │
  │ RSA Private Key
  │ RS256 서명
  ▼
RS256 Access Token
  │
  ▼
pdmg-service
  │
  ▼
DefaultFilter
  │
  ▼
현재 JwtProvider
  │
  ├─ application.yml의 jwt.secret 조회
  ├─ HMAC SecretKey 생성
  └─ HMAC 방식으로 JWT 검증
  │
  ▼
RS256 토큰 검증 실패
```

즉 현재는 다음과 같이 서로 다릅니다.

```text
┌──────────────────────┬───────────────────────────────┐
│ 구분                 │ 현재 구현                     │
├──────────────────────┼───────────────────────────────┤
│ pdmg-jwt 발급 방식   │ RS256                         │
│ pdmg-jwt 서명 키     │ RSA Private Key               │
│ pdmg-fw 검증 방식    │ HMAC                          │
│ pdmg-fw 검증 키      │ jwt.secret 공유 비밀키        │
│ JWKS 검증 연결       │ 구현되지 않음                 │
│ 최종 결과            │ 발급 토큰과 검증 방식 불일치  │
└──────────────────────┴───────────────────────────────┘
```

또한 `pdmg-ui`의 일반 업무용 `service-client.js`는 현재 `Authorization` 헤더를 전달하지 않습니다.

```text
현재 일반 업무 화면
  │
  ▼
service-client.js
  │
  ├─ Content-Type
  ├─ Accept
  └─ Authorization 없음
  │
  ▼
JWT 검증이 활성화된 pdmg-service
  │
  ▼
HTTP 401 가능
```

## 10. Refresh Token 갱신

```text
Access Token 만료 예정 또는 만료
      │
      ▼
pdmg-ui
      │
      │ sessionStorage의 Refresh Token
      │ Service ID: mgjwa1000U0
      ▼
pdmg-jwt
      │
      ▼
mgjwa1000Service
      │
      ├─ Refresh Token Hash 계산
      ├─ DB 저장 정보 조회
      ├─ 만료 여부 확인
      ├─ 폐기 여부 확인
      ├─ Token Family 확인
      ├─ 사용자 상태 확인
      └─ 재사용 여부 확인
      │
      ├─────────────────────────────┐
      │                             │
      │ 정상                        │ 비정상
      ▼                             ▼
기존 Refresh Token 폐기         갱신 거부
      │                             │
신규 Access Token 생성          필요 시 Token Family 폐기
      │                             │
신규 Refresh Token 생성         보안 이력 기록
      │                             │
DB 저장                         HTTP 401
      │
      ▼
신규 토큰 응답
      │
      ▼
pdmg-ui sessionStorage 교체
```

이를 Refresh Token Rotation이라고 합니다.

```text
Refresh Token R1 사용
       │
       ├─ R1 폐기
       └─ R2 신규 발급

폐기된 R1 재사용 시도
       │
       ▼
토큰 탈취 가능성 감지
       │
       └─ 같은 Token Family 전체 폐기 가능
```

## 12. Access Token 강제 폐기

```text
관리자
  │
  ▼
pdmg-ui JWT 토큰 관리 화면
  │
  │ Service ID: mgjwa1001D0
  │ JTI + 폐기 사유
  ▼
pdmg-jwt
  │
  ├─ 토큰 조회
  ├─ 폐기 권한 확인
  ├─ Denylist 등록
  └─ 폐기 이력 저장
  │
  ▼
이후 해당 Access Token 차단
```

다만 서명 검증만 하는 `pdmg-service`에서는 Denylist가 자동으로 적용되지 않습니다.

실시간 폐기까지 적용하려면 다음 중 하나가 필요합니다.

```text
방법 1: pdmg-service가 pdmg-jwt에 JTI 상태 조회
방법 2: Denylist를 Redis 같은 공유 저장소에 보관
방법 3: 짧은 Access Token 만료시간을 사용하고 갱신 시점에만 상태 확인
```

일반적으로는 `짧은 Access Token + Refresh Rotation + 공유 Denylist` 조합이 적절합니다.

## 13. 인증 실패 처리

```text
JWT 검증
  │
  ├─ Authorization 없음
  ├─ Bearer 형식 오류
  ├─ 전자서명 불일치
  ├─ 만료된 토큰
  ├─ 발급자 불일치
  ├─ Audience 불일치
  ├─ ACCESS가 아닌 토큰
  ├─ 폐기된 JTI
  └─ 알 수 없는 kid
  │
  ▼
DefaultFilter 또는 Security Filter
  │
  ├─ 업무 Controller 호출 차단
  ├─ 내부 예외 정보 숨김
  └─ HTTP 401 표준 오류 응답
```

인증과 권한 실패는 구분해야 합니다.

```text
인증 실패
  └─ HTTP 401 Unauthorized
     예: 토큰 없음, 만료, 서명 오류

권한 실패
  └─ HTTP 403 Forbidden
     예: 정상 토큰이지만 해당 업무 권한 없음
```

## 14. 최종 권장 아키텍처

```text
┌────────────────┐

        │ 로그인
        ▼

│                                                       │
│ · Access Token은 메모리 또는 보호된 세션 영역에 보관 │
│ · Refresh Token은 HttpOnly/Secure Cookie 권장         │
└───────┬───────────────────────────────┬───────────────┘
        │                               │
        │ 인증 요청                     │ 업무 요청 + Access Token
        ▼                               ▼
┌───────────────────────┐      ┌────────────────────────┐
│ pdmg-jwt              │      │ pdmg-service           │
│                       │      │                        │
│ Private Key 보유      │      │ 업무 처리              │
│ RS256 토큰 서명       │      └────────────┬───────────┘
│ JWKS 공개             │                   │
│ Refresh Token 관리    │                   ▼
│ Denylist 관리         │      ┌────────────────────────┐
└──────────┬────────────┘      │ pdmg-fw                │
           │                   │                        │
           │ JWKS              │ DefaultFilter          │
           └──────────────────▶│ RS256 JwtDecoder       │
                               │                        │
                               │ · Public Key 캐시      │
                               │ · 서명 검증            │
                               │ · Claim 검증           │
                               │ · Denylist 확인        │
                               │ · ServiceContext 생성  │
                               └────────────┬───────────┘
                                            │
                                            ▼
                               Handler → Facade → Service
                                            │
                                            ▼
                                          업무 DB
```

## 전체 흐름 요약

```text
로그인
  → 사용자 인증
  → pdmg-jwt가 Private Key로 RS256 토큰 발급
  → pdmg-ui가 토큰 보관
  → 업무 요청에 Access Token 첨부
  → pdmg-fw가 JWKS Public Key로 서명 검증
  → Claim과 Denylist 검증
  → ServiceContext에 사용자 정보 저장
  → pdmg-service 업무 실행
  → Access Token 만료 시 Refresh Token Rotation
  → 로그아웃 시 Refresh Token 폐기 및 Access Token Denylist 등록
```

현재 반드시 보완해야 하는 연결 지점은 다음 두 곳입니다.

```text
1. pdmg-fw
   HMAC JwtProvider
     → JWKS 기반 RS256 JwtDecoder로 변경

2. pdmg-ui
   일반 업무 요청의 service-client.js
     → Authorization: Bearer {Access Token} 추가
```
