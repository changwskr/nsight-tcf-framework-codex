## 1. 정의

**전문 DTO**는 요청/응답 JSON의 **`dto` 노드**를 담는 업무 타입이다.  
봉투 키 `hdr_nhnis`는 FW 헤더 타입이고, 업무 모듈 DTO가 아니다.

```text
와이어 JSON                    Java
─────────────────────         ─────────────────────────────
hdr_nhnis                     nhnis.fw…header.hdr_nhnis     ← FW
  └─ sys_comm                 …header.sys_comm              ← FW
dto                           nhnis.mg.co.a.dto.*DTOin/out  ← 업무 ★
```

| 구분 | 타입 | 누가 만드나 |
|------|------|-------------|
| 헤더 | `hdr_nhnis` / `sys_comm` | UI·Filter·Interceptor |
| 업무 입력 | `{서비스ID}DTOin` | UI JSON → Facade `convert` |
| 업무 출력 | `{서비스ID}DTOout` | Service → Advice가 `dto`에 실음 |
| 목록 행 | `{서비스ID}DTOSub[n]` | Service가 out에 적재 |
| (선택) MsgJson | `…MsgJson` | marshal/특수 직렬화 |

봉투 전체 계약·실패 `NH_NIS_ERR_DTO`는 [10](./10.전문.md) · [11](./11.예외처리.md).

## 2. 위치 · 네이밍

| 항목 | 규칙 |
|------|------|
| 패키지 | `nhnis.mg.co.a.dto` (`application` 밖) |
| 입력 | `{서비스ID}DTOin` — `mgcoa8888S0DTOin` |
| 출력 | `{서비스ID}DTOout` — `mgcoa8888S0DTOout` |
| 행 | `{서비스ID}DTOSub0` — 목록 요소 (Sub1… 가능) |
| 상속 | 보통 `com.ims.superspring.dto.DataObject` |
| JSON 필드 | **camelCase** (예외: 일부 결과코드 `PROC_CNT` 등 레거시 대문자) |

```text
좋음: mgcoa8888S0DTOin / mgcoa8888D0DTOin   (거래마다 타입)
나쁨: mgcoa8888DtoIn, ImageLogRequest, RequestDto
나쁨: nhnis.mg.co.a.application.dto (…)
```

서비스 ID **전체**(구분자·순번 포함)가 클래스명에 들어간다.  
Handler/Facade/Service **파일명**에는 구분자 없고, **DTO만** 거래 단위다.

## 3. 계층별 변환

```text
① HTTP Body { hdr_nhnis, dto: {…} }
② Filter — hdr → ServiceContext / dto는 Body에 유지
③ Controller — request.get("dto") → Object (대개 Map)
④ Handler — dtoBody 그대로 Facade
⑤ Facade — objectMapper.convertValue(dtoBody, *DTOin.class)  ★
⑥ Service — *DTOin → 업무 → *DTOout
⑦ Advice — body(*DTOout) → JSON dto (+ hdr_nhnis)         ★
     removeUnwantedFields (fieldPropertyMap, *List, *Array …)
```

| 계층 | 시그니처 |
|------|----------|
| Handler | `Object dtoBody` |
| Facade | `Object` → `*DTOin` / return `*DTOout` |
| Service | `*DTOin` → `*DTOout` |
| DAO | `Map` (DTO 직접 전달 안 함) |

`null` dtoBody → Facade에서 `emptyMap()`으로 convert하는 샘플이 있다.

## 4. 타입 종류

### 4.1 `*DTOin` (요청 dto)

거래 입력 필드. 조회면 검색조건 + 페이징.

| 공통(목록 S) | 의미 |
|--------------|------|
| `pageNo` / `pageSize` | 페이지 (Service가 보정, offset 계산) |
| 업무 검색 키 | `trtBrc`, `guid`, `keyword` … |

`offset`은 **DTO/와이어에 두지 않는다** ([08](./08.대용량%20페이징%20처리방식.md)).

### 4.2 `*DTOout` (응답 dto)

| 목록형 | 쓰기형 |
|--------|--------|
| `*DTOSub0` 목록 + `size` | `PROC_CNT`, `RSLT_CD`, `RSLT_MSG` |
| `pageNo`, `pageSize` | (업무 정책 코드) |
| `totalCount`, `totalPages` | |

목록 out의 리스트 getter는 DataObject 관례상  
`getmgcoa8888S0DTOSub0()` / `getmgcoa8888S0DTOSub0List()` 등이 함께 있다.  
Advice가 `*List`/`*Array` 메타를 와이어에서 깎는다 → 클라이언트에는 정리된 JSON.

### 4.3 `*DTOSub0` (행)

한 행 = DB Map → Service `asString` 매핑 대상 필드.

### 4.4 `*MsgJson` (선택)

`mgcoa9999` 등에 `…DTOinMsgJson` / `…DTOoutMsgJson` / `…DTOSub0MsgJson`이 있다.  
superspring marshal·메시지 JSON 엔진용 부가 타입.  
일반 Facade `convertValue` 경로의 주 타입은 여전히 `*DTOin`/`*DTOout`.

### 4.5 헤더 (참고 — 업무 DTO 아님)

- `hdr_nhnis` — `sys_comm` 하나 보유  
- `sys_comm` — `rms_svc_c`, `std_gbl_id`, `scid`, `optr_eno`, …  
상세 필드: [10](./10.전문.md) §2.1 · `pdmg-fw` 소스.

## 5. DataObject · 와이어 정리

업무 DTO는 `DataObject`를 상속해 메타(`fieldPropertyMap`, logicalName 등)를 가질 수 있다.

| 구간 | 처리 |
|------|------|
| 업무 후처리 로그 | `PdmgMessagePrinter.businessDto` — sanitize 후 JSON |
| 시스템 후처리 | `removeUnwantedFields` — `dtoLogicalName`, `fieldPropertyMap`, `*List`/`*Array` 제거 |

클라이언트·ImageLog 응답 전문에는 **업무 필드 중심**만 남긴다.

## 7. JSON 예 (dto만)

요청 (`mgcoa8888S0`):

```json
{
  "guid": null,
  "serviceId": null,
  "withinSeconds": 300,
  "pageNo": 1,
  "pageSize": 20
}
```

요청 (`mgcoa8888D0`):

```json
{ "guidList": ["abc…"] }
```

응답 목록 dto (개념):

```json
{
  "mgcoa8888S0DTOSub0": [ { "guid": "…", "serviceId": "…" } ],
  "size": 1,
  "pageNo": 1,
  "pageSize": 20,
  "totalCount": 1,
  "totalPages": 1
}
```

응답 쓰기 dto (개념):

```json
{
  "PROC_CNT": 1,
  "RSLT_CD": "0000",
  "RSLT_MSG": "OK"
}
```

실제 HTTP Body는 항상(성공 시) `{ "hdr_nhnis":…, "dto":… }` ([26](./26.시스템후처리.md)).

## 8. 신규 거래 시 DTO

1. `{서비스ID}DTOin` / `{서비스ID}DTOout` 생성  
2. 목록이면 `{서비스ID}DTOSub0` + out 페이징 필드  
3. 쓰기면 out에 `PROC_CNT`/`RSLT_*` 또는 동등 계약  
4. Facade `convert(…, DTOin.class)` · Service 시그니처 맞추기  
5. UI sample-request의 `dto` 키 = Java 필드명  
6. (필요 시) MsgJson 생성 — 9999 패턴 참고  

같은 프로그램에 거래만 추가할 때 Handler/Facade/Service **클래스**는 유지하고 DTO 파일은 **거래마다 추가**.

---

## 9. 하지 말 것

1. 전문 전체(`hdr_nhnis` 포함)를 `*DTOin`으로 convert  
2. DTO를 DAO 인자로 직접 전달 (현행은 Map)  
3. `DtoIn`/`RequestDto` 등 서비스 ID 없는 이름  
4. `application.dto` 패키지에 두기  
5. 클라이언트에 `fieldPropertyMap` 노출을 전제로 설계 (Advice가 제거)  
6. 성공 응답을 `NH_NIS_ERR_DTO` 스키마와 섞기  
7. StandardRequestDto / STF-ETF 계약 재도입
