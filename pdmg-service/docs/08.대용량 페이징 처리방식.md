# 08. 대용량 페이징 처리방식 (PDMG)

기준일: 2026-08-09  
대상: `pdmg-service` 목록 조회(S0)  
기준 구현: `mgcoa8888S0` / `mgcoa5530S0` / `mgcoa9000S0`  
관련: [06.네이밍 형식.md](./06.네이밍%20형식.md) · [07.도메인 정의 및 호출방식.md](./07.도메인%20정의%20및%20호출방식.md) · [성능감시.md](./성능감시.md)

---

## 1. 목적

목록 API가 대량 행을 **한 번에 메모리·네트워크로 끌어오지 않도록**,  
**페이지 단위 DB 조회 + 건수 조회**로 응답 크기를 제한한다.

| 목표 | 방법 |
|------|------|
| 응답 행 수 제한 | `pageSize` 상한 **100** |
| 전체 건수·페이지 수 | 별도 `*_count` SQL |
| DB에서 자르기 | Oracle `ROWNUM` 래핑 (`offset` + `pageSize`) |
| 검색 범위 축소 | WHERE + (선택) 시간창·임계 필터 |

**금지:** Service에서 전체 `List`를 받은 뒤 `subList`로 페이징.

---

## 2. 표준 방식 요약 (현재)

```text
요청 dto: pageNo, pageSize (+ 검색조건)
    │
Service
    ├─ pageNo 기본 1, pageSize 기본 20, 최대 100
    ├─ offset = (pageNo - 1) * pageSize
    ├─ DAO.*_S0_count(param)  → totalCount
    └─ DAO.*_S0(param)        → 현재 페이지 rows
    │
응답 dto: Sub 목록 + pageNo, pageSize, totalCount, totalPages, size
```

| SQL ID | 역할 |
|--------|------|
| `{서비스ID}_S0` | 페이지 데이터 |
| `{서비스ID}_S0_count` | 동일 WHERE의 `COUNT(*)` |

예: `mgcoa8888S0_S0` / `mgcoa8888S0_S0_count`

---

## 3. 계약 (DTO)

### 3.1 입력 (`*S0DTOin`)

| 필드 | 타입 | 기본 | 규칙 |
|------|------|------|------|
| `pageNo` | Integer | `1` | `null` 또는 `≤0` → 1 |
| `pageSize` | Integer | `20` | `null` 또는 `≤0` → 20, **`>100` → 100** |
| (검색조건) | … | | 업무별. count와 list에 **동일** 적용 |

`offset`은 클라이언트에 받지 않는다. **Service가 계산**해 param에 넣는다.

### 3.2 출력 (`*S0DTOout`)

| 필드 | 의미 |
|------|------|
| `*DTOSub0` 목록 | 현재 페이지 행 |
| `size` | 이번 응답 행 수 |
| `pageNo` / `pageSize` | 실제 적용값(보정 후) |
| `totalCount` | 조건 전체 건수 |
| `totalPages` | `ceil(totalCount / pageSize)` |

0건이면 목록 빈 배열 + `totalCount=0` (업무 정책상 오류가 아니면 `BizException` 없음).

## 4. Service 처리 패턴

```java
int pageNo = (input == null || input.getPageNo() == null || input.getPageNo() <= 0)
        ? 1 : input.getPageNo();
int pageSize = (input == null || input.getPageSize() == null || input.getPageSize() <= 0)
        ? 20 : input.getPageSize();
if (pageSize > 100) {
    pageSize = 100;
}
int offset = (pageNo - 1) * pageSize;
param.put("pageNo", pageNo);
param.put("pageSize", pageSize);
param.put("offset", offset);

int totalCount = dao.mgcoaXXXXS0_S0_count(param);
List<Map<String, Object>> rows = dao.mgcoaXXXXS0_S0(param);

output.setPageNo(pageNo);
output.setPageSize(pageSize);
output.setTotalCount(totalCount);
output.setTotalPages(pageSize <= 0 ? 0 : (int) ((totalCount + pageSize - 1L) / pageSize));
```

| 계층 | 책임 |
|------|------|
| Facade | TX(`readOnly`), DTO 변환 |
| **Service** | page 보정·offset·count/list 호출·Sub 조립 |
| DAO/XML | SQL만 |

## 5. SQL 패턴 (Oracle ROWNUM)

목록·건수가 **같은 WHERE**를 `<sql id="…Where">`로 공유한다.

```xml
<select id="mgcoa8888S0_S0" …>
    SELECT * FROM (
      SELECT a.*, ROWNUM rnum
        FROM (
           SELECT /* mgcoa8888S0_S0 */ …
             FROM … T1
           <include refid="mgcoa8888Where"/>
            ORDER BY …          <!-- 페이징 안정성을 위해 ORDER BY 필수 -->
        ) a
       WHERE ROWNUM &lt;= #{offset} + #{pageSize}
    )
    WHERE rnum > #{offset}
</select>

<select id="mgcoa8888S0_S0_count" resultType="int" …>
    SELECT /* mgcoa8888S0_S0_count */ COUNT(*)
      FROM … T1
    <include refid="mgcoa8888Where"/>
</select>
```

### 5.1 규칙

1. **ORDER BY 고정** — 없으면 페이지마다 행이 흔들릴 수 있다.  
2. **count와 list WHERE 동일** — 페이지 수·화면 총건수 불일치 방지.  
3. bind만 사용 (`#{offset}`, `#{pageSize}`).  
4. H2 로컬은 Oracle 호환 모드/동일 문법 전제를 유지한다. DB별 분기 시 Mapper를 분리한다.

### 5.2 offset 의미

```text
pageNo=1, pageSize=20 → offset=0  → rnum 1~20
pageNo=2, pageSize=20 → offset=20 → rnum 21~40
```

## 6. “대용량”에서 이 방식의 한계와 보완

### 6.1 깊은 페이지 문제

`ROWNUM`+`offset`은 **앞쪽 `offset+pageSize` 행을 만든 뒤** 자른다.  
`pageNo`가 커질수록(예: 1만 페이지) DB·정렬 비용이 커진다.

| 상황 | 권장 |
|------|------|
| 화면 일반 목록 (앞쪽 페이지) | 현재 표준(offset)으로 충분 |
| 매우 깊은 페이지·무한 스크롤 | **키셋(keyset) 페이징** 검토 (아래 §7) |
| 전체 수천만 건을 매번 COUNT | 대략치·캐시·“10000+” UI 등 별도 정책 |

### 6.2 검색으로 집합을 줄이기 (현재 샘플)

대용량 테이블은 **페이징 전에 WHERE로 줄이는 것**이 우선이다.

| 기법 | 예 (`mgcoa8888`) |
|------|------------------|
| 기간 창 | `withinSeconds` → `requestTimeFrom`/`To` |
| 임계 필터 | `minElapsedSeconds` (응답 지연 건만) |
| 키·부분일치 | `guid`, `serviceId`, `optrEno` … |
| 예외만 | `exceptionOnly` |

인덱스는 `ORDER BY`·WHERE 선두 컬럼에 맞춘다. (예: `REQUEST_TIME`, `GUID`)

### 6.3 pageSize 상한

`100`은 API·UI·DB 보호용 hard cap이다.  
배치성 대량 추출이 필요하면 **목록 S0가 아니라** 전용 거래(R/배치/파일)로 분리한다.

## 7. 키셋(Cursor) 페이징 (확장 옵션)

표준은 아직 offset이다. 초대규모·무한 스크롤이 필요하면 거래 단위로 도입한다.

```text
요청: lastRequestTime + lastGuid + pageSize
SQL:  WHERE (REQUEST_TIME, GUID) < (#{lastRequestTime}, #{lastGuid})
      ORDER BY REQUEST_TIME DESC, GUID DESC
      FETCH FIRST #{pageSize} ROWS ONLY   -- 또는 ROWNUM 상한만
```

| 장점 | 단점 |
|------|------|
| 깊은 페이지에서도 비용 안정 | `totalCount`/`totalPages`와 궁합이 다름 |
| | UI가 “N페이지로 점프”하기 어려움 |

도입 시 서비스 ID·DTO 필드를 명시하고, 기존 S0와 계약을 섞지 않는다.

---

## 8. 트랜잭션·성능

- 목록은 Facade `@Transactional(readOnly = true)`.  
- count + list는 **같은 요청·같은 TX**에서 연속 호출(기본).  
- SQL 시간은 `MybatisLogInterceptor` DEBUG로 확인. → [성능감시.md](./성능감시.md)  
- count가 느리면 WHERE·인덱스·필요 시 count 생략/비동기 정책을 업무과 합의한다.

---

## 9. 체크리스트 (신규 목록 S0)

- [ ] DTOin: `pageNo`, `pageSize`  
- [ ] DTOout: Sub 목록 + `pageNo`, `pageSize`, `totalCount`, `totalPages`, `size`  
- [ ] Service: 기본 1/20, 상한 100, `offset` 계산  
- [ ] DAO: `{id}_S0` + `{id}_S0_count`  
- [ ] XML: 공통 Where, ORDER BY, ROWNUM 래핑  
- [ ] count와 list 조건 동일  
- [ ] 전체 조회 후 자른 페이징 없음  
- [ ] 대용량 테이블이면 기간·키 조건·인덱스 검토

## 10. 요약

```text
대용량 대응의 PDMG 기본값
  = pageSize≤100
  + DB ROWNUM 페이징
  + 동일 WHERE의 COUNT
  + (가능하면) 검색·기간으로 집합 축소

한 번에 다 가져오기 · 메모리 페이징 · pageSize 무제한 금지
깊은 페이지·초대규모는 키셋/전용 추출 거래를 검토
```
