## 15. Interceptor — ServicePrevention.preHandle 분석 결과

`ServicePreventionInterceptor.preHandle()`은 Controller가 실행되기 직전에 호출되는 시스템 선처리입니다.

핵심 기능은 다음입니다.

```text
GUID 확정
+ 공통 헤더 보완
+ 요청 전문 로그
+ ImageLog INSERT
```

이름이 `ServicePrevention`이지만 현재 코드에는 서비스 차단이나 거래통제 기능이 없습니다. 모든 정상 분기에서 `true`를 반환하여 요청을 계속 진행시킵니다.

소스: [ServicePreventionInterceptor.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/interceptor/ServicePreventionInterceptor.java:47>)

---

## 1. 호출 위치

```text
HTTP 요청
  ↓
DefaultFilter
  ├─ JWT 검증
  ├─ Body 캐시
  ├─ hdr_nhnis 파싱
  └─ ServiceContext 생성
  ↓
DispatcherServlet
  ↓
HandlerMapping
  ↓
ServicePreventionInterceptor.preHandle     ★ 현재 위치
  ├─ GUID·헤더 보완
  ├─ 요청 전문 로그
  └─ ImageLog INSERT
  ↓
OnlineTransactionController
  ↓
TcfFacade → Handler
  ↓
Facade / TransactionTemplate              ★ 업무 TX 시작
  ↓
Service → DAO
```

따라서 `preHandle()`은 업무 트랜잭션이 시작되기 전입니다.

## 3. 실제 처리 순서

`preHandle()`은 TX-FLOW 로그를 감싸고 내부 메서드를 호출합니다.

```java
public boolean preHandle(...) throws Exception {
    PdmgTxFlowLog.enter(...);
    try {
        return preHandleInternal(...);
    } finally {
        PdmgTxFlowLog.leave(...);
    }
}
```

내부 처리 흐름은 다음과 같습니다.

```text
[시스템 선처리] 시작
  ↓
multipart 요청인가?
  ├─ YES → 아무 처리 없이 true
  └─ NO
       ↓
ServiceContext가 있는가?
  ├─ NO → WARN 후 true
  └─ YES
       ↓
hdr_nhnis / sys_comm 보장
  ↓
GUID 보장
  ↓
serviceId·화면ID·IP·사용자 보완
  ↓
요청 원문 조회
  ↓
요청 전문 로그 출력
  ↓
TB_FW_IMAGE_LOG INSERT
  ↓
[시스템 선처리] 종료
  ↓
return true
```

핵심 코드:

```java
hdr_nhnis header = ensureHeader(ctx);
String guid = ensureGuid(ctx, header);
enrichHeaderFromRequest(request, header);

String requestRaw = resolveRequestBodyRaw(ctx, request);
logRequestMessage(requestRaw);

imageLogHandler.preImagelog(header, requestRaw);

return true;
```

## 4. multipart 요청

다음 조건이면 시스템 선처리를 건너뜁니다.

```java
String contentType = request.getContentType();

if (contentType != null
        && contentType.startsWith("multipart")) {
    return true;
}
```

multipart에서는 다음 작업을 하지 않습니다.

```text
GUID 보정
공통 헤더 보완
요청 전문 로그
ImageLog INSERT
```

또한 앞서 분석한 `DefaultFilter`에서도 multipart는 JWT 검증을 건너뜁니다.

따라서 현재 비-local multipart 흐름은:

```text
DefaultFilter
  → JWT 검사 없음
  → 최소 ServiceContext만 생성
  ↓
ServicePreventionInterceptor
  → 시스템 선처리 전체 생략
  ↓
Controller 실행
```

파일 업로드 기능을 운영할 경우 반드시 별도 보완이 필요합니다.

## 5. ServiceContext 처리

`DefaultFilter`가 다음과 같이 생성한 요청별 Context를 사용합니다.

```java
ServiceContext ctx =
        ServiceContextHolder.getInstance();
```

### Context가 없을 때

현재는 요청을 차단하지 않습니다.

```java
if (ctx == null) {
    LOGGER.warn(...);
    return true;
}
```

그 결과:

```text
ServiceContext 없음
→ 요청 전문 로그 없음
→ ImageLog 없음
→ GUID 추적 불가
→ 그래도 Controller 실행
```

이를 fail-open 방식이라고 볼 수 있습니다.

운영에서 `ServiceContext`가 필수라면 다음 중 하나를 선택해야 합니다.

```text
엄격 모드:
  Context 없음 → 시스템 오류 응답, Controller 진입 차단

완화 모드:
  현재처럼 WARN 후 통과
```

금융 온라인 거래 추적이 필수라면 엄격 모드가 더 적합합니다.

## 6. hdr_nhnis 보장

다음 메서드가 헤더 객체를 보장합니다.

```java
private hdr_nhnis ensureHeader(ServiceContext ctx)
```

처리 방식:

```text
ctx.header가 null
→ new hdr_nhnis()
→ ctx.setHeader()

header.sys_comm이 null
→ new sys_comm()
```

따라서 이후 로직은 `header.getSys_comm()`을 안전하게 사용할 수 있습니다.

단, Context 자체가 null이면 이 메서드가 실행되지 않습니다.

## 7. GUID 생성과 동기화

GUID는 `hdr_nhnis.sys_comm.std_gbl_id`를 사용합니다.

```java
String guid = sys.getStd_gbl_id();
```

값이 없으면 UUID를 생성합니다.

```java
guid = UUID.randomUUID()
        .toString()
        .replace("-", "");
```

생성된 값은 세 군데에 동기화됩니다.

```java
sys.setStd_gbl_id(guid);
ctx.setGuid(guid);
ThreadContext.put("guid", guid);
```

즉:

```text
표준 전문 GUID
= ServiceContext GUID
= 로그 MDC GUID
```

이미 값이 있어도 Context와 MDC에 다시 반영합니다.

이 부분은 `DefaultFilter`에서 헤더는 있지만 GUID가 빠진 경우를 보완하는 방어 로직입니다.

다만 `DefaultFilter`가 GUID null을 `ThreadContext.put()`에 넣다가 먼저 예외가 발생하면 Interceptor까지 도달하지 못할 가능성이 있습니다. 따라서 GUID 기본값 생성은 Filter와 Interceptor 중 한 곳의 명확한 책임으로 통합하는 것이 좋습니다.

## 8. 공통 헤더 보완

`enrichHeaderFromRequest()`는 비어 있는 다음 필드를 보완합니다.

| 필드           | 보완 방식                             |
| -------------- | ------------------------------------- |
| `rms_svc_c`    | URL 마지막 세그먼트                   |
| `scid`         | serviceId에서 `[SD]\d+$` 제거         |
| `tr_trm_ipadr` | X-Forwarded-For 첫 값 또는 remoteAddr |
| `optr_eno`     | MDC `userId`, 없으면 `LOCAL`          |

### serviceId

```java
String pathService = extractServiceId(request);
```

예:

```text
/mgcoa5530S0 → mgcoa5530S0
/mgcoa8888D0 → mgcoa8888D0
```

하지만 다음 경로는 문제가 있습니다.

```text
/online       → online
/mg/online    → online
```

헤더에 `rms_svc_c`가 없다면 실제 업무 serviceId 대신 `online`이 저장될 수 있습니다. `/online` 경로는 전문 헤더의 `rms_svc_c`를 필수로 검증하는 것이 안전합니다.

### 화면 ID

```java
sys.setScid(
    serviceId.replaceFirst("[SD]\\d+$", "")
);
```

예:

```text
mgcoa5530S0 → mgcoa5530
mgcoa8888D0 → mgcoa8888
```

현재 정규식은 `S`, `D` 유형만 제거합니다.

```text
mgcoa9000C0 → mgcoa9000C0
mgcoa9000U0 → mgcoa9000U0
```

CRUD 거래에서 `C0`, `U0`도 화면 ID 접미사로 제거하려면 다음처럼 범위를 확장해야 합니다.

```regex
[SCUD]\d+$
```

## 9. 사용자 ID 처리

사용자 ID는 다음 순서로 구합니다.

```text
1. 전문의 optr_eno가 이미 있으면 유지
2. MDC userId 사용
3. 없으면 "LOCAL"
```

코드:

```java
Object mdcUser = ThreadContext.get("userId");

if (mdcUser != null) {
    sys.setOptr_eno(String.valueOf(mdcUser));
} else {
    sys.setOptr_eno("LOCAL");
}
```

JWT에서 얻은 `ssoId`는 `DefaultFilter`에서 request attribute에 저장됩니다.

```java
request.setAttribute("ssoId", ssoId);
```

하지만 현재 `preHandle()`은 `request.getAttribute("ssoId")`를 읽지 않습니다.

또한 `DefaultFilter`가 MDC `userId`에 넣는 값은 JWT subject가 아니라 전문의 `optr_eno`입니다.

따라서 비-local에서 전문에 사용자번호가 없으면 JWT가 정상이어도:

```text
JWT subject = USER100
request.ssoId = USER100
MDC userId = 없음
preHandle optr_eno = LOCAL
```

이 될 수 있습니다.

사용자별 거래통제를 계획한다면 `ssoId`와 `optr_eno`의 신뢰 기준을 명확히 하고, JWT 인증 사용자 정보를 우선 사용해야 합니다.

## 10. 클라이언트 IP

처리 순서는 다음과 같습니다.

```text
전문 tr_trm_ipadr가 있으면 그대로 사용
→ 없으면 X-Forwarded-For 첫 값
→ 없으면 request.remoteAddr
```

현재는 클라이언트가 전문에 넣은 `tr_trm_ipadr`를 우선 신뢰합니다.

따라서 IP별 거래통제를 적용한다면 클라이언트가 임의 IP를 전문에 넣을 수 있습니다. IP 통제용 값은 다음 기준으로 분리하는 것이 안전합니다.

```text
감사 전문 IP:
  요청 전문 tr_trm_ipadr

통제용 실제 IP:
  신뢰 프록시가 기록한 X-Forwarded-For
  또는 request.remoteAddr
```

신뢰할 프록시 목록 없이 `X-Forwarded-For`를 그대로 믿는 것도 위조 위험이 있습니다.

## 11. 요청 전문 조회

요청 원문은 다음 순서로 찾습니다.

```text
1. ServiceContext.requestBody
2. request attribute PDMG_REQUEST_BODY
3. wrapper chain에서 CachedBodyHttpServletRequest 검색
4. 없으면 "(empty-request-body)"
```

첫 번째:

```java
String raw = ctx.getRequestBody();
```

두 번째:

```java
request.getAttribute(
    DefaultFilter.REQUEST_BODY_ATTR
)
```

세 번째:

```java
if (current instanceof CachedBodyHttpServletRequest cached) {
    raw = new String(
        cached.getCachedBody(),
        StandardCharsets.UTF_8
    );
}
```

이렇게 여러 경로를 두어 Filter와 MVC 래퍼가 변경되더라도 가능한 한 요청 전문을 확보합니다.

## 14. ImageLog와 업무 트랜잭션

`preHandle()`은 Facade/timeout worker의 업무 트랜잭션이 시작되기 전에 실행됩니다.

또한 `ImageLogHandler`에는 `@Transactional`이나 `REQUIRES_NEW`가 없습니다.

```java
public ImageLogHandler(DataSource dataSource) {
    this.jdbcTemplate = new JdbcTemplate(dataSource);
}
```

따라서 일반적인 현재 흐름은:

```text
Interceptor thread
  → JdbcTemplate INSERT
  → auto-commit
  ↓
Controller
  ↓
timeout worker thread
  → 업무 TX 시작
```

즉, ImageLog INSERT는 업무 트랜잭션과 묶이지 않습니다.

이것은 감사 로그 관점에서는 적절합니다.

```text
업무 성공 → 로그 유지
업무 실패 → 로그 유지
업무 롤백 → 로그 유지
타임아웃 → 로그 유지
```

하지만 데이터소스나 트랜잭션 설정이 변경되더라도 분리를 보장하려면 전용 로그 데이터소스 또는 명시적인 `REQUIRES_NEW` 정책을 고려할 수 있습니다.

## 15. 동일 GUID 재요청

이미 같은 GUID가 존재하면 신규 행을 추가하지 않고 기존 행을 갱신합니다.

```text
동일 GUID 존재
→ SERVICE_ID 등 선처리 정보 덮어쓰기
→ RESPONSE_TIME 초기화
→ 기존 응답·예외 정보 초기화
```

즉, 동일 GUID로 샘플을 재전송하면 과거 거래 이력이 보존되지 않습니다.

운영 거래에서 GUID는 요청마다 유일해야 합니다. 중복 GUID를 허용해 덮어쓰기보다는 다음 방식이 더 안전합니다.

```text
중복 GUID
→ 요청 거절
또는
→ 별도 순번을 둔 신규 거래행 INSERT
```

감사 추적 관점에서는 기존 이력을 덮어쓰는 정책이 위험합니다.

## 16. 거래통제 수행 여부

현재 `preHandle()`에는 다음 통제 로직이 없습니다.

```text
서비스별 통제
사용자별 통제
IP별 통제
브랜치별 통제
시간대별 통제
거래량 제한
서비스 중지 여부 조회
```

현재 하는 일은 통제에 필요한 데이터 준비뿐입니다.

```text
serviceId 준비
userId 준비
clientIp 준비
GUID 준비
```

즉:

```text
현재 preHandle
= 거래통제 실행기 X
= 거래통제 입력정보 준비 O
```

거래통제를 추가한다면 `preImagelog()` 전후에 다음 구조를 둘 수 있습니다.

```text
헤더·GUID·사용자·IP 보완
  ↓
TransactionControlService.check(...)
  ├─ 허용 → ImageLog INSERT → Controller
  └─ 차단 → 표준 오류 응답 → return false
```

다만 Controller 호출 전 차단 시 `ResponseBodyAdvice`가 실행되지 않을 수 있으므로 직접 표준 오류 전문을 작성하거나 예외를 던져 `GlobalExceptionHandler`가 처리하도록 해야 합니다.

권장 방식은 예외입니다.

```java
transactionControlService.validate(context);

if (blocked) {
    throw new TransactionBlockedException(...);
}
```

| 우선순위 | 발견 사항                                 | 영향                      |

| P0       | 요청 전문 전체를 마스킹 없이 로그·DB 저장 | 개인정보·비밀정보 노출    |
| P0       | multipart는 JWT와 시스템 선처리 모두 우회 | 인증·감사 공백            |
| P1       | Context가 없어도 요청 통과                | 추적되지 않는 거래 발생   |
| P1       | JWT `ssoId`를 사용자번호에 반영하지 않음  | 사용자별 통제 부정확      |
| P1       | 전문의 IP를 우선 신뢰                     | IP별 통제 우회 가능       |
| P1       | 동일 GUID 재요청 시 기존 이력 덮어쓰기    | 감사 이력 유실            |
| P1       | `/online`을 serviceId로 저장할 가능성     | 잘못된 거래 식별          |
| P2       | 화면 ID 정규식이 S/D만 지원               | C/U 거래 scid 부정확      |
| P2       | 모든 MVC URL에 Interceptor 적용           | 관리·정적 URL 오동작 가능 |
| P2       | ImageLog 실패를 삼키고 거래 진행          | 감사로그 유실 감지 어려움 |

## 결론

현재 `preHandle()`의 실제 책임은 다음과 같습니다.

```text
ServicePreventionInterceptor.preHandle
  = 시스템 선처리 로그
  + GUID 확정
  + 공통헤더 보완
  + 요청 전문 기록
  + ImageLog INSERT
```

그러나 이름에서 기대되는 거래 차단 기능은 아직 없습니다.

현재 구조에서 가장 먼저 보완할 사항은 다음입니다.

1. 요청 전문의 개인정보 마스킹과 길이 제한
2. multipart 인증·ImageLog 우회 제거
3. JWT `ssoId`를 신뢰 가능한 사용자 ID로 연결
4. 통제용 IP와 전문 입력 IP 분리
5. Context 없는 요청의 fail-open 정책 재검토
6. 동일 GUID 이력 덮어쓰기 정책 변경

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
