# pdmg-ui는 JWT를 pdmg-service로 보내고 시스템 선처리에서 검증하는가

## 결론

| 질문 | 답 |
|------|----|
| pdmg-ui 전문 테스트가 JWT를 pdmg-service로 보내는가? | **아니오** (현재) |
| 시스템 선처리(`ServicePreventionInterceptor`)가 JWT를 검증하는가? | **아니오** |
| 누가 검증하는가? | **`DefaultFilter` + `JwtProvider`** (그리고 **local이면 검증 생략**) |

---

## 1. pdmg-ui → pdmg-service (전문 테스트)

브라우저 직접 호출:

- `online-single.js` / `service-client.js`
- `POST {targetBaseUrl}/{serviceId}` (예: `http://localhost:8080/mgcoa5530S0`)

`service-client.js`의 fetch 헤더는 대략 다음과 같다.

```text
Content-Type: application/json;charset=UTF-8
Accept: application/json
```

**`Authorization: Bearer …` 를 붙이지 않는다.**  
JWT 로그인으로 받은 `accessToken`은 JWT 관리 화면(sessionStorage)용이며, 전문 테스트 호출에 자동 연결되지 않는다.

---

## 2. pdmg-ui → pdmg-jwt (JWT 화면)

`jwt-admin.js`는 pdmg-jwt(`:8110`) `POST /online` 을 직접 호출한다.

- 로그인/갱신 등으로 토큰 **발급·관리**
- 이 토큰을 pdmg-service 전문 호출에 **전달하는 코드는 없음**

---

## 3. 서버 쪽 검증 위치

```text
DefaultFilter          ← JWT 검증 (non-local만)  ★여기
  → ServicePreventionInterceptor  ← 시스템 선처리 (GUID·전문로그·ImageLog)
       → 업무 처리
```

- **시스템 선처리** = Interceptor → JWT 검증 안 함
- **Filter** = JWT 검증 (또는 local 생략)

현재 `spring.profiles.active=local` 이면 Filter가 Bearer를 요구하지 않으므로, UI가 토큰을 안 보내도 전문 호출이 된다.

---

## 4. 앞으로 전문 테스트에 토큰을 붙이려면

1. JWT 로그인 세션의 `accessToken`을 읽는다
2. `service-client.js` / `online-single.js` fetch에  
   `Authorization: Bearer ${accessToken}` 추가
3. pdmg-service를 **non-local**로 기동하고, 발급 토큰과 `JwtProvider` 검증 방식을 맞춘다  
   (RS256 JWKS vs HS256 정합 — [42번 문서](./42.토큰을%20생성해서%20pdmg-service로%20요청시%20전달하는%20방법.md) §4)
