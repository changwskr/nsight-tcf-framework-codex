# TCF OFF 아키텍처 텍스트 다이어그램

설정:

```yaml
nhnis:
  fw:
    tcf:
      enabled: false
```

## 2. TCF OFF에서 비활성화되는 컴포넌트

```text
nhnis.fw.tcf.enabled=false
             │
             ▼
┌─────────────────────────────────────────┐
│ 생성·실행되지 않는 TCF 컴포넌트         │
│                                         │
│ X OnlineTransactionController           │
│ X TcfFacade                             │
│ X TransactionDispatcher                 │
│ X STF                                   │
│ X ETF                                   │
│ X TransactionHandler 기반 라우팅        │
└─────────────────────────────────────────┘
```

따라서 다음 경로는 사용할 수 없습니다.

```text
POST /online
   │
   ▼
OnlineTransactionController 없음
   │
   ▼
TCF 거래 실행 불가
```

대신 업무 URL을 직접 호출합니다.

```text
POST /mgcoa5530S0
POST /mgcoa8888S0
POST /mgcoa9000C0
POST /mgcoa9000U0
POST /mgcoa9000D0
```

## 3. TCF ON/OFF 비교

```text
TCF ON

POST /online
   │
   ▼
OnlineTransactionController
   │
   ▼
TcfFacade
   │
   ├─ STF
   ▼
TransactionDispatcher
   │
   ▼
TransactionHandler
   │
   ▼
Business Facade
   │
   ▼
Service → DAO → DB
   │
   ▼
ETF
```

```text
TCF OFF

POST /{Service ID}
   │
   ▼
업무 Controller
   │
   ▼
Business Facade
   │
   ▼
Service → DAO → DB
```

## 4. URL과 Service ID 처리

### TCF ON

```text
HTTP URL
└─ POST /online

Service ID 위치
└─ hdr_nhnis.sys_comm.rms_svc_c
   └─ mgcoa5530S0
```

### TCF OFF

```text
HTTP URL
└─ POST /mgcoa5530S0

Controller 매핑
└─ @PostMapping("/mgcoa5530S0")

Controller 메서드
└─ mgcoa5530S0(...)
```

TCF OFF에서도 표준 Header의 Service ID를 URL과 동일하게 유지하는 것이 좋습니다.

```text
URL
/ mgcoa5530S0

rms_svc_c
  mgcoa5530S0

두 값이 동일해야 함
```

## 5. 권장 Controller 호출 구조

```text
업무 Controller
      │
      ▼
Business Facade
      │
      ├─ @Transactional
      ▼
Business Service
      │
      ▼
Rule → DAO → Mapper → DB
```

예:

```java
@Slf4j
@RestController
@RequiredArgsConstructor
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "false",
    matchIfMissing = true
)
public class mgcoa5530Controller {

    private final mgcoa5530Facade facade;

    @PostMapping("/mgcoa5530S0")
    public mgcoa5530S0DTOout mgcoa5530S0(
            @Valid @RequestBody mgcoa5530S0DTOin input
    ) throws Exception {
        return facade.mgcoa5530S0(input);
    }
}
```

## 6. 현재 호환 Controller 구조

현재 일부 Controller는 Facade가 아니라 Service를 직접 호출합니다.

```text
업무 Controller
      │
      ▼
Business Service
      │
      ▼
DAO → Mapper → DB
```

예:

```java
@PostMapping("/mgcoa5530S0")
public mgcoa5530S0DTOout mgcoa5530S0(
        @RequestBody mgcoa5530S0DTOin input
) throws Throwable {
    return mgcoa5530Service.mgcoa5530S0(input);
}
```

이 구조의 문제:

```text
Controller → Service 직접 호출
      │
      ├─ Facade 우회
      ├─ Facade @Transactional 우회
      ├─ TCF ON/OFF 트랜잭션 경계 불일치
      └─ DTO 변환·유스케이스 조정 경계 불일치
```

따라서 권장 변경은 다음과 같습니다.

```text
변경 전

Controller
   → Service
      → DAO


변경 후

Controller
   → Facade(@Transactional)
      → Service
         → DAO
```

## 7. TCF OFF 트랜잭션

### Facade를 호출하는 경우

```text
Controller
   │
   ▼
Facade Proxy
   │
   ├════════════ TX BEGIN ════════════╗
   ║                                 ║
   ║ BizPre                          ║
   ║   → Service                     ║
   ║     → DAO                       ║
   ║       → DB                      ║
   ║   → BizPost                     ║
   ║                                 ║
   ║ 정상: COMMIT                    ║
   ║ 예외: ROLLBACK                  ║
   ╚═════════════════════════════════╝
```

### Service를 직접 호출하는 경우

```text
Controller
   │
   ▼
Service
   │
   ▼
DAO
   │
   ▼
DB
```

Facade를 지나지 않으므로 `rdwTransactionManager` 기반 업무 트랜잭션이 시작되지 않을 수 있습니다.

## 8. Controller에 트랜잭션을 붙이는 방식

기술적으로 가능합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
@PostMapping("/mgcoa5530S0")
public mgcoa5530S0DTOout mgcoa5530S0(
        @RequestBody mgcoa5530S0DTOin input
) throws Throwable {
    return service.mgcoa5530S0(input);
}
```

실행 범위:

```text
Controller Proxy
   │
   ├──────────── TX BEGIN
   ▼
Controller
   │
   ├─ 요청 처리
   ├─ Service
   ├─ DAO / DB
   ├─ 응답 DTO 생성
   └─ Controller 반환
   │
   ├─ 정상: COMMIT
   └─ 예외: ROLLBACK
```

하지만 HTTP 계층과 트랜잭션이 결합되므로 Facade 적용이 더 적절합니다.

## 9. 업무 선후처리

현재 `BizPrePostAspect`가 Service 메서드를 대상으로 한다면:

```text
Controller
   │
   ▼
Facade TX BEGIN
   │
   ▼
BizPrePostAspect
   │
   ├─ BizPre
   ▼
Service
   │
   ▼
DAO / DB
   │
   ▼
BizPrePostAspect
   │
   ├─ BizPost
   ▼
Facade
   │
   └─ COMMIT / ROLLBACK
```

따라서 TCF OFF에서도 Controller가 Facade를 호출하면 업무 선후처리와 본 업무를 동일 트랜잭션으로 묶을 수 있습니다.

## 10. 시스템 선후처리 변화

```text
TCF ON

DefaultFilter
   → Interceptor
   → STF
   → 업무 처리
   → ETF
   → Context 정리
```

```text
TCF OFF

DefaultFilter
   → Interceptor
   → 업무 Controller
   → 업무 처리
   → Context 정리
```

TCF OFF에서는 다음 처리가 빠집니다.

```text
X STF 시스템 선처리
X ETF 시스템 후처리
X TCF TransactionContext
X ETF 경과시간 확인
X TCF Handler 라우팅 로그
```

Filter와 Interceptor가 활성화되어 있다면 다음 기능은 유지될 수 있습니다.

```text
O JWT 검증
O GUID 생성
O ServiceContext 생성
O HTTP 요청 로깅
O 거래 통제
O 입력 전문 공통 처리
O Context 정리
```

## 11. 타임아웃

TCF OFF에서는 ETF를 거치지 않습니다.

```text
TCF ON
업무 처리 → ETF → 경과시간 확인

TCF OFF
업무 처리 → Controller 응답
              │
              └─ ETF 타임아웃 확인 없음
```

TCF OFF에서도 작업 취소와 롤백이 필요하다면 Facade 내부에 타임아웃 실행 경계를 둬야 합니다.

```text
Controller
   │
   ▼
Facade TX BEGIN
   │
   ▼
TimeoutExecutor
   │
   ▼
Service → DAO
   │
   ├─ 제한시간 이내
   │      └─ COMMIT
   │
   └─ 제한시간 초과
          ├─ 작업 취소
          ├─ OnlineTimeoutException
          └─ ROLLBACK
```

## 12. 예외처리

```text
Controller
   │
   ▼
Facade → Service → DAO
   │
   │ 예외 발생
   ▼
Facade ROLLBACK
   │
   ▼
GlobalExceptionHandler
   │
   ├─ 예외 분류
   ├─ exceptionCode.yml 조회
   ├─ 표준 오류 코드 생성
   └─ HTTP 상태 결정
   │
   ▼
HTTP 4xx / 5xx 응답
```

TCF가 꺼져도 `GlobalExceptionHandler`의 생성 조건이 TCF 활성화에 묶여 있다면 함께 비활성화될 수 있으므로 설정 조건을 분리해야 합니다.

권장 조건:

```text
TCF enabled
└─ TCF Controller·STF·Dispatcher·ETF만 제어

공통 예외 처리
└─ TCF ON/OFF와 관계없이 항상 활성화
```

## 13. 최종 권장 구조

```text
HTTP POST /{Service ID}
          │
          ▼
DefaultFilter
          │
          ├─ JWT 검증
          └─ ServiceContext 생성
          │
          ▼
ServicePreventionInterceptor
          │
          └─ 거래 통제
          │
          ▼
업무 Controller
          │
          └─ HTTP 입출력만 담당
          │
          ▼
Business Facade
          │
          ├════════════ TX BEGIN ════════════╗
          ║                                 ║
          ║ BizPre                          ║
          ║   → Business Service            ║
          ║     → Rule                      ║
          ║       → DAO                     ║
          ║         → Mapper / DB           ║
          ║   → BizPost                     ║
          ║                                 ║
          ║ COMMIT / ROLLBACK               ║
          ╚═════════════════════════════════╝
          │
          ▼
GlobalExceptionHandler 또는 정상 응답
          │
          ▼
ServiceContext / MDC 정리
          │
          ▼
HTTP 응답
```

핵심 차이는 다음과 같습니다.

```text
TCF ON
  → 공통 /online
  → Service ID로 Handler 자동 라우팅
  → STF·ETF 실행

TCF OFF
  → 업무별 URL
  → 업무별 Controller 직접 진입
  → STF·ETF·Dispatcher 미실행
  → Controller가 Facade를 호출해야 TX 구조 유지
```
