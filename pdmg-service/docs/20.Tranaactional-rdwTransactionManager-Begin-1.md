## 20. `@Transactional` · `rdwTransactionManager` · BEGIN 분석

먼저 파일명의 `Tranaactional`은 오타이고 정확한 표기는 다음입니다.

```java
@Transactional
```

현재 PDMG에서 DB 트랜잭션은 `rdwTransactionManager`가 관리합니다. 다만 실제 BEGIN 위치는 실행 설정에 따라 달라집니다.

```text
TCF ON + timeout ON
→ Timeout Executor의 TransactionTemplate에서 BEGIN

TCF ON + timeout OFF
→ Business Facade의 @Transactional에서 BEGIN

TCF OFF 현재 구조
→ Controller가 Service 직접 호출
→ BEGIN 없음
```

# 3. rdwTransactionManager

트랜잭션 매니저 Bean:

```java
@Bean
@Primary
public PlatformTransactionManager
        rdwTransactionManager(
            DataSource rdwDataSource) {

    return new DataSourceTransactionManager(
            rdwDataSource);
}
```

구현체:

```text
PlatformTransactionManager
  └─ DataSourceTransactionManager
```

Bean 이름은 메서드 이름에 따라 다음이 됩니다.

```text
rdwTransactionManager
```

Facade와 Timeout Executor 모두 이 Bean을 명시적으로 사용합니다.

```java

    transactionManager =
        "rdwTransactionManager"

```

# 4. MyBatis와 동일한 DataSource

MyBatis 구성도 같은 `rdwDataSource`를 사용합니다.

```java
factory.setDataSource(rdwDataSource);
```

그리고 DAO는 다음 SqlSessionTemplate을 사용합니다.

```java
@Bean
public SqlSessionTemplate
        rdwSqlSessionTemplate(
            SqlSessionFactory factory) {

    return new SqlSessionTemplate(factory);
}
```

따라서:

```text
rdwTransactionManager가 관리하는 Connection
               =
MyBatis DAO가 사용하는 Connection
```

Spring 트랜잭션이 활성화되어 있으면 MyBatis의 여러 SQL이 같은 Connection에 참여합니다.

# 5. JDBC에서 BEGIN의 실제 의미

JDBC에서는 애플리케이션이 항상 다음 SQL을 직접 실행하는 것은 아닙니다.

```sql
BEGIN;
```

`DataSourceTransactionManager`는 보통 다음과 같이 동작합니다.

```text
1. HikariDataSource에서 Connection 획득
2. Connection을 현재 스레드에 바인딩
3. autoCommit이 true이면 false로 변경
4. isolation/readOnly 등 속성 적용
5. DAO가 같은 Connection 사용
6. 정상 종료 시 connection.commit()
7. 실패 시 connection.rollback()
8. autoCommit 복원
9. Connection을 Pool에 반환
```

개념적으로는 다음 코드와 유사합니다.

```java
Connection connection =
        dataSource.getConnection();

connection.setAutoCommit(false);

try {
    // MyBatis SQL 실행
    connection.commit();
} catch (Exception e) {
    connection.rollback();
    throw e;
} finally {
    connection.setAutoCommit(true);
    connection.close();
}
```

따라서 로그에 문자 그대로 `BEGIN` SQL이 보이지 않아도 트랜잭션이 시작될 수 있습니다.

Oracle과 일부 DB에서는 첫 SQL 실행 시 실제 DB 트랜잭션이 시작되는 것으로 볼 수 있습니다.

# 6. 현재 설정: timeout ON

현재 설정:

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    timeout:
      enabled: true
      milliseconds: 5000
```

실제 트랜잭션 흐름:

```text

  ↓
OnlineTransactionController
  ↓
TcfFacade
  ↓
DefaultOnlineTimeoutExecutor
  ↓
worker thread
  ↓
TransactionTemplate.execute()
  ↓
rdwTransactionManager.getTransaction()
  ↓

  ↓
autoCommit(false)                       ★ BEGIN
  ↓
Dispatcher
  ↓
Handler
  ↓
Business Facade 프록시
  ↓
@Transactional(REQUIRED)                ★ 기존 TX 참여
  ↓
Service
  ↓
DAO / SQL
  ↓

  ↓
```

# 7. Facade의 REQUIRED 참여

Facade 선언:

```java
@Transactional(
    transactionManager =
        "rdwTransactionManager",
    rollbackFor = Exception.class
)
public Output execute(Object dtoBody) {
}
```

`propagation`을 생략하면 기본값은 다음입니다.

```text
PROPAGATION_REQUIRED
```

의미:

```text
기존 TX 있음
→ 기존 TX 참여

기존 TX 없음
→ 새 TX 시작
```

timeout ON에서는 worker의 TransactionTemplate가 이미 TX를 시작했습니다.

따라서:

```text
TransactionTemplate TX
  ↓
Facade @Transactional(REQUIRED)
  ↓
새 Connection을 열지 않음
  ↓
같은 Connection·같은 TX에 참여
```

Facade 종료 시 바로 commit하지 않고 외부 TransactionTemplate 종료까지 기다립니다.

# 8. timeout ON의 정확한 COMMIT 위치

다음 흐름에 주의해야 합니다.

```text
Facade 정상 반환
  ↓
아직 COMMIT 아님
  ↓
Handler 정상 반환
  ↓
Dispatcher 정상 반환
  ↓
Executor가 deadline·interrupt 재검사
  ↓
정상일 때만 외부 TransactionTemplate 종료
  ↓
COMMIT
```

이 구조가 필요한 이유는 Facade가 반환된 직후 제한시간 초과가 확인되면 DB 작업을 rollback하기 위해서입니다.

```text
Facade가 자체 COMMIT
→ 이후 timeout 발견
→ 이미 commit되어 rollback 불가능
```

현재 외부 트랜잭션은 이 문제를 피하기 위한 구조입니다.

# 10. RuntimeException

Service 또는 DAO에서 RuntimeException이 발생하면:

```text
RuntimeException
  ↓
Facade 밖으로 전달
  ↓
TransactionTemplate catch
  ↓
status.setRollbackOnly()
  ↓
rdwTransactionManager.rollback()
```

예:

```text
첫 번째 INSERT 성공
두 번째 UPDATE에서 MyBatis 예외
→ 두 SQL 모두 rollback
```

# 11. checked Exception

쓰기 Facade에는 다음 설정이 있습니다.

```java
rollbackFor = Exception.class
```

따라서 checked Exception도 rollback 대상입니다.

timeout ON에서는 외부 Executor도 모든 `Exception`을 잡아 rollback-only로 표시합니다.

```java
catch (Exception ex) {
    status.setRollbackOnly();
    throw new OnlineTimeoutExecutionException(ex);
}
```

따라서 현재 timeout ON에서는:

```text
RuntimeException → rollback
checked Exception → rollback
timeout Exception → rollback
overload 관련 실행 예외 → 실행 전 또는 rollback
```

# 12. 타임아웃 발생

요청 스레드는 다음 코드로 최대 5초 대기합니다.

```java
future.get(
    properties.getMilliseconds(),
    TimeUnit.MILLISECONDS
);
```

5초 초과:

```text
요청 스레드
  ↓
TimeoutException
  ↓
future.cancel(true)
  ↓
worker에 interrupt 요청
  ↓
OnlineTimeoutException
  ↓
HTTP 504
```

worker가 interrupt를 인식하면:

```text
status.setRollbackOnly()
→ TransactionTemplate 종료
→ rollback
```

하지만 `cancel(true)`는 강제 스레드 종료가 아니라 interrupt 요청입니다.

업무 코드가 interrupt를 무시하면:

```text
HTTP는 504 반환
worker는 계속 실행 가능
TX와 Connection도 계속 점유 가능
```

작업이 최종 반환되면 Executor가 deadline을 재검사하여 rollback하지만, 영원히 반환하지 않거나 DB 호출이 interrupt에 반응하지 않으면 즉시 rollback된다는 보장은 없습니다.

# 13. timeout 설정과 DB TX timeout 차이

현재 설정:

```yaml
milliseconds: 5000
```

이 값은 다음에 사용됩니다.

```text
Future.get(5000ms)
worker deadline 검사
```

하지만 TransactionTemplate에는 Spring 트랜잭션 timeout이 설정되지 않았습니다.

없는 설정:

```java
transactionTemplate.setTimeout(5);
```

따라서 현재 5초는:

```text
온라인 응답 대기 제한
```

이지, 완전한 JDBC/DB statement timeout은 아닙니다.

안전한 타임아웃은 보통 세 층이 필요합니다.

```text
Online timeout       5초
Transaction timeout  5초 또는 조금 짧게
DB query timeout     4초 등
```

현재는 Online timeout 중심이며 DB query timeout과의 결합을 추가 점검해야 합니다.

# 15. 조회 readOnly

조회 Facade:

```java
@Transactional(
    transactionManager =
        "rdwTransactionManager",
    readOnly = true
)
```

적용 거래:

```text
S0 조회 거래
```

### timeout OFF

Facade가 새 TX를 시작하므로 `readOnly=true`가 트랜잭션 속성에 적용됩니다.

```text
Facade 프록시
→ 새 TX readOnly=true
```

### timeout ON

외부 TransactionTemplate가 이미 기본 쓰기 TX를 시작했습니다.

```text
외부 TX readOnly=false
  ↓
Facade readOnly=true
  ↓
REQUIRED로 기존 TX 참여
```

참여하는 내부 Facade가 외부 TX 속성을 바꾸지 않으므로 실제 트랜잭션은 readOnly가 아닐 가능성이 높습니다.

따라서 현재 timeout ON에서는 조회 Facade의 `readOnly=true` 선언이 실제 외부 TX에 반영되지 않습니다.

# 16. 업무 선후처리의 TX 포함 여부

`BizPrePostAspect`는 Service 메서드를 감쌉니다.

```text
Facade / 외부 TX
  ↓
업무 선처리
  ↓
Service
  ↓
DAO
  ↓
업무 후처리
  ↓
TX 종료
```

따라서 업무 선처리 또는 후처리에서 같은 RDW DataSource로 INSERT/UPDATE하면 동일 트랜잭션에 참여합니다.

예:

```text
업무 본처리 UPDATE
→ 업무 후처리 INSERT
→ 이후 예외
→ UPDATE와 INSERT 모두 rollback
```

시스템 선후처리의 ImageLog는 업무 TX 밖에서 실행됩니다.

# 17. ImageLog 트랜잭션

시스템 선처리:

```text
ServicePreventionInterceptor.preHandle
  ↓
ImageLogHandler.preImagelog
  ↓
JdbcTemplate INSERT
```

이 시점에는 업무 worker TX가 아직 없습니다.

```text
요청 스레드 ImageLog INSERT
≠ worker thread 업무 TX
```

ImageLogHandler 자체에도 `@Transactional`이 없습니다. 따라서 일반적으로 별도 Connection의 auto-commit 처리입니다.

결과:

```text
업무 성공 → ImageLog 유지
업무 rollback → ImageLog 유지
업무 timeout → ImageLog 유지
```

감사로그 관점에서는 의도에 맞는 분리입니다.

# 18. TCF OFF

설정:

```yaml
nhnis:
  fw:
    tcf:
      enabled: false
```

현재 업무별 Controller는 Facade가 아닌 Service를 직접 호출합니다.

```text
업무 Controller
  ↓
Service
  ↓
DAO
```

이 경로에는 다음이 없습니다.

```text
TransactionTemplate
Business Facade @Transactional
```

따라서 현재 TCF OFF에서는 업무 BEGIN이 없습니다.

여러 SQL이 실행되면 전체 원자성이 보장되지 않습니다.

TCF OFF에서도 트랜잭션을 사용하려면:

```text
업무 Controller
  ↓
Business Facade @Transactional
  ↓
Service
  ↓
DAO
```

로 변경해야 합니다.

# 19. TX-FLOW 로그와 실제 BEGIN

`PdmgBizTxFlowAspect`는 Handler, Facade, Service, DAO의 시작·종료 로그를 출력합니다.

```java
@Order(50)
@Around("bizFlow()")
```

하지만 이 로그는 실제 TransactionManager 로그가 아닙니다.

특히 timeout OFF에서 Advisor 순서는 일반적으로 다음처럼 될 수 있습니다.

```text
PdmgBizTxFlowAspect Facade 시작 로그
  ↓
TransactionInterceptor
  ↓
실제 BEGIN
  ↓
Facade 본문
  ↓
실제 COMMIT
  ↓
PdmgBizTxFlowAspect Facade 종료 로그
```

따라서:

```text
[Facade 시작]
```

로그가 찍힌 바로 그 줄에서 DB BEGIN이 발생했다고 단정하면 안 됩니다.

실제 트랜잭션 확인은 다음을 이용해야 합니다.

```text
DataSourceTransactionManager DEBUG/TRACE 로그
TransactionSynchronizationManager 상태
JDBC Connection autoCommit 상태
rollback 통합 테스트
```

# 20. self-invocation

Spring `@Transactional`은 프록시를 통과해야 적용됩니다.

정상:

```text
Handler Bean
→ Facade Spring Proxy
→ TransactionInterceptor
→ Facade 실제 객체
```

문제:

```java
public void outer() {
    this.inner();
}

@Transactional
public void inner() {
}
```

`this.inner()`는 프록시를 통하지 않기 때문에 `inner()`의 별도 트랜잭션 설정이 적용되지 않습니다.

현재 Facade에는 self-invocation이 없으므로 문제는 없습니다.

# 21. 문서에서 수정할 부분

현재 문서 앞부분은 timeout ON/OFF를 올바르게 구분합니다.

하지만 마지막 요약은 다음처럼 되어 있습니다.

```text
BEGIN = Business Facade @Transactional 진입 시
끝    = Facade 반환 COMMIT
```

이 설명은 timeout OFF에서만 정확합니다.

현재 timeout ON 기준으로는 다음이 맞습니다.

```text
BEGIN = worker의 TransactionTemplate 진입
Facade = REQUIRED로 기존 TX 참여
COMMIT = Handler/Dispatcher 종료 후 deadline 검사 통과 시
ROLLBACK = 예외·deadline·interrupt 감지 시
```

또한 다음 표현도 수정하는 것이 좋습니다.

```text
DB 트랜잭션 BEGIN 주체:
rdwTransactionManager @ Facade
```

현행 기준:

```text
timeout ON:
  rdwTransactionManager @ TransactionTemplate

timeout OFF:
  rdwTransactionManager @ Facade 프록시
```

# 22. 현재 점검 결과

| 우선순위 | 항목                                                | 판단                                 |
| -------- | --------------------------------------------------- | ------------------------------------ |
| 정상     | TransactionManager와 MyBatis가 동일 DataSource 사용 | TX 참여 정상                         |
| 정상     | Facade가 TM 이름 명시                               | 다중 DS에 안전                       |
| 정상     | 쓰기 `rollbackFor=Exception`                        | checked 예외 대응                    |
| 정상     | timeout ON에서 deadline 후 commit 결정              | rollback 목표에 적합                 |
| P0       | TCF OFF에서 Facade 우회                             | 업무 TX 없음                         |
| P0       | interrupt 무시 작업은 즉시 취소·rollback 불확실     | DB timeout 병행 필요                 |
| P1       | TransactionTemplate 자체 timeout 미설정             | Connection 장기 점유 가능            |
| P1       | timeout ON 조회 TX가 readOnly가 아님                | 정책 전달 필요                       |
| P1       | 문서 마지막 요약이 Facade BEGIN으로 단정            | 현행과 불일치                        |
| P2       | TX-FLOW 로그가 실제 BEGIN 로그처럼 오해될 수 있음   | TM 로그 분리 필요                    |
| 테스트   | Executor 단위 rollback 테스트는 존재                | 실제 MyBatis 통합 rollback 보강 필요 |

## 결론

현재 PDMG에서 `rdwTransactionManager`는 정상적으로 RDW DataSource와 MyBatis SQL을 같은 트랜잭션으로 묶습니다.

실제 BEGIN 위치는 설정별로 다음과 같습니다.

```text
TCF ON + timeout ON
  TransactionTemplate BEGIN
    → Handler
    → Facade REQUIRED 참여
    → Service/DAO
  → deadline 검사
  → commit/rollback

TCF ON + timeout OFF
  Handler
    → Facade @Transactional BEGIN
    → Service/DAO
  → commit/rollback

TCF OFF 현재 구현
  Controller → Service
  → BEGIN 없음
```

운영 전 핵심 보완 항목은 다음입니다.

1. TCF OFF Controller를 Facade 경유로 변경
2. TransactionTemplate에 거래별 readOnly 정책 전달
3. Online timeout과 TX/DB query timeout 병행
4. 실제 MyBatis INSERT 두 건을 이용한 commit/rollback 통합 테스트
5. 문서 요약을 timeout ON/OFF 기준으로 수정

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
