## 19. Business Facade 분석 결과

Business Facade는 Handler와 Service 사이에서 다음 역할을 담당합니다.

```text
요청 dto를 입력 DTO로 변환
+ 업무 Service 호출
+ 트랜잭션 선언
```

현재 호출 구조:

```text
Business Handler
  ↓
Business Facade                      ★ 현재 위치
  ├─ Object dtoBody → DTOin 변환
  ├─ @Transactional 선언
  └─ Service 호출
  ↓
Business Service
  ↓
DAO / MyBatis
```

다만 현재 timeout이 활성화되어 있기 때문에 “Facade가 항상 실제 트랜잭션을 시작한다”는 설명은 정확하지 않습니다. 현재 설정에서는 Timeout Executor가 먼저 트랜잭션을 시작하고 Facade는 그 트랜잭션에 참여합니다.

---

# 1. 현재 Facade 구성

패키지:

```text
nhnis.mg.co.a.application.facade
```

현재 4개 Facade가 있습니다.

| Facade            | 거래                         |
| ----------------- | ---------------------------- |
| `mgcoa5530Facade` | `mgcoa5530S0`                |
| `mgcoa8888Facade` | `mgcoa8888S0`, `mgcoa8888D0` |
| `mgcoa9999Facade` | `mgcoa9999S0`                |
| `mgcoa9000Facade` | `mgcoa9000S0/C0/U0/D0`       |

모든 Facade는 `@Service` Bean입니다.

```java
@Service
public class mgcoa9000Facade {
}
```

여기서 `@Service`는 Spring Bean 종류를 나타낼 뿐이며, 아키텍처 계층은 Facade입니다.

---

# 2. Facade 역할

Facade가 하는 일:

```text
dtoBody null 처리
Object/Map → DTOin 변환
트랜잭션 속성 선언
업무 Service 호출
DTOout 반환
```

Facade가 하지 않는 일:

```text
serviceId 라우팅
SQL 작성
DAO 직접 호출
응답 hdr_nhnis 조립
ImageLog 처리
긴 업무 흐름·업무 규칙
```

한 줄로 표현하면:

```text
Business Facade = 입력 바인딩 + 유스케이스 진입 + TX 선언
```

# 3. 표준 구현

[mgcoa8888Facade.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/application/facade/mgcoa8888Facade.java:22>)

```java
@Service
public class mgcoa8888Facade {

    private final mgcoa8888Service service;
    private final ObjectMapper objectMapper;

    public mgcoa8888Facade(

            ObjectMapper objectMapper) {

        this.service = service;
        this.objectMapper = objectMapper;
    }

    @Transactional(
        transactionManager = "rdwTransactionManager",
        readOnly = true
    )

```

생성자 주입을 사용하고 있으며 Facade가 DAO를 직접 주입하지 않는 점은 적절합니다.

# 4. 요청 DTO 변환

Controller가 전체 전문에서 `dto`만 추출합니다.

```json
{
  "hdr_nhnis": {},
  "dto": {
    "guid": "1234"
  }
}
```

Handler는 `dto` 내용을 `Object`로 전달합니다.

```java
facade.mgcoa8888S0(dtoBody);
```

Facade에서 실제 입력 DTO로 변환합니다.

```java
private <T> T convert(
        Object dtoBody,
        Class<T> type) {

    Object source = dtoBody == null
            ? Collections.emptyMap()
            : dtoBody;

    return objectMapper.convertValue(
            source,
            type);
}
```

결과:

```text
Map/Object
  ↓ ObjectMapper.convertValue
mgcoa8888S0DTOin
  ↓
Service
```

## 5. dto가 없을 때

`dtoBody == null`이면 오류를 발생시키지 않고 빈 Map으로 변환합니다.

```java
Object source = dtoBody == null
        ? Collections.emptyMap()
        : dtoBody;
```

따라서:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000D0"
    }
  }
}
```

처럼 `dto`가 없어도 빈 DTO가 생성됩니다.

```text
dto 없음
→ emptyMap
→ mgcoa9000D0DTOin 생성
→ Service 호출
```

조회 거래는 모든 조건이 선택사항이면 허용할 수 있습니다. 하지만 등록·수정·삭제는 필수 입력 누락을 명시적으로 검사해야 합니다.

현재 Facade에는 Bean Validation이나 필수 필드 검증이 없습니다.

---

# 6. 조회 트랜잭션 선언

조회 거래는 다음 형식을 사용합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
```

적용 거래:

```text
mgcoa5530S0
mgcoa8888S0
mgcoa9999S0
mgcoa9000S0
```

의도:

```text
읽기 전용 트랜잭션
→ 불필요한 쓰기 방지 의도
→ JDBC/ORM 최적화 힌트
```

단, `readOnly=true`는 DB가 모든 쓰기를 반드시 차단하는 절대적인 보안 장치가 아니라 Spring/JDBC에 전달되는 트랜잭션 속성입니다.

---

# 7. 쓰기 트랜잭션 선언

등록·수정·삭제는 다음 형식을 사용합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

적용 거래:

```text
mgcoa8888D0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
```

`rollbackFor=Exception.class`를 사용하므로 RuntimeException뿐 아니라 checked Exception도 rollback 대상입니다.

예:

```text
INSERT 성공
→ 후속 UPDATE에서 checked Exception
→ 전체 rollback
```

Facade에서 예외를 잡아 정상 반환으로 바꾸면 rollback되지 않을 수 있으므로 예외는 상위로 전달해야 합니다.

# 8. TransactionManager

Facade가 지정하는 TransactionManager:

```java
transactionManager =
        "rdwTransactionManager"
```

Bean 정의: [RdwDataSourceConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/RdwDataSourceConfig.java:60>)

```java

@Primary

        rdwTransactionManager(
            DataSource rdwDataSource) {

    return new DataSourceTransactionManager(

```

같은 RDW DataSource로 다음이 연결됩니다.

```text
rdwDataSource
  ├─ rdwTransactionManager
  ├─ rdwSqlSessionFactory
  ├─ rdwSqlSessionTemplate
  └─ MyBatis DAO
```

따라서 Facade 트랜잭션과 DAO SQL이 같은 DataSource를 사용합니다.

# 9. timeout ON에서 실제 트랜잭션

현재 설정:

```yaml
nhnis:
  fw:
    timeout:
      enabled: true
```

실제 실행 순서:

```text
HTTP 요청 스레드
  ↓
TcfFacade
  ↓
DefaultOnlineTimeoutExecutor
  ↓
worker thread
  ↓
TransactionTemplate BEGIN                ★ 실제 최초 시작
  ↓
Dispatcher
  ↓
Handler
  ↓
Business Facade 프록시
  ↓
@Transactional(REQUIRED)                 ★ 기존 TX 참여
  ↓
Service
  ↓
DAO
  ↓
deadline 확인
  ↓
COMMIT / ROLLBACK
```

`@Transactional`의 기본 propagation은 `REQUIRED`입니다.

따라서 이미 `TransactionTemplate` 트랜잭션이 있으면 새 트랜잭션을 만들지 않고 참여합니다.

정확한 표현:

```text
Facade는 트랜잭션 속성을 선언한다.
timeout ON에서는 Executor가 실제 외부 TX를 시작한다.
Facade는 외부 TX에 참여한다.
```

---

# 10. timeout ON에서 readOnly 문제

`DefaultOnlineTimeoutExecutor`는 다음과 같이 TransactionTemplate을 만듭니다.

```java
this.transactionTemplate =
        new TransactionTemplate(
            transactionManager);

this.transactionTemplate
        .setPropagationBehavior(
            PROPAGATION_REQUIRED);
```

그런데 다음 설정은 하지 않습니다.

```java
transactionTemplate.setReadOnly(true);
```

따라서 외부 트랜잭션은 기본 쓰기 가능 트랜잭션입니다.

그 상태에서 조회 Facade가 호출됩니다.

```java
@Transactional(readOnly = true)
```

그러나 Facade는 기존 트랜잭션에 참여하므로 내부 선언이 외부 트랜잭션의 readOnly 속성을 다시 정의하지 않습니다.

현재 timeout ON 조회 흐름:

```text
TransactionTemplate
  readOnly=false
  ↓
조회 Facade
  readOnly=true 선언
  ↓
기존 TX 참여
  ↓
실제 외부 TX는 readOnly=false
```

즉, 현재 설정에서는 조회 Facade의 `readOnly=true` 효과가 제대로 적용되지 않을 가능성이 높습니다.

문서의 다음 표현은 timeout OFF일 때만 정확합니다.

```text
Handler → Facade 프록시 → BEGIN
```

timeout ON에서는 다음으로 현행화해야 합니다.

```text
Timeout Executor → BEGIN
→ Handler → Facade 기존 TX 참여
```

---

# 11. readOnly를 정확히 적용하려면

외부 TransactionTemplate이 거래 유형을 알아야 합니다.

예:

```text
S 거래 → TransactionTemplate readOnly=true
C/U/D 거래 → readOnly=false
```

단순한 방법:

```java
boolean readOnly =
        serviceId.endsWith("S0");

TransactionTemplate template =
        new TransactionTemplate(
            transactionManager);

template.setReadOnly(readOnly);
```

하지만 serviceId 접미사만으로 판단하기보다 Handler 또는 서비스 카탈로그가 트랜잭션 속성을 제공하는 구조가 안전합니다.

예:

```java
public record TransactionPolicy(
    boolean readOnly,
    int timeoutSeconds
) {
}
```

```text
serviceId
→ TransactionPolicy 조회
→ TransactionTemplate 설정
→ Handler 실행
```

---

# 12. timeout ON에서 rollbackFor

외부 `TransactionTemplate`은 checked Exception도 다음 코드에서 rollback-only 처리합니다.

```java
catch (Exception ex) {
    status.setRollbackOnly();
    throw new OnlineTimeoutExecutionException(ex);
}
```

따라서 timeout ON에서는 Facade의 `rollbackFor=Exception.class`가 없어도 외부 Executor가 checked Exception을 rollback 처리합니다.

그렇다고 Facade의 `rollbackFor`가 불필요한 것은 아닙니다.

```text
timeout ON:
  외부 TransactionTemplate가 checked Exception rollback 보장

timeout OFF:
  Facade가 TX 시작
  rollbackFor=Exception.class가 필요

TCF OFF를 Facade 경유로 개선한 경우:
  Facade rollbackFor 필요
```

Facade에 rollback 정책을 선언해 두는 현재 방식은 실행 모드가 바뀌어도 안전합니다.

# 14. TCF OFF 문제

```yaml
nhnis:
  fw:
    tcf:
      enabled: false
```

현재 업무별 Controller는 Facade를 호출하지 않고 Service를 직접 호출합니다.

```text
업무 Controller
  ↓
Service
  ↓
DAO
```

따라서 Business Facade의 `@Transactional`이 전혀 적용되지 않습니다.

현재 모드별 차이:

| 모드                 | 트랜잭션                       |
| -------------------- | ------------------------------ |
| TCF ON + timeout ON  | Executor 외부 TX + Facade 참여 |
| TCF ON + timeout OFF | Facade가 TX 시작               |
| TCF OFF 현재 구현    | Facade 우회 → TX 없음          |

TCF OFF도 지원하려면 업무별 Controller를 다음처럼 변경해야 합니다.

```text
Controller → Business Facade → Service → DAO
```

# 15. 업무 선후처리와 Facade TX

`BizPrePostAspect` 포인트컷은 Service입니다.

```java
execution(
    public *
    nhnis.mg.co.a.application.service..*(..)
)
```

따라서 정상 흐름은:

```text
Facade TX 안
  ↓
업무 선처리
  ↓
Service
  ↓
DAO
  ↓
업무 후처리
  ↓
Facade 종료
```

timeout ON에서도 외부 트랜잭션이 더 넓게 감싸고 있으므로 업무 선처리와 후처리는 트랜잭션 안입니다.

```text
TransactionTemplate BEGIN
  ↓
Handler
  ↓
Facade 참여
  ↓
업무 선처리
  ↓
Service / DAO
  ↓
업무 후처리
  ↓
deadline 확인
  ↓
COMMIT
```

업무 후처리에서 같은 DataSource로 UPDATE하면 같은 트랜잭션에 포함됩니다.

# 16. DTO 변환도 트랜잭션 안인가?

### timeout ON

외부 TX가 Handler 전에 시작되므로 다음 전체가 TX 안입니다.

```text
Handler 분기
Facade DTO 변환
업무 선처리
Service
DAO
업무 후처리
```

### timeout OFF

Facade 프록시가 메서드 진입 전에 TX를 시작하므로 DTO 변환도 TX 안입니다.

```text
Facade 프록시 BEGIN
→ ObjectMapper.convertValue
→ Service
```

DTO 변환은 DB 자원을 사용하지 않으므로 트랜잭션 시작 전에 수행하는 것이 조금 더 효율적일 수 있습니다. 다만 현재 구조는 단순하며 변환 비용이 작다면 큰 문제는 아닙니다.

# 17. 입력 검증 부족

현재 Facade는 타입 변환만 하고 유효성 검사를 하지 않습니다.

```text
Object → DTOin
→ 바로 Service 호출
```

없는 항목:

```text
Bean Validator
필수 필드 검사
길이 검사
코드값 검사
C/U/D dto 필수 검사
```

권장 방식:

```java
public Output create(
        @Valid InputDTO input)
```

또는 Facade에서 `Validator`를 사용하되, 업무 규칙은 Service 또는 Rule 계층에 둡니다.

구분:

```text
Facade:
  필수값·형식 검증

Service/Rule:
  업무 상태·업무 가능 여부 검증
```

# 18. Object 기반 인터페이스

현재 Facade 메서드는 다음 형태입니다.

```java
public mgcoa9000C0DTOout mgcoa9000C0(
        Object dtoBody)
```

장점:

- 공통 Controller/Handler에서 Map을 그대로 전달 가능
- Handler 코드가 단순함

단점:

- 컴파일 시 입력 타입 검증 불가능
- 변환 오류가 실행 시점에 발생
- IDE 리팩터링 지원 약화
- TCF OFF Controller가 이미 DTO를 갖고 있어도 다시 변환해야 함

더 명확한 구조는 Handler가 변환 책임을 전담하는 별도 Binder를 사용하고 Facade는 타입 DTO를 받는 방식입니다.

```java
mgcoa9000C0DTOin input =
        requestBinder.bind(
            dtoBody,
            mgcoa9000C0DTOin.class);

return facade.mgcoa9000C0(input);
```

Facade:

```java
@Transactional(...)
public mgcoa9000C0DTOout mgcoa9000C0(
        mgcoa9000C0DTOin input) {

    return service.mgcoa9000C0(input);
}
```

다만 현재 문서와 아키텍처는 Facade 변환 방식을 표준으로 정하고 있으므로 변경한다면 전체 Handler/Facade 계약을 함께 바꿔야 합니다.

# 19. 예외 처리와 rollback

정상적인 쓰기 Facade:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
public Output execute(Object dtoBody)
        throws Exception {

    Input input =
            objectMapper.convertValue(
                dtoBody,
                Input.class);

    return service.execute(input);
}
```

다음 예외는 rollback됩니다.

```text
ObjectMapper 변환 RuntimeException
업무 BizException
DAO RuntimeException
MyBatis 예외
checked Exception
timeout deadline 초과
worker interrupt 확인
```

주의해야 할 구현:

```java
try {
    service.execute(input);
} catch (Exception e) {
    log.error(...);
    return new Output();          // 예외를 정상 반환으로 변경
}
```

이 경우 TransactionManager는 정상 종료로 판단하여 commit할 수 있습니다.

예외를 잡아야 한다면 다시 던지거나 rollback-only를 명시해야 합니다.

# 20. self-invocation 주의

같은 Facade 안에서 다른 `@Transactional` 메서드를 직접 호출하면 Spring 프록시를 거치지 않습니다.

```java
public void outer() {
    this.inner();       // inner의 별도 TX 속성 미적용
}

@Transactional
public void inner() {
}
```

현재 Facade에는 이런 호출이 없으므로 문제는 없습니다. 향후 복합 유스케이스를 추가할 때 주의해야 합니다.

| 우선순위 | 항목                                                          | 판단                      |
| -------- | ------------------------------------------------------------- | ------------------------- |
| 정상     | Facade가 Service만 호출                                       | 계층 책임 준수            |
| 정상     | rdwTransactionManager 명시                                    | MyBatis DataSource와 일치 |
| 정상     | 조회/쓰기 어노테이션 구분                                     | 선언은 적절               |
| 정상     | 쓰기 `rollbackFor=Exception`                                  | timeout OFF에도 안전      |
| P0       | TCF OFF Controller가 Facade를 우회                            | 트랜잭션 없음             |
| P1       | timeout ON에서 조회 `readOnly=true`가 외부 TX에 반영되지 않음 | 정책 전달 필요            |
| P1       | C/U/D에서도 dto null을 빈 DTO로 허용                          | 필수 입력 검증 필요       |
| P1       | Bean Validation 없음                                          | 잘못된 입력 실행 가능     |
| P1       | Facade를 실제 TX 시작점으로 설명한 문서                       | timeout ON 흐름과 불일치  |
| P2       | Object 기반 입력 계약                                         | 타입 안정성 부족          |
| P2       | 각 Facade의 변환 코드 반복                                    | 공통 Binder 고려          |
| 테스트   | Facade 트랜잭션 통합 테스트 검색 안 됨                        | commit/rollback 검증 필요 |

## 결론

현재 Business Facade의 책임 분리는 적절합니다.

```text
Handler          serviceId 라우팅
Business Facade  DTO 변환 + TX 선언
Service          업무 흐름
DAO              DB 접근
```

그러나 실제 트랜잭션 시작 위치는 모드별로 다릅니다.

```text
TCF ON + timeout ON
→ Timeout Executor가 TX 시작
→ Facade 참여

TCF ON + timeout OFF
→ Facade가 TX 시작

TCF OFF 현재 구현
→ Facade 우회
→ TX 없음
```

운영 전에 우선 보완해야 할 사항은 다음입니다.

1. TCF OFF Controller도 Facade 호출
2. timeout ON 외부 TransactionTemplate에 readOnly 정책 전달
3. C/U/D 거래의 dto·필수 필드 검증
4. commit·RuntimeException·checked Exception·timeout rollback 통합 테스트
5. 문서의 “Facade가 항상 BEGIN” 표현을 실행 모드별로 수정

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
