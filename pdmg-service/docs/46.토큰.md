## jwt 토큰 발급시 키는 무엇을 가지고 사용하는가 ?

**RSA 개인키(비대칭)** 로 서명합니다. 공유 `jwt.secret`(HS256)이 아닙니다.

| 항목          | 내용                                                       |
| ------------- | ---------------------------------------------------------- |
| 알고리즘      | **RS256**                                                  |
| 키            | 기동 시 `JwtKeyConfiguration`이 **RSA 2048** 키쌍 **생성** |
| kid           | `nsight-jwt-rs256`                                         |
| 서명          | `RSAPrivateKey` + `RSASSASigner`                           |
| 검증용 공개키 | `/.well-known/jwks.json` 로 공개                           |

즉 발급 = **서버 메모리의 RSA Private Key**.  
재기동하면 키가 새로 만들어지므로, 예전 Access는 JWKS가 바뀌면 검증에 실패할 수 있습니다.

개인키는 어디에 있는가 ?
**파일/DB에는 없습니다.** 기동 시 메모리에만 만들어집니다.

`JwtKeyConfiguration.jwtSigningKey()`가 RSA 2048 키쌍을 생성하고, `RSAPrivateKey` 빈으로 Spring 컨텍스트에 올립니다.

| 구분        | 위치                                                                    |
| ----------- | ----------------------------------------------------------------------- |
| Private Key | 프로세스 **힙 메모리** (재기동 시 소멸·재생성)                          |
| Public Key  | 동일 키쌍의 공개키 → JWKS `http://127.0.0.1:8110/.well-known/jwks.json` |

디스크의 `*.pem` / keystore 경로는 현재 없습니다.

## 개인키는 어떤 모듈에서 어떤 시점에 생성하는가 ?

**모듈:** `pdmg-jwt`  
**클래스:** `nhnis.mg.jw.a.config.JwtKeyConfiguration`  
**메서드/빈:** `@Bean jwtSigningKey()` → RSA 2048 생성

**시점:** pdmg-jwt 애플리케이션 **기동 시** Spring이 해당 `@Bean`을 만들 때(컨텍스트 초기화). 로그인 요청마다 만들지 않습니다.

이후 `JwtTokenIssuer`가 같은 프로세스의 `RSAPrivateKey` 빈으로 Access Token에 서명합니다.

## 이후 사용자가 로그인하면 토큰을 만든다. 그럼 이때 토큰은 어떤 원리로 만드는가 ?

맞습니다. **서버 공통 RSA 개인키 1개**로 서명하고, 사용자마다 키를 만들지 않습니다.

### 로그인 후 Access Token 만드는 원리

1. **로그인 성공** (`mgjwa1000C0`) → `issueTokenPair`
2. **Claims(내용) 구성** — 사용자·만료 정보만 담음
   - `sub` / `userId`, `iss`, `aud`, `jti`, `iat`, `exp`, `type=ACCESS` 등
3. **JWT 조립**
   - Header: `alg=RS256`, `kid=nsight-jwt-rs256`
   - Payload: 위 claims
   - Signature: `RSASSASigner(서버 RSA 개인키)`로 Header+Payload 서명
4. **문자열로 직렬화** → `eyJ...header.eyJ...payload.서명` = **Access Token**
5. **Refresh Token**은 JWT가 아니라 **임의 문자열**을 만들어 DB에 해시 저장 (서명 키와 별개)

### 한 줄로

> 사용자마다 다른 것은 **토큰 안의 claims**이고,  
> **서명에 쓰는 키는 pdmg-jwt 기동 때 만든 공용 RSA 개인키 하나**입니다.

검증 쪽(pdmg-service)은 JWKS의 **같은 kid 공개키**로 서명이 그 서버가 만든 것인지 확인합니다.

## RSA 개인키는 KMS을 통해서 받을 수 잇나 ?

**가능합니다.** 다만 **현재 pdmg-jwt는 KMS를 쓰지 않습니다.** 기동 시 로컬에서 RSA를 생성합니다.

### KMS로 바꾸는 일반적인 방식

| 방식                                      | 설명                                                                         |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| KMS에서 키 보관 + 서명 API                | 개인키를 앱으로 안 빼고, KMS에 “이 바이트 서명해줘” 요청                     |
| KMS/키볼트에서 개인키 export(또는 unwrap) | 기동 시 키를 받아 `RSAPrivateKey`로 주입 (보안 정책에 따라 비권장일 수 있음) |

AWS KMS, Azure Key Vault, GCP KMS, HashiCorp Vault 등이 이런 용도입니다.

### 지금 코드와의 차이

- 지금: `JwtKeyConfiguration`에서 `RSAKeyGenerator(2048).generate()`
- KMS 도입 시: 그 생성을 없애고, KMS 클라이언트/`JwtTokenIssuer` 서명부를 KMS 연동으로 교체

원하시면 pdmg-jwt에 **설정으로 KMS/로컬 키를 고르는 구조**로 설계안을 잡아 드리겠습니다.
