## 2. Service 계층의 위치

```text
HTTP / TCF
    │
    ▼
Controller 또는 Handler
    │
    ▼
Facade
    │
    ▼
┌──────────────────────────────┐
│ Business Service             │
│                              │
│ 업무 유스케이스의 처리 절차  │
└──────────────┬───────────────┘
               │
       ┌───────┼──────────┐
       │       │          │
       ▼       ▼          ▼
     Rule     DAO       Client
               │          │
               ▼          ▼
              DB       외부 시스템
```

Service는 HTTP 진입점도 아니고 SQL 계층도 아닙니다.

```text
Controller / Handler
└─ 어떻게 업무에 진입하는가?

Facade
└─ 어떤 트랜잭션으로 업무를 실행하는가?

Service
└─ 어떤 순서로 업무를 처리하는가?

Rule
└─ 어떤 업무 규칙을 적용하는가?

DAO
└─ 어떤 데이터를 읽고 변경하는가?
```

## 8. Service와 트랜잭션

권장 구조에서는 Service에 `@Transactional`을 선언하지 않고 Facade에 둡니다.

```text
Facade Proxy
   │
   ├══════════════════ TX BEGIN ══════════════════╗
   ║                                              ║
   ║ BizPre                                       ║
   ║    │                                         ║
   ║    ▼                                         ║
   ║ Service                                      ║
   ║    ├─ DAO SELECT                             ║
   ║    ├─ DAO INSERT                             ║
   ║    ├─ DAO UPDATE                             ║
   ║    └─ DAO DELETE                             ║
   ║    │                                         ║
   ║ BizPost                                      ║
   ║                                              ║
   ├════════ 정상 COMMIT / 예외 ROLLBACK ═════════╝
```

이유:

```text
Facade
 ├─ 업무 유스케이스 전체 경계
 ├─ 여러 Service를 하나의 TX로 조정 가능
 ├─ 업무 선후처리를 TX에 포함 가능
 └─ TCF ON/OFF 트랜잭션 구조 통일

Service
 ├─ 순수한 업무 처리 흐름에 집중
 ├─ 트랜잭션 기술 의존 감소
 └─ 다른 Facade에서 재사용 가능
```

## 9. 여러 Service를 하나의 트랜잭션으로 실행

```text
Business Facade
      │
      ├────────── TX BEGIN
      │
      ├─ customerService.updateCustomer()
      │      └─ 고객 데이터 UPDATE
      │
      ├─ historyService.insertHistory()
      │      └─ 업무 이력 INSERT
      │
      └─ notificationService.createRequest()
             └─ 알림 요청 INSERT
      │
      ├─ 전체 정상
      │      └─ COMMIT
      │
      └─ 하나라도 예외
             └─ 전체 ROLLBACK
```

## 10. ServiceContext 활용

```text
DefaultFilter
   │
   └─ ServiceContextHolder 설정
   │
   ▼
Service
   │
   ▼
ServiceContextHolder.getInstance()
   │
   ├─ getGuid()
   ├─ getHeader()
   ├─ 사용자 ID
   ├─ 영업점 ID
   ├─ 채널 ID
   └─ 요청 정보
```

개념적인 사용:

```java
ServiceContext context = ServiceContextHolder.getInstance();

String guid = context.getGuid();
hdr_nhnis header = context.getHeader();
```

활용 예:

```text
ServiceContext
   │
   ├─ 등록자 ID 설정
   ├─ 수정자 ID 설정
   ├─ 거래 영업점 설정
   ├─ 감사 로그 GUID 설정
   └─ 외부 연계 추적 ID 설정
```

Service가 HTTP Request를 직접 참조하기보다 `ServiceContext`를 사용하는 것이 적절합니다.

## 11. Rule 호출

```text
Service
   │
   ├─ 처리 순서 제어
   │
   ▼
Rule
   │
   ├─ 입력 검증
   ├─ 업무 상태 검증
   ├─ 권한·조건 판정
   ├─ 금액·한도 계산
   └─ 정책 결정
   │
   ▼
Service
   │
   └─ Rule 결과에 따라 DAO 호출
```

구분:

```text
Service
└─ 검증하고 조회하고 변경하는 순서

Rule
└─ 무엇이 유효하고 어떤 결과가 맞는지 결정
```

## 12. DAO 호출

```text
Service
   │
   ├─ DTO 또는 파라미터 객체 구성
   │
   ▼
DAO
   │
   ├─ Mapper Statement 선택
   └─ SQL 파라미터 전달
   │
   ▼
MyBatis Mapper XML
   │
   ├─ SELECT
   ├─ INSERT
   ├─ UPDATE
   └─ DELETE
   │
   ▼
업무 DB
```

Service에서 직접 SQL Session이나 JDBC Connection을 사용하면 안 됩니다.

```text
잘못된 구조

Service
   └─ JdbcTemplate / SqlSession 직접 호출


권장 구조

Service
   └─ DAO
       └─ Mapper
           └─ DB
```

## 13. 외부 시스템 호출

```text
Service
   │
   ▼
Client 계층
   │
   ├─ 외부 요청 전문 생성
   ├─ 인증 Header 설정
   ├─ 타임아웃 적용
   ├─ tcf-eai 또는 HTTP Client 호출
   └─ 외부 오류를 내부 예외로 변환
   │
   ▼
외부 시스템
```

DB 트랜잭션 안에서 장시간 외부 호출을 수행하면 커넥션을 오래 점유할 수 있습니다.

```text
TX BEGIN
  → DB 조회
  → 외부 시스템 장시간 호출
  → DB 수정
  → COMMIT
```

필요하면 외부 호출과 DB 트랜잭션의 순서를 유스케이스 특성에 맞게 분리해야 합니다.

## 14. Service 예외 처리

```text
Service
   │
   ├─ 입력 오류
   ├─ 데이터 없음
   ├─ 중복 데이터
   ├─ 상태 변경 불가
   ├─ DAO 오류
   └─ 외부 연계 오류
   │
   ▼
업무 예외 발생
   │
   ▼
BizPrePostAspect
   │
   ├─ 오류 후처리
   └─ 예외 재전파
   │
   ▼
Facade
   │
   └─ ROLLBACK
   │
   ▼
GlobalExceptionHandler
   │
   └─ 표준 오류 응답
```

Service에서 예외를 숨기지 않아야 합니다.

```java
// 피해야 하는 구조
try {
    dao.update(input);
} catch (Exception e) {
    log.error("오류", e);
    return output;
}
```

권장 구조:

```java
try {
    dao.update(input);
} catch (Exception e) {
    log.error("업무 데이터 수정 실패", e);
    throw e;
}
```

## 16. Service가 담당하지 않는 영역

```text
Business Service
   │
   ├─ X HTTP URL 매핑
   ├─ X HttpServletRequest 직접 처리
   ├─ X JWT 직접 검증
   ├─ X TCF Service ID 등록
   ├─ X 트랜잭션 경계 선언
   ├─ X SQL 문자열 작성
   ├─ X HTTP 응답 Status 결정
   └─ X 표준 오류 전문 직접 생성
```

해당 책임의 위치:

```text
HTTP URL             → Controller
JWT 검증             → pdmg-fw DefaultFilter
Service ID 등록      → TransactionHandler
트랜잭션 경계        → Business Facade
업무 규칙            → Rule
SQL                  → Mapper XML
HTTP 오류 응답       → GlobalExceptionHandler
```
