## 20. 타임아웃 분석 결과

현재 PDMG 타임아웃은 다음과 같이 동작합니다.

```text
HTTP 요청 Thread
  → TcfFacade
    → OnlineTimeoutExecutor
      → timeoutMs = resolveMilliseconds(serviceId)
      → Worker Pool에 업무 제출
      → Future.get(timeoutMs) 대기
          ├─ 제한시간 안에 완료 → 정상 응답
          ├─ 제한시간 초과 → cancel(true) → HTTP 504
          └─ Pool 포화 → HTTP 503

Worker Thread
  → TransactionTemplate로 TX 시작
    → Dispatcher
      → Handler
        → Facade
          → 업무 선처리
          → Service
          → 업무 후처리
    → 정상 완료 + 제한시간 이내 → COMMIT
    → 예외/인터럽트/기한 초과 → ROLLBACK
```

제한시간은 **기본 `milliseconds`(5000)** 이고, `overrides.<serviceId>`가 있으면 그 값을 씁니다.  
예: `mgcoa5530S0 → 10000`.

결론부터 말하면:

> 현재 구조는 `작업 취소 요청 + 트랜잭션 롤백`을 구현하고 있습니다.  
> 다만 Java의 `future.cancel(true)`는 작업을 강제로 죽이는 기능이 아니므로, 업무 코드가 인터럽트를 무시하면 Worker는 계속 실행될 수 있습니다.

## 1. 적용 중인 환경설정

현재 [`application.yml`](../src/main/resources/application.yml) 설정은 다음과 같습니다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true

    timeout:
      enabled: true
      milliseconds: 5000
      overrides:
        mgcoa5530S0: 10000
      pool-size: 20
      queue-capacity: 100
```

각 설정 의미는 다음과 같습니다.

| 설정 | 현재값 | 의미 |
| --- | ---: | --- |
| `enabled` | `true` | Worker 기반 타임아웃 활성화 |
| `milliseconds` | `5000` | 기본 제한시간(미등록 serviceId) |
| `overrides.mgcoa5530S0` | `10000` | 해당 거래만 10초 |
| `pool-size` | `20` | 동시에 실행할 수 있는 Worker 최대 20개 |
| `queue-capacity` | `100` | 실행 대기 가능한 요청 최대 100개 |

Pool 20개와 Queue 100개가 모두 차면 새로운 요청은 즉시 거절됩니다.

제한시간 결정은 [`OnlineTimeoutProperties.resolveMilliseconds(serviceId)`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutProperties.java)입니다.

```text
1. overrides 에 serviceId 가 있으면 → 해당 ms
2. 없으면 → milliseconds
```

`serviceId`는 Worker 제출 전 스냅샷의 `rms_svc_c`(없으면 MDC `serviceId`)입니다.  
`Future.get`·Deadline·`OnlineTimeoutException.timeoutMs`·로그의 `timeoutMs`에 **같은 값**이 들어갑니다.

주의할 점은 적용된 제한시간에 다음 시간이 모두 포함된다는 것입니다.

```text
Queue 대기시간
+ 트랜잭션 시작시간
+ Dispatcher/Handler 처리
+ Facade/Service/DAO 처리
```

따라서 기본 5초 거래에서 Queue에서 3초를 기다렸다면 실제 업무 처리에 남는 시간은 약 2초입니다.  
`mgcoa5530S0`처럼 override 10초면 같은 Queue 3초 대기 후 업무 여유는 약 7초입니다.

## 2. 타임아웃 활성화 조건

[`OnlineTimeoutConfiguration.java`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutConfiguration.java)가 설정값에 따라 실행기를 선택합니다.

### `enabled=true`

```java
@Bean
@ConditionalOnProperty(
    name = "nhnis.fw.timeout.enabled",
    havingValue = "true"
)
public OnlineTimeoutExecutor defaultOnlineTimeoutExecutor(...) {
    return new DefaultOnlineTimeoutExecutor(
        properties,
        taskExecutor,
        transactionManager
    );
}
```

이때 `rdwTransactionManager`가 명시적으로 주입됩니다.

```java
@Qualifier("rdwTransactionManager")
PlatformTransactionManager transactionManager
```

따라서 Worker마다 RDW 데이터소스 트랜잭션이 시작됩니다.

### `enabled=false` 또는 설정 생략

```java
return new SyncOnlineTimeoutExecutor();
```

[`SyncOnlineTimeoutExecutor.java`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/SyncOnlineTimeoutExecutor.java)는 단순히 현재 HTTP Thread에서 실행합니다.

```java
return action.call();
```

이 경우:

- Worker Pool을 사용하지 않습니다.
- `Future.get()` 제한시간이 없습니다.
- Executor가 트랜잭션을 시작하지 않습니다.
- 업무 Facade의 `@Transactional`이 트랜잭션을 시작합니다.

## 3. 정상 처리 시 트랜잭션

핵심 구현은 [`DefaultOnlineTimeoutExecutor.java`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/DefaultOnlineTimeoutExecutor.java)입니다.

```java
return transactionTemplate.execute(status -> {
    T result = action.call();

    if (isDeadlineExceeded(deadlineNanos)
            || Thread.currentThread().isInterrupted()) {
        status.setRollbackOnly();
        throw new OnlineTimeoutException(...);
    }

    return result;
});
```

정상 처리 흐름은 다음과 같습니다.

```text
Worker 시작
→ TransactionTemplate BEGIN
→ Dispatcher
→ Handler
→ Facade
→ BizPrePostAspect
→ Service
→ DAO/SQL
→ 제한시간 재검사
→ COMMIT
```

업무가 제한시간 전에 반환됐더라도 커밋 직전에 다시 다음을 검사합니다.

```java
isDeadlineExceeded(deadlineNanos)
Thread.currentThread().isInterrupted()
```

따라서 요청 Thread가 타임아웃을 감지한 직후 Worker 업무가 반환되더라도, Worker가 인터럽트나 기한 초과를 확인하면 커밋하지 않고 롤백합니다.

## 4. 제한시간 초과 시 처리

요청 Thread에서는 다음처럼 **적용된 timeoutMs** 동안 기다립니다.

```java
long timeoutMs = properties.resolveMilliseconds(
    workerContext.getServiceId()
);

future.get(timeoutMs, TimeUnit.MILLISECONDS);
```

제한시간이 초과되면:

```java
boolean cancelled = future.cancel(true);
throw new OnlineTimeoutException(
    timeoutMs, elapsed, serviceId, guid
);
```

처리 결과는 다음과 같습니다.

```text
요청 Thread
  → Future 타임아웃
  → Worker에 interrupt 요청
  → OnlineTimeoutException
  → HTTP 504 응답

Worker Thread
  → InterruptedException 또는 interrupt 상태 인지
  → rollbackOnly 설정
  → ROLLBACK
```

[`GlobalExceptionHandler.java`](../../pdmg-fw/src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java)가 타임아웃을 HTTP 504로 변환합니다.

```java
return error(
    "FW_TIMEOUT",
    e.getMessage(),
    TYPE.COMMON,
    HttpStatus.GATEWAY_TIMEOUT,
    detail
);
```

Advice 적용 후 응답 개념은 다음과 같습니다. (`dto`가 아니라 **`result`**)

```json
{
  "hdr_nhnis": { "...": "..." },
  "result": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "온라인 거래 처리시간을 초과했습니다.",
    "errType": "COMMON"
  }
}
```

`addMsgContents` / 로그의 `timeoutMs`는 해당 거래에 적용된 값입니다.  
예: `mgcoa5530S0` → `timeoutMs=10000`.

메시지는 [`exceptionCode.yml`](../src/main/resources/exceptionCode.yml)에 정의되어 있습니다.

## 5. 현재 가장 중요한 문제

### 인터럽트를 잡고 업무를 계속함

현재 [`mgcoa5530Service.java`](../src/main/java/nhnis/mg/co/a/application/service/mgcoa5530Service.java)는 다음과 같습니다.

```java
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    log.warn("mgcoa5530S0 Service sleep interrupted", e);
}
```

인터럽트 상태는 복원하지만 예외를 다시 던지지 않고 이후 DAO 조회를 계속합니다.

```text
제한시간 초과 (mgcoa5530S0 이면 10초)
→ cancel(true)
→ sleep에서 InterruptedException 발생
→ catch에서 인터럽트만 복원
→ DAO 조회 계속 실행
→ Executor의 마지막 검사에서 롤백
```

최종적으로는 Executor가 인터럽트 상태를 확인해 롤백할 가능성이 높지만, 불필요한 DAO/SQL이 실행됩니다.

권장 방식은 즉시 예외를 다시 전달하는 것입니다.

```java
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    log.warn("mgcoa5530S0 Service sleep interrupted", e);
    throw e;
}
```

또는 업무 공통 예외로 변환하되 cause와 인터럽트 상태를 보존해야 합니다.

```java
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new IllegalStateException("업무 처리가 취소되었습니다.", e);
}
```

첫 번째 방식이 취소 의미를 가장 정확하게 전달합니다.

## 6. JDBC 작업은 즉시 중단되지 않을 수 있음

`future.cancel(true)`는 Worker Thread에 인터럽트를 설정할 뿐입니다.

다음 작업들은 즉시 중단되지 않을 수 있습니다.

- Oracle JDBC SQL 실행
- DB Lock 대기
- 원격 API 호출
- 인터럽트를 검사하지 않는 반복문
- 인터럽트 예외를 무시하는 업무 코드

예를 들어 SQL이 DB에서 30초 동안 실행되는데 적용 제한시간(기본 5초, override면 그 값) 후 타임아웃이 발생하면:

```text
T초: HTTP 504 반환
T초: Worker interrupt 요청
T~30초: JDBC가 계속 실행될 가능성
30초: SQL 반환
30초: Worker가 deadline 초과 확인
30초: ROLLBACK
```

즉, 클라이언트는 제한시간에 응답받지만 DB Connection과 Worker는 더 오래 점유될 수 있습니다.

보완하려면 Executor 타임아웃과 별도로 SQL 타임아웃이 필요합니다.

```yaml
mybatis:
  configuration:
    default-statement-timeout: 4
```

또는 Mapper별로 설정할 수 있습니다.

```xml
<select id="selectData"
        parameterType="map"
        resultType="map"
        timeout="4">
```

온라인 제한이 5초(또는 override 값)라면 SQL 제한은 일반적으로 그보다 짧아야 합니다.

## 7. 트랜잭션 롤백 범위

타임아웃 활성화 시 Worker의 `TransactionTemplate`이 가장 바깥 트랜잭션을 시작합니다.

```text
TransactionTemplate BEGIN
  Dispatcher
    Handler
      Facade @Transactional(REQUIRED)
        업무 선처리 Aspect
        Service
        업무 후처리 Aspect
TransactionTemplate COMMIT/ROLLBACK
```

따라서 다음 처리는 같은 트랜잭션입니다.

- Facade 처리
- 업무 선처리에서 수행한 DB 변경
- Service DB 변경
- 업무 후처리에서 수행한 DB 변경
- DAO/MyBatis SQL

단, 시스템 선후처리는 Worker 트랜잭션 밖입니다.

```text
Filter                         TX 밖
Interceptor.preHandle         TX 밖
시스템 ImageLog INSERT         TX 밖

Worker TransactionTemplate
  업무 처리                    TX 안

Interceptor.afterCompletion   TX 밖
ResponseBodyAdvice            TX 밖
```

따라서 업무가 타임아웃으로 롤백되어도 시스템 거래 로그는 별도로 남을 수 있습니다. 이는 실패 거래 추적 관점에서는 정상적인 설계입니다.

## 8. Pool 포화 처리

Pool 설정은 다음과 같습니다.

```java
executor.setCorePoolSize(20);
executor.setMaxPoolSize(20);
executor.setQueueCapacity(100);
executor.setRejectedExecutionHandler(
    new ThreadPoolExecutor.AbortPolicy()
);
```

최대 수용 개념은 다음과 같습니다.

```text
실행 중 20건
+ 대기 중 100건
= 최대 120건 수용
```

그 이상 들어오면 `OnlineOverloadException`이 발생하고 HTTP 503으로 반환됩니다.

```json
{
  "stdErrCode": "FW_OVERLOADED",
  "stdErrMsgCntn": "온라인 거래 처리 요청이 일시적으로 많습니다.",
  "errType": "COMMON"
}
```

다만 20은 DB Connection Pool 크기와 함께 검토해야 합니다.

예를 들어:

```text
Worker Pool = 20
DB Connection Pool = 10
```

이면 Worker 10개가 Connection을 기다리면서 타임아웃될 수 있습니다.

## 9. ServiceContext 전달 문제

[`OnlineTimeoutWorkerContext.java`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutWorkerContext.java)는 요청 Thread의 컨텍스트를 Worker로 전달합니다.

MDC는 복사합니다.

```java
Map<String, String> mdcCopy = new HashMap<>();
mdcCopy.putAll(ThreadContext.getContext());
```

하지만 `ServiceContext`는 복사하지 않고 같은 객체를 참조합니다.

```java
ServiceContext ctx = ServiceContextHolder.getInstance();

return new OnlineTimeoutWorkerContext(
    ctx,
    mdcCopy,
    guid,
    serviceId
);
```

주석에는 “Servlet request/response는 보관하지 않는다”고 되어 있지만 실제로는 기존 `ServiceContext` 객체 자체를 보관합니다. `ServiceContext`가 request/response를 가지고 있다면 Worker도 간접적으로 동일한 Servlet 객체를 참조합니다.

타임아웃 후에는:

```text
HTTP Thread → 오류 응답 처리
Worker Thread → 동일 ServiceContext로 업무 계속 가능
```

두 Thread가 같은 가변 객체를 동시에 사용할 수 있으므로 현행 구조의 중요한 위험입니다.

권장 구조는 다음 정보만 가진 불변 스냅샷입니다.

```text
guid
serviceId
header 복사본
userContext 복사본
MDC 복사본
```

`HttpServletRequest`, `HttpServletResponse`, 원본 `ServiceContext` 참조는 Worker에 전달하지 않는 것이 안전합니다.

## 10. 테스트 수준

[`DefaultOnlineTimeoutExecutorTest.java`](../../pdmg-fw/src/test/java/nhnis/fw/tcf/timeout/DefaultOnlineTimeoutExecutorTest.java) · [`OnlineTimeoutPropertiesTest.java`](../../pdmg-fw/src/test/java/nhnis/fw/tcf/timeout/OnlineTimeoutPropertiesTest.java)에는 다음 단위 테스트가 있습니다.

- 제한시간 내 정상 완료 및 커밋
- 타임아웃 예외
- 업무 RuntimeException 롤백
- 비활성 동기 실행
- Pool 포화
- 늦게 종료된 Worker의 rollbackOnly 검사
- **serviceId override 적용** (긴 제한으로 성공)
- **override 없는 serviceId는 기본 milliseconds**
- `resolveMilliseconds` / override 값 검증 실패

다만 실제 DB 기준 통합 테스트는 확인되지 않았습니다.

현재 테스트는 가짜 `RecordingTransactionManager`를 사용하므로 다음은 별도 검증이 필요합니다.

- 실제 H2/Oracle INSERT 후 타임아웃 롤백
- 업무 후처리 INSERT까지 함께 롤백되는지
- SQL 실행 중 타임아웃
- Worker가 인터럽트를 무시한 경우
- HTTP 504 응답 후 DB 커밋이 남지 않는지
- ServiceContext가 요청 종료 후 사용되지 않는지

## 11. UI Abort와의 관계

서버 Executor와 UI `pdmg.ui.timeout-ms`(브라우저 `AbortController`)는 **별개**입니다.

```text
권장: UI timeout-ms ≥ 서버 적용 최대값
      (기본 milliseconds 와 overrides 중 큰 값)
```

예: `mgcoa5530S0`이 10초면 UI는 15초 이상이 안전합니다.  
UI가 먼저 끊어도 서버 Worker는 cancel/Deadline까지 돌 수 있습니다.

## 12. 최종 평가

| 항목 | 평가 |
| --- | --- |
| 공통 기본 제한 (`milliseconds`) | 적용됨 (5000) |
| serviceId별 시간 (`overrides`) | **적용됨** (`resolveMilliseconds`) |
| 작업 취소 요청 | 적용됨, `cancel(true)` |
| Worker 트랜잭션 | 적용됨 |
| 타임아웃 시 롤백 | 적용됨 |
| 업무 선·후처리 포함 | 포함됨 |
| 시스템 선·후처리 포함 | 포함되지 않음 |
| Pool 포화 방어 | 적용됨 |
| 강제 작업 종료 | 보장되지 않음 |
| SQL 실행 제한 | 미적용 |
| 안전한 Context 복사 | 미흡 |
| 실제 DB 롤백 통합 테스트 | 보강 필요 |
| UI Abort와 서버 정렬 | 운영에서 최대 override보다 UI를 크게 |

가장 쉽게 요약하면 다음과 같습니다.

> 정상적인 업무 코드가 인터럽트를 즉시 전달하면, 적용된 제한시간(`milliseconds` 또는 `overrides`) 초과 시 작업 취소와 전체 업무 트랜잭션 롤백이 수행됩니다.  
> `mgcoa5530S0`은 override 10초로 동작합니다.  
> 하지만 현재 `mgcoa5530Service`처럼 인터럽트를 잡고 계속 진행하거나 JDBC가 인터럽트를 무시하면 HTTP 504 이후에도 Worker가 잠시 계속 실행될 수 있습니다. 최종 롤백 장치는 있지만, 즉시 중단까지 보장하려면 업무 인터럽트 전파와 SQL Statement Timeout을 함께 적용해야 합니다.

이번 분석에서는 검증 문서의 형식·문체를 유지한 채, `overrides` 반영과 관련 전제만 수정했습니다.
