## 1. 역할

한 HTTP 요청(온라인 거래 1건) 동안 살아 있는 **스레드 로컬 컨텍스트**다.  
헤더·GUID·요청/응답 전문 원문·서블릿 참조를 시스템 선후·Controller·TCF가 공유한다.

```text
DefaultFilter
  → new ServiceContext(…) + setRequestBody
  → ServiceContextHolder.setInstance(ctx)     ★ 생성
       │
       ├─ Interceptor.preHandle → header/GUID 보강, 요청 로그, ImageLog
       ├─ OnlineController → rms_svc_c / IP 보강, serviceId 해석
       ├─ TcfFacade → TransactionContext.fromCurrent (ServiceContext 참조)
       ├─ BizPrePost → GUID / rms_svc_c / BRC 로그
       ├─ Advice → hdr echo, setResponseBody
       └─ afterCompletion → postImagelog(responseBody)
  → Filter finally / 예외 after → removeInstance()   ★ 해제
```

| 한다 | 하지 않는다 |
|------|-------------|
| 요청 단위 `hdr_nhnis` 보관 | 업무 `*DTOin` 보관 (dto는 Body/Facade) |
| GUID · request/response 전문 원문 | DB TX / SqlSession |
| ThreadLocal로 계층 간 전달 | 요청 간 공유 (스레드 풀 누수 주의) |

`TransactionContext`(TCF)와 이름만 비슷하다.  
TCF Context는 serviceId·경과시간 + **이 ServiceContext 참조**를 담는 얇은 래퍼다 ([17](./17.TCF-TcfFace-Dispatcher.md)).

## 2. 타입 · Holder

### 2.1 `ServiceContext`

FQCN: `nhnis.fw.commons.context.ServiceContext` (`@Getter` + 일부 setter)

| 필드 | 의미 | 누가 채우나 |
|------|------|-------------|
| `applicationName` | 앱 이름 | Filter (`spring.application.name`) |
| `guid` | 거래 GUID | Filter(헤더) → Interceptor 강제 채번 가능 |
| `active` | 프로파일 (`local` 등) | Filter |
| `requestHeaders` | HTTP 헤더 스냅샷 | Filter |
| `httpServletRequest` | 요청 (캐시 래퍼 가능) | Filter |
| `httpServletResponse` | 응답 | Filter |
| `header` | `hdr_nhnis` | Filter 파싱/합성 → Interceptor/Controller 보강 |
| `userContext` | 확장 Map | (예약) |
| `requestBody` | 요청 전문 **원문 문자열** | Filter |
| `responseBody` | 응답 전문 **원문 문자열** | Advice `setResponseBody` |

생성자로는 header까지 넣고, `requestBody`/`responseBody`/`guid`/`header`는 이후 setter로 갱신한다.

### 2.2 `ServiceContextHolder`

```java
ThreadLocal<ServiceContext> INSTANCE;

setInstance(ctx)
getInstance()      // 없으면 null
removeInstance()   // 반드시 호출 — 스레드 재사용 누수 방지
```

비즈니스 코드에서 `ServiceContextHolder.getInstance()`로 읽는다.  
**새 스레드/비동기**로 넘기면 Holder는 비어 있다 (상속 안 함).

## 3. 생명주기

| 시점 | 동작 |
|------|------|
| **생성** | `DefaultFilter` — JSON 파싱 후 `setInstance` (+ `setRequestBody`) |
| **multipart** | 최소 header(GUID)만 담은 Context 생성 |
| **보강** | Interceptor `ensureGuid`/`enrichHeader…`, Controller `ensureRmsSvcC`/`enrichClientIp` |
| **응답 원문** | `ResponseBodyArgumentResolver` → `setResponseBody` |
| **ImageLog 후** | `afterCompletion` → `postImagelog(header, responseBody)` |
| **해제** | Filter `finally`에서 `removeInstance()` / 예외 after에서 remove 후 rethrow |

Filter가 `sendError`로 조기 반환하면 Context가 안 생기거나, 생긴 뒤에도 체인 미진입일 수 있다 → [11](./11.예외처리.md) · [13](./13.Filter-DefaultFilter.md).

요청 attribute `PDMG_REQUEST_BODY`는 Body 원문 복사본(Interceptor가 읽을 수 있음). Context의 `requestBody`와 同源.

## 4. 주요 소비처

| 소비자 | 용도 |
|--------|------|
| `ServicePreventionInterceptor` | header/GUID, 요청 로그, pre/post/exception ImageLog |
| `OnlineTransactionController` | `rms_svc_c` 우선 serviceId, 헤더·IP 보정 |
| `TransactionContext.fromCurrent` | TCF에 ServiceContext 전달 → `getHeader`/`getGuid` |
| `BizPrePostAspect` | GUID · `rms_svc_c` 선처리 로그 |
| `ResponseBodyArgumentResolver` | 응답 `hdr_nhnis` echo, `setResponseBody` |

업무 Service/DAO는 보통 DTO만 쓰고 Context에 의존하지 않는 것이 원칙이다.  
필요 시(조작자·점코드) header에서 읽되, **테스트·비동기**를 고려한다.

## 5. GUID · 헤더 · MDC

```text
Filter
  guid ← sys_comm.std_gbl_id (없으면 local 합성 등)
  ThreadContext(MDC): guid, ip, userId, serviceId
Interceptor
  GUID 공백 → UUID 채번 → ctx.setGuid + header + MDC
Controller
  rms_svc_c 비면 path serviceId로 보정
```

| 저장소 | 내용 |
|--------|------|
| `ServiceContext.guid` / `header.sys_comm.std_gbl_id` | 업무·ImageLog 키 |
| Log4j2 `ThreadContext` | 로그 패턴 `%X{guid}` 등 |
| ImageLog `GUID` 컬럼 | pre/post 동일 키 |

세 곳이 어긋나면 추적·ImageLog UPDATE 실패(WARN no row)가 난다.

## 6. `TransactionContext`와의 관계

```text
TcfFacade.process(serviceId, dto)
  TransactionContext ctx =
      TransactionContext.fromCurrent(serviceId)
        // serviceId + ServiceContextHolder.getInstance() + startedAt
```

| | ServiceContext | TransactionContext |
|--|----------------|-------------------|
| 범위 | Filter~응답 전체 | TcfFacade.process 구간 |
| 보관 | ThreadLocal | 메서드 인자로 Handler에 전달 |
| 내용 | HTTP·헤더·전문 원문 | serviceId + ServiceContext 참조 + 경과 |

Handler는 `context.getServiceId()`로 분기하고, 헤더가 필요하면 `context.getHeader()`.

---

## 7. 하지 말 것

1. `removeInstance` 누락 (스레드 풀에 이전 거래 Context 잔존)  
2. 자식 스레드에서 Holder만 읽고 Context null NPE  
3. Context에 대용량 업무 List를 쌓아 두기 (원문은 request/responseBody로 충분)  
4. ServiceContext를 DB 엔티티처럼 직렬화·세션에 저장  
5. Filter 없이 Controller만 호출하는 테스트에서 Holder null을 무시
