## 11. HTTP CORS 적용 분석 결과

[11.Http CORS적용.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/11.Http%20CORS적용.md>)는 현재 구현과 대부분 일치합니다.

브라우저가 `pdmg-ui:8090`에서 `pdmg-service:8080`으로 직접 요청하므로 CORS가 필요하고, OPTIONS 요청도 `DefaultFilter`에서 정상적으로 제외합니다.

다만 Filter 순서 때문에 인증·전문 오류 응답에는 CORS 헤더가 붙지 않을 수 있는 중요한 문제가 있습니다.

## 1. 현재 호출 구조

실제 UI는 Relay보다 브라우저 직접 호출을 사용합니다.

```text
브라우저
Origin: http://localhost:8090
  ↓ fetch
http://localhost:8080/mgcoa8888S0
  ↓
pdmg-service
```

[pdmg-ui service-client.js](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-ui/src/main/resources/static/_shared/service-client.js:36>)

```javascript
const response = await fetch(targetUrl, {
  method: "POST",
  headers: {
    "Content-Type": "application/json;charset=UTF-8",
    Accept: "application/json",
  },
  body: JSON.stringify(body),
});
```

다음 조건 때문에 브라우저는 일반적으로 사전 요청인 preflight를 보냅니다.

```text
다른 Origin
+ POST
+ Content-Type: application/json
```

실제 흐름:

```text
① OPTIONS /mgcoa8888S0
② POST /mgcoa8888S0
```

문서의 호출 전제는 정확합니다.

## 2. Origin 판단

Origin은 다음 세 가지 조합으로 결정됩니다.

```text
Protocol + Host + Port
```

따라서 다음 두 URL은 다른 Origin입니다.

```text
UI      http://localhost:8090
Service http://localhost:8080
```

또한 다음도 서로 다른 Origin입니다.

```text
http://localhost:8090
http://127.0.0.1:8090
```

현재 설정은 둘 다 허용합니다.

[application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml:10>)

```yaml
spring:
  mvc:
    cors:
      allowed-origins:
        - http://localhost:8090
        - http://127.0.0.1:8090
      allowed-methods:
        - GET
        - POST
        - OPTIONS
      allowed-headers:
        - "*"
```

로컬 개발 설정으로는 적절합니다.

## 3. CORS 설정 연결

### 설정 바인딩

[CorsProperties.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/CorsProperties.java:14>)

```java
@ConfigurationProperties("spring.mvc.cors")
public class CorsProperties {
    private List<String> allowedOrigins;
    private List<String> allowedMethods;
    private List<String> allowedHeaders;
}
```

`PdmgApplication`에 다음 설정이 있어 자동으로 등록됩니다.

```java
@ConfigurationPropertiesScan("nhnis")
```

연결 관계:

```text
application.yml
  spring.mvc.cors
       ↓
CorsProperties
       ↓
WebMvcConfig
```

### MVC CORS

[WebMvcConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/WebMvcConfig.java:29>)

```java
registry.addMapping("/**")
        .allowedOrigins(...)
        .allowedMethods(...)
        .allowedHeaders(...)
        .maxAge(3600);
```

거래 URL이 다음 형태이므로 `/**` 사용은 맞습니다.

```text
/mgcoa5530S0
/mgcoa8888S0
/mgcoa9000C0
```

`/api/**`만 등록하면 온라인 거래 URL은 허용되지 않습니다.

## 4. Spring Security CORS

[SecurityConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/SecurityConfig.java:28>)

```java
http.cors(Customizer.withDefaults())
```

`WebMvcConfig`가 제공하는 다음 Bean을 Spring Security가 사용합니다.

```java
@Bean
public CorsConfigurationSource corsConfigurationSource()
```

현재 CORS 설정은 두 경로에 같은 값으로 적용됩니다.

```text
WebMvc CORS mapping
Security CorsFilter
```

중복처럼 보이지만 현재 설정값이 동일하므로 충돌 가능성은 낮습니다. Spring Security를 사용하는 현재 구조에서는 `CorsConfigurationSource`가 특히 중요합니다.

## 5. pdmg-fw의 CORS 설정 충돌 여부

`pdmg-fw`에도 별도 Security/CORS 설정이 있습니다.

```java
@ConditionalOnProperty(
    name = "nhnis.fw.commons.security.enabled",
    havingValue = "true"
)
```

현재 `application.yml`에는 다음 설정이 없습니다.

```yaml
nhnis:
  fw:
    commons:
      security:
        enabled: true
```

따라서 `pdmg-fw`의 레거시 `SecurityConfig`는 비활성이고, `pdmg-service`의 `SecurityConfig`만 활성화됩니다.

현재는 CORS Bean 중복이 발생하지 않는 구조입니다.

레거시 설정을 실수로 활성화하면 다음 문제가 발생할 수 있습니다.

- `SecurityFilterChain` 복수 등록
- `CorsConfigurationSource` Bean 이름 충돌
- 모든 Origin 허용
- credentials 허용
- 서비스 설정과 FW 설정의 정책 불일치

따라서 현재 상태처럼 비활성으로 유지해야 합니다.

## 6. OPTIONS 처리

[DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java:73>)에 OPTIONS 제외가 구현되어 있습니다.

```java
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    return "OPTIONS".equalsIgnoreCase(request.getMethod());
}
```

따라서 preflight에는 다음 검사가 적용되지 않습니다.

- JWT 검사
- 요청 Body 검사
- JSON 파싱
- `hdr_nhnis` 검사
- ServiceContext 생성
- 전문 로깅
- 업무 처리

정상 흐름:

```text
OPTIONS
  ↓
DefaultFilter.shouldNotFilter() = true
  ↓
Spring Security CorsFilter
  ↓
CORS 응답
```

이 부분은 문서와 구현이 일치합니다.

## 7. 중요한 문제: 오류 응답의 CORS 헤더

DefaultFilter는 다음 순서로 등록됩니다.

[FilterConfiguration.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/configuration/FilterConfiguration.java:25>)

```java
registrationBean.setOrder(
    Ordered.HIGHEST_PRECEDENCE + 20
);
```

이 값은 Spring Security Filter보다 상당히 앞에서 실행될 가능성이 높습니다.

```text
POST 요청
  ↓
DefaultFilter
  ↓
Spring Security CorsFilter
  ↓
Controller
```

정상 요청은 DefaultFilter가 `filterChain.doFilter()`를 호출하므로 이후 Security CORS가 응답 헤더를 붙일 수 있습니다.

하지만 DefaultFilter에서 오류가 발생하면 다음처럼 즉시 종료됩니다.

```java
response.sendError(401, "Access Token이 없습니다.");
return;
```

대표적인 조기 종료:

- Access Token 없음: 401
- Token 검증 실패: 401
- Body 없음: 400
- 잘못된 JSON: 400
- 공통 헤더 없음: 400

이때 Security CorsFilter까지 요청이 진행되지 않을 수 있습니다.

```text
브라우저 POST
  ↓
DefaultFilter
  ↓ sendError(401)
요청 종료
  ✕ Security CorsFilter 미실행 가능
  ✕ Access-Control-Allow-Origin 없음
```

브라우저 화면에는 실제 401 메시지 대신 다음과 같이 보일 수 있습니다.

```text
CORS error
Failed to fetch
NetworkError
```

즉, 문서에 기술된 “응답에도 Allow-Origin 헤더가 붙는다”는 정상 처리에는 맞지만 Filter 조기 오류에는 보장되지 않습니다.

### 권장 방향

CORS 처리를 DefaultFilter보다 먼저 실행해야 합니다.

예를 들면 DefaultFilter 순서를 Spring Security 이후로 조정할 수 있습니다.

```java
registrationBean.setOrder(0);
```

단, 정확한 순서는 애플리케이션의 전체 Filter Chain을 확인해 결정해야 합니다.

또 다른 방법은 별도의 최우선 `CorsFilter`를 명시적으로 등록하는 것입니다.

```text
CorsFilter
  ↓
DefaultFilter
  ↓
Security
  ↓
MVC
```

이렇게 해야 성공과 실패 응답 모두 CORS 헤더를 가질 수 있습니다.

## 8. 인증과 CORS는 다른 기능

현재 Spring Security는 모든 요청을 허용합니다.

```java
.authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
```

실제 인증은 non-local 환경에서 `DefaultFilter`가 수행합니다.

```text
CORS
- 어느 브라우저 Origin이 응답을 읽을 수 있는가

JWT
- 요청한 사용자가 인증됐는가
```

CORS를 허용했다고 API 인증이 생기는 것은 아닙니다. 또한 CORS는 Postman, curl 또는 서버 프로그램의 호출을 차단하지 않습니다.

현재 보안 구조는 다음과 같습니다.

```text
브라우저 접근 통제 → CORS
API 사용자 인증    → DefaultFilter JWT
업무 접근 통제     → Interceptor/거래통제
```

## 9. credentials 동작

UI의 `fetch()`에는 다음 옵션이 없습니다.

```javascript
credentials: "include";
```

따라서 교차 Origin 쿠키·세션을 전달하지 않는 현재 구조에서는 `allowCredentials=true`가 필요하지 않습니다.

현재 `pdmg-service` CORS 설정도 credentials를 활성화하지 않습니다. 이는 무상태 JWT 방식과 맞습니다.

향후 브라우저에서 쿠키 기반 세션을 사용한다면 다음을 함께 변경해야 합니다.

```java
config.setAllowCredentials(true);
```

그리고 Origin은 `*`가 아닌 명확한 Origin 목록이어야 합니다.

## 10. UI에서 URL을 바꿀 때

화면은 대상 서비스 URL을 직접 변경할 수 있습니다.

```text
http://localhost:8080
http://개발서버:8080
https://테스트서버.example.com
```

하지만 브라우저가 임의의 URL을 입력했다고 해당 서비스가 자동 허용하는 것은 아닙니다.

예:

```text
UI Origin:
http://localhost:8090

대상 Service:
http://192.168.0.20:8080
```

대상 서버의 CORS 정책에 반드시 다음 Origin이 있어야 합니다.

```yaml
allowed-origins:
  - http://localhost:8090
```

CORS의 허용 대상은 호출 대상 URL이 아니라 호출하는 브라우저 페이지의 Origin입니다.

## 11. Relay 방식과 차이

현재 화면은 직접 호출을 사용하지만 Relay API도 남아 있습니다.

### 직접 호출

```text
브라우저 → pdmg-service
```

- CORS 필요
- 브라우저에서 실제 Service URL 노출
- 브라우저 AbortController 사용 가능
- 대상 서비스가 UI Origin을 알아야 함

### Relay 호출

```text
브라우저 → pdmg-ui → pdmg-service
```

- 브라우저와 UI가 same-origin이면 CORS 불필요
- pdmg-service가 UI 브라우저 Origin을 몰라도 됨
- UI 서버에서 인증정보·대상 URL을 통제 가능

문서의 “Relay는 남아 있지만 현재 화면은 사용하지 않는다”는 설명은 실제 코드와 일치합니다.

## 12. 테스트 부족

현재 [SecurityConfigTest.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/test/java/nhnis/mg/co/a/config/SecurityConfigTest.java:22>)는 POST가 200인지 확인할 뿐 CORS를 검증하지 않습니다.

필요한 테스트:

```java
mockMvc.perform(options("/mgcoa8888S0")
        .header("Origin", "http://localhost:8090")
        .header("Access-Control-Request-Method", "POST")
        .header("Access-Control-Request-Headers", "content-type"))
    .andExpect(status().isOk())
    .andExpect(header().string(
        "Access-Control-Allow-Origin",
        "http://localhost:8090"));
```

추가로 확인해야 할 항목:

- 허용 Origin의 OPTIONS 성공
- 비허용 Origin 거부
- 정상 POST의 Allow-Origin
- 잘못된 JSON 400의 Allow-Origin
- Token 누락 401의 Allow-Origin
- `localhost`와 `127.0.0.1` 각각 허용
- dev 및 운영 Origin

특히 Filter가 반환하는 400/401에 CORS 헤더가 붙는지 검증하는 테스트가 가장 중요합니다.

## 13. 운영 설정 문제

현재 CORS 설정은 공통 영역에 있어 local과 dev에 모두 적용됩니다.

```yaml
allowed-origins:
  - http://localhost:8090
  - http://127.0.0.1:8090
```

운영에서는 실제 UI 주소로 분리해야 합니다.

```yaml
---
spring:
  config:
    activate:
      on-profile: prod
  mvc:
    cors:
      allowed-origins:
        - https://pdmg-ui.example.com
```

운영에서 localhost를 계속 허용할 필요는 없습니다.

또한 현재 `spring.profiles.active: local`이 기본 파일에 고정되어 있으므로 배포 시 프로파일 지정 누락 위험이 있습니다.

## 최종 평가

문서 정확도는 약 85~90%입니다.

잘 구현된 부분:

- 브라우저 직접 호출에 CORS 적용
- 명시적 Origin 허용
- `/**` 경로 적용
- POST·OPTIONS 허용
- Spring Security CORS 연결
- DefaultFilter의 OPTIONS 제외
- Relay와 직접 호출 구분

보완할 부분:

1. DefaultFilter 조기 오류의 CORS 헤더 누락 가능성
2. Filter 순서 명시
3. 정상 응답과 Filter 오류 응답을 구분
4. local/dev/prod Origin 분리
5. 실제 OPTIONS 및 오류 POST 테스트 추가
6. 운영 환경의 localhost Origin 제거

핵심 흐름은 다음처럼 정리하는 것이 가장 정확합니다.

```text
OPTIONS
  → DefaultFilter 제외
  → Security CORS 처리
  → 정상

정상 POST
  → DefaultFilter 통과
  → Security CORS
  → TCF 처리
  → 정상

오류 POST
  → DefaultFilter에서 400/401 즉시 종료
  → Security CORS까지 도달하지 않을 수 있음
  → 브라우저에서 실제 오류 대신 CORS 오류로 보일 위험
```

이번 분석은 현재 소스와 설정을 기준으로 한 정적 점검이며, 앞서 확인된 Gradle Plugin 의존성 미확보로 실제 MockMvc/브라우저 테스트는 실행하지 못했습니다.
