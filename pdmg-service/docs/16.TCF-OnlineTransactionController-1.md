## 16. TCF — OnlineTransactionController 분석 결과

`OnlineTransactionController`는 TCF가 활성화된 상태에서 PDMG 온라인 거래를 하나의 HTTP Controller로 받는 공통 진입점입니다.

쉽게 말하면:

```text
요청 URL과 전문에서 serviceId 확인
→ dto 부분만 분리
→ TcfFacade에 전달
```

업무별 Controller를 대신하지만 직접 업무를 처리하지는 않습니다.

소스: [OnlineTransactionController.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/web/OnlineTransactionController.java:29>)

---

## 1. 전체 위치

```text
HTTP 요청
  ↓
DefaultFilter
  ├─ JWT 검증
  ├─ Body 캐시
  ├─ hdr_nhnis 파싱
  └─ ServiceContext 생성
  ↓
ServicePreventionInterceptor.preHandle
  ├─ GUID 보정
  ├─ 요청 전문 로그
  └─ ImageLog INSERT
  ↓
OnlineTransactionController               ★ 현재 위치
  ├─ serviceId 결정
  ├─ IP·헤더 보완
  ├─ dto 추출
  └─ TcfFacade 호출
  ↓
OnlineTimeoutExecutor
  ↓
TransactionDispatcher
  ↓
TransactionHandler
  ↓
업무 Facade → Service → DAO
  ↓
ResponseBodyAdvice
  ↓
Interceptor.afterCompletion
```

## 2. 활성 조건

Controller는 다음 조건에서만 Bean으로 생성됩니다.

```java
@RestController
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "true"
)
public class OnlineTransactionController {
}
```

현재 설정:

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
```

따라서 현재는 공통 `OnlineTransactionController`가 활성화됩니다.

### TCF OFF

```yaml
nhnis.fw.tcf.enabled: false
```

이면 공통 Controller는 사라지고 업무별 Controller가 활성화됩니다.

```text
mgcoa5530Controller
mgcoa8888Controller
mgcoa9999Controller
mgcoa9000Controller
```

같은 URL이 중복 매핑되지 않도록 ON/OFF 조건이 서로 반대로 구성되어 있습니다.

## 3. 지원 URL

세 가지 POST 경로를 제공합니다.

| 메서드                   | URL                           | 기본 목적 |
| ------------------------ | ----------------------------- | --------- |
| `handleByServiceId`      | `POST /{serviceId}`           | PDMG 기본 |
| `handleRoot`             | `POST /online`                | TCF 호환  |
| `handleWithBusinessCode` | `POST /{businessCode}/online` | TCF 호환  |

### 권장 경로

현재 PDMG에서는 다음 방식을 권장할 수 있습니다.

```http
POST /mgcoa5530S0
POST /mgcoa8888S0
POST /mgcoa8888D0
POST /mgcoa9000C0
```

URL에 실제 serviceId가 있기 때문에 헤더가 누락되더라도 local 환경에서는 serviceId를 보완할 수 있습니다.

---

## 4. 세 URL의 동작 차이

### 4.1 `POST /{serviceId}`

```java
@PostMapping("/{serviceId}")
public Object handleByServiceId(
        @PathVariable String serviceId,
        @RequestBody Map<String, Object> request,
        HttpServletRequest servletRequest)
```

예:

```text
POST /mgcoa5530S0
→ pathServiceId = mgcoa5530S0
```

local에서 `hdr_nhnis`가 없어도 `DefaultFilter`가 URI 마지막 값을 사용해 다음처럼 보완합니다.

```text
rms_svc_c = mgcoa5530S0
```

따라서 세 경로 중 가장 안정적입니다.

---

### 4.2 `POST /online`

```java
@PostMapping("/online")
public Object handleRoot(...)
```

`pathServiceId`는 `null`로 전달됩니다.

```java
return handle(null, request, servletRequest);
```

따라서 반드시 전문 헤더에 실제 serviceId가 있어야 합니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa5530S0"
    }
  },
  "dto": {}
}
```

### 헤더가 없을 때 문제

local에서 헤더 없이 다음 요청을 보내면:

```http
POST /online

{
  "dto": {}
}
```

`DefaultFilter`는 URL 마지막 값인 `online`을 serviceId로 합성합니다.

```text
ServiceContext.rms_svc_c = online
```

Controller는 Context 값을 가장 우선하므로:

```text
serviceId = online
```

Dispatcher에는 `online` Handler가 없어서 다음 오류가 발생합니다.

```text
등록되지 않은 serviceId입니다: online
```

따라서 `/online` 경로에서는 `rms_svc_c`를 필수로 검사해야 합니다.

---

### 4.3 `POST /{businessCode}/online`

예:

```http
POST /mg/online
```

메서드는 다음과 같습니다.

```java
public Object handleWithBusinessCode(
        @PathVariable String businessCode,
        ...)
```

그런데 내부에서는 `businessCode`를 그대로 `pathServiceId` 위치에 전달합니다.

```java
return handle(businessCode, request, servletRequest);
```

즉, 헤더 serviceId가 없다면:

```text
pathServiceId = mg
```

가 되어 `mg`라는 Handler를 찾으려 합니다.

그런데 실제로는 `DefaultFilter`가 URI 마지막 값인 `online`을 Context에 먼저 넣을 수 있습니다.

```text
Context.rms_svc_c = online
pathServiceId = mg
```

Controller 우선순위상 Context가 이기므로 최종값은:

```text
serviceId = online
```

입니다.

따라서 이 경로에서도 실제 거래 ID 헤더가 필수입니다. 현재 `businessCode`는 검증이나 라우팅에 실질적으로 사용되지 않습니다.

## 5. 요청 전문

Controller는 전체 JSON을 다음 타입으로 받습니다.

```java
@RequestBody Map<String, Object> request
```

표준 형식:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "GUID",
      "rms_svc_c": "mgcoa5530S0",
      "tr_trm_ipadr": "127.0.0.1",
      "optr_eno": "USER01"
    }
  },
  "dto": {
    "customerName": "홍길동"
  }
}
```

Controller는 전체 전문을 업무에 넘기지 않습니다.

```java
Object dtoBody =
        request == null
            ? null
            : request.get("dto");
```

즉:

```text
hdr_nhnis → ServiceContext와 시스템 처리에서 사용
dto       → Handler/Facade/Service에 전달
```

## 6. 내부 처리 순서

모든 URL은 다음 메서드로 모입니다.

```java
private Object handle(
        String pathServiceId,
        Map<String, Object> request,
        HttpServletRequest servletRequest)
```

실행 순서:

```text
1. enrichClientIp()
2. resolveServiceId()
3. ensureRmsSvcC()
4. request.get("dto")
5. tcfFacade.process()
```

코드:

```java
enrichClientIp(servletRequest);

String serviceId =
        resolveServiceId(pathServiceId, request);

ensureRmsSvcC(serviceId);

Object dtoBody =
        request == null ? null : request.get("dto");

return tcfFacade.process(
        serviceId,
        dtoBody
);
```

Controller의 책임 범위가 작게 유지된 점은 적절합니다.

## 7. serviceId 결정

우선순위는 다음과 같습니다.

```text
1. ServiceContext.header.sys_comm.rms_svc_c
2. 요청 JSON hdr_nhnis.sys_comm.rms_svc_c
3. URL path 값
4. 없으면 null
```

### 예시 1: 모두 동일

```text
URL             = mgcoa5530S0
Context header  = mgcoa5530S0
JSON header     = mgcoa5530S0
```

결과:

```text
serviceId = mgcoa5530S0
```

### 예시 2: URL과 헤더 불일치

```text
URL             = mgcoa5530S0
Context header  = mgcoa8888D0
JSON header     = mgcoa8888D0
```

결과:

```text
serviceId = mgcoa8888D0
```

즉, `/mgcoa5530S0`으로 요청했지만 이미지로그 삭제 거래가 실행될 수 있습니다.

Dispatcher가 등록된 ID만 허용하므로 임의 Bean 실행은 어렵지만, 등록된 다른 거래로 우회할 수 있습니다.

운영에서는 다음 검증이 필요합니다.

```java
if (StringUtils.hasText(pathServiceId)
        && StringUtils.hasText(headerServiceId)
        && !pathServiceId.equals(headerServiceId)) {
    throw new InvalidServiceIdException(
        "URL과 전문의 serviceId가 일치하지 않습니다."
    );
}
```

## 8. `ensureRmsSvcC`

최종 serviceId가 결정된 후 Context 헤더가 비어 있으면 채웁니다.

```java
if (!StringUtils.hasText(
        sys.getRms_svc_c())) {
    sys.setRms_svc_c(serviceId);
}
```

목적:

```text
응답 hdr_nhnis
ImageLog SERVICE_ID
업무 로그 serviceId
```

하지만 이미 값이 있으면 최종값과 다르더라도 덮어쓰지 않습니다. 현재 `resolveServiceId()`가 Context 값을 우선하므로 일반적으로 같지만, serviceId 검증 책임이 분산되어 있습니다.

## 9. 클라이언트 IP 보완

Context 헤더에 IP가 없을 때만 보완합니다.

```text
1. X-Forwarded-For 첫 번째 값
2. request.remoteAddr
```

```java
if (StringUtils.hasText(
        sys.getTr_trm_ipadr())) {
    return;
}
```

따라서 전문에 이미 IP가 있으면 HTTP 요청에서 계산한 IP로 바꾸지 않습니다.

IP별 거래통제에서는 전문 IP를 신뢰하면 안 됩니다. 통제용 실제 IP와 전문 기록용 IP를 분리해야 합니다.

## 10. dto가 없을 때

다음 요청도 Filter의 JSON 검증은 통과합니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa5530S0"
    }
  }
}
```

Controller에서는:

```text
dtoBody = null
```

업무 Facade들은 null을 빈 Map으로 변환합니다.

```java
Object source = dtoBody == null
        ? Collections.emptyMap()
        : dtoBody;

InputDTO input =
        objectMapper.convertValue(
            source,
            InputDTO.class
        );
```

따라서 DTO가 없어도 기본값이 채워진 입력 DTO로 업무가 실행될 수 있습니다.

조회 거래에서는 허용될 수 있지만 등록·수정·삭제 거래에서는 위험합니다.

권장 정책:

```text
조회 + 입력조건 선택사항
→ dto 생략 허용 가능

등록·수정·삭제
→ dto 필수
→ Bean Validation 적용
```

현재 Controller에는 `@Valid`나 `dto` 필수 검증이 없습니다.

## 12. 현재 등록 Handler

현재 Dispatcher에 등록되는 serviceId는 다음과 같습니다.

| Handler            | serviceId                                                  |
| ------------------ | ---------------------------------------------------------- |
| `mgcoa5530Handler` | `mgcoa5530S0`                                              |
| `mgcoa8888Handler` | `mgcoa8888S0`, `mgcoa8888D0`                               |
| `mgcoa9999Handler` | `mgcoa9999S0`                                              |
| `mgcoa9000Handler` | `mgcoa9000S0`, `mgcoa9000C0`, `mgcoa9000U0`, `mgcoa9000D0` |

serviceId가 없거나 등록되지 않았으면 `ServiceHandlerNotFound`가 발생합니다.

```java
if (!StringUtils.hasText(serviceId)) {
    throw new ServiceHandlerNotFound(
        "serviceId가 없습니다."
    );
}

if (handler == null) {
    throw new ServiceHandlerNotFound(
        "등록되지 않은 serviceId입니다: " + serviceId
    );
}
```

이 예외는 `GlobalExceptionHandler`에서 `E9999`, HTTP 500으로 처리됩니다.

미등록 URL은 기술적으로 서버 장애가 아니라 클라이언트 요청 오류에 가까우므로 HTTP 400 또는 404가 더 적합합니다.

## 13. 트랜잭션 처리

`OnlineTransactionController`에는 `@Transactional`이 없습니다.

현재 타임아웃 설정:

```yaml
nhnis:
  fw:
    timeout:
      enabled: true
      milliseconds: 5000
```

현재 처리:

```text
Controller 요청 스레드
  ↓
TcfFacade
  ↓
OnlineTimeoutExecutor
  ↓
worker thread
  ↓
TransactionTemplate TX 시작
  ↓
Dispatcher → Handler
  ↓
업무 Facade @Transactional(REQUIRED)
  ↓
Service → DAO
  ↓
commit / rollback
```

따라서 Controller는 트랜잭션 밖에 있고 업무 실행 구간만 worker 트랜잭션에 포함됩니다.

타임아웃이 비활성화되면 worker의 `TransactionTemplate`이 없고 업무 Facade의 `@Transactional`이 트랜잭션을 시작합니다.

## 15. URL 매핑 범위 문제

다음 매핑은 애플리케이션 루트의 모든 한 단계 POST URL을 잡습니다.

```java
@PostMapping("/{serviceId}")
```

예:

```text
POST /health
POST /admin
POST /login
POST /favicon.ico
```

정확한 별도 매핑이 없으면 모두 온라인 serviceId 요청으로 처리되고 `ServiceHandlerNotFound`가 발생할 수 있습니다.

serviceId 패턴이 고정되어 있다면 URL 정규식을 적용하는 것이 안전합니다.

예:

```java
@PostMapping(
    "/{serviceId:mg[a-z0-9]{8}[SCDU][0-9]}"
)
```

또는 온라인 API에 명확한 prefix를 둘 수 있습니다.

```text
POST /api/online/{serviceId}
```

다만 기존 UI·연계 URL 호환성을 고려해야 합니다.

## 결론

현재 `OnlineTransactionController`는 공통 진입점 역할을 작게 유지하고 있으며 기본 구조는 적절합니다.

```text
OnlineTransactionController
  = serviceId 확정
  + dto 분리
  + TcfFacade 위임
```

현재 가장 안전한 호출 방식은:

```http
POST /{serviceId}

{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "{동일한 serviceId}"
    }
  },
  "dto": {}
}
```

운영 전 우선 보완할 항목은 다음입니다.

1. URL과 헤더 serviceId 일치 검증
2. `/online` 계열은 `rms_svc_c` 필수 처리
3. C/U/D 거래의 `dto` 및 필수 필드 검증
4. serviceId URL 패턴 제한
5. 비-local UI Authorization 전달
6. 미등록 serviceId의 HTTP 상태를 400/404로 조정

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
