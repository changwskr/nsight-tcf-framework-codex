# 은행 정보계 차세대 제안용 서버군 분류 및 인프라 조사 기준서

## 1. 도입 전 안내말

은행 정보계 차세대를 제안할 때 서버를 단순히 `서버명 / CPU / Memory / OS / IP` 수준으로 조사하면 목표 아키텍처를 설계하기 어렵다.

차세대 제안에서는 서버를 최소한 다음 관점으로 동시에 분류해야 한다.

```text
서비스 제공모델
  IaaS / PaaS / SaaS

배포모델
  Private Cloud / Public Cloud / Hybrid Cloud / Multi Cloud / On-Premise

실행 기반
  Bare Metal / VM / Container / Kubernetes / Serverless

기술 역할
  Web / WAS / API / Gateway / Middleware / DB / Cache / MQ
  Batch / File / Search / Analytics / AI / Monitoring / Security

업무 역할
  채널계 / 정보계 / 계정계 연계 / 데이터플랫폼 / BI / 마케팅
  공통 / 운영관리 / 배치 / 대외계 / 개발·테스트

운영 특성
  24×365 / 중요도 / HA / DR / RTO / RPO / 백업 / 보안등급

전환 관점
  유지 / 증설 / 통합 / 가상화 / 컨테이너화 / 클라우드 전환
  재구축 / SaaS 대체 / 폐기
```

따라서 서버군 조사는 **현행 인벤토리 작성**이 목적이 아니라 다음 의사결정의 입력자료를 만드는 작업이어야 한다.

```text
현행 서버군 조사
  ↓
업무·기술 역할 분류
  ↓
의존관계 분석
  ↓
용량·성능·가용성 분석
  ↓
클라우드 적합성 평가
  ↓
IaaS / PaaS / SaaS / Bare Metal 배치 결정
  ↓
목표 서버군 정의
  ↓
센터·DR·네트워크·보안 설계
  ↓
비용 및 라이선스 산정
  ↓
전환 Wave 수립
```

# 3. 문제 정의 및 설계 배경

## 3.1 기존 서버 조사 방식의 한계

기존 인프라 조사에서는 다음 정보만 관리되는 경우가 많다.

```text
서버명
IP
CPU
Memory
Disk
OS
설치 위치
```

그러나 차세대 제안에는 이 정보만으로 부족하다.

예를 들어 CPU 32Core, Memory 256GB 서버가 존재하더라도 다음을 모르면 목표 배치 방식을 결정하기 어렵다.

```text
어떤 업무인가?
24×365 업무인가?
현재 TPS는 얼마인가?
DB와 어떤 관계인가?
다른 서버에 어떤 의존성이 있는가?
Web/WAS/Batch 중 어떤 역할인가?
Scale-Up이 필요한가?
Scale-Out 가능한가?
Container로 전환 가능한가?
PaaS DB를 사용할 수 있는가?
SaaS로 대체 가능한가?
DR에서 반드시 살아 있어야 하는가?
라이선스가 Core 기반인가?
개인정보를 처리하는가?
```

따라서 물리 자원 정보뿐만 아니라 **업무·애플리케이션·데이터·연계·보안·운영 정보를 함께 조사**해야 한다.

# 5. IaaS·PaaS·SaaS·Bare Metal 구분

## 5.1 Bare Metal

### 적용 후보

- 대형 Oracle DB
- 초고성능 DW
- 고성능 In-Memory 시스템
- Appliance 기반 솔루션
- HSM 등 특수 H/W
- GPU 대규모 학습 서버
- Core 기반 라이선스 최적화가 필요한 시스템
- Vendor가 가상화 환경을 제한하는 시스템

### 주요 조사정보

| 항목 | 조사내용 |
|---|---|
| 제조사/모델 | HPE, Dell, Lenovo, IBM 등 |
| CPU | Socket, Core, Clock |
| Memory | 총 용량, DIMM 구성 |
| Local Disk | RAID, SSD/NVMe |
| HBA/NIC | FC, Ethernet 속도 |
| OS | 종류·버전·지원종료일 |
| Cluster | RAC, HA Cluster 등 |
| 라이선스 | CPU/Core 기반 라이선스 |
| 장애영향 | 물리 서버 장애 시 영향업무 |

## 5.3 PaaS

대표 대상은 다음과 같다.

```text
Managed Kubernetes
Managed Database
Managed Cache
Managed MQ
Managed Kafka
Managed Search
Managed API Gateway
Managed Monitoring
Managed CI/CD
Object Storage
Function/Serverless
```

### PaaS 적용 검토 기준

| 평가항목 | 확인사항 |
|---|---|
| 운영부담 | OS·Patch·HA 운영을 CSP/플랫폼으로 이전 가능한가 |
| 표준성 | 오픈 표준 기반인가 |
| Lock-in | 특정 CSP 종속성이 과도하지 않은가 |
| 보안 | 금융 보안기준을 충족하는가 |
| 데이터 위치 | 데이터 저장 위치가 허용되는가 |
| HA/DR | Multi-AZ·Region DR 지원 여부 |
| Backup | 자동 백업·PITR 지원 |
| 성능 | 필요한 TPS·IOPS 지원 |
| 비용 | 관리형 비용과 운영절감 비교 |
| Migration | 기존 기술과 호환성 |

| 이용 목적 | 업무 목적 |
| 사용자 수 | License 산정 |

| 데이터 저장위치 | 국가·Region |
| 인증 | SSO·MFA |
| 연계 | API, SFTP, Webhook |

```text
× 업무 증가율
× 데이터 증가율
× 안전계수

정상 운영 용량
= 목표 처리량 / 목표 사용률

N-1 용량
= 한 Node 장애 후에도 목표 Peak 처리 가능
```

Cloud/Container는 반드시 Scale-Out 단위를 정의한다.

# 36. 마무리말

은행 정보계 차세대의 서버군 조사는 단순한 H/W 실사가 아니다.

최종적으로 다음 질문에 답할 수 있어야 한다.

```text
현재 무엇이 어디에서 실행되는가?

어떤 업무가 어떤 서버와 DB를 사용하는가?

어떤 서버가 장애 나면 어떤 업무가 영향을 받는가?

Peak 시점에 실제 자원은 얼마나 필요한가?

어떤 시스템은 Bare Metal에 남겨야 하는가?

어떤 시스템은 IaaS로 이동할 수 있는가?

어떤 기능은 PaaS로 전환할 수 있는가?

어떤 기능은 SaaS로 대체할 수 있는가?

센터 장애 시 얼마 만에 복구해야 하는가?

현행에서 목표로 어떤 순서로 전환할 것인가?

그 결과 비용과 운영복잡도는 어떻게 달라지는가?
```

따라서 차세대 제안용 서버 관리체계는 다음 연결을 기준으로 설계해야 한다.

```text
업무
↔ Application
↔ Server Group
↔ Server / VM / Container
↔ Middleware
↔ Database
↔ Interface
↔ Network
↔ Security
↔ Monitoring
↔ HA / DR
↔ Capacity
↔ Cost
↔ Migration
```

이 구조를 기준으로 현행 인벤토리를 확보하면 이후 **목표 인프라 아키텍처, 용량산정, Cloud 전환안, DR 구성, 비용산정, 전환계획**을 동일 데이터에서 연속적으로 만들 수 있다.
