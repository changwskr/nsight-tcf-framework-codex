# 1. 도입

PDMK의 거래통제 화면은 서비스 사용여부 `Y/N`만 바꾸는 단순 관리화면이 아니다.

온라인 요청 `hdr_nhnis.sys_comm`에는 다음이 포함된다.

```text
누가             optr_eno
어느 지점에서     tr_brc
어느 단말로       trmno / trm_kdc / tr_trm_ipadr
어느 시스템에서   tr_sysid
언제             tr_dtm
어떤 거래를       rms_svc_c
어떤 방식으로     sync_dsc
요청했는지        std_gbl_id
```

`pdmk-om`은 이 값과 Service Catalog·(향후) 인증 Context·런타임 상태를 결합해 다음을 판단한다.

```text
이 사용자가
이 지점·단말에서
이 호출 시스템을 통해
현재 시각에
이 서비스를
실행해도 되는가?
```

화면은 크게 두 영역으로 나눈다.

```text
[설계·정책 관리]
rms_svc_c별 거래통제 정책(Catalog) 정의

[운영·검증]
sys_comm 평가 시뮬레이션
(후속) 통제결과·긴급중지·변경이력
```

# 2. 문서 개요

## 2.1 목적

운영자가 `sys_comm` 기반 거래통제 정책을 등록·변경·조회하고, 평가 결과(`ALLOW`/`REJECT`/`BLOCK`/`THROTTLE`)를 확인하기 위한 **PDMK-OM UI 구조**를 정의한다.

| 목적 | 설명 |
| ---- | ---- |
| 서비스 관리 | `rms_svc_c`(=`serviceCode`) Catalog 관리 |
| 거래상태 관리 | `NORMAL` / `MAINTENANCE` / `STOP` (±후속 `EMERGENCY_STOP`) |
| 호출시스템 통제 | `allowedSystemIds` ↔ `tr_sysid` |
| 지점·단말 통제 | `allowedBranches` / `allowedTerminalTypes` (±후속 단말원장) |
| 성능·Timeout | Catalog의 `timeoutMs`·`maxTps`·`maxConcurrent` |
| 중복 정책 | `duplicateWindowSec` (런타임 카운터는 후속) |
| 평가 검증 | `mkcoa6666E0`으로 Header 단위 통제 결과 확인 |
| 감사 | (후속) 정책 변경·차단 이력 |

## 2.2 적용 범위 (PDMK 모듈 경계)

```text
브라우저
   ↓
pdmk-ui :8090
  /txcontrol          ← 관리 UI (정적)
  /mkcoa6666          ← 전문 테스트 UI
  /api/txcontrol/*    ← UI→OM 중계
   ↓
pdmk-om :8081
  POST /mkcoa6666S0   Catalog 목록
  POST /mkcoa6666I0   Catalog 등록
  POST /mkcoa6666U0   Catalog 수정
  POST /mkcoa6666D0   Catalog 삭제
  POST /mkcoa6666E0   sys_comm 평가
   ↓
TB_OM_SVC_CATALOG
```

| 구분 | 담당 | 비고 |
| ---- | ---- | ---- |
| 원장·평가 엔진 | `pdmk-om` | H2 로컬 / 운영 Oracle |
| 관리·시뮬 화면 | `pdmk-ui` | OM에 SPA를 두지 않음 |
| 업무 거래 게이트 | `pdmk-fw` STF / Interceptor (후속) | E0 결과 소비 |

> REST 스타일 `GET/PUT /om/api/transaction-controls/...` 는 **본 프로젝트 네이밍과 불일치**한다.  
> PDMK는 **전문형 `POST /mkcoa6666*` + `hdr_nhnis`/`dto`** 를 정본으로 한다.

## 2.3 네이밍 (현행 유지)

| 구분 | 현재 | 비고 |
| ---- | ---- | ---- |
| 프로그램 ID | `mkcoa6666` | OM이어도 당분간 `mkcoa*` |
| 패키지 | `nhnis.mk.co.a.*` | 환경 분리 A안 |
| 화면 경로 | `/txcontrol` | pdmk-ui static |
| 향후 | `omcoa*` / `nhnis.om` | B안 재배치 |

## 4.2 상태 값

현행(P0) Catalog 상태:

```text
NORMAL
MAINTENANCE
STOP
```

우선순위(차단 강도):

```text
STOP  >  MAINTENANCE  >  NORMAL
```

후속(P1) 확장:

```text
EMERGENCY_STOP   ← 긴급중지 전용 UX(TCT-060)
```

| 상태 | 신규거래 | E0 결과 | 오류코드 |
| ---- | -------- | ------- | -------- |
| NORMAL + enabled=Y | 허용 후보 | (이후 단계 통과 시) ALLOW | - |
| enabled=N 또는 STOP | 차단 | BLOCK | `TCF-CTL-003` |
| MAINTENANCE | 차단 | BLOCK | `TCF-CTL-004` |

## 4.3 허용 목록 표기 규칙

| 값 | 의미 |
| -- | ---- |
| `*` | 전체 허용 |
| `PDMK,PDMK-UI` | 나열 값만 허용 (대소문자 무시 비교) |
| 빈 값 | 저장 시 `*` 또는 업무 기본값 |

# 5. 화면 설계 — Phase 0 (현행 `/txcontrol`)

## 5.1 화면 목적

1. Catalog를 `serviceCode` 기준으로 조회·등록·수정·삭제한다.  
2. 실제 요청에 가까운 `sys_comm`을 넣어 **즉시 평가(E0)** 한다.  
3. 운영자가 “정책이 왜 막히는지”를 `TCF-CTL-*` + `checkStep`으로 확인한다.

## 5.2 Layout

```text
┌──────────────────────────────────────────────────────────────┐
│ PDMK-UI > 거래통제 (mkcoa6666)                              │
│ 대상 pdmk-om: http://localhost:8081                         │
├──────────────────────────────────────────────────────────────┤
│ ① sys_comm 평가 (mkcoa6666E0)                               │
│ std_gbl_id / rms_svc_c / sync_dsc / tr_sysid / ...          │
│ [평가 실행] [이 서비스로 Catalog 등록]                        │
│ 결과: ALLOW|REJECT|BLOCK · TCF-CTL-xxx · step · timeoutMs   │
├──────────────────────────────────────────────────────────────┤
│ ② Service Catalog 필터                                      │
│ serviceCode / businessCode / status / enabled / pageSize    │
│ [초기화] [Catalog 조회] [신규 등록]                           │
├──────────────────────────────────────────────────────────────┤
│ TB_OM_SVC_CATALOG Grid                                      │
│ code · name · biz · status · systems · trm · brc · ...      │
│ [수정] [삭제]                                                │
└──────────────────────────────────────────────────────────────┘
         │
         ▼ 등록/수정 Modal
┌──────────────────────────────────────────────────────────────┐
│ serviceCode* · name · businessCode · scid                   │
│ enabled · status · syncType                                 │
│ allowedSystemIds · allowedTerminalTypes · allowedBranches   │
│ start/end time · timeoutMs · maxTps · maxConcurrent         │
│ duplicateWindowSec · auditLevel · reason                    │
│ [저장]                                                       │
└──────────────────────────────────────────────────────────────┘
```

## 5.3 평가 패널 입력 (`sys_comm`)

| UI 필드 | DTO | 필수 | 비고 |
| ------- | --- | ---: | ---- |
| `std_gbl_id` | `stdGblId` | Y | 32 hex |
| `rms_svc_c` | `rmsSvcC` | Y | Catalog Key |
| `sync_dsc` | `syncDsc` | Y | Catalog `syncType` 일치 |

# 8. 평가 흐름 (UI ↔ OM)

요건 §23 순서를 UI 평가 패널이 그대로 드러내야 한다.

```text
[평가 실행]
   ↓
pdmk-ui /api/txcontrol/evaluate
   ↓
pdmk-om mkcoa6666E0
   ↓
필수값 → gbl_id → Q구분 → tr_dtm → (auth 정합)
   → Catalog 조회 → enabled/status
   → tr_sysid → tr_brc → trm_kdc → sync → 거래시간 → scid
   ↓
ALLOW | REJECT | BLOCK
(+ timeoutMs 등 정책 반환)
```

UI는 `checkStep`을 표시해 “몇 번째 통제에서 막혔는지”를 운영자가 즉시 보게 한다.

# 9. 화면에서 관리하지 않는 값

| 필드 | 화면 직접 편집 | 이유 |
| ---- | -------------: | ---- |
| `std_gbl_id` | N (평가 입력만) | 거래 추적 Key, 정책이 아님 |
| `tr_optrnm` | N | 권한 판단 금지, 표시·감사만 |
| `tr_dtm` | N (평가 입력만) | 요청 시각, Catalog는 허용 시간대만 |
| JWT 원문 | N | 서버 인증 Context만 신뢰 |

화면은 **정책(Catalog)** 과 **요청 시뮬레이션(E0 입력)** 만 다룬다.

# 10. 정책 변경 검증 (저장 시)

| 규칙 | 적용 |
| ---- | ---- |
| `serviceCode` 필수 | I0/U0 |
| I0 중복 `serviceCode` 거부 | RSLT_CD=`0009` |
| `allowedStartTime` ≤ `allowedEndTime` (자정넘김 예외는 후속) | UI+서버 |
| `timeoutMs` > 0 | UI+서버 |
| STOP/MAINTENANCE 변경 시 `reason` 권장(P1 필수) | UI |
| Warning TPS > Max TPS | P1 UI 검증 |

변경 후 반영:

```text
Catalog U0 저장
   ↓
다음 E0 / (후속) STF 게이트가 최신 원장 조회
   ↓
WAS 재기동 불필요 (DB 원장 기준)
```

캐시 Evict는 후속(요건 Cache 관리)에서 명시.

# 15. 핵심 아키텍처 판단 (PDMK)

1. **정책의 중심 Key는 `rms_svc_c` → `TB_OM_SVC_CATALOG.SERVICE_CODE`** 이다.  
2. **1차 UI는 화면을 많이 쪼개지 않고 `/txcontrol` 통합**으로 간다 (요건 P2 “OM 통합 화면”과 정합).  
3. **평가(E0)는 화면의 1급 기능**이다. CRUD만으로는 통제 품질을 검증할 수 없다.  
4. 호출시스템·지점·단말·성능은 P0에서 **Catalog 컬럼(CSV/`*`)** 으로 충분하고, 별도 마스터 화면은 P1~P2에서 Tab/원장으로 확장한다.  
5. 범용 REST `/om/api/...` 대신 **기존 PDMK 거래 네이밍(`mkcoa6666*`)** 을 유지한다.

```text
                   rms_svc_c
                       │
              TB_OM_SVC_CATALOG
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
   tr_sysid         tr_brc          trm_kdc
 allowedSystems  allowedBranches  allowedTypes
       │               │               │
       └───────────────┼───────────────┘
                       ▼
                 mkcoa6666E0
                       │
          ALLOW / REJECT / BLOCK / THROTTLE
```

# 16. 마무리

본 설계서는 일반 TCF-OM REST UI 초안을 **PDMK-OM 현실**에 맞게 재구성한 문서이다.

| 구분 | 내용 |
| ---- | ---- |
| 원장·엔진 | `pdmk-om` + `mkcoa6666` + `TB_OM_SVC_CATALOG` |
| 화면 | `pdmk-ui` `/txcontrol` · `/mkcoa6666` |
| P0 목표 | Catalog CRUD + sys_comm 평가 |
| P1+ | 대시보드·긴급중지·통제결과·통합상세 Tab |
| 게이트 연동 | `pdmk-fw` STF/Interceptor (별도 설계) |

**화면의 핵심 목적은 “특정 서비스가 누가·어디서·어떤 단말과 시스템을 이용해·언제·어느 정책으로 실행될 수 있는지를 운영자가 통제·검증하는 것”이다.**
