# NSIGHT TCF `sys_comm` 기반 거래통제 요구사항 정의서

## 1. 도입 전 안내말

`sys_comm`은 단순한 공통 Header 정보가 아니다.

온라인 거래가 업무 프로그램에 진입하기 전에 다음 사항을 판단하기 위한 **거래통제 Context**로 사용해야 한다.

```text
sys_comm 수신
  ↓
필수값·형식 검증
  ↓
요청 거래 식별
  ↓
사용자·지점·단말 식별
  ↓
호출 시스템 식별
  ↓
Service Catalog 조회
  ↓
거래 사용 여부 확인
  ↓
권한·지점·단말 통제
  ↓
중복·시간·동시성·TPS 통제
  ↓
Timeout 정책 결정
  ↓
거래 허용
  ↓
Handler → Facade → Service → Rule → DAO → Mapper
```

핵심 원칙은 다음과 같다.

```text
거래통제를 통과하지 못한 요청은
업무 Handler를 실행하지 않는다.
```

---

# 2. 문서 개요

## 2.1 목적

본 요구사항의 목적은 `sys_comm` 정보를 이용하여 NSIGHT 온라인 거래의 실행 가능 여부를 일관되게 판단하는 거래통제 기준을 정의하는 것이다.

주요 목적은 다음과 같다.

| 목적         | 설명                                       |
| ------------ | ------------------------------------------ |
| 거래 식별    | 거래 한 건을 전 구간에서 유일하게 식별     |
| 서비스 통제  | 등록·허용된 서비스만 실행                  |
| 사용자 통제  | 허용된 사용자만 거래 실행                  |
| 지점 통제    | 거래 가능 지점 여부 검증                   |
| 단말 통제    | 등록된 단말·단말종류·IP만 허용             |
| 시스템 통제  | 허용된 호출 시스템만 접근                  |
| 중복 방지    | 동일 거래의 중복 실행 방지                 |
| 부하 통제    | TPS·동시실행 수 초과 방지                  |
| Timeout 통제 | 서비스별 최대 수행시간 적용                |
| 감사 추적    | 사용자·지점·단말·서비스·시간을 로그로 보존 |

---

## 2.2 적용범위

본 요구사항은 다음 구간에 적용한다.

```text
WEBTOPSUITE / React / 외부 채널
        ↓
Apache / Gateway
        ↓
업무 WAR
        ↓
OnlineTransactionController
        ↓
TCF
        ↓
STF.preProcess()
        ├─ sys_comm 검증
        ├─ 인증 Context 정합성
        ├─ 거래통제
        ├─ Timeout
        └─ 거래로그 시작
        ↓
Dispatcher
        ↓
Handler
```

거래통제의 주 실행 위치는 `STF.preProcess()` 또는 이에 대응하는 TCF 공통 사전처리 영역으로 한다.

# 4. 필드별 거래통제 요구사항

## 4.1 기본 통제 정의

| 필드                   | 통제 역할                       |   필수 | 주요 검증                  |
| ---------------------- | ------------------------------- | -----: | -------------------------- |
| `std_gbl_id`           | 전역 거래 식별자                |      Y | 형식·중복 여부             |
| `rms_svc_c`            | 실행 대상 서비스/거래 식별 코드 |      Y | Service Catalog 등록 여부  |
| `sync_dsc`             | 동기·비동기 처리 구분           |      Y | 서비스 정책과 일치         |
| `tr_sysid`             | 거래 요청 시스템                |      Y | 허용 호출 시스템           |
| `ttl_ug_ync`           | 프로젝트 정의 통제 속성         | 조건부 | 코드사전 값 검증           |
| `std_tgrm_rqr_rsp_dsc` | 요청·응답 구분                  |      Y | 요청 전문인지 확인         |
| `std_tgrm_lclc`        | 전문 언어/Locale                |      Y | 허용 Locale                |
| `tr_trm_ipadr`         | 거래 단말 IP                    |      Y | 등록 IP·허용망 확인        |
| `tr_dtm`               | 거래 발생시각                   |      Y | 시간 형식·시차 검증        |
| `tr_brc`               | 거래 지점                       |      Y | 지점 존재·사용 상태        |
| `trmno`                | 단말번호                        |      Y | 단말 등록·사용 상태        |
| `trm_kdc`              | 단말 종류                       |      Y | 서비스별 허용 단말         |
| `scid`                 | 업무 정의 식별자                | 조건부 | 기준정보 정합성            |
| `optr_eno`             | 조작자/직원번호                 |      Y | 사용자·권한·재직 상태      |
| `tr_optrnm`            | 조작자명                        |      N | 표시·감사용, 권한판단 금지 |

`ttl_ug_ync`, `scid`는 현재 제공된 예제만으로 정확한 업무 의미를 확정할 수 없다. 따라서 **코드사전 또는 기존 전문 정의서에서 의미를 확정한 후 통제규칙을 연결**해야 한다.

# 5. 핵심 거래통제 요구사항

## 5.1 CTL-01 — 전역 거래 ID 통제

`std_gbl_id`는 모든 거래를 유일하게 식별하는 Key로 사용한다.

현재 값:

```text
992674f81e9d4762b0d56a7fb38a1cc0
```

요구사항:

```text
1. NULL 또는 공백 금지
2. 32자리 형식 검증
3. 거래로그의 Primary Trace Key로 사용
4. 동일 ID가 허용 시간 내 재수신되면 중복거래 판단
5. 업무 WAR 간 연계 시 동일 ID 유지
6. 하위 연계 거래가 필요하면 Parent/Child Trace 관계 별도 관리
```

권장 형식 검증:

```text
^[0-9a-fA-F]{32}$
```

중복 요청의 경우:

```text
동일 std_gbl_id
+ 동일 rms_svc_c
+ 중복 허용시간 이내
        ↓
DUPLICATE_TRANSACTION
        ↓
업무 Handler 실행 금지
```

단, 조회 거래를 재호출 가능하게 할 것인지 등록·변경 거래만 강하게 차단할 것인지는 서비스별 정책으로 관리한다.

---

# 6. CTL-02 — 서비스 등록 통제

가장 중요한 거래통제 값은 다음이다.

```text
rms_svc_c = mkcoa6666S0
```

모든 `rms_svc_c`는 OM 또는 거래통제 기준정보에 등록되어 있어야 한다.

예:

| 속성          | 값            |
| ------------- | ------------- |
| 서비스 코드   | `mkcoa6666S0` |
| 사용여부      | Y             |
| 서비스명      | 예: 고객조회  |
| 업무코드      | MK            |
| 호출 시스템   | `PDMK-OM`     |
| 동기구분      | S             |
| Timeout       | 3,000 ms      |
| TPS 제한      | 100           |
| 동시처리 제한 | 50            |
| 허용 단말종류 | 01            |
| 허용 시작시간 | 00:00         |
| 허용 종료시간 | 24:00         |
| 감사대상      | Y             |

처리 기준:

```text
rms_svc_c 수신
   ↓
Service Catalog 조회
   ├─ 미등록 → 차단
   ├─ 사용중지 → 차단
   ├─ 점검중 → 차단
   └─ 정상 → 다음 통제
```

---

# 7. CTL-03 — 호출 시스템 통제

현재 값:

```text
tr_sysid = PDMK-OM
```

서비스별로 호출 가능한 시스템을 등록한다.

예:

```text
mkcoa6666S0
  ├─ PDMK-OM : 허용
  ├─ PDMK-UI : 허용
  └─ OTHER   : 차단
```

즉,

```text
rms_svc_c
        +
tr_sysid
```

조합을 기준으로 접근 가능 여부를 확인한다.

허용되지 않은 호출 시스템이면:

```text
TCF-CTL-005
CALL_SYSTEM_NOT_ALLOWED
```

로 업무 실행 전 차단한다.

---

# 8. CTL-04 — 요청/응답 전문 구분 통제

현재:

```text
std_tgrm_rqr_rsp_dsc = Q
```

프로젝트 코드사전에서 `Q=요청`으로 정의되어 있다는 전제하에 온라인 Endpoint 진입 시 반드시 `Q`여야 한다.

```text
Q → 요청 처리
R → 응답 전문

업무 Endpoint에 R 수신
→ 비정상 전문
→ 즉시 거부
```

요청·응답 코드의 실제 값 정의는 전문 코드사전을 기준으로 한다.

---

# 9. CTL-05 — 동기/비동기 통제

현재:

```text
sync_dsc = S
```

`S=동기`라고 정의되어 있다면 `rms_svc_c`에 등록된 처리방식과 일치해야 한다.

예:

```text
Catalog
mkcoa6666S0
syncType = S

Request
sync_dsc = S

→ 정상
```

반대로:

```text
Catalog = A
Request = S

→ TRANSACTION_MODE_MISMATCH
```

업무 프로그램이 요청 Header만 보고 처리방식을 임의로 변경해서는 안 된다.

---

# 10. CTL-06 — 사용자 거래통제

현재:

```text
optr_eno = E0000001
tr_optrnm = LOCAL_TESTER
```

실제 권한 판단은 `tr_optrnm`이 아니라 `optr_eno`를 기준으로 한다.

다만 더 중요한 원칙은 다음이다.

```text
클라이언트가 보낸 optr_eno
≠ 신뢰 가능한 인증정보
```

JWT 또는 SSO가 적용되어 있다면 다음 정합성 검증이 필요하다.

```text
JWT / AuthenticationContext
userId = E0000001

sys_comm
optr_eno = E0000001

→ 일치 : 다음 단계

불일치
→ 보안 위변조 의심
→ 거래 즉시 차단
→ 감사로그 기록
```

권장 신뢰 우선순위:

```text
1. 서버 인증 Context
2. 사용자/직원 기준정보
3. 등록 단말 정보
4. sys_comm 수신값
```

`tr_optrnm`은 권한 통제에 사용하지 않는다.

오히려 서버가 직원정보에서 다시 조회하여 보정하는 것이 안전하다.

---

# 11. CTL-07 — 지점 통제

현재:

```text
tr_brc = 10001
```

다음 항목을 확인한다.

```text
지점 존재 여부
→ 지점 사용 상태
→ 사용자 소속 지점
→ 서비스 허용 지점
→ 특수 지점 제한
```

예:

```text
사용자 E0000001
소속지점 = 10001

요청 tr_brc
= 10001

→ 정상
```

불일치가 무조건 오류는 아니다.

타점 조회 권한 등이 존재할 수 있으므로 다음과 같이 관리한다.

```text
본점 사용자
→ 전체 지점 허용

일반 영업점 사용자
→ 소속 지점만 허용

특별 권한 보유자
→ 권한 범위 내 허용
```

---

# 12. CTL-08 — 단말번호 통제

현재:

```text
trmno = LOCAL01
```

단말관리 원장과 비교한다.

예:

| 단말번호 | 사용자   | 지점  | IP        | 종류 | 상태 |
| -------- | -------- | ----- | --------- | ---- | ---- |
| LOCAL01  | E0000001 | 10001 | 127.0.0.1 | 01   | TEST |

운영환경에서는 다음 관계가 일치해야 한다.

```text
trmno
↔ tr_brc
↔ trm_kdc
↔ tr_trm_ipadr
↔ 사용자
```

미등록 단말 또는 사용중지 단말은 업무에 진입시키지 않는다.

---

# 13. CTL-09 — 단말 종류 통제

현재:

```text
trm_kdc = 01
```

서비스별 허용 단말 종류를 설정한다.

예:

| 코드 | 예시 의미 | 거래 허용 |
| ---- | --------- | --------- |
| 01   | 전용 단말 | Y         |
| 02   | 일반 Web  | Y         |
| 03   | 모바일    | 조건부    |
| 99   | 미등록    | N         |

예를 들어 고위험 거래가 전용단말에서만 허용된다면:

```text
rms_svc_c = 고위험거래
AllowedTerminalType = 01

Request
trm_kdc = 02

→ 거래 차단
```

---

# 14. CTL-10 — 단말 IP 통제

현재:

```text
tr_trm_ipadr = 127.0.0.1
```

이 값은 로컬 테스트에서는 허용할 수 있지만 운영 거래라면 특별히 주의해야 한다.

운영환경:

```text
127.0.0.1
localhost
0.0.0.0

→ 원칙적으로 정상 사용자 단말 IP로 인정하지 않음
```

단, Proxy를 사용하는 경우 요청 Socket IP와 실제 단말 IP가 다를 수 있으므로:

```text
Client
 ↓
Apache / Gateway
 ↓
업무 WAR
```

구조에서는 신뢰 가능한 Proxy가 설정한 IP 정보만 사용한다.

클라이언트가 임의로 `tr_trm_ipadr` 값을 넣어 보안통제를 우회할 수 없어야 한다.

---

# 15. CTL-11 — 거래시간 통제

현재:

```text
tr_dtm = 20260808000000
```

형식:

```text
yyyyMMddHHmmss
```

기본 검증:

```text
14자리 여부
→ 날짜 유효성
→ 서버 현재시간과 차이 확인
```

예를 들어 허용 시차를 ±5분으로 설정한다.

```text
abs(ServerTime - tr_dtm) <= 5분
→ 정상

5분 초과
→ STALE_OR_FUTURE_REQUEST
```

허용시간은 서비스별로 설정 가능해야 한다.

예:

```text
신용조회       00:00 ~ 24:00
대량출력       07:00 ~ 20:00
마감업무       18:00 ~ 22:00
관리자서비스   지정시간
```

---

# 16. CTL-12 — Locale 통제

현재:

```text
std_tgrm_lclc = KO
```

허용 코드사전에 등록된 값만 허용한다.

예:

```text
KO
EN
```

Locale은 거래 허용 여부 자체보다는 다음에 사용한다.

```text
오류 메시지
코드명
날짜 표시
화면 메시지
```

지원하지 않는 Locale은 기본 Locale로 보정하거나 오류로 처리하는 정책을 명확히 한다.

---

# 17. CTL-13 — 거래 사용중지 통제

운영 중 특정 서비스만 즉시 차단할 수 있어야 한다.

예:

```text
mkcoa6666S0
status = STOP
```

이 경우:

```text
요청
 ↓
STF
 ↓
OM Service Catalog 조회
 ↓
STOP 확인
 ↓
Handler 실행 금지
 ↓
표준 오류 반환
```

Tomcat이나 WAR 전체를 중지하지 않고 `rms_svc_c` 단위로 거래를 차단할 수 있어야 한다.

---

# 18. CTL-14 — 점검시간 통제

서비스별 점검상태를 둔다.

```text
NORMAL
MAINTENANCE
STOP
EMERGENCY_STOP
```

우선순위:

```text
EMERGENCY_STOP
     >
STOP
     >
MAINTENANCE
     >
NORMAL
```

`EMERGENCY_STOP`은 모든 조건보다 우선한다.

---

# 19. CTL-15 — TPS 통제

서비스별 TPS 임계치를 관리한다.

예:

```text
mkcoa6666S0

평시 TPS     = 30
Warning TPS = 80
Max TPS     = 100
```

처리:

```text
TPS < 80
→ 정상

80 ≤ TPS < 100
→ 경고 기록

TPS ≥ 100
→ 신규 요청 제한
```

전체 시스템 TPS만 보는 것이 아니라 최소한 다음 단위가 필요하다.

```text
System
→ WAR
→ rms_svc_c
```

---

# 20. CTL-16 — 동시 실행 거래수 통제

TPS와 별도로 실행 중인 거래 수를 제한한다.

예:

```text
mkcoa6666S0

maxConcurrent = 50
```

현재 50건 수행 중이라면:

```text
51번째 요청
→ Handler 실행 금지
→ BUSY 응답
```

이 통제는 느린 SQL이나 외부 시스템 지연 시 Thread가 무한 점유되는 것을 방지한다.

---

# 21. CTL-17 — Timeout 통제

Timeout은 `rms_svc_c`별로 관리한다.

예:

```text
mkcoa6666S0
timeoutMs = 3000
```

처리:

```text
STF
 ↓
Timeout 정책 조회
 ↓
TimeoutExecutor
 ↓
Handler
 ↓
업무 실행
```

3초 초과 시:

```text
TimeoutException
→ 거래 실패
→ ETF 표준 Timeout 응답
→ 거래로그 TIMEOUT 종료
→ Slow Transaction 기록
```

업무 개발자가 임의로 Timeout을 설정하지 않는다.

---

# 22. CTL-18 — `scid` 정합성 통제

현재:

```text
scid = mkcoa6666
rms_svc_c = mkcoa6666S0
```

두 값 사이에 프로젝트 차원의 관계가 존재한다면 반드시 정합성 검증을 수행한다.

예를 들어 `scid`가 서비스 기본 식별자이고 `S0`가 처리유형이라면:

```text
scid        = mkcoa6666
rms_svc_c   = mkcoa6666 + S0
```

관계를 기준정보로 관리할 수 있다.

하지만 현재 제공된 정보만으로 `scid`의 정확한 의미를 확정할 수 없으므로 **문자열 앞부분이 같다는 사실만으로 통제규칙을 확정해서는 안 된다.**

공식 전문정의서 또는 코드사전에서 의미를 먼저 확정한다.

# 24. 통제 결과 상태

통제 결과는 최소 네 종류로 표준화하는 것을 권장한다.

| 상태       | 의미                         |
| ---------- | ---------------------------- |
| `ALLOW`    | 거래 실행 허용               |
| `REJECT`   | 요청 자체가 잘못되어 거부    |
| `BLOCK`    | 정책에 의해 거래 중지        |
| `THROTTLE` | 부하·동시성 초과로 일시 제한 |

예:

```text

  → Handler 실행

REJECT
  → 입력/보안 오류

BLOCK
  → 사용중지·점검·권한 없음

THROTTLE
  → TPS·동시거래 한도 초과
```

# 31. 자동검증 및 품질 Gate

개발 및 배포 전 다음을 자동검증한다.

```text
rms_svc_c 코드에 존재
↔ OM Catalog 등록

Service Catalog
↔ Handler 등록

tr_sysid
↔ 호출시스템 Registry

trm_kdc
↔ Terminal Code Dictionary

오류코드
↔ TCF 오류코드 Registry

Timeout
↔ 서비스별 정책 존재
```

특히 다음 상태는 배포 Gate 실패로 한다.

```text
Handler는 존재하지만 Catalog 없음
Catalog는 존재하지만 Handler 없음
Timeout 미등록
호출 시스템 미등록
허용 단말 정책 미정의
중복통제 정책 미정의
```

# 35. 시사점

## 35.1 핵심 아키텍처 판단

현재 `sys_comm` 구조는 거래통제에 필요한 상당한 정보를 이미 가지고 있다.

따라서 새로운 통제 Header를 별도로 많이 만드는 것보다:

```text
sys_comm
        +
인증 Context
        +
OM Service Catalog
        +
단말 Registry
        +
거래통제 Runtime 상태
```

를 결합하는 것이 적절하다.

최종 거래허용식은 다음처럼 볼 수 있다.

```text
거래 허용
=
전문 정상
AND 사용자 정상
AND 서비스 등록
AND 서비스 사용중
AND 호출시스템 허용
AND 지점 권한 정상
AND 단말 정상
AND 중복 아님
AND 거래시간 정상
AND TPS 한도 이내
AND 동시실행 한도 이내
```

## 35.2 가장 중요한 판단

`sys_comm`에 값이 존재한다고 해서 그 값을 모두 신뢰하면 안 된다.

특히:

```text
optr_eno
tr_brc
trmno
tr_trm_ipadr
```

는 반드시 서버가 가지고 있는 인증·사용자·단말 기준정보와 비교해야 한다.

즉,

```text
sys_comm
= 거래통제 입력정보

인증 Context / OM 기준정보
= 거래통제의 신뢰 기준
```

으로 분리하는 것이 핵심이다.

## 35.3 우선 구현 과제

우선순위는 다음이 적절하다.

```text
P0
1. sys_comm 필수값 검증
2. rms_svc_c Service Catalog
3. 서비스 사용/중지
4. 인증 사용자 정합성
5. std_gbl_id 거래 추적

P1
6. 지점·단말 통제
7. Timeout
8. 중복 거래
9. 거래시간

P2
10. TPS
11. 동시거래수
12. 자동 거래 차단
13. OM 통합 화면
```
