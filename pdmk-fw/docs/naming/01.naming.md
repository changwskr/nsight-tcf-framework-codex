앞선 설명에서 추정했던 의미를 정정합니다. 앞으로 PDMK 네이밍은 [MK-NAMING_CONVENTION.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-service/docs/MK-NAMING_CONVENTION.md>)를 공식 기준으로 봐야 합니다.

특히 PDMK는 일반적인 Java/REST 네이밍으로 변경하지 않고, 프로그램·전문 중심의 기존 규칙을 의도적으로 사용합니다.

## 1. 서비스 ID 공식 구조

```text
[대구분 2자]
[업무구분 2자]
[세부업무구분 1자]
[식별번호 4자]
[구분자 1자]
[순번 1자]
```

총 11자리입니다.

```text
mkcoa8888S0
│ │ │   ││
│ │ │   │└─ 순번: 0
│ │ │   └── 구분자: S(조회)
│ │ └────── 식별번호: 8888
│ └──────── 세부업무: a(상담)
└────────── 대구분 mk + 업무구분 co
```

공식 의미:

| 영역         | 값     | 의미                   |
| ------------ | ------ | ---------------------- |
| 대구분       | `mk`   | 애플리케이션 그룹 MK   |
| 업무구분     | `co`   | 공통                   |
| 세부업무구분 | `a`    | 상담                   |
| 식별번호     | `8888` | 화면번호 또는 일반번호 |
| 구분자       | `S`    | 조회                   |
| 순번         | `0`    | 동일 기능 내 순번      |

따라서 앞서 제가 `co`, `a`의 의미를 추정 대상으로 설명한 것은 정정해야 합니다.

```text
CO = 공통
A  = 상담
```

## 2. 애플리케이션 분류

### 대구분

```text
MK = PDMK 애플리케이션 그룹
```

소스에서는 소문자를 사용합니다.

```text
MK → mk
```

### 업무구분

| 코드 | 의미        |
| ---- | ----------- |
| `CO` | 공통        |
| `IC` | 통합고객    |
| `MS` | 미니 상품부 |
| `SA` | 사업관리    |

### 세부업무구분

| 코드 | 의미 |
| ---- | ---- |
| `A`  | 상담 |
| `B`  | 고객 |

예:

```text
mkcoa8888S0
  ││
  │└─ A: 상담
  └── CO: 공통
```

## 3. 거래 구분자

서비스 ID 끝에서 두 번째 문자는 거래 기능을 나타냅니다.

| 구분자 | 의미   | 예            |
| ------ | ------ | ------------- |
| `S`    | 조회   | `mkcoa8888S0` |
| `C`    | 등록   | `mkcoa0000C0` |
| `U`    | 수정   | `mkcoa0000U0` |
| `D`    | 삭제   | `mkcoa8888D0` |
| `A`    | 혼합   | `mkcoa0000A0` |
| `R`    | 리포트 | `mkcoa0000R0` |

마지막 문자는 동일 기능 내 순번입니다.

```text
0~9
A~Z
```

예:

```text
mkcoa8888S0 → 첫 번째 조회 거래
mkcoa8888S1 → 두 번째 조회 거래
mkcoa8888SA → 11번째 조회 거래
```

## 4. 패키지 규칙

공식 패키지 구조:

```text
nhnis.[대구분].[업무구분].[세부업무구분]
```

하위 계층:

```text
controller
service
dao
dto
```

`mkcoa`의 공식 패키지:

```text
nhnis.mk.co.a.controller
nhnis.mk.co.a.service
nhnis.mk.co.a.dao
nhnis.mk.co.a.dto
```

현재 소스는 이 규칙을 따릅니다.

```text
pdmk-service/src/main/java/nhnis/mk/co/a
```

## 5. Controller 규칙

Controller는 서비스 ID 전체가 아니라 식별번호까지만 사용합니다.

```text
[대구분][업무구분][세부업무구분][식별번호]Controller
```

예:

```java
mkcoa8888Controller
```

서비스 구분자 `S0`, `D0`는 클래스명에 넣지 않습니다.

```text
mkcoa8888S0 ┐
            ├─ mkcoa8888Controller
mkcoa8888D0 ┘
```

동일 식별번호의 거래는 하나의 Controller에 통합합니다.

```java
@Slf4j
@RestController
public class mkcoa8888Controller {

    @PostMapping("/mkcoa8888S0")
    public mkcoa8888S0DTOout mkcoa8888S0(
            @RequestBody mkcoa8888S0DTOin input)
            throws Throwable {
        ...
    }

    @PostMapping("/mkcoa8888D0")
    public mkcoa8888D0DTOout mkcoa8888D0(
            @RequestBody mkcoa8888D0DTOin input)
            throws Throwable {
        ...
    }
}
```

공식 Controller 규칙:

- `@Slf4j`
- `@RestController`
- 메서드에 `@PostMapping("/서비스ID")`
- 클래스 레벨 `@RequestMapping` 사용 금지
- PDMK 전용 `nhnis.fw.commons.resolver.RequestBody` 사용
- 메서드 이름은 서비스 ID 전체 사용
- `throws Throwable` 사용

따라서 일반적인 REST URL로 바꾸지 않습니다.

```text
사용하지 않음:
/api/mk/co/a/8888/list

PDMK 공식 방식:
POST /mkcoa8888S0
```

## 6. Service 규칙

Service도 식별번호 단위로 생성합니다.

```text
[대구분][업무구분][세부업무구분][식별번호]Service
```

예:

```java
mkcoa8888Service
```

메서드는 서비스 ID 전체를 사용합니다.

```java
public mkcoa8888S0DTOout mkcoa8888S0(
        mkcoa8888S0DTOin input)
        throws Exception
```

공식 어노테이션:

```java
@Slf4j
@Service
```

동일 프로그램의 조회와 삭제는 같은 Service에 둘 수 있습니다.

```java
mkcoa8888Service
  ├─ mkcoa8888S0()
  └─ mkcoa8888D0()
```

## 7. DAO 규칙

DAO 역시 식별번호 단위입니다.

```text
[대구분][업무구분][세부업무구분][식별번호]DAO
```

예:

```java
@RDWMapper
public interface mkcoa8888DAO {
}
```

DAO 메서드는 서비스 ID 뒤에 실제 SQL 유형과 순번을 붙입니다.

```text
[서비스ID]_[DML구분][순번]
```

예:

```java
mkcoa8888S0_S0
mkcoa8888S0_S0_count
mkcoa8888D0_D0
```

구조:

```text
mkcoa8888S0_S0
└─ 거래 ID     └─ 첫 번째 SELECT SQL

mkcoa8888D0_D0
└─ 거래 ID     └─ 첫 번째 DELETE SQL
```

앞서 `S0_S0`, `D0_D0`가 중복처럼 보인다고 설명했지만, 공식 규칙에서는 각각 역할이 다릅니다.

```text
앞의 S0/D0 = 서비스 거래 구분과 순번
뒤의 S0/D0 = 해당 거래 내부의 SQL DML 구분과 순번
```

따라서 임의로 `selectImageLogs`, `deleteImageLogs` 등으로 변경하면 안 됩니다.

## 8. SQL ID 규칙

SQL ID는 DAO 메서드명과 반드시 같아야 합니다.

DAO:

```java
int mkcoa8888D0_D0(
    Map<String, Object> input
);
```

XML:

```xml
<delete id="mkcoa8888D0_D0">
```

공식 DML 코드:

| 코드 | 의미 |
| ---- | ---- |
| `S`  | 조회 |
| `C`  | 등록 |
| `U`  | 수정 |
| `D`  | 삭제 |
| `A`  | 혼합 |

리포트 서비스는 내부에서 조회 SQL을 사용할 수 있습니다.

```text
서비스: mkcoa0000R0
SQL ID: mkcoa0000R0_S0
```

즉 서비스 구분자와 SQL DML 구분자가 항상 같아야 하는 것은 아닙니다.

## 9. DTO 규칙

DTO는 서비스 ID 전체를 사용합니다.

```text
[서비스ID]DTOin
[서비스ID]DTOout
[서비스ID]DTOio
```

예:

```text
mkcoa8888S0DTOin
mkcoa8888S0DTOout
mkcoa8888D0DTOin
mkcoa8888D0DTOout
```

입출력 구분:

| 접미어 | 의미         |
| ------ | ------------ |
| `in`   | 입력         |
| `out`  | 출력         |
| `io`   | 입·출력 공용 |

기본 요건:

- `DataObject` 상속
- Getter/Setter 구현
- `clone()` 구현
- `toString()` 구현
- `getFieldPropertyMap()` 구현

앞서 일반 Java 네이밍인 `Input`, `Output`으로 바꾸는 방안을 제시했지만, 이 문서 기준에서는 사용하지 않습니다.

```text
공식: mkcoa8888S0DTOin
비공식: Mkcoa8888S0Input
```

## 10. Sub DTO 규칙

목록이나 GRID의 항목 DTO는 다음 형식입니다.

```text
[서비스ID]DTOSub[순번]
```

예:

```text
mkcoa8888S0DTOSub0
mkcoa5530S0DTOSub0
mkcoa9999S0DTOSub0
```

순번:

```text
0~9
A~Z
```

Sub DTO 목록 필드도 생성 규칙과 일치해야 합니다.

```java
mkcoa8888S0DTOSub0
```

`Item`, `Row` 등으로 임의 변경하지 않습니다.

## 11. Mapper XML 규칙

리소스 디렉터리:

```text
src/main/resources/
rdw.[대구분].[업무구분].[세부업무구분]/
```

예:

```text
src/main/resources/rdw.mk.co.a/
```

파일명:

```text
[대구분][업무구분][세부업무구분][식별번호]-[DB구분].xml
```

예:

```text
mkcoa8888-ORA.xml
mkcoa5530-ORA.xml
mkcoa9999-ORA.xml
```

DB 구분:

| 코드  | DB            |
| ----- | ------------- |
| `ORA` | Oracle        |
| `MYS` | MySQL         |
| `MSS` | MS SQL Server |

Mapper namespace:

```xml
<mapper namespace=
    "nhnis.mk.co.a.dao.mkcoa8888DAO">
```

## 12. 변수와 DB 네이밍

Java 변수는 camelCase입니다.

```java
guid
serviceId
totalCount
pageNo
pageSize
```

SQL 규칙:

```text
DB 키워드       → 대문자
DB Object       → 대문자
사용자 변수     → 소문자
테이블 Alias    → T1, T2, T3
컬럼 Alias      → AS 사용
```

예:

```sql
SELECT /* mkcoa8888S0_S0 */
       T1.GUID       AS GUID
     , T1.SERVICE_ID AS SERVICE_ID
  FROM TB_FW_IMAGE_LOG T1
 WHERE T1.GUID = #{guid}
```

파라미터는 반드시 `#{...}` 바인딩을 사용합니다.

```xml
#{guid}
```

`${guid}` 직접 치환은 사용하지 않습니다.

## 13. 현재 소스의 준수 상태

현재 주요 구조는 대부분 공식 규칙과 일치합니다.

| 항목                                 | 현재 상태 |
| ------------------------------------ | --------- |
| 서비스 ID `mkcoa8888S0`              | 준수      |
| Controller 식별번호 단위             | 준수      |
| 동일 식별번호 Controller 통합        | 준수      |
| 클래스 레벨 `@RequestMapping` 미사용 | 준수      |
| PDMK 전용 `@RequestBody`             | 준수      |
| Service 식별번호 단위                | 준수      |
| DAO 식별번호 단위                    | 준수      |
| DAO 메서드와 SQL ID 일치             | 준수      |
| DTO `DTOin`/`DTOout`                 | 준수      |
| Sub DTO `DTOSub0`                    | 준수      |
| XML `rdw.mk.co.a` 위치               | 준수      |
| XML `-ORA.xml`                       | 준수      |
| SQL `#{}` 바인딩                     | 준수      |

확인되는 차이는 Service 어노테이션입니다.

문서 기준:

```java
@Slf4j
@Service
```

현재 일부 Service:

```java
@Service
public class mkcoa5530Service {

    private static final Logger log =
        LoggerFactory.getLogger(mkcoa5530Service.class);
}
```

기능에는 문제가 없지만 문서의 생성 규칙과는 다릅니다. 새로 생성하는 Service는 `@Slf4j`를 사용하는 것이 공식 기준입니다.

## 14. 문서 내부 확인 필요 항목

문서의 서비스 ID 기본 규칙은 식별번호 4자리입니다.

```text
mk + co + a + 8888 + S + 0
```

그런데 예시 중 다음 값이 있습니다.

```text
mkcoaZ0000S0
```

이 값은 `a` 다음에 `Z0000`이 있어 식별번호가 5자리처럼 보입니다. 기본 구조의 “식별번호 4자” 규칙과 맞지 않습니다.

따라서 다음 중 어느 의미인지 문서 보완이 필요합니다.

- `Z`가 별도의 화면 구분자인지
- 식별번호가 특정 경우 5자리까지 가능한지
- 단순 예시 오타인지

공식 검증기를 만들 때는 이 예외를 확정해야 합니다.

## 15. 최종 네이밍 체계

```text
서비스 ID
  mkcoa8888S0

Controller
  mkcoa8888Controller
  ├─ mkcoa8888S0()
  └─ mkcoa8888D0()

Service
  mkcoa8888Service
  ├─ mkcoa8888S0()
  └─ mkcoa8888D0()

DAO
  mkcoa8888DAO
  ├─ mkcoa8888S0_S0()
  ├─ mkcoa8888S0_S0_count()
  └─ mkcoa8888D0_D0()

DTO
  mkcoa8888S0DTOin
  mkcoa8888S0DTOout
  mkcoa8888S0DTOSub0
  mkcoa8888D0DTOin
  mkcoa8888D0DTOout

Mapper
  rdw.mk.co.a/mkcoa8888-ORA.xml
```

앞으로 PDMK 네이밍은 일반 Java/REST 스타일로 정규화하지 않고, 이 문서의 프로그램·전문 기반 규칙을 우선 적용해야 합니다. 특히 클래스가 소문자로 시작하는 형식, `DTOin/DTOout`, `S0_S0`, `POST /서비스ID`는 이 프로젝트에서 의도된 공식 규칙입니다.
