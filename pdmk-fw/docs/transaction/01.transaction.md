현재 PDMK에는 트랜잭션을 수행할 기반 구성은 있지만, 실제 업무 Service에는 `@Transactional`이 적용되어 있지 않습니다.

즉 현재 상태는 다음과 같습니다.

```text
TransactionManager Bean     존재
MyBatis 연동                정상 구성
업무 Service @Transactional 없음
수동 ServiceTransactionManager 미사용
```

따라서 현재 DAO SQL은 “Service 메서드 전체가 하나의 트랜잭션”으로 묶여 있지 않습니다.

## 1. 트랜잭션 구성

[RdwDataSourceConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-service/src/main/java/nhnis/mk/config/RdwDataSourceConfig.java>)에서 RDW용 TransactionManager를 생성합니다.

```java
@Bean
@Primary
public PlatformTransactionManager rdwTransactionManager(
        DataSource rdwDataSource) {

    return new DataSourceTransactionManager(rdwDataSource);
}
```

연결 구조는 다음과 같습니다.

```text
@Transactional
  → rdwTransactionManager
  → DataSourceTransactionManager
  → rdwDataSource
  → JDBC Connection
  → MyBatis/JdbcTemplate SQL
```

같은 스레드에서 같은 `rdwDataSource`를 사용하는 MyBatis와 `JdbcTemplate`은 활성 트랜잭션이 있으면 같은 Connection에 참여할 수 있습니다.

## 2. 현재 실제 적용 상태

PDMK Service 전체를 검색한 결과 현재 `@Transactional`은 없습니다.

예:

```java
@Service
public class mkcoa8888Service {

    public mkcoa8888D0DTOout mkcoa8888D0(
            mkcoa8888D0DTOin input) throws Exception {

        int cnt = dao.mkcoa8888D0_D0(param);
        return output;
    }
}
```

따라서 현재 실행 특성은 다음과 같습니다.

| 거래          |            SQL 수 | 현재 특성                                      |
| ------------- | ----------------: | ---------------------------------------------- |
| `mkcoa9999S0` |          조회 1회 | 단일 조회                                      |
| `mkcoa5530S0` | Count + 목록 조회 | 두 조회가 하나의 읽기 트랜잭션으로 묶이지 않음 |
| `mkcoa8888S0` | Count + 목록 조회 | 두 조회가 하나의 읽기 트랜잭션으로 묶이지 않음 |
| `mkcoa8888D0` |        Delete 1회 | 단일 SQL로 실행                                |
| ImageLog      |     Insert/Update | 각 호출 시 별도 실행                           |

단일 SQL은 일반적으로 SqlSession/JDBC 실행 단위로 완료되지만, 여러 SQL을 하나의 원자적 업무 단위로 묶는 보장은 없습니다.

## 3. Count와 목록 조회 불일치 가능성

조회 Service는 다음 순서로 실행됩니다.

```java
int totalCount = dao.count(param);
List<Map<String, Object>> rows = dao.select(param);
```

두 SQL 사이에 다른 거래가 데이터를 추가하거나 삭제하면 다음처럼 달라질 수 있습니다.

```text
1. Count 조회       → 100건
2. 다른 거래 삭제   → 10건 삭제
3. 목록 조회        → 실제 90건 기준 결과
```

따라서 응답의 `totalCount`와 목록이 서로 다른 시점의 데이터일 수 있습니다.

일관된 조회 시점이 반드시 필요하다면 읽기 전용 트랜잭션과 DB 격리 수준을 검토해야 합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
public Output inquiry(Input input) {
    int count = dao.count(input);
    List<Row> rows = dao.select(input);
    return createOutput(count, rows);
}
```

다만 `readOnly=true`만으로 Oracle의 두 SELECT가 반드시 동일한 Snapshot을 공유하는지는 DB 격리 수준과 설정에 따라 검토해야 합니다.

## 4. 변경 거래의 트랜잭션

현재 삭제 거래는 SQL 하나입니다.

```java
int cnt = dao.mkcoa8888D0_D0(param);
```

SQL 한 번만 실행할 때는 부분 성공 문제가 상대적으로 적습니다. 하지만 다음처럼 다중 변경으로 확대되면 트랜잭션이 필수입니다.

```text
업무 테이블 DELETE
  → 삭제 이력 INSERT
  → 감사 로그 INSERT
```

트랜잭션이 없으면:

```text
DELETE 성공
이력 INSERT 실패
  → 업무 데이터만 삭제됨
```

트랜잭션이 있으면:

```text
DELETE 성공
이력 INSERT 실패
  → 전체 Rollback
```

권장 예:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
public DeleteOutput delete(DeleteInput input)
        throws Exception {

    int count = dao.delete(input);
    historyDao.insertDeleteHistory(input);

    return createOutput(count);
}
```

## 5. 예외와 Rollback 기준

Spring의 기본 Rollback 규칙은 중요합니다.

| 예외                     | 기본 Rollback            |
| ------------------------ | ------------------------ |
| `RuntimeException`       | 수행                     |
| `Error`                  | 수행                     |
| 일반 checked `Exception` | 기본적으로 수행하지 않음 |

현재 Service 메서드는 다음처럼 checked Exception을 선언합니다.

```java
throws Exception
```

따라서 `@Transactional`만 추가하면 checked Exception에서 Rollback되지 않을 수 있습니다.

현재 코드 스타일을 유지한다면 다음처럼 명시하는 편이 안전합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

또는 시스템·업무 예외를 RuntimeException 기반으로 표준화할 수 있습니다.

예외를 잡고 반환해버리면 Spring은 실패를 알 수 없어 Commit할 수 있습니다.

```java
@Transactional
public void execute() {
    try {
        dao.update();
        dao.insert();
    } catch (Exception e) {
        log.error("실패", e);
        // 예외를 다시 던지지 않으면 Commit 가능
    }
}
```

다음처럼 다시 던지거나 Rollback-only로 표시해야 합니다.

```java
catch (Exception e) {
    throw new BusinessRuntimeException(e);
}
```

## 6. 트랜잭션을 적용할 계층

트랜잭션 경계는 DAO가 아니라 Service 또는 Facade에 두는 것이 적절합니다.

```text
Controller
  → Facade       ← 유스케이스 전체 경계가 필요하면 여기
    → Service    ← 하나의 업무 흐름 경계
      → DAO A
      → DAO B
      → DAO C
```

DAO 메서드마다 `@Transactional`을 붙이면 SQL 각각의 트랜잭션만 생성되어 업무 전체의 원자성을 구성하기 어려워집니다.

권장:

```java
@Service
@RequiredArgsConstructor
public class CustomerService {

    private final CustomerDAO customerDAO;
    private final HistoryDAO historyDAO;

    @Transactional(
        transactionManager = "rdwTransactionManager",
        rollbackFor = Exception.class
    )
    public Output execute(Input input) {
        customerDAO.update(input);
        historyDAO.insert(input);
        return new Output();
    }
}
```

## 7. Spring AOP 적용 조건

`@Transactional`은 Spring Proxy 기반으로 동작합니다.

외부 Bean 호출은 적용됩니다.

```text
Controller
  → Service Proxy
      → 트랜잭션 시작
      → 실제 Service 실행
      → Commit/Rollback
```

하지만 같은 클래스 내부의 자기 호출에는 일반적으로 적용되지 않습니다.

```java
public void outer() {
    inner(); // 같은 객체 내부 호출
}

@Transactional
public void inner() {
    // Proxy를 통하지 않아 트랜잭션이 적용되지 않을 수 있음
}
```

트랜잭션 메서드는 외부 Bean을 통해 호출되도록 구조화해야 합니다.

또한 일반적으로 `public` 메서드에 적용하는 것이 안전합니다.

## 8. 트랜잭션 실행 순서

Service에 `@Transactional`을 적용하면 요청 흐름은 다음과 같습니다.

```text
DefaultFilter
  → ServiceContext 생성

ServicePreventionInterceptor.preHandle
  → Pre ImageLog INSERT

Controller
  → Service Transaction Proxy
      → Transaction 시작
      → Service
          → DAO SQL 1
          → DAO SQL 2
      → 정상: Commit
      → 예외: Rollback

Response 처리

ServicePreventionInterceptor.afterCompletion
  → Post/Exception ImageLog UPDATE
```

즉 시스템 ImageLog의 Pre 기록은 일반적으로 Service 트랜잭션이 시작되기 전에 실행되고, Post/Exception 기록은 Service 트랜잭션이 끝난 다음 실행됩니다.

이 구조는 업무 트랜잭션이 Rollback되어도 장애 추적용 ImageLog를 남기는 데 유리합니다.

## 9. ImageLog 트랜잭션 특성

[ImageLogHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-fw/src/main/java/nhnis/fw/commons/imagelog/ImageLogHandler.java>)는 `JdbcTemplate`을 사용합니다.

```java
this.jdbcTemplate = new JdbcTemplate(dataSource);
```

처리:

```text
preImagelog       → INSERT
postImagelog      → 응답시각 UPDATE
exceptionImagelog → 예외정보 UPDATE, 없으면 INSERT
```

현재 ImageLog에는 별도의 `@Transactional` 또는 `REQUIRES_NEW`가 없습니다.

현재 호출 위치상 Service 트랜잭션의 바깥에서 실행되지만, 향후 ImageLog를 트랜잭션 내부에서 호출하면 같은 RDW 트랜잭션에 참여할 수 있습니다. 그러면 업무 Rollback과 함께 ImageLog도 Rollback될 수 있습니다.

감사·장애 로그를 업무 Rollback과 무관하게 반드시 남겨야 한다면 별도 Bean에서 `REQUIRES_NEW`를 사용하는 방식을 검토할 수 있습니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    propagation = Propagation.REQUIRES_NEW
)
public void writeImageLog(...) {
    ...
}
```

단, 별도 트랜잭션을 같은 클래스 내부 호출로 사용하면 Proxy가 적용되지 않으므로 별도 Bean으로 분리해야 합니다.

## 10. `ServiceTransactionManager`의 정체

PDMK Framework에는 Spring `@Transactional`과 별도로 수동 트랜잭션 API가 있습니다.

[ServiceTransactionManager.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-fw/src/main/java/nhnis/fw/commons/transaction/ServiceTransactionManager.java>)

```java
private static ThreadLocal<TransactionManagerHolder>
    transactionManager = new ThreadLocal<>();
```

초기화:

[InitTransactionManager.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-fw/src/main/java/nhnis/fw/commons/transaction/InitTransactionManager.java>)

```java
PlatformTransactionManager txManager =
    applicationContext.getBean(transactionName);

TransactionManagerHolder holder =
    new TransactionManagerHolder(txManager);

ServiceTransactionManager.setInstance(holder);
```

개념적인 사용 방식은 다음과 같습니다.

```java
InitTransactionManager.initTransactionManager(
    "rdwTransactionManager"
);

TransactionManagerHolder holder =
    ServiceTransactionManager.getInstance();

TransactionStatus status =
    holder.beginTransaction();

try {
    dao.update();
    holder.commit(status);
} catch (Exception e) {
    holder.rollback(status);
    throw e;
} finally {
    ServiceTransactionManager.remove();
}
```

그러나 현재 `pdmk-service`에서는 이 수동 API를 사용하는 호출부가 발견되지 않았습니다.

따라서 현재는 트랜잭션 기반시설 코드만 존재하고 실질적으로 사용되지 않는 상태입니다.

## 11. 수동 TransactionManager 구현 문제

[TransactionManagerHolder.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-fw/src/main/java/nhnis/fw/commons/transaction/TransactionManagerHolder.java>)에는 사용 전 검토해야 할 문제가 있습니다.

### 정의 재사용 시 재귀 호출

```java
public TransactionStatus beginTransaction(
        String definitionName) {

    TransactionDefinition definition =
        definitionMap.get(definitionName);

    if (definition == null) {
        return beginTransaction(...);
    } else {
        return beginTransaction(definitionName);
    }
}
```

정의가 이미 존재하는 경우 자기 자신을 다시 호출하기 때문에 무한 재귀로 이어질 수 있습니다. 의도는 다음이었을 가능성이 큽니다.

```java
return beginTransaction(definition);
```

### 격리 수준이 덮어써짐

```java
definition.setIsolationLevel(isolationLevel);
definition.setIsolationLevel(-1);
```

전달받은 격리 수준을 설정한 뒤 다시 기본값 `-1`로 덮어씁니다. 결과적으로 호출자가 요청한 격리 수준이 적용되지 않습니다.

### 활성 트랜잭션 정리 문제

```java
public void release() {
    definitionMap.clear();
    txStack.clear();
}
```

Stack에 활성 `TransactionStatus`가 남아 있어도 Commit이나 Rollback 없이 목록만 비웁니다. 잘못 사용하면 Connection 및 트랜잭션 상태 관리 문제가 생길 수 있습니다.

### ThreadLocal 정리 책임

`ServiceTransactionManager`는 ThreadLocal을 사용하므로 모든 종료 경로에서 반드시 다음을 호출해야 합니다.

```java
ServiceTransactionManager.remove();
```

현재 요청 필터에서는 `ServiceContextHolder`만 제거하고 `ServiceTransactionManager.remove()`는 호출하지 않습니다.

수동 트랜잭션을 사용하기 시작하면 정리 누락으로 스레드 재사용 문제가 생길 수 있습니다.

결론적으로 현재 수동 TransactionManager는 수정과 테스트 없이 업무 코드에서 사용하면 안 됩니다.

## 12. 선언형과 수동 방식 비교

| 항목             | `@Transactional`  | `ServiceTransactionManager` |
| ---------------- | ----------------- | --------------------------- |
| 방식             | 선언형            | 직접 begin/commit/rollback  |
| 코드량           | 적음              | 많음                        |
| 예외 Rollback    | Spring이 처리     | 직접 처리                   |
| ThreadLocal 관리 | Spring 담당       | 애플리케이션 담당           |
| 중첩 전파        | 표준 Propagation  | 직접 Stack 관리             |
| 현재 상태        | 구성 가능, 미적용 | 구현 존재, 미사용·결함 있음 |
| 권장도           | 높음              | 특별한 경우에만             |

PDMK 업무에서는 Spring의 `@Transactional`을 우선 사용하는 것이 안전합니다.

## 14. 수정 후 필요한 테스트

- 정상 변경 거래가 Commit되는지
- 첫 SQL 성공 후 두 번째 SQL 실패 시 전체 Rollback되는지
- checked Exception에서도 Rollback되는지
- 조회 메서드에 쓰기 SQL이 실행되지 않는지
- 자기 호출로 트랜잭션이 누락되지 않는지
- ImageLog가 업무 Rollback 후에도 남는지
- 여러 동시 요청에서 Connection과 Context가 섞이지 않는지
- TransactionManager Bean 이름이 정확한지
- H2뿐 아니라 Oracle 환경의 격리 수준과 잠금 동작이 적절한지

핵심 결론은 `rdwTransactionManager`는 정상적으로 등록되어 있지만 현재 업무 Service에는 트랜잭션 경계가 적용되지 않았다는 점입니다. 신규 변경 업무는 Service 또는 Facade에 `@Transactional`을 적용하고, 기존 `ServiceTransactionManager` 수동 방식은 구현 결함을 수정하고 테스트하기 전까지 사용하지 않는 것이 적절합니다.
