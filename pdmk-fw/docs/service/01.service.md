현재 PDMK의 Service는 Controller에서 받은 입력 DTO를 DB 조회용 파라미터로 변환하고, DAO를 호출한 다음 조회 결과를 출력 DTO로 조립하는 역할을 합니다.

```text
Controller
  → Service
      ├─ 입력값 정리
      ├─ 기본값/업무조건 적용
      ├─ DAO 호출
      ├─ 결과 변환
      └─ 출력 DTO 생성
  → Controller
```

## 3. 입력값 정리

Service는 Controller로부터 입력 DTO를 받습니다.

```java
public mkcoa5530S0DTOout mkcoa5530S0(
    mkcoa5530S0DTOin input
)
```

입력값이 존재하고 공백이 아니면 DAO 파라미터 Map에 저장합니다.

```java
Map<String, Object> param = new HashMap<>();

if (input != null) {
    putIfHasText(param, "trtBrc", input.getTrtBrc());
    putIfHasText(param, "basDt", input.getBasDt());
}
```

공통 보조 메서드:

```java
private void putIfHasText(
        Map<String, Object> param,
        String key,
        String value) {

    if (value != null && !value.isBlank()) {
        param.put(key, value.trim());
    }
}
```

이 처리의 의미는 다음과 같습니다.

```text
null     → 조회조건에서 제외
""       → 조회조건에서 제외
"   "    → 조회조건에서 제외
" 001 "  → "001"로 정리하여 전달
```

MyBatis XML은 Map에 해당 키가 존재하는지에 따라 동적 SQL 조건을 구성합니다.

## 4. 페이징 처리

`mkcoa5530Service`와 `mkcoa8888Service`는 Service에서 페이징 기본값과 최대 크기를 통제합니다.

```java
int pageNo =
    input == null
    || input.getPageNo() == null
    || input.getPageNo() <= 0
        ? 1
        : input.getPageNo();

int pageSize =
    input == null
    || input.getPageSize() == null
    || input.getPageSize() <= 0
        ? 20
        : input.getPageSize();
```

페이지 크기는 최대 100건으로 제한합니다.

```java
if (pageSize > 100) {
    pageSize = 100;
}
```

조회 시작 위치:

```java
int offset = (pageNo - 1) * pageSize;
```

DAO 전달값:

```java
param.put("pageNo", pageNo);
param.put("pageSize", pageSize);
param.put("offset", offset);
```

예:

```text
pageNo=1, pageSize=20 → offset=0
pageNo=2, pageSize=20 → offset=20
pageNo=3, pageSize=20 → offset=40
```

출력 DTO에는 다음 페이징 정보를 설정합니다.

```java
output.setPageNo(pageNo);
output.setPageSize(pageSize);
output.setTotalCount(totalCount);
output.setTotalPages(
    (int) ((totalCount + pageSize - 1L) / pageSize)
);
```

## 6. 조회 결과 변환

현재 DAO 조회 결과는 다음 타입입니다.

```java
List<Map<String, Object>>
```

Service는 각 Map을 출력용 Sub DTO로 변환합니다.

```java
for (Map<String, Object> row : rows) {
    mkcoa5530S0DTOSub0 sub =
        new mkcoa5530S0DTOSub0();

    sub.setL5101(asString(row, "L5101", "l5101"));
    sub.setL5102(asString(row, "L5102", "l5102"));
    sub.setL5103(asString(row, "L5103", "l5103"));
    sub.setL5104(asString(row, "L5104", "l5104"));

    output.addmkcoa5530S0DTOSub0(sub);

```

`asString()`은 DB 또는 환경에 따른 컬럼명 대소문자 차이를 흡수합니다.

```text

H2:     l5101
기타:   대소문자를 무시하여 탐색
```

이는 H2와 Oracle 테스트 호환에는 도움이 되지만, Map 기반 결과는 컴파일 시 컬럼 오타를 잡을 수 없다는 단점이 있습니다.

더 명확한 구조는 MyBatis가 조회 결과를 전용 Row DTO로 직접 변환하도록 하는 것입니다.

## 9. Service와 ServiceContext

현재 Service 구현은 `ServiceContextHolder`를 직접 사용하지 않습니다. Controller에서 받은 업무 입력 DTO만 사용합니다.

이 구조는 Service를 HTTP 환경에서 분리하기 때문에 바람직합니다.

필요한 사용자나 거래 정보를 Service에서 사용해야 한다면 두 가지 방법이 있습니다.

권장 방식은 Facade 또는 Controller가 필요한 값만 명시적으로 전달하는 것입니다.

```java
String ssoId = requestContext.currentUserId();

service.execute(input, ssoId);
```

기존 방식으로 직접 접근할 수도 있습니다.

```java
ServiceContext context =
    ServiceContextHolder.getInstance();

String guid = context.getGuid();

String ssoId = (String) context
    .getHttpServletRequest()
    .getAttribute("ssoId");
```

하지만 이렇게 하면 Service가 Servlet과 ThreadLocal에 의존하여 단위 테스트와 비동기 실행이 어려워집니다.

## 10. 트랜잭션 처리 분석

RDW용 TransactionManager는 구성되어 있습니다.

[RdwDataSourceConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-service/src/main/java/nhnis/mk/config/RdwDataSourceConfig.java>)

```java
return new DataSourceTransactionManager(rdwDataSource);
```

그러나 현재 세 Service에서는 `@Transactional`을 사용하지 않습니다.

```java
@Service
public class mkcoa8888Service {
    // @Transactional 없음
}
```

조회 한 번 또는 단일 DELETE는 실행될 수 있지만, 여러 DB 작업을 하나의 원자적 거래로 묶는 Service 트랜잭션 경계는 현재 보이지 않습니다.

예를 들어 다음 업무가 추가된다면 트랜잭션이 필요합니다.

```text
계좌 테이블 UPDATE
  → 이력 테이블 INSERT
  → 통계 테이블 UPDATE
```

중간에 실패했을 때 전부 롤백하려면 Service에 RDW TransactionManager를 명시해야 합니다.

개념적인 예:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
public Output execute(Input input) throws Exception {
    dao.updateMain(input);
    dao.insertHistory(input);
    return output;
}
```

정확한 TransactionManager Bean 이름은 `RdwDataSourceConfig`의 Bean 선언을 기준으로 사용해야 합니다.

조회는 필요에 따라 다음처럼 지정할 수 있습니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
```

특히 현재 `mkcoa8888D0`는 삭제 거래이므로 업무 정책상 명시적인 트랜잭션 적용을 검토하는 것이 좋습니다.

## 11. 예외 처리

현재 Service 메서드는 대부분 다음과 같이 선언합니다.

```java
throws Exception
```

DAO 또는 변환 과정에서 예외가 발생하면 그대로 Controller 밖으로 전달됩니다.

```text
DAO 예외
  → Service throws Exception
  → Controller throws Throwable
  → 전역 예외 처리
  → 시스템 Exception ImageLog
```

하지만 `ResponseBodyArgumentResolver`의 명시적인 예외 변환 대상은 주로 `NhBaseException`입니다.

따라서 Service에서는 기술 예외를 업무적으로 의미 있는 공통 예외로 변환하는 방식을 고려할 수 있습니다.

```java
try {
    return dao.select(param);
} catch (DataAccessException e) {
    throw new NhBaseException(
        /* 표준 오류 코드와 원인 */
    );
}
```

주의할 점:

- SQL이나 내부 DB 메시지를 클라이언트에 노출하지 않기
- 원인 예외는 서버 로그에 남기기
- 조회 결과 없음과 시스템 오류를 구분하기
- 예외를 잡고 정상 응답 코드로 위장하지 않기
- 트랜잭션 롤백 대상 예외를 명확하게 지정하기

## 12. Service TX-FLOW 로그

`PdmkBizTxFlowAspect`가 Service 메서드 진입과 종료를 자동으로 기록합니다.

적용 Pointcut:

```java
execution(* nhnis.mk.co..service..*(..))
```

따라서 다음 메서드들은 자동 추적됩니다.

```text
mkcoa5530Service.mkcoa5530S0()
mkcoa8888Service.mkcoa8888S0()
mkcoa8888Service.mkcoa8888D0()
mkcoa9999Service.mkcoa9999S0()
```

Service에 직접 작성된 다음 로그는 공통 TX-FLOW 로그와 일부 중복됩니다.

```java
log.info("Service Start");
log.info("Service End");
```

업무상 의미 있는 건수나 상태만 Service에서 추가로 기록하는 것이 가독성이 좋습니다.

```java
log.info("조회 완료: totalCount={}", totalCount);
```

문자열 연결보다 파라미터 로그가 적절합니다.

```java
// 현재 형태
log.info("Total: " + totalCount);

// 권장 형태
log.info("Total: {}", totalCount);
```

## 14. 개선이 필요한 부분

### Facade와 Rule 계층 부재

현재 구조는 다음과 같습니다.

```text
Controller → Service → DAO
```

저장소 아키텍처 기준은 다음 구조입니다.

```text
Controller
  → Facade
    → Service
      → Rule
        → DAO/Mapper
```

현재 기능이 단순하므로 직접 호출도 동작하지만, 기능이 커지면 다음을 분리하는 것이 좋습니다.

- Facade: DTO 변환, 유스케이스 조정, 트랜잭션 경계
- Service: 업무 처리 흐름
- Rule: 입력 검증과 계산 규칙
- DAO: 데이터 접근

### Map 기반 DAO 계약

현재는 다음 타입에 의존합니다.

```java
Map<String, Object>
List<Map<String, Object>>
```

문제점:

- 파라미터 이름 오타를 컴파일 시 확인 불가
- SQL 컬럼 변경 영향 파악 어려움
- 반복적인 `asString()` 필요
- 값의 타입이 런타임까지 불명확

검색 조건과 조회 결과에 전용 클래스를 사용하면 더 안전합니다.

### 트랜잭션 경계 부재

- 현재 Service에 `@Transactional` 없음
- 다중 변경 작업 시 부분 반영 위험
- 삭제 거래의 명시적 트랜잭션 정책 필요

### 검증 정책 부족

현재는 null·공백·페이지 범위 정도만 처리합니다. 다음 규칙은 Rule 계층으로 분리할 수 있습니다.

- 날짜 형식
- GUID 형식과 길이
- 조회 기간 제한
- 허용된 서비스 코드
- 삭제 권한
- 최대 GUID 삭제 건수
- 영업점 접근 권한

### 예외 표준화 부족

일반 `Exception` 대신 의미 있는 예외 계약이 필요합니다.

```text
입력 오류       → Validation/BIZ 오류
조회 결과 없음  → 업무 정책에 따른 정상 빈 목록 또는 BIZ 오류
DB 오류         → 공통 시스템 오류
권한 오류       → AUTH 오류
```

## 15. 권장 Service 작성 형태

현재 구조를 크게 바꾸지 않는다면 다음 형태가 안전합니다.

```java
@Service
@RequiredArgsConstructor
public class CustomerInquiryService {

    private final CustomerInquiryDAO dao;
    private final CustomerInquiryRule rule;

    @Transactional(
        transactionManager = "rdwTransactionManager",
        readOnly = true
    )
    public CustomerInquiryOutput inquiry(
            CustomerInquiryInput input) {

        rule.validate(input);

        CustomerSearchCondition condition =
            CustomerSearchCondition.from(input);

        int totalCount = dao.count(condition);
        List<CustomerRow> rows = dao.select(condition);

        return CustomerInquiryOutput.of(
            rows,
            totalCount,
            condition.page()
        );
    }
}
```

핵심적으로 PDMK Service는 입력 조건 정리, 업무 규칙 수행, DAO 호출 조정, 결과 DTO 조립을 담당합니다. 현재 조회 기능은 비교적 일관되게 구현되어 있지만, 트랜잭션 경계·Rule 분리·예외 표준화·Map 기반 계약은 향후 실제 업무 확대 전에 보완할 부분입니다.
