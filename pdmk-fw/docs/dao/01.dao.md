## 2. `@RDWMapper` 역할

[RDWMapper.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-service/src/main/java/nhnis/mk/config/RDWMapper.java>)

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Mapper
public @interface RDWMapper {
}
```

`@RDWMapper`는 MyBatis의 `@Mapper`를 포함한 PDMK 전용 메타 어노테이션입니다.

```text
@RDWMapper
   └─ @Mapper
       └─ MyBatis Mapper 인터페이스로 인식
```

이름상 해당 Mapper가 RDW DataSource를 사용한다는 의미도 제공합니다.

```java

}
```

현재 `RdwDataSourceConfig`의 `@MapperScan`도 DAO 패키지를 스캔하므로 Bean 등록 측면에서는 일부 역할이 중복됩니다. 그래도 코드에서 RDW Mapper임을 명시하는 표식으로 사용할 수 있습니다.

## 5. SqlSessionFactory 설정

```java
@Bean
public SqlSessionFactory rdwSqlSessionFactory(
        DataSource rdwDataSource,
        MybatisLogInterceptor mybatisLogInterceptor)
        throws Exception {

    Configuration config = new Configuration();

    config.setJdbcTypeForNull(JdbcType.NULL);
    config.setCallSettersOnNulls(true);

    SqlSessionFactoryBean factory =
        new SqlSessionFactoryBean();

    factory.setDataSource(rdwDataSource);
    factory.setConfiguration(config);
    factory.setMapperLocations(...);
    factory.setPlugins(mybatisLogInterceptor);

    return factory.getObject();
}
```

주요 설정은 다음과 같습니다.

| 설정                      | 의미                                        |
| ------------------------- | ------------------------------------------- |
| `jdbcTypeForNull=NULL`    | null 파라미터 바인딩 시 JDBC NULL 사용      |
| `callSettersOnNulls=true` | 조회 컬럼이 null이어도 결과 객체/Map에 반영 |
| `mapperLocations`         | MyBatis XML 검색                            |
| `mybatisLogInterceptor`   | SQL 실행 로그 처리                          |
| `rdwDataSource`           | 실제 RDW DB 연결                            |


DAO:


## 8. 파라미터 전달

현재 DAO는 `Map<String, Object>`를 받습니다.

Service:

```java
Map<String, Object> param = new HashMap<>();

param.put("trtBrc", input.getTrtBrc());
param.put("basDt", input.getBasDt());
param.put("offset", offset);
param.put("pageSize", pageSize);

dao.mkcoa5530S0_S0(param);
```

XML에서는 Map의 키를 사용합니다.

```xml
<if test="trtBrc != null and trtBrc != ''">
    AND T1.L5104 = #{trtBrc}
</if>

<if test="basDt != null and basDt != ''">
    AND T1.L5103 = #{basDt}
</if>
```

```text

       ↕
#{trtBrc}
```

Map 키가 XML과 다르면 조건이 적용되지 않거나 바인딩 오류가 발생할 수 있습니다.

```java
param.put("treatBranch", value);
```

```xml
#{trtBrc}
```

위와 같이 이름이 다르면 정상 연결되지 않습니다.

## 9. SQL 파라미터 바인딩

현재 XML은 `#{...}`를 사용합니다.

```xml
AND T1.L5104 = #{trtBrc}
```

이는 PreparedStatement 파라미터 바인딩입니다.

개념적으로:

```sql
AND T1.L5104 = ?
```

```text
? ← trtBrc 값
```

따라서 입력값을 SQL 문자열에 직접 합치는 방식보다 SQL Injection에 안전합니다.

현재 LIKE 조건도 바인딩을 사용합니다.

```xml
AND T1.SERVICE_ID LIKE '%' || #{serviceId} || '%'
```

`serviceId`가 SQL 문자열로 직접 치환되는 것이 아니라 바인딩되므로 SQL Injection 위험을 줄입니다.

다음 방식은 피해야 합니다.

```xml
AND T1.SERVICE_ID LIKE '%${serviceId}%'
```

`${...}`는 문자열을 SQL에 직접 삽입하므로 외부 입력에 사용하면 안 됩니다.

## 12. 페이징 SQL

현재 Oracle `ROWNUM` 방식입니다.

```sql
SELECT *
FROM (
    SELECT a.*, ROWNUM rnum
    FROM (
        SELECT ...
        FROM ...
        ORDER BY ...
    ) a
    WHERE ROWNUM <= #{offset} + #{pageSize}
)
WHERE rnum > #{offset}
```

예를 들어:

```text
pageNo=3
pageSize=20
offset=40
```

실행 범위:

```text
ROWNUM <= 60
rnum > 40
→ 41~60번째 데이터
```

Local H2가 Oracle 호환 모드이므로 이 SQL을 최대한 비슷하게 검증할 수 있습니다. 다만 Oracle 실행계획과 성능까지 H2가 보장하지는 않습니다.

DAO 반환형:


예:

```java
Map<String, Object> row = Map.of(
    "L5101", "...",
    "L5102", "...",
```

- 컬럼명 오타를 컴파일 시 확인할 수 없음
- 값의 Java 타입이 불명확
- Service에 반복적인 변환 코드 발생
- SQL과 DTO의 계약 파악이 어려움

## 14. 삭제 처리

`mkcoa8888D0_D0`는 GUID 목록으로 ImageLog를 삭제합니다.

```xml
<delete id="mkcoa8888D0_D0"
        parameterType="java.util.HashMap">

    DELETE FROM TB_FW_IMAGE_LOG
    WHERE GUID IN

    <foreach
        collection="guidList"
        item="guid"
        open="("
        separator=","
        close=")">
        #{guid}
    </foreach>
</delete>
```

입력:

```java
param.put(
    "guidList",
    List.of("GUID01", "GUID02")
);
```

생성되는 SQL 개념:

```sql
DELETE
FROM TB_FW_IMAGE_LOG
WHERE GUID IN (?, ?)
```

Service에서 빈 목록을 먼저 차단하므로 현재 정상 흐름에서는 다음과 같은 잘못된 SQL이 만들어지지 않습니다.

```sql
WHERE GUID IN ()
```

그러나 Oracle에는 `IN` 목록 표현식의 개수 제한을 고려해야 합니다. Service에서 삭제 GUID 최대 개수를 제한하거나 일정 크기로 분할하는 것이 안전합니다.

또한 ImageLog 삭제는 감사 데이터 삭제이므로 다음 통제가 필요합니다.

- 관리자 권한 확인
- 삭제 가능한 보존기간 정책
- 최대 삭제 건수
- 삭제 사용자와 사유 기록
- 운영 직접 삭제 제한

현재 Service에서는 GUID 존재 여부만 검사하고 권한 통제는 확인되지 않습니다.

## 15. 트랜잭션 처리

RDW TransactionManager는 다음과 같이 등록됩니다.

```java
@Bean
@Primary
public PlatformTransactionManager
        rdwTransactionManager(
            DataSource rdwDataSource) {

    return new DataSourceTransactionManager(
        rdwDataSource
    );
}
```

하지만 현재 Service에는 `@Transactional`이 없습니다.

DAO는 트랜잭션 경계를 정의하는 계층이 아니라 이미 열린 트랜잭션 안에서 SQL을 실행하는 데이터 접근 계층으로 두는 것이 좋습니다.

권장 구조:

```java
@Service
public class ImageLogService {

    @Transactional(
        transactionManager = "rdwTransactionManager",
        rollbackFor = Exception.class
    )
    public DeleteOutput delete(DeleteInput input) {
        return dao.delete(input);
    }
}
```

특히 여러 DAO 작업이 하나의 업무 거래라면 Service 또는 Facade에 트랜잭션이 필요합니다.

```text
DAO A UPDATE 성공
DAO B INSERT 실패
      ↓
@Transactional 있음  → 둘 다 롤백
@Transactional 없음 → A만 반영될 가능성
```

조회 Count와 목록 조회도 완전히 같은 시점의 데이터를 보장해야 한다면 동일한 읽기 트랜잭션이나 격리 수준을 검토해야 합니다.

## 16. SQL 로그

`SqlSessionFactory`에 `MybatisLogInterceptor`가 등록됩니다.

```java
factory.setPlugins(mybatisLogInterceptor);
```

따라서 DAO 실행은 공통 MyBatis 로그 처리의 적용을 받습니다.

```text
Service 진입
  → DAO 진입 TX-FLOW
  → MyBatis SQL 로그
  → DB 실행
  → DAO 종료 TX-FLOW
```

SQL 로그에 실제 파라미터가 출력될 경우 다음 정보가 포함되지 않도록 주의해야 합니다.

- 개인정보
- 계좌번호
- 인증정보
- 비밀번호
- 토큰
- 대량 IN 목록

```xml
            resultType="java.util.HashMap">

        SELECT CUSTOMER_ID,
               CUSTOMER_NAME
          FROM TB_CUSTOMER
         WHERE BRANCH_CODE = #{branchCode}

    </select>

    <select id="countCustomers"
            parameterType="java.util.HashMap"
            resultType="int">

        SELECT COUNT(*)
          FROM TB_CUSTOMER
         WHERE BRANCH_CODE = #{branchCode}

</mapper>
```

연결 조건:

```text
DAO 클래스 전체 이름 = mapper namespace
DAO 메서드 이름      = SQL id
Map key              = #{파라미터명}
XML 위치             = classpath*:rdw.*/*.xml 패턴
```

## 19. 수정 시 함께 확인할 항목

DAO 또는 SQL을 수정할 때는 최소한 다음을 확인해야 합니다.

- DAO 메서드명과 XML `id`가 같은가
- DAO 전체 클래스명과 XML `namespace`가 같은가
- Service Map 키와 XML 파라미터명이 같은가
- `#{}` 바인딩을 사용하는가
- 목록과 Count의 WHERE 조건이 동일한가
- 정렬 기준이 결정적인가
- 페이징 쿼리가 Oracle과 H2에서 동작하는가
- SQL 결과 컬럼명이 Service 변환 코드와 일치하는가
- null 값 처리가 올바른가
- 대량 조회나 전체 테이블 조회 가능성이 없는가
- 수정·삭제 업무에 트랜잭션이 적용되는가
- 권한 없이 중요한 데이터를 변경할 수 없는가
- SQL 로그에 민감정보가 노출되지 않는가

## 20. 현재 DAO 구조의 핵심 평가

좋은 점:

- SQL을 XML로 분리
- `#{}` 파라미터 바인딩 사용
- 목록과 Count가 공통 WHERE를 재사용
- RDW DataSource와 SqlSession이 명확하게 구분됨
- Local H2 Oracle 호환 환경 제공
- 삭제 목록도 `<foreach>` 바인딩 사용

보완할 점:

- `Map<String, Object>` 계약으로 타입 안정성이 낮음
- `mkcoa9999` 조회에 페이징과 정렬이 없음
- ImageLog 삭제 권한과 최대 건수 통제가 보이지 않음
- Service 트랜잭션 경계가 없음
- Oracle 대량 `IN` 처리 제한 고려 필요
- H2 테스트만으로 Oracle SQL 성능을 보장할 수 없음
- DAO AOP가 MyBatis Proxy에도 의도대로 적용되는지 검증 필요

정리하면 PDMK DAO는 `@RDWMapper` 인터페이스와 MyBatis XML을 `namespace + SQL id`로 연결하고, `rdwSqlSessionTemplate`을 통해 RDW DB에 접근합니다. DAO는 SQL 실행과 결과 반환에만 집중하고, 검증·업무 판단·트랜잭션 경계·DTO 조립은 Service/Rule/Facade 계층에 두는 것이 적절합니다.
