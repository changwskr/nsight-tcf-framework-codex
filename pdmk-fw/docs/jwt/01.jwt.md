공유 비밀키를 이용해 JWT의 서명을 다시 계산하고, 토큰에 포함된 서명과 일치하는지 비교해서 검증합니다.

```text
JWT 발급 서버                         PDMK
─────────────                       ────
Header + Payload                    전달받은 Header + Payload
       ↓                                      ↓
공유 비밀키로 HMAC 서명              동일한 공유 비밀키로 서명 재계산
       ↓                                      ↓
JWT 생성                            토큰의 Signature와 비교
                                              ↓
                                      같음: 정상 / 다름: 거부
```

JWT는 다음 세 부분으로 구성됩니다.

```text
Base64URL(Header).Base64URL(Payload).Signature
```

예시:

```text
eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiJ1c2VyMDEiLCJ0eXBlIjoiQUNDRVNTIn0
.
AbCdEf123...
```

## 발급할 때

발급 서버는 Header와 Payload를 결합한 후 공유 비밀키로 HMAC 서명을 생성합니다.

개념적으로는 다음과 같습니다.

```text
Signature =
    HMAC-SHA256(
        Base64URL(Header) + "." + Base64URL(Payload),
        공유 비밀키
    )
```

그리고 세 값을 합쳐 JWT를 만듭니다.

```text
Header.Payload.Signature
```

공유 비밀키 자체는 JWT 안에 들어가지 않습니다.

## PDMK에서 검증할 때

[JwtProvider.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-fw/src/main/java/nhnis/fw/commons/jwt/JwtProvider.java>)에서 설정 문자열을 HMAC 키로 변환합니다.

```java
@Value("${jwt.secret}")
private String secret;

private SecretKey key;

@PostConstruct
public void init() {
    key = Keys.hmacShaKeyFor(
        secret.getBytes(StandardCharsets.UTF_8)
    );
}
```

요청으로 받은 JWT는 다음 코드로 검증합니다.

```java
public boolean validate(String token) {
    try {
        Jwts.parser()
            .verifyWith(key)
            .build()
            .parseSignedClaims(token);

        return true;
    } catch (Exception e) {
        return false;
    }
}
```

`parseSignedClaims(token)`을 호출하면 JJWT 라이브러리가 내부적으로 다음 작업을 수행합니다.

1. JWT의 Header, Payload, Signature를 분리합니다.
2. Header에 명시된 서명 알고리즘을 확인합니다.
3. `jwt.secret`으로 서명을 다시 계산합니다.
4. 계산된 서명과 JWT의 Signature를 비교합니다.
5. `exp` 만료시간 등 표준 Claim을 검사합니다.
6. 파싱이나 검증에 실패하면 예외를 발생시킵니다.

그래서 코드에서는 예외가 없으면 `true`, 예외가 발생하면 `false`를 반환합니다.

## 요청 처리 과정

클라이언트는 HTTP 헤더에 JWT를 넣습니다.

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

`DefaultFilter`가 `Bearer ` 부분을 제거합니다.

```java
String token = authorization.substring(7);
```

그리고 다음 순서로 검증합니다.

```java
if (!jwtProvider.validate(token)) {
    // 401 Unauthorized
}

if (!jwtProvider.isAccessToken(token)) {
    // type이 ACCESS가 아니면 401
}

String ssoId = jwtProvider.getSsoId(token);
request.setAttribute("ssoId", ssoId);
```

따라서 PDMK의 검증 범위는 다음과 같습니다.

| 검증 항목      | 처리                   |
| -------------- | ---------------------- |
| JWT 형식       | `parseSignedClaims()`  |
| HMAC 서명      | `verifyWith(key)`      |
| 만료시간 `exp` | JJWT 파싱 과정         |
| 토큰 종류      | `type == "ACCESS"`     |
| 사용자 식별    | `sub`를 `ssoId`로 추출 |

## 왜 위조할 수 없는가

공격자가 Payload의 사용자 ID를 변경하면 Payload 문자열이 달라집니다.

```json
{
  "sub": "admin",
  "type": "ACCESS"
}
```

하지만 공유 비밀키를 모르면 변경된 Payload에 맞는 올바른 Signature를 만들 수 없습니다. 따라서 PDMK가 같은 비밀키로 계산한 서명과 일치하지 않아 검증이 실패합니다.

주의할 점은 HMAC 방식에서는 발급 서버와 검증 서버가 모두 동일한 비밀키를 가지고 있다는 것입니다. 따라서 PDMK 서버의 키가 유출되면 공격자가 토큰을 직접 발급할 수도 있습니다. 검증 서버가 많거나 보안 분리가 중요하다면 발급 서버만 개인키를 보유하고 PDMK에는 공개키만 배포하는 RSA/ECDSA 방식이 더 안전합니다.
