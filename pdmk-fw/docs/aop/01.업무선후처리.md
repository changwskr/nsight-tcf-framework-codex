업무 선후 처리는 Controller의 실제 업무 메서드가 실행되기 전과 정상 종료된 후에 공통 업무 로그를 자동으로 기록하는 기능입니다.

현재 PDMK에서는 Spring AOP 기반의 `BizPrePostAspect`가 담당합니다.

```text
시스템 사전 처리
  → 업무 사전 처리
    → Controller
      → Service
        → DAO
      ← Service 결과
    ← Controller 결과
  → 업무 사후 처리
→ 시스템 사후 처리
```

## 1. 구현 위치

[BizPrePostAspect.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-service/src/main/java/nhnis/mk/co/common/BizPrePostAspect.java>)

Aspect는 다음 조건에서 활성화됩니다.

```java
@Aspect
@Component
@Order(100)
@ConditionalOnProperty(
    name = "nhnis.fw.commons.legacy-web.enabled",
    havingValue = "true",
    matchIfMissing = true
)
public class BizPrePostAspect {
}
```

설정:

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: true
```

현재 설정에서는 활성화되어 있습니다.

## 2. 적용 대상

Pointcut은 다음과 같습니다.

```java
@Pointcut(
    "execution(* nhnis.mk.co..controller..*(..))"
)
public void mkCoControllers() {
}
```

따라서 다음 조건을 충족하는 모든 메서드에 자동 적용됩니다.

- `nhnis.mk.co` 하위
- `controller` 패키지 하위
- 접근 제한자 및 반환형과 관계없이 모든 메서드

현재 적용 예:

```text
nhnis.mk.co.a.controller.mkcoa5530Controller
nhnis.mk.co.a.controller.mkcoa8888Controller
nhnis.mk.co.a.controller.mkcoa9999Controller
```

Controller에 별도의 어노테이션을 붙일 필요는 없습니다.

다만 `nhnis.mk.co`가 아닌 새로운 업무 패키지에 Controller를 만들면 현재 Pointcut의 적용을 받지 않습니다.

예:

```text
nhnis.mk.customer.controller   → 적용 안 됨
nhnis.mk.account.controller    → 적용 안 됨
nhnis.mk.co.a.controller       → 적용됨
```

새 업무 영역을 추가할 때는 Pointcut 범위를 함께 확인해야 합니다.

## 3. 업무 사전 처리

Controller 메서드 실행 전에 `@Before` Advice가 실행됩니다.

```java
@Before("mkCoControllers()")
public void before(JoinPoint joinPoint) {
    log.info(PdmkTxLog.bizPreStart());

    logBizPreProgress(joinPoint);

    log.info(PdmkTxLog.bizPreEnd());
    log.info(PdmkTxLog.bizProcessStart());
}
```

처리 순서:

```text
업무 사전처리 시작
  → GUID 출력
  → 서비스 ID 출력
  → Controller 메서드 출력
  → BRC 출력
업무 사전처리 종료
업무 처리 시작
```

### GUID 추출

`ServiceContext`에서 GUID를 가져옵니다.

```java
ServiceContext ctx =
    ServiceContextHolder.getInstance();

String guid = ctx != null
        ? ctx.getGuid()
        : null;
```

GUID는 앞 단계인 `DefaultFilter`와 `ServicePreventionInterceptor`에서 생성되어 있어야 합니다.

### 서비스 ID 추출

표준 헤더에서 서비스 ID를 가져옵니다.

```java
String serviceId =
    ctx.getHeader()
       .getSys_comm()
       .getRms_svc_c();
```

이를 통해 어떤 서비스 거래가 어떤 Controller를 호출했는지 연결할 수 있습니다.

### 호출 메서드 추출

AOP의 `JoinPoint`를 이용해 실행할 클래스와 메서드 이름을 구합니다.

```java
MethodSignature signature =
    (MethodSignature) joinPoint.getSignature();

String method =
    signature.getDeclaringType().getSimpleName()
    + "."
    + signature.getName();
```

예:

```text
호출: mkcoa5530Controller.selectMember
```

### BRC 추출

Controller 파라미터에서 다음 getter를 순서대로 찾습니다.

```java
getTrtBrc()
getBrc()
getBRC()
getL5104()
```

예를 들어 요청 DTO에 다음 메서드가 있다면:

```java
public String getBrc() {
    return brc;
}
```

Aspect가 Reflection을 통해 값을 꺼내 로그에 기록합니다.

```text
BRC: 001
```

어떤 getter도 없으면 `null`을 기록합니다.

이 방식은 기존 DTO와의 호환성에는 편리하지만, getter 이름에 의존하므로 신규 DTO의 필드명이 달라지면 BRC가 기록되지 않습니다.

## 4. 실제 업무 처리

사전 처리가 끝나면 Controller가 실행됩니다.

```java
@RestController
public class mkcoa5530Controller {

    public ResponseDto execute(RequestDto request) {
        return service.execute(request);
    }
}
```

Aspect가 업무 로직을 직접 호출하는 것은 아닙니다. Spring AOP가 Controller 메서드 호출 전후에 Advice를 자동으로 삽입합니다.

```text
BizPrePostAspect.before()
        ↓
Controller.execute()
        ↓
BizPrePostAspect.after()
```

## 5. 업무 사후 처리

Controller가 정상적으로 반환한 경우 `@AfterReturning`이 실행됩니다.

```java
@AfterReturning(
    pointcut = "mkCoControllers()",
    returning = "result"
)
public void after(
        JoinPoint joinPoint,
        Object result) {

    log.info(PdmkTxLog.bizProcessEnd());
    log.info(PdmkTxLog.bizPostStart());

    log.info(PdmkTxLog.bizResponseMessage());
    log.info(PdmkMessagePrinter.businessDto(result));

    log.info(PdmkTxLog.bizPostEnd());
}
```

처리 순서:

```text
업무 처리 종료
업무 사후처리 시작
  → 업무 응답 DTO 로그
업무 사후처리 종료
```

`returning = "result"`를 통해 Controller가 반환한 객체를 받습니다.

예:

```java
public CustomerResponse inquiry(...) {
    return response;
}
```

이 경우 `CustomerResponse`가 `result`로 전달되어 업무 응답 로그에 출력됩니다.

## 6. 예외가 발생하면

현재 업무 사후 처리는 `@AfterReturning` 방식입니다.

```java
@AfterReturning(...)
```

따라서 Controller에서 예외가 발생하면 업무 사후 처리는 실행되지 않습니다.

```text
업무 사전처리      실행
업무 처리 시작     실행
Controller         예외 발생
업무 처리 종료     실행 안 됨
업무 사후처리      실행 안 됨
시스템 예외처리    실행
```

예외 거래는 바깥쪽의 다음 계층에서 처리됩니다.

- `ServicePreventionInterceptor.afterCompletion()`
- `ImageLogHandler.exceptionImagelog()`
- 전역 Exception Handler
- `DefaultFilter`의 예외/정리 처리

로그에서 “업무 처리 시작”은 있지만 “업무 처리 종료”가 없다면 업무 수행 중 예외가 발생했을 가능성이 있습니다.

## 7. TX-FLOW Aspect와의 관계

Controller, Service, DAO 메서드의 진입·종료 흐름은 별도의 Aspect가 처리합니다.

[PdmkBizTxFlowAspect.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmk-service/src/main/java/nhnis/mk/co/common/PdmkBizTxFlowAspect.java>)

적용 대상:

```java
@Pointcut(
    "execution(* nhnis.mk.co..controller..*(..))"
    + " || execution(* nhnis.mk.co..service..*(..))"
    + " || execution(* nhnis.mk.co..dao..*(..))"
)
```

두 Aspect의 역할 차이는 다음과 같습니다.

| Aspect                         | 적용 범위              | 역할                                          |
| ------------------------------ | ---------------------- | --------------------------------------------- |
| `BizPrePostAspect`             | Controller             | 업무 거래 시작·종료, 요청 식별정보와 응답 DTO |
| `PdmkBizTxFlowAspect`          | Controller·Service·DAO | 클래스와 메서드별 진입·종료 흐름              |
| `ServicePreventionInterceptor` | 전체 HTTP 요청         | 시스템 사전·사후 처리                         |

실행 순서는 `@Order`로 결정됩니다.

```java
PdmkBizTxFlowAspect  @Order(50)
BizPrePostAspect     @Order(100)
```

숫자가 작은 `PdmkBizTxFlowAspect`가 바깥에서 감쌉니다.

```text
PdmkBizTxFlowAspect 진입
  → BizPrePostAspect 업무 사전
    → Controller 실행
  → BizPrePostAspect 업무 사후
→ PdmkBizTxFlowAspect 종료
```

## 8. 활용 측면

### 업무 거래 추적

GUID와 서비스 ID로 시스템 로그와 업무 로그를 연결할 수 있습니다.

```text
GUID: a123...
서비스: CustomerInquiryS01
호출: mkcoa5530Controller.inquiry
BRC: 001
업무 응답: CustomerResponse(...)
```

### 계층별 지연 위치 파악

TX-FLOW 로그와 함께 보면 어느 계층에서 시간이 소요됐는지 파악할 수 있습니다.

```text
Controller 진입
  Service 진입
    DAO 진입
    DAO 종료        ← DB 처리시간
  Service 종료      ← 업무 처리시간
Controller 종료     ← 전체 Controller 시간
```

### 공통 감사 로그

다음과 같은 업무 감사정보를 일관된 형식으로 기록할 수 있습니다.

- 실행 사용자
- 서비스 ID
- 거래 GUID
- 처리 영업점
- 호출 기능
- 처리 결과

다만 개인정보나 전체 응답 DTO를 기록할 때는 마스킹 정책이 필요합니다.

## 9. 신규 업무에 적용하는 방법

현재 구조를 그대로 사용하려면 Controller·Service·DAO를 Pointcut 대상 패키지에 배치합니다.

```text
nhnis.mk.co.{domain}.controller
nhnis.mk.co.{domain}.service
nhnis.mk.co.{domain}.dao
```

예:

```text
nhnis.mk.co.customer.controller
nhnis.mk.co.customer.service
nhnis.mk.co.customer.dao
```

Controller 요청 DTO에서 BRC 로그가 필요하면 현재 Aspect가 인식하는 getter 중 하나를 제공해야 합니다.

```java
public String getBrc() {
    return brc;
}
```

설정도 활성화되어 있어야 합니다.

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: true
```

## 10. 개선할 때 고려할 점

현재 구현에서 개선이 필요한 부분은 다음과 같습니다.

- `nhnis.mk.co`로 Pointcut이 고정되어 신규 업무 패키지가 빠질 수 있음
- BRC 추출이 Reflection과 특정 getter 이름에 의존
- 정상 반환만 처리하고 업무 예외 Advice가 없음
- 반환 DTO 전체 로깅에 개인정보가 포함될 수 있음
- Controller에만 업무 전후 처리가 적용되어 실제 트랜잭션 경계와 다를 수 있음
- Controller 내부에서 자체적으로 예외를 잡아 정상 응답으로 바꾸면 실패 거래가 정상 종료로 기록될 수 있음

구조를 확장한다면 패키지 이름보다 전용 어노테이션을 사용하는 방식도 고려할 수 있습니다.

```java
@PdmkBusinessTransaction
public ResponseDto execute(RequestDto request) {
    ...
}
```

이렇게 하면 패키지 위치와 관계없이 적용 대상을 명확하게 지정할 수 있습니다.

정리하면 업무 선후 처리는 `BizPrePostAspect`가 Controller 호출 전후에 GUID·서비스 ID·BRC·호출 메서드·응답 DTO를 자동 기록하는 구조이고, 세부 계층 호출 흐름은 `PdmkBizTxFlowAspect`가 보완합니다. 현재는 `nhnis.mk.co` 패키지에 한정되어 있다는 점이 가장 중요한 적용 조건입니다.
