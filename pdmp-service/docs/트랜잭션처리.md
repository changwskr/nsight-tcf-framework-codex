여기에는 이름이 비슷하지만 서로 다른 “트랜잭션”이 2개 있습니다.

## 1. `@TcfTransaction`: 요청 흐름 관리

[TCFAspect.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmp-service/src/main/java/nhnis/fw/tcf/aspect/TCFAspect.java>)는 DB의 commit/rollback을 담당하지 않습니다.

```java
@TcfTransaction(...)
```

이 애노테이션은 다음 공통 처리를 위한 표시입니다.

```text
요청
 ↓
STF: Header 검사, GUID 설정, 시작 로그
 ↓
Controller 실행
 ↓
Service 실행
 ↓
ETF: 성공·실패 응답 조립, 종료 로그
```

즉 `@TcfTransaction`의 “Transaction”은 하나의 업무 요청 또는 거래를 뜻합니다.

## 2. `@Transactional`: 실제 DB 트랜잭션

DB 트랜잭션은 [mpcoa9999Service.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmp-service/src/main/java/nhnis/mp/co/a/service/mpcoa9999Service.java>)가 담당합니다.

```java
@Service
@Transactional(readOnly = true)
public class mpcoa9999Service {
}
```

`readOnly = true`이므로 현재 Service의 모든 public 메서드는 조회 전용 트랜잭션으로 실행됩니다.

처리 순서는 다음과 같습니다.

```text
Controller가 Service 호출
 ↓
Spring 트랜잭션 프록시가 가로챔
 ↓
DB Connection 획득
 ↓
트랜잭션 시작
 ↓
Service → DAO → MyBatis SQL 실행
 ↓
정상 종료: 트랜잭션 종료
예외 발생: rollback
 ↓
Connection 반환
```

현재 목록·상세 기능은 `SELECT`만 사용하므로 실제 변경사항을 commit하지는 않습니다.

## 3. TransactionManager는 누가 만드는가

[RdwDataSourceConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmp-service/src/main/java/nhnis/mp/config/RdwDataSourceConfig.java>)에 DB 트랜잭션 관리자가 있습니다.

```java
@Bean
public PlatformTransactionManager rdwTransactionManager(
        DataSource rdwDataSource) {
    return new DataSourceTransactionManager(rdwDataSource);
}
```

이 관리자가 같은 DB 연결 안에서 SQL을 묶고 commit 또는 rollback을 수행합니다.

```text
@Transactional
      ↓
rdwTransactionManager
      ↓
rdwDataSource
      ↓
H2 또는 Oracle
```

MyBatis의 `SqlSessionTemplate`도 같은 `rdwDataSource`를 사용하므로 Service의 트랜잭션에 참여합니다.

## 4. 오류가 발생하면 어떻게 되는가

예를 들어 Service에서 다음 오류가 발생한다고 생각해 봅시다.

```java
throw new BizException("FW0003", ...);
```

처리 흐름은 다음과 같습니다.

```text
Service에서 BizException 발생
 ↓
@Transactional 프록시가 예외를 받음
 ↓
DB rollback
 ↓
예외를 바깥으로 다시 전달
 ↓
TCFAspect가 BizException을 받음
 ↓
ETF.businessFail() 호출
 ↓
표준 실패 JSON 반환
```

중요한 점은 `TCFAspect`가 예외를 잡기 전에 Service의 트랜잭션 프록시가 먼저 rollback을 처리한다는 것입니다.

따라서 TCF Aspect가 오류를 응답 객체로 바꿔도 DB rollback에는 문제가 없습니다.

## 5. 데이터를 저장하려면

현재 클래스 전체가 다음처럼 조회 전용입니다.

```java
@Transactional(readOnly = true)
```

나중에 등록·수정·삭제 메서드를 추가하면 해당 메서드에 별도로 쓰기 트랜잭션을 선언해야 합니다.

```java
@Transactional
public void saveSalesTip(...) {
    dao.insert(...);
    dao.update(...);
}
```

두 SQL 중 두 번째 SQL에서 오류가 발생하면:

```text
INSERT 성공
UPDATE 실패
 ↓
전체 rollback
 ↓
INSERT도 취소
```

이것이 DB 트랜잭션의 핵심인 “모두 성공하거나, 모두 취소”입니다.

정리하면:

```text
@TcfTransaction = 업무 요청의 시작·종료와 표준 응답 관리
@Transactional   = DB SQL의 commit·rollback 관리
```
