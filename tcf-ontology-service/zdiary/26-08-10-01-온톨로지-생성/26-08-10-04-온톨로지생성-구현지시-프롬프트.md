# tcf-ontology-service Ontology 1.0 구현 지시

`ONTOLOGY-ANALYSIS.md` 분석결과를 기준으로 `tcf-ontology-service`의 Ontology 1.0을 구현하라.

이번 작업의 목적은 기능을 많이 추가하는 것이 아니다.

**NSIGHT/PDMG의 아키텍처 지식을 Concept + Relation 구조로 정확히 표현하고, 실제 PDMG 프로그램 한 건을 End-to-End로 질의·역추적·검증할 수 있는 최소 Ontology Core를 완성하는 것**이다.

## 1. 작업 원칙

다음 원칙을 반드시 지켜라.

1. 기존 동작을 최대한 유지한다.
2. 대규모 리패키징을 하지 않는다.
3. Neo4j를 추가하지 않는다.
4. Apache Jena/RDF4J를 추가하지 않는다.
5. H2 영속화를 이번 단계에서는 구현하지 않는다.
6. YAML을 Source of Truth로 유지한다.
7. 기동 시 YAML을 Concept/Relation Graph로 로딩한다.
8. 기존 scan/seed/validate 기능을 최대한 재사용한다.
9. 기존 REST API를 깨지 않는다.
10. 새로운 `/query/**` API를 추가한다.

---

# 2. Concept Type과 Instance를 구분한다

Ontology Type은 다음을 우선 구현한다.

- System
- Business
- Function
- Program
- ServiceId
- Component
- Mapper
- SqlId
- Table
- Column

예:

Concept Type:

System
Business
Function
Program
ServiceId

Instance:

MG : System
CO : Business
A : Function
mgcoa8888 : Program
mgcoa8888S0 : ServiceId

Type과 Instance를 같은 개념으로 처리하지 마라.

---

# 3. 공통 Concept 모델

다음과 유사한 공통 모델을 설계한다.

OntologyConcept

필수 속성:

- id
- type
- name
- description
- attributes
- version
- status
- provenance

ID는 이름과 분리한다.

향후 여러 시스템이 들어와도 충돌하지 않도록 안정적인 ID 체계를 설계하라.

예:

system:MG

business:MG:CO

function:MG:CO:A

program:MG:CO:A:8888

service:mgcoa8888S0

component:nhnis.mg.co.a.entry.handler.mgcoa8888Handler

table:RDW:TB_FW_IMAGE_LOG

# 8. ServiceId Value Object

PDMG ServiceId는 11자리다.

구조:

대그룹 2

- 업무 2
- 기능 1
- 프로그램번호 4
- 처리구분 1
- 순번 1

예:

mgcoa8888S0

다음 속성으로 분해한다.

groupCode = mg
businessCode = co
functionCode = a
programNo = 8888
operationType = S
sequence = 0
fullServiceId = mgcoa8888S0

`ServiceIdParser`를 작성하고 단위테스트를 작성한다.

잘못된 ServiceId는 명확한 Validation Error를 반환해야 한다.

# 10. Query API

다음 API를 구현한다.

GET /api/ontology/query/service/{serviceId}/structure

목적:
ServiceId에서 시작하여 전체 Design Graph 조회

예상:

ServiceId
→ Handler
→ Facade
→ Service
→ DAO
→ Mapper
→ SQL
→ Table

GET /api/ontology/query/program/{programId}/services

Program이 제공하는 ServiceId 조회

GET /api/ontology/query/handler/{handler}/services

Handler가 담당하는 ServiceId 조회

GET /api/ontology/query/table/{table}/services

Table을 사용하는 ServiceId 역추적

GET /api/ontology/query/service/{serviceId}/tables

ServiceId가 사용하는 Table 조회

GET /api/ontology/query/business/{businessCode}/tree

Business
→ Function
→ Program
→ ServiceId

전체 트리 조회

# 12. Architecture Rule 검증

다음 Rule을 구현한다.

RULE-001
ServiceId는 11자리 형식이어야 한다.

RULE-002
모든 ServiceId는 최소 하나의 Handler와 연결되어야 한다.

RULE-003
Handler가 등록한 ServiceId와 Ontology 관계가 일치해야 한다.

RULE-004
Program은 최소 하나 이상의 ServiceId를 가져야 한다.

RULE-005
Service는 DAO 또는 Client 중 최소 하나의 하위 의존성을 가져야 한다.

RULE-006
DAO를 통해 DB 접근 시 Mapper 또는 SqlId 관계가 존재해야 한다.

결과:

ruleId
severity
target
message
evidence
source

형식으로 반환한다.
