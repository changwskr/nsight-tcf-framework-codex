너는 지금부터 NSIGHT/PDMG의 Ontology Architecture를 설계·구현하는 수석 Java 아키텍트다.

현재 저장소에 이미 생성된 `tcf-ontology-service`를 먼저 전체 분석하라.

중요:
처음부터 코드를 수정하지 마라.
먼저 현재 구조, 구현 수준, 부족한 기능을 분석한 뒤 구현계획을 작성하라.

## 1. 서비스 목적

`tcf-ontology-service`는 일반적인 업무 CRUD 서비스가 아니다.

이 서비스의 목적은 NSIGHT/PDMG에서 사용되는 다음 지식을 구조화하여 저장하고 조회하는 것이다.

## 3. ServiceId 규칙

PDMG ServiceId는 다음 11자리 구조를 기준으로 한다.

대그룹 2

- 업무 2
- 세부기능 1
- 프로그램번호 4
- 처리구분 1
- 순번 1

예:

mgcoa8888S0

Ontology에서는 ServiceId를 단순 문자열로만 저장하지 말고 다음 속성으로 분해 가능하게 설계한다.

- groupCode
- businessCode
- functionCode
- programNo
- operationType
- sequence
- fullServiceId

## 4. 전문 모델

PDMG 요청 전문의 기본 개념도 Ontology에 표현할 수 있게 한다.

RequestMessage
├─ Header : hdr_nhnis
│ └─ sys_comm
└─ Body : dto

특히 `rms_svc_c`는 ServiceId와 연결할 수 있어야 한다.

다음 관계를 고려한다.

Message
HAS_HEADER → Header

Message
HAS_BODY → DTO

HeaderField.rms_svc_c
IDENTIFIES → ServiceId

Ontology에서 단순 프로그램 호출 관계와 런타임 실행 관계를 구분하는 방안을 제시하라.

예:

## 6. 구현 원칙

현재 프로젝트 기술스택과 패키지 구조를 먼저 분석하라.

기존 프로젝트가 사용하는 Spring Boot, DB, MyBatis, Repository 패턴 등을 최대한 재사용하고 새로운 Graph DB나 외부 제품을 임의로 추가하지 마라.

Neo4j, RDF Store, Apache Jena 등의 도입이 필요하다고 판단되더라도 바로 추가하지 말고 다음을 먼저 비교하라.

1. 현재 DB만 이용하는 방식
2. RDF Triple 구조
3. Property Graph 구조

각 대안의 장단점과 NSIGHT 적용성을 분석한 뒤 추천안을 작성하라.

## 8. 향후 목적

향후 신규 시스템 구축 시 다음 형태로 사용하려 한다.

신규 요구사항
→ Ontology 검색
→ 기존 유사업무 탐색
→ 기존 Architecture Pattern 탐색
→ 적용 가능한 ServiceId/프로그램 패턴 조회
→ 신규 시스템 Architecture Baseline 생성
→ LLM/자동 Harness에 Context 제공

따라서 현재 설계는 단순 CRUD 데이터 모델이 아니라
향후 Architecture Knowledge Base로 확장 가능해야 한다.
