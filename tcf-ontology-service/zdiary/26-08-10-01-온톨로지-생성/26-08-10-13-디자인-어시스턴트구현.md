Architecture Design Assistant 구현을 재개하라.

단, 다음 P1 항목을 먼저 처리한 뒤 Design 기능을 진행한다.

## 1. Gate 대상 스코프

현재 `/validate/rules`는 전체 Ontology를 검증한다.

Architecture Design Assistant에서는 선택한 ServiceId 또는 Design Baseline만 검증할 수 있어야 한다.

다음을 설계하라.

- 전체 검증
- ServiceId 단위 검증
- Design-Time Baseline 검증

가능하면 다음과 같이 분리한다.

GET /api/ontology/validate/rules
GET /api/ontology/validate/service/{serviceId}

Design 단계에서는 아직 구현되지 않은 Handler/DAO 등을 무조건 FAIL 처리하지 말고 다음 상태를 지원한다.

- PASS
- FAIL
- NOT_YET_IMPLEMENTED
- UNRESOLVED
- NOT_APPLICABLE

## 2. Program AUTO 검색 수정

Workbench의 자동 타입 감지에서

mgcoa8888

이 Program으로 정확히 인식되는지 수정한다.

PDMG Program 형식을 기준으로 테스트를 추가한다.

정상 예:

mgcoa8888

ServiceId:

mgcoa8888S0

두 형식을 AUTO 검색에서 명확히 구분하라.

---

## 3. RecommendService 개선

현재 OntologyRegistry/YAML 휴리스틱 점수만으로 추천하지 말고 다음 정보를 함께 사용한다.

- Business
- Function
- Operation Type
- Program
- ServiceId
- Component Relation
- DB Access
- Mapper/Table
- Paging metadata
- Transaction metadata
- Provenance
- Architecture Rule

추천 결과마다 다음을 반환한다.

- candidateId
- candidateType
- confidence
- matchedAttributes
- unmatchedAttributes
- evidence
- provenance
- status

confidence는 HIGH / MEDIUM / LOW를 기본으로 사용한다.

설명 불가능한 99.8% 같은 정밀 점수는 사용하지 않는다.

---

## 4. Evidence 정책

추천 결과에는 반드시 다음 근거를 제공한다.

- sourceType
- sourcePath
- verificationStatus
- discoveredBy
- referenceProgram
- referenceServiceId

추측 경로는 VERIFIED로 처리하지 않는다.

YAML에서 발견만 된 경우:

DISCOVERED

실제 Scanner가 Source를 확인한 경우:

VERIFIED

로 구분한다.

---

## 5. Classification 정합성

ServiceId 문자열을 파싱해서 가상의 관계를 만드는 것과 실제 Ontology Relation을 구분한다.

실제 관계가 Graph에 존재하면 VERIFIED relation으로 사용한다.

파싱으로 유도한 값은 필요 시:

INFERRED

또는

DERIVED

상태로 명확히 표시한다.

## 7. Pattern 정책

기존 Ontology에 확정 Pattern이 없으면:

DERIVED_PATTERN

으로 표시한다.

기존 Program/ServiceId에서 추출했음을 Evidence로 보여준다.

예:

ONLINE_PAGING_QUERY

Derived From:

- mgcoa5530S0
- mgcoa9000S0

---

## 8. UNRESOLVED 정책

Ontology에 없는 정보는 임의 생성하지 않는다.

예:

ProgramId = UNRESOLVED
ServiceId = UNRESOLVED
Table = UNRESOLVED
PersonalDataPolicy = UNRESOLVED

---

## 9. Golden Scenario

다음 입력으로 실제 테스트한다.

Business = CO
Function = A
Transaction = QUERY
DB = YES
Paging = YES

실제 Ontology에서 Candidate를 찾아야 한다.

Candidate 선택 후:

ServiceId
→ Handler
→ Facade
→ Service
→ DAO
→ Mapper
→ Table

구조와 Evidence를 표시한다.
