새로운 기능을 추가하지 마라.

현재 `ONTOLOGY-CHECK-REPORT.md`의 최종 승인만 수행한다.

보고서에서 다음 모순이 있다.

- Test E에서는 Table Impact가 PARTIAL로 기록됨
- affectedHandlers / affectedPrograms / affectedBusinesses가 빈 배열이었음
- 코드 품질에서도 Impact 계층 수집 문제가 P0로 기록됨
- 그런데 최종 판정에서는 Impact Analysis와 Reverse Query가 PASS로 기록됨

따라서 P0 수정 여부를 실제 실행 결과로 다시 증명하라.

## 1. 서버를 새로 기동

clean 상태에서 다음을 수행하라.

gradlew.bat clean test
gradlew.bat war
gradlew.bat bootRun

각 명령의 실제 결과를 기록하라.

## 2. 다음 API를 실제 호출

GET /api/ontology/impact/table/TB_FW_IMAGE_LOG

실제 JSON Response 전체를 저장하라.

최소 다음 결과가 비어 있지 않아야 한다.

- affectedMappers
- affectedDaos
- affectedServices
- affectedFacades
- affectedHandlers
- affectedServiceIds
- affectedPrograms
- affectedBusinesses

가능하면 `paths`도 반환하라.

## 3. 기대하는 역추적 구조

실제 Ontology 관계가 존재하는 범위에서 다음 경로를 증명하라.

TB_FW_IMAGE_LOG
← Mapper / SqlId
← DAO
← Service
← Facade
← Handler
← ServiceId
← Program
← Function
← Business
← System

관계가 실제로 존재하지 않는 단계는 임의 생성하지 말고 FAIL 또는 NOT_AVAILABLE로 표시하라.

## 5. Provenance도 다시 확인

다음 Relation:

mgcoa8888S0
HANDLED_BY
mgcoa8888Handler

에 대해

- sourceType
- sourcePath
- discoveredBy
- verificationStatus

를 출력하라.

`discoveredBy`가 실제 로더 또는 Scanner와 일치하는지 확인하라.

## 6. Git 상태도 확인

현재 보고서에는 `tcf-ontology-service/` 전체가 untracked라고 되어 있다.

다음을 출력하라.

git status
git diff --stat
git ls-files tcf-ontology-service

Ontology 1.0의 공식 Baseline을 만들 수 있는 상태인지 판단하라.

아직 Commit하지는 마라.

## 7. 최종 판정 기준

다음 조건을 모두 만족할 때만:

A. Ontology Core 1.0 완료

로 판정한다.

하나라도 만족하지 않으면:

B. 핵심 보완 후 완료 가능

으로 판정한다.

특히 Table → Business 전체 역추적 결과가 실제 API Response로 증명되지 않으면 A로 판정하지 마라.

검증 결과는

`ONTOLOGY-FINAL-ACCEPTANCE-REPORT.md`

로 작성하라.
