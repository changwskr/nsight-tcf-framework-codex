새 기능을 추가하지 말고 현재 구현의 완성도를 증명하는 데 집중하라.

실제 기동 로그의 핵심 결과를 보고서에 기록하라.

## 4. 가장 중요한 기능 검증

다음 질문에 API 또는 테스트 코드가 실제로 답할 수 있는지 검증하라.

### 테스트 A

`mgcoa8888S0`의 전체 구조를 조회하라.

최소 다음 관계가 보여야 한다.

```text
MG
→ CO
→ A
→ mgcoa8888
→ mgcoa8888S0
→ Handler
→ Facade
→ Service
→ DAO
→ Mapper/SQL
→ Table
```

실제 확인되지 않는 관계는 임의로 만들어 결과에 넣지 마라.

각 관계의 출처도 함께 표시하라.

### 테스트 B

`mgcoa8888`이 제공하는 ServiceId 목록을 조회하라.

예상:
`mgcoa8888S0` 등 실제 등록된 ServiceId

### 테스트 C

`mgcoa8888Handler`가 처리하는 ServiceId 목록을 조회하라.

### 테스트 D

`mgcoa8888S0`가 사용하는 Table을 조회하라.

### 테스트 E

위 Table에서 역방향으로 영향도를 조회하라.

최소 목표:

```text
Table
← Mapper/SQL
← DAO
← Service
← Facade
← Handler
← ServiceId
← Program
← Business
```

각 테스트에 대해 다음을 기록하라.

- 호출 URL 또는 테스트 메서드
- 실제 Request
- 실제 Response
- PASS / FAIL
- 실패 원인

## 5. ServiceId 검증

다음을 검증하라.

정상:

```text
mgcoa8888S0
```

분해 결과:

```text
groupCode = mg
businessCode = co
functionCode = a
programNo = 8888
operationType = S
sequence = 0
```

비정상 ServiceId도 최소 3개 테스트하라.

예:

- 자리수 오류
- 처리구분 오류
- 프로그램번호 오류

비정상 값이 정상 등록되는지 확인하라.

## 6. Architecture Rule 검증

다음 오류를 일부러 만들어 테스트하라.

### Case 1

ServiceId는 있는데 Handler 관계가 없음

기대:
ERROR

### Case 2

Handler는 있는데 ServiceId 등록관계가 없음

기대:
ERROR

### Case 3

Program은 있는데 ServiceId가 없음

기대:
ERROR

### Case 4

Service는 있는데 DAO 또는 Client 관계가 없음

기대:
ERROR 또는 WARNING

### Case 5

DAO는 있는데 Mapper/SQL 관계가 없음

기대:
ERROR 또는 WARNING

검증 결과에 Rule ID와 Evidence가 표시되어야 한다.

## 7. Provenance 점검

다음 관계를 선택한다.

```text
mgcoa8888S0
HANDLED_BY
mgcoa8888Handler
```

그리고 이 관계에 대해 다음 질문에 답하라.

- 어디에서 얻은 정보인가?
- 실제 Java 소스인가?
- Markdown인가?
- 자동 Scanner인가?
- 어느 파일인가?
- 언제 수집했는가?
- VERIFIED 상태인가?

이 질문에 답할 수 없다면 Provenance 기능은 미완료로 판정하라.

## 9. 코드 품질 확인

다음을 점검하라.

- Controller에 비즈니스 로직이 들어갔는가
- Graph 탐색 코드가 중복되었는가
- Concept/Relation 모델이 특정 `mgcoa8888`에 하드코딩되었는가
- ServiceId 파싱 코드가 여러 곳에 중복되는가
- YAML 파싱 모델과 Domain 모델이 과도하게 결합되었는가
- Runtime Graph와 Design Graph가 혼재하는가
- 테스트가 실제 관계를 검증하지 않고 Mock만 검증하는가

발견한 문제를 P0/P1/P2로 분류하라.
