## 10. 전문 분석 결과

[10.전문.md](./10.전문.md)의 기본 요청 구조와 처리 흐름은 맞습니다. 다만 실제 구현을 보면 오류 응답 형식(`result` vs `dto`), 헤더 보강, Filter 단계 오류, DTO 변환 방식에 대한 수정이 필요합니다.

## 1. 실제 전문 구조

PDMG 온라인 전문은 다음 구조입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa8888S0",
      "std_gbl_id": "...",
      "tr_sysid": "PDMG",
      "tr_trm_ipadr": "127.0.0.1",
      "tr_brc": "10001",
      "scid": "mgcoa8888",
      "optr_eno": "E0000001"
    }
  },
  "dto": {
    "pageNo": 1,
    "pageSize": 20
  }
}
```

구조적으로는 두 영역입니다.

```text
hdr_nhnis
  └─ sys_comm      시스템 공통정보

dto                업무별 입력·출력정보
```

이 설명은 문서와 실제 구현이 일치합니다.

---

## 2. 요청 전문의 실제 처리 흐름

```text
클라이언트 JSON
  ↓
DefaultFilter
  ├─ 요청 Body 캐시
  ├─ hdr_nhnis → 헤더 DTO 변환
  ├─ 누락된 공통값 보강
  ├─ 원문 → ServiceContext.requestBody
  └─ ThreadLocal ServiceContext 생성
  ↓
ServicePreventionInterceptor
  ├─ 공통 헤더 확인
  ├─ 요청 전문 로그
  └─ ImageLog 시작 처리
  ↓
OnlineTransactionController
  ├─ serviceId 결정
  ├─ request["dto"] 추출
  └─ TcfFacade.process(serviceId, dto)
  ↓
Handler → BusinessFacade → Service
```

[`OnlineTransactionController.java`](../../pdmg-fw/src/main/java/nhnis/fw/tcf/web/OnlineTransactionController.java)는 전체 JSON 중 `dto`만 추출합니다.

```java
Object dtoBody = request == null ? null : request.get("dto");

return tcfFacade.process(serviceId, dtoBody);
```

따라서 Handler 이후 업무 계층은 `hdr_nhnis`를 전달받지 않습니다.

공통 헤더가 필요한 경우 다음과 같이 `ServiceContext`에서 접근합니다.

```java
ServiceContext context = ServiceContextHolder.getInstance();

String guid = context.getGuid();
String serviceId =
    context.getHeader().getSys_comm().getRms_svc_c();
String userId =
    context.getHeader().getSys_comm().getOptr_eno();
```

업무 DTO와 시스템 헤더의 접근 경로가 분리된 구조입니다.

---

## 3. 서비스 ID 결정 주의사항

실제 서비스 ID 결정 순서는 다음과 같습니다.

```text
1. ServiceContext의 rms_svc_c
2. 요청 JSON의 hdr_nhnis.sys_comm.rms_svc_c
3. URL path의 serviceId
```

따라서 요청 URL과 헤더가 다르면 헤더가 우선합니다.

```text
POST /mgcoa8888S0

rms_svc_c = mgcoa8888D0
```

이 요청은 조회 `S0`가 아니라 삭제 `D0`로 라우팅될 수 있습니다.

문서의 다음 표현:

```text
rms_svc_c / URL = 서비스 ID
```

은 업무 표준으로는 맞지만 현재 코드가 일치를 강제하지는 않습니다. “동일하게 보내야 한다”와 “FW가 동일 여부를 검증한다”를 구분해야 합니다.

---

## 4. 로컬 헤더 합성

[`DefaultFilter.java`](../../pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java)의 동작은 다음과 같습니다.

### local 프로파일

다음 요청도 허용됩니다.

```json
{
  "dto": {
    "pageNo": 1,
    "pageSize": 20
  }
}
```

Filter가 합성하는 주요 값은 다음과 같습니다.

```text
std_gbl_id  ← UUID 생성
rms_svc_c   ← URL 마지막 경로
scid        ← 서비스 ID에서 유도
tr_trm_ipadr← 요청 IP
optr_eno    ← LOCAL
tr_sysid    ← spring.application.name
```

### local 이외 프로파일

- Bearer Access Token 필요
- 요청 Body 필요
- 정상 JSON이어야 함
- `hdr_nhnis`가 반드시 있어야 함

다만 “완전한 모든 `sys_comm` 필드가 필수”인 것은 아닙니다. 헤더가 있으면 일부 누락값을 Filter가 보강합니다.

## 5. 성공 응답 조립

성공 시 업무 Facade가 반환한 DTO는 `ResponseBodyAdvice`가 다음 구조로 감쌉니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "...": "..."
    }
  },
  "dto": {
    "...업무 응답...": "..."
  }
}
```

[`ResponseBodyArgumentResolver.java`](../../pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java)가 담당합니다.

```java
responseBody.set("hdr_nhnis", headerNode);
responseBody.set("dto", bodyNode);   // 성공(업무)만
```

문서에서 “요청 헤더 echo”라고 표현한 부분은 다음처럼 수정하는 것이 정확합니다.

```text
요청 헤더 원문을 그대로 반환하는 것이 아니라,
ServiceContext에 저장되고 처리 중 보강·변경된 헤더 객체를 응답에 사용한다.
```

응답으로 변환된 전문은 다시 다음 위치에 저장됩니다.

```java
ServiceContextHolder.getInstance().setResponseBody(...);
```

따라서 ImageLog 후처리에서 조립된 응답 전문을 사용할 수 있습니다.

## 6. 오류 응답 설명이 실제 코드와 다름

문서에는 다음과 같이 되어 있습니다.

```text
성공: { hdr_nhnis, dto }
실패: NH_NIS_ERR_DTO
```

그리고 성공과 실패의 스키마가 다르다고 설명합니다. 하지만 현재 `ResponseBodyAdvice`가 활성화된 경우 오류도 `hdr_nhnis` 봉투로 감싸되, **업무 `dto`가 아니라 `result`** 에 실립니다.

[`ResponseBodyArgumentResolver.java`](../../pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java)

```java
if (body instanceof NH_NIS_ERR_DTO) {
    responseBody.set("result", errorJson);  // 실패
} else {
    responseBody.set("dto", bodyNode);      // 성공
}
```

따라서 Controller 이후 발생한 일반적인 오류 응답은 실제로 다음 형태입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa8888S0"
    }
  },
  "result": {
    "stdErrCode": "E9999",
    "stdErrMsgCntn": "등록되지 않은 serviceId입니다.",
    "errType": "SERVICE"
  }
}
```

즉, 정확한 설명은 다음과 같습니다.

```text
성공: hdr_nhnis + dto(업무 DTO)
실패: hdr_nhnis + result(NH_NIS_ERR_DTO)

dto  = 업무 전용
result = 오류 전용
```

현재 설정에서도 Advice가 활성화되어 있습니다.

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: true
```

## 7. Filter 오류는 표준 오류 전문이 아니다

더 중요한 예외가 있습니다.

다음 오류는 Controller에 진입하기 전에 `DefaultFilter.sendError()`로 종료됩니다.

- Access Token 없음
- JWT 검증 실패
- 요청 Body 없음
- JSON 파싱 실패
- non-local 환경에서 `hdr_nhnis` 없음
- Filter 내부 예외

예:

```java
response.sendError(
    HttpServletResponse.SC_BAD_REQUEST,
    "공통 Header 정보가 없습니다."
);
```

이 경우 `GlobalExceptionHandler`와 `ResponseBodyAdvice`를 거치지 않을 수 있으므로 다음 표준 형태가 보장되지 않습니다.

```json
{
  "hdr_nhnis": {},
  "result": {
    "stdErrCode": "..."
  }
}
```

Servlet Container 또는 Spring Boot 기본 오류 JSON이 내려갈 가능성이 있습니다.

따라서 현재 시스템에는 오류 응답 형식이 두 종류 존재합니다.

| 발생 위치                   | 응답 형태                            |
| --------------------------- | ------------------------------------ |
| Filter 이전·내부            | Servlet 기본 오류 응답 가능          |
| Controller/TCF/Handler 이후 | `hdr_nhnis + result(NH_NIS_ERR_DTO)` |
| Timeout                     | 동일 오류 봉투, HTTP 504             |
| 과부하                      | 동일 오류 봉투, HTTP 503             |

전문 규격을 완전히 통일하려면 Filter에서 `sendError()`를 쓰지 않고 공통 오류 전문을 직접 작성하거나 전용 오류 응답 Writer를 사용해야 합니다.

---

## 8. HTTP 상태코드

오류는 모두 HTTP 500으로 처리되는 것이 아닙니다.

[`GlobalExceptionHandler.java`](../../pdmg-fw/src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java) 기준:

| 오류             | HTTP 상태 | 오류 코드       |
| ---------------- | --------: | --------------- |
| Handler 없음     |       500 | `E9999`         |
| 업무 예외        |       500 | 업무 오류 코드  |
| 온라인 Timeout   |       504 | `FW_TIMEOUT`    |
| Executor 과부하  |       503 | `FW_OVERLOADED` |
| Token 없음·실패  |       401 | Filter 오류     |
| Body/Header 오류 |       400 | Filter 오류     |

UI는 HTTP 상태와 응답 Body를 모두 본다. 서비스 오류 본문은 **`result.stdErrCode`** 이며, `dto`는 업무 전용이다. (`error-popup.js`의 `errorPayload`는 `result`만 사용)

## 9. DTO 변환 방식

온라인 공통 Controller는 요청 `dto`를 우선 `Map<String,Object>` 형태로 Handler에 전달합니다.

그 후 Facade에서 업무 DTO로 변환합니다.

```text
JSON dto
  ↓ Jackson
Map<String, Object>
  ↓ MappingUtil
mgcoa8888S0DTOin
```

그러므로 다음 검증이 별도로 필요합니다.

- 필수 필드 누락
- 문자열 길이
- 숫자 범위
- 날짜 형식
- 페이지 범위
- 알 수 없는 필드
- null 허용 여부

현재 공통 Controller 자체에는 `@Valid` 기반 업무 DTO 검증이 없습니다. 각 Facade, Service 또는 Rule 계층에서 업무 검증을 수행해야 합니다.

## 10. 응답 필드 제거 로직 주의

응답 Advice는 DTO를 JSON으로 변환하면서 다음 필드를 재귀적으로 제거합니다.

```text
dtoLogicalName
fieldPropertyMap
이름이 List로 끝나는 모든 필드
이름이 Array로 끝나는 모든 필드
```

문제는 업무적으로 정상적인 필드까지 제거될 수 있다는 점입니다.

```java
private List<String> customerList;
private String[] guidArray;
```

이 필드들은 실제 업무 응답에 필요하더라도 응답 전문에서 사라질 수 있습니다.

메타데이터 제거가 목적이라면 이름 suffix로 제거하기보다는 실제 SuperSpring 내부 메타 필드만 명시적으로 제거하는 것이 안전합니다.

## 11. 보안상 확인할 부분

레거시 `NhBaseException` 처리에서는 Stack Trace 상위 15개를 `NH_NIS_ERR_DTO`에 넣습니다.

```java
errorDto.setStackTrace(getTop15StackTrace(e.getStackTrace()));
```

이는 운영 환경에서 다음 정보를 클라이언트에 노출할 수 있습니다.

- 내부 클래스명
- 패키지 구조
- 메서드명
- 파일명
- 소스 라인
- 프레임워크 내부 호출 구조

프로젝트 보안 지침상 Stack Trace는 로그에만 기록하고 외부 응답에서는 제거하는 것이 적절합니다.

## 12. UI 호출 경로와 Relay

현재 샘플 화면(mgcoa/imagelog 등)의 **주 경로**는 브라우저가 `PdmgServiceClient`로 `pdmg-service/{serviceId}`에 직접 POST하는 방식입니다(CORS).

[`TransactionRelayService.java`](../../pdmg-ui/src/main/java/nhnis/mg/ui/client/TransactionRelayService.java)와 `/api/relay/{serviceId}`는 UI에 남아 있으나 **대안 경로**입니다. Relay는 요청 전문 문자열을 그대로 전송합니다.

```java
.body(requestBody == null ? "{}" : requestBody)
```

따라서 문서의 “UI Relay는 Body를 수정하지 않는다”는 설명은 Relay 경로에 한해 맞습니다. 주 경로 설명은 브라우저 직접 호출로 써야 합니다.

Relay를 쓸 때 다음 값은 서로 독립적으로 구성됩니다.

```text
Relay URL의 transactionId / serviceId
Catalog에 등록된 실제 path
전문 안의 rms_svc_c
```

세 값의 일치 여부를 UI Relay가 검증하지 않으므로 잘못된 전문이 전달될 수 있습니다.

## 최종 평가

문서 정확도는 약 70~75%입니다. 요청 구조와 계층별 책임은 잘 설명되어 있지만 다음 내용을 우선 수정해야 합니다.

1. 실패 응답을 `hdr_nhnis + result(NH_NIS_ERR_DTO)`로 정정 (`dto`는 업무 전용)
2. Filter 오류는 표준 오류 전문을 보장하지 않는다고 명시
3. HTTP 500·503·504·401·400 상태 구분 추가
4. 응답 헤더는 단순 echo가 아니라 보강된 `ServiceContext.header`라고 수정
5. `rms_svc_c`와 URL 불일치를 코드가 검증하지 않는다는 점 추가
6. `dto`가 먼저 Map으로 전달된 뒤 업무 DTO로 변환된다는 점 추가
7. 응답의 `*List`, `*Array` 제거 위험 추가
8. 오류 전문 Stack Trace 외부 노출 문제 추가
9. UI 주 경로를 브라우저 직접 호출(+CORS)로 명시 (Relay는 대안)

가장 정확하게 요약하면 다음과 같습니다.

```text
PDMG 전문
  요청 = hdr_nhnis + dto
  성공 = 보강된 hdr_nhnis + 업무 dto
  실패 = 보강된 hdr_nhnis + result(NH_NIS_ERR_DTO)

단, Filter에서 종료되는 인증·JSON·헤더 오류는
동일한 표준 오류 봉투가 보장되지 않는다.
```

이번 분석에서는 검증 문서의 형식·문체를 유지한 채 잘못된 전제만 수정했습니다.
