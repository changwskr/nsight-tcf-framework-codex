## 1. 최종 결론

현재 의도된 트랜잭션 구조는 다음과 같습니다.

```text
요청 스레드
  → Filter
  → OnlineTransactionController
  → TcfFacade
  → TimeoutExecutor 호출
       ↓ 별도 작업 스레드
       TransactionTemplate로 TX 시작
         → Dispatcher
         → Handler
         → Business Facade
         → Service
             → 업무 선처리
             → Service 본문
             → 업무 후처리
         → DAO / Mapper
       정상 종료: Commit
       예외/타임아웃: Rollback
```

즉, 타임아웃 기능이 활성화된 TCF 거래에서는 `TimeoutExecutor`가 가장 바깥쪽 트랜잭션을 시작하고 종료합니다.

Service에 선언된 `@Transactional`은 이 외부 트랜잭션에 참여하며, 업무 선후처리 Pointcut도 Service 호출 안에서 실행되므로 동일 트랜잭션에 참여합니다.

다만 현재 프로젝트에는 구 패키지와 신규 패키지가 함께 존재하여 Bean 이름 충돌이 발생합니다. 따라서 위 흐름은 현재 정상 실행이 검증된 상태가 아니라, 중복 코드를 정리한 후의 목표 구조입니다.

---

## 2. 트랜잭션은 정확히 어디서 시작되는가

설정은 다음 조건으로 나뉩니다.

### TCF 활성화 + 타임아웃 활성화

```yaml
nhnis:
  fw:
    commons:
      tcf:
        enabled: true
      timeout:
        enabled: true
        default-timeout-ms: 5000
```

이 경우 작업 스레드에서 다음과 같은 구조로 실행됩니다.

```java
transactionTemplate.execute(status -> {
    return action.call();
});
```

여기서 `action.call()`은 단순히 Service만 호출하는 것이 아니라 다음 전체 구간을 포함합니다.

```text
Dispatcher
  → Handler
  → Facade
  → Service
  → DAO
```

따라서 트랜잭션 범위는 생각보다 넓습니다.

```text
TX BEGIN
  Dispatcher
  Handler
  Facade
  Service
  업무 선처리
  업무 후처리
  DAO
TX COMMIT 또는 ROLLBACK
```

문서에서 Handler를 `TX 없음`으로 표현했다면 정확하지 않습니다.

정확한 표현은 다음과 같습니다.

> Handler가 트랜잭션을 직접 선언하거나 시작하지는 않지만, TimeoutExecutor가 이미 시작한 트랜잭션 안에서 실행된다.

---

## 3. 업무 선후처리 Pointcut 변경 결과

현재 신규 업무 선후처리 Aspect의 Pointcut은 Service 계층입니다.

```java
@Pointcut(
    "execution(public * nhnis.mg.co.a.application.service..*(..))"
)
```

적용 순서는 다음과 같습니다.

```text
Service Proxy 진입
  → 업무 선처리 @Before
  → Service 메서드
  → 업무 후처리 @AfterReturning
  → Service Proxy 반환
```

타임아웃이 활성화된 TCF 거래에서는 Service에 진입하기 전에 외부 트랜잭션이 이미 시작되어 있습니다.

```text
TimeoutExecutor
  → TX BEGIN
  → Dispatcher
  → Handler
  → Facade
  → Service Proxy
       → 업무 선처리
       → Service
       → 업무 후처리
  → TX COMMIT
```

따라서 업무 후처리에서 DB를 갱신하면 Service 및 DAO 작업과 같은 트랜잭션으로 묶입니다.

```java
@AfterReturning(pointcut = "businessService()", returning = "result")
public void afterReturning(JoinPoint joinPoint, Object result) {
    historyDao.insertHistory(...);
}
```

위 `insertHistory()`는 별도 `REQUIRES_NEW` 트랜잭션을 사용하지 않는 한 기존 트랜잭션에 참여합니다.

---

## 4. `@AfterReturning`의 중요한 의미

현재 업무 후처리는 `@AfterReturning`입니다.

따라서 Service가 정상 반환할 때만 실행됩니다.

```text
Service 정상 반환
  → 업무 후처리 실행
  → Commit
```

반면 Service에서 예외가 발생하면 다음과 같습니다.

```text
Service 예외
  → @AfterReturning 실행 안 됨
  → TimeoutExecutor까지 예외 전파
  → Rollback
```

실패 거래에 대해서도 업무 후처리를 수행해야 한다면 별도로 다음 중 하나가 필요합니다.

```java
@AfterThrowing(...)
```

또는:

```java
@Around(...)
```

현재 문서에서 업무 후처리를 “모든 종료 시 실행”으로 이해하면 안 됩니다. 정상 종료에만 실행됩니다.

## 5. 실행 설정별 실제 동작

| 실행 조건                            | 트랜잭션 시작 위치        | 업무 선후처리 TX 참여 | 주요 범위              |
| ------------------------------------ | ------------------------- | --------------------: | ---------------------- |
| TCF ON, Timeout ON                   | TimeoutExecutor           |                  참여 | Dispatcher부터 DAO까지 |
| TCF ON, Timeout OFF                  | Facade의 `@Transactional` |                  참여 | Facade부터 DAO까지     |
| TCF OFF, Legacy Controller 직접 호출 | 명시적 TX 없음            |                미참여 | Service 직접 실행      |

### TCF ON + Timeout OFF

동기 실행 Executor는 현재 스레드에서 Dispatcher를 호출합니다. 외부 `TransactionTemplate`이 없으므로 Facade의 `@Transactional`에서 트랜잭션이 시작됩니다.

```text
Dispatcher
  → Handler
  → Facade Proxy
       → TX BEGIN
       → Service
           → 업무 선처리
           → 업무 후처리
       → TX COMMIT
```

이 구조에서도 Service Pointcut은 Facade 트랜잭션 안에서 실행됩니다.

### TCF OFF

Legacy Controller가 Service를 직접 호출하면 Handler와 Facade를 우회합니다.

```text
Controller
  → Service
      → 업무 선처리
      → Service
      → 업무 후처리
```

Service에 별도의 `@Transactional`이 없다면 트랜잭션이 보장되지 않습니다. 여러 DAO 작업이 개별적으로 반영될 수 있습니다.

이 부분은 문서에 반드시 명시해야 하는 가장 큰 예외 조건입니다.

---

## 6. Service의 `@Transactional`과 외부 트랜잭션 관계

Facade 또는 Service가 다음과 같이 선언되어 있다고 가정합니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

기본 전파 속성은 `REQUIRED`입니다.

TimeoutExecutor가 이미 `rdwTransactionManager`로 트랜잭션을 시작한 상태라면 새로운 트랜잭션을 만들지 않고 기존 트랜잭션에 참여합니다.

```text
TimeoutExecutor TX
  └─ Facade @Transactional(REQUIRED)
       └─ Service @Transactional(REQUIRED)
            └─ 같은 물리 트랜잭션 사용
```

따라서 정상적으로 같은 트랜잭션으로 묶이려면 모든 계층이 동일한 `rdwTransactionManager`를 사용해야 합니다.

---

## 7. 조회 `readOnly=true`의 제한

Facade 조회 메서드가 다음과 같아도:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
```

TimeoutExecutor가 이미 일반 트랜잭션을 시작했다면 Facade는 기존 트랜잭션에 참여합니다.

따라서 내부 Facade의 `readOnly=true`가 외부 트랜잭션의 속성을 조회 전용으로 바꾸지는 못합니다.

```text
외부 TX: readOnly=false
  → 내부 Facade: readOnly=true
  → 실제 물리 TX: 계속 readOnly=false
```

현재 구조에서 조회 거래의 `readOnly` 최적화는 TimeoutExecutor 외부 트랜잭션 때문에 완전하게 적용되지 않을 수 있습니다.

## 8. 타임아웃과 롤백

현재 타임아웃 시간은 작업 실행 시점이 아니라 작업 제출 전부터 계산됩니다.

따라서 다음 시간이 모두 타임아웃에 포함됩니다.

```text
ThreadPool 대기 시간
+ Dispatcher 처리
+ Handler 처리
+ Facade 처리
+ Service 처리
+ DAO/SQL 처리
```

타임아웃이 발생하면 요청 스레드는 다음 작업을 수행합니다.

```java
future.cancel(true);
throw new OnlineTimeoutException(...);
```

작업 스레드는 실행 종료 시점에 deadline 또는 interrupt 상태를 확인하고 트랜잭션을 rollback-only로 만듭니다.

중요한 점은 다음과 같습니다.

> 클라이언트가 타임아웃 응답을 받은 순간에 DB 롤백까지 이미 완료되었다고 단정할 수는 없습니다.

DB 드라이버 또는 SQL이 인터럽트에 즉시 반응하지 않으면:

```text
요청 스레드: 타임아웃 응답 반환
작업 스레드: SQL 종료 대기
작업 스레드: deadline 확인
작업 스레드: Rollback
```

순서가 될 수 있습니다.

다만 작업이 늦게 정상 반환하더라도 deadline 재확인을 통해 Commit을 방지하려는 방어 로직은 들어가 있습니다.

## 9. 현재 업무 선후처리가 실제로 하는 일

현재 `BizPrePostAspect`는 주로 로그를 남기는 구조입니다.

따라서:

- 업무 선처리 DB 작업
- 업무 후처리 이력 INSERT
- 업무 후처리 상태 UPDATE

등이 현재 실제 구현되어 있다는 의미는 아닙니다.

문서에서는 다음과 같이 구분하는 것이 정확합니다.

```text
현재 구현:
  Service 진입/정상 종료 로그 처리

확장 가능한 동작:
  업무 검증
  거래 통제
  이력 INSERT
  업무 상태 UPDATE
  결과값 가공
```

업무 후처리에서 DB 작업을 추가하면 같은 트랜잭션에 참여할 수 있다는 것은 현재의 “구조적 가능성”입니다.

## 10. `@Order(100)`의 의미

업무 Aspect의 `@Order(100)`이 트랜잭션 참여를 보장하는 것은 아닙니다.

동일한 Service 메서드에 여러 Aspect가 적용될 때 순서를 조정할 뿐입니다.

업무 선후처리가 트랜잭션 안에 들어가는 실제 이유는 다음과 같습니다.

- Timeout ON: Service 호출 전에 외부 `TransactionTemplate`이 시작됨
- Timeout OFF: Facade 프록시가 Service 호출 전에 트랜잭션을 시작함

즉, 다른 프록시 경계에서 트랜잭션이 이미 시작되어 있기 때문입니다.

---

## 11. 현재 발견된 실행 차단 문제

현재 프로젝트에는 기존 패키지와 신규 패키지가 동시에 스캔됩니다.

```text
nhnis.mg.*
nhnis.mg.co.a.*
```

`PdmgApplication`이 `nhnis` 전체를 Component Scan하므로 동일한 기본 Bean 이름을 가진 클래스들이 충돌합니다.

실제로 확인된 대표 충돌은:

```text
mgcoa5530Service
```

이며 Service 충돌을 제거하면 기존/신규 `BizPrePostAspect`도 다음 Bean 이름으로 충돌할 가능성이 큽니다.

```text
bizPrePostAspect
```

따라서 현재 문서는 다음 상태로 표현해야 정확합니다.

> 신규 트랜잭션 구조의 설계와 구현은 존재하지만, 구·신 패키지 중복 Bean을 정리하기 전에는 애플리케이션 정상 기동을 보장할 수 없다.

## 12. 문서에서 수정이 필요한 핵심 사항

현재 문서에는 다음 내용을 보완하는 것이 좋습니다.

1. Handler는 트랜잭션을 시작하지 않지만 Timeout ON에서는 트랜잭션 내부에서 실행된다고 정정
2. `@AfterReturning`은 정상 반환에만 실행된다고 명시
3. TCF OFF에서는 Facade와 TimeoutExecutor를 우회하므로 명시적 트랜잭션이 없다고 강조
4. 타임아웃 응답과 실제 DB 롤백 완료 시점이 다를 수 있다고 명시
5. `readOnly=true`가 외부 트랜잭션 속성을 변경하지 못한다고 명시
6. 업무 선후처리의 DB 갱신은 현재 구현이 아니라 확장 가능한 방식이라고 구분
7. 구·신 패키지 중복 Bean으로 현재 애플리케이션 기동이 차단된 상태를 문서 최상단에 표시
8. Handler가 트랜잭션의 소유자는 아니지만 트랜잭션 범위에는 포함된다는 책임 구분 추가

최종적으로 문서의 핵심 정의는 다음 한 문장으로 정리할 수 있습니다.

> TCF 및 타임아웃이 활성화된 거래는 TimeoutExecutor가 작업 스레드에서 `rdwTransactionManager` 트랜잭션을 시작하고, Dispatcher·Handler·Facade·Service·업무 선후처리·DAO를 하나의 트랜잭션으로 실행한 뒤 정상 시 Commit, 예외 또는 타임아웃 시 Rollback한다. 단, TCF를 우회하는 Legacy Controller 직접 호출은 이 트랜잭션 경계를 적용받지 않는다.
