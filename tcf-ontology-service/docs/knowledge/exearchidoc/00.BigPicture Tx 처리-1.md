`00.BigPicture TX 흐름`은 **HTTP 요청 한 건이 들어와 응답될 때까지의 전체 흐름과 DB 트랜잭션 범위를 한눈에 보여주는 문서**입니다.

핵심은 요청 Thread와 업무 Worker Thread가 분리된다는 점입니다.

## 1. 전체 흐름

```text
브라우저
→ pdmg-ui
→ pdmg-service:8080
→ pdmg-fw 시스템 선처리
→ pdmg-fw TCF 거래 분배
→ Worker Thread에서 업무 및 DB 트랜잭션 처리
→ pdmg-fw 시스템 후처리
→ 브라우저 응답
```

조금 더 구체적으로 보면 다음과 같습니다.

```text
[HTTP 요청 Thread]

① DefaultFilter
② ServicePreventionInterceptor.preHandle
③ OnlineTransactionController
④ TcfFacade
⑤ OnlineTimeoutExecutor
       │
       └─ Worker Thread로 업무 전달
             ↓
       ⑥ TransactionTemplate TX 시작
       ⑦ TransactionDispatcher
       ⑧ TransactionHandler
       ⑨ Business Facade
       ⑩ 업무 선처리
       ⑪ Service
       ⑫ DAO / Mapper / SQL
       ⑬ 업무 후처리
       ⑭ Deadline 검사
       ⑮ Commit 또는 Rollback
             ↓
       요청 Thread로 결과 반환

⑯ ResponseBodyArgumentResolver
⑰ ServicePreventionInterceptor.afterCompletion
⑱ DefaultFilter Context 정리
⑲ HTTP 응답
```

## 2. 환경 설정과 전체 흐름의 관계

현재 주요 설정은 [application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml>)에 있습니다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    timeout:
      enabled: true
      milliseconds: 5000
      pool-size: 20
      queue-capacity: 100
    commons:
      legacy-web:
        enabled: true
      filter:
        enabled: true
```

각 설정은 다음 구간을 활성화합니다.

| 설정                      | 활성 구간                                     |
| ------------------------- | --------------------------------------------- |
| `tcf.enabled=true`        | Controller → TcfFacade → Dispatcher → Handler |
| `timeout.enabled=true`    | Worker Thread와 외부 DB 트랜잭션              |
| `legacy-web.enabled=true` | Interceptor, 시스템·업무 선후처리             |
| `filter.enabled=true`     | Header, JWT, ServiceContext, MDC              |

## 7. OnlineTimeoutExecutor

설정:

```yaml
nhnis:
  fw:
    timeout:
      enabled: true
      milliseconds: 5000
      pool-size: 20
      queue-capacity: 100
```

관련 소스:

- [OnlineTimeoutProperties.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutProperties.java>)
- [OnlineTimeoutConfiguration.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutConfiguration.java>)

설정값의 의미:

```text
milliseconds=5000
→ 요청 Thread는 최대 5초 동안 결과 대기

pool-size=20
→ 업무 Worker 최대 20개 동시 실행

queue-capacity=100
→ Worker가 모두 사용 중일 때 100건까지 대기

20개 실행 + 100개 대기 초과
→ FW_OVERLOADED
→ HTTP 503
```

## 8. 요청 Thread와 Worker Thread

타임아웃을 사용하면 업무는 HTTP 요청 Thread에서 실행되지 않습니다.

```text
HTTP 요청 Thread
└─ Future.get(5000ms)로 결과 대기

Worker Thread: pdmg-online-N
└─ TransactionTemplate
   └─ 실제 업무 수행
```

`ServiceContext`와 MDC는 ThreadLocal이므로 자동으로 Worker에 전달되지 않습니다.

[OnlineTimeoutWorkerContext.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutWorkerContext.java>)가 다음 정보를 복사합니다.

```text
GUID
serviceId
사용자 ID
클라이언트 IP
ServiceContext
MDC
```

Worker가 끝나면 반드시 정리합니다.

```java
workerContext.clear();
```

## 9. DB 트랜잭션 시작 위치

실제 DB 트랜잭션은 Worker에서 시작됩니다.

```java
return transactionTemplate.execute(status -> {
    Object result = action.call();

    if (deadlineExceeded) {
        status.setRollbackOnly();
        throw new OnlineTimeoutException(...);
    }

    return result;
});
```

트랜잭션 범위는 정확히 다음과 같습니다.

```text
TransactionTemplate BEGIN
├─ TransactionDispatcher
├─ TransactionHandler
├─ Business Facade
├─ 업무 선처리
├─ Service
├─ DAO / Mapper / SQL
├─ 업무 후처리
├─ Deadline 검사
└─ COMMIT 또는 ROLLBACK
```

따라서 **Handler도 DB 트랜잭션 안에서 실행됩니다.**

기존 `00.BigPicture TX 흐름.md` 그림은 Handler 다음에 DB TX 박스를 그려서 Facade부터 TX가 시작되는 것처럼 보일 수 있습니다. 실제 구현은 `TransactionTemplate`이 Dispatcher 호출 전체를 감싸므로 Dispatcher와 Handler도 TX 안입니다.

다만 Handler는 SQL을 실행하지 않기 때문에 실질적인 DB 작업은 Facade 이후부터 발생합니다.

## 10. Dispatcher와 Handler

`TransactionDispatcher`는 `serviceId`로 Handler를 찾습니다.

```text
mgcoa9000S0
→ mgcoa9000Handler
→ facade.mgcoa9000S0()

mgcoa9000C0
→ mgcoa9000Handler
→ facade.mgcoa9000C0()
```

Handler 역할은 거래 분기까지만입니다.

```text
허용:
Handler → Facade

피해야 함:
Handler → DAO
Handler → SQL
Handler → 복잡한 업무 처리
```

## 11. Facade 트랜잭션

예시: [mgcoa9000Facade.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/application/facade/mgcoa9000Facade.java>)

조회:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
```

등록·수정·삭제:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

그러나 TimeoutExecutor가 이미 외부 트랜잭션을 시작했습니다.

```text
TimeoutExecutor TransactionTemplate
└─ Facade @Transactional(REQUIRED)
```

`@Transactional`의 기본 전파 속성은 `REQUIRED`이므로 Facade는 새로운 트랜잭션을 만들지 않고 기존 Worker 트랜잭션에 참여합니다.

```text
외부 TX 있음
→ Facade가 같은 TX 사용
```

## 12. 업무 선처리


따라서 업무 선처리에서 같은 `rdwDataSource`의 DAO를 호출하면 같은 트랜잭션에 참여합니다.

## 13. Service와 DAO

```text
Service
→ DAO Interface
→ MyBatis SqlSessionTemplate
→ Mapper XML
→ DB
```

관련 환경 설정:

```yaml
spring:
  datasource:
    rdw:
      jdbc-url: ...
```

`RdwDataSourceConfig`가 다음 Bean을 만듭니다.

```text

rdwSqlSessionFactory

```

TimeoutExecutor와 Facade가 모두 같은 `rdwTransactionManager`를 사용하므로 DAO SQL은 동일 트랜잭션에 묶입니다.

## 14. 업무 후처리

업무 Service가 정상 반환하면 `@AfterReturning` 후처리가 실행됩니다.

```text
Service 정상 종료
→ 업무 후처리
→ Facade 반환
→ Handler 반환
→ Deadline 검사
→ Commit
```

업무 후처리에서 DB를 변경하는 경우:

```java
postProcessDao.insert(...);
```

같은 DataSource를 사용하고 예외를 삼키지 않으면 앞의 업무 SQL과 같은 트랜잭션입니다.

```text
Service UPDATE
+ 업무 후처리 INSERT
→ 함께 COMMIT

후처리 예외
→ 둘 다 ROLLBACK
```

## 15. 타임아웃 처리

정상 처리:

```text
TX BEGIN
→ 업무 완료
→ 5초 이내
→ Deadline 정상
→ COMMIT
→ HTTP 200
```

5초 초과:

```text
요청 Thread
→ Future.get(5000ms) 초과
→ future.cancel(true)
→ OnlineTimeoutException
→ HTTP 504
```

Worker가 인터럽트를 처리하면:

```text
Worker 예외
→ rollbackOnly
→ ROLLBACK
```

JDBC가 인터럽트를 즉시 처리하지 않으면:

```text
HTTP 요청에는 먼저 504 반환
→ JDBC가 나중에 반환
→ Worker Deadline 재검사
→ rollbackOnly
→ ROLLBACK
```

즉, 즉시 SQL 종료를 완전히 보장하지는 않지만 늦은 Commit을 방지하도록 설계되어 있습니다.

## 16. 시스템 후처리

업무 트랜잭션 종료 후 요청 Thread에서 실행됩니다.

```text
ResponseBodyArgumentResolver
→ 응답 전문 구성
→ 응답 로그

ServicePreventionInterceptor.afterCompletion
→ ImageLog 응답정보 UPDATE
→ 예외정보 기록
```

이 구간은 업무 트랜잭션 밖입니다.

따라서 시스템 후처리의 이미지 로그 UPDATE가 실패해도 이미 Commit된 업무 데이터를 되돌릴 수 없습니다.

## 17. 성공과 실패 흐름

### 성공

```text
Filter
→ 시스템 선처리
→ Worker TX BEGIN
→ Handler
→ Facade
→ 선처리
→ Service
→ DAO
→ 후처리
→ COMMIT
→ 시스템 후처리
→ 200 응답
```

### 업무 예외

```text
Worker TX BEGIN
→ Service 또는 후처리 예외
→ ROLLBACK
→ GlobalExceptionHandler
→ 오류 전문
→ 시스템 후처리
→ 오류 응답
```

### 타임아웃

```text
Worker TX BEGIN
→ 5초 초과
→ 요청 Thread 504
→ Worker 취소 요청
→ Worker가 반환되는 시점에 ROLLBACK
→ 시스템 후처리
```

### Executor 포화

```text
Worker 20개 사용 중
+ 큐 100개 대기 중
+ 추가 요청
→ OnlineOverloadException
→ HTTP 503
→ 업무 TX 시작 안 함
```

## 핵심 요약

```text
시스템 구간:
Filter / Interceptor / Controller / 응답 후처리
→ 업무 DB TX 밖

업무 구간:
TimeoutExecutor Worker
→ TransactionTemplate
→ Dispatcher / Handler / Facade
→ 선처리 / Service / DAO / 후처리
→ 하나의 DB TX

타임아웃:
요청 Thread는 5초 대기
→ 초과 시 504
→ Worker는 Commit 전에 Deadline 검사
→ 초과 거래 Rollback
```

현재 [00.BigPicture TX 흐름.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/00.BigPicture%20TX%20흐름.md>)의 전체 방향은 맞습니다. 다만 도식에서 DB TX 시작 위치는 Facade가 아니라 **`DefaultOnlineTimeoutExecutor`의 `TransactionTemplate`이며, Dispatcher와 Handler도 그 트랜잭션 범위 안**이라는 점을 명확히 하는 것이 좋습니다.
