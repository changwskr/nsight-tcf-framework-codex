## 분석 결론

[07.도메인 정의 및 호출방식.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/07.도메인 정의 및 호출방식.md>)는 PDMG의 `serviceId → Handler → Facade → Service → DAO` 호출 구조를 이해하기 쉽게 설명합니다.

현재 등록된 프로그램과 UI Catalog, Handler의 `serviceIds()` 매핑도 대부분 정확합니다.

다만 이 문서에서 말하는 “도메인”은 DDD의 업무 도메인이라기보다 다음을 조합한 기술적 분류입니다.

```text
업무·세부 코드 축
  → 프로그램 식별번호
  → 거래 serviceId
```

현재 소스에는 별도의 Domain Model, Entity, Value Object, Domain Service 또는 `application.rule`이 없습니다. 따라서 제목의 “도메인 정의”를 업무 모델 정의로 이해하면 안 됩니다.

또한 TimeoutExecutor, 트랜잭션 경계, UI Relay 보안, 프로그램 간 호출 원칙에 수정이 필요합니다.

---

## 1. 문서가 정의한 계층

문서는 다음 네 단계로 도메인을 구분합니다.

```text
MG 애플리케이션
  └─ CO/A 업무·세부 축
       └─ 프로그램 8888
            └─ 거래 mgcoa8888S0
```

현재 신규 소스 구조와 대응하면 다음과 같습니다.

| 문서 용어    | 실제 구현                                          |
| ------------ | -------------------------------------------------- |
| 애플리케이션 | `pdmg-service`, `nhnis.mg.PdmgApplication`         |
| 업무·세부 축 | `nhnis.mg.co.a.*`                                  |
| 프로그램     | `mgcoa5530`, `mgcoa8888`, `mgcoa9000`, `mgcoa9999` |
| 거래         | `mgcoa8888S0` 같은 serviceId                       |
| 거래 라우팅  | `TransactionDispatcher`와 `TransactionHandler`     |
| 업무 수행    | Facade, Service, DAO                               |

구조적 분류는 현재 구현과 맞습니다.

## 2. “도메인”이라는 용어의 정확성

현재 문서에서 도메인은 세 가지 의미로 사용됩니다.

```text
업무 도메인:
  co.a

프로그램 도메인:
  mgcoa8888

거래 도메인:
  mgcoa8888S0
```

하지만 일반적인 DDD 관점의 도메인은 다음과 같습니다.

```text
마케팅 희망고객
이미지로그
거래 파라미터
영업팁 실적
```

현재 PDMG에는 이 업무 개념을 독립 모델로 표현하는 다음 요소가 없습니다.

```text
domain 패키지
Entity
Value Object
Aggregate
Domain Service
Repository 인터페이스
application.rule
```

현재 구현은 사실상 다음 구조입니다.

```text
프로그램 ID 중심의 Transaction Script
```

예:

```text
mgcoa8888Service
  → 입력 검증
  → 조건 구성
  → DAO 호출
  → DTO 조립
```

따라서 문서 서두에 다음 정의가 필요합니다.

> 본 문서에서 도메인은 DDD의 Domain Model이 아니라 PDMG 업무 코드, 프로그램 식별번호와 온라인 거래 ID를 기반으로 한 기술적 업무 분류 단위를 의미한다.

## 3. 업무·세부 축 분석

문서는 다음 업무 코드를 정의합니다.

| 코드 | 문서상 의미 |
| ---- | ----------- |
| `CO` | 공통        |
| `IC` | 통합고객    |
| `MS` | 미니 상품부 |
| `SA` | 사업관리    |
| `A`  | 상담        |
| `B`  | 고객        |

현재 소스에서 실제로 확인되는 축은 다음 하나입니다.

```text
co.a
```

다른 축은 향후 확장 예시이며 현재 코드, 설정 또는 Enum으로 강제되지 않습니다.

또한 현재 `co.a` 아래에는 성격이 서로 다른 프로그램들이 함께 있습니다.

```text
mgcoa5530 : 마케팅희망고객
mgcoa8888 : 이미지로그
mgcoa9000 : 거래 파라미터
mgcoa9999 : 영업팁 실적
```

따라서 `CO+A = 공통+상담`이라는 의미가 실제 업무 경계를 정확히 반영하는지는 별도 업무 코드 정본으로 확인해야 합니다.

현재 프레임워크가 보장하는 것은 의미가 아니라 패키지 문자열입니다.

```text
nhnis.mg.co.a
rdw.mg.co.a
mgcoa...
```

## 4. 프로그램 단위 분석

문서는 식별번호 4자리를 하나의 프로그램으로 정의합니다.

```text
8888
  → mgcoa8888Handler
  → mgcoa8888Facade
  → mgcoa8888Service
  → mgcoa8888DAO
  → mgcoa8888-ORA.xml
```

동일 프로그램의 여러 거래는 하나의 클래스 세트에 모읍니다.

```text
mgcoa8888S0
mgcoa8888D0
```

현재 `mgcoa8888`과 `mgcoa9000`은 이 규칙을 잘 따릅니다.

```text
mgcoa9000
  ├─ S0
  ├─ C0
  ├─ U0
  └─ D0
```

다만 다음 문장은 너무 강한 정의입니다.

> 한 프로그램 = 화면/기능 묶음

프로그램은 화면과 항상 1:1이 아닙니다.

```text
하나의 프로그램을 여러 화면에서 호출할 수 있음
하나의 화면이 여러 프로그램을 호출할 수 있음
배치나 외부 시스템도 동일 프로그램을 호출할 수 있음
```

따라서 정확한 정의는 다음입니다.

> 프로그램은 같은 식별번호와 구현 클래스 세트를 공유하는 업무 처리 묶음이며 화면과 반드시 1:1 대응하지 않는다.

## 5. Handler 단위와 “도메인당 하나” 문제

현재 신규 구현에는 다음 Handler가 있습니다.

```text
mgcoa5530Handler
mgcoa8888Handler
mgcoa9000Handler
mgcoa9999Handler
```

즉, 현재는 프로그램 식별번호별 Handler 하나입니다.

하지만 저장소 공식 규칙에는 다음과 같이 정의되어 있습니다.

```text
업무 도메인마다 하나의 TransactionHandler
serviceIds()로 여러 거래 등록
```

여기서 “업무 도메인”을 `co.a`로 해석하면 Handler가 하나여야 하고, 프로그램으로 해석하면 현재처럼 네 개가 맞습니다.

따라서 문서에서 Handler 생성 단위를 명확히 확정해야 합니다.

현재 PDMG 구현 기준 정의는 다음입니다.

> 프로그램 식별번호 하나당 Handler 하나를 두고 해당 프로그램의 S/C/U/D 거래를 `serviceIds()`로 함께 등록한다.

## 6. serviceId 등록 구조

현재 Handler는 `serviceIds()`로 자신이 처리할 거래를 등록합니다.

예:

```java
@Override
public Collection<String> serviceIds() {
    return List.of(
        "mgcoa8888S0",
        "mgcoa8888D0"
    );
}
```

`TransactionDispatcher`는 시작 시점에 모든 Handler를 받아 Map을 구성합니다.

```text
mgcoa8888S0 → mgcoa8888Handler
mgcoa8888D0 → mgcoa8888Handler
```

문서의 “문자열을 등록하면 Dispatcher가 찾는다”는 설명은 맞습니다.

추가로 다음 동작도 명시하면 좋습니다.

### serviceId가 없는 경우

```text
ServiceHandlerNotFound
  "serviceId가 없습니다."
```

### 등록되지 않은 경우

```text
ServiceHandlerNotFound
  "등록되지 않은 serviceId입니다."
```

### 중복 등록된 경우

Dispatcher 생성 시 다음 예외가 발생합니다.

```text
IllegalStateException
  "Duplicate serviceId detected"
```

따라서 serviceId 충돌은 요청 시점이 아니라 애플리케이션 기동 시점에 검출됩니다.

## 7. 실제 serviceId 목록

현재 신규 `co.a` Handler 기준 등록 거래는 총 8개입니다.

| 프로그램    | serviceId                       |
| ----------- | ------------------------------- |
| `mgcoa5530` | `mgcoa5530S0`                   |
| `mgcoa8888` | `mgcoa8888S0`, `mgcoa8888D0`    |
| `mgcoa9999` | `mgcoa9999S0`                   |
| `mgcoa9000` | `mgcoa9000S0`, `C0`, `U0`, `D0` |

문서의 매핑표와 일치합니다.

단, 앞 문서에서 확인한 것처럼 serviceId는 10자가 아니라 11자입니다.

```text
mgcoa8888S0
= 11자
```

## 8. TCF ON 호출 흐름

문서의 TCF ON 흐름은 핵심적으로 맞지만 `OnlineTimeoutExecutor`가 빠져 있습니다.

문서 흐름:

```text
TcfFacade / Dispatcher
  → Handler
  → Facade
```

현재 실제 흐름:

```text
OnlineTransactionController
  → TcfFacade
  → OnlineTimeoutExecutor
       → Worker Thread
       → TransactionTemplate BEGIN
       → TransactionDispatcher
       → Handler
       → Facade
       → Service
       → DAO
       → Commit/Rollback
```

따라서 정확한 흐름은 다음입니다.

```text
Client/UI
  → POST /mgcoa8888S0
  → DefaultFilter
  → ServicePreventionInterceptor
  → OnlineTransactionController
  → TcfFacade
  → OnlineTimeoutExecutor
       ↓ Worker Thread
       → TX BEGIN
       → TransactionDispatcher
       → mgcoa8888Handler
       → mgcoa8888Facade
       → BizPrePostAspect Before
       → mgcoa8888Service
       → mgcoa8888DAO
       → BizPrePostAspect AfterReturning
       → Commit/Rollback
  → ResponseBodyAdvice
  → ImageLog 후처리
```

## 9. 트랜잭션 최소 단위 설명 오류

문서에는 다음과 같이 되어 있습니다.

```text
한 거래
≈ Facade 메서드 1개
≈ DB 트랜잭션 1건(쓰기 시)
```

현재 Timeout ON에서는 완전히 정확하지 않습니다.

트랜잭션은 Facade 앞에서 시작됩니다.

```text
TransactionTemplate BEGIN
  → Dispatcher
  → Handler
  → Facade
  → Service
  → DAO
```

조회 거래도 `readOnly=true` Facade가 있지만, 이미 외부 일반 트랜잭션이 시작된 상태라 같은 외부 트랜잭션에 참여합니다.

정확한 설명은 다음입니다.

> 하나의 serviceId 호출은 하나의 업무 유스케이스 및 Facade 메서드와 대응한다. DB 트랜잭션은 Timeout ON이면 Executor가 Dispatcher 이하를 감싸고, Timeout OFF이면 Facade가 시작한다.

## 10. Handler에서 Facade 호출

Handler는 다음 정보를 받습니다.

```java
handle(
    Object dtoBody,
    TransactionContext context
)
```

역할은 다음과 같습니다.

```text
context.serviceId 확인
  → 동일 프로그램 내부 거래 분기
  → 해당 Facade 메서드 호출
```

예:

```java
return switch (context.getServiceId()) {
    case S0 -> facade.mgcoa8888S0(dtoBody);
    case D0 -> facade.mgcoa8888D0(dtoBody);
    default -> throw new ServiceHandlerNotFound(...);
};
```

이 부분은 문서와 정확히 일치합니다.

Dispatcher에서 이미 serviceId를 사용해 Handler를 찾았지만 Handler 내부에서 다시 serviceId를 분기하는 이유는 하나의 Handler가 여러 거래를 담당하기 때문입니다.

---

## 11. Facade 호출과 DTO 변환

Handler는 요청의 `dto` 노드를 아직 구체적인 DTO 타입으로 변환하지 않고 `Object`로 전달합니다.

```text
Handler
  → Object dtoBody

Facade
  → ObjectMapper.convertValue
  → mgcoa8888S0DTOin

Service
  → typed DTOin
```

문서의 프로그램 내부 호출 표는 현재 구현과 맞습니다.

```text
Handler → Facade : Object → DTOout
Facade → Service : DTOin → DTOout
Service → DAO    : Map → List/int
```

다만 Facade를 단순 TX 계층으로만 설명하면 부족합니다. 현재 Facade의 중요한 책임은 거래별 DTO 타입 결정입니다.

---

## 12. serviceId 결정 우선순위

문서는 다음을 동일해야 한다고 설명합니다.

```text
UI id
Catalog path
백엔드 URL serviceId
Handler 등록 문자열
```

현재 샘플에서는 실제로 동일합니다.

하지만 백엔드 `OnlineTransactionController`는 URL path만 사용하지 않습니다.

serviceId 결정 우선순위는 다음입니다.

```text
1. ServiceContext Header의 rms_svc_c
2. 요청 JSON Header의 rms_svc_c
3. URL path의 serviceId
```

따라서 다음 요청에서:

```text
URL    : /mgcoa8888S0
Header : mgcoa9000D0
```

현재 구현은 Header 값을 우선할 수 있습니다.

문서의 “반드시 모두 동일”은 운영 규칙으로는 맞지만 코드가 일치 여부를 검증하는 것은 아닙니다.

필요한 보완은 다음입니다.

> URL, UI Catalog와 Header serviceId는 동일해야 한다. 현재 Controller는 Header 우선으로 값을 결정하므로 서로 다를 경우 요청을 거부하는 정합성 검증이 추가로 필요하다.

## 13. UI Relay 분석

현재 UI Relay 구조는 문서와 대체로 일치합니다.

```text
브라우저
  → POST /api/relay/{id}
  → TransactionCatalog.findById(id)
  → Catalog에 등록된 path 조회
  → TransactionRelayService
  → pdmg-service로 POST
```

Catalog에는 현재 8개 거래가 등록되어 있습니다.

```text
mgcoa5530S0
mgcoa8888S0
mgcoa8888D0
mgcoa9999S0
mgcoa9000S0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
```

등록되지 않은 ID는 UI에서 다음 오류가 발생합니다.

```text
HTTP 404
등록되지 않은 거래입니다
```

따라서 `/api/relay/{id}`는 완전히 임의의 ID를 백엔드로 넘기지 않고 Catalog를 먼저 확인합니다.

## 14. UI Catalog 중복 검사 문제

`TransactionCatalog.register()`는 다음과 같습니다.

```java
transactions.put(info.id(), info);
```

같은 ID가 두 번 등록되면 예외를 발생시키지 않고 나중 값으로 덮어씁니다.

반면 백엔드 Dispatcher는 중복 serviceId에 대해 기동 실패를 발생시킵니다.

```text
UI Catalog:
  중복 ID → 조용히 덮어쓰기

Backend Dispatcher:
  중복 ID → IllegalStateException
```

문서에서는 UI와 백엔드 모두 ID가 동일해야 한다고 설명하지만, UI 쪽에는 중복 방지 검증이 없습니다.

권장 검증은 다음입니다.

```java
if (transactions.putIfAbsent(info.id(), info) != null) {
    throw new IllegalStateException(
        "Duplicate transaction id: " + info.id()
    );
}
```

분석 요청이므로 실제 변경은 하지 않았습니다.

## 15. UI Relay의 baseUrl 보안

현재 `/api/relay/{id}`는 요청 파라미터로 `baseUrl`을 받을 수 있습니다.

```text
POST /api/relay/mgcoa8888S0?baseUrl=...
```

`TransactionRelayService`는 해당 값을 대상 URL로 사용합니다.

```java
trimTrailingSlash(baseUrl) + info.path()
```

그리고:

```java
URI.create(targetUrl)
```

로 직접 외부 요청을 보냅니다.

baseUrl에 대한 허용 호스트 검증이 없으므로 외부 사용자가 UI API에 접근할 수 있다면 SSRF 위험이 있습니다.

예를 들어 내부 관리 주소 또는 원하지 않는 외부 URL로 Relay가 가능할 수 있습니다.

문서에는 단순 호출 편의뿐 아니라 다음 제약이 필요합니다.

```text
운영 환경:
  baseUrl 사용자 override 금지
  또는 허용된 scheme/host/port만 허용
```

이것은 현재 호출 방식에서 가장 중요한 보안 위험입니다.

## 16. UI가 body를 그대로 전달한다는 의미

문서의 다음 설명은 맞습니다.

> TransactionRelayService는 body를 그대로 백엔드 POST한다.

실제로 UI는 requestBody 문자열을 변환하지 않고 전달합니다.

```java
.body(requestBody == null ? "{}" : requestBody)
```

다만 `Content-Type`과 `Accept`는 UI Relay가 다음 값으로 지정합니다.

```text
application/json;charset=UTF-8
```

UI Relay는 백엔드 오류 상태를 예외로 바꾸지 않고 `RelayResult`로 감쌉니다.

```text
transactionId
targetUrl
status
elapsedMs
body
```

따라서 브라우저가 받는 최종 UI API 응답은 백엔드 전문 자체가 아니라 Relay 메타데이터를 포함한 응답입니다.

이 점은 문서에 빠져 있습니다.

---

## 17. TCF OFF 호출

문서에는 다음처럼 되어 있습니다.

```text
Controller
  → Service 또는 Facade
```

현재 신규 `co.a` Controller는 모두 Service를 직접 호출합니다.

```text
Controller
  → Service
  → DAO
```

따라서 현재 TCF OFF에서는 다음을 우회합니다.

```text
Handler
Facade
OnlineTimeoutExecutor
Facade @Transactional
```

업무 Aspect는 Service Pointcut이라 실행되지만 명시적인 업무 트랜잭션은 없습니다.

정확한 AS-IS 설명은 다음입니다.

> 현재 TCF OFF Controller는 Service를 직접 호출한다. Facade를 경유하지 않으므로 명시적인 업무 트랜잭션이 없으며 TCF ON과 같은 경계를 보장하려면 Controller를 Facade 호출 방식으로 변경해야 한다.

---

## 18. 실패 응답 설명

문서에는 직접 HTTP 실패 응답이 다음처럼 표현되어 있습니다.

```text
실패: NH_NIS_ERR_DTO
```

예외 Handler가 만드는 본문 타입은 맞습니다.

하지만 `ResponseBodyAdvice`가 활성화되면 실제 최종 HTTP 응답은 다음과 같습니다.

```json
{
  "hdr_nhnis": {},
  "dto": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "...",
    "errType": "COMMON"
  }
}
```

정확한 구분은 다음입니다.

```text
예외 처리 본문:
  NH_NIS_ERR_DTO

최종 HTTP 응답:
  { hdr_nhnis, dto: NH_NIS_ERR_DTO }
```

## 19. 프로그램 간 호출 원칙 문제

문서는 다른 프로그램 기능이 필요하면 다음을 권장합니다.

```text
1. 공개 serviceId를 HTTP/Client로 호출
2. 공통 로직을 support로 이동
```

이 규칙은 주의가 필요합니다.

### 같은 애플리케이션 내부 호출

같은 `pdmg-service` 내부에서 단순히 프로그램이 다르다는 이유만으로 자기 자신을 HTTP 호출하면 다음 문제가 생깁니다.

```text
불필요한 네트워크 비용
새 요청 Context와 새 트랜잭션 생성
원래 트랜잭션과 분리
Timeout 중첩
장애 지점 증가
```

같은 트랜잭션으로 묶어야 하는 공통 업무 로직이라면 다음이 더 적합합니다.

```text
application.rule
공통 업무 Service
명시적인 내부 Port/Interface
```

### 다른 애플리케이션 또는 WAS 호출

외부 호출이면 다음이 맞습니다.

```text
client 계층
pdmg-fw/TCF 표준 전문
필요 시 tcf-eai
```

### Support 사용

`support`는 순수 유틸, 상수와 상태 없는 Helper에 적합합니다. 업무 규칙을 `support`로 옮기면 책임이 불명확해집니다.

따라서 문서의 프로그램 간 호출 원칙은 다음처럼 수정해야 합니다.

```text
같은 모듈의 공통 업무 규칙:
  application.rule 또는 공통 application service

다른 모듈/WAS 거래:
  client + 표준 serviceId 호출

순수 변환·상수·Helper:
  support
```

## 20. 동기·트랜잭션 표 오류

문서에는 다음과 같이 되어 있습니다.

```text
Handler → Facade
  동기
  Facade에서 TX 시작
```

Timeout ON에서는 Handler 호출 전에 이미 트랜잭션이 시작됩니다.

```text
OnlineTimeoutExecutor
  → Worker Thread
  → TransactionTemplate BEGIN
  → Dispatcher
  → Handler
  → Facade
```

정확한 표는 다음과 같습니다.

| 호출                  | 동기 여부        | DB TX                             |
| --------------------- | ---------------- | --------------------------------- |
| UI → Service          | 동기 HTTP        | 해당 없음                         |
| Executor → Dispatcher | Worker 내부 동기 | Timeout ON이면 TX 시작            |
| Dispatcher → Handler  | 동기             | Timeout ON이면 TX 안              |
| Handler → Facade      | 동기             | 기존 TX 참여 또는 Facade에서 시작 |
| Facade → Service      | 동기             | 같은 TX                           |
| Service → DAO         | 동기             | 같은 TX                           |
| ImageLog              | 요청 스레드 동기 | 업무 TX 밖                        |

## 22. 현재 실행 가능성

문서는 신규 `nhnis.mg.co.a` 호출 경로가 정상 기동된다는 전제입니다.

하지만 현재 다음 패키지가 함께 존재합니다.

```text
nhnis.mg.*
nhnis.mg.co.a.*
```

Boot는 `nhnis` 전체를 스캔합니다.

따라서 다음 Bean 충돌 가능성이 있습니다.

```text
Service
Handler
Facade
Aspect
RdwDataSourceConfig
TransactionManager
```

그러므로 문서의 호출 흐름은 현재 검증된 실행 상태라기보다 구 패키지를 정리한 후의 목표 실행 구조로 보는 것이 정확합니다.

## 최종 평가

| 영역                    |        평가 |
| ----------------------- | ----------: |
| 기술적 도메인 계층 구분 |        높음 |
| 프로그램과 거래 관계    |        높음 |
| Handler serviceId 등록  |        높음 |
| Handler 내부 분기       |        높음 |
| Facade DTO 변환         |        높음 |
| UI Catalog/Relay 설명   | 대체로 높음 |
| TimeoutExecutor 반영    |        부족 |
| 트랜잭션 설명           |   수정 필요 |
| DDD 도메인 의미         |      과장됨 |
| 프로그램 간 호출 원칙   |   수정 필요 |
| Relay 보안              |        누락 |
| 현재 기동 상태          |        누락 |

문서 정확도는 약 75~80%입니다.

가장 먼저 수정할 내용은 다음입니다.

1. “도메인”을 PDMG 기술적 업무 분류라고 명시
2. TCF ON 흐름에 `OnlineTimeoutExecutor`와 Worker TX 추가
3. “Facade에서 TX 시작”을 Timeout ON/OFF별로 구분
4. Header와 URL serviceId 일치 검증 필요성 추가
5. UI Relay `baseUrl` 허용 목록과 SSRF 방지 규칙 추가
6. UI Relay 응답이 `RelayResult`라는 점 추가
7. 공통 업무 로직을 `support`가 아닌 Rule/공통 Service로 분류
8. TCF OFF의 현재 호출은 Controller → Service 직접 호출이라고 확정적으로 기술
9. 구·신 패키지 충돌로 현재 기동이 보장되지 않는다고 명시

이번 분석에서는 파일이나 소스를 수정하지 않았고 테스트도 실행하지 않았습니다.
