## 26. 시스템 후처리 분석 결과

현재 시스템 후처리는 다음 두 단계로 구성됩니다.

1. `ResponseBodyArgumentResolver`: 표준 응답 조립 및 응답 전문 로그
2. `ServicePreventionInterceptor.afterCompletion`: ImageLog 갱신

큰 흐름은 정상입니다. 다만 26번 문서에는 ImageLog 데이터소스 설명과 예외 처리 흐름에서 현행 소스와 다른 부분이 있습니다.

분석 대상:

- [26.시스템후처리.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/26.시스템후처리.md>)
- [ResponseBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java:81>)
- [ServicePreventionInterceptor.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/interceptor/ServicePreventionInterceptor.java:253>)
- [ImageLogHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/imagelog/ImageLogHandler.java:175>)

### 1. 전체 처리 순서

정상 거래의 실제 흐름은 다음과 같습니다.

```text
DefaultFilter
  → ServicePreventionInterceptor.preHandle
      → ImageLog 요청 INSERT
  → OnlineTransactionController
      → TcfFacade
          → Timeout Executor
              → 업무 트랜잭션 BEGIN
              → Handler
              → Facade
              → Service / DAO
              → 업무 후처리
              → Deadline 검사
              → COMMIT
  → ResponseBodyArgumentResolver.beforeBodyWrite
      → 표준 응답 조립
      → 시스템 후처리 로그
      → ServiceContext.responseBody 저장
  → HTTP 응답 기록
  → Interceptor.postHandle
  → Interceptor.afterCompletion
      → ImageLog 응답 UPDATE
  → DefaultFilter finally
      → ServiceContext 제거
      → MDC 제거
```

업무 트랜잭션은 `ResponseBodyArgumentResolver`가 호출되기 전에 이미 종료됩니다.

## 2. 시스템 후처리 1단계: 응답 조립

[ResponseBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java:92>)는 `ResponseBodyAdvice<Object>`입니다.

```java
@ControllerAdvice
@ConditionalOnProperty(
    name = "nhnis.fw.commons.legacy-web.enabled",
    havingValue = "true"
)
public class ResponseBodyArgumentResolver
        implements ResponseBodyAdvice<Object> {
}
```

현재 설정은 다음과 같으므로 활성화되어 있습니다.

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: true
```

### 정상 응답

Service 결과가 일반 DTO이면 다음처럼 조립합니다.

```java
responseBody.set("hdr_nhnis", headerNode);
responseBody.set("dto", bodyNode);
```

결과:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "...",
      "rms_svc_c": "mgcoa9000S0"
    }
  },
  "dto": {
    "totalCount": 10
  }
}
```

### 오류 응답

응답 객체가 `NH_NIS_ERR_DTO`이면 `dto`가 아닌 `result`에 넣습니다.

```java
if (body instanceof NH_NIS_ERR_DTO) {
    responseBody.set("result", errorNode);
}
```

결과:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "..."
    }
  },
  "result": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "온라인 거래 처리시간을 초과했습니다.",
    "errType": "COMMON"
  }
}
```

따라서 현행 표준은 다음과 같습니다.

```text
정상: { hdr_nhnis, dto }
오류: { hdr_nhnis, result }
```

26번 문서 일부의 “에러 DTO도 `dto`에 실린다”는 설명은 현행 소스와 다릅니다. 오류는 `result`에 실립니다.

## 3. 시스템 후처리 로그

응답 조립 과정에서 다음 로그가 기록됩니다.

```text
[시스템 후처리] 시작 ===============================================
[온라인전문][응답][원문] ===============================================
{"hdr_nhnis":{...},"dto":{...}}
[시스템 후처리] 종료 ===============================================
```

오류 응답이면 다음 형태입니다.

```text
[시스템 후처리] 시작 ===============================================
[온라인전문][응답][원문] ===============================================
{"hdr_nhnis":{...},"result":{"stdErrCode":"FW_TIMEOUT",...}}
[시스템 후처리] 종료 ===============================================
```

조립된 응답은 HTTP로 반환되는 동시에 `ServiceContext`에도 저장됩니다.

```java
ServiceContextHolder.getInstance()
        .setResponseBody(prettyResponseBody);
```

이 값은 뒤의 `afterCompletion()`에서 ImageLog의 `RESPONSE_MSG`로 사용합니다.

## 4. `postHandle`에서 처리하지 않는 이유

현재 `postHandle()`은 실질적인 후처리를 하지 않습니다.

```java
@Override
public void postHandle(...) {
    // 시스템 후처리 시작/종료·응답 전문은
    // ResponseBodyAdvice에서 출력한다.
}
```

Spring MVC의 `@ResponseBody` 처리에서는 응답 객체를 HTTP 본문으로 변환하는 과정이 `postHandle()`보다 먼저 진행됩니다.

따라서 표준 응답 봉투 조립은 `ResponseBodyAdvice.beforeBodyWrite()`에서 처리하는 것이 맞습니다.

```text
Controller return
→ ResponseBodyAdvice
→ HttpMessageConverter
→ postHandle
→ afterCompletion
```

## 5. 메타 필드 제거

응답 DTO를 JSON으로 변환한 뒤 다음 필드를 재귀적으로 제거합니다.

```text
dtoLogicalName
fieldPropertyMap
이름이 List로 끝나는 필드
이름이 Array로 끝나는 필드
```

```java
if (fieldName.endsWith("List")
        || fieldName.endsWith("Array")) {
    fieldsToRemove.add(fieldName);
}
```

이 부분은 주의가 필요합니다.

예를 들어 실제 업무 필드가 다음 이름이면:

```text
txIdList
customerList
resultArray
```

메타 정보가 아닌 정상 업무 데이터여도 클라이언트 응답에서 제거됩니다.

업무 후처리 로그뿐 아니라 실제 HTTP 응답에서도 제거된다는 점이 중요합니다. `*List`, `*Array`를 이름만 보고 삭제하지 말고, DataObject 메타 필드인지 명확하게 구분하는 방식이 안전합니다.

## 6. 시스템 후처리 2단계: `afterCompletion`

[ServicePreventionInterceptor.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/interceptor/ServicePreventionInterceptor.java:253>)의 처리 구조는 다음과 같습니다.

```java
if (ex != null) {
    imageLogHandler.exceptionImagelog(
        header,
        responseBody,
        ex
    );

    ServiceContextHolder.removeInstance();
    throw ex;
}

imageLogHandler.postImagelog(
    ctx.getHeader(),
    ctx.getResponseBody()
);
```

처리는 크게 두 경로입니다.

| 구분               | 조건         | ImageLog 처리         |
| ------------------ | ------------ | --------------------- |
| MVC 정상 완료      | `ex == null` | `postImagelog()`      |
| 처리되지 않은 예외 | `ex != null` | `exceptionImagelog()` |

여기서 `ex == null`이 반드시 업무 성공을 의미하지는 않습니다.

`GlobalExceptionHandler`가 예외를 처리해 오류 응답을 정상 생성하면 Spring MVC 관점에서는 예외가 처리된 것이므로 `afterCompletion()`의 `ex`가 `null`일 수 있습니다.

그 경우:

```text
BizException 발생
→ GlobalExceptionHandler가 오류 응답 생성
→ ResponseBodyAdvice가 result 조립
→ afterCompletion(ex == null)
→ postImagelog()
→ result.stdErrCode를 읽어 예외 컬럼 갱신
```

즉, 오류 응답도 반드시 `exceptionImagelog()`로 가는 것은 아닙니다.

## 7. 정상 ImageLog 갱신

`postImagelog()`는 다음 정보를 설정합니다.

```java
dto.setResponseTime(DateUtil.getCurrentTime());
dto.setResponseMsg(resolveWireMsg(inputDto, false));
```

그리고 GUID 기준으로 갱신합니다.

```sql
UPDATE TB_FW_IMAGE_LOG
   SET RESPONSE_TIME = ?,
       RESPONSE_MSG = ?,
       REQUEST_MSG = COALESCE(REQUEST_MSG, ?)
 WHERE GUID = ?
```

처리 결과:

| 결과     | 동작                     |
| -------- | ------------------------ |
| 1건 갱신 | 정상 완료                |
| 0건 갱신 | `no row for guid` 경고   |
| SQL 예외 | 오류 로그 후 예외를 삼킴 |

ImageLog 실패는 업무 응답에 영향을 주지 않습니다.

```java
catch (Exception e) {
    log.error(
        "[ImageLog] postImagelog failed guid={}",
        dto.getGuid(),
        e
    );
}
```

## 8. 오류 결과도 ImageLog 예외로 기록

`postImagelog()`는 응답 JSON에 `result.stdErrCode`가 있는지 검사합니다.

```java
JsonNode result = root.get("result");
JsonNode codeNode = result.get("stdErrCode");
```

오류 코드가 발견되면 다음 정보를 채웁니다.

```text
EXCEPTION_CODE
EXCEPTION_MSG
EXCEPTION_TYPE
RESPONSE_MSG
RESPONSE_TIME
```

`errType`이 없으면 다음 기본값을 사용합니다.

```text
RESULT_ERROR
```

따라서 처리된 예외는 다음 흐름으로 기록됩니다.

```text
GlobalExceptionHandler
→ { hdr_nhnis, result }
→ postImagelog
→ fillExceptionFromResult
→ persistException
```

## 9. 처리되지 않은 예외 ImageLog

`afterCompletion(ex != null)`이면 `exceptionImagelog()`를 호출합니다.

예외별 코드 변환은 다음과 같습니다.

| 예외                      | ImageLog 코드              |
| ------------------------- | -------------------------- |
| `NhBaseException`         | 예외가 가진 `stdErrCode`   |
| `BizException`            | 예외가 가진 업무 코드      |
| `OnlineTimeoutException`  | `FW_TIMEOUT`               |
| `OnlineOverloadException` | `FW_OVERLOADED`            |
| 기타 예외                 | 코드 `null`, 메시지만 저장 |

기존 GUID 행이 없으면 신규 INSERT까지 수행합니다.

```text
UPDATE by GUID
→ updated == 0
→ INSERT
```

## 10. 트랜잭션과 ImageLog 관계

26번 문서에는 다음 취지의 설명이 있습니다.

```text
별도 JDBC(ImageLog용 DS)
```

하지만 현행 소스에는 별도의 ImageLog 전용 DataSource가 없습니다.

`ImageLogHandler`는 단순히 타입으로 `DataSource`를 주입받습니다.

```java
public ImageLogHandler(DataSource dataSource) {
    this.jdbcTemplate = new JdbcTemplate(dataSource);
}
```

현재 [RdwDataSourceConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/config/RdwDataSourceConfig.java:33>)의 `rdwDataSource`가 `@Primary`입니다.

```java
@Bean
@Primary
public DataSource rdwDataSource() {
    ...
}
```

따라서 현재 ImageLog는 업무 DAO와 동일한 `rdwDataSource`를 사용합니다.

다만 실행 시점이 업무 트랜잭션 밖이기 때문에 업무 트랜잭션과 커밋·롤백을 공유하지 않습니다.

```text
동일 DataSource
≠ 동일 트랜잭션

업무 DAO
→ 업무 TX 안

ImageLog postImagelog
→ 업무 TX 종료 후 별도 JDBC 작업
```

정확한 표현은 다음과 같습니다.

```text
ImageLog는 별도 전용 DataSource가 아니라
동일한 Primary RDW DataSource를 사용하지만,
업무 트랜잭션 밖에서 실행되는 독립 JDBC 작업이다.
```

## 11. 타임아웃의 시스템 후처리

타임아웃이 발생하면 다음 순서입니다.

```text
Worker 업무 처리
→ Deadline 초과
→ rollbackOnly
→ 업무 TX ROLLBACK
→ OnlineTimeoutException
→ GlobalExceptionHandler
→ HTTP 504 + NH_NIS_ERR_DTO
→ ResponseBodyAdvice
     { hdr_nhnis, result }
→ afterCompletion
→ postImagelog
→ EXCEPTION_CODE = FW_TIMEOUT
```

업무 후처리 로그가 이미 출력된 다음 사후 Deadline 검사에서 타임아웃이 판정될 수도 있지만, 시스템 후처리는 최종 타임아웃 응답을 기준으로 기록합니다.

따라서 최종 거래 결과를 확인할 때는 업무 후처리보다 시스템 후처리와 ImageLog 결과가 더 정확합니다.

## 12. ServiceContext 정리

성공 경로의 `afterCompletion()`에서는 Context를 직접 제거하지 않습니다.

하지만 최외곽 [DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java:270>)가 `finally`에서 반드시 정리합니다.

```java
finally {
    if (ServiceContextHolder.getInstance() != null) {
        ServiceContextHolder.removeInstance();
    }

    if (!ThreadContext.isEmpty()) {
        ThreadContext.clearAll();
    }
}
```

따라서 정상적인 Filter 경로에서는 ThreadLocal 누수가 방지됩니다.

```text
afterCompletion
→ ImageLog 처리
→ Filter finally
→ ServiceContext 제거
→ MDC 제거
```

다만 Interceptor 예외 경로에서 먼저 `removeInstance()`를 수행하므로 Filter가 다시 확인했을 때는 이미 비어 있습니다.

## 13. 주요 문제점

### 13.1 응답 조립 예외를 삼킨다

```java
catch (Exception e) {
    e.printStackTrace();
}
```

응답 조립 중 오류가 발생해도 부분적으로 만들어진 JSON을 반환할 수 있습니다.

문제점:

- 표준 응답 필드가 누락될 수 있음
- HTTP 상태는 성공인데 응답 전문이 불완전할 수 있음
- Stack Trace가 표준 로깅 체계를 거치지 않음

최소한 로거를 사용하고 표준 시스템 오류로 변환하는 편이 안전합니다.

### 13.2 오류 DTO에 Stack Trace가 포함될 수 있다

`NhBaseException` 처리에서는 상위 15개 Stack Trace를 오류 DTO에 넣습니다.

```java
errorDto.setStackTrace(
    getTop15StackTrace(e.getStackTrace())
);
```

이 DTO가 클라이언트 응답의 `result`로 내려가면 내부 클래스명과 소스 위치가 외부에 노출될 수 있습니다. 운영 응답에서는 제거하는 것이 적절합니다.

### 13.3 `afterCompletion()`에서 예외를 다시 던진다

```java
throw ex;
```

`afterCompletion()`은 이미 요청 처리가 끝나는 단계입니다. 여기서 기존 예외를 다시 던지면 중복 로깅이나 추가 오류 디스패치가 발생할 수 있습니다.

ImageLog를 기록한 뒤 로깅만 하고 종료하는 방향을 검토할 필요가 있습니다.

### 13.4 Advice 적용 범위가 매우 넓다

```java
public boolean supports(...) {
    return true;
}
```

모든 Controller 응답에 표준 봉투를 적용합니다. 파일 다운로드, 문자열, 상태 확인 API 또는 향후 관리 API까지 `{hdr_nhnis, dto}`로 감쌀 수 있습니다.

적용 대상 Controller나 경로를 명시적으로 제한하는 것이 안전합니다.

## 14. 문서 현행화가 필요한 부분

| 문서 내용                       | 현행 소스 기준                                     |
| ------------------------------- | -------------------------------------------------- |
| 오류 DTO도 `dto`에 조립         | 오류는 `result`에 조립                             |
| ImageLog 전용 별도 DS           | 별도 DS 없음, Primary `rdwDataSource` 사용         |
| 예외면 항상 `exceptionImagelog` | 처리된 예외는 `ex == null`이고 `postImagelog` 가능 |
| 성공 경로 Context 정리가 불명확 | `DefaultFilter finally`에서 반드시 정리            |
| `ex != null` 후 재던짐          | 실제로 `throw ex` 수행, 개선 검토 필요             |

## 최종 평가

| 영역                      | 평가                    |
| ------------------------- | ----------------------- |
| 정상 응답 봉투            | 구현됨                  |
| 오류 응답 봉투            | `result`로 구현됨       |
| 응답 전문 로그            | 구현됨                  |
| ImageLog 응답 갱신        | 구현됨                  |
| 오류 결과 ImageLog 기록   | 구현됨                  |
| 업무 트랜잭션과 분리      | 실행 시점상 분리됨      |
| ImageLog 전용 DataSource  | 없음                    |
| Context 정리              | Filter에서 수행         |
| 개인정보 마스킹           | 별도 처리 없음          |
| 시스템 후처리 전용 테스트 | 검색 결과 발견되지 않음 |

핵심적으로 정리하면 다음과 같습니다.

```text
업무 후처리
= Service 정상 반환 결과를 기록
= 업무 TX 안

시스템 후처리
= 최종 HTTP 응답을 표준 전문으로 조립
= 업무 TX 밖
= 성공·오류 응답 모두 ImageLog에 기록
```

이번에는 정적 분석만 수행했으며 파일 수정과 테스트 실행은 하지 않았습니다.
