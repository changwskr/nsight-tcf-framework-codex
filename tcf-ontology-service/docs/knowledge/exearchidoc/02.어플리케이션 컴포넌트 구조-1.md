다만 “현재 구현 설명”과 “PDMG 권장 아키텍처”가 섞여 있습니다. 특히 Controller/Facade 패키지 위치, 트랜잭션 책임, TCF 라우팅 책임은 수정이 필요합니다.

## 1. 전체 판단

문서의 현재 구조는 다음과 같습니다.

```text
entry.handler
  → application.facade
    → application.service
      → persistence.dao
```

그러나 저장소의 공식 아키텍처 규칙은 다음입니다.

```text
entry/handler
  → entry/facade
    → application/service
      → application/rule
        → persistence/dao 또는 persistence/mapper
```

따라서 문서는 현재 작성된 `pdmg-service` 소스를 설명하는 “AS-IS 문서”로는 대체로 맞지만, 저장소 표준 아키텍처 정의서로 사용하기에는 차이가 있습니다.

| 구분       | 현재 소스                | 저장소 권장 구조                            |
| ---------- | ------------------------ | ------------------------------------------- |
| Controller | `application.controller` | `entry.web`                                 |
| Handler    | `entry.handler`          | `entry.handler`                             |
| Facade     | `application.facade`     | `entry.facade`                              |
| Service    | `application.service`    | `application.service`                       |
| Rule       | 없음                     | `application.rule`                          |
| DAO        | `persistence.dao`        | `persistence.dao` 또는 `persistence.mapper` |
| DTO        | 최상위 `dto`             | 명시적 강제 규칙 없음                       |

---

## 2. 현재 실제 컴포넌트 구조

현재 신규 패키지는 다음과 같이 구성되어 있습니다.

```text
nhnis.mg
├─ PdmgApplication
└─ co.a
   ├─ entry
   │  ├─ handler
   │  └─ aspect
   ├─ application
   │  ├─ controller
   │  ├─ facade
   │  └─ service
   ├─ dto
   ├─ persistence
   │  └─ dao
   ├─ config
   ├─ client
   └─ support
```

프로그램은 다음 네 개가 구현되어 있습니다.

```text
mgcoa5530
mgcoa8888
mgcoa9000
mgcoa9999
```

각 프로그램에는 대체로 다음 파일 세트가 존재합니다.

```text
Handler
Controller
Facade
Service
DAO
DTO
Mapper XML
```

따라서 문서의 패키지 트리와 프로그램 단위 파일 세트는 현재 소스와 일치합니다.

## 3. 컴포넌트별 분석

### 3.1 Boot

현재 `PdmgApplication`은 다음 범위를 모두 스캔합니다.

```java
@SpringBootApplication(scanBasePackages = "nhnis")
```

따라서 다음 패키지가 모두 Component Scan 대상입니다.

```text
nhnis.mg.*
nhnis.mg.co.a.*
nhnis.fw.*
```

이 설정은 `pdmg-fw` 공통 Bean까지 자동 등록하는 장점이 있지만, 현재처럼 구 패키지와 신규 패키지가 함께 존재하면 같은 Bean 이름이 충돌할 수 있습니다.

실제로 기존 구조의:

```text
nhnis.mg.application.service.mgcoa5530Service
```

와 신규 구조의:

```text
nhnis.mg.co.a.application.service.mgcoa5530Service
```

는 기본 Bean 이름이 모두 `mgcoa5530Service`입니다.

그러므로 문서의 Boot 설명에는 다음 내용을 추가해야 합니다.

> `PdmgApplication`은 `nhnis` 전체를 스캔하므로 구·신 패키지를 동시에 유지하면 동일 클래스 단순명에 의한 Bean 충돌이 발생할 수 있다.

---

### 3.2 Handler

현재 Handler의 실제 책임은 다음 두 가지입니다.

1. 자신이 처리할 `serviceId` 목록 등록
2. `serviceId`별 Facade 메서드 분기

예를 들어 `mgcoa8888Handler`는:

```java
@Override
public Collection<String> serviceIds() {
    return List.of("mgcoa8888S0", "mgcoa8888D0");
}
```

그리고:

```java
return switch (context.getServiceId()) {
    case S0 -> facade.mgcoa8888S0(dtoBody);
    case D0 -> facade.mgcoa8888D0(dtoBody);
    default -> throw new ServiceHandlerNotFound(...);
};
```

형태로 동작합니다.

문서의 다음 설명은 맞습니다.

```text
Handler는 Facade만 호출한다.
Handler에서 SQL이나 업무 검증을 수행하지 않는다.
```

다만 “HTTP path/serviceId 라우팅 담당은 Handler”라는 표현은 정확하지 않습니다.

실제 책임은 다음과 같이 나뉩니다.

| 처리                                  | 담당                          |
| ------------------------------------- | ----------------------------- |
| HTTP URL 매핑                         | `OnlineTransactionController` |
| 요청에서 serviceId 추출               | `OnlineTransactionController` |
| serviceId에 맞는 Handler 검색         | `TransactionDispatcher`       |
| 같은 업무 Handler 내부 세부 거래 분기 | 각 `TransactionHandler`       |

따라서 문서에는 다음과 같이 표현하는 것이 정확합니다.

> Handler는 HTTP 라우팅을 담당하지 않고, Dispatcher가 선택한 업무 도메인 안에서 serviceId별 Facade 메서드를 분기한다.

---

### 3.3 Facade

현재 Facade는 다음 역할을 수행합니다.

```text
Object dtoBody
  → 구체적인 DTOin 변환
  → 트랜잭션 참여
  → Service 호출
  → DTOout 반환
```

예:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
public mgcoa8888D0DTOout mgcoa8888D0(Object dtoBody) throws Exception {
    mgcoa8888D0DTOin input =
        convert(dtoBody, mgcoa8888D0DTOin.class);

    return service.mgcoa8888D0(input);
}
```

이 부분은 문서와 일치합니다.

다만 패키지 위치는 저장소 권장 구조와 다릅니다.

```text
현재: nhnis.mg.co.a.application.facade
권장: nhnis.mg.co.a.entry.facade
```

Facade는 Handler와 Service 사이의 진입 조정 계층이므로 저장소 규칙에서는 `entry.facade`에 두도록 정의되어 있습니다.

현재 소스를 당장 설명하는 AS-IS 문서라면 `application.facade`를 유지할 수 있지만, 다음 주석은 필요합니다.

> 현재 Facade는 `application.facade`에 구현되어 있으나 저장소 공통 아키텍처 규칙은 `entry.facade`를 권장한다.

---

### 3.4 Service

현재 Service는 실제로 다음 역할을 모두 수행합니다.

```text
입력값 검증
기본값 적용
페이징 계산
검색 조건 조립
업무 분기
DAO 호출
DAO 결과를 DTO로 변환
응답 DTO 조립
```

예를 들어 `mgcoa8888Service`는 다음을 모두 처리합니다.

- `withinSeconds` 범위 제한
- `minElapsedSeconds` 범위 제한
- 페이지 번호와 페이지 크기 보정
- DAO 조회
- Map 결과를 DTO로 변환
- 삭제 대상 GUID 정제
- 처리 결과 코드 설정

따라서 문서의 “검증, 페이징, 업무 규칙, DAO 호출” 설명은 현재 구현에 맞습니다.

하지만 Service에 역할이 상당히 집중되어 있습니다.

권장 구조라면 다음처럼 분리할 수 있습니다.

```text
Service
  → 전체 업무 절차 조정
  → Rule
       입력 검증
       검색 조건 계산
       업무 계산
  → DAO/Mapper
       데이터 접근
```

현재 `application.rule` 패키지가 없으므로 문서가 “컴포넌트 전체 구조”를 설명하려면 Rule 컴포넌트를 누락시키면 안 됩니다.

정확한 구분은 다음과 같습니다.

```text
AS-IS:
  Rule 컴포넌트 없음
  Service가 검증과 계산까지 수행

TO-BE 권장:
  application.rule 추가
  Service는 유스케이스 흐름 조정
  Rule은 검증과 계산 담당
```

### 3.5 Controller

현재 Controller는 다음 조건에서만 등록됩니다.

```java
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "false",
    matchIfMissing = true
)
```

따라서:

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
```

이면 업무별 Controller는 등록되지 않고 공통 `OnlineTransactionController`가 사용됩니다.

TCF OFF에서는 Controller가 Service를 직접 호출합니다.

```text
Controller
  → Service
  → DAO
```

문서의 TCF OFF 호출 흐름은 현재 구현과 일치합니다.

그러나 두 가지 문제가 있습니다.

첫째, 저장소 권장 패키지는 `application.controller`가 아니라 `entry.web`입니다.

둘째, Controller가 Facade를 우회하므로 다음 기능도 함께 우회합니다.

```text
Facade의 DTO 변환
Facade의 @Transactional
Handler의 serviceId 분기
TimeoutExecutor의 외부 트랜잭션
```

Service Pointcut은 여전히 적용되지만 명시적인 트랜잭션이 없는 상태가 됩니다.

따라서 문서의 다음 표현:

> 일관된 TX·선후처리를 원하면 Controller → Facade → Service가 더 맞다.

는 “더 맞다”가 아니라 다음처럼 강하게 정의해야 합니다.

> TCF OFF에서도 트랜잭션 일관성을 보장하려면 Controller는 Service를 직접 호출하지 않고 Facade를 호출해야 한다.

권장 흐름은 다음입니다.

```text
Controller
  → Facade
      → TX BEGIN
      → Service
          → 업무 선처리
          → DAO
          → 업무 후처리
      → TX COMMIT
```

### 3.6 Aspect

현재 `BizPrePostAspect` Pointcut은 다음 Service 계층입니다.

```java
execution(
    public * nhnis.mg.co.a.application.service..*(..)
)
```

따라서 문서의 다음 설명은 맞습니다.

```text
Facade → Service 진입 전 업무 선처리
Service 정상 반환 후 업무 후처리
```

다만 정확히는 `@AfterReturning`이므로 정상 반환 때만 후처리가 실행됩니다.

```text
정상 반환: 후처리 실행
예외 발생: 후처리 실행 안 됨
```

또한 Aspect 패키지는 현재 `entry.aspect`이지만, 이 Aspect는 Service 구현에 직접 의존하지 않고 Pointcut으로 횡단 관심사를 적용합니다.

문서 의존 방향에서:

```text
entry.aspect → application.service
```

라고 표현하면 Java 코드 의존처럼 보일 수 있습니다. 다음 표현이 더 정확합니다.

```text
entry.aspect --AOP 적용 대상--> application.service
```

### 3.7 DAO와 Mapper XML

현재 `persistence.dao`의 DAO는 클래스가 아니라 MyBatis Mapper 인터페이스입니다.

```java
@RDWMapper
public interface mgcoa8888DAO {
    List<Map<String, Object>> mgcoa8888S0_S0(...);
    int mgcoa8888D0_D0(...);
}
```

그리고 `RdwDataSourceConfig`가 다음 패키지를 스캔합니다.

```java
@MapperScan(
    basePackages = "nhnis.mg.co.a.persistence.dao",
    sqlSessionTemplateRef = "rdwSqlSessionTemplate"
)
```

따라서 현재 구조에서는:

```text
DAO 인터페이스 = MyBatis Mapper 인터페이스
Mapper XML = 실제 SQL
```

입니다.

문서에서 DAO와 Mapper를 서로 다른 구현 컴포넌트처럼 설명하면 혼동될 수 있습니다. 다음과 같이 표현하는 것이 정확합니다.

```text
persistence.dao:
  MyBatis Mapper 인터페이스

rdw.mg.co.a/*.xml:
  해당 인터페이스의 SQL 구현
```

저장소 표준은 `persistence.dao` 또는 `persistence.mapper`를 허용하지만, 현재 구현은 DAO 방식입니다.

## 4. 실제 TCF ON 호출 흐름

문서에는 TimeoutExecutor가 생략되어 있습니다. 현재 실제 구조는 다음과 같습니다.

```text
DefaultFilter
  → ServicePreventionInterceptor
  → OnlineTransactionController
  → TcfFacade
  → OnlineTimeoutExecutor
       ↓ 작업 스레드
       TX BEGIN
       → TransactionDispatcher
       → Handler
       → Facade
       → BizPrePostAspect Before
       → Service
       → DAO
       → Mapper XML
       → BizPrePostAspect AfterReturning
       → TX COMMIT
```

예외 또는 타임아웃이면:

```text
Service/DAO 예외
  → 업무 후처리 미실행
  → 예외 전파
  → TX ROLLBACK
```

따라서 문서의 TCF ON 흐름에는 반드시 `OnlineTimeoutExecutor`를 추가해야 합니다.

## 5. 트랜잭션 책임 정정

문서의 책임 매트릭스에는 다음과 같이 되어 있습니다.

```text
DB commit / rollback → Facade
```

이것은 일부 조건에서만 맞습니다.

정확한 책임은 다음과 같습니다.

| 실행 조건                                | 트랜잭션 시작·종료 담당 |
| ---------------------------------------- | ----------------------- |
| TCF ON + Timeout ON                      | `OnlineTimeoutExecutor` |
| TCF ON + Timeout OFF                     | Facade `@Transactional` |
| TCF OFF + Controller가 Service 직접 호출 | 명시적 트랜잭션 없음    |
| TCF OFF + Controller가 Facade 호출       | Facade `@Transactional` |

따라서 책임 매트릭스는 다음으로 바꾸는 것이 좋습니다.

```text
DB TX 경계
  → 기본 업무 경계: Facade
  → Timeout 활성 TCF 거래의 최외곽 경계: OnlineTimeoutExecutor
```

## 6. 의존 방향에서 수정할 부분

현재 문서의 의존 방향은 AS-IS 소스와 일치합니다.

```text
entry.handler
  → application.facade
  → application.service
  → persistence.dao
```

하지만 권장 구조는 다음이어야 합니다.

```text
entry.handler
  → entry.facade
  → application.service
  → application.rule
  → persistence.dao 또는 persistence.mapper
```

Controller까지 포함하면:

```text
TCF ON
  pdmg-fw.entry.web
    → entry.handler
    → entry.facade
    → application.service
    → application.rule
    → persistence

TCF OFF
  entry.web
    → entry.facade
    → application.service
    → application.rule
    → persistence
```

TCF ON/OFF 모두 Facade 이하를 공통으로 사용하면 업무 실행 구조와 트랜잭션 경계가 일관됩니다.

## 7. 문서에서 잘못되거나 불완전한 부분

수정 우선순위는 다음과 같습니다.

### 중요

1. `DB commit / rollback = Facade`를 실행 조건별로 구분
2. TCF ON 흐름에 `OnlineTimeoutExecutor`와 외부 TX 추가
3. `HTTP/serviceId 라우팅 = Handler`를 Controller·Dispatcher·Handler 책임으로 분리
4. TCF OFF Controller가 Service를 직접 호출해 Facade TX를 우회한다고 명시
5. 현재 애플리케이션은 구·신 패키지 Bean 충돌로 정상 기동이 차단된 상태임을 표시

### 아키텍처 정합성

6. `application.controller`와 권장 `entry.web` 차이 표시
7. `application.facade`와 권장 `entry.facade` 차이 표시
8. 누락된 `application.rule` 컴포넌트 추가
9. DAO가 실제로는 MyBatis Mapper 인터페이스라는 점 명시
10. 외부 연동은 일반 Client만 아니라 `pdmg-fw`/TCF 연동 체계 사용 원칙 추가

### 표현 보완

11. `@AfterReturning`은 정상 반환에만 실행
12. Aspect의 Pointcut 관계와 Java 의존 관계 구분
13. TCF OFF를 단순 호환 구조가 아니라 트랜잭션 보장 제한이 있는 구조로 표시
14. 신규 거래 체크리스트에 Rule과 테스트 추가
15. Mapper namespace·statement ID 검증 항목 추가

---

## 8. 이 문서의 올바른 최종 정의

이 문서는 다음 두 관점으로 분리해서 작성해야 가장 이해하기 쉽습니다.

### AS-IS

```text
Handler
  → application.facade
  → application.service
  → persistence.dao(MyBatis Mapper)
  → Mapper XML
```

- TCF ON + Timeout ON이면 TimeoutExecutor가 최외곽 TX 담당
- TCF OFF이면 Controller가 Service를 직접 호출
- Rule 계층 없음
- 구·신 패키지 중복 존재

### 권장 아키텍처

```text
entry.web 또는 entry.handler
  → entry.facade
  → application.service
  → application.rule
  → persistence.dao/mapper
```

- TCF ON/OFF 모두 Facade 이하 공통 사용
