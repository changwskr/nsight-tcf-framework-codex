# 성능 감시 (PDMG)

현재 성능 감시는 **로그 기반**이며, 구간을 나눠 추적한다.  
관련: [tcf.md](./tcf.md) · [pdmg-service 트랜잭션흐름.md](./pdmg-service%20트랜잭션흐름.md)

## 1. HTTP·시스템 구간 (pdmg-fw)

`DefaultFilter` → `ServicePreventionInterceptor` 가 요청 진입부터 시스템 선·후처리·ImageLog까지 다룬다.

포함되는 시간은 대략 다음과 같다.

```text
DefaultFilter / Security
+ JSON·전문 해석
+ 시스템 선처리 · ImageLog INSERT
+ OnlineController → Handler → Facade → Service → DB
+ 시스템 후처리 · ImageLog UPDATE
= 요청 전체 체감 시간
```

흐름 로그는 `PdmgTxLog` / `PdmgTxFlowLog` 등으로 GUID·구간을 남긴다.  
ImageLog에 요청/응답·처리 결과가 남으면 GUID로 한 거래를 추적할 수 있다.

## 2. 업무 TX·선후처리 구간

- **Facade `@Transactional`**: DB 트랜잭션 구간 (commit/rollback)
- **`BizPrePostAspect`**: Service 전후 업무 선·후처리 (`[업무 선처리] 호출: …`)
- **`PdmgBizTxFlowAspect`**: TX-FLOW 진입/이탈 로그 (`entry.aspect`)

업무 시간이 HTTP 전체보다 짧으면, 차이는 필터·직렬화·ImageLog 등 바깥 구간이다.

timeout으로 강제 중단하려면 **공통 OnlineTimeoutExecutor** (`nhnis.fw.timeout`) 가 1차다.  
→ [20.타임아웃.md](./20.타임아웃.md)

Facade `@Transactional(timeout=…)` 는 **보조(2차)** 이며, 공통 Executor가 켜진 환경에서는 보통 쓰지 않는다.  
→ (구문서) [롤백아키텍처 4초지나면롤백되나.md](./롤백아키텍처%204초지나면롤백되나.md)

## 3. SQL별 실행 시간

`nhnis.mg.co.a.config.MybatisLogInterceptor` 가 MyBatis `query` / `update` 를 가로챈다.

```java
long startedAt = System.currentTimeMillis();
try {
    return invocation.proceed();
} finally {
    long elapsed = System.currentTimeMillis() - startedAt;
    log.debug("{} | param={} | {}ms", sqlId, parameter, elapsed);
}
```

기록 예:

```text
mgcoa9999S0_S0_count | param={...} | 12ms
mgcoa9999S0_S0       | param={...} | 85ms
```

`log4j2.xml` 에서 해당 로거가 `DEBUG` 이다.

```xml
<Logger name="nhnis.mg.co.a.config.MybatisLogInterceptor" level="debug" .../>
```

## 5. 현재 감시의 한계

| 항목 | 상태 |
|------|------|
| 요청·구간 로그 | 있음 (Filter/Interceptor/TX-FLOW) |
| SQL 실행시간 DEBUG | 있음 |
| 느린 거래 자동 WARN 임계치 설정 | 환경·로거에 의존 (구 `nsight.tcf.slow-transaction-ms` Pdmk 방식과 동일하지 않음) |
| 느린 SQL WARN | 없음 (시간 기록만) |
| 평균·백분위 통계 / 대시보드 | 없음 |
| 트랜잭션 강제 timeout | **OnlineTimeoutExecutor** (공통) · Facade timeout은 보조 |

즉 “느리면 로그·GUID·serviceId로 추적하는 단계”이며 APM 집계는 아직 아니다.
