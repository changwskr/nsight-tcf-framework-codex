## 분석 결론

[06.네이밍 형식.md](./06.네이밍%20형식.md)는 `MG-NAMING_CONVENTION.md`를 상세 예제로 풀어낸 문서이며, 프로그램 ID·서비스 ID·Handler·Facade·Service·DTO·DAO·Mapper 연결 규칙은 현재 `nhnis.mg.co.a.*` 소스와 대부분 일치합니다.

다만 다음과 같은 중요한 오류와 실제 소스 불일치가 있습니다.

1. 서비스 ID 길이가 10자가 아니라 11자
2. 오류 코드 규칙과 실제 코드가 불일치
3. SQL ID 보조 접미사 `_exists` 누락
4. DTO 필드는 camelCase라는 규칙을 실제 DTO가 일부 위반
5. 실패 응답 형식 설명이 실제 ResponseBodyAdvice 동작과 다름 (`result` vs `dto`)
6. 트랜잭션 담당을 Facade로만 설명한 부분이 Timeout ON 구조와 불일치
7. `entry.facade` 금지 규칙이 저장소 공식 아키텍처와 충돌
8. (해소) 구·신 패키지 공존 — 현재는 `nhnis.mg.co.a.*`로 통합됨

---

## 1. 서비스 ID 구조

문서가 정의한 서비스 ID 구조는 다음과 같습니다.

```text
[대구분2][업무2][세부1][식별4][구분자1][순번1]

mg + co + a + 8888 + S + 0
= mgcoa8888S0
```

구조 자체는 현재 소스와 일치합니다.

```text
mg          대구분
co          업무 구분
a           세부 업무
8888        프로그램 식별번호
S           처리 구분자
0           순번
```

하지만 총길이 계산이 잘못되었습니다.

```text
2 + 2 + 1 + 4 + 1 + 1 = 11
```

실제로:

```text
mgcoa8888S0
12345678901
```

은 11자리입니다.

따라서 체크리스트의 다음 문장은 틀렸습니다.

```text
서비스 ID 10자 구조
```

다음으로 수정해야 합니다.

```text
서비스 ID 11자 구조
대구분2 + 업무2 + 세부1 + 식별4 + 구분자1 + 순번1
```

## 2. 프로그램 접두와 서비스 ID 분리

문서의 가장 중요한 네이밍 원칙은 현재 구현과 잘 맞습니다.

### 프로그램 접두

```text
mgcoa8888
```

다음 클래스에 사용합니다.

```text
mgcoa8888Handler
mgcoa8888Facade
mgcoa8888Service
mgcoa8888Controller
mgcoa8888DAO
mgcoa8888-ORA.xml
```

### 서비스 ID

```text
mgcoa8888S0
mgcoa8888D0
```

다음 요소에 사용합니다.

```text
URL
Handler 상수
Facade 메서드
Service 메서드
DTO 타입
SQL ID 앞부분
```

실제 `mgcoa8888` 구현도 이 구조를 따릅니다.

```text
Handler    : mgcoa8888Handler
Facade     : mgcoa8888Facade
Service    : mgcoa8888Service
Controller : mgcoa8888Controller
DAO        : mgcoa8888DAO
Mapper     : mgcoa8888-ORA.xml

조회 거래 : mgcoa8888S0
삭제 거래 : mgcoa8888D0
```

이 부분은 문서와 구현이 일치합니다.

## 3. 구분자 분석

현재 문서의 구분자는 다음과 같습니다.

| 구분자 | 의미   |
| ------ | ------ |
| `S`    | 조회   |
| `C`    | 등록   |
| `U`    | 수정   |
| `D`    | 삭제   |
| `A`    | 혼합   |
| `R`    | 리포트 |

현재 실제 구현에서는 다음 구분자가 확인됩니다.

```text
S
C
U
D
```

예:

```text
mgcoa9000S0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
```

`A`, `R`은 문서상 허용 규칙이지만 현재 PDMG 샘플에 구현된 거래는 없습니다.

따라서 다음처럼 구분하는 것이 정확합니다.

```text
현재 사용: S, C, U, D
예약/확장: A, R
```

## 4. Java 타입명 분석

문서는 일반 Java 규칙과 다르게 업무 타입을 소문자로 시작하도록 정의합니다.

```text
mgcoa8888Handler
mgcoa8888Facade
mgcoa8888Service
mgcoa8888DAO
```

일반적인 Java 타입명은 PascalCase이므로 보통 다음과 같이 작성합니다.

```text
Mgcoa8888Handler
```

하지만 PDMG에서는 Mapper namespace, 기존 소스, 전문 코드 생성 결과와의 호환을 위해 소문자 프로그램 접두를 유지하고 있습니다.

문서도 이를 예외 규칙으로 명시합니다.

```text
업무 타입:
  소문자로 시작하는 PDMG 호환 규칙

FW/Config/Aspect:
  PascalCase
```

현재 실제 타입도 이 규칙을 따릅니다.

```text
업무:
  mgcoa8888Handler
  mgcoa8888Service
  mgcoa8888DAO

공통:
  BizPrePostAspect
  RdwDataSourceConfig
  SecurityConfig
  GlobalExceptionHandler
```

따라서 이 부분은 일반 Java 표준에서는 예외지만 현재 프로젝트 규칙으로는 일관됩니다.

## 5. Handler 네이밍

현재 Handler 이름은 프로그램 접두에 `Handler`를 붙입니다.

```text
mgcoa5530Handler
mgcoa8888Handler
mgcoa9000Handler
mgcoa9999Handler
```

서비스 ID 전체를 클래스명에 넣지 않는 규칙도 적용되어 있습니다.

```text
좋음:
  mgcoa8888Handler

사용하지 않음:
  mgcoa8888S0Handler
  mgcoa8888D0Handler
```

하나의 Handler가 동일 프로그램의 여러 거래를 담당합니다.

```java
private static final String S0 = "mgcoa8888S0";
private static final String D0 = "mgcoa8888D0";
```

다만 상수 이름이 `S0`, `D0`로만 되어 있어 클래스 내부에서는 이해할 수 있지만, 더 명확한 이름을 원한다면 다음처럼 사용할 수 있습니다.

```text
SERVICE_ID_SELECT
SERVICE_ID_DELETE
```

현재 네이밍 정본이 `S0`, `D0`를 허용하므로 오류는 아닙니다.

## 6. Facade와 Service 메서드

문서는 Facade와 Service 메서드명을 서비스 ID와 동일하게 정의합니다.

```java
mgcoa8888S0(...)
mgcoa8888D0(...)
```

현재 실제 소스도 이 규칙을 따릅니다.

```text
Handler
  → facade.mgcoa8888S0(dtoBody)

Facade
  → service.mgcoa8888S0(input)

Service
  → DAO SQL 호출
```

일반적인 Java 업무 메서드라면 다음과 같은 의미 중심 이름을 사용할 수 있습니다.

```text
findImageLogs
deleteImageLogs
```

하지만 PDMG에서는 거래 추적성과 생성 규칙 때문에 서비스 ID 자체를 메서드명으로 사용합니다.

이것은 일반 Java camelCase 동사 규칙과 충돌하지만, PDMG 거래 프로그램에는 명시적인 예외 규칙입니다.

따라서 문서에서 다음 두 규칙의 우선순위를 명확히 해야 합니다.

```text
일반 공통 메서드:
  동사형 camelCase

거래 진입 메서드:
  서비스 ID 전체를 그대로 사용
```

## 7. Controller와 URL

현재 업무 Controller는 다음 URL 규칙을 따릅니다.

```text
POST /mgcoa5530S0
POST /mgcoa8888S0
POST /mgcoa8888D0
POST /mgcoa9000S0
POST /mgcoa9000C0
POST /mgcoa9000U0
POST /mgcoa9000D0
POST /mgcoa9999S0
```

문서의 RPC형 URL 규칙과 일치합니다.

```java
@PostMapping("/mgcoa8888S0")
```

다만 문서의 다음 표현은 일반 API 규칙과 충돌합니다.

```text
API 경로는 소문자를 사용한다.
```

실제 URL에는 대문자 구분자가 들어갑니다.

```text
/mgcoa8888S0
```

따라서 정확한 규칙은 다음과 같습니다.

> 일반 URL 세그먼트는 소문자를 사용하지만 PDMG 거래 URL은 서비스 ID 계약을 그대로 사용하므로 구분자 `S/C/U/D`가 대문자다.

## 8. DTO 타입명

현재 DTO 이름은 서비스 ID 전체에 접미사를 붙입니다.

```text
mgcoa8888S0DTOin
mgcoa8888S0DTOout
mgcoa8888S0DTOSub0
mgcoa8888D0DTOin
mgcoa8888D0DTOout
```

이 부분은 문서와 소스가 일치합니다.

접미사 표기도 일반 Java 관례와 다릅니다.

```text
PDMG:
  DTOin
  DTOout
  DTOSub0

일반 Java:
  DtoIn
  DtoOut
  SubDto
```

하지만 전문 생성기 및 기존 계약과의 호환을 위한 프로젝트 예외로 명시되어 있으므로 현재 구조에서는 유효합니다.

## 9. DTO 메서드 네이밍 위반

문서는 메서드와 필드에 camelCase를 사용하도록 규정합니다.

그러나 생성 DTO에는 다음과 같은 메서드가 있습니다.

```text
getmgcoa5530S0DTOSub0List
clearmgcoa5530S0DTOSub0
ensureCapacitymgcoa5530S0DTOSub0
sizemgcoa5530S0DTOSub0
addmgcoa5530S0DTOSub0
```

일반 camelCase라면 다음과 같아야 합니다.

```text
getMgcoa5530S0DtoSub0List
clearMgcoa5530S0DtoSub0
ensureCapacityMgcoa5530S0DtoSub0
sizeMgcoa5530S0DtoSub0
addMgcoa5530S0DtoSub0
```

하지만 이 메서드들은 SuperSpring DTO 생성 패턴에 따른 것으로 보입니다.

따라서 문서에는 예외를 추가해야 합니다.

> 자동 생성된 `DataObject` DTO의 컬렉션 접근 메서드와 `MsgJson` 메서드는 생성기 계약을 우선하며 일반 Java camelCase 검수 대상에서 제외하거나 별도 생성 DTO 규칙을 적용한다.

이 예외가 없으면 현재 DTO 대부분이 문서 규칙 위반으로 판정됩니다.

## 10. DTO 필드명 위반

문서는 DTO와 JSON 필드를 camelCase로 정의합니다.

```text
pageNo
totalCount
serviceId
```

실제로 많은 DTO 필드는 이 규칙을 따릅니다.

```text
trtBrc
basDt
pageNo
pageSize
salzTipKdc
```

하지만 등록·수정·삭제 결과 DTO에는 다음 대문자 필드가 있습니다.

```text
PROC_CNT
RSLT_CD
RSLT_MSG
```

관련 getter/setter도 다음과 같습니다.

```text
getPROC_CNT()
setPROC_CNT()
getRSLT_CD()
setRSLT_CD()
getRSLT_MSG()
setRSLT_MSG()
```

이는 문서의 camelCase 규칙과 맞지 않습니다.

camelCase로 통일한다면:

```text
procCnt
rsltCd
rsltMsg
```

가 되어야 합니다.

다만 외부 전문 계약이 대문자 필드명을 요구한다면 Java 필드는 camelCase로 두고 JSON 이름만 고정하는 방법이 안전합니다.

```java
@JsonProperty("PROC_CNT")
private Integer procCnt;
```

현재 문서에는 이 호환 전략이 없습니다.

## 11. SQL ID 분석

문서의 기본 SQL ID 형식은 다음입니다.

```text
[서비스ID]_[DML구분][순번]
```

현재 소스는 이 규칙을 잘 따릅니다.

```text
mgcoa5530S0_S0
mgcoa8888S0_S0
mgcoa8888D0_D0
mgcoa9000C0_C0
mgcoa9000U0_U0
mgcoa9000D0_D0
mgcoa9999S0_S0
```

건수 조회도 문서 규칙과 일치합니다.

```text
mgcoa5530S0_S0_count
mgcoa8888S0_S0_count
mgcoa9000S0_S0_count
```

하지만 실제 Mapper에는 문서에 정의되지 않은 접미사가 있습니다.

```text
mgcoa9000S0_S0_exists
```

따라서 SQL ID 보조 접미사는 최소 다음과 같이 정의해야 합니다.

| 접미사    | 의미           |
| --------- | -------------- |
| 없음      | 본 조회/처리   |
| `_count`  | 목록 전체 건수 |
| `_exists` | 존재 여부 확인 |

그렇지 않으면 실제 `mgcoa9000S0_S0_exists`가 네이밍 위반으로 판정됩니다.

## 13. 오류 코드 규칙 불일치

문서는 오류 코드를 다음과 같이 설명합니다.

```text
FW + 숫자 4자리
```

예:

```text
FW0001
FW0401
FW9999
```

하지만 실제 `exceptionCode.yml`에는 세 가지 형식이 혼재합니다.

### FW 숫자형

```text
FW0001
FW0002
FW0003
FW0401
FW0403
FW9999
```

### 업무 도메인 숫자형

```text
MP0404
MP0409
```

### 의미형 공통 코드

```text
FW_TIMEOUT
FW_OVERLOADED
```

따라서 “오류 코드는 FW+4자리”라는 규칙은 현재 구현을 설명하지 못합니다.

정확한 규칙은 다음처럼 분리해야 합니다.

```text
공통 숫자형:
  FWdddd

업무 오류:
  [업무코드]dddd
  예: MP0404

기술 상태형:
  FW_[UPPER_SNAKE_CASE]
  예: FW_TIMEOUT, FW_OVERLOADED
```

또는 장기적으로 한 가지 형식으로 통합해야 합니다.

## 14. 실패 응답 형식

문서에는 다음처럼 되어 있습니다.

```text
성공:
  { hdr_nhnis, dto }

실패:
  NH_NIS_ERR_DTO
```

하지만 `ResponseBodyArgumentResolver`가 활성화되어 있으면 오류 본문은 **`dto`가 아니라 `result`** 에 실립니다. (`dto`는 업무 데이터 전용)

실제 최종 HTTP 실패 응답은 다음 형태입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {}
  },
  "result": {
    "stdErrCode": "FW_TIMEOUT",
    "stdErrMsgCntn": "온라인 거래 처리시간을 초과했습니다.",
    "errType": "COMMON"
  }
}
```

성공 시에는 다음 형태입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {}
  },
  "dto": { }
}
```

따라서 다음처럼 구분해야 정확합니다.

```text
예외 Handler가 생성하는 업무 본문:
  NH_NIS_ERR_DTO

ResponseBodyAdvice 적용 후 HTTP 응답:
  성공 → { hdr_nhnis, dto }
  실패 → { hdr_nhnis, result: NH_NIS_ERR_DTO }
```

## 15. 패키지 네이밍 충돌

문서에서는 다음을 나쁜 패키지로 정의합니다.

```text
nhnis.mg.co.a.entry.facade
```

그리고 Facade는 다음에 둔다고 규정합니다.

```text
nhnis.mg.co.a.application.facade
```

이는 현재 소스와는 일치합니다.

하지만 저장소 공식 아키텍처 규칙은 다음입니다.

```text
entry.handler
  → entry.facade
  → application.service
  → application.rule
```

따라서 `entry.facade`를 절대 금지로 정의하면 저장소 규칙과 충돌합니다.

문서에서는 다음 중 하나를 최종적으로 선택해야 합니다.

### 현재 PDMG AS-IS 유지

```text
application.facade
application.controller
```

### 저장소 표준으로 전환

```text
entry.facade
entry.web
```

현재 상태를 설명하는 문서라면 다음처럼 써야 합니다.

> 현재 PDMG 소스는 `application.facade`를 사용한다. 저장소 공통 표준은 `entry.facade`를 사용하므로, 문서에는 “PDMG 배치 기준”임을 밝히고 `entry.facade`를 일반적인 금지 패키지로만 규정하지 않는다.

---

## 16. 트랜잭션 네이밍 설명 오류

문서에서는 다음처럼 설명합니다.

```text
DB commit/rollback은 Facade의 @Transactional이 담당한다.
```

Timeout OFF에서는 맞습니다.

하지만 Timeout ON에서는 다음과 같습니다.

```text
DefaultOnlineTimeoutExecutor
  → TransactionTemplate BEGIN
  → Handler
  → Facade @Transactional(REQUIRED) 참여
  → Service/DAO
  → Commit/Rollback
```

따라서 네이밍 문서에서도 Facade 책임을 다음처럼 표현해야 정확합니다.

> Facade는 `@Transactional`을 선언하는 기본 업무 트랜잭션 지점이다. Timeout ON에서는 외부 TimeoutExecutor 트랜잭션에 참여한다.

## 17. 로그·MDC 키 분석

문서에서 정의한 MDC 키는 다음입니다.

```text
guid
traceId
userId
serviceId
ip
sqlId
ifId
errCode
```

현재 실제 사용이 확인되는 주요 키는 다음입니다.

```text
guid
userId
serviceId
ip
sqlId
errCode
```

`traceId`, `ifId`는 문서상 표준이지만 현재 핵심 실행 경로에서 사용이 제한적이거나 확인되지 않습니다.

따라서 다음처럼 분리하는 것이 좋습니다.

```text
현재 사용:
  guid, userId, serviceId, ip, sqlId, errCode

예약/확장:
  traceId, ifId
```

또한 현재 Log4j2 `ThreadContext`와 SLF4J `MDC`를 혼용합니다.

```text
FW:
  ThreadContext

MyBatisLogInterceptor:
  MDC
```

두 API는 Log4j2 바인딩 환경에서 연동될 수 있지만, 문서에는 MDC 구현 API를 하나로 통일하거나 “논리적 MDC 키”라는 표현이 필요합니다.

## 18. 네이밍 기준 문서 중복

현재 네이밍 관련 문서가 최소 세 개 존재합니다.

```text
MG-NAMING_CONVENTION.md
네이밍원칙.md
06.네이밍 형식.md
```

`06` 문서는 마스터 규약이 `MG-NAMING_CONVENTION.md`라고 선언하지만 내용이 매우 상세해서 사실상 또 하나의 규약처럼 동작합니다.

실제로 규칙 간 차이도 발생하고 있습니다.

```text
일반 메서드: 동사형 camelCase
거래 메서드: 서비스 ID 사용

일반 타입: PascalCase
업무 타입: 소문자 시작

DTO 필드: camelCase
실제 결과 DTO: UPPER_SNAKE_CASE
```

따라서 문서 역할을 명확히 해야 합니다.

```text
MG-NAMING_CONVENTION.md
  → 유일한 정본

06.네이밍 형식.md
  → 정본을 변경하지 않는 예제·해설서

네이밍원칙.md
  → 일반 Java 원칙과 예외 설명
```

## 19. 현재 소스 준수 상태

| 영역                               |           준수 상태 |
| ---------------------------------- | ------------------: |
| 서비스 ID 프로그램 구조            |                높음 |
| Handler/Facade/Service 클래스 접두 |                높음 |
| URL과 서비스 ID 일치               |                높음 |
| Facade/Service 메서드명            |                높음 |
| DTO 타입명                         |                높음 |
| DAO와 Mapper ID 일치               |                높음 |
| Mapper namespace                   |                높음 |
| SQL 보조 접미사                    |         문서 불완전 |
| DTO 필드 camelCase                 |           일부 위반 |
| 생성 DTO 메서드 camelCase          |           다수 예외 |
| 오류 코드 형식                     |                혼재 |
| 패키지 표준                        |  저장소 규칙과 충돌 |
| 실패 응답 봉투                     | `result` 미반영 |
| TX 책임 설명                       | Timeout 구조 미반영 |

전체적으로 `co.a` 거래 프로그램의 핵심 식별 네이밍은 약 85% 이상 일관됩니다. 반면 Java 일반 네이밍, 오류 코드, 생성 DTO 예외와 패키지 표준까지 포함하면 문서 정확도는 약 70~75%입니다. 구·신 패키지 공존으로 인한 네이밍 이원화는 **현재 해소**되었습니다.

## 20. 우선 수정해야 할 항목

1. 서비스 ID를 10자가 아닌 11자로 정정
2. 오류 코드 패턴에 `MPdddd`, `FW_TIMEOUT`, `FW_OVERLOADED` 반영
3. SQL ID 접미사 `_exists` 추가
4. 자동 생성 DTO 메서드 네이밍 예외 규칙 추가
5. `PROC_CNT`, `RSLT_CD`, `RSLT_MSG` 처리 방침 명시
6. 실패 응답을 `{hdr_nhnis, result}` 로 정정 (`dto`는 업무 전용)
7. `entry.facade` 절대 금지 규칙을 “PDMG 배치”로 한정
8. Timeout ON에서 실제 Commit/Rollback 주체를 Executor로 정정
9. 현재 사용 MDC 키와 예약 키 분리
10. (해소) 구·신 패키지 공존 서술은 삭제 — `nhnis.mg.co.a.*` 단일 적용

이번 분석에서는 검증 문서의 형식·문체를 유지한 채 잘못된 전제만 수정했습니다.
