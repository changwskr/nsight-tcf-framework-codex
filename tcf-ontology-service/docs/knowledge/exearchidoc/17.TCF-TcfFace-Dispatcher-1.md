## 17. TCF — TcfFacade · TransactionDispatcher 분석 결과

먼저 명칭부터 정리하면 문서 파일명의 `TcfFace`는 오타입니다.

```text
잘못된 명칭: TcfFace
실제 클래스: TcfFacade
```

문서 제목 자체는 현재 이를 명시하고 있습니다.

핵심 구조는 다음과 같습니다.

```text
OnlineTransactionController
  ↓
TcfFacade
  ↓
OnlineTimeoutExecutor
  ↓
TransactionDispatcher
  ↓
TransactionHandler
  ↓
업무 Facade
  ↓
Service → DAO
```

---

## 1. 각 컴포넌트 역할

| 컴포넌트                | 역할                               |
| ----------------------- | ---------------------------------- |
| `TcfFacade`             | Controller와 TCF 실행기의 연결점   |
| `OnlineTimeoutExecutor` | 타임아웃·worker·외부 트랜잭션 관리 |
| `TransactionContext`    | serviceId와 요청 Context 전달      |
| `TransactionDispatcher` | serviceId에 해당하는 Handler 검색  |
| `TransactionHandler`    | 업무별 Facade 호출 및 거래 분기    |

중요한 구분:

```text
TcfFacade
= TCF 실행 조정

업무 mgcoa*Facade
= 업무 유스케이스와 @Transactional 경계
```

---

# 2. 전체 실행 흐름

현재 설정은 다음과 같습니다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    timeout:
      enabled: true
      milliseconds: 5000
      pool-size: 20
      queue-capacity: 100
```

따라서 현재 실행 흐름은:

```text
HTTP 요청 스레드
  ↓
OnlineTransactionController
  ↓
TcfFacade.process(serviceId, dtoBody)
  ├─ TransactionContext 생성
  └─ OnlineTimeoutExecutor.execute(...)
       ↓
worker thread
  ├─ ServiceContext / MDC 설치
  ├─ TransactionTemplate TX 시작
  └─ TransactionDispatcher.dispatch(...)
       ↓
serviceId로 Handler 검색
  ↓
Handler.handle(dtoBody, context)
  ↓
업무 Facade @Transactional(REQUIRED)
  ↓
Service
  ↓
DAO / SQL
  ↓
정상: commit
예외·timeout: rollback
```

# 3. TcfFacade

소스: [TcfFacade.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/core/facade/TcfFacade.java:28>)

핵심 메서드:

```java
public Object process(
        String serviceId,
        Object dtoBody) throws Exception {

    TransactionContext context =
            TransactionContext.fromCurrent(serviceId);

    Object result = onlineTimeoutExecutor.execute(
            () -> dispatcher.dispatch(
                    serviceId,
                    dtoBody,
                    context));

    return result;
}
```

### 입력

| 값               | 설명                               |
| ---------------- | ---------------------------------- |
| `serviceId`      | Controller가 결정한 거래 ID        |
| `dtoBody`        | 요청 전문의 `dto` 부분             |
| `ServiceContext` | 직접 인자가 아니라 Holder에서 캡처 |

### 출력

Handler와 업무 Facade가 반환한 업무 DTO를 그대로 반환합니다.

```text
TcfFacade
→ mgcoa5530S0DTOout
→ Controller 반환
→ ResponseBodyAdvice가 hdr_nhnis + dto로 조립
```

### TcfFacade가 하지 않는 일

```text
SQL 실행
업무 DTO 변환
ImageLog 처리
응답 전문 조립
serviceId별 업무 분기
```

# 4. TcfFacade의 트랜잭션

`TcfFacade.process()` 자체에는 `@Transactional`이 없습니다.

```java
public Object process(...) {
}
```

그렇다고 현재 트랜잭션이 없는 것은 아닙니다.

타임아웃이 활성화되어 있으므로 `OnlineTimeoutExecutor`가 worker thread에서 `TransactionTemplate`을 시작합니다.

```text
TcfFacade
  ↓
OnlineTimeoutExecutor
  ↓
TransactionTemplate TX 시작
  ↓
Dispatcher → Handler → 업무 Facade → Service → DAO
```

즉, 현재 트랜잭션 경계는 `TcfFacade` 내부에서 호출되는 Timeout Executor가 만듭니다.

## 6. TransactionContext의 실제 특성

문서에는 `ServiceContextHolder 스냅샷`이라고 표현되어 있지만 정확히는 스냅샷이 아닙니다.

현재 구현은:

```java
this.serviceContext = serviceContext;
```

즉, 기존 `ServiceContext` 객체 참조를 그대로 보관합니다.

```text
HTTP 요청 스레드
   └─ ServiceContext ─────┐
                          ├─ 같은 객체
TransactionContext ───────┘
```

따라서 다음 값은 불변 복사가 아닙니다.

```text
header
guid
requestBody
responseBody
userContext
HttpServletRequest
HttpServletResponse
```

타임아웃 후 worker가 계속 실행되면 요청 스레드와 같은 mutable Context를 공유할 가능성이 있습니다.

문서의 `스냅샷` 표현은 다음처럼 수정하는 것이 정확합니다.

```text
현재: ServiceContextHolder의 ServiceContext 참조
권장: Servlet 객체 없는 불변 Context 스냅샷
```

# 7. OnlineTimeoutExecutor

`TcfFacade`는 구현체를 직접 알지 않고 인터페이스를 사용합니다.

```java
private final OnlineTimeoutExecutor onlineTimeoutExecutor;
```

설정에 따라 구현체가 바뀝니다.

| 설정                    | 구현체                         |
| ----------------------- | ------------------------------ |
| `timeout.enabled=true`  | `DefaultOnlineTimeoutExecutor` |
| `timeout.enabled=false` | `SyncOnlineTimeoutExecutor`    |

---

## 8. 타임아웃 활성화

```yaml
nhnis:
  fw:
    timeout:
      enabled: true
      milliseconds: 5000
```

처리:

```text
요청 Context 캡처
→ worker pool에 작업 제출
→ worker에서 TransactionTemplate 시작
→ Dispatcher 실행
→ 요청 스레드는 최대 5초 대기
```

worker pool 설정:

```text
corePoolSize = 20
maxPoolSize  = 20
queueCapacity = 100
Thread prefix = pdmg-online-
```

### 정상 완료

```text
worker 업무 정상 종료
→ TransactionTemplate commit
→ Future 결과 반환
→ Controller 응답
```

### 업무 예외

```text
Handler/Facade/Service 예외
→ rollback-only
→ TransactionTemplate rollback
→ 예외를 요청 스레드로 전달
→ GlobalExceptionHandler 처리
```

### 5초 초과

```text
Future.get(5000ms) timeout
→ future.cancel(true)
→ OnlineTimeoutException
→ HTTP 504 / FW_TIMEOUT
```

worker가 interrupt를 받아 정상 중단하면 transaction rollback이 수행됩니다.

그러나 업무 코드가 interrupt를 잡아 무시하고 계속 실행하면 즉시 멈춘다는 보장은 없습니다. 작업이 최종 반환된 후 deadline 또는 interrupt 상태를 확인해 rollback을 시도하지만, 무한 대기·interrupt 무시 SQL에 대해서는 강제 종료가 보장되지 않습니다.

## 9. 타임아웃 비활성화

```yaml
nhnis:
  fw:
    timeout:
      enabled: false
```

이 경우:

```java
return action.call();
```

즉:

```text
HTTP 요청 스레드
  ↓
TcfFacade
  ↓
SyncOnlineTimeoutExecutor
  ↓
Dispatcher
  ↓
Handler
  ↓
업무 Facade @Transactional
  ↓
Service → DAO
```

`SyncOnlineTimeoutExecutor`에는 `TransactionTemplate`이 없습니다.

따라서 트랜잭션은 업무 Facade의 `@Transactional`이 시작합니다.

```text
timeout ON:
  worker TransactionTemplate가 외부 TX 시작
  → 업무 Facade가 참여

timeout OFF:
  업무 Facade가 TX 시작
```

두 경우 모두 Handler가 반드시 트랜잭션 Facade를 호출해야 합니다.

## 11. Handler Map 구성

실제 자료구조:

```java
private final Map<String, TransactionHandler>
        handlerMap = new ConcurrentHashMap<>();
```

등록:

```java
for (TransactionHandler handler : handlers) {
    for (String serviceId : handler.serviceIds()) {
        TransactionHandler previous =
                handlerMap.put(serviceId, handler);

        if (previous != null) {
            throw new IllegalStateException(
                "Duplicate serviceId detected: "
                    + serviceId
            );
        }
    }
}
```

### 중복 serviceId

두 Handler가 같은 ID를 등록하면 애플리케이션 기동이 실패합니다.

```text
Handler A → mgcoa8888S0
Handler B → mgcoa8888S0

→ IllegalStateException
→ 서버 기동 실패
```

이것은 잘못된 거래 라우팅을 실행 중이 아니라 기동 시 발견한다는 점에서 적절합니다.

### serviceIds가 비어 있는 Handler

```java
if (serviceIds == null || serviceIds.isEmpty()) {
    log.warn(...);
    continue;
}
```

Bean은 존재하지만 Dispatcher에 등록되지 않습니다.

# 12. serviceId 정규화 문제

현재 Handler Map은 serviceId를 그대로 사용합니다.

다음 처리가 없습니다.

```text
trim
대소문자 통일
형식 검증
null/공백 등록 검증
```

호출도 정확히 일치해야 합니다.

```text
등록: mgcoa8888S0
호출: mgcoa8888s0
→ 미등록

호출: " mgcoa8888S0 "
→ Controller에서 trim하면 정상
```

Controller는 최종 serviceId를 `trim()`하지만 Handler가 등록할 때는 정규화하지 않습니다.

기동 시 다음 검증을 추가하는 것이 안전합니다.

```java
if (!StringUtils.hasText(serviceId)) {
    throw new IllegalStateException(
        "Handler serviceId가 비어 있습니다."
    );
}

String normalized = serviceId.trim();
```

# 13. dispatch 처리

호출:

```java
dispatcher.dispatch(
    serviceId,
    dtoBody,
    context
);
```

처리 순서:

```text
serviceId가 null 또는 공백인가?
  ├─ YES → ServiceHandlerNotFound
  └─ NO
       ↓
handlerMap에서 Handler 조회
  ├─ 없음 → ServiceHandlerNotFound
  └─ 있음
       ↓
handler.handle(dtoBody, context)
```

코드:

```java
if (!StringUtils.hasText(serviceId)) {
    throw new ServiceHandlerNotFound(
        "serviceId가 없습니다."
    );
}

TransactionHandler handler =
        handlerMap.get(serviceId);

if (handler == null) {
    throw new ServiceHandlerNotFound(
        "등록되지 않은 serviceId입니다: "
            + serviceId
    );
}

return handler.handle(dtoBody, context);
```

# 14. 미등록 serviceId 예외

현재 `GlobalExceptionHandler`는 `ServiceHandlerNotFound`를 다음처럼 처리합니다.

```text
HTTP 500
stdErrCode = E9999
```

하지만 미등록 serviceId는 대부분 요청 형식 또는 존재하지 않는 API 문제입니다.

보다 적절한 상태는:

```text
serviceId 누락 → 400 Bad Request
serviceId 미등록 → 404 Not Found
```

서버 내부 장애와 잘못된 거래 요청을 구분하는 것이 좋습니다.

# 16. Dispatcher와 Handler 책임 구분

```text
TransactionDispatcher
  → 어느 Handler인가?

TransactionHandler
  → 그 Handler 안에서 어느 업무 메서드인가?
```

예:

```text
serviceId = mgcoa9000U0

Dispatcher:
  mgcoa9000Handler 선택

Handler:
  U0 분기
  → mgcoa9000Facade.mgcoa9000U0(dto)
```

Dispatcher에 업무별 `if`나 `switch`를 추가하지 않는 현재 방식은 적절합니다.

# 17. 신규 거래 추가 방법

```java
private static final String A0 = "mgcoa9000A0";
```

# 18. 현재 트랜잭션 범위

타임아웃 ON 기준:

```text
TransactionTemplate BEGIN
  ↓
TransactionDispatcher.dispatch
  ↓
Handler.handle
  ↓
업무 Facade @Transactional(REQUIRED)
  ↓
업무 선처리 Aspect
  ↓
Service
  ↓
DAO
  ↓
업무 후처리 Aspect
  ↓
Facade 종료
  ↓
deadline / interrupt 검사
  ↓
COMMIT 또는 ROLLBACK
```

따라서 다음이 같은 트랜잭션에 들어갑니다.

```text
Dispatcher
Handler
업무 Facade
업무 선처리
Service
DAO
업무 후처리
```

다만 Dispatcher와 Handler는 일반적으로 DB 작업을 하지 않습니다.

다음은 트랜잭션 밖입니다.

```text
DefaultFilter
ServicePreventionInterceptor.preHandle
ImageLog INSERT
OnlineTransactionController
ResponseBodyAdvice
Interceptor.afterCompletion
```

# 19. 개선이 필요한 부분

| 우선순위 | 항목                                               | 판단                               |
| -------- | -------------------------------------------------- | ---------------------------------- |
| P0       | 타임아웃 worker가 원본 mutable ServiceContext 공유 | 불변 스냅샷 필요                   |
| P0       | 업무 코드가 interrupt를 무시하면 즉시 취소 불가    | 서비스·DB timeout 병행 필요        |
| P1       | serviceId 등록 시 null·공백·형식 검증 없음         | 기동 검증 필요                     |
| P1       | serviceId 대소문자·정규화 정책 없음                | 공통 정규화 필요                   |
| P1       | 미등록 serviceId가 HTTP 500                        | 400/404 권장                       |
| P1       | 미등록 Handler 확인도 TX 시작 후 수행              | 불필요한 TX 생성                   |
| P1       | TransactionContext가 “스냅샷”이 아닌 객체 참조     | 문서와 구현 정정                   |
| P2       | 프레임워크 기본 메서드마다 INFO 시작/종료 로그     | 로그 과다                          |
| 테스트   | Timeout Executor 테스트만 확인됨                   | Dispatcher/중복/미등록 테스트 보강 |

## 20. 미등록 Handler 조회와 트랜잭션

현재 타임아웃 ON에서는 다음 순서입니다.

```text
TransactionTemplate BEGIN
  ↓
Dispatcher에서 serviceId 조회
  ↓
Handler 없음
  ↓
ServiceHandlerNotFound
  ↓
ROLLBACK
```

Handler가 존재하는지 확인하기 위해서도 DB 트랜잭션이 시작됩니다.

기능상 문제는 작지만 효율을 높이려면 Handler 조회와 유효성 검사를 TX 전에 수행할 수 있습니다.

예:

```text
TcfFacade
  ↓
Dispatcher.resolveHandler(serviceId)     TX 밖
  ↓
OnlineTimeoutExecutor
  ↓
TransactionTemplate BEGIN
  ↓
handler.handle(...)
```

다만 구조 복잡도가 늘어나므로 실제 미등록 호출 빈도와 성능 요구를 보고 결정하면 됩니다.

## 결론

현재 구조의 핵심은 다음과 같습니다.

```text
TcfFacade
  = Context 생성 + TimeoutExecutor 호출

OnlineTimeoutExecutor
  = worker + timeout + 외부 TX

TransactionDispatcher
  = serviceId → Handler 검색

TransactionHandler
  = serviceId별 업무 Facade 호출
```
