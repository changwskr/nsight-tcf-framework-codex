# 22. Business Service 분석

## 1. 결론

현재 PDMG Business Service는 전체적으로 다음 역할을 수행합니다.

```text
입력 DTO
→ 업무값 검증·정규화
→ DAO 파라미터 Map 생성
→ DAO 호출
→ 조회 Row를 DTO로 변환
→ 출력 DTO 반환
```

레이어 배치는 대체로 적절합니다.

```text
Handler       serviceId 분기
→ Facade      DTO 변환, 트랜잭션 참여
→ Service     업무 절차·검증·결과 조립
→ DAO         MyBatis 호출
→ Mapper XML  SQL
```

다만 현행 소스에는 중요한 문제가 있습니다.

> `mgcoa5530Service`에 약 8초의 테스트용 `Thread.sleep()`이 남아 있어서, 공통 타임아웃 5초 설정에서는 `mgcoa5530S0`가 정상 완료될 수 없습니다.

또한 쓰기 Service의 결과 코드 처리, 동시성 검증, 테스트 부족을 보완할 필요가 있습니다.

## 3. 호출 위치와 트랜잭션

### TCF ON + 타임아웃 ON

현재 운영 흐름은 다음과 같습니다.

```text
OnlineTimeoutExecutor
→ TransactionTemplate BEGIN
  → Dispatcher
    → Handler
      → Business Facade @Transactional(REQUIRED)
        → DTOin 변환
        → BizPrePostAspect.before
        → Service
          → DAO
          → SQL
        → BizPrePostAspect.afterReturning
  → 제한시간 검사
→ COMMIT 또는 ROLLBACK
```

따라서 Service는 트랜잭션을 시작하지 않지만, 이미 시작된 트랜잭션 안에서 실행됩니다.

### 타임아웃 OFF

```text
Handler
→ Facade @Transactional BEGIN
  → Service
  → DAO
→ COMMIT/ROLLBACK
```

이 경우 Facade가 트랜잭션을 시작합니다.

### TCF OFF

레거시 Controller가 Service를 직접 호출합니다.

```text
Controller
→ Service
→ DAO
```

이 경로에서는 `BizPrePostAspect`는 실행되지만 Facade를 통과하지 않으므로 트랜잭션이 빠질 수 있습니다.

## 4. Service가 담당하는 일

현재 구현 기준으로 Service가 담당하는 일은 다음과 같습니다.

- 입력 DTO의 null 및 빈 문자열 처리
- 검색 조건 정규화
- 페이징 기본값과 상한 적용
- DAO 파라미터 Map 구성
- 존재 여부와 중복 여부 확인
- DAO 메서드 순서 제어
- 조회 Row를 출력 DTO로 변환
- 처리 건수와 결과 코드 설정

Service가 하지 않는 일:

- HTTP 요청·응답 처리
- `serviceId` 분기
- JSON Map을 입력 DTO로 변환
- 트랜잭션 시작·커밋
- SQL 문자열 보유
- 표준 응답 봉투 조립
- JWT 검증
- 시스템 ImageLog 관리

이 역할 분리는 적절합니다.

# 5. `mgcoa5530Service`

소스: [mgcoa5530Service.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/application/service/mgcoa5530Service.java:22>)

## 역할

마케팅희망고객 목록을 조회하며 다음 필터와 페이징을 지원합니다.

```text
trtBrc
basDt
pageNo
pageSize
```

처리 흐름:

```text
입력 조건 Map 생성
→ pageNo 기본 1
→ pageSize 기본 20, 최대 100
→ offset 계산
→ count SQL
→ 목록 SQL
→ L5101~L5104 DTO 변환
→ 페이징 메타데이터 설정
```

### 페이징 계산

```java
int offset = (pageNo - 1) * pageSize;
```

```java
totalPages =
    (totalCount + pageSize - 1L) / pageSize;
```

계산 자체는 정상입니다.

## 치명적인 문제: 테스트용 지연

현재 Service에는 다음 코드가 있습니다.

```java
Thread.sleep(1000);
Thread.sleep(1000);
Thread.sleep(1000);
Thread.sleep(1000);
Thread.sleep(1000);
Thread.sleep(1000);
Thread.sleep(1000);
Thread.sleep(1000);
```

주석에는 7초라고 되어 있지만 실제로는 약 8초입니다.

현재 타임아웃은 5초입니다.

```yaml
nhnis:
  fw:
    timeout:
      milliseconds: 5000
```

따라서 정상 호출도 다음과 같이 처리됩니다.

```text
0초  Service 시작
5초  OnlineTimeoutExecutor 타임아웃
     future.cancel(true)
     HTTP 504 FW_TIMEOUT
```

Service는 인터럽트를 잡은 다음 예외를 전달하지 않습니다.

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    log.warn(...);
}
```

그리고 DAO 처리를 계속합니다.

```java
mgcoa5530DAO.mgcoa5530S0_S0_count(param);
mgcoa5530DAO.mgcoa5530S0_S0(param);
```

Executor가 마지막에 인터럽트 상태를 확인해 롤백하지만, 불필요한 SQL이 실행됩니다.

### 권장 상태

테스트용 코드라면 제거해야 합니다. 의도적으로 타임아웃을 시험하려는 코드라면 최소한 예외를 즉시 전파해야 합니다.

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw e;
}
```

현재 상태에서 `mgcoa5530S0`는 정상 업무 거래가 아니라 타임아웃 시험용 거래처럼 동작합니다.

# 6. `mgcoa8888Service`

소스: [mgcoa8888Service.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/application/service/mgcoa8888Service.java:27>)

## `mgcoa8888S0`: 이미지로그 조회

지원 조건:

- GUID
- serviceId
- screenId
- 사용자번호
- 예외 거래만 조회
- 최근 N초
- 최소 처리시간 N초
- 페이징

### 상한 방어

```java
MAX_WITHIN_SECONDS = 86400;
MAX_MIN_ELAPSED_SECONDS = 3600;
```

사용자가 과도하게 큰 값을 보내도 다음 상한으로 제한합니다.

| 조건           |           최대값 |
| -------------- | ---------------: |
| 최근 조회 범위 | 86,400초, 24시간 |
| 최소 소요시간  |   3,600초, 1시간 |

이는 무제한 조회 범위를 방지하는 적절한 처리입니다.

### CLOB 변환

요청·응답 전문이 CLOB이면 문자열로 변환합니다.

```java
if (value instanceof java.sql.Clob clob) {
    return clob.getSubString(1, size);
}
```

하지만 CLOB 전체를 메모리에 올릴 수 있습니다. 이미지로그 전문이 크면 다음 위험이 있습니다.

- 응답 DTO 메모리 증가
- JSON 직렬화 비용 증가
- `BizPrePostAspect`의 결과 DTO 로그 폭증
- 타임아웃 증가

최대 전문 길이나 요약 조회 정책이 필요합니다.

## `mgcoa8888D0`: 이미지로그 삭제

입력 GUID 목록을 다음과 같이 정리합니다.

```java
guidList
→ null/blank 제거
→ trim
→ 중복 제거
→ DAO DELETE
```

빈 목록이면:

```text
PROC_CNT = 0
RSLT_CD  = 0001
RSLT_MSG = NO_DATA
```

삭제 SQL이 실행되면 실제 삭제 건수와 관계없이:

```text
RSLT_CD = 0000
RSLT_MSG = OK
```

따라서 요청한 GUID가 하나도 존재하지 않아 삭제 건수가 0이어도 성공으로 반환합니다. 이것이 계약상 성공인지 `NOT_FOUND`인지 정책을 명확히 해야 합니다.

# 7. `mgcoa9000Service`

## `mgcoa9000C0`: 등록

처리 흐름:

```text
txId, txName 필수 확인
→ txId 중복 조회
→ 파라미터 정규화
→ 등록 사용자·시각 설정
```

결과 코드:

| 코드   | 의미         |
| ------ | ------------ |
| `0000` | 성공         |
| `0001` | 필수값 누락  |
| `0002` | 거래 ID 중복 |

### 동시성 문제

현재 중복 검사는 다음 두 SQL로 나뉩니다.

```text
SELECT EXISTS
→ INSERT
```

동시에 같은 `txId`가 들어오면:

```text
요청 A: EXISTS = 0
요청 B: EXISTS = 0
요청 A: INSERT
요청 B: INSERT
```

따라서 애플리케이션의 존재 확인만으로 중복을 보장할 수 없습니다.

DB에 `TX_ID` PK 또는 UNIQUE 제약이 반드시 있어야 합니다. 중복 제약 예외를 업무 코드 `0002` 또는 표준 예외로 변환해야 합니다.

## `mgcoa9000U0`: 수정

처리 흐름:

```text
txId, txName 필수 확인
→ txId 존재 조회
→ 변경값 정규화
→ UPDATE
→ 성공 반환
```

결과 코드:

| 코드   | 의미        |
| ------ | ----------- |
| `0000` | 성공        |
| `0001` | 필수값 누락 |
| `0003` | 대상 없음   |

존재 확인 후 실제 UPDATE 사이에 다른 트랜잭션이 데이터를 삭제할 수 있습니다.

```text
EXISTS = 1
→ 다른 트랜잭션 DELETE
→ UPDATE 결과 0건
→ 현재 코드는 0000 OK 반환
```

실제 `cnt`가 0이면 `NOT_FOUND`로 처리할지 검토해야 합니다.

## `mgcoa9000D0`: 삭제

입력 목록을 정리한 후 다건 삭제합니다.

```text
txIdList
→ blank 제거
→ trim
→ 중복 제거
→ DELETE
```

삭제 결과가 0건이어도 다음처럼 반환합니다.

```text
PROC_CNT = 0
RSLT_CD = 0000
RSLT_MSG = OK
```

삭제를 멱등 처리로 본다면 정상입니다. 존재하지 않는 대상 삭제를 오류로 본다면 `0003 NOT_FOUND`가 필요합니다.

# 8. `mgcoa9999Service`

소스: [mgcoa9999Service.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/co/a/application/service/mgcoa9999Service.java:23>)

영업팁 실적 목록을 조회합니다.

처리 흐름:

```text
salzTipKdc 조건 생성
→ DAO 목록 조회
→ Row를 Sub DTO로 변환
→ size 설정
→ DTOout 반환
```

다른 목록 Service와 달리 다음 기능이 없습니다.

- count SQL
- pageNo
- pageSize
- offset
- totalCount
- totalPages

따라서 데이터가 많으면 전체 목록을 한 번에 조회할 수 있습니다. 업무 데이터가 계속 증가한다면 대용량 조회 위험이 있습니다.

또한 입력값은 empty 여부만 검사하고 trim하지 않습니다.

```java
if (input.getSalzTipKdc() != null
        && !input.getSalzTipKdc().isEmpty()) {
    param.put("salzTipKdc", input.getSalzTipKdc());
}
```

예를 들어 `"   "`도 검색 조건으로 전달됩니다. 다른 Service처럼 `isBlank()`와 `trim()`을 사용하는 편이 일관적입니다.

Row 변환도 대문자·camelCase 두 개만 확인합니다.

```java
Object value = row.get(upperKey);
if (value == null) {
    value = row.get(camelKey);
}
```

`mgcoa5530`, `8888`, `9000`은 마지막으로 `equalsIgnoreCase()` 전체 검색을 수행합니다. 따라서 `9999`만 DB/MyBatis 키 대소문자 차이에 상대적으로 취약합니다.

# 9. 예외와 업무 결과 코드

문서에는 Service가 `BizException`을 사용할 수 있다고 되어 있지만 현재 4개 Service에서는 실제 `BizException` 사용이 확인되지 않습니다.

현행 오류 처리는 두 방식입니다.

### 방식 A: 출력 DTO 결과 코드

```java
output.setRSLT_CD("0001");
output.setRSLT_MSG("NO_DATA");
return output;
```

이 방식은 Java 예외가 없으므로 트랜잭션이 정상 커밋됩니다.

```text
업무 오류 DTO 반환
→ BizPrePostAspect 후처리 실행
→ Transaction COMMIT
→ HTTP 200 가능
```

### 방식 B: DAO/시스템 예외

DAO나 SQL에서 예외가 발생하면:

```text
Service 예외 전파
→ BizPrePostAspect 후처리 미실행
→ Transaction ROLLBACK
→ GlobalExceptionHandler
```

현재 문제는 출력 DTO 업무 코드와 표준 오류 코드의 경계가 명확하지 않다는 것입니다.

권장 기준:

| 상황                  | 처리                           |
| --------------------- | ------------------------------ |
| 정상적인 조건 불충족  | 업무 결과 코드                 |
| 사용자 입력 형식 오류 | 400 또는 업무 예외             |
| 중복 등록             | 명시적 업무 예외/코드          |
| 대상 없음             | 정책에 따른 404 또는 업무 코드 |
| SQL·시스템 장애       | 예외 전파 및 롤백              |
| 타임아웃              | `FW_TIMEOUT`, HTTP 504         |

한 시스템에서 `RSLT_CD`, `stdErrCode`, HTTP 상태를 함께 사용하므로 계약을 문서화해야 합니다.

# 10. 입력 검증

현재 DTO에는 Bean Validation을 사용하지 않습니다.

확인되지 않은 항목:

```java
@NotBlank
@NotNull
@Size
@Pattern
@Min
@Max
```

대신 Service에서 수동으로 검증합니다.

```java
if (txId == null || txName == null) {
    // 결과 코드 반환
}
```

수동 검증은 가능하지만 다음 문제가 생깁니다.

- 거래마다 필수값 처리 방식이 달라짐
- 최대 길이 검증 누락
- 날짜 형식 검증 누락
- URL 및 HTTP Method 허용값 검증 누락
- DB 컬럼 길이 초과가 SQL 시점에 발견됨

특히 `mgcoa9000C0/U0`의 다음 값은 형식 검증이 없습니다.

- `txId`
- `txName`
- `appId`
- `pathUrl`
- `httpMethod`
- 사용자 ID

`httpMethod`는 단순 대문자 변환만 합니다.

```java
return value == null
        ? "POST"
        : value.toUpperCase(Locale.ROOT);
```

따라서 `"INVALID"`도 그대로 저장할 수 있습니다.

# 11. Row → DTO 변환 중복

각 Service가 거의 동일한 `asString()`을 따로 구현하고 있습니다.

```text
mgcoa5530Service.asString
mgcoa8888Service.asString
mgcoa9000Service.asString
mgcoa9999Service.asString
```

구현도 조금씩 다릅니다.

| Service | 대소문자 보정 | CLOB 처리 |
| ------- | ------------- | --------- |
| 5530    | 있음          | 없음      |
| 8888    | 있음          | 있음      |
| 9000    | 있음          | 없음      |
| 9999    | 없음          | 없음      |

이 차이로 환경에 따라 같은 Mapper 결과도 Service별로 다르게 처리될 수 있습니다.

장기적으로는 다음 중 하나가 더 안전합니다.

- MyBatis `resultMap`으로 DTO 직접 매핑
- 공통 Row 변환 Utility
- 명시적인 Mapper 인터페이스 반환 타입
- 타입 안전한 persistence DTO

현재 `Map<String,Object>` 방식은 컬럼명이 바뀌어도 컴파일 오류가 발생하지 않는다는 위험이 있습니다.

# 12. 의존성 주입

모든 Service가 필드 주입을 사용합니다.

```java
@Autowired
private mgcoa9000DAO mgcoa9000DAO;
```

동작에는 문제가 없지만 생성자 주입이 더 적합합니다.

```java
private final mgcoa9000DAO dao;

public mgcoa9000Service(mgcoa9000DAO dao) {
    this.dao = dao;
}
```

장점:

- 의존성이 명확함
- null 상태로 객체 생성 불가
- 단위 테스트가 단순함
- 필드를 `final`로 유지 가능
- Spring 없이도 객체 생성 가능

Facade는 이미 생성자 주입을 사용하므로 Service도 통일할 수 있습니다.

# 13. 시간 생성

`mgcoa9000Service`는 현재 시간을 다음처럼 생성합니다.

```java
new SimpleDateFormat(
    "yyyyMMddHHmmss",
    Locale.KOREA
).format(new Date());
```

문제점:

- 시스템 기본 TimeZone에 의존
- 테스트에서 시간을 고정하기 어려움
- 등록·수정 시각의 일관된 Clock 정책이 없음

권장 방식은 `Clock` 주입과 `java.time` 사용입니다.

```java
private final Clock clock;

String now = LocalDateTime.now(clock)
    .format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"));
```

운영 서버 TimeZone이 다르면 현재 구현은 예상과 다른 시각을 저장할 수 있습니다.

# 14. 타임아웃 대응

Service는 Worker Thread에서 실행되므로 장기 작업은 인터럽트를 존중해야 합니다.

권장 원칙:

```java
if (Thread.currentThread().isInterrupted()) {
    throw new InterruptedException(
        "온라인 거래가 취소되었습니다.");
}
```

`InterruptedException`을 잡는다면 반드시 다시 전달해야 합니다.

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw e;
}
```

현재 `mgcoa5530Service`는 인터럽트 상태만 복원하고 DAO 실행을 계속하기 때문에 이 원칙을 위반합니다.

또한 JDBC SQL 자체의 중단을 보장하려면 별도의 Statement Timeout이 필요합니다. Executor의 5초 설정만으로 DB SQL이 5초에 즉시 중단되는 것은 아닙니다.

Service 단위 테스트는 사실상 `mgcoa5530ServiceTest` 하나만 확인됩니다.

검증 내용:

누락된 테스트:

# 16. 문서 현행성

[22.Business-Service.md](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/22.Business-Service.md:1>)는 전체 레이어 역할을 대체로 정확히 설명합니다.

보정할 부분은 다음과 같습니다.

### “Facade가 TX를 소유한다”

다음처럼 구분해야 정확합니다.

```text
timeout ON  → OnlineTimeoutExecutor가 외곽 TX 시작
              Facade REQUIRED 참여

timeout OFF → Facade @Transactional이 TX 시작
```

### `BizException` 사용

문서에는 Service가 `BizException`을 사용한다고 되어 있지만 현행 Service에서는 사용하지 않습니다. 현재 업무 오류는 주로 출력 DTO의 `RSLT_CD`로 반환합니다.

### 표준 조회 절차

`mgcoa9999S0`에는 페이징이 없으므로 모든 조회 Service가 표준 페이징을 구현하는 것은 아닙니다.

### 쓰기 성공 판정

현재 C/U/D는 DAO 결과가 0이어도 일부 메서드가 `0000 OK`를 반환합니다. 성공 판정 기준을 문서에 명확히 기록해야 합니다.
