## 분석 결론

[03.어플리케이션 레이어드 아키텍처.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/03.어플리케이션 레이어드 아키텍처.md>)는 아직 업데이트되지 않은 기존 내용입니다.

레이어 구분의 기본 방향은 이해하기 쉽지만, 현재 `pdmg-service`와 `pdmg-fw` 구현 기준으로는 트랜잭션 설명에 중대한 오류가 있습니다.

특히 다음 두 문장은 현재 구현과 반대입니다.

```text
업무 DB 트랜잭션을 FW에서 열지 않는다.
TX는 Application(Facade)에만 둔다.
```

Timeout이 활성화된 현재 기본 설정에서는 `pdmg-fw`의 `DefaultOnlineTimeoutExecutor`가 최외곽 트랜잭션을 시작합니다.

---

## 1. 현재 문서가 정의한 구조

문서는 다음과 같은 수직 레이어를 정의합니다.

```text
UI
  → Framework
  → Entry
  → Application
  → Contract
  → Persistence
  → DB
```

하지만 현재 구현을 정확하게 설명하려면 다음과 같이 수정해야 합니다.

```text
외부 채널
  pdmg-ui
      │ HTTP/JSON
      ▼
프레임워크 진입·제어
  Filter / Interceptor
  OnlineTransactionController
  TcfFacade
  TimeoutExecutor
  TransactionDispatcher
      │
      ▼
업무 진입
  Handler
  Facade
      │
      ▼
애플리케이션
  Service
      │
      ▼
영속
  DAO(MyBatis Mapper)
  Mapper XML
  DB
```

다음 컴포넌트들은 수직 레이어 밖의 공유·횡단 요소로 표현하는 것이 정확합니다.

```text
DTO      : 공유 입출력 계약
Aspect   : Service 횡단 처리
Config   : Spring/DataSource/MyBatis 조립
Client   : 외부 시스템 연동
Support  : 공통 유틸
```

---

## 2. TCF ON + Timeout ON 실제 흐름

현재 설정에서 TCF와 Timeout이 활성화되면 실제 흐름은 다음과 같습니다.

```text
요청 스레드
  → DefaultFilter
  → ServicePreventionInterceptor
  → OnlineTransactionController
  → TcfFacade
  → DefaultOnlineTimeoutExecutor
       │
       │ 작업 제출
       ▼
작업 스레드
  → ServiceContext 설치
  → TransactionTemplate
       → TX BEGIN
       → TransactionDispatcher
       → Handler
       → Facade @Transactional(REQUIRED)
       → BizPrePostAspect @Before
       → Service
       → DAO
       → Mapper XML / DB
       → BizPrePostAspect @AfterReturning
       → TX COMMIT
  → ServiceContext 정리
```

예외 또는 타임아웃이면:

```text
업무 예외 또는 Timeout
  → 예외 전파
  → TX ROLLBACK
```

따라서 문서의 다음 설명은 잘못되었습니다.

```text
Entry Handler ← TX 없음
Application Facade ← TX BEGIN
```

정확한 설명은 다음입니다.

```text
Timeout ON:
  TimeoutExecutor에서 TX BEGIN
  Handler도 트랜잭션 안에서 실행
  Facade는 기존 트랜잭션에 참여

Timeout OFF:
  Handler는 TX 밖에서 실행
  Facade에서 TX BEGIN
```

Handler가 트랜잭션을 직접 선언하거나 소유하는 것은 아니지만, Timeout ON에서는 트랜잭션 범위에 포함됩니다.

---

## 3. TCF ON + Timeout OFF

Timeout이 비활성화되면 `SyncOnlineTimeoutExecutor`가 같은 요청 스레드에서 Dispatcher를 실행합니다.

이 경우 외부 `TransactionTemplate`은 없습니다.

```text
OnlineTransactionController
  → TcfFacade
  → SyncOnlineTimeoutExecutor
  → TransactionDispatcher
  → Handler
  → Facade
       → TX BEGIN
       → Service
       → DAO
       → TX COMMIT/ROLLBACK
```

이 조건에서는 문서의 “Facade가 트랜잭션 경계”라는 설명이 맞습니다.

따라서 트랜잭션 설명은 하나로 고정하면 안 되고 설정 조건별로 나누어야 합니다.

---

## 4. TCF OFF 실제 흐름

현재 업무별 Controller는 다음 조건에서만 활성화됩니다.

```java
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "false",
    matchIfMissing = true
)
```

현재 Controller는 Facade가 아니라 Service를 직접 호출합니다.

```text
DefaultFilter / Interceptor
  → 업무 Controller
  → Service
  → DAO
  → Mapper XML
```

이 경로에서는 다음 컴포넌트를 우회합니다.

```text
TransactionDispatcher
Handler
Facade
TimeoutExecutor
Facade @Transactional
```

Service Pointcut은 실행되므로 업무 선후처리 로그는 동작하지만, 명시적인 업무 트랜잭션은 없습니다.

문서의 다음 표현:

> Controller → Facade → Service가 더 일관적이다.

는 다음과 같이 강화해야 합니다.

> TCF OFF에서도 트랜잭션 일관성을 보장하려면 Controller는 Service를 직접 호출하지 않고 Facade를 호출해야 한다.

---

## 5. Facade 역할 분석

현재 Facade는 다음 역할을 수행합니다.

```text
Object dtoBody
  → DTOin 변환
  → @Transactional 선언
  → Service 호출
  → DTOout 반환
```

Facade는 업무 유스케이스의 경계로 보는 것이 맞습니다.

다만 문서의 다음 등식은 항상 성립하지 않습니다.

```text
Facade 1메서드
  ≈ 온라인 거래 1건
  ≈ 트랜잭션 1건
```

Timeout ON에서는 트랜잭션이 Facade보다 앞에서 시작되기 때문입니다.

정확한 정의는 다음과 같습니다.

```text
Facade 메서드
  = 업무 유스케이스 경계
  = 기본 트랜잭션 선언 지점

실제 최외곽 트랜잭션 경계
  = Timeout ON이면 TimeoutExecutor
  = Timeout OFF이면 Facade
```

## 6. 업무 선후처리 Aspect

현재 업무 Aspect는 Service 계층을 대상으로 합니다.

```java
@Pointcut(
    "execution(public * " +
    "nhnis.mg.co.a.application.service..*(..))"
)
```

Timeout ON에서는 외부 트랜잭션이 이미 시작된 상태입니다.

```text
TX BEGIN
  → Handler
  → Facade
  → 업무 선처리
  → Service
  → 업무 후처리
TX COMMIT
```

Timeout OFF에서는 Facade 트랜잭션 안에서 실행됩니다.

```text
Facade TX BEGIN
  → 업무 선처리
  → Service
  → 업무 후처리
Facade TX COMMIT
```

따라서 두 경우 모두 TCF ON이라면 업무 선후처리는 같은 트랜잭션에 참여합니다.

단, 업무 후처리는 `@AfterReturning`이므로 Service가 정상 반환한 경우에만 실행됩니다.

```text
정상 반환 → 업무 후처리 실행
예외 발생 → 업무 후처리 실행 안 됨
```

## 7. Contract 레이어 문제

현재 문서는 DTO를 다음 위치에 배치합니다.

```text
Application
  → Contract DTO
  → Persistence
```

하지만 실제 소스에서 DTO는 Application과 Persistence 사이를 연결하는 레이어가 아닙니다.

실제 사용 관계는 다음과 같습니다.

```text
Controller → DTO
Facade → DTO
Service → DTO
DAO → 주로 Map과 기본 타입
```

따라서 DTO는 수직 레이어가 아니라 공유 계약으로 보는 것이 정확합니다.

```text
DTO Contract
   ↑       ↑
 Entry   Application
```

문서에서는 `Contract 레이어`를 주 호출 스택에서 제거하고 다음처럼 정의하는 것이 좋습니다.

> DTO는 Entry와 Application이 공유하는 입출력 데이터 계약이며 자체 실행 흐름, Bean, SQL 또는 트랜잭션을 갖지 않는다.

## 8. 호출 방향과 컴파일 의존 방향

문서는 다음을 하나의 “의존 방향”으로 표현합니다.

```text
UI → FW → Entry → Application → Persistence
```

하지만 이것은 런타임 호출 방향입니다.

Java 컴파일 의존은 다릅니다.

업무 Handler가 `pdmg-fw`의 인터페이스를 구현합니다.

```java
public class mgcoa8888Handler
        implements TransactionHandler
```

따라서 컴파일 의존은 다음과 같습니다.

```text
pdmg-service
  → pdmg-fw API/SPI
```

런타임 호출은 반대 방향입니다.

```text
pdmg-fw TransactionDispatcher
  → pdmg-service TransactionHandler 구현체
```

이는 Spring을 통한 의존성 역전 구조입니다.

```text
pdmg-fw가 SPI 정의
pdmg-service가 SPI 구현
Spring이 구현체 수집
Dispatcher가 런타임에 구현체 호출
```

문서에서는 반드시 두 방향을 분리해야 합니다.

## 9. 현재 패키지와 저장소 표준 차이

현재 구현은 다음 패키지를 사용합니다.

```text
entry.handler
entry.aspect
application.controller
application.facade
application.service
persistence.dao
dto
```

저장소 공식 권장 구조는 다음입니다.

```text
entry.handler
entry.facade
entry.web
application.service
application.rule
persistence.dao 또는 persistence.mapper
```

차이는 다음과 같습니다.

| 컴포넌트   | 현재 구현                | 저장소 권장                                 |
| ---------- | ------------------------ | ------------------------------------------- |
| Controller | `application.controller` | `entry.web`                                 |
| Facade     | `application.facade`     | `entry.facade`                              |
| Service    | `application.service`    | `application.service`                       |
| Rule       | 없음                     | `application.rule`                          |
| DAO/Mapper | `persistence.dao`        | `persistence.dao` 또는 `persistence.mapper` |

문서는 AS-IS 기준으로 현재 패키지를 본문에 설명하되, 이 차이는 별도 참고사항으로 표시해야 합니다.

## 10. Persistence 분석

현재 `DAO`는 일반적인 구현 클래스가 아니라 MyBatis Mapper 인터페이스입니다.

```java
@RDWMapper
public interface mgcoa8888DAO
```

실제 SQL은 다음 경로에 있습니다.

```text
src/main/resources/rdw.mg.co.a/*.xml
```

따라서 Persistence 구조는 다음과 같습니다.

```text
Service
  → DAO 인터페이스
  → MyBatis Proxy
  → Mapper XML statement
  → DB
```

문서의 “DAO → Mapper XML” 표현은 개념적으로 맞지만, DAO가 MyBatis Mapper Proxy라는 점을 명시해야 합니다.

## 11. Config를 단순 옆길로 보기 어려운 이유

문서에서는 Config를 호출 스택 밖의 옆길로 정의합니다.

하지만 DAO가 다음 annotation을 직접 import합니다.

```java
import nhnis.mg.co.a.config.RDWMapper;
```

따라서 실제 컴파일 의존은:

```text
persistence.dao
  → config.RDWMapper
```

입니다.

Config는 업무 호출 레이어는 아니지만 다음 기술 요소를 조립하는 인프라 구성 영역으로 정의해야 합니다.

```text
DataSource
TransactionManager
SqlSessionFactory
SqlSessionTemplate
MapperScan
Security
WebMvc
```

## 12. 현재 문서에서 수정이 필요한 문장

| 현재 문서 표현                  | 수정 방향                                                  |
| ------------------------------- | ---------------------------------------------------------- |
| FW는 업무 DB TX를 열지 않는다   | Timeout ON이면 FW TimeoutExecutor가 최외곽 TX 시작         |
| TX는 Facade에만 둔다            | Facade는 기본 선언 지점, Timeout ON은 Executor가 실제 시작 |
| Handler는 TX 없음               | TX 소유는 없지만 Timeout ON에서는 TX 안에서 실행           |
| Facade 1메서드 = TX 1건         | Facade는 유스케이스 경계, 실제 TX 경계는 설정별 상이       |
| DTO는 Contract 수직 레이어      | DTO는 공유 데이터 계약                                     |
| 의존은 UI → FW → Entry          | 런타임 호출과 컴파일 의존을 분리                           |
| TCF OFF Controller → Service    | 현재는 TX가 없음을 명확하게 경고                           |
| Application에 Controller/Facade | AS-IS이며 권장 구조는 `entry.web/facade`                   |
| Service가 검증·규칙 전부 수행   | AS-IS이며 권장 구조의 Rule 계층은 현재 없음                |

## 최종 평가

이 문서는 레이어 역할을 설명하는 기본 자료로는 유용하지만, 현재 구현 정확도는 약 60~70% 수준입니다.

가장 위험한 오해는 다음입니다.

```text
잘못된 이해:
  Handler는 항상 TX 밖
  Facade에서만 TX 시작
  FW는 업무 TX와 무관

실제 구현:
  Timeout ON이면 pdmg-fw가 TX 시작
  Handler부터 DAO까지 같은 TX
  Facade는 외부 TX에 REQUIRED로 참여
```

따라서 현재 문서를 개발자 아키텍처 기준서로 사용하기 전에 트랜잭션, DTO 위치, 의존 방향을 우선 수정해야 합니다. 이번에는 분석만 수행했으며 대상 문서는 수정하지 않았습니다.
