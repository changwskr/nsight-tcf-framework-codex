## 09. 서비스 ID 분석 결과

[09.서비스ID.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/09.서비스ID.md>)는 전체 흐름을 비교적 잘 설명하고 있습니다. 다만 실제 소스를 기준으로 보면 형식 길이, 서비스 ID 결정 우선순위, 필수 일치 범위 등 몇 가지 핵심 내용을 수정해야 합니다.

### 1. 서비스 ID의 실제 역할

PDMG에서 서비스 ID는 요청받은 거래를 어떤 `TransactionHandler`로 전달할지 결정하는 라우팅 키입니다.

```text
HTTP 요청
  ↓
OnlineTransactionController
  ↓ 서비스 ID 결정
TcfFacade
  ↓
TransactionDispatcher
  ↓ serviceIds() 조회
TransactionHandler
  ↓ context.getServiceId() 분기
BusinessFacade
  ↓
Service → DAO
```

핵심은 다음 코드 관계입니다.

```java
public Collection<String> serviceIds() {
    return List.of(
        "mgcoa8888S0",
        "mgcoa8888D0"
    );
}
```

```java
String serviceId = context.getServiceId();

return switch (serviceId) {
    case "mgcoa8888S0" -> facade.mgcoa8888S0(body);
    case "mgcoa8888D0" -> facade.mgcoa8888D0(body);
    default -> throw new ServiceHandlerNotFound(...);
};
```

서비스 ID가 실제 런타임에서 반드시 일치해야 하는 곳은 다음 세 군데입니다.

```text
Controller가 결정한 serviceId
        =
Handler.serviceIds() 등록값
        =
Handler.handle() 분기값
```

Facade·Service·DTO·SQL 이름을 서비스 ID와 맞추는 것은 중요한 개발 표준이지만, Dispatcher 자체가 강제로 검증하는 런타임 조건은 아닙니다.

## 2. 문서의 형식 오류

문서에는 전체 길이가 “보통 10자”라고 되어 있지만 실제 형식은 11자입니다.

```text
mg + co + a + 8888 + S + 0
 2    2    1     4     1   1
                         합계 11자
```

따라서 정확한 형식은 다음과 같습니다.

```regex
^[a-z]{2}[a-z]{2}[a-z][0-9]{4}[SCUDAR][0-9A-Z]$
```

현재 PDMG 규칙에 한정하면 더 엄격하게 다음과 같이 표현할 수도 있습니다.

```regex
^mg[a-z]{2}[a-z][0-9]{4}[SCUDAR][0-9A-Z]$
```

예:

```text
mgcoa8888S0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
```

현재 코드에는 이 형식을 검사하는 공통 Validator가 없습니다. 따라서 규칙에 맞지 않는 문자열도 Handler에 등록만 되면 사용될 수 있습니다.

## 3. 실제 서비스 ID 결정 우선순위

문서의 흐름도는 URL path가 항상 서비스 ID가 되는 것처럼 표현되어 있지만 실제 구현은 다릅니다.

[OnlineTransactionController.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/web/OnlineTransactionController.java:99>)의 우선순위는 다음과 같습니다.

```text
1순위: ServiceContext.header.sys_comm.rms_svc_c
2순위: 요청 JSON hdr_nhnis.sys_comm.rms_svc_c
3순위: URL path의 serviceId
```

예를 들어 요청이 다음과 같으면:

```http
POST /mgcoa8888S0
```

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa8888D0"
    }
  }
}
```

실제로는 `mgcoa8888D0`가 선택될 가능성이 있습니다.

즉, 현재 구조에서는 다음과 같은 불일치가 가능합니다.

```text
요청 URL       : 조회 거래 S0
전문 서비스 ID : 삭제 거래 D0
실제 Dispatcher: 삭제 거래 D0
```

문서의 “path와 동일 권장”보다 더 강하게, 시스템에서 두 값의 일치 여부를 검증해야 합니다.

권장 검증:

```java
if (StringUtils.hasText(pathServiceId)
        && StringUtils.hasText(headerServiceId)
        && !pathServiceId.equals(headerServiceId)) {
    throw new IllegalArgumentException(
        "URL serviceId와 전문 rms_svc_c가 일치하지 않습니다."
    );
}
```

## 4. Handler 등록 및 중복 처리

`TransactionDispatcher`는 애플리케이션 시작 시 모든 `TransactionHandler` Bean을 수집해 서비스 ID Map을 만듭니다.

```text
serviceId                         Handler
------------------------------------------------
mgcoa5530S0  ──────────────────▶ mgcoa5530Handler
mgcoa8888S0  ─┐
mgcoa8888D0  ─┴────────────────▶ mgcoa8888Handler
mgcoa9000S0  ─┐
mgcoa9000C0   │
mgcoa9000U0   ├────────────────▶ mgcoa9000Handler
mgcoa9000D0  ─┘
```

동일 서비스 ID가 두 Handler에 등록되면 애플리케이션 시작 시 예외가 발생합니다.

```text
IllegalStateException:
Duplicate serviceId detected: mgcoa8888S0
```

이 동작은 정상적입니다. 한 거래가 어느 Handler로 전달될지 모호해지는 것을 시작 단계에서 방지합니다.

다만 현재 등록 과정에는 다음 검증이 없습니다.

- 서비스 ID 정규식 검증
- 대소문자 규칙 검증
- 공백 제거
- 구분자 유효성 검증
- 프로그램 접두와 Handler 이름 일치 검증
- UI Catalog 등록 여부 검증

## 5. 현재 등록된 서비스 ID

현재 Handler와 UI Catalog를 기준으로 확인되는 거래는 8개입니다.

| 서비스 ID     | 구분                | Handler            |
| ------------- | ------------------- | ------------------ |
| `mgcoa5530S0` | 마케팅희망고객 조회 | `mgcoa5530Handler` |
| `mgcoa8888S0` | 이미지로그 조회     | `mgcoa8888Handler` |
| `mgcoa8888D0` | 이미지로그 삭제     | `mgcoa8888Handler` |
| `mgcoa9999S0` | 영업팁 실적 조회    | `mgcoa9999Handler` |
| `mgcoa9000S0` | 거래 파라미터 조회  | `mgcoa9000Handler` |
| `mgcoa9000C0` | 거래 파라미터 등록  | `mgcoa9000Handler` |
| `mgcoa9000U0` | 거래 파라미터 수정  | `mgcoa9000Handler` |
| `mgcoa9000D0` | 거래 파라미터 삭제  | `mgcoa9000Handler` |

UI의 샘플 요청 파일에 있는 `rms_svc_c`도 현재 등록 ID와 일치합니다.

다만 다음 샘플은 구분해서 이해해야 합니다.

[mgcoa9000-update.json](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-ui/src/main/resources/sample-requests/mgcoa9000-update.json:4>)

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000U0"
    }
  },
  "data": {
    "txId": "mgcoa5530S0",
    "pathUrl": "/mgcoa5530S0"
  }
}
```

여기서:

- `rms_svc_c = mgcoa9000U0`는 현재 실행할 거래 ID입니다.
- `data.txId = mgcoa5530S0`는 DB에 저장하거나 수정할 거래통제 대상 데이터입니다.

두 필드 모두 서비스 ID 형태지만 역할이 완전히 다릅니다.

## 6. UI Catalog의 주의점

UI `TransactionCatalog`도 서비스 ID를 Map의 key로 등록합니다.

하지만 백엔드와 동작이 다릅니다.

```text
백엔드 Dispatcher
- 서비스 ID 중복 시 애플리케이션 시작 실패

UI TransactionCatalog
- 동일 ID를 다시 등록하면 기존 항목을 조용히 덮어씀
```

따라서 UI에서도 중복 검사를 추가하는 것이 좋습니다.

또한 UI 중계는 Catalog에 등록된 `path`를 사용합니다.

```text
catalog.id   = mgcoa8888S0
catalog.path = /mgcoa8888S0
```

현재 둘은 일치하지만 코드가 이를 강제하지는 않습니다. 잘못 등록하면 ID와 실제 호출 URL이 달라질 수 있습니다.

## 7. 프로그램 ID와 서비스 ID 구분

문서의 구분은 적절합니다.

```text
프로그램 ID : mgcoa8888
서비스 ID   : mgcoa8888S0
                         └ 거래 종류와 순번
```

하나의 프로그램 아래 여러 거래가 존재할 수 있습니다.

```text
mgcoa9000
  ├─ mgcoa9000S0
  ├─ mgcoa9000C0
  ├─ mgcoa9000U0
  └─ mgcoa9000D0
```

따라서 클래스는 프로그램 단위로 구성하고, 메서드와 DTO·SQL은 거래 단위로 구성하는 현재 방향이 타당합니다.

```text
mgcoa9000Handler
mgcoa9000Facade
mgcoa9000Service
mgcoa9000DAO

mgcoa9000S0DTOin
mgcoa9000C0DTOin
mgcoa9000U0DTOin
mgcoa9000D0DTOin
```

## 8. `scid` 생성 오류 가능성

[DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java:310>)는 서비스 ID에서 화면 ID를 만들 때 다음 정규식을 사용합니다.

```java
serviceId.replaceFirst("[SD]\\d+$", "")
```

따라서 현재 결과는 다음과 같습니다.

| 서비스 ID     | 생성되는 `scid` |
| ------------- | --------------- |
| `mgcoa8888S0` | `mgcoa8888`     |
| `mgcoa8888D0` | `mgcoa8888`     |
| `mgcoa9000C0` | `mgcoa9000C0`   |
| `mgcoa9000U0` | `mgcoa9000U0`   |

`S`, `D`만 제거하고 `C`, `U`, `A`, `R`은 제거하지 못합니다.

문서에서 정의한 구분자를 모두 지원하려면 다음과 같이 맞춰야 합니다.

```java
serviceId.replaceFirst("[SCUDAR][0-9A-Z]$", "")
```

같은 로직이 `ServicePreventionInterceptor`에도 있으므로 동시에 변경해야 합니다.

## 9. 저장소 전체 규칙과 충돌

루트 프로젝트 지침에서는 서비스 ID 표준을 다음처럼 설명합니다.

```text
{BusinessCode}.{Domain}.{action}
```

반면 PDMG 문서는 다음 형식을 사용합니다.

```text
mgcoa8888S0
```

따라서 “점 구분 서비스 ID는 쓰지 않는다”는 표현은 저장소 전체 표준으로 해석되면 충돌합니다.

다음처럼 범위를 명확히 해야 합니다.

> PDMG 업무 모듈은 기존 전문 및 UI 호환성을 위해 `mgcoa8888S0` 형식을 사용한다. 이 규칙은 PDMG 전용 규칙이며, 저장소 전체의 신규 서비스 ID 표준과는 구분한다.

## 10. 서비스 ID 변경 시 확인 범위

서비스 ID를 변경하려면 단순히 Handler 문자열만 바꾸면 안 됩니다.

```text
1. Handler
   - 상수
   - serviceIds()
   - handle() switch

2. Facade / Service
   - 메서드명
   - 로그 메시지
   - 테스트

3. DTO
   - DTOin / DTOout / Sub 타입명
   - JSON 계약 영향

4. DAO / Mapper
   - DAO 메서드
   - Mapper namespace
   - XML statement id

5. HTTP
   - Controller mapping
   - rms_svc_c
   - 샘플 요청

6. UI
   - TransactionCatalog id
   - path
   - 화면 호출부
   - 도움말 및 샘플

7. 운영·추적
   - ImageLog
   - 거래통제 테이블의 txId
   - 모니터링 및 로그 검색 조건
```

기존 서비스 ID는 외부 계약에 가깝기 때문에 변경보다는 신규 ID 추가 후 구 ID를 일정 기간 병행하는 방식이 안전합니다.

## 최종 평가

문서 정확도는 약 75~80%입니다. 기본 개념과 현재 목록은 잘 정리됐지만 다음 항목은 반드시 보완해야 합니다.

1. 전체 길이를 `10자`에서 `11자`로 수정
2. 서비스 ID 결정 우선순위를 실제 코드대로 기술
3. URL과 `rms_svc_c` 불일치 위험 명시
4. Facade·DTO·SQL 명명은 런타임 필수가 아니라 개발 규약임을 구분
5. `scid` 정규식의 C/U/A/R 미지원 문제 기록
6. PDMG 규칙과 저장소 공통 점 구분 규칙의 적용 범위 구분
7. 라우팅 서비스 ID와 업무 데이터의 `txId`를 명확히 구분

가장 쉽게 요약하면 다음과 같습니다.

```text
서비스 ID는 “거래 이름”이면서 Dispatcher의 정확한 라우팅 키다.

현재는 전문 헤더의 rms_svc_c가 URL보다 우선할 수 있으므로
URL만 보고 실행 거래를 판단해서는 안 된다.
```
