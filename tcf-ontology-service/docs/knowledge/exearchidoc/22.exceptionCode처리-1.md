# 22. `exceptionCode.yml` 처리 분석

## 1. 결론

현재 `exceptionCode.yml`은 Spring 환경에 정상적으로 로딩되고 `ExceptionCodeProperties`에도 바인딩됩니다.

하지만 실제 예외 응답에는 두 개의 예외 처리 체계가 혼재합니다.

```text
신규 TCF 예외 체계
  BizException
  → GlobalExceptionHandler
  → 현재 YAML 메시지를 조회하지 않음

레거시 예외 체계
  NhBaseException
  → ResponseBodyArgumentResolver
  → 일부는 YAML, 일부는 MessageCache 조회
```

따라서 현재 상태는 다음과 같습니다.

| 항목                     | 상태   |
| ------------------------ | ------ |
| YAML 로딩                | 정상   |
| Java Properties 바인딩   | 정상   |
| 대소문자 무시 조회       | 지원   |
| `{0}` 메시지 치환        | 지원   |
| 없는 코드의 기본 메시지  | 지원   |
| `BizException` 응답 연결 | 미완성 |
| Timeout 메시지 연결      | 미완성 |
| 실제 업무 Service 사용   | 없음   |
| 공통·업무 코드 분리      | 안 됨  |
| 동일 리소스 중복         | 있음   |
| 예외 체계 통합           | 안 됨  |

핵심적으로:

> 현재 `new BizException("MP0404")`를 던지면 메시지가 “요청한 영업팁 실적을 찾을 수 없습니다”가 아니라 코드 그대로 `"MP0404"`로 응답됩니다.

## 2. 환경 파일 로딩

[application.yml](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml:1>)에서 다음 파일을 가져옵니다.

```yaml
spring:
  config:
    import: classpath:exceptionCode.yml
```

처리 흐름:

```text
PDMG 기동
→ application.yml 로딩
→ classpath:exceptionCode.yml import
→ nhnis.exception.* Spring Environment 등록
→ ExceptionCodeProperties 바인딩
```

애플리케이션 클래스에는 다음 설정이 있습니다.

```java
@ConfigurationPropertiesScan("nhnis")
```

따라서 `nhnis.fw.exception.ExceptionCodeProperties`가 Spring Bean으로 등록됩니다.

## 3. 현재 등록된 오류 코드

파일: [exceptionCode.yml](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/exceptionCode.yml:1>)

```yaml
nhnis:
  exception:
    FW0001: "{0} 오류가 발생하였습니다."
    FW0002: "TEST Exception"
    FW0003: "{0} Exception 은 {1}로 문의해주세요"
    FW0401: "인증에 실패하였습니다. 다시 로그인해주세요."
    FW0403: "요청한 거래에 대한 권한이 없습니다."
    MP0404: "요청한 영업팁 실적을 찾을 수 없습니다."
    MP0409: "동일한 기본키의 영업팁 실적이 이미 존재합니다."
    FW9999: "예기치 않은 시스템 오류가 발생하였습니다. 시스템 관리자에게 문의해주세요."
    FW_TIMEOUT: "온라인 거래 처리시간을 초과했습니다."
    FW_OVERLOADED: "온라인 거래 처리 요청이 일시적으로 많습니다."
```

코드 성격은 다음과 같습니다.

| 코드            | 성격                   |
| --------------- | ---------------------- |
| `FW0001~FW0003` | 공통 프레임워크 메시지 |
| `FW0401`        | 인증 실패              |
| `FW0403`        | 권한 없음              |
| `MP0404`        | 업무 데이터 없음       |
| `MP0409`        | 업무 중복              |
| `FW9999`        | 미분류 시스템 오류     |
| `FW_TIMEOUT`    | 거래 타임아웃          |
| `FW_OVERLOADED` | Worker Pool 포화       |

PDMG 업무 코드인데 접두사가 `MP`인 점은 네이밍 기준과 확인이 필요합니다. PDMG 업무 코드를 `MG`로 볼지 기존 `MP` 계약을 유지할지 명확히 해야 합니다.

## 4. `ExceptionCodeProperties`

소스: [ExceptionCodeProperties.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/ExceptionCodeProperties.java:15>)

```java
@ConfigurationProperties("nhnis")
public class ExceptionCodeProperties {

    public static final String DEFAULT_CODE = "FW9999";

    private Map<String, String> exception =
            new LinkedHashMap<>();
}
```

YAML 구조와 다음과 같이 대응합니다.

```text
nhnis
└─ exception
   ├─ FW0001
   ├─ FW0401
   ├─ MP0404
   └─ FW9999
```

### 대소문자 무시

바인딩할 때 `TreeMap`을 사용합니다.

```java
Map<String, String> caseInsensitive =
        new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
```

따라서 다음 조회 결과는 같습니다.

```java
properties.message("MP0404");
properties.message("mp0404");
properties.message("Mp0404");
```

다만 오류 코드는 계약값이므로 호출부에서는 정해진 대문자 표기를 사용하는 것이 좋습니다.

## 5. 메시지 조회와 파라미터 치환

기본 조회:

```java
String message =
        properties.message("MP0404");
```

결과:

```text
요청한 영업팁 실적을 찾을 수 없습니다.
```

파라미터가 있는 메시지는 `MessageFormat`으로 치환합니다.

YAML:

```yaml
FW0001: "{0} 오류가 발생하였습니다."
```

Java:

```java
properties.message(
    "FW0001",
    "고객정보 조회"
);
```

결과:

```text
고객정보 조회 오류가 발생하였습니다.
```

두 개의 인자를 사용하는 경우:

```yaml
FW0003: "{0} Exception 은 {1}로 문의해주세요"
```

```java
properties.message(
    "FW0003",
    "DB",
    "시스템 관리자"
);
```

결과:

```text
DB Exception 은 시스템 관리자로 문의해주세요
```

## 6. 등록되지 않은 코드

다음처럼 없는 코드를 조회하면:

```java
properties.message("UNKNOWN_CODE");
```

내부에서 `FW9999` 메시지를 찾습니다.

```java
if (template == null) {
    template = exception.getOrDefault(
        DEFAULT_CODE,
        FALLBACK_MESSAGE
    );
}
```

결과:

```text
예기치 않은 시스템 오류가 발생하였습니다.
시스템 관리자에게 문의해주세요.
```

`FW9999`도 등록되어 있지 않으면 코드 내부 문자열을 사용합니다.

```text
시스템 오류가 발생하였습니다.
```

주의할 점은 `message()`가 메시지만 대체한다는 것입니다. 요청 코드까지 `FW9999`로 바꾸지는 않습니다.

예를 들어 향후 Handler에서 다음처럼 처리하면:

```java
String message =
    properties.message("UNKNOWN_CODE");
```

응답이 이렇게 될 수 있습니다.

```json
{
  "stdErrCode": "UNKNOWN_CODE",
  "stdErrMsgCntn": "예기치 않은 시스템 오류가 발생하였습니다."
}
```

알 수 없는 코드는 응답 코드도 `FW9999`로 정규화하는 것이 안전합니다.

# 7. `BizException` 처리

소스: [BizException.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/BizException.java:3>)

```java
public class BizException extends RuntimeException {

    private final String code;
    private final transient Object[] args;

    public BizException(String code, Object... args) {
        super(code);
        this.code = code;
        this.args = args;
    }
}
```

이 예외는 메시지를 조회하지 않습니다.

```java
throw new BizException("MP0404");
```

```text

getMessage() = MP0404
args         = []
```

YAML에 있는 메시지는 아직 사용되지 않았습니다.

## 8. `GlobalExceptionHandler`의 실제 문제

소스: [GlobalExceptionHandler.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java:36>)

현재 구현:

```java
@ExceptionHandler(BizException.class)
public ResponseEntity<NH_NIS_ERR_DTO>
        handleBizException(BizException e) {

    return error(
        e.getCode(),
        e.getMessage(),
        TYPE.BIZ,
        HttpStatus.INTERNAL_SERVER_ERROR,
        null
    );
}
```

`e.getMessage()`는 오류 코드이므로 현재 응답은 다음과 같습니다.

```json
{
  "hdr_nhnis": {
    "...": "..."
  },
  "result": {
    "stdErrCode": "MP0404",
    "stdErrMsgCntn": "MP0404",
    "errType": "BIZ"
  }
}
```

원래 기대되는 응답은 다음입니다.

```json
{
  "hdr_nhnis": {
    "...": "..."
  },
  "result": {
    "stdErrCode": "MP0404",
    "stdErrMsgCntn": "요청한 영업팁 실적을 찾을 수 없습니다.",
    "errType": "BIZ"
  }
}
```

즉, `ExceptionCodeProperties`를 Handler에 주입해야 합니다.

개념적인 연결 방식:

```java
private final ExceptionCodeProperties messages;

public GlobalExceptionHandler(
        ExceptionCodeProperties messages) {
    this.messages = messages;
}
```

```java
@ExceptionHandler(BizException.class)
public ResponseEntity<NH_NIS_ERR_DTO>
        handleBizException(BizException e) {

    String code = messages.getException()
            .containsKey(e.getCode())
            ? e.getCode()
            : ExceptionCodeProperties.DEFAULT_CODE;

    String message = messages.message(
            code,
            e.getArgs()
    );

    return error(
        code,
        message,
        TYPE.BIZ,
        HttpStatus.BAD_REQUEST,
        null
    );
}
```

현재는 이 연결이 없습니다.

# 9. 타임아웃 오류 코드

YAML에는 다음 메시지가 있습니다.

```yaml
FW_TIMEOUT: "온라인 거래 처리시간을 초과했습니다."
FW_OVERLOADED: "온라인 거래 처리 요청이 일시적으로 많습니다."
```

하지만 Handler에서는 YAML을 조회하지 않습니다.

```java
return error(
    "FW_TIMEOUT",
    e.getMessage(),
    TYPE.COMMON,
    HttpStatus.GATEWAY_TIMEOUT,
    detail
);
```

```java
return error(
    "FW_OVERLOADED",
    e.getMessage(),
    TYPE.COMMON,
    HttpStatus.SERVICE_UNAVAILABLE,
    detail
);
```

현재 응답 메시지는 다음 클래스가 자체 생성한 메시지입니다.

- `OnlineTimeoutException`
- `OnlineOverloadException`

따라서 YAML의 `FW_TIMEOUT`, `FW_OVERLOADED` 메시지를 수정해도 실제 HTTP 응답이 같이 변경된다고 보장할 수 없습니다.

정책을 YAML 중심으로 통일하려면:

```java
messages.message("FW_TIMEOUT")
messages.message("FW_OVERLOADED")
```

를 사용해야 합니다.

# 10. `ServiceHandlerNotFound`

Handler를 찾지 못하면 현재 다음 코드가 사용됩니다.

```java
return error(
    "E9999",
    e.getMessage(),
    TYPE.SERVICE,
    HttpStatus.INTERNAL_SERVER_ERROR,
    null
);
```

문제점:

- YAML에는 `E9999`가 없습니다.
- 기본 오류 코드는 `FW9999`로 정의되어 있습니다.
- 내부 메시지인 `e.getMessage()`가 클라이언트에 노출됩니다.
- 잘못된 serviceId 요청을 무조건 HTTP 500으로 반환합니다.

예:

```json
{
  "stdErrCode": "E9999",
  "stdErrMsgCntn": "mgcoa5530Handler 미지원 serviceId: ...",
  "errType": "SERVICE"
}
```

이는 내부 클래스명과 라우팅 구조를 노출할 수 있습니다.

권장 방향은 다음 중 하나입니다.

```text
등록되지 않은 serviceId → FW0404 또는 별도 FW 서비스 코드
내부 Handler 구성 오류  → FW9999
```

클라이언트 메시지와 서버 로그를 분리해야 합니다.

```text
클라이언트: 요청한 서비스를 찾을 수 없습니다.
서버 로그:  mgcoa5530Handler 미지원 serviceId=...
```

# 11. 레거시 `NhBaseException` 처리

`BizException`과 별도로 `NhBaseException` 처리도 존재합니다.

소스: [ResponseBodyArgumentResolver.java](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java:155>)

```java
@ExceptionHandler(NhBaseException.class)
public ResponseEntity<NH_NIS_ERR_DTO>
        errorProcessor(NhBaseException e) {
}
```

메시지 조회 방식은 예외 타입에 따라 다릅니다.

### Runtime/Common/Auth

```java
SpringContext.getProperty(
    "nhnis.exception." + e.getStdErrCode()
);
```

이 경로는 `exceptionCode.yml`을 조회합니다.

### Service/Biz

```java
messageCache.getMessage(
    e.getStdErrCode(),
    e.getMessageValue()
);
```

이 경로는 YAML이 아니라 `MessageCache`를 사용합니다.

따라서 동일한 `TYPE.BIZ`라도 예외 클래스에 따라 메시지 출처가 다릅니다.

```text
BizException
→ GlobalExceptionHandler
→ 현재 예외 코드 자체를 메시지로 반환

NhBaseException(TYPE.BIZ)
→ ResponseBodyArgumentResolver
→ MessageCache 조회
```

이 구조는 개발자가 어떤 예외 클래스를 사용하느냐에 따라 응답 메시지가 달라지는 문제를 만듭니다.

## 12. 레거시 처리의 null 오류 가능성

현재 코드는 다음과 같습니다.

```java
if (e.getErrMsgType() == null) {
    errorDto.setErrType(TYPE.RUNTIME.name());
}

if (e.getStdErrMsgContents() == null) {
    switch (e.getErrMsgType()) {
        // ...
    }
}
```

`errMsgType`이 null이면 응답 DTO에는 `RUNTIME`을 설정하지만, 바로 다음 `switch`에는 여전히 null 값을 넘깁니다.

```java
switch (null)
```

따라서 `stdErrMsgContents`도 null이면 `NullPointerException`이 발생할 수 있습니다.

실제로 사용할 타입을 별도 변수로 확정해야 합니다.

```java
TYPE type = e.getErrMsgType() == null
        ? TYPE.RUNTIME
        : e.getErrMsgType();

errorDto.setErrType(type.name());

switch (type) {
    // ...
}
```

# 13. 현재 업무 Service의 실제 사용 여부

현재 PDMG 업무 Service에서는 다음 코드가 없습니다.

```java
throw new BizException(...);
```

현재 C/U/D 업무 오류는 출력 DTO의 결과 코드로 반환합니다.

```java
output.setRSLT_CD("0001");
output.setRSLT_MSG("NO_DATA");
return output;
```

즉, 현재 처리 흐름은 다음과 같습니다.

```text
입력값 누락
→ BizException 없음
→ exceptionCode.yml 조회 없음
→ 업무 DTO RSLT_CD/RSLT_MSG 반환
→ HTTP 200 가능
→ 트랜잭션 정상 종료
```

예를 들어 `mgcoa9000C0`의 중복은:

```text
RSLT_CD  = 0002
RSLT_MSG = DUPLICATE_TX_ID
```

으로 처리하며 YAML의 `MP0409`를 사용하지 않습니다.

따라서 현재 `MP0404`, `MP0409`는 테스트 외 실제 업무 경로에서 사용되지 않는 코드입니다.

# 14. 응답 봉투 구성

`GlobalExceptionHandler`가 `NH_NIS_ERR_DTO`를 반환하면 `ResponseBodyArgumentResolver`가 이를 `result` 아래에 넣습니다.

```java
if (body instanceof NH_NIS_ERR_DTO) {
    responseBody.set("result", ...);
} else {
    responseBody.set("dto", ...);
}
```

성공 응답:

```json
{
  "hdr_nhnis": {},
  "dto": {}
}
```

오류 응답:

```json
{
  "hdr_nhnis": {},
  "result": {
    "stdErrCode": "MP0404",
    "stdErrMsgCntn": "...",
    "errType": "BIZ"
  }
}
```

이 성공/오류 분리는 적절합니다.

다만 Advice 내부에서 변환 예외를 잡아 `printStackTrace()`만 하고 계속 반환하는 문제가 있습니다. 오류 응답 조립이 실패해도 불완전한 본문이 나갈 수 있습니다.

# 15. 동일한 YAML 파일 중복

현재 실제로 파일이 두 곳에 존재합니다.

- [pdmg-service exceptionCode.yml](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/exceptionCode.yml:1>)
- [pdmg-fw exceptionCode.yml](</C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/resources/exceptionCode.yml:1>)

두 파일의 현재 해시는 동일합니다. 즉, 내용도 같습니다.

하지만 `pdmg-service`가 `pdmg-fw`를 의존하므로 실행 classpath에 같은 이름의 리소스가 두 개 들어갈 수 있습니다.

```text
pdmg-service/classes/exceptionCode.yml
pdmg-fw.jar!/exceptionCode.yml
```

현재 내용이 같아서 문제가 드러나지 않지만, 한쪽만 수정하면 어떤 파일이 선택되는지 이해하기 어려워집니다.

현재 문서의 다음 설명은 현행과 다릅니다.

```text
pdmg-fw/src/main/resources에는 별도 exceptionCode.yml이 없다.
```

실제로는 두 곳에 존재합니다.

### 권장 분리

```text
pdmg-fw/src/main/resources/
  pdmg-fw-exception-code.yml

pdmg-service/src/main/resources/
  pdmg-service-exception-code.yml
```

```yaml
spring:
  config:
    import:
      - classpath:pdmg-fw-exception-code.yml
      - classpath:pdmg-service-exception-code.yml
```

공통 코드:

```yaml
nhnis:
  exception:
    FW0001: ...
    FW0401: ...
    FW0403: ...
    FW9999: ...
    FW_TIMEOUT: ...
    FW_OVERLOADED: ...
```

업무 코드:

```yaml
nhnis:
  exception:
    MP0404: ...
    MP0409: ...
```

다만 같은 `nhnis.exception` Map을 여러 문서에서 병합할 때 Spring ConfigData 우선순위가 명확해야 합니다. 운영에서는 중복 코드 자체를 금지하는 편이 안전합니다.

# 16. HTTP 상태 코드

현재 `BizException`은 코드 종류와 관계없이 HTTP 500입니다.

```java
HttpStatus.INTERNAL_SERVER_ERROR
```

하지만 모든 업무 오류가 서버 장애는 아닙니다.

| 오류        | 적절한 HTTP 후보 |
| ----------- | ---------------: |
| 입력값 오류 |              400 |
| 인증 실패   |              401 |
| 권한 없음   |              403 |
| 데이터 없음 |              404 |
| 중복        |              409 |
| 시스템 오류 |              500 |
| 타임아웃    |              504 |
| 과부하      |              503 |

오류 코드에 HTTP 상태 메타데이터가 없기 때문에 Handler가 임의로 상태를 선택하고 있습니다.

단순 메시지 Map을 유지한다면 예외 유형별 Handler에서 상태를 지정해야 합니다. 더 체계적으로 관리하려면 코드별 메타데이터를 둘 수 있습니다.

```yaml
nhnis:
  exception:
    MP0404:
      message: "요청한 데이터를 찾을 수 없습니다."
      http-status: 404
      type: BIZ
```

다만 이는 현재 `Map<String,String>` 계약을 변경하므로 별도 설계가 필요합니다.

# 18. 중요도별 문제

## P0

1. `BizException`이 YAML 메시지를 사용하지 않음
2. 일반 `Exception` 처리기가 없어 예상하지 못한 예외의 표준 응답을 보장하지 못함
3. 레거시 `NhBaseException`에서 null TYPE일 때 `switch(null)` 가능

## P1

1. `exceptionCode.yml`이 FW와 Service에 중복
2. 신규·레거시 예외 처리 체계 혼재
3. 업무 오류를 모두 HTTP 500으로 반환
4. 등록되지 않은 코드가 원래 코드 그대로 응답될 가능성
5. 내부 Handler 오류 메시지가 클라이언트에 노출됨
6. 타임아웃 메시지가 YAML과 연결되지 않음

## P2

1. 공통 코드와 업무 코드 분리
2. 코드별 HTTP 상태 정책 정의
3. 실제 예외 응답 통합 테스트 추가
4. PDMG 업무 코드 접두사 기준 정리
5. `RSLT_CD`와 `stdErrCode` 사용 기준 통일

## 최종 평가

```text
현재:
exceptionCode.yml
→ Spring 로딩
→ ExceptionCodeProperties 바인딩
→ 테스트 조회 성공

그러나:
BizException
→ GlobalExceptionHandler
→ e.getMessage()
→ 코드 문자열이 메시지로 반환
```

권장 최종 흐름은 다음입니다.

```text
Service 또는 Rule
→ throw new BizException("MP0404")
→ GlobalExceptionHandler
→ 코드 등록 여부 확인
→ ExceptionCodeProperties.message("MP0404")
→ NH_NIS_ERR_DTO
→ ResponseBodyAdvice
→ { hdr_nhnis, result }
```

쉽게 말하면:

> `exceptionCode.yml`이라는 메시지 사전은 만들어졌지만, 신규 `BizException` 처리기가 아직 그 사전을 펼쳐보지 않고 있습니다. 현재는 오류 코드를 메시지로 그대로 반환하며, 업무 Service도 YAML 코드 대신 자체 `RSLT_CD/RSLT_MSG`를 사용합니다. 따라서 로딩은 정상이고 실제 업무 연결은 미완성입니다.
