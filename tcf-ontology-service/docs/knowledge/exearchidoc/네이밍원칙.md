# PDMG Service 네이밍 원칙

이 문서는 `pdmg-service`의 Java 코드와 아키텍처 구성요소에 적용하는 단일 네이밍 기준이다.  
이름은 대상의 **컴포넌트 타입·패키지·데이터 흐름**을 드러내야 한다.  
패키지 위치와 컴포넌트 매핑의 상세는 §4 및 [`MG-NAMING_CONVENTION.md`](./MG-NAMING_CONVENTION.md) §4를 따른다.

## 1. 목적과 적용 범위

다음 항목에 적용한다.

- Java 패키지, 파일, 타입, 메서드, 변수, 상수
- Handler, Facade, Controller, Service, DAO, DTO, Config, Filter, Aspect
- TCF(`OnlineTransactionController`, `TransactionHandler`), 표준 전문과 거래 식별자
- API, JSON, HTTP Header
- DB 객체, MyBatis XML과 SQL ID
- YAML, Spring Bean, 예외 코드, 로그와 MDC
- 테스트, 리소스, 스크립트와 문서

신규 코드에는 즉시 적용한다. 외부 연계나 DB·화면 프로그램과 결합된 기존 이름은 18장의 호환 예외를 따른다.

## 2. 규칙의 강도

| 구분 | 의미 |
|---|---|
| 필수 | 신규·변경 코드가 반드시 지킨다. |
| 권장 | 특별한 사유가 없다면 따른다. |
| 금지 | 신규 코드에 사용하지 않는다. |
| 호환 예외 | 외부 계약이나 기존 프레임워크 때문에 유지한다. |

우선순위는 `외부 계약 > 호환 예외 > 필수 > 권장`이다. 외부 계약과 연결된 이름은 영향 분석 없이 변경하지 않는다.

## 3. 공통 언어와 표기 원칙

- 코드 식별자는 영어, 설명 문서는 한국어를 사용할 수 있다.
- 같은 개념에는 같은 단어를 쓴다. 사용자 식별자는 `userId`로 통일한다.
- 의미가 분명한 완전한 단어를 우선하고 임의의 축약어를 만들지 않는다.
- 한 건은 단수, 컬렉션은 복수로 쓴다: `record`, `records`.
- 시간과 용량에는 단위를 붙인다: `elapsedMs`, `startedAtNanos`, `sizeBytes`.

### 약어

| 상황 | 원칙 | 예시 |
|---|---|---|
| 독립 프레임워크 컴포넌트 | 약어·확립명 유지 | `TCF`, `DAO`, `DTO`, `NH_NIS_ERR_DTO` |
| 확립된 Java 타입 계열 | PascalCase 유지 | `TcfFacade`, `TransactionHandler`, `JwtProvider` |
| 일반 역할 접미사 | Java 관례·PDMG 규칙 | `DTOin`, `DTOout`, `DAO`, `Handler`, `Facade` |
| 과거 호환 언급만 | 쓰지 않음 | `DtoIn`, `Dao`, `STF`/`ETF` 업무 진입 (신규 금지) |
| 상수·DB 객체 | 대문자와 밑줄 | `DEFAULT_SYSTEM_ID`, `TRT_BRC` |
| 변수·JSON | camelCase | `traceId`, `clientIp`, `sqlId` |

## 4. Java 패키지 명명 — 컴포넌트 ↔ 패키지 ↔ 이름

PDMG는 **컴포넌트 타입**을 기준으로 패키지와 이름을 설계한다.  
“Handler다”가 정해지면 패키지는 `entry.handler`, 이름은 `mgcoa[식별]Handler`로 고정된다.

상세 표·의존 방향은 [`MG-NAMING_CONVENTION.md`](./MG-NAMING_CONVENTION.md) §4 와 동일하다. 본 장은 원칙만 요약한다.

### 필수

- 모두 소문자로 쓰고 점(`.`)으로 계층을 구분한다.
- 공통 프레임워크는 `nhnis.fw`, Boot만 `nhnis.mg`, 업무는 `nhnis.mg.[업무].[세부].*` 아래에 둔다.
- 업무구분·세부업무구분은 서비스 ID와 같은 축을 **소문자**로 쓴다. 현재 샘플 `co.a`.
- Mapper 폴더 `rdw.mg.[업무].[세부]/` 와 Java 업무 축을 맞춘다.
- 마지막 패키지(세부패키지)는 **컴포넌트 타입**을 나타낸다 (`handler`, `facade`, `service` …).

### 컴포넌트 → 패키지 → 네이밍 (필수 매핑)

| 컴포넌트 | 패키지 (샘플 `co.a`) | 네이밍 골격 |
|---|---|---|
| Handler | `nhnis.mg.co.a.entry.handler` | `mgcoa[식별4]Handler` |
| Aspect | `nhnis.mg.co.a.entry.aspect` | 역할명 (`BizPrePostAspect`) |
| Controller | `nhnis.mg.co.a.application.controller` | `mgcoa[식별4]Controller` |
| Facade | `nhnis.mg.co.a.application.facade` | `mgcoa[식별4]Facade` · 메서드=`서비스ID` |
| Service | `nhnis.mg.co.a.application.service` | `mgcoa[식별4]Service` · 메서드=`서비스ID` |
| DTO | `nhnis.mg.co.a.dto` | `mgcoa[식별4][구분]DTOin/out/Sub` |
| DAO | `nhnis.mg.co.a.persistence.dao` | `mgcoa[식별4]DAO` · 메서드=`SQL ID` |
| Client | `nhnis.mg.co.a.client` | `*Client` |
| Config | `nhnis.mg.co.a.config` | `*Config` / `*Properties` |
| Support | `nhnis.mg.co.a.support` | 유틸 타입 |
| Mapper XML | `rdw.mg.co.a/` | `mgcoa[식별4]-ORA.xml` |

```text
nhnis.mg.[업무].[세부].[계층].[세부패키지]
```

현재 샘플:

```text
nhnis.mg.PdmgApplication
nhnis.mg.co.a.entry.handler
nhnis.mg.co.a.entry.aspect
nhnis.mg.co.a.application.controller
nhnis.mg.co.a.application.facade
nhnis.mg.co.a.application.service
nhnis.mg.co.a.dto
nhnis.mg.co.a.persistence.dao
nhnis.mg.co.a.config
nhnis.mg.co.a.client
nhnis.mg.co.a.support
```

### 설계 원칙

- **진입(`entry`)** 에는 TCF 라우팅(Handler)과 요청 횡단(Aspect)만 둔다.
- **애플리케이션(`application`)** 에는 HTTP 진입(Controller)·TX 경계(Facade)·업무(Service)를 둔다.
- **계약(`dto`)** 과 **영속(`persistence`)** 은 application과 분리한다.
- 식별번호가 같으면 Handler/Facade/Controller/Service/DAO 접두는 같고, 구분자(S/C/U/D)는 DTO·URL·SQL에만 붙인다.

### 금지

- 업무 코드를 `nhnis.mg.entry`처럼 업무·세부 세그먼트 없이 루트 바로 아래에 두지 않는다.
- Java 업무축과 Mapper `rdw.mg.*` 축을 어긋나게 두지 않는다.
- 컴포넌트 타입과 다른 패키지에 두지 않는다 (예: Handler를 `application`에 두기).
- `common` / `misc` / `util` 처럼 책임이 불분명한 패키지를 만들지 않는다.

## 5. Java 타입과 파일 명명

- 일반 타입은 PascalCase로 작성한다.
- public 최상위 타입과 파일명을 정확히 일치시킨다.
- 역할이 있는 타입은 역할 접미사를 사용한다.

```text
SecurityConfig.java              → SecurityConfig
StandardHeaderValidator.java     → StandardHeaderValidator
GlobalExceptionHandler.java      → GlobalExceptionHandler
TcfAuthenticationEntryPoint.java → TcfAuthenticationEntryPoint
```

- 인터페이스에 습관적으로 `I` 접두사를 붙이지 않는다.
- enum 타입은 PascalCase, enum 값은 UPPER_SNAKE_CASE로 작성한다: `ProcessingType.INQUIRY`.
- annotation은 선언 목적이 드러나는 PascalCase를 쓴다: `@Transactional`, `@RequestBody`.
- 예외는 `Exception`, 설정 바인딩 타입은 `Properties`로 끝낸다.

## 6. 메서드 명명

- camelCase 동사 또는 동사구로 시작한다.
- 이름으로 한 가지 책임을 설명할 수 있어야 한다.

| 목적 | 권장 이름 | 예시 |
|---|---|---|
| 조회 | `get`, `find`, `select` | `selectSalesTipDetail` |
| 목록 조회 | `find...List`, `select...List` | `selectSalesTipList` |
| 검증 | `validate`, `require` | `validate`, `require` |
| 변환·생성 | `to`, `from`, `of`, `copyOf`, `create` | `responseHeaderOf` |
| 등록·수정·삭제 | `save`, `insert`, `update`, `delete`, `remove` | `saveSalesTip` |
| 존재·상태 확인 | `exists`, `has`, `is` | `hasText` |

`doIt`, `proc`, `process1`, `handleData`처럼 대상을 설명하지 못하는 이름은 금지한다.

## 7. 변수·필드·상수 명명

- 변수와 필드는 camelCase를 사용한다.
- 컬렉션은 복수형을 사용한다: `records`, `headers`.
- 개수는 `count`, 크기는 `size`, 위치는 `offset`을 사용한다.
- boolean은 `is`, `has`, `can`, `should`, `enabled`로 질문처럼 읽히게 한다.
- `static final` 상수는 UPPER_SNAKE_CASE를 사용한다.

```java
String serviceId;
List<mgcoa9999S0DTOout> records;
long totalCount;
long elapsedMs;
boolean clientSuppliedHeader;
static final String HEADER_REQUEST_ID = "X-Request-Id";
```

단순 제네릭은 `T`, `K`, `V`를 사용할 수 있다. 여러 도메인 타입이 섞이면 의미 있는 타입 매개변수명을 쓴다.

## 8. 계층별 컴포넌트 명명

컴포넌트 타입 → 패키지 → 접미사/메서드 규칙이 한 세트다.  
자세한 매핑표는 §4 및 [`MG-NAMING_CONVENTION.md`](./MG-NAMING_CONVENTION.md) §4를 본다.

```text
TCF ON:
  Filter → OnlineTransactionController (FW)
    → Handler(entry) → Facade(application, @Transactional)
      → [BizPrePostAspect] Service(application) → DAO(persistence) → DB

TCF OFF:
  Filter → Controller(application) → Service → DAO
```

| 컴포넌트 | 패키지 | 접미사/형태 | 책임 | 예시 |
|---|---|---|---|---|
| Handler | `entry.handler` | `*Handler` | serviceId → Facade. `TransactionHandler` 구현 | `mgcoa8888Handler` |
| Aspect | `entry.aspect` | `*Aspect` | Service 선·후처리 / TX-FLOW | `BizPrePostAspect` |
| Facade | `application.facade` | `*Facade` | DTO 변환, `@Transactional`, Service 호출 | `mgcoa8888Facade` |
| Controller | `application.controller` | `*Controller` | TCF OFF HTTP 진입 | `mgcoa8888Controller` |
| Service | `application.service` | `*Service` | 업무 규칙. TX는 Facade | `mgcoa8888Service` |
| DTO | `dto` | `*DTOin/out/Sub` | 계층 간 데이터 계약 | `mgcoa8888S0DTOin` |
| DAO | `persistence.dao` | `*DAO` | MyBatis 메서드=SQL ID | `mgcoa8888DAO` |
| Config | `config` | `*Config` / `*Properties` | Bean·설정 조립 | `SecurityConfig` |
| Client | `client` | `*Client` | 외부 연동 | (필요 시) |
| Support | `support` | 유틸 | 공통 헬퍼 | (필요 시) |
| Filter (FW) | `nhnis.fw…` | `*Filter` | 요청 전후 공통 | `DefaultFilter` |
| Interceptor (FW) | `nhnis.fw…` | `*Interceptor` | 시스템 선후처리 | `ServicePreventionInterceptor` |
| 전역 Handler (FW) | `nhnis.fw…` | `*Handler` | 예외→응답. 업무 Handler와 구분 | `GlobalExceptionHandler` |

### Handler 원칙 (필수)

- 패키지: `nhnis.mg.co.a.entry.handler`
- 이름: `[대구분][업무][세부][식별번호4자리]Handler` (구분자 S/C/U/D 미포함)
- 동일 식별번호의 여러 서비스 ID는 **하나의 Handler**로 묶는다.
- `TransactionHandler`를 구현하고 `serviceIds()` / `handle(...)`만 제공한다.
- Facade만 주입한다. Service·DAO·`ObjectMapper`·`@Transactional`은 넣지 않는다.
- TCF ON에서만 Bean 등록: `@ConditionalOnProperty(name = "nhnis.fw.tcf.enabled", havingValue = "true")`

### Facade 원칙 (필수)

- 패키지: `nhnis.mg.co.a.application.facade`
- 이름: `[대구분][업무][세부][식별번호4자리]Facade` (구분자 미포함)
- 동일 식별번호의 여러 서비스는 **하나의 Facade**로 묶는다.
- 메서드명 = 서비스 ID (`mgcoa8888S0`). 입력은 `Object dtoBody`, 출력은 typed `*DTOout`.
- `@Transactional(transactionManager = "rdwTransactionManager")` 은 Facade 메서드에 둔다. 조회는 `readOnly = true`.
- Bean 스테레오타입은 `@Service`를 사용한다 (역할명은 Facade).
- Service만 호출한다. SQL·HTTP 응답 조립은 하지 않는다.

### Controller 원칙 (필수)

- 패키지: `nhnis.mg.co.a.application.controller`
- 이름: `[대구분][업무][세부][식별번호4자리]Controller`
- TCF OFF 호환용. `@ConditionalOnProperty(..., havingValue = "false", matchIfMissing = true)`
- 클래스 `@RequestMapping` 금지. 메서드 `@PostMapping("/서비스ID")`
- 신규 TCF ON 거래는 Handler+Facade를 우선하고 Controller는 필요 시에만 둔다.

### Service / DTO / DAO 원칙 (필수)

- Service 패키지 `application.service`, 메서드명 = 서비스 ID, TX 미보유.
- DTO 패키지 `dto`, 이름 `…DTOin` / `…DTOout` / `…DTOSub0`, 필드 camelCase.
- DAO 패키지 `persistence.dao`, 메서드명 = SQL ID, `@RDWMapper`.

Handler·Facade·Controller는 SQL을 실행하지 않고, DAO는 업무 판단을 하지 않으며, DTO는 Service를 호출하지 않는다.  
업무 `*Handler`와 FW `GlobalExceptionHandler`를 혼동하지 않는다.

## 9. DTO와 표준 전문 명명

### 업무 DTO (PDMG)

```text
입력:  <서비스ID>DTOin      → mgcoa8888S0DTOin
출력:  <서비스ID>DTOout     → mgcoa8888S0DTOout
목록행: <서비스ID>DTOSub0   → mgcoa8888S0DTOSub0
```

패키지: `nhnis.mg.co.a.dto`

### 표준 전문 (요청/응답 봉투)

```text
hdr_nhnis          (헤더)
dto                (업무 본문: *DTOin / *DTOout)
NH_NIS_ERR_DTO     (실패 시)
```

DTO와 JSON 필드는 camelCase로 일치시킨다. DTO에는 DB 접근, 트랜잭션, 외부 호출 같은 업무 동작을 넣지 않는다. `Map<String, Object>`는 구조가 실제로 동적인 경우에만 쓴다.

## 10. TCF 아키텍처 명명

| 이름 | 책임 |
|---|---|
| `OnlineTransactionController` | FW 공통 HTTP 진입 (`POST /online`, `POST /{serviceId}`) |
| `TcfFacade` | FW 거래 디스패치. 업무 Facade와 이름만 유사하고 계층이 다름 |
| `TransactionHandler` | 업무 Handler가 구현하는 라우팅 계약 |
| `TransactionContext` | 한 거래의 serviceId·요청 상태 |
| `BizPrePostAspect` | Service 호출 선·후처리 (`nhnis.mg.co.a.application.service..*`) |
| `ServicePreventionInterceptor` | FW 시스템 선·후처리 |

```text
serviceId:        mgcoa8888S0
```

- `serviceId`는 `mg` + 업무 + 세부 + 식별번호 + 구분자 + 순번 규칙을 사용한다. (`MG.Xxx.yyy` 점 구분 체계는 쓰지 않는다.)
- 업무 진입은 `*Handler` → `*Facade` → `*Service` 이다.
- DB commit/rollback은 Facade의 `@Transactional`이 담당한다.
- FW `TcfFacade`와 업무 `mgcoa*Facade`를 혼동하지 않는다.

## 11. API·JSON·HTTP 명명

- API 경로는 소문자를 사용하고 계층을 `/`로 구분한다.
- 현재 RPC형 거래는 마지막 경로에 명확한 동사를 사용한다.

```text
/api/mp/co/a/9999/list
/api/mp/co/a/9999/detail
```

- JSON 필드는 camelCase를 사용한다.
- 표준 요청은 `header`, `body`, 응답은 `header`, `result`, `body`를 사용한다.
- 이전 JSON 이름 호환은 `@JsonAlias`로 제한한다.
- HTTP Header는 표준 하이픈 표기를 사용한다.

```text
X-Request-Id
X-Trace-Id
X-User-Id
X-Forwarded-For
Authorization
```

## 12. DB·MyBatis 명명

### DB

- 테이블, 컬럼, 제약조건은 UPPER_SNAKE_CASE를 사용한다.

```text
TB_CR_AH_SALES_TIP_RACT
TRT_BRC
SALZ_TIP_KDC
TB_CR_AH_SALES_TIP_RACT_PK
```

### MyBatis

- mapper `namespace`는 DAO 완전한 클래스명과 일치시킨다.
- statement `id`는 DAO 메서드명과 정확히 일치시킨다.
- `parameterType`, `resultType`은 실제 Java 타입과 일치시킨다.
- SQL alias는 DTO 필드의 camelCase와 일치시킨다.

```xml
<mapper namespace="nhnis.mg.co.a.persistence.dao.mgcoa8888DAO">
<select id="mgcoa8888S0_S0">
```

`mgcoa8888S0_S0` 같은 SQL ID는 서비스 ID 계약이므로 임의로 바꾸지 않는다. mapper 파일은 `rdw.mg.[업무].[세부]/[프로그램ID]-ORA.xml` 규칙을 사용한다.

```text
rdw.mg.co.a/mgcoa8888-ORA.xml
```

## 13. Spring 설정과 Bean 명명

- Bean 조립 클래스는 `Config`, 외부 설정 바인딩 클래스는 `Properties`로 끝낸다.
- Bean 이름은 lowerCamelCase를 사용한다.
- 같은 타입의 Bean이 여러 개면 데이터소스와 목적을 명시한다.

```text
RdwDataSourceConfig
CorsProperties
rdwDataSource
rdwSqlSessionFactory
rdwSqlSessionTemplate
rdwTransactionManager
securityFilterChain
```

YAML 키는 lowercase kebab-case를 사용하고 시간 값은 이름이나 값에 단위를 명시한다.

```yaml
nsight:
  tcf:
    slow-transaction-ms: 3000
```

비밀번호, JWT secret, 실제 접속정보를 예제 이름이나 문서에 노출하지 않는다.

## 14. 예외·결과 코드 명명

- 업무·시스템 오류 코드는 `FW`와 네 자리 숫자를 사용한다: `FW0001`, `FW0401`, `FW9999`.
- 하나의 코드는 하나의 의미에만 사용한다.
- 메시지는 `exceptionCode.yml`의 `nhnis.exception` 아래에서 관리한다.
- 예상하지 못한 시스템 오류의 기본 코드는 `FW9999`다.

```text
S0000 / E0001 형태의 resultCode 봉투는 쓰지 않는다.
성공: { hdr_nhnis, dto }
실패: NH_NIS_ERR_DTO (stdErrCode, stdErrMsgCntn, errType)
```

업무 오류는 `BizException`, 미분류 오류는 일반 `Exception`으로 구분한다.  
실패 응답 조립은 `GlobalExceptionHandler` → `NH_NIS_ERR_DTO` 가 담당하고 Handler/Controller별 오류 형식을 만들지 않는다.  
(구 ETF/`result.resultCode` 계약은 사용하지 않는다.)

```java
SUCCESS_CODE
FAIL_CODE
DEFAULT_CODE
CODE_REQUIRED
CODE_UNAUTHENTICATED
```

## 15. 로그·MDC·로그 파일 명명

### MDC

다음 lowerCamelCase 이름을 공통 사용한다.

```text
guid
traceId
userId
serviceId
ip
sqlId
ifId
errCode
```

같은 값을 `requestId`, `reqId`, `guid`처럼 중복 정의하지 않는다.

### 로그 태그

컴포넌트명과 일치시킨다: `[업무 선처리]`, `[TX-FLOW]`, `[TRACE]`, `[SQL]`, `[GlobalExceptionHandler]`.

### 로그 파일

`<project>_<purpose>.log`를 사용한다.

```text
pk_framework.log
pk_service.log
pk_framework_yyyy-MM-dd.log.gz
pk_service_yyyy-MM-dd.log.gz
```

`pk_`는 `pdmg-service`의 권장 접두사다. 운영 로그 수집기가 기존 이름에 의존하면 수집 계약을 확인한 뒤 별도 변경한다.

## 16. 테스트 명명

- 단위 테스트 클래스는 `<대상타입>Test`로 끝낸다.
- 통합 테스트는 `<기능>IntegrationTest`를 사용할 수 있다.
- 테스트 메서드는 대상, 조건, 기대결과를 표현한다.

```java
class mgcoa8888ServiceTest { }
class mgcoa8888DaoIntegrationTest { }

void mgcoa8888S0_missingKey_throwsBizException() { }
void facade_write_timeout_rollsBack() { }
```

`test1`, `successTest`, `tempTest`처럼 실패 원인을 설명하지 못하는 이름은 사용하지 않는다.

## 17. 리소스와 문서 명명

- 기본 설정은 `application.yml`을 사용한다.
- 도구가 요구하는 표준 이름은 유지한다: `log4j2.xml`, `schema.sql`, `data.sql`.
- DB 종류가 계약에 포함되면 `-ORA.xml`처럼 접미사를 명시한다.
- 문서명은 내용을 바로 알 수 있게 작성하고 같은 주제의 기준 문서를 둘 이상 만들지 않는다.
- 설계·실행 기록은 `docs/superpowers/specs`, `docs/superpowers/plans`에 날짜와 영문 kebab-case를 사용한다.

```text
docs/네이밍원칙.md
docs/트랜잭션처리.md
docs/superpowers/specs/2026-08-01-naming-principles-design.md
```

## 18. 레거시 호환 예외

| 기존 이름 | 유지 이유 |
|---|---|
| `mgcoa8888Handler` / `mgcoa8888Facade` | 식별번호 단위 소문자 접두사 결합 규칙 |
| `mgcoa8888Controller` | TCF OFF 호환 HTTP 진입 |
| `mgcoa8888Service` | Handler·Facade·DAO·XML과 프로그램 ID 공유 |
| `mgcoa8888DAO` | MyBatis namespace 계약 |
| `mgcoa8888S0DTOin/out` | 전문·SQL 매핑 계약 |
| `mgcoa8888S0_S0` | 프로그램·SQL ID 계약 |

이 이름들은 일부만 독립적으로 바꾸지 않는다. 새 호환 예외가 필요하면 외부 계약, 영향 범위, 종료 조건을 문서화한다.

## 19. 금지 목록

### 금지 이름

```text
data
obj
temp
tmp
proc
doIt
value1
list2
commonUtil
misc
```

### 금지 구조

- public 타입과 Java 파일명을 다르게 작성한다.
- Handler·Facade·Controller에서 SQL을 실행하거나 DAO에서 HTTP 응답을 만든다.
- Handler에서 Service/DAO를 직접 호출하거나 `@Transactional`을 건다.
- Facade 없이 Handler만으로 업무·트랜잭션을 처리한다.
- DTO에 Service 또는 DAO를 주입한다.
- 동일 개념에 여러 약어를 만든다.
- 시간·용량 변수에서 단위를 생략한다.
- DAO 메서드와 MyBatis statement ID를 다르게 작성한다.
- DB alias와 DTO 필드명을 불일치시킨다.
- 동일 주제의 별도 네이밍 기준 문서를 만든다.
- 비밀값이나 개인정보를 이름·로그·문서 예시에 넣는다.

| 좋은 이름 | 나쁜 이름 | 이유 |
|---|---|---|
| `elapsedMs` | `elapsed` | 단위가 명확함 |
| `salesTipRecords` | `dataList` | 도메인과 복수가 명확함 |
| `CODE_UNAUTHENTICATED` | `ERR1` | 오류 의미가 명확함 |
| `selectSalesTipDetail` | `procDetail` | 동작과 대상이 명확함 |
| `rdwTransactionManager` | `txManager2` | 데이터소스 목적이 명확함 |
| `StandardHeaderValidator` | `HeaderUtil` | 책임이 명확함 |

## 20. 신규 코드 체크리스트

- [ ] 컴포넌트 타입(Handler/Facade/Controller/Service/DAO/DTO…)을 먼저 정했는가?
- [ ] 패키지가 §4 매핑표의 컴포넌트→패키지 규칙과 일치하는가? (`nhnis.mg.[업무].[세부].[계층]…`)
- [ ] Boot 클래스만 `nhnis.mg`에 두고, 업무 코드는 `nhnis.mg.co.a`(또는 해당 업무 축) 아래인가?
- [ ] Mapper 경로 `rdw.mg.[업무].[세부]/` 와 Java 업무 축이 같은가?
- [ ] 타입 이름이 컴포넌트 접미사(`Handler`/`Facade`/`Service`/`DAO`/`Controller`/`DTOin`…)와 맞는가?
- [ ] 식별번호가 같으면 Handler·Facade·Service·DAO 접두(`mgcoa8888`)가 같은가?
- [ ] Facade/Service 메서드명·URL·SQL ID가 서비스 ID 규칙과 맞는가?
- [ ] public 타입과 파일명이 정확히 일치하는가?
- [ ] 타입은 PascalCase, 메서드·변수는 camelCase, 상수는 UPPER_SNAKE_CASE인가?
- [ ] TCF ON 신규 거래에 Handler + Facade가 있고, TX는 Facade에 있는가?
- [ ] Handler가 Service/DAO를 직접 호출하지 않는가?
- [ ] DTO와 JSON 필드가 camelCase로 일치하는가?
- [ ] DAO 메서드, mapper ID, namespace가 일치하는가?
- [ ] `data`, `temp`, `proc`, `doIt` 같은 모호한 이름이 없는가?
- [ ] 비밀값이나 개인정보가 이름과 예시에 없는가?

체크리스트를 통과하지 못한 이름은 구현 내용이 맞더라도 수정한 뒤 병합한다.
