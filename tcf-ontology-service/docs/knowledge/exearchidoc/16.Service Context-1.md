## 16. ServiceContext 분석 결과

`ServiceContext`는 HTTP 요청 한 건에서 공통으로 사용하는 요청 단위 저장소입니다.

쉽게 말하면 다음과 같습니다.

```text
ServiceContext
= 한 거래의 공통정보 가방

ServiceContextHolder
= 현재 요청 스레드가 그 가방을 찾는 보관함
```

주요 소스:

- [ServiceContext.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/context/ServiceContext.java:14>)
- [ServiceContextHolder.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/context/ServiceContextHolder.java:3>)

## 1. 전체 생명주기

```text
HTTP 요청
  ↓
DefaultFilter
  ├─ hdr_nhnis 파싱·생성
  ├─ 요청 Body 캐시
  ├─ new ServiceContext(...)
  ├─ context.setRequestBody(...)
  └─ ServiceContextHolder.setInstance(context)
       ↓
ServicePreventionInterceptor
  ├─ Context 조회
  ├─ GUID·헤더 보완
  └─ 요청 ImageLog
       ↓
OnlineTransactionController
  ├─ serviceId 조회
  └─ IP·헤더 보완
       ↓
Timeout Executor
  ├─ 요청 스레드 Context 캡처
  ├─ worker thread에 설치
  └─ Handler → Facade → Service
       ↓
ResponseBodyAdvice
  ├─ hdr_nhnis 응답에 추가
  └─ context.setResponseBody(...)
       ↓
Interceptor.afterCompletion
  └─ 응답 ImageLog
       ↓
DefaultFilter.finally
  ├─ ServiceContextHolder.removeInstance()
  └─ MDC clear
```

## 2. ServiceContext 필드

현재 필드는 다음과 같습니다.

| 필드                  | 의미                     | 주요 입력자         |
| --------------------- | ------------------------ | ------------------- |
| `applicationName`     | 애플리케이션 이름        | DefaultFilter       |
| `guid`                | 거래 추적 GUID           | Filter, Interceptor |
| `active`              | 활성 프로파일            | Filter              |
| `requestHeaders`      | HTTP 요청 헤더 복사본    | Filter              |
| `httpServletRequest`  | 실제 또는 캐시 래퍼 요청 | Filter              |
| `httpServletResponse` | HTTP 응답 객체           | Filter              |
| `header`              | 표준 `hdr_nhnis`         | Filter, Interceptor |
| `userContext`         | 사용자 확장정보 Map      | 현재 거의 미사용    |
| `requestBody`         | 요청 전문 원문           | Filter              |
| `responseBody`        | 응답 전문 원문           | ResponseBodyAdvice  |

### 생성 시 입력

```java
ServiceContext context = new ServiceContext(
        applicationName,
        guid,
        active,
        requestHeaders,
        request,
        response,
        header
);
```

이후 필요한 정보가 추가됩니다.

```java
context.setRequestBody(requestBody);
context.setGuid(guid);
context.setHeader(header);
context.setResponseBody(responseBody);
```

## 3. Getter와 Setter

`ServiceContext`에는 Lombok `@Getter`가 있습니다.

```java
@Getter
public class ServiceContext {
}
```

따라서 모든 필드에 Getter가 생성됩니다.

```java
context.getApplicationName();
context.getGuid();
context.getActive();
context.getRequestHeaders();
context.getHttpServletRequest();
context.getHttpServletResponse();
context.getHeader();
context.getUserContext();
context.getRequestBody();
context.getResponseBody();
```

명시적으로 제공되는 Setter는 네 개입니다.

```java
setGuid(...)
setHeader(...)
setRequestBody(...)
setResponseBody(...)
```

`userContext`에는 Setter가 없지만 Getter가 반환하는 Map을 통해 값을 넣을 수 있습니다.

```java
ServiceContext context =
        ServiceContextHolder.getInstance();

context.getUserContext().put("branchCode", "001");
context.getUserContext().put("userId", "USER100");
```

조회:

```java
String branchCode = (String) context
        .getUserContext()
        .get("branchCode");
```

다만 업무 핵심정보를 문자열 키 기반 Map에 과도하게 저장하는 것은 권장하지 않습니다.

## 4. ServiceContextHolder

구현은 단순한 `ThreadLocal`입니다.

```java
private static ThreadLocal<ServiceContext> INSTANCE =
        new ThreadLocal<>();
```

### 저장

```java
ServiceContextHolder.setInstance(context);
```

### 조회

```java
ServiceContext context =
        ServiceContextHolder.getInstance();
```

값이 없으면 예외가 아니라 `null`을 반환합니다.

```java
if (context == null) {
    // Filter 밖에서 호출됐거나 다른 스레드일 수 있음
}
```

### 제거

```java
ServiceContextHolder.removeInstance();
```

서버 스레드 풀은 같은 스레드를 다음 요청에 다시 사용하기 때문에 반드시 제거해야 합니다.

제거하지 않으면:

```text
사용자 A 요청 Context
→ 스레드에 남음
→ 같은 스레드가 사용자 B 요청 처리
→ 사용자 A 정보가 사용자 B 요청에서 조회될 위험
```

현재는 `DefaultFilter.finally`에서 정리하므로 일반 HTTP 요청은 안전한 구조입니다.

## 5. DefaultFilter에서 생성

일반 JSON 요청에서는 다음 순서입니다.

```text
요청 Body 캐시
→ hdr_nhnis 파싱
→ GUID·서비스ID·IP·사용자 보완
→ ServiceContext 생성
→ 요청 원문 저장
→ ThreadLocal 등록
```

핵심 코드:

```java
ServiceContext serviceContext = new ServiceContext(
        applicationName,
        guid,
        active,
        requestHeaders,
        wrapper,
        response,
        header
);

serviceContext.setRequestBody(requestBody);
ServiceContextHolder.setInstance(serviceContext);
```

multipart 요청에서는 Body 원문을 저장하지 않고 최소 Context만 생성합니다.

## 6. Interceptor에서 보완

`ServicePreventionInterceptor`는 Context가 존재하면 다음 값을 보완합니다.

```text
header가 null → 새 hdr_nhnis 생성
sys_comm이 null → 새 sys_comm 생성
GUID가 null → UUID 생성
serviceId가 null → URL에서 추출
IP가 null → 요청에서 추출
사용자가 null → MDC 또는 LOCAL
```

GUID는 다음 세 위치를 맞춥니다.

```text
ServiceContext.guid
header.sys_comm.std_gbl_id
ThreadContext["guid"]
```

세 값이 같아야 요청 로그와 ImageLog를 동일 거래로 추적할 수 있습니다.

## 7. Controller에서 사용하는 정보

`OnlineTransactionController`는 Context를 이용해 serviceId를 결정합니다.

```java
ServiceContext context =
        ServiceContextHolder.getInstance();

String serviceId = context
        .getHeader()
        .getSys_comm()
        .getRms_svc_c();
```

우선순위는 다음과 같습니다.

```text
1. ServiceContext의 rms_svc_c
2. 요청 JSON의 rms_svc_c
3. URL path serviceId
```

따라서 Context 헤더 값이 URL과 다르면 Context 값이 선택됩니다.

URL과 헤더가 모두 존재할 경우 일치 검증이 필요합니다.

## 8. 업무 Aspect에서 사용

`BizPrePostAspect`는 Service 실행 전에 다음 값을 조회합니다.

```java
ServiceContext ctx =
        ServiceContextHolder.getInstance();

String guid = ctx != null
        ? ctx.getGuid()
        : null;

String serviceId = ctx.getHeader()
        .getSys_comm()
        .getRms_svc_c();
```

현재 용도는 대부분 로그입니다.

```text
GUID
서비스 ID
업무 메서드
BRC
```

업무 Service와 DAO가 Context에 직접 의존하지 않고 DTO를 사용하는 현재 방향은 적절합니다.

## 9. TransactionContext와 차이

두 Context는 역할이 다릅니다.

| 구분          | ServiceContext         | TransactionContext              |
| ------------- | ---------------------- | ------------------------------- |
| 범위          | HTTP 요청 전체         | TCF 처리 구간                   |
| 저장          | ThreadLocal            | 메서드 인자                     |
| 주요 정보     | HTTP, 헤더, GUID, 전문 | serviceId, 시작시간             |
| Servlet 객체  | 포함                   | ServiceContext를 통해 간접 포함 |
| 트랜잭션 객체 | 없음                   | 없음                            |

`TransactionContext`는 다음과 같이 현재 ServiceContext를 참조합니다.

```java
return new TransactionContext(
        serviceId,
        ServiceContextHolder.getInstance()
);
```

즉:

```text
TransactionContext
  ├─ serviceId
  ├─ startedAtNanos
  └─ ServiceContext 참조
```

ServiceContext가 트랜잭션을 관리하는 것은 아닙니다.

```text
ServiceContext ≠ DB Transaction
ServiceContextHolder ≠ TransactionManager
```

## 10. 타임아웃 worker thread 전달

일반적인 `ThreadLocal` 값은 다른 스레드로 자동 전달되지 않습니다.

```text
HTTP 요청 스레드
  ServiceContext 있음

worker thread
  ServiceContext 없음
```

현재 PDMG는 이를 해결하기 위해 `OnlineTimeoutWorkerContext`를 사용합니다.

[OnlineTimeoutWorkerContext.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/tcf/timeout/OnlineTimeoutWorkerContext.java:18>)

### 요청 스레드에서 캡처

```java
ServiceContext ctx =
        ServiceContextHolder.getInstance();

OnlineTimeoutWorkerContext workerContext =
        OnlineTimeoutWorkerContext.capture();
```

함께 캡처하는 값:

```text
ServiceContext
MDC 전체
GUID
serviceId
```

### worker thread에 설치

```java
workerContext.install();
```

내부:

```java
ServiceContextHolder.setInstance(serviceContext);
ThreadContext.putAll(mdc);
```

따라서 worker에서 실행되는 다음 계층도 Context를 조회할 수 있습니다.

```text
Handler
Facade
BizPrePostAspect
Service
```

### worker 종료 시 제거

```java
finally {
    workerContext.clear();
}
```

내부:

```java
ServiceContextHolder.removeInstance();
ThreadContext.clearAll();
```

이 정리는 worker pool 스레드 재사용 누수를 방지합니다.

## 11. worker Context의 중요한 문제

`OnlineTimeoutWorkerContext` 주석에는 다음과 같이 되어 있습니다.

```text
Servlet request/response는 보관하지 않는다.
```

하지만 실제 구현은 새로운 안전한 Context를 만드는 것이 아니라 기존 객체를 그대로 저장합니다.

```java
private final ServiceContext serviceContext;
```

그 `ServiceContext` 안에는 다음 참조가 들어 있습니다.

```java
HttpServletRequest
HttpServletResponse
```

따라서 실제 구조는:

```text
요청 스레드
   └─ ServiceContext ─────────┐
                              ├─ 같은 객체
worker thread                 │
   └─ ServiceContext ─────────┘
       ├─ HttpServletRequest
       └─ HttpServletResponse
```

즉, 주석과 구현이 다릅니다.

### 정상 완료

worker가 끝난 뒤 요청 스레드가 응답을 처리하므로 대부분 문제가 드러나지 않습니다.

### 타임아웃 발생

```text
요청 스레드:
  future.cancel(true)
  → timeout 응답 처리
  → ResponseBodyAdvice가 Context 수정

worker thread:
  interrupt를 무시하면 계속 실행 가능
  → 같은 Context 객체 조회·사용
```

두 스레드가 같은 mutable 객체를 공유할 수 있습니다.

특히 다음 필드는 동기화되지 않았습니다.

```text
guid
header
userContext
requestBody
responseBody
```

이로 인해 다음 문제가 생길 수 있습니다.

- 응답 Body 경합
- 헤더 변경 경합
- 타임아웃 응답 이후 worker가 Context를 수정
- Servlet request/response를 worker에서 잘못 사용
- 요청 완료 후 Servlet 객체 접근
- 예측하기 어려운 로그와 ImageLog 결과

## 12. 권장 worker 전달 구조

worker에는 Servlet 객체를 넘기지 않는 스냅샷이 안전합니다.

예:

```java
public record ServiceContextSnapshot(
        String applicationName,
        String guid,
        String active,
        hdr_nhnis header,
        Map<String, Object> userContext,
        String requestBody
) {
}
```

요청 스레드에서 깊은 복사:

```text
ServiceContext
  ↓ capture
ServiceContextSnapshot
  ├─ guid 복사
  ├─ header 깊은 복사
  ├─ userContext 복사
  └─ requestBody 복사
```

worker에는 다음을 전달하지 않습니다.

```text
HttpServletRequest
HttpServletResponse
원본 mutable header
원본 mutable userContext
```

더 단순하게는 worker의 업무 코드가 필요한 값만 명시적 인자로 받는 것이 가장 안전합니다.

```java
handler.handle(
    transactionContext,
    dtoBody
);
```

## 13. 요청 헤더 보관 위험

`DefaultFilter`는 모든 HTTP 요청 헤더를 `HttpHeaders`에 복사합니다.

여기에는 다음 정보가 포함될 수 있습니다.

```text
Authorization: Bearer ...
Cookie
Session ID
내부 인증 헤더
```

현재 요청 처리 동안만 보관되고 종료 시 Context 참조가 해제되므로 일반 흐름은 괜찮습니다.

하지만 다음은 피해야 합니다.

```text
requestHeaders 전체 로그 출력
Context를 세션·캐시에 저장
Context를 비동기 큐에 장기 보관
Context를 직렬화
Authorization 값을 userContext에 복사
```

특히 worker가 지연되면 요청 종료 후에도 Context와 헤더가 메모리에 남아 있을 수 있습니다.

## 14. userContext 현황

정의:

```java
private Map<String, Object> userContext =
        new HashMap<>();
```

현재 검색된 업무 소스에서는 실질적인 사용처가 거의 없습니다. 예약 확장영역에 가깝습니다.

사용한다면 키 문자열을 상수화하는 것이 좋습니다.

```java
public static final String USER_ID = "userId";
public static final String BRANCH_CODE = "branchCode";
```

하지만 사용자·브랜치·권한정보는 가능하면 명확한 타입을 사용하는 것이 낫습니다.

```java
public record AuthenticatedUserContext(
    String userId,
    String branchCode,
    Set<String> roles
) {
}
```

## 15. Service에서 사용하는 방법

필요하다면 다음과 같이 조회할 수 있습니다.

```java
ServiceContext context =
        ServiceContextHolder.getInstance();

if (context == null) {
    throw new IllegalStateException(
        "ServiceContext가 초기화되지 않았습니다."
    );
}

hdr_nhnis header = context.getHeader();
sys_comm sysComm = header.getSys_comm();

String guid = context.getGuid();
String serviceId = sysComm.getRms_svc_c();
String operatorId = sysComm.getOptr_eno();
String clientIp = sysComm.getTr_trm_ipadr();
```

다만 업무 Service가 Context에 직접 의존하면 단위 테스트가 어려워집니다.

권장 방식:

```java
public Output execute(
        Input input,
        OperatorContext operator
)
```

Controller/Handler/Facade에서 필요한 값만 꺼내 명시적으로 넘기는 것이 좋습니다.

## 16. 현재 구조의 주요 점검 결과

| 우선순위 | 항목                                            | 판단                           |
| -------- | ----------------------------------------------- | ------------------------------ |
| P0       | worker가 원본 mutable ServiceContext 공유       | 타임아웃 시 경합 가능          |
| P0       | worker에 Servlet request/response가 간접 전달됨 | 주석과 구현 불일치             |
| P1       | Authorization 포함 전체 요청 헤더 보관          | 로그·장기보관 금지             |
| P1       | Context와 header가 모두 mutable                 | 여러 계층에서 값 변경 가능     |
| P1       | Context 조회 결과가 nullable                    | 비HTTP·테스트에서 NPE 가능     |
| P1       | 사용자 인증정보가 명확한 타입으로 저장되지 않음 | 사용자 통제에 부적합           |
| P2       | `userContext`가 문자열/Object Map               | 타입 안정성 부족               |
| P2       | Holder 필드가 `static final`이 아님             | 재할당 방지 개선 가능          |
| P2       | Context 전용 테스트 검색되지 않음               | 생명주기·worker 전달 검증 필요 |

## 결론

현재 `ServiceContext`의 기본 개념과 Filter 정리 구조는 적절합니다.

```text
생성: DefaultFilter
사용: Interceptor → Controller → TCF → Aspect → Advice
정리: Filter finally
```

가장 큰 문제는 타임아웃 worker 전달 방식입니다.

```text
현재:
요청 스레드와 worker가 같은 ServiceContext 객체 공유

권장:
Servlet 객체가 없는 불변 스냅샷을 worker에 전달
```

운영 안정성을 위해 우선적으로 다음을 권장합니다.

1. worker용 불변 Context 스냅샷 도입
2. worker에서 Servlet request/response 제거
3. 헤더와 userContext 깊은 복사
4. 사용자·브랜치 정보를 명확한 인증 Context 타입으로 분리
5. 정상·예외·타임아웃 후 두 스레드의 Holder 정리 테스트 추가

이번 요청은 현행 분석만 수행했으며 소스와 문서는 변경하지 않았습니다.
