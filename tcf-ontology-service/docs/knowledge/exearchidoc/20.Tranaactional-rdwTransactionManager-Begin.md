# 20. `@Transactional` · `rdwTransactionManager` · BEGIN (PDMG)

기준일: 2026-08-09  
대상: Facade 진입 시 DB 트랜잭션 **시작(BEGIN)**  
관련: [19.Business-Facade.md](./19.Business-Facade.md) · [21.업무선처리-BizPrePostAspect.md](./21.업무선처리-BizPrePostAspect.md) · [트랜잭션처리.md](./트랜잭션처리.md) · [pdmg-service 트랜잭션흐름.md](./pdmg-service%20트랜잭션흐름.md)

> 파일명 `Tranaactional`은 오타이며, 애노테이션은 **`@Transactional`** 이다.

---

## 1. 한 줄 정의

업무 `*Facade` 메서드가 **스프링 TX 프록시**를 통해 호출될 때  
`rdwTransactionManager`가 커넥션에 트랜잭션을 연다(BEGIN) — **또는** 이미 열린 외부 TX에 `REQUIRED`로 참여한다.

```text
(TCF ON + timeout enabled)
TcfFacade → OnlineTimeoutExecutor(Worker)
  → TransactionTemplate BEGIN          ★ 외부 TX (1차)
  → Handler → (프록시) Facade.…
       └─ @Transactional REQUIRED      ★ 같은 TX 참여
            convert → Service → DAO
  → Deadline 재검사 → COMMIT / ROLLBACK

(timeout disabled / Sync)
Handler → (프록시) Facade.…
  └─ ★ BEGIN (Facade가 경계)
```

공통 타임아웃·외부 TX: [20.타임아웃.md](./20.타임아웃.md)  
시스템 선후·ImageLog·요청 Thread의 TcfFacade 대기는 업무 BEGIN **밖**이다.

---

## 2. TM 빈 정의

FQCN: `nhnis.mg.co.a.config.RdwDataSourceConfig`

```java
@Bean
@Primary
public PlatformTransactionManager rdwTransactionManager(DataSource rdwDataSource) {
    return new DataSourceTransactionManager(rdwDataSource);
}
```

| 항목 | 값 |
|------|-----|
| 빈 이름 | `rdwTransactionManager` |
| 구현 | `DataSourceTransactionManager` |
| 데이터소스 | `rdwDataSource` (`spring.datasource.rdw`, Hikari, `@Primary`) |
| MyBatis | 동일 DS의 `rdwSqlSessionFactory` / `rdwSqlSessionTemplate` |

Facade 선언은 **반드시** 이름을 명시한다.

```java
@Transactional(transactionManager = "rdwTransactionManager", …)
```

기본 TM이 Primary라서 생략해도 동작할 수 있으나, 다중 DS·가독성을 위해 **이름 지정**이 표준이다.

---

## 3. BEGIN이 일어나는 지점

| 시점 | TX |
|------|-----|
| Filter / Interceptor.preHandle / ImageLog INSERT | 업무 TX 아님 (별도 커넥션·정책) |
| OnlineController · TcfFacade(요청 Thread) | 없음 |
| **OnlineTimeoutExecutor Worker + TransactionTemplate** | **★ BEGIN (공통 timeout ON)** |
| **Facade 메서드 진입 (프록시)** | BEGIN **또는** REQUIRED 참여 |
| `convert(dtoBody → DTOin)` | TX 안 |
| Service · BizPrePost · DAO · SQL | TX 안 (같은 커넥션 참여) |
| Facade 정상 return → Executor 완료 | **COMMIT** (deadline OK) |
| 예외 / deadline 초과 | **ROLLBACK** |
| ResponseBodyAdvice · afterCompletion ImageLog | 업무 TX 이미 종료 |

Spring AOP: **자기 호출(self-invocation)** 으로 Facade 내부에서 다른 `@Transactional` 메서드를 `this.`로 부르면 프록시를 안 타 BEGIN이 안 열릴 수 있다.  
외부(Handler) → Facade 빈 호출만 전제한다.

---

## 4. 선언 옵션과 BEGIN 이후 의미

```java
// 조회
@Transactional(transactionManager = "rdwTransactionManager", readOnly = true)

// 쓰기
@Transactional(transactionManager = "rdwTransactionManager", rollbackFor = Exception.class)
```

| 옵션 | BEGIN 후 효과 |
|------|----------------|
| `readOnly = true` | 드라이버/DB에 읽기 전용 힌트. 조회 S 거래 관례 |
| `rollbackFor = Exception.class` | checked `Exception` 포함 롤백 (기본은 Runtime만) |
| (미지정 timeout) | Facade 단독으로는 “N초 자동 롤백” **미보장**. 공통 SLA는 `OnlineTimeoutExecutor` ([20.타임아웃](./20.타임아웃.md)) |
| `timeout = N` (초) | Facade **보조** Spring TX timeout. 공통 Executor와 병행 시 보통 불필요 |

중첩: Service에 `@Transactional`을 추가로 두지 않는 것이 기본.  
Facade 한 건 = 온라인 거래 DB TX 한 건.

## 5. 시퀀스 (Facade 구간만)

```text
1. Handler가 facade.mgcoa8888D0(dtoBody) 호출
2. TransactionInterceptor
     - rdwTransactionManager.getTransaction(…)
     - DataSource에서 Connection, setAutoCommit(false) 등 → BEGIN
3. Facade 본문
     - convert
     - service.… → Aspect → DAO → SQL (같은 TX)
4. 인터셉터 after
     - 성공 → commit
     - rollback 규칙에 맞는 예외 → rollback
5. Connection 반환(풀)
```

MyBatis `SqlSession`은 스프링이 연 TX에 **동기화**되어 참여한다.  
Facade 밖에서 DAO만 단독 호출하면 자동커밋/별도 세션 위험이 있다 → **반드시 Facade 경유**.

---

## 6. 요청(거래) 흐름 vs DB TX

| 층 | “트랜잭션” 말의 뜻 | BEGIN 주체 |
|----|-------------------|------------|
| 온라인 요청 흐름 | Filter~ImageLog 한 사이클 | (DB BEGIN 아님) |
| **DB 트랜잭션** | commit/rollback | **`rdwTransactionManager` @ Facade** |

과거 TCF `@TcfTransaction` 마커와 혼동하지 않는다. PDMG 온라인은 Facade `@Transactional`이 DB 경계다.

---

## 7. 실패·주의

| 현상 | 원인 후보 |
|------|-----------|
| SQL은 도는데 롤백 안 됨 | Facade `@Transactional` 누락 · 프록시 미적용(self-call) · TM 이름 오타 |
| 다른 DS로 붙음 | `transactionManager` 미지정 + 다른 Primary TM |
| 시스템/ImageLog 실패로 업무도 롤백되길 기대 | 설계상 **분리** — 업무 TX 밖 |
| Handler 예외인데 Facade 미진입 | BEGIN 자체 없음 |
| checked Exception만 던졌는데 커밋됨 | `rollbackFor = Exception.class` 빠짐 |

---

## 8. 하지 말 것

1. BEGIN을 Filter/Interceptor/TcfFacade에 옮기기  
2. Service·DAO에 기본 TX를 올려 Facade 경계를 흐리기  
3. `rdwDataSource`와 다른 DS의 TM으로 업무 SQL 묶기  
4. Facade 없이 Controller→DAO로 쓰기  
5. “요청이 길면 무조건 롤백”을 Facade BEGIN만으로 가정하기
