## 1. 정의

**전문**은 온라인 거래의 **요청·응답 JSON 봉투**다.  
HTTP Body 하나로 헤더(공통)와 업무 본문(dto)을 실어 나른다.

```text
요청/성공응답 봉투
{
  "hdr_nhnis": { "sys_comm": { … } },
  "dto":       { … 업무 필드 … }
}
```

| 쓰지 않음 (구 Pdmk) | PDMG |
|---------------------|------|
| `StandardRequestDto` / `StandardResponseDto` | `hdr_nhnis` + `dto` |
| `result.resultCode` (S0000/E0001) | 성공은 업무 `dto`, 실패는 `NH_NIS_ERR_DTO` |
| `@TcfTransaction` 메타 | path·`rms_svc_c` = 서비스 ID |

Content-Type: `application/json`  
HTTP 메서드: **POST** (`POST /{serviceId}`)

---

## 2. 요청 전문 구조

```text
{
  "hdr_nhnis": {          ← 시스템 공통 헤더 블록
    "sys_comm": { … }     ← NH 시스템 공통 (거래·단말·조작자)
  },
  "dto": { … }            ← 업무 입력 (= *DTOin 필드, camelCase)
}
```

| 키 | 타입(개념) | 역할 |
|----|------------|------|
| `hdr_nhnis` | `nhnis.fw.commons.dto.header.hdr_nhnis` | 헤더 루트 |
| `hdr_nhnis.sys_comm` | `…header.sys_comm` | 거래 식별·단말·조작자 등 |
| `dto` | 업무별 `*DTOin` | Handler/Facade에 전달되는 본문 |

### 2.1 `sys_comm` 주요 필드 (샘플 기준)

UI 샘플(`pdmg-ui/.../sample-requests/*.json`)에서 쓰는 핵심 필드:

| 필드 | 예 | 설명 |
|------|----|------|
| `rms_svc_c` | `mgcoa8888S0` | **서비스 ID**. path와 동일하게 맞춘다 |
| `sync_dsc` | `S` | 동기 구분 |
| `tr_sysid` | `PDMG` | 거래 시스템 ID |
| `ttl_ug_ync` | `0` | TTL 사용 여부 등 |
| `std_tgrm_rqr_rsp_dsc` | `Q` | 요청/응답 구분 |
| `std_tgrm_lclc` | `KO` | 로케일 |
| `tr_trm_ipadr` | `127.0.0.1` | 단말 IP |
| `tr_dtm` | `yyyyMMddHHmmss` | 거래 일시 |
| `tr_brc` | 점코드 | 취급점 |
| `trmno` / `trm_kdc` | 단말번호/종류 | |
| `scid` | `mgcoa8888` | 화면·프로그램 접두 |
| `optr_eno` / `tr_optrnm` | 조작자 사번/명 | ImageLog 등에 사용 |

그 외 `std_gbl_id`(GUID), `orgtr_gbl_id` 등은 FW·Filter가 채번·보강할 수 있다.  
전체 필드는 `pdmg-fw`의 `sys_comm.java`를 본다.

### 2.2 `dto` (업무 본문)

- JSON 키는 **camelCase**, DTO 필드와 1:1.
- 타입은 서비스 ID별 `nhnis.mg.co.a.dto.*DTOin`.
- 목록이면 `pageNo`/`pageSize` 등 → [08.대용량 페이징](./08.대용량%20페이징%20처리방식.md)

조회 예 (`mgcoa8888S0`):

```json
"dto": {
  "guid": null,
  "serviceId": null,
  "withinSeconds": 300,
  "pageNo": 1,
  "pageSize": 20
}
```

삭제 예 (`mgcoa8888D0`):

```json
"dto": {
  "guidList": ["…"]
}
```

## 3. 성공 응답 전문

정상 시에도 **같은 봉투 형태**를 유지하는 것이 원칙이다.

```text
{
  "hdr_nhnis": { "sys_comm": { … } },   ← 요청 echo·보강
  "dto": { … }                          ← *DTOout (목록·결과)
}
```

목록 `dto` 예:

```text
dto
├─ mgcoa8888S0DTOSub0[] (또는 size·목록 필드)
├─ pageNo, pageSize
├─ totalCount, totalPages
└─ size
```

업무 Facade/Service는 **`dto`에 넣을 객체(`*DTOout`)** 만 반환한다.  
헤더 조립·봉투 씌우기는 **pdmg-fw** (ResponseBodyAdvice 등)가 담당한다.

---

## 4. 실패 응답 전문

업무·Handler 경로 실패는 **`NH_NIS_ERR_DTO`** 다.  
성공 봉투(`hdr_nhnis`+`dto`)와 **스키마가 다르다**.

```text
NH_NIS_ERR_DTO (요지)
├─ stdErrCode      오류 코드 (예 FW0001, E9999)
├─ stdErrMsgCntn   메시지
├─ addMsgContents  부가 메시지
├─ errType         BIZ / SERVICE / …
├─ errClassName, errFileName, … (발생 위치 메타)
└─ …
```

| 발생 | 처리 |
|------|------|
| `BizException` | `GlobalExceptionHandler` → `NH_NIS_ERR_DTO` |
| Handler 없음 | `ServiceHandlerNotFound` → 동상 |
| 쓰기 중 예외 | Facade TX **rollback** 후 실패 전문 |

구 `result: { resultCode: E0001, errorCode, … }` / ETF 조립은 **사용하지 않는다**.  
상세: [에러처리.md](./에러처리.md)

## 5. 처리 흐름에서의 전문

```text
① Client/UI
     Body = { hdr_nhnis, dto }

② DefaultFilter (pdmg-fw)
     Body 캐시
     hdr_nhnis → ServiceContext
     (local: hdr 없으면 합성 가능 — §6)

③ ServicePreventionInterceptor
     요청 전문 로그 · ImageLog INSERT (헤더+본문)

④ OnlineController → Handler
     dto 부분(Object) → Facade

⑤ Facade
     Object → *DTOin 변환 → Service → *DTOout

⑥ 시스템 후처리
     성공: { hdr_nhnis, dto: DTOout }
     실패: NH_NIS_ERR_DTO
     ImageLog UPDATE
```

Facade/Service는 JSON 전체를 파싱하지 않고, **이미 분리된 `dto` 객체**만 다룬다.

## 6. 로컬·중계 편의

### 6.1 local 프로파일

`DefaultFilter`는 local에서 `hdr_nhnis` 없이 `{"dto":…}` 만 와도 **합성 헤더**로 통과시킬 수 있다.  
운영·통합 테스트에서는 **완전한 `hdr_nhnis.sys_comm`** 을 보내는 것을 표준으로 한다.

### 6.2 UI Relay

`pdmg-ui`는 Body를 **수정하지 않고** `pdmg-service`로 전달한다.

```text
POST /api/relay/{serviceId}   Body = 요청 전문 전체
  → POST http://service/{serviceId}  동일 Body
```

샘플: `pdmg-ui/src/main/resources/sample-requests/mgcoa*.json`

### 6.3 `rms_svc_c` ↔ path

표준: **`sys_comm.rms_svc_c` = URL path 서비스 ID**.  
예: path `/mgcoa8888S0` ↔ `"rms_svc_c": "mgcoa8888S0"`.

## 7. 계층별 전문 책임

| 계층 | 전문 관련 책임 |
|------|----------------|
| UI | 샘플·화면에서 봉투 구성, relay |
| Filter | hdr 파싱·GUID·Context, Body 캐시 |
| Interceptor / ImageLog | 요청·응답 전문 감사 |
| Handler | `dto` Object만 Facade에 전달 |
| Facade | `dto` → DTOin, DTOout 반환 |
| Service | DTOin/out 업무 처리 (JSON 봉투 모름) |
| GlobalExceptionHandler | 실패 시 `NH_NIS_ERR_DTO` |

---

## 8. 필드·명명 규칙

| 구분 | 규칙 |
|------|------|
| 봉투 키 | `hdr_nhnis`, `sys_comm`, `dto` (고정 snake/약어 — FW 계약) |
| `sys_comm` 내부 | 기존 NH 헤더 스키마 (snake_case 필드명) |
| `dto` 내부 | **camelCase** ↔ Java DTO |
| DB 컬럼 | UPPER_SNAKE (SQL alias → DTO 매핑) |

```text
좋음:  "dto": { "pageNo": 1, "guidList": ["…"] }
나쁨:  "body": { … } / "request": { … }
나쁨:  StandardRequestDto 래핑
나쁨:  dto에 hdr 필드 혼입
```
