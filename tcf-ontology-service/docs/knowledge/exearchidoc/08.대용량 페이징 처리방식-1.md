## 분석 결론

[08.대용량 페이징 처리방식.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/docs/08.대용량 페이징 처리방식.md>)는 현재 PDMG 목록 조회가 사용하는 Offset 기반 DB 페이징을 전반적으로 정확하게 설명합니다.

현재 구현의 기본 구조는 다음과 같습니다.

```text
pageNo/pageSize 수신
  → Service에서 보정
  → offset 계산
  → COUNT SQL
  → 페이지 목록 SQL
  → DTO 목록 조립
  → totalPages 계산
```

전체 데이터를 조회한 뒤 Java에서 `subList()`하는 방식이 아니라 DB의 `ROWNUM`으로 행 수를 제한하므로 기본적인 서버 페이징은 정상적으로 적용되어 있습니다.

하지만 “대용량 처리”라는 제목에 비해 현재 구현에는 다음 한계가 있습니다.

1. `mgcoa9000`의 기본 pageSize가 문서와 다름
2. `offset` 계산이 `int`라서 큰 페이지 번호에서 오버플로 가능
3. DAO의 `COUNT(*)` 결과가 `int`라서 초대용량 건수 표현에 한계
4. 같은 트랜잭션에서 COUNT와 목록을 조회해도 결과 일관성이 완전히 보장되지 않음
5. Offset 페이징은 깊은 페이지에서 비용 증가
6. 동시 INSERT/DELETE 시 중복·누락 페이지가 생길 수 있음
7. 이미지로그는 한 행의 전문 데이터가 커서 100건 제한만으로 응답 크기를 통제하기 어려움
8. 일부 검색조건은 인덱스를 효율적으로 사용하기 어려움
9. 문서의 Oracle 키셋 SQL 예시는 수정이 필요

## 1. 현재 페이징 적용 프로그램

현재 신규 `co.a` 패키지에서 페이징이 구현된 거래는 다음 세 개입니다.

| 거래          | 대상           | 기본 pageSize | 최대 |
| ------------- | -------------- | ------------: | ---: |
| `mgcoa5530S0` | 마케팅희망고객 |            20 |  100 |
| `mgcoa8888S0` | 이미지로그     |            20 |  100 |
| `mgcoa9000S0` | 거래 파라미터  |        **10** |  100 |

문서에서는 모든 목록 거래의 기본값을 다음처럼 정의합니다.

```text
pageNo  = 1
pageSize = 20
```

그러나 `mgcoa9000Service`는 다음 기본값을 사용합니다.

```java
int pageSize =
    input == null
    || input.getPageSize() == null
    || input.getPageSize() <= 0
        ? 10
        : input.getPageSize();
```

따라서 문서의 “PDMG 표준 기본값 20”과 실제 `mgcoa9000`이 다릅니다.

다음 중 하나로 정리해야 합니다.

```text
표준을 20으로 확정:
  mgcoa9000도 20으로 변경

거래별 기본값 허용:
  공통 기본은 20
  mgcoa9000은 업무별 예외로 10
```

현재 상태를 설명한다면 예외를 명시해야 합니다.

## 2. 입력값 보정

현재 Service는 다음 규칙을 적용합니다.

```text
pageNo가 null 또는 0 이하
  → 1

pageSize가 null 또는 0 이하
  → 기본값

pageSize가 100 초과
  → 100
```

이 부분은 문서와 실제 구현이 일치합니다.

```java
if (pageSize > 100) {
    pageSize = 100;
}
```

클라이언트가 `offset`을 직접 전달하지 못하고 Service가 계산하는 것도 적절합니다.

```java
int offset = (pageNo - 1) * pageSize;
```

이를 통해 다음과 같은 비정상 입력을 어느 정도 방지합니다.

```text
pageNo = 0
pageNo = -1
pageSize = 0
pageSize = -100
pageSize = 100000
```

## 3. `int offset` 오버플로 위험

현재 계산은 `int`입니다.

```java
int offset = (pageNo - 1) * pageSize;
```

`pageNo`에는 최대값이 없습니다.

따라서 매우 큰 페이지 번호를 보내면 정수 오버플로가 발생할 수 있습니다.

예:

```text
pageNo   = 30,000,000
pageSize = 100

offset = 2,999,999,900
```

이는 Java `int` 최대값을 넘습니다.

```text
Integer.MAX_VALUE = 2,147,483,647
```

오버플로되면 offset이 음수 또는 예상과 다른 값이 될 수 있습니다.

대용량 안전성을 확보하려면 다음이 필요합니다.

```java
long offset =
    Math.multiplyExact(
        (long) pageNo - 1L,
        (long) pageSize
    );
```

그리고 업무적으로 허용할 최대 페이지 번호도 제한하는 것이 좋습니다.

```text
pageNo 최대값
또는 offset 최대값
또는 일정 깊이 이후 keyset 방식 강제
```

## 4. COUNT 결과 타입 문제

Service의 `totalCount`는 현재 `int`입니다.

```java
int totalCount = dao.mgcoaXXXXS0_S0_count(param);
```

DAO 메서드도 `int`를 반환합니다.

```java
int mgcoa8888S0_S0_count(...);
```

그런데 출력 DTO는 `long totalCount`를 사용합니다.

```java
private long totalCount;
```

즉, DB COUNT 결과가 먼저 `int`로 축소된 뒤 `long`으로 저장됩니다.

```text
DB COUNT(*)
  → int
  → long DTO
```

약 21억 건을 넘으면 `int`로 표현할 수 없습니다.

진정한 대용량 기준이라면 다음처럼 통일해야 합니다.

```text
DAO COUNT 반환: long 또는 Long
Service totalCount: long
DTO totalCount: long
```

현재 출력 DTO가 `long`이어도 DAO가 `int`이므로 대용량 건수를 완전히 지원하는 것은 아닙니다.

## 5. totalPages 계산

현재 계산식은 다음과 같습니다.

```java
(int) ((totalCount + pageSize - 1L) / pageSize)
```

일반적인 올림 나눗셈이며 계산 방식은 맞습니다.

예:

```text
totalCount = 101
pageSize   = 20

totalPages = (101 + 19) / 20
           = 6
```

다만 반환 타입이 `int`입니다.

```java
private int totalPages;
```

pageSize가 최소 1이고 전체 건수가 `long` 범위라면 페이지 수도 `int` 범위를 넘을 수 있습니다. 현재 DAO count가 `int`이므로 당장 더 큰 값이 들어오지 않지만, count를 `long`으로 변경한다면 `totalPages`도 `long`을 검토해야 합니다.

## 6. SQL 페이징 구조

현재 세 Mapper 모두 Oracle `ROWNUM` 이중 래핑 방식을 사용합니다.

```sql
SELECT *
  FROM (
        SELECT a.*, ROWNUM rnum
          FROM (
                SELECT ...
                  FROM ...
                 WHERE ...
                 ORDER BY ...
               ) a
         WHERE ROWNUM <= #{offset} + #{pageSize}
       )
 WHERE rnum > #{offset}
```

이 구조는 Oracle의 전통적인 Offset 페이징 방식입니다.

처리 순서는 다음과 같습니다.

```text
1. WHERE로 후보 집합 결정
2. ORDER BY로 정렬
3. offset + pageSize까지만 ROWNUM 부여
4. offset 이하는 외부 쿼리에서 제거
```

문서의 설명과 실제 SQL이 일치합니다.

## 7. 정렬 안정성

페이징에서 정렬은 반드시 결정적이어야 합니다.

### `mgcoa8888`

```sql
ORDER BY
    T1.REQUEST_TIME DESC,
    T1.GUID DESC
```

GUID가 고유하다면 안정적인 정렬입니다.

### `mgcoa9000`

```sql
ORDER BY
    T1.REG_DTM DESC,
    T1.TX_ID ASC
```

`TX_ID`가 고유키라면 안정적입니다.

### `mgcoa5530`

```sql
ORDER BY T1.L5101
```

`L5101`이 유일한 값이라면 문제가 없습니다. 하지만 중복 가능한 컬럼이면 같은 값 안에서 행 순서가 보장되지 않습니다.

문서에는 단순히 “ORDER BY 필수”뿐 아니라 다음 조건이 필요합니다.

> ORDER BY의 마지막 항목에는 PK 또는 유일값을 포함하여 모든 행의 순서가 완전히 결정되어야 한다.

예:

```sql
ORDER BY
    T1.L5101,
    T1.추가_PK_컬럼
```

## 8. 동시 변경 시 Offset 페이징 문제

정렬이 안정적이어도 페이지를 이동하는 사이 데이터가 추가되거나 삭제되면 Offset 방식은 중복이나 누락이 발생할 수 있습니다.

예를 들어 최신순 정렬에서 1페이지를 본 뒤 새 행이 추가되면:

```text
1페이지 조회 시:
  A B C D E

새로운 X가 맨 앞에 INSERT

2페이지 조회 시 offset=5:
  E F G H I
```

`E`가 중복될 수 있습니다.

삭제가 발생하면 특정 행을 건너뛸 수도 있습니다.

따라서 문서에는 Offset 방식의 한계를 다음처럼 추가해야 합니다.

```text
Offset 페이징:
  임의 페이지 이동 가능
  totalPages 표시 가능
  동시 변경 시 중복/누락 가능

Keyset 페이징:
  연속 탐색에 적합
  동시 변경에 상대적으로 안정적
  임의 N페이지 이동이 어려움
```

## 9. COUNT와 목록의 WHERE 공유

현재 Mapper는 `<sql>` 조각으로 WHERE를 공유합니다.

예:

```xml
<sql id="mgcoa8888Where">
    ...
</sql>
```

목록과 COUNT 모두 다음을 사용합니다.

```xml
<include refid="mgcoa8888Where"/>
```

이 부분은 매우 적절합니다.

검색조건을 별도로 복사하면 다음 문제가 생길 수 있습니다.

```text
COUNT 결과: 100건
목록 SQL 조건: 90건
화면 totalPages 불일치
```

현재는 공통 SQL 조각으로 이 위험을 줄이고 있습니다.

## 10. 같은 트랜잭션이어도 COUNT와 목록이 다를 수 있음

문서는 다음처럼 설명합니다.

> count와 list는 같은 요청·같은 TX에서 연속 호출한다.

호출 구조상으로는 맞습니다.

```text
TX
  → COUNT
  → LIST
```

하지만 같은 트랜잭션이라는 사실만으로 두 SQL이 완전히 같은 데이터 스냅샷을 본다고 단정할 수 없습니다.

Oracle의 기본 격리 수준인 `READ COMMITTED`에서는 일반적으로 각 SQL 문 시작 시점의 일관된 읽기를 제공합니다.

따라서 다음 사이에 다른 트랜잭션이 Commit하면:

```text
COUNT 실행
  → 다른 세션 INSERT/DELETE COMMIT
  → LIST 실행
```

COUNT와 목록 결과가 달라질 수 있습니다.

완전히 같은 스냅샷이 필요하다면 다음 중 하나를 검토해야 합니다.

```text
더 강한 격리 수준
Flashback Query의 동일 SCN
한 SQL에서 COUNT와 페이지 목록을 함께 계산
업무적으로 약간의 오차 허용
```

일반 관리 화면에서는 약간의 차이를 허용하는 경우가 많으므로 정책 결정이 필요합니다.

## 11. 조회 `readOnly=true`의 실제 효과

문서는 다음과 같이 설명합니다.

```text
목록 Facade
  → @Transactional(readOnly = true)
```

Facade 선언 자체는 맞습니다.

하지만 TCF ON + Timeout ON에서는 외부 `DefaultOnlineTimeoutExecutor`가 먼저 일반 트랜잭션을 시작합니다.

```text
TransactionTemplate BEGIN
  → Handler
  → Facade(readOnly=true, REQUIRED)
```

Facade는 이미 시작된 트랜잭션에 참여하므로 `readOnly=true`가 외부 물리 트랜잭션을 조회 전용으로 바꾸지는 못합니다.

따라서 문서에는 다음 조건을 추가해야 합니다.

```text
Timeout OFF:
  Facade readOnly=true가 트랜잭션 생성 속성에 반영

Timeout ON:
  외부 일반 TX에 참여하므로 Facade readOnly 속성은 제한적
```

## 12. 깊은 페이지 성능

문서가 설명한 대로 Offset 방식은 깊은 페이지에서 느려집니다.

```text
pageNo = 10,000
pageSize = 100
offset = 999,900
```

DB는 결과 100건만 반환하더라도 정렬 후 앞쪽 약 100만 건을 처리해야 할 수 있습니다.

```text
정렬/검색:
  offset + pageSize까지 처리

최종 반환:
  pageSize만 반환
```

따라서 네트워크 응답은 작지만 DB 비용까지 작은 것은 아닙니다.

문서의 Keyset 전환 권고는 방향이 맞습니다.

## 13. Keyset SQL 예시 문제

문서 예시는 다음과 같습니다.

```sql
WHERE (REQUEST_TIME, GUID)
    < (#{lastRequestTime}, #{lastGuid})
ORDER BY REQUEST_TIME DESC, GUID DESC
```

Oracle 버전과 SQL 문맥에 따라 행 값 비교 연산 지원이 제한될 수 있으므로 안전한 Oracle 조건으로 다음처럼 풀어 쓰는 것이 좋습니다.

```sql
WHERE (
       REQUEST_TIME < #{lastRequestTime}
    OR (
           REQUEST_TIME = #{lastRequestTime}
       AND GUID < #{lastGuid}
    )
)
ORDER BY
    REQUEST_TIME DESC,
    GUID DESC
```

또한 다음 구문도 Oracle 버전과 드라이버의 bind 처리 여부를 확인해야 합니다.

```sql
FETCH FIRST #{pageSize} ROWS ONLY
```

PDMG가 구버전 Oracle까지 고려한다면 다음처럼 ROWNUM 상한을 유지하는 편이 호환성이 좋습니다.

```sql
SELECT *
FROM (
    SELECT ...
    FROM ...
    WHERE keyset_condition
    ORDER BY REQUEST_TIME DESC, GUID DESC
)
WHERE ROWNUM <= #{pageSize}
```

## 14. COUNT 비용

현재 페이지 요청마다 다음 두 SQL이 실행됩니다.

```text
COUNT(*)
페이지 목록
```

따라서 DB 입장에서는 조건 검색 비용을 두 번 부담합니다.

특히 다음 조건은 비용이 커질 수 있습니다.

### 선행 와일드카드

```sql
LIKE '%' || #{serviceId} || '%'
```

일반 B-Tree 인덱스를 효율적으로 사용하기 어렵습니다.

### 컬럼 함수 적용

```sql
UPPER(T1.TX_ID)
UPPER(NVL(T1.APP_ID, ''))
```

일반 인덱스가 그대로 사용되지 않을 수 있습니다.

### 날짜 문자열 변환과 계산

```sql
TO_DATE(SUBSTR(RESPONSE_TIME, 1, 14), ...)
- TO_DATE(SUBSTR(REQUEST_TIME, 1, 14), ...)
```

행마다 함수를 계산해야 하므로 이미지로그가 많으면 COUNT와 목록 모두 느려질 수 있습니다.

문서의 “WHERE와 인덱스 검토”보다 다음처럼 구체적으로 정의할 필요가 있습니다.

```text
정확 검색은 = 우선
선행 % LIKE 최소화
UPPER 검색이면 함수 기반 인덱스 검토
시간은 문자열보다 DATE/TIMESTAMP 컬럼 검토
경과시간 검색이 많으면 계산 컬럼/별도 컬럼 검토
```

## 15. 이미지로그 행 크기 문제

`mgcoa8888S0`은 목록 조회에서 다음 컬럼까지 모두 가져옵니다.

```text
REQUEST_MSG
RESPONSE_MSG
EXCEPTION_MSG
```

요청·응답 전문이 크면 100건만 조회해도 응답 데이터가 매우 커질 수 있습니다.

```text
행당 전문 100KB
× 100건
= 약 10MB 이상
```

따라서 `pageSize <= 100`은 행 수만 제한할 뿐 메모리와 네트워크 바이트를 완전히 보호하지 못합니다.

대용량 이미지로그 목록은 다음 구조가 더 적절합니다.

### 목록 거래

```text
GUID
SERVICE_ID
REQUEST_TIME
RESPONSE_TIME
EXCEPTION_CODE
전문 길이 또는 요약
```

### 상세 거래

```text
GUID로 단건 조회
REQUEST_MSG
RESPONSE_MSG
전체 EXCEPTION_MSG
```

즉, 큰 CLOB 또는 전문 본문은 목록에서 제외하고 상세 거래로 분리하는 것이 좋습니다.

이 부분은 현재 문서에서 가장 중요한 누락입니다.

## 16. 목록 조립 메모리

DB가 최대 100행만 반환하므로 행 개수 기준 메모리 사용은 제한됩니다.

하지만 현재 흐름에는 중간 객체가 여러 번 만들어집니다.

```text
MyBatis List<Map<String,Object>>
  → Map별 조회
  → DTOSub0 생성
  → DTO 목록
  → ResponseBodyAdvice JsonNode
  → JSON 문자열
```

이미지로그처럼 각 행의 전문이 크면 같은 데이터가 다음 형태로 메모리에 중복될 수 있습니다.

```text
JDBC/Clob
Map
String
DTO
JsonNode
응답 JSON
ServiceContext.responseBody
ImageLog 응답 전문
```

따라서 대용량 행에서는 pageSize뿐 아니라 컬럼 크기와 응답 전문 로깅 정책도 함께 통제해야 합니다.

---

## 17. `totalCount == 0`일 때 목록 SQL

현재 Service는 COUNT 결과가 0이어도 목록 SQL을 실행합니다.

```java
int totalCount = dao.count(param);
List<Map<String, Object>> rows = dao.list(param);
```

다음과 같이 최적화할 수 있습니다.

```text
totalCount == 0
  → 빈 목록 반환
  → 목록 SQL 생략
```

다만 일반적으로 이 최적화 효과는 작고, COUNT와 LIST 사이의 동시 변경을 고려하면 정책적으로 판단해야 합니다.

COUNT 직후 데이터가 추가될 가능성을 허용한다면 목록을 실행하는 현재 방식이 더 자연스러울 수도 있습니다.

## 18. 인덱스 검토

문서에서 제시한 인덱스 방향은 대체로 맞지만 “WHERE 선두 컬럼”만으로는 부족합니다.

인덱스는 다음을 함께 고려해야 합니다.

```text
동등 조건
범위 조건
정렬 컬럼
선택도
복합 인덱스 컬럼 순서
조회 빈도
INSERT/UPDATE 비용
```

예를 들어 이미지로그의 기본 최신순 목록이 중요하다면 다음과 같은 인덱스 후보가 있습니다.

```text
REQUEST_TIME DESC, GUID DESC
```

사용자별 최신 목록이 중요하다면:

```text
OPTR_ENO, REQUEST_TIME DESC, GUID DESC
```

하지만 실제 데이터 분포와 실행 계획 없이 특정 인덱스를 확정하면 안 됩니다.

문서에는 `EXPLAIN PLAN` 또는 실제 실행 계획 검증이 필요하다는 항목을 추가해야 합니다.

## 19. Timeout과 대용량 조회

현재 TCF ON + Timeout ON에서는 전체 거래 제한 시간이 기본 5초입니다.

해당 시간에는 다음이 모두 포함됩니다.

```text
Worker Queue 대기
COUNT SQL
목록 SQL
DTO 조립
업무 후처리
```

따라서 COUNT가 4초, 목록이 2초라면 거래는 Timeout될 수 있습니다.

또한 Future 취소가 JDBC SQL을 즉시 중단한다는 보장은 없습니다.

대용량 페이징에서는 다음을 함께 관리해야 합니다.

```text
온라인 전체 Timeout
JDBC/MyBatis Query Timeout
DB 실행 계획
COUNT 정책
페이지 크기
검색조건 강제 여부
```

현재 `MybatisLogInterceptor`는 SQL ID와 실행시간 로깅이 주 역할이며, 그 자체가 DB Query Timeout을 설정하는 구현은 아닙니다.

문서가 타임아웃으로 DB 비용까지 자동 통제된다고 오해하게 해서는 안 됩니다.

## 20. 구현별 평가

### `mgcoa5530S0`

장점:

```text
pageSize 최대 100
DB ROWNUM 페이징
공통 WHERE
COUNT 분리
ORDER BY 존재
```

확인 필요:

```text
L5101이 유일한 정렬키인지
PK 힌트가 실제 Oracle 인덱스명과 일치하는지
trtBrc/basDt 조건과 인덱스 구성
```

### `mgcoa8888S0`

장점:

```text
기간 범위 지원
GUID 보조 정렬
예외 필터
최대 100건
```

위험:

```text
요청/응답 전문까지 목록에서 조회
선행 와일드카드 LIKE
시간 문자열 변환
경과시간 행별 계산
COUNT 비용
```

### `mgcoa9000S0`

장점:

```text
TX_ID 보조 정렬
CRUD와 목록 구조 분리
COUNT/WHERE 공유
```

불일치 및 위험:

```text
기본 pageSize가 문서 20과 달리 10
keyword 검색이 다중 UPPER + %LIKE%
함수 기반 조건으로 인덱스 사용 제한 가능
```

## 우선 수정해야 할 사항

1. `mgcoa9000` 기본 pageSize 10을 예외로 명시하거나 20으로 통일
2. `offset`을 `long`으로 계산하고 최대 pageNo/offset 정책 추가
3. DAO COUNT 반환 타입을 `long`으로 변경하는 대용량 기준 추가
4. 정렬 마지막에 유일키가 필요하다는 규칙 추가
5. 동시 데이터 변경 시 Offset 중복·누락 가능성 명시
6. 같은 TX라도 COUNT와 LIST 스냅샷이 다를 수 있음을 명시
7. 이미지로그 목록에서 대형 요청·응답 전문 분리 권고
8. 선행 `%LIKE%`, `UPPER`, `TO_DATE`의 인덱스 제약 명시
9. Oracle 키셋 조건을 명시적 OR 비교로 수정
10. Timeout과 JDBC Query Timeout을 분리해 설명
11. 실행 계획과 실제 데이터 분포 검증 항목 추가

이번 분석에서는 문서나 소스를 수정하지 않았고 테스트도 실행하지 않았습니다.
