# NSIGHT TCF 전문 구성

## 1. 목적과 범위

이 문서는 NSIGHT TCF 표준 온라인 거래가 사용하는 요청·응답 전문의 공통 계약을 정의한다. 구현 기준은 `tcf-core`의 `StandardRequest<T>`, `StandardHeader`, `StandardResponse<T>`, `Result` 및 `TcfStandardMessageCatalog`이다. 업무별 `body`의 필드와 의미는 각 `serviceId`의 업무 계약에서 별도로 정의한다.

## 2. 핵심 용어

| 용어 | 의미 |
| --- | --- |
| 전문 | HTTP로 주고받는 표준 요청 또는 응답 JSON 전체 |
| Header | 라우팅, 추적, 채널, 사용자 등 공통 거래 메타데이터 |
| Body | 업무·`serviceId`별로 달라지는 입력 또는 출력 데이터 |
| Result | 처리 성공·실패와 오류 정보를 담는 응답 공통 영역 |
| serviceId | Dispatcher가 `TransactionHandler`를 찾는 거래 식별자 |
| guid / traceId | 거래 단위 및 연계 추적을 위한 상관관계 식별자 |

## 3. 전문 전체 구조

```text
StandardRequest<T> = header + body
StandardResponse<T> = header + result + body
```

```text
요청:  { "header": { ... }, "body": { ... } }
응답:  { "header": { ... }, "result": { ... }, "body": { ... } }
```

`header`와 `result`는 표준 계약이며, `body`는 업무 DTO 또는 Map으로 직렬화된다. 실패 응답은 `StandardResponse.fail(...)`가 생성하며 body를 설정하지 않는다.

## 4. 전송 계약

- 표준 온라인 거래 URL은 `POST /online` 또는 `POST /{businessCode}/online`이다.
- Content-Type은 `application/json; charset=UTF-8`이다.
- 표준 거래의 성공·실패는 HTTP 200과 `result.resultCode` 조합으로 판정한다.
- `result.resultCode`가 `S0000`이면 업무 성공이며, 그 밖의 값은 실패로 처리한다.
- multipart, 브라우저 Relay, 관리용 REST 등 비표준 엔드포인트는 이 계약과 다른 HTTP 상태 코드 동작을 사용할 수 있다.

## 5. 요청 전문

### 5.1 요청 JSON

```json
{
  "header": {
    "businessCode": "SV",
    "serviceId": "SV.Sample.inquiry",
    "transactionCode": "SV-INQ-0001",
    "processingType": "INQUIRY",
    "channelId": "WEBTOP"
  },
  "body": {}
}
```

### 5.2 Header 필드 사전

| 필드 | Java 타입 | 요청 필수 | 생성·보완 주체 | 검증·정규화 | 주요 사용처 | 예시 | 보안 주의 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `systemId` | `String` | 아니오 | `StandardHeader.normalize()` | 미입력 시 `NSIGHT-MP` | 연계 시스템 식별 | `NSIGHT-MP` | 외부 시스템 식별값은 승인된 값만 사용 |
| `businessCode` | `String` | 예 | 클라이언트 | trim 후 대문자, 최대 10자 | WAR/context 식별·라우팅 | `SV` | 임의 업무코드로 권한을 우회하지 않음 |
| `serviceId` | `String` | 예 | 클라이언트 | 최대 100자 | Dispatcher 라우팅 키 | `SV.Sample.inquiry` | 허가된 거래만 호출 |
| `serviceName` | `String` | 아니오 | 클라이언트 또는 서비스 카탈로그 | 최대 200자 | 표시·감사 | `SV 샘플 조회` | 비밀·개인정보를 이름에 넣지 않음 |
| `transactionCode` | `String` | 예 | 클라이언트 | 최대 50자 | 화면·거래 설계 식별 | `SV-INQ-0001` | 업무 식별자만 사용 |
| `processingType` | `String` | 예 | 클라이언트 | trim 후 대문자; 카탈로그 계약은 `ProcessingType` enum 값 | 처리 유형·정책 | `INQUIRY` | 현재 구현은 enum 소속을 검사하지 않으므로, 허용값 검증을 추가하기 전에는 임의 문자열을 신뢰하지 않음 |
| `guid` | `String` | 아니오 | STF | 빈 값이면 STF가 UUID 생성 | 거래 로그·상관관계 | `1f5d9b4a-7f62-4e6e-8a2e-4b0de3c0a001` | 세션·토큰으로 사용하지 않음 |
| `traceId` | `String` | 아니오 | STF | 빈 값이면 STF가 생성 | 연계 추적 | `trace-demo-20260726-0001` | 로그 상관관계 용도에 한정 |
| `channelId` | `String` | 예 | 클라이언트 | 최대 30자 | 채널·포털 식별 | `WEBTOP` | 신뢰 경계에서 채널값을 검증 |
| `userId` | `String` | 아니오 | 클라이언트·세션/권한 처리 | 최대 50자; JSON `user` 별칭 허용 | 세션·권한·감사 | `U-DEMO-001` | 개인정보·권한값을 로그에 과다 노출하지 않음 |
| `branchId` | `String` | 아니오 | 클라이언트 | 최대 20자; JSON `branch` 별칭 허용 | 거래통제·감사 | `001234` | 권한 검증 없이 부점 범위를 신뢰하지 않음 |
| `centerId` | `String` | 아니오 | 클라이언트 | 최대 20자 | 센터 식별 | `DC1` | 운영 조직 정보 최소화 |
| `requestTime` | `String` | 아니오 | `StandardHeader.normalize()` | 미입력 시 서버 ISO-8601 현재 시각 | 감사·추적 | `2026-07-26T10:00:00+09:00` | 시간값을 인증 근거로 단독 사용하지 않음 |
| `clientIp` | `String` | 아니오 | Controller | 최대 50자 | 거래통제·감사 | `127.0.0.1` | 현재는 신뢰 프록시 판별 없이 `X-Forwarded-For` 첫 값을 반영하므로 외부 입력으로 신뢰하지 않음; 신뢰 프록시 검증을 추가해야 함 |
| `idempotencyKey` | `String` | 아니오 | 클라이언트 | 최대 100자 | 중복 요청 방지 | `idem-demo-20260726-0001` | 예측 가능한 민감값 사용 금지 |

요청 카탈로그상 필수 필드는 `businessCode`, `serviceId`, `transactionCode`, `processingType`, `channelId`이다. `user`는 `userId`로, `branch`는 `branchId`로 JSON 역직렬화할 수 있다.

#### `clientIp` 현재 구현과 신뢰 프록시 검증 권고

현재 `OnlineTransactionController`는 Header의 `clientIp`이 비어 있으면 신뢰 프록시 판별 없이 `X-Forwarded-For`의 첫 값을 사용하고, 없으면 `request.getRemoteAddr()`를 사용한다. 따라서 직접 연결한 클라이언트도 `X-Forwarded-For` 값에 영향을 줄 수 있으므로, 현재 구현을 신뢰 경계 검증으로 해석해서는 안 된다.

권고 구현에서는 요청의 직접 피어(`remoteAddr`)가 설정된 신뢰 프록시 IP/서브넷 허용목록에 속하는 경우에만 `X-Forwarded-For`를 해석한다. 그 밖의 경우에는 `remoteAddr`만 사용하며, 전달 헤더에서 채택한 값도 IP 형식을 검증한다. 이 신뢰 프록시 검증은 후속 보안 변경 사항이며 현재 Controller가 강제하는 동작이 아니다.

### 5.3 processingType

카탈로그 계약과 개선 권고에서 `processingType`은 다음 `ProcessingType` enum 중 하나여야 한다. 그러나 현재 `StandardHeaderValidator`는 `normalize()` 뒤 카탈로그의 `requiredYn=Y` 필드가 비어 있는지만 검사하며, `ProcessingType` enum 소속 여부는 검사하지 않는다. 따라서 현재 구현에서는 공백이 아닌 임의 문자열도 Header 필수값 검증을 통과할 수 있다.

후속 구현에서는 아래 값 목록을 허용목록으로 사용해 enum 소속 여부를 검증하고, 비허용 값은 `INVALID_HEADER`로 거절해야 한다. 이 표는 현재 강제되는 런타임 검증이 아니라 카탈로그 계약과 목표 검증 규칙이다.

| 값 | 의미 |
| --- | --- |
| `INQUIRY` | 조회 |
| `CREATE` | 등록 |
| `UPDATE` | 변경 |
| `DELETE` | 삭제 |
| `EXECUTE` | 실행 |
| `DOWNLOAD` | 다운로드 |
| `UPLOAD` | 업로드 |

### 5.4 Body 계약

`body`는 표준 공통 필드가 아니라 업무 가변 영역이다. 요청 DTO의 필수값, 형식, 허용 범위는 해당 `serviceId`의 Handler·Facade 계약으로 검증한다. 새 CRUD 예시의 명명은 `SV.Customer.selectList`를 사용한다. `SV.Sample.inquiry`는 현재 제공되는 기존 샘플 거래 식별자다.

## 6. 응답 전문

### 6.1 응답 JSON

```json
{
  "header": { "businessCode": "SV", "serviceId": "SV.Sample.inquiry", "guid": "1f5d9b4a-7f62-4e6e-8a2e-4b0de3c0a001" },
  "result": { "resultCode": "S0000", "resultMessage": "정상 처리되었습니다." },
  "body": {}
}
```

### 6.2 응답 Header

응답은 요청의 `StandardHeader`를 전달하며, 요청에서 비어 있던 `guid`와 `traceId`는 서버 처리 중 생성된 값으로 보완될 수 있다. 응답 카탈로그의 공통 반환 필드는 `systemId`, `businessCode`, `serviceId`, `serviceName`, `transactionCode`, `processingType`, `guid`, `traceId`, `channelId`, `requestTime`이며, 이 중 `businessCode`, `serviceId`, `guid`는 응답 필수로 정의되어 있다. 요청 Header의 전체 15개 필드 의미는 5.2를 따른다.

### 6.3 Result 필드 사전

| 필드 | Java 타입 | 응답 필수 | 생성 주체 | 의미·검증 | 예시 | 보안 주의 |
| --- | --- | --- | --- | --- | --- | --- |
| `resultCode` | `String` | 예 | `Result.success()` 또는 `Result.fail()` | 성공은 `S0000`, 현재 일반 실패는 `E0001` | `S0000` | HTTP 상태만으로 성공 판정하지 않음 |
| `resultMessage` | `String` | 예 | `Result` factory | 처리 결과의 공통 메시지 | `정상 처리되었습니다.` | 내부 구현 정보 제외 |
| `errorCode` | `String` | 아니오 | 실패 처리 | 업무·시스템 오류 식별자 | `E-VALID-0001` | 외부 계약으로 공개된 코드만 사용 |
| `errorMessage` | `String` | 아니오 | 실패 처리 | 사용자에게 필요한 오류 설명 | `필수 입력값이 없습니다.` | SQL·예외 클래스 노출 금지 |
| `errorDetail` | `String` | 아니오 | 실패 처리 | 내부 진단용 상세값 | `필수값 검증 실패` | SQL, stack trace, 파일 경로, 예외 클래스는 외부 클라이언트에 절대 노출하지 않음 |
| `errorSystemId` | `String` | 아니오 | `Result.fail()` | 오류 발생 시스템 | `NSIGHT-MP` | 시스템 구성 상세를 과다 노출하지 않음 |
| `errorDateTime` | `String` | 아니오 | `Result.fail()` | ISO-8601 오류 시각 | `2026-07-26T10:00:01+09:00` | 감사 목적 외 민감정보와 결합 금지 |

#### `errorDetail` 현재 구현과 목표 보안 계약

현재 `GlobalStandardExceptionHandler`는 검증 오류에 `e.getMessage()`를, 허용하지 않은 HTTP 메서드와 시스템 오류에 예외 클래스 단순명을 `errorDetail`로 넣어 응답 직렬화한다. 그러므로 현재 구현만으로는 위 표의 외부 노출 금지 기준이 강제되지 않으며, 예외 메시지·클래스가 클라이언트에 노출될 수 있다.

목표 보안 계약은 `errorDetail`을 서버 로그 전용 진단 정보로 처리하는 것이다. 클라이언트 응답에는 `errorDetail`을 비우거나, 공개가 승인된 고정 안전값만 허용목록으로 반환한다. 예외 원문, SQL, stack trace, 파일 경로와 예외 클래스명은 `guid`·`traceId`와 함께 서버 로그에서만 확인하도록 후속 처리를 개선한다. 아래 오류 JSON 예시는 이 목표 계약의 안전한 응답 형태이며, 현재 예외 처리기가 모든 경로에서 이를 보장한다는 뜻은 아니다.

### 6.4 성공 판정

`result.resultCode == "S0000"`이면 성공이다. 실패 factory는 현재 `resultCode`를 `E0001`, `resultMessage`를 `처리 중 오류가 발생했습니다.`로 설정한다. `StandardResponse.fail(...)`은 `header`와 `result`만 설정하고 body는 설정하지 않는다.

## 8. 전문 처리 흐름

```text
Client
  ↓
OnlineTransactionController
  ↓
TCF.process
  ↓
STF.preProcess
  ↓
TransactionDispatcher
  ↓
Handler → Facade → Service
  ↓
ETF.success / businessFail / systemError
  ↓
Client
```

Client는 `header`와 업무 `body`를 `POST /online` 또는 `POST /{businessCode}/online`으로 보낸다. Controller는 Header가 없으면 빈 Header를 만들고, Header의 `businessCode`가 비었을 때만 경로 값을 넣으며, `clientIp`가 비었을 때 `X-Forwarded-For` 첫 값 또는 `remoteAddr`를 넣는다. STF는 Header 정규화·공통 검증, 상관 ID 생성, 세션·인증·권한·거래 통제·timeout·멱등성 검증과 거래 로그 시작을 맡는다.

Dispatcher는 `header.serviceId`로 등록된 Handler를 찾아 request와 `TransactionContext`를 전달한다. Handler는 거래 분기 후 Facade·Service·Rule·persistence로 Body를 처리한다. 반환 Body는 ETF가 성공 응답에 감싼다. `BusinessException`은 `ETF.businessFail`, 그 밖의 예외는 `ETF.systemError`로 가며 timeout 예외는 업무 오류 경로로 변환된다. ETF는 `StandardResponse`와 멱등·거래·감사 로그 및 메트릭의 최종 처리를 맡고, TCF는 모든 종료 경로에서 컨텍스트와 MDC를 정리한다.

## 9. 주요 필드 생명주기

| 필드 | 생산자·처리 | 최종 소비자·응답 |
| --- | --- | --- |
| `businessCode` | Client Header 또는 URL path. Controller가 Header 빈 값만 보완하고 STF가 처리 Header를 trim·대문자 정규화한다. | 거래 통제·업무 컨텍스트. 응답은 Controller 보완 후의 client Header 사본을 사용한다. |
| `serviceId` | Client Header, STF의 카탈로그 필수값 검증 후 Dispatcher Handler 선택 키. | Handler·Facade·Service의 유스케이스 식별, 응답 Header. |
| `guid` | Client 제공 또는 STF의 빈 값 자동 생성. MDC·거래·감사 로그에 사용한다. | 빈 값이면 client Header 사본에도 보완되어 Client 응답·운영 로그 상관 키가 된다. |
| `traceId` | Client 제공 또는 STF의 빈 값 자동 생성, MDC에 사용. | 빈 값이면 응답 Header에도 보완되어 분산 추적 키가 된다. |
| `clientIp` | Header가 비면 Controller가 `X-Forwarded-For` 첫 값 또는 `remoteAddr` 설정. | 거래 통제·감사 및 응답 Header. 신뢰 프록시 검증은 현재 없다. |
| `body` | Client의 서비스별 DTO/Map을 Handler와 업무 계층이 검증·처리한다. | ETF는 성공 반환 객체를 `StandardResponse.body`에 넣고, 실패 factory는 body를 설정하지 않는다. |

응답 Header는 STF 처리 Header 전체가 아니다. TCF가 STF 전에 만든 client Header 사본을 ETF가 반환하고, STF가 새로 만든 `guid`·`traceId`만 그 사본에 보완한다. 그러므로 `systemId` 기본값이나 대문자 정규화가 응답 Header에 항상 반영된다고 가정해서는 안 된다.

## 10. 검증과 정합성

| 계층 | 책임 |
| --- | --- |
| Controller | HTTP/JSON 진입, URL `businessCode`·`clientIp` 보완 |
| STF / `StandardHeaderValidator` | 공통 Header, 정규화, 세션·인증·멱등성·거래 통제·timeout |
| Handler / DTO | Body 형식·타입·필수 입력 |
| Rule / Service | 업무 규칙·상태·계산 정합성 |

`StandardHeaderValidator`는 `TcfStandardMessageCatalog.requiredRequestHeaderFieldKeys()`의 `requiredYn=Y` 필드를 검사한다. 필수 Header를 바꾸면 카탈로그·샘플·도움말·계약 테스트를 함께 바꾼다.

| 허용 enum | `INQUIRY` | `CREATE` | `UPDATE` | `DELETE` | `EXECUTE` | `DOWNLOAD` | `UPLOAD` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 처리 유형 | 조회 | 등록 | 수정 | 삭제 | 실행 | 다운로드 | 업로드 |

카탈로그는 `ProcessingType` enum에서 validation rule 문자열을 만들지만, 현행 Validator는 정규화와 필수값 존재만 검사한다. enum 소속 여부는 현재 강제하지 않아 공백이 아닌 임의 값이 통과할 수 있다. 향후 검증은 호환성·오류 코드·샘플을 검토한 뒤 `INVALID_HEADER`로 적용한다.

## 11. 성공과 오류 응답

표준 JSON 거래는 보통 HTTP 200과 `result.resultCode`를 함께 해석한다. `S0000`은 성공, `E0001`은 실패 factory의 공통 코드다. 비표준 REST·multipart·relay는 endpoint별 HTTP 상태 계약을 별도로 적용할 수 있다.

| 오류 경로 | ETF 처리 | 응답 |
| --- | --- | --- |
| 공통 검증 | Header 누락, 세션·권한·통제·멱등성의 `BusinessException` → `businessFail` | `E0001`, 공개 오류 코드·메시지, body 없음 |
| 업무 | Handler·Facade·Service·Rule 또는 미등록 serviceId의 `BusinessException` → `businessFail` | `E0001`, 공개 오류 코드·메시지, body 없음 |
| 시스템 | 예상하지 못한 Exception → `systemError` | `E0001`, 시스템 오류 메시지, body 없음 |

ETF는 `StandardResponse.success(header, body)` 또는 `StandardResponse.fail(header, errorCode, message, detail)`를 만들고 멱등·거래·감사 로그 및 메트릭을 마감한다. 현행 TCF 시스템 오류와 전역 예외 처리기 일부는 `errorDetail`에 예외 단순 클래스명 또는 검증 예외 메시지를 넣는다. 이는 아래 권고 보안 계약과 다른 현행 동작이다.

## 12. 보안·개인정보·로그

표준 전문·로그·Client 응답에는 password, access token, refresh token, private key, session ID, 개인정보, 전체 body, SQL, stack trace, 내부 파일 경로를 남기거나 노출하지 않는다. 로그에는 최소 상관 키(`guid`, `traceId`, `serviceId`)와 승인된 결과 코드만 남기고 민감값은 마스킹·제외한다.

`clientIp`는 인증·권한 또는 신뢰 경계의 단독 근거가 아니다. 현행 Controller는 신뢰 프록시 판별 없이 `X-Forwarded-For` 첫 값을 반영하므로, allowlist와 IP 형식 검증이 적용될 때까지 보안 판단에 사용하지 않는다. 오류 응답의 `errorDetail`은 비우거나 허용된 안전값만 반환하고, 예외 원문·SQL·stack trace·내부 경로·예외 클래스명은 `guid`·`traceId`로 서버에서만 추적한다. 특히 현행 `TCF.logClientRequest()`와 `logClientResponse()`는 Header와 body를 콘솔 출력하므로 이 금지 원칙을 완전히 충족하지 않는다. allowlist 구조화 로그와 마스킹으로 개선해야 한다.

## 13. 구현·문서·샘플 정합성 분석

| 항목 | 현재 구현 | 문서·샘플 | 영향 | 개선 권고 |
| --- | --- | --- | --- | --- |
| 레거시 시각·일자 | `StandardHeader`에 `transactionIntime`, `transactionOuttime`, `systemDate`, `bizDate` 없음 | `sv-sample-inquiry.json`에 네 필드 존재 | 서버 검증·응답·감사 대상으로 오해 | 샘플 제거 또는 채널 확장임을 명시, 필요 시 계약·모델·검증 동시 추가 |
| 필수 Header | Validator가 `requiredRequestHeaderFieldKeys()`를 순회 | 카탈로그가 필수 계약의 정본 | 카탈로그 변경만으로 호출 실패 가능 | 카탈로그·샘플·도움말·계약 테스트 동시 변경 |
| 거래 어휘 | 기존 예시는 `inquiry`·`save` | 신규 CRUD 승인 어휘는 `selectList`·`selectDetail`·`create`·`update`·`delete` | 새 Handler와 예시 serviceId 불일치 | 신규는 승인 어휘 사용, 기존은 호환 대상으로 명시·전환 |
| Body 식별자 중복 | ETF는 Header와 body를 분리 조립 | 일부 응답 body가 `businessCode`·`serviceId`·`guid` 중복 | 값 불일치 시 정본 모호 | Header를 정본으로 하고 호환 목적만 중복 유지 |
| HTTP 상태·결과 코드 | 표준 Controller/TCF는 주로 HTTP 200 + `resultCode` | 비표준 REST는 HTTP 상태를 다르게 사용 가능 | HTTP 상태만 검사하면 표준 오류 누락 | 표준 Client는 `result.resultCode`, 비표준은 endpoint 계약 사용 |
| 전체 본문 로그 | TCF가 request·response body를 콘솔 출력 | 목표 보안은 secrets·session ID·PII·전체 body 기록 금지 | 운영 로그 유출 위험 | allowlist·마스킹 로그로 교체하고 본문 진단을 제한 |
