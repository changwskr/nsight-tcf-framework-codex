# NSIGHT TCF 메시지 처리 방식

## 1. 목적과 범위

이 문서는 채널에서 작성한 JSON이 NSIGHT TCF에 도착해 역직렬화, 보완, 검증, 라우팅, 업무 처리, 응답 조립과 직렬화를 거쳐 돌아가는 메시지 생명주기를 설명한다. 기준 문서는 [`04-messaging.md`](../../zdocs-1/architecture/04-messaging.md)이며, 실제 Java·JavaScript 구현을 최종 근거로 사용한다.

다루는 범위는 표준 HTTP/JSON, `TcfGateway`, UI·Gateway Relay, 하이브리드 REST, 서비스 간 `tcf-eai` 연동이다. Header와 Result의 전체 필드 사전은 [전문 구성](2026-07-26-04-전문구성.md), DB 트랜잭션과 Rollback은 [트랜잭션 처리 방식](2026-07-26-05-트랜잭션처리방식.md)을 따른다.

이 문서의 표기는 다음과 같다.

- **현재 구현**: 저장소 소스에서 확인한 동작
- **개발 표준**: 신규 메시지가 따라야 할 기준
- **개선 권고**: 현재 구현과 목표 계약 사이의 차이

현재 코어 메시징은 동기 HTTP/JSON 기반이다. Kafka·JMS 등 비동기 브로커는 코어에 포함되지 않는다.

## 2. 핵심 용어

| 용어 | 의미 |
| --- | --- |
| 표준 메시지 | `StandardRequest`와 `StandardResponse` 계약을 사용하는 HTTP/JSON 메시지 |
| Header | 라우팅, 추적, 인증·권한과 거래통제에 쓰는 공통 정보 |
| Body | 서비스별 요청 또는 응답 데이터 |
| Result | 성공·실패와 공개 오류 정보를 표현하는 공통 결과 |
| Relay | 메시지 의미를 해석하지 않고 대상 시스템에 전달하는 중계 |
| Adaptation | 비표준 입력을 표준 요청으로 조립하거나 응답을 다른 외형으로 감싸는 변환 |
| 상관관계 ID | 요청과 로그를 연결하는 `guid`, `traceId` |
| 표준 성공 | HTTP 상태뿐 아니라 `result.resultCode == "S0000"`인 상태 |

## 3. 메시지 처리 4계층

| 계층 | 입력 | 책임 | 출력 | 대표 구현 |
| --- | --- | --- | --- | --- |
| Transport | HTTP 요청 | Method, URL, Content-Type, Cookie, Authorization, 상태 코드 | JSON·바이너리 또는 HTTP 오류 | Spring MVC, `RestClient` |
| Serialization | JSON 문자열 | JSON과 Java 객체 변환 | `StandardRequest` 또는 응답 JSON | Jackson |
| Semantic | Header·Body | 정규화, 공통 검증, 라우팅, 업무 처리, Result 조립 | `StandardResponse` | STF, Dispatcher, Handler, ETF |
| Adaptation | REST·multipart·UI 요청 | 표준 요청 조립 또는 투명 Relay | 표준 요청, Relay 결과, 비표준 응답 | `TcfGateway`, UI·Gateway Relay |

계층 경계를 섞지 않는 것이 중요하다. 잘못된 JSON은 Serialization 오류이고, 필수 Header 누락은 Semantic 오류다. `header/result/body` 모양이 비슷해도 STF와 ETF를 거치지 않았다면 표준 TCF 거래가 아니다.

```text
Channel
  │ HTTP/JSON
  ▼
Transport ── Jackson 역직렬화 ──► Serialization
  │                                  │ StandardRequest
  ▼                                  ▼
Adaptation(선택) ───────────────► Semantic(STF → Handler → ETF)
  ▲                                  │ StandardResponse
  └──── Relay 또는 응답 래핑 ◄───────┘
```

## 4. 전체 메시지 생명주기

### 4.1 표준 경로

```text
[1] Compose      채널이 Header + Body 작성
[2] Send         POST /online 또는 /{businessCode}/online, UTF-8 JSON
[3] Receive      Spring MVC가 요청 수신
[4] Deserialize  Jackson → StandardRequest<Map<String,Object>>
[5] Enrich       Controller가 Header, businessCode, clientIp 보완
[6] Normalize    STF의 StandardHeaderValidator가 Header 정규화·필수값 검사
[7] Correlate    STF가 guid·traceId 생성, Context와 MDC 준비
[8] Control      세션·인증·권한·거래통제·Timeout·멱등성·거래로그 시작
[9] Route        serviceId → TransactionHandler
[10] Process     Handler → Facade → Service → Rule → DAO/Mapper
[11] Assemble    ETF → StandardResponse(header + result + body)
[12] Serialize   Jackson → JSON
[13] Respond     HTTP 응답
[14] Judge       채널이 경로별 HTTP 상태와 resultCode 판정
```

`TCF.process()`는 성공, `BusinessException`, Timeout 변환, 기타 시스템 예외를 각각 ETF 경로에 연결하고 `finally`에서 TransactionContext, 인증 Context, Timeout Context와 MDC를 정리한다.

### 4.2 메시지 변환 지점

| 단계 | 변경 주체 | 현재 구현 |
| --- | --- | --- |
| 역직렬화 | Jackson | JSON을 `StandardRequest<Map<String,Object>>`로 변환 |
| HTTP 보완 | `OnlineTransactionController` | Header가 없으면 생성하고, 비어 있는 `businessCode`와 `clientIp`를 보완 |
| 정규화 | `StandardHeaderValidator`·`StandardHeader` | 기본값과 대문자 정규화 후 카탈로그 필수값 검사 |
| 상관관계 | STF | 비어 있는 `guid`, `traceId`를 생성하고 응답용 Header에도 반영 |
| 라우팅 | `TransactionDispatcher` | `header.serviceId`로 Handler 한 개를 선택 |
| 업무 전달 | Handler | 요청 Body와 `TransactionContext`를 업무 계층에 전달 |
| 응답 조립 | ETF | 성공·업무 실패·시스템 실패에 맞는 Result와 Body 조립 |

## 5. 진입점 유형 비교

| 유형 | 진입 컴포넌트 | 입력 | 메시지 변환 | TCF 적용 위치 | 오류 계약 | 사용 사례 |
| --- | --- | --- | --- | --- | --- | --- |
| 표준 JSON | `OnlineTransactionController` | `StandardRequest` JSON | Jackson 역직렬화와 Header 일부 보완 | **TCF 전체 적용** | 주로 HTTP 200 + Result | 외부 채널·테스트 요청 |
| 프로그램 위임 | `TcfGateway.invoke()` | Java `TcfInvokeRequest` | Header·Body를 `StandardRequest`로 조립 | **TCF 전체 적용** | StandardResponse | REST·multipart Controller 내부 위임 |
| UI Relay | `tcf-ui` Relay | JSON 문자열 | 원칙적으로 투명 전달, 응답을 Relay 결과로 감쌈 | **대상 WAR에서 적용** | Relay HTTP 상태 + 대상 응답 문자열 | 다중 업무 테스트·OM Admin |
| API Gateway Relay | Gateway Route | HTTP 요청 | 라우팅 Header를 전달하고 대상 URL로 중계 | **대상 WAR에서 적용** | Gateway 오류 또는 대상 응답 | 통합 관문 |
| 하이브리드 REST | 파일·관리 REST Controller | multipart·바이너리·일반 JSON | Controller별 수동 변환 | **TCF 미적용** 또는 명시적 Gateway 위임 | HTTP 상태 또는 유사 응답 | 파일 업·다운로드 |
| 서비스 연동 | `tcf-eai` | Java 호출 계약 | 표준 요청 조립 후 HTTP 호출 | **대상 WAR에서 적용** | 연동 예외 + 대상 Result | 업무 WAR 간 호출 |

진입점별 TCF 적용 위치를 먼저 확인해야 한다. Relay가 표준 검증을 수행하는 것이 아니라 대상 업무 WAR가 STF·Handler·ETF를 실행한다.

## 6. 표준 JSON 메시지 처리

### 6.1 Transport 계약

```text
POST /online
POST /{businessCode}/online
Content-Type: application/json; charset=UTF-8
```

요청은 다음 외형을 사용한다.

```json
{
  "header": {
    "businessCode": "SV",
    "serviceId": "SV.Sample.inquiry",
    "transactionCode": "SV-SMP-0001",
    "processingType": "INQUIRY",
    "channelId": "WEBTOP"
  },
  "body": {
    "query": "demo"
  }
}
```

예시는 메시지 외형 설명용이다. 실제 호출에는 서비스별 필수 Header, 거래통제 조건부 필드와 Body 계약을 함께 충족해야 한다.

### 6.2 Controller 보완

**현재 구현**에서 `OnlineTransactionController`는 다음만 수행한다.

1. `request.header == null`이면 빈 `StandardHeader`를 만든다.
2. URL에 `businessCode`가 있고 Header 값이 비어 있을 때만 URL 값을 넣는다.
3. Header의 `clientIp`가 비어 있으면 `X-Forwarded-For` 첫 값 또는 `remoteAddr`를 넣는다.
4. `TCF.process(request)`를 호출한다.

URL과 Header의 `businessCode`가 서로 다를 때 강제로 거부하거나 덮어쓰지 않는다. `X-Forwarded-For`도 신뢰 프록시 판별 없이 사용하므로 보안 경계로 해석해서는 안 된다.

### 6.3 Semantic 처리

STF는 Header 검증 후 상관관계 ID, 세션·인증·권한, 거래통제, Timeout, 멱등성과 거래로그를 준비한다. Dispatcher는 오직 `serviceId`로 Handler를 찾으며, 미등록 값은 `SERVICE_NOT_FOUND` 업무 오류가 된다. ETF는 성공이면 `S0000`, 실패면 `E0001` Result를 조립한다.

표준 경로의 업무 결과는 HTTP 200만으로 판정하지 않는다. 클라이언트는 `result.resultCode`를 반드시 확인한다.

## 7. TcfGateway 프로그램 위임

`TcfGateway`는 표준 JSON을 직접 받지 않는 Controller도 동일한 STF→Dispatcher→ETF 파이프라인을 사용하게 하는 Java 어댑터다.

```java
StandardResponse<Object> response = tcfGateway.invoke(
    TcfGateway.TcfInvokeRequest.builder(
            "UD.File.list",
            "UD-LST-0001",
            "INQUIRY")
        .body(body)
        .userId(userId)
        .clientIp(clientIp)
        .build()
);
```

### 7.1 현재 Header 기본값

| 필드 | 현재 구현 |
| --- | --- |
| `systemId` | `NSIGHT-MP` |
| `businessCode` | `serviceId`의 첫 `.` 앞 토큰, 점이 없거나 null이면 `UD` |
| `serviceId` | Builder 인자 |
| `transactionCode` | Builder 인자 |
| `processingType` | Builder 인자 |
| `channelId` | 지정 값, 비어 있으면 `WEBTOP` |
| `userId`, `clientIp` | 값이 있을 때만 설정 |
| `body` | null이면 빈 Map |

`invoke()`는 조립한 `StandardRequest`를 `TCF.process()`에 넘긴다. 따라서 Gateway 사용은 단순히 표준 모양의 응답만 만드는 것이 아니라 **TCF 전체 적용**이다.

**개발 표준**: 비표준 REST가 공통 검증·거래통제·Timeout·멱등성·거래로그를 필요로 하면 업무 Service를 직접 호출하지 말고 `TcfGateway` 사용을 우선한다. 단, 파일 스트리밍처럼 TCF 응답 외형과 충돌하는 경로는 적용 범위와 누락되는 통제를 API 계약에 명시한다.
