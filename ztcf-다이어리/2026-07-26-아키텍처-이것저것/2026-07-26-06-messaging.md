# NSIGHT TCF 메시지 처리 방식

## 1. 목적과 범위

이 문서는 채널에서 작성한 JSON이 NSIGHT TCF에 도착해 역직렬화, 보완, 검증, 라우팅, 업무 처리, 응답 조립과 직렬화를 거쳐 돌아가는 메시지 생명주기를 설명한다. 기준 문서는 [`04-messaging.md`](../../zdocs-1/architecture/04-messaging.md)이며, 실제 Java·JavaScript 구현을 최종 근거로 사용한다.

다루는 범위는 표준 HTTP/JSON, `TcfGateway`, UI·Gateway Relay, 하이브리드 REST, 서비스 간 `tcf-eai` 연동이다. Header와 Result의 전체 필드 사전은 [전문 구성](2026-07-26-04-전문구성.md), DB 트랜잭션과 Rollback은 [트랜잭션 처리 방식](2026-07-26-05-트랜잭션처리방식.md)을 따른다.

이 문서의 표기는 다음과 같다.

- **현재 구현**: 저장소 소스에서 확인한 동작
- **개발 표준**: 신규 메시지가 따라야 할 기준
- **개선 권고**: 현재 구현과 목표 계약 사이의 차이

현재 코어 메시징은 동기 HTTP/JSON 기반이다. Kafka·JMS 등 비동기 브로커는 코어에 포함되지 않는다.

## 2. 핵심 용어

| 용어 | 의미 |
| --- | --- |
| 표준 메시지 | `StandardRequest`와 `StandardResponse` 계약을 사용하는 HTTP/JSON 메시지 |
| Header | 라우팅, 추적, 인증·권한과 거래통제에 쓰는 공통 정보 |
| Body | 서비스별 요청 또는 응답 데이터 |
| Result | 성공·실패와 공개 오류 정보를 표현하는 공통 결과 |
| Relay | 메시지 의미를 해석하지 않고 대상 시스템에 전달하는 중계 |
| Adaptation | 비표준 입력을 표준 요청으로 조립하거나 응답을 다른 외형으로 감싸는 변환 |
| 상관관계 ID | 요청과 로그를 연결하는 `guid`, `traceId` |
| 표준 성공 | HTTP 상태뿐 아니라 `result.resultCode == "S0000"`인 상태 |

## 3. 메시지 처리 4계층

| 계층 | 입력 | 책임 | 출력 | 대표 구현 |
| --- | --- | --- | --- | --- |
| Transport | HTTP 요청 | Method, URL, Content-Type, Cookie, Authorization, 상태 코드 | JSON·바이너리 또는 HTTP 오류 | Spring MVC, `RestClient` |
| Serialization | JSON 문자열 | JSON과 Java 객체 변환 | `StandardRequest` 또는 응답 JSON | Jackson |
| Semantic | Header·Body | 정규화, 공통 검증, 라우팅, 업무 처리, Result 조립 | `StandardResponse` | STF, Dispatcher, Handler, ETF |
| Adaptation | REST·multipart·UI 요청 | 표준 요청 조립 또는 투명 Relay | 표준 요청, Relay 결과, 비표준 응답 | `TcfGateway`, UI·Gateway Relay |

계층 경계를 섞지 않는 것이 중요하다. 잘못된 JSON은 Serialization 오류이고, 필수 Header 누락은 Semantic 오류다. `header/result/body` 모양이 비슷해도 STF와 ETF를 거치지 않았다면 표준 TCF 거래가 아니다.

```text
Channel
  │ HTTP/JSON
  ▼
Transport ── Jackson 역직렬화 ──► Serialization
  │                                  │ StandardRequest
  ▼                                  ▼
Adaptation(선택) ───────────────► Semantic(STF → Handler → ETF)
  ▲                                  │ StandardResponse
  └──── Relay 또는 응답 래핑 ◄───────┘
```

## 4. 전체 메시지 생명주기

### 4.1 표준 경로

```text
[1] Compose      채널이 Header + Body 작성
[2] Send         POST /online 또는 /{businessCode}/online, UTF-8 JSON
[3] Receive      Spring MVC가 요청 수신
[4] Deserialize  Jackson → StandardRequest<Map<String,Object>>
[5] Enrich       Controller가 Header, businessCode, clientIp 보완
[6] Normalize    STF의 StandardHeaderValidator가 Header 정규화·필수값 검사
[7] Correlate    STF가 guid·traceId 생성, Context와 MDC 준비
[8] Control      세션·인증·권한·거래통제·Timeout·멱등성·거래로그 시작
[9] Route        serviceId → TransactionHandler
[10] Process     Handler → Facade → Service → Rule → DAO/Mapper
[11] Assemble    ETF → StandardResponse(header + result + body)
[12] Serialize   Jackson → JSON
[13] Respond     HTTP 응답
[14] Judge       채널이 경로별 HTTP 상태와 resultCode 판정
```

`TCF.process()`는 성공, `BusinessException`, Timeout 변환, 기타 시스템 예외를 각각 ETF 경로에 연결하고 `finally`에서 TransactionContext, 인증 Context, Timeout Context와 MDC를 정리한다.

### 4.2 메시지 변환 지점

| 단계 | 변경 주체 | 현재 구현 |
| --- | --- | --- |
| 역직렬화 | Jackson | JSON을 `StandardRequest<Map<String,Object>>`로 변환 |
| HTTP 보완 | `OnlineTransactionController` | Header가 없으면 생성하고, 비어 있는 `businessCode`와 `clientIp`를 보완 |
| 정규화 | `StandardHeaderValidator`·`StandardHeader` | 기본값과 대문자 정규화 후 카탈로그 필수값 검사 |
| 상관관계 | STF | 비어 있는 `guid`, `traceId`를 생성하고 응답용 Header에도 반영 |
| 라우팅 | `TransactionDispatcher` | `header.serviceId`로 Handler 한 개를 선택 |
| 업무 전달 | Handler | 요청 Body와 `TransactionContext`를 업무 계층에 전달 |
| 응답 조립 | ETF | 성공·업무 실패·시스템 실패에 맞는 Result와 Body 조립 |

## 5. 진입점 유형 비교

| 유형 | 진입 컴포넌트 | 입력 | 메시지 변환 | TCF 적용 위치 | 오류 계약 | 사용 사례 |
| --- | --- | --- | --- | --- | --- | --- |
| 표준 JSON | `OnlineTransactionController` | `StandardRequest` JSON | Jackson 역직렬화와 Header 일부 보완 | **TCF 전체 적용** | 주로 HTTP 200 + Result | 외부 채널·테스트 요청 |
| 프로그램 위임 | `TcfGateway.invoke()` | Java `TcfInvokeRequest` | Header·Body를 `StandardRequest`로 조립 | **TCF 전체 적용** | StandardResponse | REST·multipart Controller 내부 위임 |
| UI Relay | `tcf-ui` Relay | JSON 문자열 | 원칙적으로 투명 전달, 응답을 Relay 결과로 감쌈 | **대상 WAR에서 적용** | Relay HTTP 상태 + 대상 응답 문자열 | 다중 업무 테스트·OM Admin |
| API Gateway Relay | Gateway Route | HTTP 요청 | 라우팅 Header를 전달하고 대상 URL로 중계 | **대상 WAR에서 적용** | Gateway 오류 또는 대상 응답 | 통합 관문 |
| 하이브리드 REST | 파일·관리 REST Controller | multipart·바이너리·일반 JSON | Controller별 수동 변환 | **TCF 미적용** 또는 명시적 Gateway 위임 | HTTP 상태 또는 유사 응답 | 파일 업·다운로드 |
| 서비스 연동 | `tcf-eai` | Java 호출 계약 | 표준 요청 조립 후 HTTP 호출 | **대상 WAR에서 적용** | 연동 예외 + 대상 Result | 업무 WAR 간 호출 |

진입점별 TCF 적용 위치를 먼저 확인해야 한다. Relay가 표준 검증을 수행하는 것이 아니라 대상 업무 WAR가 STF·Handler·ETF를 실행한다.

## 6. 표준 JSON 메시지 처리

### 6.1 Transport 계약

```text
POST /online
POST /{businessCode}/online
Content-Type: application/json; charset=UTF-8
```

요청은 다음 외형을 사용한다.

```json
{
  "header": {
    "businessCode": "SV",
    "serviceId": "SV.Sample.inquiry",
    "transactionCode": "SV-SMP-0001",
    "processingType": "INQUIRY",
    "channelId": "WEBTOP"
  },
  "body": {
    "query": "demo"
  }
}
```

예시는 메시지 외형 설명용이다. 실제 호출에는 서비스별 필수 Header, 거래통제 조건부 필드와 Body 계약을 함께 충족해야 한다.

### 6.2 Controller 보완

**현재 구현**에서 `OnlineTransactionController`는 다음만 수행한다.

1. `request.header == null`이면 빈 `StandardHeader`를 만든다.
2. URL에 `businessCode`가 있고 Header 값이 비어 있을 때만 URL 값을 넣는다.
3. Header의 `clientIp`가 비어 있으면 `X-Forwarded-For` 첫 값 또는 `remoteAddr`를 넣는다.
4. `TCF.process(request)`를 호출한다.

URL과 Header의 `businessCode`가 서로 다를 때 강제로 거부하거나 덮어쓰지 않는다. `X-Forwarded-For`도 신뢰 프록시 판별 없이 사용하므로 보안 경계로 해석해서는 안 된다.

### 6.3 Semantic 처리

STF는 Header 검증 후 상관관계 ID, 세션·인증·권한, 거래통제, Timeout, 멱등성과 거래로그를 준비한다. Dispatcher는 오직 `serviceId`로 Handler를 찾으며, 미등록 값은 `SERVICE_NOT_FOUND` 업무 오류가 된다. ETF는 성공이면 `S0000`, 실패면 `E0001` Result를 조립한다.

표준 경로의 업무 결과는 HTTP 200만으로 판정하지 않는다. 클라이언트는 `result.resultCode`를 반드시 확인한다.

## 7. TcfGateway 프로그램 위임

`TcfGateway`는 표준 JSON을 직접 받지 않는 Controller도 동일한 STF→Dispatcher→ETF 파이프라인을 사용하게 하는 Java 어댑터다.

```java
StandardResponse<Object> response = tcfGateway.invoke(
    TcfGateway.TcfInvokeRequest.builder(
            "UD.File.list",
            "UD-LST-0001",
            "INQUIRY")
        .body(body)
        .userId(userId)
        .clientIp(clientIp)
        .build()
);
```

### 7.1 현재 Header 기본값

| 필드 | 현재 구현 |
| --- | --- |
| `systemId` | `NSIGHT-MP` |
| `businessCode` | `serviceId`의 첫 `.` 앞 토큰, 점이 없거나 null이면 `UD` |
| `serviceId` | Builder 인자 |
| `transactionCode` | Builder 인자 |
| `processingType` | Builder 인자 |
| `channelId` | 지정 값, 비어 있으면 `WEBTOP` |
| `userId`, `clientIp` | 값이 있을 때만 설정 |
| `body` | null이면 빈 Map |

`invoke()`는 조립한 `StandardRequest`를 `TCF.process()`에 넘긴다. 따라서 Gateway 사용은 단순히 표준 모양의 응답만 만드는 것이 아니라 **TCF 전체 적용**이다.

**개발 표준**: 비표준 REST가 공통 검증·거래통제·Timeout·멱등성·거래로그를 필요로 하면 업무 Service를 직접 호출하지 말고 `TcfGateway` 사용을 우선한다. 단, 파일 스트리밍처럼 TCF 응답 외형과 충돌하는 경로는 적용 범위와 누락되는 통제를 API 계약에 명시한다.

## 8. tcf-ui Relay

```text
Browser
→ POST /api/relay/{code}/online 또는 /api/multi/relay/{code}/online
→ TcfApiController(@RequestBody String)
→ TransactionRelayService
→ 대상 업무 WAR /{contextPath}/online
→ 대상 WAR OnlineTransactionController → TCF
→ RelayResult { businessCode, targetUrl, httpStatus, elapsedMs, responseBody, setCookies }
→ Browser가 responseBody를 JSON.parse하고 resultCode 판정
```

UI Relay는 요청을 문자열로 받아 그대로 전달한다. 직접 Relay에서 Header·Body를 파싱하거나 재작성하지 않으므로 실제 TCF 처리는 **대상 WAR에서 적용**된다.

| 모드 | 현재 URL 구성 |
| --- | --- |
| `bootrun` | `{bootrunHost}:{localPort}{contextPath}/online` |
| `tomcat` | `{tomcatGatewayUrl}{contextPath}/online` |
| Gateway Relay 활성 | `GatewayRelayService`가 Gateway 온라인 URL 결정 |

직접 Relay는 UTF-8 JSON으로 POST하고 대상의 HTTP 상태, 응답 문자열과 `Set-Cookie`를 `RelayResult`에 담는다. `TcfApiController`는 `Set-Cookie`를 브라우저 응답에 다시 추가한다.

**현재 구현**에서 직접 Relay는 Cookie만 대상에 전달한다. Controller가 Authorization을 서비스에 넘기지만 직접 Relay 구현은 사용하지 않는다. Gateway Relay 활성 경로에서는 `GatewayRelayService`가 Cookie와 Authorization을 담당한다. 연결 예외는 상태 값 502와 연결 오류 JSON을 가진 `RelayResult`로 변환한다.

**개선 권고**: 직접 Relay에 Authorization이 필요하면 허용 경로와 대상 신뢰 범위를 정해 명시적으로 전달하고 테스트한다.

## 9. API Gateway Relay

Gateway는 `businessCode`로 Route를 해석해 대상 WAR로 요청을 전달한다. `serviceId → Handler` 라우팅은 대상 WAR 내부에서 수행되므로 **대상 WAR에서 적용** 경로다.

`GatewayRouteDispatcher`의 현재 동작은 다음과 같다.

1. Route Connect/Read Timeout을 사용하고 0 이하면 각각 3000ms와 5000ms를 적용한다.
2. Content-Type과 Accept를 UTF-8 JSON으로 설정한다.
3. Cookie와 Route Context의 Authorization이 있으면 전달한다.
4. 보완된 요청 Body를 대상 URL로 POST한다.
5. 대상 HTTP 상태, 응답 문자열과 `Set-Cookie`를 수집한다.

Gateway 인증·세션·Route 실패는 대상 TCF의 `StandardResponse`가 아닐 수 있다. 인증 실패는 HTTP 401과 Gateway 오류 JSON을 사용할 수 있으므로 채널은 HTTP 상태와 응답 외형을 먼저 확인한다.

## 10. 하이브리드 REST·multipart

`OmUpdownloadFileController`의 `/ud/files/*`는 multipart 업로드, 바이너리 다운로드와 일반 REST를 제공하며 `TcfGateway`를 호출하지 않는다. 따라서 현재 경로는 **TCF 미적용**이다.

| 기능 | 입력·출력 | 현재 계약 |
| --- | --- | --- |
| 업로드 | multipart → Map JSON | 수동 `header/result/body` 성공·실패 조립 |
| 목록·상세·수정·삭제 | REST → Map JSON | `OmUpdownloadResponseSupport` 사용 |
| 다운로드 | GET → `ResponseEntity<byte[]>` | 바이너리와 HTTP Header |

성공 응답은 `businessCode=UD`, `requestTime`, `resultCode=S0000`과 Body를 포함한다. 실패 응답은 `E0001`이 아니라 업무 오류 코드 자체를 `resultCode`에 넣고 `status=ERROR`, `body.error`를 사용하며 Header도 없다. 표준 `StandardResponse`와 동일하지 않다.

이 경로에는 STF의 검증·거래통제·Online Timeout·멱등성·공통 거래로그가 자동 적용되지 않는다. 필요한 통제는 별도 정책으로 검증하거나 가능한 작업은 `TcfGateway`로 위임한다.

## 11. 직렬화·역직렬화

```text
요청  StandardRequest<T>  = header + body
응답  StandardResponse<T> = header + result + body
```

Spring MVC와 Jackson은 JSON을 `StandardRequest<Map<String,Object>>`로 역직렬화하고 Controller 반환값을 JSON으로 직렬화한다. 공통 모델의 JSON 필드는 camelCase다. 잘못된 JSON이나 호환되지 않는 타입은 Handler 진입 전에 MVC 계층에서 실패한다.

공통 TCF 계층은 Body를 `Map<String,Object>`로 운반한다. Handler는 거래를 선택하고 Facade가 업무 DTO 변환과 응답 조립을 담당하는 것을 원칙으로 한다. Relay는 Body를 재구성하지 않는다.

필드 삭제·이름 변경·타입 변경·필수 전환은 호출자, UI Composer, Relay, Gateway, EAI와 샘플 요청을 동시에 검토해야 한다.

## 12. Header 보완·정규화·검증

| 순서 | 주체 | 현재 구현 |
| --- | --- | --- |
| 1 | Jackson | JSON Header를 Java 객체로 생성 |
| 2 | Controller | 빈 Header 생성, URL businessCode와 clientIp 조건부 보완 |
| 3 | `StandardHeaderValidator` | `normalize()` 후 카탈로그 필수값 공백 검사 |
| 4 | STF | guid·traceId 생성과 응답용 Header 반영 |
| 5 | STF 하위 검증 | 세션, 인증 Context, 권한, 거래통제, Timeout, 멱등성 |

카탈로그의 길이·UUID·ISO-8601 메타데이터와 `processingType` Enum을 현재 Validator가 모두 강제하지는 않는다. 필수 집합과 미강제 항목은 [전문 구성](2026-07-26-04-전문구성.md)을 따른다.

Relay는 Header를 보완하지 않는다. Controller와 STF가 대상 WAR 안에서 보완한다. `TcfGateway`와 `tcf-eai`는 HTTP 수신 전 Java 측에서 Header를 조립하는 Adaptation이다.

## 13. Handler 라우팅과 Body 전달

`TransactionDispatcher`는 `request.header.serviceId` 하나로 Handler를 찾는다.

- serviceId가 비어 있으면 `INVALID_HEADER` 업무 오류다.
- 등록된 Handler가 없으면 `SERVICE_NOT_FOUND` 업무 오류다.
- 동일 serviceId를 둘 이상의 Handler가 등록하면 기동 중 실패한다.
- businessCode와 serviceId 조합 일치 여부를 Dispatcher가 별도로 검증하지 않는다.

Handler는 거래 분기와 Facade 호출에 집중한다. 계층 책임은 [레이어드 아키텍처](2026-07-26-03-어플리케이션레이어드아키텍처.md)를 따른다.

## 14. 응답 메시지 조립

| 경로 | Result | Body | 후처리 |
| --- | --- | --- | --- |
| `success` | `S0000` | Handler 반환값 | 멱등 성공, 거래로그, 감사, 메트릭 |
| `businessFail` | `E0001` + 업무 errorCode/message | 없음 | 멱등 실패, 거래로그, 감사, 메트릭 |
| `systemError` | `E0001` + `E-COM-SYS-0001` | 없음 | 실패 후처리와 시스템 로그 |

응답 Header는 클라이언트 Header 사본을 기반으로 하며 STF가 생성한 guid·traceId를 반영한다. 처리 중 보완된 모든 내부 Header가 그대로 Echo된다고 가정하면 안 된다.

## 15. 오류·HTTP 상태 처리

| 오류 위치 | 예 | 현재 판정 방식 |
| --- | --- | --- |
| 표준 TCF 업무·시스템 오류 | Header·거래통제·Handler·Timeout | 주로 HTTP 200 + `resultCode=E0001` + errorCode |
| MVC 역직렬화·검증 | 잘못된 JSON·타입 | 전역 예외 처리 또는 HTTP 오류 |
| JWT Filter | 토큰 없음·검증 실패 | HTTP 401 비표준 JSON 가능 |
| Gateway | 인증·Route·연결 실패 | HTTP 4xx/5xx와 Gateway JSON 가능 |
| UI Relay | 대상 상태·연결 예외 | `RelayResult.httpStatus`와 `responseBody` |
| 하이브리드 REST | 업로드·파일 오류 | Controller별 HTTP/유사 Result 계약 |
| tcf-eai | 연결·Timeout·대상 업무 실패 | 연동 예외 또는 성공 결과 |

클라이언트 판정 순서는 `HTTP 상태 → Content-Type과 응답 외형 → 표준이면 resultCode`다. 모든 오류를 `StandardResponse`로 강제 파싱하지 않는다.

## 16. Cookie·Authorization·보안

| 경로 | Cookie | Authorization | Set-Cookie 역전달 |
| --- | --- | --- | --- |
| tcf-ui 직접 Relay | 전달 | 현재 미전달 | 전달 |
| tcf-ui → Gateway Relay | 전달 | 전달 | 전달 |
| Gateway → 업무 WAR | 전달 | Route Context 값 전달 | 수집·프록시 |
| tcf-eai | 표준 Header Context 중심 | 기본 클라이언트의 Bearer 전달 계약 없음 | 해당 없음 |

**개발 표준**:

- Cookie, Authorization, Token과 세션 식별자의 값을 로그에 남기지 않는다.
- 개인정보와 전체 Body를 운영 로그에 무조건 출력하지 않는다.
- 외부 응답에 SQL, Stack Trace, 예외 클래스와 내부 경로를 노출하지 않는다.
- Relay 대상 URL은 Catalog·Route 설정으로 제한한다.
- `X-Forwarded-For`는 신뢰 프록시 또는 네트워크 경계를 검증한 뒤 사용한다.

**현재 구현**은 신뢰 프록시 확인 없이 `X-Forwarded-For` 첫 값을 사용하고, ETF 시스템 오류는 `errorDetail`에 예외 단순 클래스명을 넣는다. 모두 개선 대상이다.

## 17. Timeout·재시도·멱등성

| 경로 | Timeout |
| --- | --- |
| Gateway Relay | Route Connect/Read Timeout, 기본 3000/5000ms |
| 대상 TCF | Online·Transaction·DB Query Timeout |
| tcf-eai | 서비스별 Connect/Read Timeout |
| tcf-ui 직접 Relay | 현재 RestClient 생성부에 명시적 Timeout 없음 |

Relay Timeout은 대상 거래의 최종 상태를 증명하지 않는다. 변경 거래가 이미 처리됐을 수 있으므로 GUID, `idempotencyKey`와 거래로그를 확인한 뒤 재처리한다.

자동 재시도는 조회 또는 명시적으로 멱등한 거래에만 적용한다. 변경 거래는 idempotencyKey, 중복 결과 재사용과 상태 조회 정책을 정의한다.

## 18. 서비스 간 tcf-eai 메시징

```text
호출 Service
→ IntegrationCallRequest
→ StandardRequestBuilder(header + body)
→ RestClient POST 대상 /online
→ 대상 WAR TCF
→ ResponseResultValidator
→ IntegrationCallResult 또는 IntegrationException
```

`StandardRequestBuilder`는 대상 식별자와 처리유형을 설정하고 원 거래 guid·traceId, channelId, userId, branchId와 호출자 정보를 전파한다. serviceName은 미지정 시 대상 serviceId로 보완한다.

현재 빌더는 표준 Header 외에 `callerBusinessCode`, `callerServiceId`, `systemDate`, `bizDate`도 Map에 넣으므로 수신 Jackson 정책과 전문 정합성을 검증해야 한다.

- Endpoint는 `nsight.integration.services.{BUSINESS_CODE}`에서 찾는다.
- Connect Timeout 기본값은 1000ms이고 Read Timeout은 서비스 또는 전역 기본값을 사용한다.
- `resultCode == S0000`이면 성공이다.
- 업무 실패는 `IntegrationBusinessException`, Timeout은 `IntegrationTimeoutException`, 기타 실패는 `IntegrationException`이다.
- 타 업무 DB 직접 접근과 업무 WAR 간 Gradle 의존 대신 이 계약을 사용한다.

## 19. 비동기 메시징 확장 고려사항

Kafka·JMS 같은 브로커는 현재 TCF 코어 기능이 아니다.

| 계약 | 향후 결정사항 |
| --- | --- |
| 식별 | messageId, correlationId, causationId, 업무 키 |
| 스키마 | 이벤트 이름, 버전, 호환성, 필수·선택 필드 |
| 전달 | at-least-once, 중복 소비 방지, 순서 보장 범위 |
| 실패 | Retry, DLQ, 재처리 승인, 독성 메시지 격리 |
| 보안 | Producer/Consumer 인증, Topic 권한, 암호화 |
| 관측성 | 발행·소비·지연·실패·DLQ 메트릭과 추적 |
| 트랜잭션 | Outbox, 보상 또는 Saga와 DB Commit 관계 |

비동기 도입은 별도 아키텍처 결정과 구현 계획이 필요한 확장 과제다.

## 25. 핵심 원칙 요약

1. Transport, Serialization, Semantic과 Adaptation의 오류 경계를 섞지 않는다.
2. 표준 TCF 거래는 HTTP 상태뿐 아니라 `resultCode`로 결과를 판정한다.
3. Relay는 투명 전달을 원칙으로 하고 실제 공통 처리는 대상 WAR가 담당한다.
4. 하이브리드 REST는 누락되는 TCF 통제와 별도 오류 계약을 명시한다.
5. `TcfGateway`와 `tcf-eai`는 표준 메시지 계약을 재사용한다.
6. Timeout 후 변경 거래는 즉시 반복하지 않고 멱등성과 거래 상태를 먼저 확인한다.
7. Cookie·Authorization·개인정보·내부 오류 상세를 로그와 외부 응답에서 보호한다.
8. Kafka·JMS는 현재 코어 기능이 아니며 별도 설계가 필요한 확장 과제다.
