# NSIGHT TCF 트랜잭션 처리 방식

## 1. 목적과 범위

이 문서는 NSIGHT TCF 온라인 거래가 요청을 받아 표준 응답을 돌려줄 때까지의 실행 흐름과, 업무 개발자가 지켜야 할 DB 트랜잭션 경계를 설명한다. 대상 독자는 `TransactionHandler`부터 `DAO/Mapper`까지를 구현하는 업무 개발자와 STF·TCF·ETF를 유지하는 프레임워크 개발자다.

여기서 말하는 트랜잭션은 온라인 처리 전체와 같은 뜻이 아니다. 온라인 처리, DB 트랜잭션, DB 질의, 외부 연동은 시작·종료 시점과 실패 의미가 서로 다르다. 이 문서는 `2026-07-26-03-어플리케이션레이어드아키텍처.md`의 계층 설명과 `2026-07-26-04-전문구성.md`의 전문 계약을 반복하지 않고, 이 경계와 연결 지점에 집중한다.

### 현재 구현과 개발 표준의 표기

- **현재 구현**: 저장소 Java 소스에서 확인한 동작이다. 모든 업무 모듈에 자동 적용된다고 단정하지 않는다.
- **개발 표준**: 신규·변경 업무 거래가 따라야 하는 설계 기준이다. 현재 모든 기존 업무 코드가 충족한다는 뜻은 아니다.

## 2. 핵심 용어

| 용어 | 의미 |
| --- | --- |
| `serviceId` | `TransactionDispatcher`가 `TransactionHandler`를 찾는 거래 식별자다. Handler는 `serviceIds()`로 담당 목록을 선언한다. |
| STF | Standard Transaction Framework 전처리 단계다. Header 검증, 상관관계 ID, 인증·권한, 거래통제, Timeout 정책, 멱등성 및 거래 로그 시작을 처리한다. |
| TCF | STF, Dispatcher, ETF와 예외 경로를 조정하는 온라인 거래 오케스트레이터다. 진입점은 `TCF.process()`다. |
| ETF | 처리 결과를 표준 응답으로 조립하고 멱등성·거래 로그·감사·메트릭을 마감하는 후처리 단계다. |
| 온라인 처리 경계 | `TCF.process()`가 전처리부터 표준 응답 조립·정리까지 수행하는 범위다. |
| DB 트랜잭션 경계 | Spring `@Transactional` 프록시 또는 `TransactionTemplate`이 시작하고 Commit 또는 Rollback하는 범위다. |
| DB 질의 경계 | DAO/Mapper가 하나의 JDBC 또는 MyBatis Statement를 실행하는 범위다. DB 트랜잭션보다 짧을 수 있다. |
| 외부 연동 경계 | `client` 계층이 외부 시스템에 한 번 연결·요청·응답 대기를 수행하는 범위다. 로컬 DB 트랜잭션과 원자적으로 결합되지 않는다. |

## 3. 전체 트랜잭션 처리 구조

### 현재 구현

표준 HTTP 요청은 `OnlineTransactionController`의 `POST /online` 또는 `POST /{businessCode}/online`으로 들어온다. Controller는 필요한 경우 Header를 만들고, 경로의 `businessCode`와 클라이언트 IP를 보완한 뒤 `TCF.process()`를 호출한다. REST·multipart 등 비표준 진입점은 `TcfGateway`가 `StandardRequest`와 Header를 구성한 뒤 같은 `TCF.process()`로 위임한다.

```text
Client
  → JWT/Gateway 또는 OnlineTransactionController
  → TCF.process()
  → STF.preProcess()
  → OnlineTransactionTimeoutExecutor
  → TransactionDispatcher
  → Handler → Facade → Service → Rule → DAO/Mapper
  → ETF.success | ETF.businessFail | ETF.systemError
  → Client
```

`TCF.process()`는 STF가 반환한 `TransactionContext`를 사용해 Dispatcher를 실행한다. Dispatcher 호출은 `OnlineTransactionTimeoutExecutor.execute(...)`로 감싸며, 성공이면 `ETF.success(...)`, `BusinessException`이면 `ETF.businessFail(...)`, 그 밖의 예외면 `ETF.systemError(...)`로 이어진다. Timeout으로 변환 가능한 예외도 업무 실패 경로로 응답한다. 종료 시 TCF는 Runtime Hook, `TransactionContextHolder`, 인증·Timeout Holder 및 MDC를 정리한다.

### 네 가지 경계

| 경계 | 현재 구현에서의 시작과 종료 | 다른 경계와의 관계 |
| --- | --- | --- |
| 온라인 처리 경계 | `TCF.process()` 진입부터 ETF 응답 조립과 `finally` 정리까지다. HTTP Controller 또는 Gateway의 보완 작업은 이 경계 바깥에 있을 수 있다. | DB 트랜잭션이나 쿼리보다 넓을 수 있으며, 온라인 응답 완료가 DB Rollback 완료와 항상 같은 시점이라는 보장은 없다. |
| DB 트랜잭션 경계 | `@Transactional` 프록시 또는 `PolicyDrivenTransactionExecutor`의 `TransactionTemplate` 진입부터 정상 반환의 Commit 또는 예외에 따른 Rollback까지다. | 온라인 처리 전체를 자동으로 감싸지 않는다. 하나의 온라인 거래에 없거나 여러 개일 수 있다. |
| DB 질의 경계 | DAO/Mapper가 개별 Statement를 DB에 실행하는 동안이다. | 하나의 DB 트랜잭션 안에 여러 질의가 있을 수 있다. MyBatis Statement Timeout은 DB 트랜잭션 Timeout과 별개다. |
| 외부 연동 경계 | `client`가 외부 시스템에 요청하는 개별 연결·읽기·응답 처리 구간이다. | 로컬 DB Commit/Rollback과 하나의 원자적 경계가 아니다. Timeout 뒤에는 원격 처리 결과가 불명확할 수 있다. |

따라서 “온라인 Timeout”, “DB 트랜잭션 Timeout”, “DB Query Timeout”, “외부 연동 Timeout”은 같은 타이머가 아니며, 네 경계는 동일한 시작·종료 시점을 공유하지 않는다.

**근거 소스(현재 구현)**: `tcf-web/.../OnlineTransactionController.java`, `tcf-web/.../TcfGateway.java`, `tcf-core/.../processor/TCF.java`, `tcf-core/.../timeout/OnlineTransactionTimeoutExecutor.java`.

## 4. 단계별 실행 흐름

1. **진입점이 요청을 표준화한다.** `OnlineTransactionController.handle(...)`은 Header가 없으면 생성하고, URL의 업무코드와 `clientIp` 미입력 값을 보완한다. `TcfGateway.invoke(...)`는 호출 정보를 `StandardRequest`로 변환한다.
2. **TCF가 원본 응답 Header를 보존하고 STF를 호출한다.** `TCF.process(...)`는 클라이언트 Header 사본을 만든 뒤 `STF.preProcess(...)`를 실행한다.
3. **STF가 실행 컨텍스트와 사전 통제를 준비한다.** STF는 Header 검증, GUID·Trace ID 생성, `TransactionContextHolder`와 MDC 설정, 세션·인증 컨텍스트·권한 검증, 거래통제 검사, Timeout 정책 적용, 멱등성 PROCESSING 표시, 거래 로그 시작을 순서대로 수행한다.
4. **Online Timeout Executor가 Dispatcher 구간을 제한한다.** Timeout 정책과 전용 Executor가 모두 활성화되어 있으면 Context Snapshot을 워커 스레드에 전달하고 `Future.get(onlineTimeout)`으로 Dispatcher 실행을 기다린다. 초과하면 Future를 취소하고 `TIMEOUT_ONLINE` 업무 예외를 던진다. Executor가 없거나 정책이 비활성이면 현재 스레드에서 바로 실행한다.
5. **Dispatcher가 Handler를 선택한다.** 애플리케이션 시작 때 Dispatcher는 각 Handler의 `serviceIds()`를 등록하고 중복 `serviceId`를 거부한다. 실행 시 요청 Header의 `serviceId`로 Handler를 찾아 `handle(...)`, 이어서 `doHandle(...)`을 호출한다. 누락 또는 미등록 `serviceId`는 업무 예외다.
6. **업무 계층이 유스케이스를 수행한다.** Handler는 거래 분기와 Facade 호출만 맡고, Facade는 DTO 변환·유스케이스 조정, Service는 업무 흐름, Rule은 검증·계산, DAO/Mapper는 데이터 접근을 맡는다. 이 계층의 DB·외부 연동 경계는 온라인 처리 경계와 별도로 설계한다.
7. **ETF가 결과를 마감한다.** 성공은 `ETF.success(...)`가 멱등성 성공, 거래 로그 종료, 감사 로그, 메트릭 후 `S0000` 응답을 만든다. 업무 예외는 `ETF.businessFail(...)`, 예상하지 못한 예외는 `ETF.systemError(...)`가 같은 마감 성격의 실패 처리를 수행한다.
8. **TCF가 ThreadLocal 성격의 상태를 정리한다.** 모든 성공·실패 경로 뒤 `finally`에서 Context, 인증, Timeout, MDC를 비운다. 온라인 Timeout 워커는 Snapshot을 사용하므로 업무 코드가 별도 스레드를 만들면 이 정리가 자동 전파된다고 가정해서는 안 된다.

**근거 소스(현재 구현)**: `tcf-core/.../processor/STF.java`, `tcf-core/.../dispatch/TransactionDispatcher.java`, `tcf-core/.../transaction/TransactionHandler.java`, `tcf-core/.../processor/ETF.java`.

## 5. 계층별 책임과 금지사항

| 계층 | 현재 구현에서 확인한 책임 | 개발 표준: 책임과 금지사항 |
| --- | --- | --- |
| Controller/Gateway | Controller는 Header·경로·클라이언트 IP를 보완하고, Gateway는 표준 요청을 만들어 `TCF.process()`로 위임한다. | 업무 DB 트랜잭션을 시작하지 않는다. Controller/Gateway에서 Service를 직접 호출하거나 업무 SQL을 작성하지 않는다. |
| STF | 검증, Context·MDC 설정, 인증·권한, 거래통제, Timeout 정책, 멱등성·거래 로그 시작을 수행한다. | 업무 데이터의 등록·수정·삭제를 수행하지 않는다. 업무 규칙을 복제하지 않는다. |
| TCF | STF, Dispatcher, ETF 및 성공·업무 실패·시스템 실패 경로를 조정하고 종료 상태를 정리한다. | 업무 DB 트랜잭션의 보편 경계로 사용하지 않는다. 예외를 임의의 성공 응답으로 바꾸지 않는다. |
| Online Timeout Executor | Dispatcher 호출을 정책 기반 온라인 Timeout으로 감싸며 Context Snapshot을 전달한다. | 클라이언트 Timeout, DB Rollback 완료, 원격 시스템 취소를 같은 사건으로 간주하지 않는다. |
| Dispatcher/Handler | `serviceId`를 Handler에 매핑하고 Handler는 `doHandle(...)`에서 거래를 분기한다. | Handler에 `@Transactional`, 직접 SQL, 복잡한 업무 흐름, 외부 연동 조합을 두지 않는다. |
| Facade | 기존 업무 모듈에서 Handler와 Service 사이의 변환·조정 지점으로 사용된다. | 여러 Service를 하나의 원자적 유스케이스로 묶어야 하면 명시적인 DB 트랜잭션 경계 후보로 삼는다. |
| Service | 업무 흐름과 상태 변경을 담당한다. | 기본적인 DB 트랜잭션 경계다. 변경 유스케이스의 Commit·Rollback 의도를 이 계층 또는 유스케이스 Facade에 명시한다. |
| Rule | 업무 검증·계산을 담당한다. | 가능한 한 무상태·무트랜잭션으로 둔다. 데이터 변경과 Commit 제어를 하지 않는다. |
| DAO/Mapper | JDBC 또는 MyBatis로 데이터에 접근한다. | Statement 실행만 담당하며 Commit·Rollback 또는 트랜잭션 시작을 직접 제어하지 않는다. |
| ETF | 표준 응답, 멱등성, 거래 로그, 감사 로그, 메트릭을 마감한다. | 업무 DB 결과를 다시 변경하거나 업무 실패를 숨기지 않는다. |

`@Transactional` 위치는 현재 모든 업무 코드에서 하나로 강제되는 규칙이 아니다. 예를 들어 `tcf-om`의 일부 Facade는 이미 `@Transactional`을 사용하지만, 위 표의 Controller/Handler 금지와 Service 또는 유스케이스 Facade 경계는 신규·변경 거래에 적용하는 **개발 표준**이다.

## 6. DB 트랜잭션 경계

### 현재 구현

TCF 자체는 업무 DB 트랜잭션을 시작하지 않는다. DB 트랜잭션은 업무 Spring Bean의 `@Transactional` 또는 `PolicyDrivenTransactionExecutor`가 사용하는 `TransactionTemplate`에 의해 시작될 때만 생긴다. Timeout 정책이 활성화되면 `TcfTimeoutTransactionManagementConfiguration`은 `PolicyDrivenTransactionAttributeSource`를 Spring Transaction Advisor에 연결하고, 현재 `TimeoutContextHolder`의 `txTimeoutSec`로 `@Transactional`의 Timeout 값을 대체한다.

이는 “모든 TCF 온라인 거래가 하나의 DB 트랜잭션”이라는 의미가 아니다. 어떤 Handler 경로에 트랜잭션 AOP 또는 `TransactionTemplate`이 없다면 온라인 처리·거래 로그·ETF는 실행되어도 업무 DB 트랜잭션은 시작되지 않는다. 반대로 한 유스케이스가 의도적으로 독립 경계를 사용하면 하나의 온라인 거래 안에 복수의 DB 트랜잭션이 생길 수 있다.

MyBatis는 `PolicyDrivenQueryTimeoutInterceptor`가 현재 Timeout Context의 `dbQueryTimeoutSec`로 각 `MappedStatement` Timeout을 설정한다. 이는 개별 Statement의 시간 제한이며, JDBC DAO의 모든 질의에 자동 적용되는 공통 인터셉터는 이 소스에서 확인되지 않는다.

**근거 소스(현재 구현)**: `tcf-web/.../TcfTimeoutTransactionManagementConfiguration.java`, `tcf-web/.../PolicyDrivenTransactionAttributeSource.java`, `tcf-web/.../PolicyDrivenTransactionExecutor.java`, `tcf-web/.../PolicyDrivenQueryTimeoutInterceptor.java`.

### 개발 표준

- 변경 유스케이스는 Service 또는 유스케이스 Facade의 public Spring Bean 메서드에 하나의 명확한 `@Transactional` 경계를 둔다. 정상 반환이면 Commit, Runtime Exception이 경계를 통과하면 기본 Rollback이라는 Spring 규칙을 전제로 예외 계약을 설계한다.
- 여러 Service의 변경을 하나의 원자적 업무 단위로 묶어야 하면 Facade에 경계를 둔다. 한 Service의 업무 상태 변경이면 Service에 둔다. 둘 다에 중복 경계를 두지 않는다.
- Controller, Gateway, Handler, Rule, DAO/Mapper에는 업무 DB 트랜잭션을 선언하지 않는다. 특히 Handler는 Timeout 워커에서 호출될 수 있으므로 거래 분기만 담당한다.
- `@Transactional`은 Spring 프록시 호출에서 적용된다. 같은 클래스 내부 호출, `private` 메서드 호출, 프록시 밖에서 만든 객체 호출에는 적용되지 않으므로 경계 메서드는 외부 Bean 호출로 설계한다.
- 외부 서비스 호출은 로컬 DB 트랜잭션에 포함되어도 원격 시스템과 원자화되지 않는다. 외부 호출 Timeout 또는 실패 후에는 멱등성, 상태 확인, 재시도 또는 보상 정책을 유스케이스에 명시한다.

## 7. 조회·등록·수정·삭제 처리 기준

| 처리 유형 | 개발 표준의 DB 트랜잭션 기준 | DB 질의·외부 연동 주의사항 |
| --- | --- | --- |
| 조회 | Service 또는 유스케이스 Facade에 `@Transactional(readOnly = true)`를 기본으로 검토한다. 데이터소스·조회 구현 특성상 불필요하면 경계를 생략한 사유를 남긴다. | MyBatis 조회도 개별 Query Timeout 대상이다. 조회 결과를 변경하거나 지연 로딩 등으로 의도치 않은 쓰기를 만들지 않는다. |
| 등록 | 등록 전 검증부터 필요한 여러 INSERT/UPDATE까지를 하나의 변경 유스케이스 경계에 둔다. | ID 생성, 중복 검사와 INSERT가 원자성을 필요로 하는지 확인한다. 외부 호출 성공만으로 DB Commit을 판단하지 않는다. |
| 수정 | 변경 대상 검증, 동시성 조건 확인, 상태 변경을 같은 변경 경계에 둔다. | 영향을 받은 행 수와 낙관적 잠금 등 동시성 규칙을 업무 계약으로 검증한다. Timeout 뒤 결과를 추정하지 말고 상태를 확인한다. |
| 삭제 | 삭제 가능 여부 검증과 삭제 또는 논리 삭제를 같은 변경 경계에 둔다. | 참조 무결성, 복구·감사 요구와 외부 시스템 잔존 상태를 먼저 검토한다. |

조회·등록·수정·삭제 모두 Handler는 `serviceId` 분기와 Facade 호출만 수행한다. Facade·Service는 DTO 변환과 유스케이스를 조정하고, Rule은 검증·계산, DAO/Mapper는 파라미터 바인딩된 데이터 접근만 담당한다. DB 질의 Timeout이나 온라인 Timeout이 발생한 경우에도 응답 수신 시점만으로 Commit·Rollback 또는 원격 처리 결과를 단정하지 않는다.

## 8. Commit과 Rollback 규칙

### 현재 구현

TCF는 업무 DB 트랜잭션을 직접 시작하거나 Commit·Rollback하지 않는다. Spring `@Transactional` 프록시 또는 `PolicyDrivenTransactionExecutor`의 `TransactionTemplate`이 경계가 될 때만 로컬 DB 트랜잭션이 생긴다. 정상 반환이면 해당 경계의 Transaction Manager가 Commit을 시도한다.

`BusinessException`은 `RuntimeException`을 상속한다. 따라서 이 예외가 활성 `@Transactional` 프록시 경계를 통과하면, 별도 `noRollbackFor` 규칙이 없는 한 Spring의 기본 Runtime Exception Rollback 규칙 대상이다. `PolicyDrivenTransactionAttributeSource`는 `@Transactional`에서 해석한 기존 propagation, isolation, readOnly 및 rollback rule을 복사하고 `TimeoutContextHolder`의 `txTimeoutSec`만 대체한다. 즉, 정책 timeout은 기존 rollback 규칙을 제거하지 않는다.

`PolicyDrivenTransactionExecutor`도 `TransactionTemplate`을 만들어 timeout을 설정하고 supplier를 실행한다. supplier가 예외를 밖으로 전파하면 `TransactionTemplate`의 예외 규칙에 따라 완료되며, TCF가 뒤에서 ETF 오류 응답을 조립하는 일은 이미 끝난 DB 트랜잭션 결정을 되돌리지 않는다.

### 개발 표준

| 상황 | Commit 또는 Rollback 의도 |
| --- | --- |
| 정상 반환 | 변경 유스케이스가 정상 완료됐을 때만 Commit한다. |
| `BusinessException` 전파 | 기본 Runtime Exception Rollback을 사용한다. 특정 업무 오류를 Commit해야 한다면 `noRollbackFor`와 그 정합성 근거를 명시한다. |
| 예상하지 못한 Runtime Exception 전파 | Rollback을 기대하고 표준 시스템 오류로 변환한다. |
| checked exception 전파 | Spring 기본 규칙에서는 Commit될 수 있으므로, Rollback이 필요하면 `rollbackFor`를 명시하거나 Runtime Exception으로 계약을 통일한다. |
| 예외를 잡아 정상 반환 | 프록시에는 정상 완료로 보이므로 Commit될 수 있다. 복구하지 못한 예외를 성공처럼 삼키지 않는다. |

자기 자신 호출(self-invocation), `private` 메서드, Spring Bean 밖에서 만든 객체 호출은 프록시 경계를 거치지 않는다. 비동기 작업도 호출자 DB 트랜잭션에 자동 참여하지 않는다. 이는 현재 TCF가 보장하는 기능이 아니라 Spring 프록시 방식에서 피해야 할 설계 위험이므로, 트랜잭션 메서드는 다른 Spring Bean의 public 경계로 호출하는 것을 **개발 표준**으로 한다.

**근거 소스(현재 구현)**: `tcf-core/.../error/BusinessException.java`, `tcf-web/.../PolicyDrivenTransactionAttributeSource.java`, `tcf-web/.../PolicyDrivenTransactionExecutor.java`.

## 9. 예외별 처리 방식

| 예외 또는 상태 | 현재 구현의 온라인 응답·후처리 | DB 트랜잭션 판단 |
| --- | --- | --- |
| 정상 반환 | `ETF.success`가 멱등성 SUCCESS, 거래 로그·감사·메트릭을 마감하고 `S0000`을 만든다. | 활성 경계가 있으면 정상 Commit 경로다. |
| `BusinessException` | TCF가 `ETF.businessFail`로 `E0001`과 업무 errorCode를 만든다. | 활성 프록시 경계를 통과했다면 기본 Rollback 대상이다. |
| 시스템 예외 | Timeout 변환 가능 여부를 먼저 확인하고, 아니면 `ETF.systemError`가 시스템 오류 응답을 만든다. | 활성 프록시 경계를 통과하면 기본 Rollback 대상이다. |
| Transaction/Query Timeout 예외 | `TimeoutExceptionResolver`가 `TIMEOUT_TRANSACTION` 또는 `TIMEOUT_DB_QUERY` `BusinessException`으로 바꿔 업무 실패 경로로 응답한다. | 실제 Rollback 여부는 활성 DB 경계와 JDBC/DB의 완료 결과를 확인한다. |
| checked exception | TCF에는 시스템 오류로 도달할 수 있다. | 기본 Commit 가능성이 있으므로 개발 표준대로 명시적 rollback rule이 필요하다. |
| 예외를 삼킨 뒤 정상 반환 | ETF는 성공으로 처리할 수 있다. | Commit될 수 있으므로 실패를 숨기지 않는다. |
| self-invocation·private 호출 | TCF가 별도 감지하지 않는다. | 선언한 `@Transactional`이 적용되지 않을 수 있다. |
| 별도 비동기 실행 | TCF가 생성하지 않은 스레드에는 컨텍스트·트랜잭션이 자동 전파되지 않는다. | 호출자 트랜잭션과 독립으로 설계·확인한다. |

## 10. 3단계 Timeout

STF는 거래통제 검사 뒤 timeout 정책을 조회·`TimeoutContextHolder`와 `TransactionContext`에 바인딩하고, 그 뒤 멱등성·거래 로그 시작을 수행한다. 이 정책은 Dispatcher 호출을 감싼 Online Timeout, 프록시 `@Transactional`의 Transaction Timeout, MyBatis Mapper Statement의 DB Query Timeout에 각각 사용된다.

| 구분 | 정책 값 | 적용 지점 | 제한 범위 | Timeout 후 상태 | 운영 확인 |
| --- | --- | --- | --- | --- | --- |
| Online Timeout | `ONLINE_TIMEOUT_SEC` (기본 5초) | `OnlineTransactionTimeoutExecutor`: Dispatcher를 워커에 제출하고 `Future.get` | Handler부터 하위 업무 호출 대기 구간. STF·ETF 자체는 이 Future 밖이다. | 초과 시 `future.cancel(true)` 후 `TIMEOUT_ONLINE` `BusinessException` 응답 경로다. interrupt 요청일 뿐 워커·DB·원격 처리의 즉시 중단은 보장하지 않는다. | `guid`로 거래 로그·런타임 모니터·업무 상태를 함께 확인한다. |
| Transaction Timeout | `TX_TIMEOUT_SEC` (기본 5초) | 정책 기반 Transaction Attribute Source 또는 `PolicyDrivenTransactionExecutor` | 활성 Spring DB 트랜잭션 경계 | `TransactionTimedOutException` 계열이면 표준 timeout 오류로 변환될 수 있다. Commit/Rollback은 Transaction Manager와 실제 경계에 달렸다. | `@Transactional`/Template 경계, 정책값, DB 완료 상태를 확인한다. |
| DB Query Timeout | `DB_QUERY_TIMEOUT_SEC` (기본 3초) | `PolicyDrivenQueryTimeoutInterceptor`가 MyBatis `MappedStatement` timeout을 복사 설정 | MyBatis Mapper의 개별 `query`/`update` Statement | SQL/JDBC timeout은 `TIMEOUT_DB_QUERY`로 변환될 수 있다. JDBC DAO 전체에 같은 공통 적용은 이 소스에서 확인되지 않는다. | Mapper timeout, DB 취소·잠금·실행 이력과 트랜잭션 완료 상태를 확인한다. |

정책 적용의 실제 호출 순서는 **STF의 timeout 정책 바인딩 → Online Timeout 워커 Snapshot 전파 → 프록시 Transaction Attribute timeout 조회 또는 Template timeout 설정 → MyBatis Statement timeout 조회**다. 각 계층은 같은 `TimeoutPolicy`를 참조하지만, 어느 timeout이 먼저 관측될지는 수행 위치와 DB·드라이버 반응에 따라 달라진다.

따라서 Online Timeout 응답, 워커 interrupt 요청, DB 트랜잭션 완료, DB Rollback, 원격 시스템 취소는 서로 다른 관측값이다. 하나가 발생했다고 나머지가 완료됐다고 판단하지 않는다.

**근거 소스(현재 구현)**: `tcf-core/.../timeout/TimeoutPolicyService.java`, `OnlineTransactionTimeoutExecutor.java`, `TimeoutThreadContext.java`, `TimeoutExceptionResolver.java`, `tcf-web/.../PolicyDrivenTransactionAttributeSource.java`, `PolicyDrivenTransactionExecutor.java`, `PolicyDrivenQueryTimeoutInterceptor.java`.

## 11. 외부 서비스 연동과 트랜잭션

### 현재 구현

서비스 간 HTTP/JSON 호출은 `tcf-eai`의 `TcfServiceClient`/`DefaultTcfServiceClient`와 업무 `client` Adapter를 사용한다. 호출자는 `TransactionContext`를 전달해 GUID·Trace ID·사용자·호출자 정보를 표준 Header에 전파한다. `RestClient` 연결·읽기 timeout은 `nsight.integration` 설정에서 따로 정하며, 응답의 `resultCode == S0000`만 성공이다. 업무 실패는 `IntegrationBusinessException`, 연결·전문 오류는 `IntegrationException`, 응답 timeout은 `IntegrationTimeoutException`으로 전파된다.

이 HTTP 호출은 호출자 로컬 DB 트랜잭션과 분산 원자 트랜잭션이 아니다. 원격 성공 뒤 로컬 Rollback, 또는 로컬 Commit 뒤 원격 실패가 가능하다. 현재 소스에는 two-phase commit, Saga 또는 Outbox를 자동 수행하는 구현이 확인되지 않는다.

### 개발 표준

- 외부 호출은 `client` Adapter에 감추고 Service/Facade가 도메인 결과만 다룬다. Handler가 URL·전문·재시도 규칙을 조합하지 않는다.
- 원격 결과가 불명확한 timeout 뒤에는 상태 조회 또는 멱등 키 기반 확인을 먼저 한다. 안전한 경우에만 재시도하고, 원격 성공·로컬 실패에는 보상 또는 후속 정합성 절차를 유스케이스별로 정한다.
- 로컬 트랜잭션을 오래 잡은 채 원격 대기를 하는 필요성과 잠금 영향을 검토한다. 필요한 보상·상태 전이·운영 소유자는 연동 계약에 함께 기록한다.

**근거 소스(현재 구현)**: `tcf-eai/.../DefaultTcfServiceClient.java`, `HeaderPropagationHelper.java`, `ResponseResultValidator.java`, `zdocs-1/architecture/46-service-integration-contract.md`.

## 12. 멱등성·재시도·중복 방지

### 현재 구현

STF는 거래통제와 timeout 정책 뒤 `checkAndMarkProcessing`을 호출한다. 기본 `InMemoryIdempotencyChecker`는 `idempotencyKey`가 있으면 그것을, 없으면 GUID를 키로 사용하고 PROCESSING 상태의 동시 요청만 `DUPLICATE_REQUEST`로 차단한다. ETF는 성공 시 SUCCESS, 업무·시스템 실패 시 FAIL을 기록한다.

이 구현은 프로세스 메모리 기반이다. 재기동·다중 인스턴스 간 중복 방지, 완료 응답 재전송, 영속 상태 조회는 확인되지 않는다. 또한 SUCCESS·FAIL 상태의 같은 키는 PROCESSING 상태가 아니므로 현재 구현만으로 완료된 요청을 재실행 불가로 만들지는 않는다.

### 개발 표준

- 변경 거래는 클라이언트 또는 업무가 정의한 안정적인 멱등 키와 결과·상태 조회 계약을 둔다. GUID만으로 장기 중복 방지 정책을 대체하지 않는다.
- 재시도는 조회 또는 명시적으로 멱등한 작업, 그리고 원격 side effect·처리 상태를 확인할 수 있는 경우에 한정한다. CREATE/UPDATE/DELETE는 무조건 재시도하지 않는다.
- 재시도에는 동일 업무 키·상관관계 ID, 제한된 횟수와 backoff, 중복 실행 시 반환할 결과를 명시한다. 현재 `tcf-eai` 기본 Client에 자동 Retry는 없다.

## 13. 거래통제·권한·세션

STF의 실제 사전 처리 순서는 Header 검증·GUID/Trace 설정·Context/MDC 등록 후 **세션 검증 → 인증 Context 검증 → 권한 검증 → 거래통제 → Timeout 정책 → 멱등성 PROCESSING → 거래 로그 시작**이다. 거래통제가 활성화되면 `TransactionControlService`는 필수 통제 Header를 검증하고 Repository가 없으면 거부하며, 일치한 차단 규칙은 `TXCTRL_NOT_ALLOWED` 업무 예외로 처리한다. 설정상 면제 serviceId는 통제를 건너뛰므로, 업무 코드가 임의로 면제 범위를 넓히지 않는다.

JWT 웹 필터가 활성화된 요청은 인증 Context를 request attribute와 Holder에 넣고 `finally`에서 제거한다. STF의 인증 Context 검증은 Header와 claim의 정합성을 확인한다. 권한·세션·거래통제 실패는 Dispatcher 이전에 중단되므로, 업무 Handler에서 같은 통제를 우회하거나 다시 구현하지 않는다.

## 14. 로그·감사·메트릭

현재 구현은 STF에서 `guid`, `traceId`, `serviceId`, `userId`, `branchId`를 MDC에 넣는다. 거래 로그는 TX_START/TX_END에 식별자·결과·경과시간을 기록하고, 설정과 Repository가 있으면 DB에 저장한다. ETF는 성공·업무 실패·시스템 실패마다 감사 로그와 메트릭 기록을 호출한다. 런타임 모니터가 활성화되면 TCF 시작·종료 hook이 활성 거래 등록·완료·느린 거래 추적을 수행한다.

개발 표준으로 로그에는 비밀번호, access/refresh token, 세션 식별자, 개인정보 원문, 전문 body 전체, SQL과 내부 stack trace를 남기지 않는다. 운영 확인은 `guid`와 `traceId`로 호출 측·피호출 측 로그, 거래 로그, timeout·DB 상태를 상호 대조하며, 클라이언트 응답에는 내부 예외를 노출하지 않는다.

## 15. ThreadLocal·MDC 정리

TCF는 성공·업무 실패·시스템 실패와 STF 실패를 포함하는 `finally`에서 Runtime Hook 호출 뒤 `TransactionContextHolder`, `AuthenticationContextHolder`, `TimeoutContextHolder`, MDC를 정리한다. HTTP 요청 바깥쪽의 `GuidMdcCleanupFilter`도 `finally`에서 MDC 및 웹 인증 Holder를 비운다. JWT 필터 역시 자신의 `finally`에서 인증 Holder를 정리한다.

Online Timeout 워커는 Snapshot으로 Timeout·Transaction Context, MDC, RequestAttributes를 전파하고, 워커 `finally`에서 RequestAttributes reset과 해당 Holder·MDC 정리를 수행한다. 이는 TCF가 만든 워커에만 해당한다. 업무 코드가 별도 Executor·비동기 작업을 만들면 Context/MDC를 명시적으로 전파하고 모든 성공·실패·취소 종료 경로에서 `finally`로 제거해야 한다.

| checked exception Rollback | 별도 전역 rollback rule은 확인되지 않는다. | `rollbackFor` 또는 Runtime Exception 계약을 명시한다. | 실패했는데 Commit될 수 있다. | checked exception 경로를 테스트하고 표준화한다. |
| swallowed exception | TCF는 정상 반환을 성공으로 처리한다. | 복구하지 못한 예외를 정상 반환으로 바꾸지 않는다. | 부분 변경 Commit·성공 응답이 발생할 수 있다. | 예외를 전파하거나 명시적인 Rollback-only·보상 절차를 둔다. |
| self-invocation | 프록시 적용 여부를 TCF가 검사하지 않는다. | 다른 Bean의 public 메서드로 TX 경계를 호출한다. | annotation이 무효가 될 수 있다. | 아키텍처 검사와 프록시 적용 테스트를 추가한다. |
| Online Timeout 취소 | `Future.cancel(true)`와 업무 실패 응답은 구현되어 있다. | 응답·interrupt·DB 완료·원격 취소를 분리해 운영한다. | 워커 또는 원격 처리의 잔존 결과가 불명확하다. | 취소 협조 코드, 상태 조회·보상, timeout 후 운영 점검 절차를 마련한다. |
| 외부 호출 부분 성공 | `tcf-eai` HTTP 호출은 로컬 DB와 독립이다. | 유스케이스별 보상·상태 전이·재처리 계약을 둔다. | 원격·로컬 상태 불일치가 남는다. | Outbox/Saga 필요성은 별도 설계로 결정한다. |
| 재시도 적격성 | 메모리 기반 PROCESSING 중복 차단이며 자동 Retry는 확인되지 않는다. | 멱등 키·상태 확인이 있는 안전한 작업만 제한 재시도한다. | 이중 변경·다중 인스턴스 중복이 가능하다. | 영속 멱등 저장소와 결과 재조회 정책을 검토한다. |
| ThreadLocal/MDC 정리 | TCF·웹 필터·JWT 필터·Online 워커에 `finally` 정리가 있다. | 업무 생성 스레드도 모든 종료 경로에서 정리한다. | 스레드풀 재사용 시 다른 요청의 보안·추적 정보가 섞일 수 있다. | 비동기 Context 전파/정리 공통 래퍼와 누수 테스트를 추가한다. |
