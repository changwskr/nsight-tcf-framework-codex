현재 NSIGHT TCF의 애플리케이션 레이어드 아키텍처는 일반적인 `Controller → Service → Repository` 구조가 아니라, **TCF 공통 파이프라인과 업무 BTF 계층을 분리한 구조**입니다.

기준 문서는 [01-application-layer.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/zdocs-1/architecture/01-application-layer.md>), [35-BTF.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/zdocs-1/architecture/35-BTF.md:21>), [29-facade.md](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/zdocs-1/architecture/29-facade.md:15>)입니다.

## 1. 전체 구조

```text
Client / UI
  → OnlineTransactionController
  → TCF
      → STF
      → TransactionDispatcher
      → BTF
          → Handler
          → Facade
          → Service
              ├→ Rule
              ├→ DAO → Mapper → DB
              └→ Client → 외부 서비스
      → ETF
  → StandardResponse
```

중요한 점은 `Rule → DAO`가 일렬로 호출되는 구조가 아니라는 것입니다.

정확한 업무 내부 흐름은 다음에 가깝습니다.

```text
Handler
  → Facade
    → Service
      ├→ Rule
      ├→ DAO
      │   └→ Mapper
      └→ Client
```

Service가 Rule 검증 결과를 사용해 DAO 또는 Client를 호출합니다. Rule이 DAO를 직접 호출하지 않습니다.

## 2. 프레임워크 계층과 업무 계층 분리

### TCF 공통 파이프라인

다음 책임은 업무 모듈이 구현하지 않습니다.

- 표준 HTTP 진입
- Header 검증
- GUID·TraceId·MDC
- 세션과 권한 검증
- 멱등성
- 거래통제
- Online·Transaction·DB Query Timeout
- 거래로그
- 표준 성공·업무 실패·시스템 오류 응답
- 감사와 메트릭

```text
OnlineTransactionController
→ TCF
→ STF
→ Dispatcher
→ BTF
→ ETF
```

### BTF 업무 계층

업무 개발자가 구현하는 영역입니다.

```text
Handler
→ Facade
→ Service
├→ Rule
├→ DAO → Mapper
└→ Client
```

## 4. Handler

Handler는 TCF와 업무 애플리케이션을 연결하는 거래 진입점입니다.

책임:

- `serviceIds()`로 거래 등록
- ServiceId 기준 거래 분기
- 표준 요청 Body를 Request DTO로 변환
- Facade 호출
- Facade 결과를 응답 Body로 반환

금지:

- SQL 실행
- Mapper·DAO 직접 호출
- 복잡한 업무 규칙
- 트랜잭션 제어
- 세션·권한·Timeout 재구현
- 여러 Domain 소유

```java
@Component
public class SvCustomerHandler implements TransactionHandler {

    @Override
    public Collection<String> serviceIds() {
        return List.of(
            "SV.Customer.selectList",
            "SV.Customer.selectDetail",
            "SV.Customer.create"
        );
    }

    @Override
    public Object doHandle(...) {
        return switch (serviceId) {
            case "SV.Customer.selectList" -> facade.selectList(...);
            case "SV.Customer.selectDetail" -> facade.selectDetail(...);
            case "SV.Customer.create" -> facade.create(...);
            default -> throw ...;
        };
    }
}
```

원칙은 **Domain당 Handler 하나**입니다.

## 5. Facade

Facade는 하나의 거래 또는 유스케이스 경계입니다.

책임:

- Request DTO 조정
- 여러 Service 호출 순서 조정
- 트랜잭션 경계
- Service 결과를 Response DTO로 변환
- 한 유스케이스의 전체 성공·실패 원자성 보장

금지:

- Mapper 직접 호출
- SQL 작성
- 세부 업무 계산
- 데이터 접근 구현
- HTTP 요청·응답 객체 의존

```java
@Transactional(readOnly = true)
public CustomerSelectListResponse selectList(
        CustomerSelectListRequest request) {
    return CustomerSelectListResponse.from(
        customerService.selectList(request.toCriteria()));
}

@Transactional
public CustomerCreateResponse create(
        CustomerCreateRequest request) {
    return CustomerCreateResponse.from(
        customerService.create(request));
}
```

트랜잭션 경계는 Facade에 두는 것이 현재 표준입니다.

- 조회: `@Transactional(readOnly = true)`
- 등록·수정·삭제: `@Transactional`

근거: [온라인 트랜잭션 경계](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/zdocs-1/architecture/14-online-arc.md:179>)

## 6. Service

Service는 Domain의 업무 흐름을 구현합니다.

책임:

- Rule 호출
- 조회·등록·수정·삭제 흐름 구성
- DAO와 Client 호출
- 상태 전이
- 여러 검증과 데이터 작업의 순서 결정
- 업무 예외 발생

금지:

- Handler처럼 ServiceId 분기
- Mapper 직접 호출
- HTTP 객체 의존
- 트랜잭션 경계의 임의 분산
- TCF 공통 정책 재구현

```java
public Customer create(CustomerCreateRequest request) {
    rule.validateCreate(request);

    if (dao.existsByCustomerId(request.customerId())) {
        throw new CustomerAlreadyExistsException(...);
    }

    dao.insertCustomer(request);
    return dao.selectCustomerById(request.customerId());
}
```

현재 CRUD Codegen 규칙에서는 다음 호출이 금지되어 있습니다.

```text
Service → Mapper
```

항상 다음을 사용합니다.

```text
Service → DAO → Mapper
```

## 7. Rule

Rule은 검증과 계산을 담당하는 업무 규칙 계층입니다.

책임:

- 필수값 이외의 업무 검증
- 값 범위와 상태 검증
- 업무 계산
- 정규화
- 상태 전이 가능 여부 판정
- 재사용 가능한 Domain 정책

금지:

- DAO·Mapper 호출
- 트랜잭션 제어
- HTTP 객체 의존
- 외부 API 호출
- 로그·응답 조립
- 전체 유스케이스 순서 조정

```java
public void validateCreate(CustomerCreateRequest request) {
    requireCustomerId(request.customerId());
    validateName(request.customerName());
}

public boolean canDeactivate(Customer customer) {
    return customer.active() && !customer.hasOpenContract();
}
```

Rule은 가능한 한 입력과 출력이 명확하고 단위 테스트가 쉬운 구조로 만듭니다.

## 8. DAO

DAO는 Service와 Mapper 사이의 데이터 접근 추상화 계층입니다.

책임:

- Mapper 호출
- Mapper 파라미터 구성
- 영속성 결과 변환
- 여러 Mapper 호출을 하나의 데이터 접근 연산으로 캡슐화
- DB 기술 세부사항을 Service에서 숨김

금지:

- 업무 규칙 판단
- 트랜잭션 경계
- Service 호출
- HTTP 객체 사용
- 다른 Domain의 유스케이스 실행

```java
@Repository
public class SvCustomerDao {

    private final SvCustomerMapper mapper;

    public List<CustomerRow> selectCustomerList(
            CustomerSearchCriteria criteria) {
        return mapper.selectCustomerList(criteria);
    }

    public int insertCustomer(CustomerCreateRow row) {
        return mapper.insertCustomer(row);
    }
}
```

DAO에는 트랜잭션 경계를 두지 않습니다.

근거: [MyBatis 계층](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/zdocs-1/architecture/26-mybatis.md:290>)

## 9. Mapper

Mapper는 SQL 실행 전용 계층입니다.

책임:

- MyBatis 인터페이스
- SQL ID 계약
- 파라미터 바인딩
- ResultMap 또는 Row 매핑
- DB Query Timeout 적용 지점

금지:

- 업무 규칙
- 트랜잭션 제어
- Service 호출
- 동적 테이블·컬럼에 검증되지 않은 외부 입력 사용
- 내부 예외를 응답 형태로 변환

```java
public interface SvCustomerMapper {

    List<CustomerRow> selectCustomerList(
        CustomerSearchCriteria criteria);

    CustomerRow selectCustomerById(String customerId);

    int insertCustomer(CustomerCreateRow row);
}
```

```xml
<select id="selectCustomerList"
        resultType="CustomerRow">
    SELECT ...
</select>
```

다음 정합성이 필수입니다.

```text
Mapper method name == XML SQL id
```

## 10. Client

Client는 외부 API 또는 다른 업무 WAR 호출을 담당합니다.

책임:

- 외부 계약 DTO
- URL·ServiceId·Header 구성
- `tcf-eai`를 통한 업무 간 호출
- 외부 오류를 내부 연동 오류로 변환
- Timeout과 재시도 정책 적용

```text
Service
→ Client
→ tcf-eai
→ 대상 ServiceId
```

금지:

- 타 업무 모듈 Java 클래스 직접 참조
- Client 안에 호출자 업무 규칙 구현
- 외부 응답 DTO를 내부 Response로 그대로 노출
- Secret 하드코딩

## 11. DTO 흐름

DTO는 계층별 책임에 맞춰 구분합니다.

```text
StandardRequest.body
→ Request DTO
→ Criteria / Command
→ Row
→ Domain Result
→ Response DTO
→ StandardResponse.body
```

권장 역할:

| DTO         | 책임                           |
| ----------- | ------------------------------ |
| `Request`   | 거래 입력 계약                 |
| `Response`  | 거래 출력 계약                 |
| `Criteria`  | 조회 조건                      |
| `Row`       | DB 조회 결과                   |
| `Result`    | 외부 연동 또는 유스케이스 결과 |
| Domain 객체 | 업무 상태와 의미               |

하나의 DTO를 Handler·Service·Mapper·외부 연동 전체에서 공유하지 않습니다.

## 12. 허용 의존 방향

```text
Handler → Facade
Facade → Service
Service → Rule
Service → DAO
Service → Client
DAO → Mapper
```

선택적으로 다음은 가능합니다.

```text
Facade → 여러 Service
Service → 같은 Domain의 보조 Service
Service → 공통 Cache Service
Rule → 순수 값 객체·공통 검증 유틸
```

## 13. 금지 의존 방향

```text
Handler → Service
Handler → DAO
Handler → Mapper

Facade → Mapper
Rule → DAO
Rule → Mapper

Service → Mapper
DAO → Service
Mapper → DAO

업무 WAR → 다른 업무 WAR Java 클래스
하위 모듈 → 상위 업무 모듈
```

특히 CRUD 프롬프트에는 다음 구조 금지가 명시되어 있습니다.

```text
Handler → Mapper
Service → Mapper
Rule → DAO
업무별 Controller
```

## 14. Controller 정책

표준 온라인 거래에는 업무별 Controller를 만들지 않습니다.

```text
POST /{businessCode}/online
→ 공통 OnlineTransactionController
→ TCF
→ ServiceId Dispatcher
→ 업무 Handler
```

업무별 Controller가 허용되는 경우는 제한적입니다.

- multipart 파일 업로드·다운로드
- 브라우저 Relay
- Gateway Proxy
- Batch 운영 API
- 표준 전문으로 처리할 수 없는 비표준 REST
- 관리용 기술 API

이 경우에도 Controller는 HTTP 변환만 담당하고 업무 로직은 Service 계층으로 위임해야 합니다.

## 15. 오류 처리

계층별 오류 책임은 다음과 같습니다.

| 계층       | 오류 책임                               |
| ---------- | --------------------------------------- |
| Handler    | 알 수 없는 ServiceId, Request 변환 오류 |
| Facade     | 유스케이스 실패와 트랜잭션 Rollback     |
| Service    | 업무 예외                               |
| Rule       | 검증·상태 위반                          |
| DAO/Mapper | 영속성 예외 발생                        |
| Client     | 외부 연동 오류 변환                     |
| ETF        | 표준 응답·로그·메트릭 정리              |

내부 SQL, Stack Trace와 영속성 예외를 클라이언트 응답에 직접 노출하지 않습니다.

## 16. 테스트 구조

| 대상        | 주요 검증                          |
| ----------- | ---------------------------------- |
| Handler     | ServiceId 등록·분기·DTO 변환       |
| Facade      | 트랜잭션 경계·Service 조정         |
| Service     | 업무 흐름·DAO/Client 상호작용      |
| Rule        | 검증·계산·상태 전이                |
| DAO/Mapper  | SQL·파라미터·Row 매핑              |
| 구조 테스트 | 금지 의존 방향·업무 Controller     |
| 거래 테스트 | StandardRequest → StandardResponse |

## 17. 현재 정리가 필요한 부분

현재 큰 방향은 일관되지만 다음 항목은 공식화가 필요합니다.

1. 문서의 선형 표현

일부 문서는 다음처럼 표현합니다.

```text
Service → Rule → DAO
```

이 표현은 Rule이 DAO를 호출하는 것으로 오해될 수 있습니다. 다음처럼 고쳐야 합니다.

```text
Service
├→ Rule
└→ DAO → Mapper
```

2. Service와 Rule 경계

- 데이터 존재 확인을 Rule이 담당할지
- Service가 DAO 조회 후 Rule에 데이터를 전달할지

현재 구조상 후자가 적합합니다.

```text
Service → DAO 조회 → Rule 검증
```

3. Facade 필수 여부

표준 온라인 거래에서는 Facade가 필수지만, 일부 비표준 REST와 배치에는 Controller → Service 직접 호출 패턴이 존재합니다. 예외 조건을 명시해야 합니다.

4. Domain 객체 계층

현재 DTO·Map 중심 구현이 많아 Domain Entity 또는 Value Object 사용 기준이 명확하지 않습니다.

5. 조회 전용 구조

복잡한 화면 조회에서 기존 계층을 그대로 사용할지, `QueryService`·`QueryDao` 같은 읽기 전용 패턴을 허용할지 정해야 합니다.

현재 아키텍처의 핵심은 다음 한 문장으로 정리할 수 있습니다.

> TCF가 공통 거래 통제를 담당하고, 업무 코드는 Handler를 진입점으로 Facade에서 트랜잭션을 열어 Service가 Rule·DAO·Client를 조정하며, DAO가 Mapper를 통해 데이터에 접근한다.
