# NSIGHT TCF 예외 처리 방식

## 1. 목적과 적용 범위

이 문서는 NSIGHT TCF에서 예외가 발생한 지점부터 표준 응답, 거래 로그, 감사와 트랜잭션 종료까지 이어지는 처리 기준을 설명한다. 기준 문서는 [`05-exception.md`](../../zdocs-1/architecture/05-exception.md)이며, 실제 Java 구현과 테스트를 최종 근거로 사용한다.

다루는 범위는 업무·시스템·검증·Timeout·Spring MVC·서비스 연동 예외, 오류 코드, HTTP 상태, 로깅, 보안과 테스트다. DB Commit·Rollback의 상세 규칙은 [트랜잭션 처리 방식](2026-07-26-05-트랜잭션처리방식.md), 요청·응답 전문과 Relay 경로는 [메시지 처리 방식](2026-07-26-06-messaging.md)을 따른다.

정책 표기는 다음과 같다.

- **현재 구현**: 저장소에서 확인한 실제 동작
- **개발 표준**: 신규 코드와 변경 코드가 따라야 할 기준
- **개선 권고**: 현재 구현과 목표 계약의 차이를 해소할 후속 과제

## 2. 핵심 원칙과 용어

### 2.1 핵심 원칙

1. 업무적으로 예상한 거절과 시스템 장애를 구분한다.
2. 예외는 의미를 판단할 수 있는 계층에서 발생시키고 공통 경계에서 응답으로 변환한다.
3. Handler·Service가 예외를 임의 JSON이나 성공 응답으로 바꾸지 않는다.
4. 표준 거래의 성공 여부는 HTTP 상태만이 아니라 `result.resultCode`로 판정한다.
5. 공개 메시지와 내부 진단 정보를 분리한다.
6. 원인 예외는 `cause`와 서버 로그에 보존하되 클라이언트에는 노출하지 않는다.
7. Timeout 후에는 처리 완료 여부와 멱등성을 확인하기 전 재시도하지 않는다.
8. 예외 처리와 DB Rollback, 거래 로그 종료, 감사와 메트릭을 함께 검증한다.

### 2.2 용어

| 용어 | 의미 |
| --- | --- |
| 업무 예외 | 입력·상태·업무 규칙 때문에 정상적으로 거래를 거절한 예외 |
| 시스템 예외 | 결함, 인프라 장애, 예기치 않은 실행 실패를 나타내는 예외 |
| 공개 오류 | 클라이언트가 분기하거나 사용자에게 표시할 수 있는 코드와 메시지 |
| 내부 원인 | Stack Trace, SQL, 라이브러리 예외, 내부 경로처럼 서버 진단에만 쓰는 정보 |
| 변환 경계 | 예외를 `StandardResponse` 또는 경로별 HTTP 응답으로 바꾸는 TCF·ETF·Web Advice |
| 상관관계 ID | 요청, 응답과 로그를 잇는 `guid`와 `traceId` |
| 표준 실패 | `result.resultCode == "E0001"`이고 `errorCode`에 상세 원인이 있는 응답 |

## 3. 예외 처리 전체 생명주기

### 3.1 표준 TCF 경로

```text
HTTP 요청
  → OnlineTransactionController
  → TCF.process
      → STF: Header 정규화·공통 검증·거래통제
      → TransactionDispatcher: serviceId 라우팅
      → Handler → Facade → Service → Rule → DAO/Mapper
          ├─ BusinessException
          │    → TCF catch(BusinessException)
          │    → ETF.businessFail
          │    → E0001 + 업무 errorCode
          └─ Exception
               → TimeoutExceptionResolver 확인
                   ├─ Timeout → ETF.businessFail
                   └─ 그 외 → ETF.systemError
                               → E0001 + E-COM-SYS-0001
      → 거래 로그 종료·감사·메트릭·멱등 상태 반영
  → StandardResponse 직렬화
```

[`TCF.process`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/processor/TCF.java)는 `BusinessException`을 먼저 잡고, 나머지 `Exception`에서 Timeout 원인을 다시 판별한다. [`ETF`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/processor/ETF.java)는 성공·업무 실패·시스템 실패 응답을 조립하면서 거래 종료 부수 효과를 수행한다.

### 3.2 TCF 진입 전 웹 경로

```text
HTTP 요청
  → Spring MVC 역직렬화·Method 선택·Bean Validation
      ├─ BusinessException
      ├─ MethodArgumentNotValidException
      ├─ HttpRequestMethodNotSupportedException
      └─ 그 밖의 Exception
  → GlobalStandardExceptionHandler
  → StandardResponse 실패 응답
```

**현재 구현:** [`GlobalStandardExceptionHandler`](../../tcf-web/src/main/java/com/nh/nsight/tcf/web/entry/web/GlobalStandardExceptionHandler.java)는 위 예외를 `StandardResponse.fail`로 변환한다. 이 경로는 `TCF.process`와 ETF를 거치지 않으므로 ETF의 거래 로그 종료·감사·메트릭·멱등 상태 처리가 자동으로 실행된다고 가정하면 안 된다.

### 3.3 서비스 연동 경로

```text
호출 업무
  → DefaultTcfServiceClient
  → 대상 HTTP/JSON 호출
      ├─ S0000                  → IntegrationCallResult
      ├─ 대상 업무 실패         → IntegrationBusinessException
      ├─ Connect/Read Timeout   → IntegrationTimeoutException
      ├─ 메시지 구조 오류       → IntegrationException(MESSAGE)
      └─ 그 밖의 호출 실패      → IntegrationException(SYSTEM)
  → 호출 업무가 로컬 업무 의미에 맞게 변환 또는 전파
```

## 4. 예외 분류 체계

| 분류 | 대표 타입·상황 | 발생 의미 | 최종 처리 경계 | 재시도 기본값 |
| --- | --- | --- | --- | --- |
| 업무 예외 | `BusinessException` | 검증 실패, 상태 불일치, 권한·거래통제 거절 | `TCF → ETF.businessFail` 또는 Web Advice | 원인 수정 전 금지 |
| 시스템 예외 | `SystemException`, 일반 `Exception` | 결함, 실행 중단, DB·인프라 장애 | `TCF → ETF.systemError` | 자동 재시도 금지 |
| 전송·웹 예외 | 잘못된 JSON, MVC 검증, 미지원 Method | TCF 진입 전 요청 계약 실패 | Spring MVC·Web Advice | 요청 수정 전 금지 |
| Timeout 예외 | 온라인 거래, Connect·Read Timeout | 제한시간 안에 완료를 확인하지 못함 | Timeout Resolver 또는 EAI 예외 | 상태·멱등 확인 후 결정 |
| 연동 예외 | `IntegrationBusinessException`, `IntegrationException` | 대상 업무 거절 또는 통신·메시지 실패 | 호출 Client와 상위 업무 계층 | 유형별 정책 필요 |

예외 분류는 HTTP 상태나 Java 클래스 이름 하나만으로 결정하지 않는다. 발생 위치, 처리 완료 가능성, 대상 시스템의 응답 유무, 공개 가능한 오류 코드와 Rollback 영향을 함께 판단한다.

## 5. 핵심 예외 클래스의 역할

### 5.1 BusinessException

[`BusinessException`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/error/BusinessException.java)은 `errorCode`, 공개 가능한 메시지와 선택적인 `cause`를 갖는 `RuntimeException`이다.

- **현재 구현:** STF 검증, Dispatcher 라우팅, 세션·권한·거래통제, 멱등성, 업무 Rule과 Timeout 변환에서 사용한다.
- **개발 표준:** Service·Rule이 예상 가능한 업무 거절을 표현할 때 사용한다. `errorCode`는 안정적인 계약이어야 하며 Java 예외 메시지나 내부 기술명을 코드 대신 사용하지 않는다.
- 원인 예외를 업무 의미로 변환할 때는 `cause` 생성자를 사용해 진단 연결을 보존한다.

### 5.2 SystemException

[`SystemException`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/error/SystemException.java)은 시스템 오류 코드, 메시지와 필수 `cause`를 갖는 `RuntimeException`이다.

- **현재 구현:** 기준 문서에는 “정의만 존재”로 설명되어 있지만, 현재 [`OnlineTransactionTimeoutExecutor`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/timeout/OnlineTransactionTimeoutExecutor.java)는 작업 중단과 `ExecutionException`의 비업무 원인을 `SystemException`으로 변환한다.
- `TCF`에는 `SystemException` 전용 catch가 없으므로 일반 `Exception` 경로에 포함되며, Timeout Resolver가 별도 변환하지 않으면 `ETF.systemError`로 처리된다.
- **개발 표준:** 복구할 수 없는 기술 실패에 업무 코드를 부여하기 위해 `BusinessException`으로 위장하지 않는다. 시스템 예외의 공개 메시지는 공통 문구로 제한한다.

### 5.3 일반 Exception

- **현재 구현:** `TCF`의 마지막 catch가 모든 `Exception`을 받고, 원인 체인에 Timeout이 없으면 `ETF.systemError`로 전달한다.
- `ETF.systemError`는 공통 코드 `E-COM-SYS-0001`을 사용한다.
- **개발 표준:** `NullPointerException`, SQL·직렬화·라이브러리 예외를 업무 계층에서 포괄적으로 잡아 성공 또는 임의 업무 오류로 바꾸지 않는다.

### 5.4 Web MVC 예외

[`GlobalStandardExceptionHandler`](../../tcf-web/src/main/java/com/nh/nsight/tcf/web/entry/web/GlobalStandardExceptionHandler.java)는 `BusinessException`, `MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`과 일반 `Exception`을 처리한다. JSON 역직렬화처럼 명시 Handler가 없는 예외는 일반 `Exception` Handler로 들어갈 수 있으며 정확한 HTTP 상태는 13장에서 경로별로 구분한다.

### 5.5 Timeout 예외

온라인 거래 Timeout은 `BusinessException(E-COM-CTL-0003)`으로 변환될 수 있다. `InterruptedException`과 비업무 `ExecutionException`은 `SystemException`으로 변환된다. `TCF`의 [`TimeoutExceptionResolver`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/timeout/TimeoutExceptionResolver.java)는 중첩 원인 체인을 검사해 Timeout을 다시 업무 실패 경로로 보낸다.

### 5.6 IntegrationException 계열

[`IntegrationException`](../../tcf-eai/src/main/java/com/nh/nsight/tcf/eai/exception/IntegrationException.java)은 대상 `serviceId`, 연동 오류 코드와 `cause`를 보존한다.

- `IntegrationBusinessException`: 대상 `resultCode != S0000`이며 대상 코드·메시지·Body를 보존한다.
- `IntegrationTimeoutException`: 대상 Connect·Read Timeout을 나타낸다.
- `IntegrationException(MESSAGE)`: JSON 파싱 실패, Result 누락 등 응답 계약 오류다.
- `IntegrationException(SYSTEM)`: 대상 설정 누락, 연결 실패와 예상하지 못한 호출 오류다.

**개발 표준:** 호출 업무는 연동 예외를 무조건 같은 업무 오류로 합치지 말고 대상 업무 실패, 처리 불명 Timeout, 메시지 계약 오류와 시스템 장애를 구분해 로컬 정책으로 변환한다.

## 6. 계층별 예외 발생·처리 책임

| 계층 | 책임 | 발생시키는 예외 | 금지사항 |
| --- | --- | --- | --- |
| Controller·Handler | 요청 보완, 거래 분기, Facade 호출 | 입력 계약을 해석할 수 있을 때만 업무 예외 | 임의 JSON 조립, 모든 예외 catch |
| Facade | DTO 변환, 유스케이스 조정, 트랜잭션 경계 | 유스케이스 조정 실패 | 원인 없는 포괄 변환 |
| Service | 업무 흐름과 상태 전이 | 예상 가능한 업무 실패 | HTTP 응답 생성 |
| Rule | 검증·계산·업무 정책 | 세분화된 `BusinessException` | DB·웹 의존과 시스템 예외 은폐 |
| DAO·Mapper | 데이터 접근과 결과 반환 | 기술 예외는 원형 또는 원인 보존 래핑 | 업무 규칙 판단, SQL 예외를 성공으로 변환 |
| client·tcf-eai | 외부 호출과 응답 계약 검증 | 연동 업무·메시지·Timeout·시스템 예외 | 모든 실패를 같은 코드로 합치기 |
| TCF·ETF·Web Advice | 예외 분류, 표준 응답, 공통 종료 처리 | 원칙적으로 새 업무 판단 없음 | 내부 정보를 공개 응답에 복사 |

**개발 표준:** 업무 코드는 `Handler → Facade → Service → Rule → DAO/Mapper` 방향을 유지한다. 하위 계층은 자신이 판단할 수 없는 업무 의미를 추측하지 않는다. Mapper의 영향 행 수가 0인 사실은 DAO가 반환하고, “수정 대상이 없다”라는 업무 판단과 오류 코드는 Service·Rule이 결정한다.

## 7. STF·Dispatcher·Handler 예외 흐름

### 7.1 STF 선처리

[`STF.preProcess`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/processor/STF.java)의 순서는 다음과 같다.

```text
Header 검증·정규화 → guid·traceId 생성 → TransactionContext·MDC 설정
→ 세션·인증·권한 검증 → 거래통제 → Timeout 정책 → 멱등 처리 중 표시 → 거래 로그 시작
```

각 단계가 `BusinessException`을 발생시키면 뒤 단계는 실행되지 않고 `TCF`의 업무 실패 catch로 이동한다. 실패 시점에 따라 `TransactionContext`와 거래 로그가 아직 생성되지 않았을 수 있으므로 ETF는 `context != null`일 때만 종료 부수 효과를 수행한다.

[`StandardHeaderValidator`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/validation/StandardHeaderValidator.java)는 Header가 없거나 필수 필드가 비어 있으면 `E-COM-VALID-0001`을 발생시킨다. Controller가 빈 Header를 생성하더라도 필수값 검증 책임은 STF에 남는다.

### 7.2 Dispatcher와 Handler

[`TransactionDispatcher`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/dispatch/TransactionDispatcher.java)는 `serviceId`가 없으면 `E-COM-VALID-0001`, 등록 Handler가 없으면 `E-COM-DISP-0001`을 발생시킨다. Handler는 등록된 거래를 분기하고 Facade에 위임하며 `StandardResponse`나 HTTP 상태를 직접 만들지 않는다.

애플리케이션 시작 시 중복 `serviceId`가 등록되면 `IllegalStateException`이 발생한다. 이것은 개별 거래의 업무 실패가 아니라 구성 오류이므로 서비스 기동 검증에서 차단해야 한다.

## 8. TCF Catch 및 ETF 응답 조립

### 8.1 Catch 순서

[`TCF.process`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/processor/TCF.java)의 우선순위는 다음과 같다.

1. `BusinessException` → `ETF.businessFail`
2. 그 밖의 `Exception` → `TimeoutExceptionResolver.toBusinessException`
3. Timeout 원인이 있으면 `ETF.businessFail`
4. 나머지는 `ETF.systemError`
5. `finally`에서 Runtime Hook, Transaction·Authentication·Timeout Context와 MDC 정리

`SystemException`은 두 번째 catch에 포함된다. 원인 체인에 Resolver가 인식하는 Timeout이 있으면 업무 실패 경로가 될 수 있고, 아니면 시스템 실패 경로가 된다.

### 8.2 ETF 종료 처리

| 분기 | 응답 | context가 있을 때 수행하는 처리 |
| --- | --- | --- |
| `success` | `S0000` + Body | 멱등 성공, 거래 로그 종료, 감사, 메트릭 |
| `businessFail` | `E0001` + 예외 코드·메시지 | 멱등 실패, 거래 로그 종료, 감사, 메트릭 |
| `systemError` | `E0001` + `E-COM-SYS-0001` | 멱등 실패, 거래 로그 종료, 감사, 메트릭 |

**현재 구현:** `ETF.systemError`는 서버 Logger에 예외를 기록하고 `errorMessage`를 “시스템 오류가 발생했습니다.”로 제한하지만 `errorDetail`에는 예외 클래스의 단순 이름을 넣는다.

**개선 권고:** 공개 응답의 `errorDetail`은 제거하거나 승인된 진단 ID만 제공한다. 실제 예외 클래스와 원인은 서버 로그에서 `guid`·`traceId`로 조회한다.

## 9. Web MVC·Global Exception Handler

[`GlobalStandardExceptionHandler`](../../tcf-web/src/main/java/com/nh/nsight/tcf/web/entry/web/GlobalStandardExceptionHandler.java)의 현재 매핑은 다음과 같다.

| 예외 | HTTP | errorCode | 공개 메시지 | Header |
| --- | --- | --- | --- | --- |
| `BusinessException` | 200 | 예외 코드 | 예외 메시지 | `null` |
| `MethodArgumentNotValidException` | 200 | `E-COM-VALID-0001` | Header 검증 공통 문구 | `null` |
| `HttpRequestMethodNotSupportedException` | 200 | `E-COM-VALID-0001` | POST 사용 안내 | `null` |
| 그 밖의 `Exception` | 200 | `E-COM-SYS-0001` | 시스템 오류 공통 문구 | `null` |

모든 명시 Handler가 `@ResponseStatus(HttpStatus.OK)`를 사용한다. `errorDetail`에는 Validation 예외 메시지 또는 예외 클래스명이 포함될 수 있고, ETF 거래 종료 처리와 상관관계 Header를 제공하지 않는다.

**개발 표준:** MVC 예외도 공개 오류 계약, 상관관계 ID, 민감정보 비노출 규칙을 따른다. 표준 거래처럼 응답할 경우 ETF의 통제·로그·감사와 다른 범위를 관측 가능하게 남긴다.

## 10. 검증·Timeout·트랜잭션 예외

### 10.1 검증 위치

- Header 구조와 필수값: `StandardHeaderValidator`
- 세션·인증·권한: STF 내부 Validator
- 거래 가능 여부와 중복: 거래통제·멱등성 Component
- 업무 입력·상태: Service·Rule
- Spring Bean Validation: MVC Advice

같은 검증 실패라도 발생 위치에 따라 Header, 거래 로그 시작 여부와 처리 경계가 다르다. 오류 코드는 실패 원인과 운영 담당자가 구분할 수 있는 수준으로 세분화한다.

### 10.2 Timeout 변환

| 원인 | 현재 변환 | 코드 |
| --- | --- | --- |
| 온라인 실행 제한 초과 | `BusinessException` | `E-TCF-TIME-001` |
| Spring Transaction Timeout | Resolver → `BusinessException` | `E-TCF-TIME-002` |
| DB Query Timeout | Resolver → `BusinessException` | `E-TCF-TIME-003` |
| 실행 Thread 중단 | `SystemException` | `E-COM-SYS-0001` |
| EAI Connect·Read Timeout | `IntegrationTimeoutException` | `IntegrationErrorCode.TIMEOUT` |

Timeout 응답만으로 DB 작업이 실행되지 않았다고 단정할 수 없다. 상세 Rollback과 재시도 기준은 [트랜잭션 처리 방식](2026-07-26-05-트랜잭션처리방식.md)의 Commit·Rollback 및 Timeout 절을 따른다.

### 10.3 Rollback 연계

`BusinessException`, `SystemException`과 일반 Runtime 예외는 Spring `@Transactional` 기본 규칙에서 Rollback 대상이다. 트랜잭션 메서드 내부에서 예외를 잡아 정상 반환하면 Rollback되지 않는다.

**개발 표준:** 업무 실패를 응답 객체로 바꾸는 작업은 DB 트랜잭션 경계 밖의 TCF·ETF에서 수행한다. Checked Exception을 사용할 때는 `rollbackFor` 또는 명시적 변환 정책을 문서와 테스트에 남긴다.

## 11. tcf-eai 연동 예외

[`DefaultTcfServiceClient`](../../tcf-eai/src/main/java/com/nh/nsight/tcf/eai/client/DefaultTcfServiceClient.java)와 [`ResponseResultValidator`](../../tcf-eai/src/main/java/com/nh/nsight/tcf/eai/support/ResponseResultValidator.java)는 대상 설정 조회, 표준 요청 조립, HTTP POST, 응답 JSON 파싱, Result 확인과 `S0000` 판정을 수행한다.

| 실패 유형 | 예외 | 보존 정보 | 호출자 판단 |
| --- | --- | --- | --- |
| 대상 업무 실패 | `IntegrationBusinessException` | 대상 serviceId, resultCode, 메시지, Body | 로컬 업무 코드 변환 여부 |
| Connect·Read Timeout | `IntegrationTimeoutException` | 대상 serviceId, 경과시간, cause | 처리 상태·멱등성 확인 |
| 파싱·Result 누락 | `IntegrationException(MESSAGE)` | 대상 serviceId, cause | 계약 장애 |
| 설정·연결·예상 외 오류 | `IntegrationException(SYSTEM)` | 대상 serviceId, cause | 시스템 장애 |

**현재 구현 정합성 주의:** Validator는 대상 `result.message`를 읽지만 TCF [`Result`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/message/Result.java)는 `resultMessage`와 `errorMessage`를 사용한다. 대상 업무 실패 메시지가 빈 값으로 인식될 수 있으므로 16장의 개선 항목으로 관리한다.

## 12. 오류 코드와 표준 응답 계약

### 12.1 Result 의미

| 필드 | 성공 | 실패 |
| --- | --- | --- |
| `resultCode` | `S0000` | `E0001` |
| `resultMessage` | 정상 처리 문구 | 공통 실패 문구 |
| `errorCode` | 없음 | 상세 오류 코드 |
| `errorMessage` | 없음 | 공개 가능한 오류 설명 |
| `errorDetail` | 없음 | 현재 일부 경로의 기술 상세 |
| `errorSystemId` | 없음 | 현재 `NSIGHT-MP` |
| `errorDateTime` | 없음 | ISO Offset Date-Time |

`resultCode`는 성공·실패의 큰 분류이고 `errorCode`는 실패 원인의 안정적인 계약이다. 클라이언트는 자신에게 공개된 `errorCode`에 따라 안내·재입력·중단·재조회 정책을 적용한다.

### 12.2 오류 코드 규칙

기본 형태는 `E-{영역}-{분류}-{일련번호}`다. 예: `E-COM-VALID-0001`, `E-TCF-TIME-001`, `E-COM-SYS-0001`.

**현재 구현:** 일련번호 자릿수가 3자리와 4자리로 혼재한다. 기존 공개 코드는 호환성을 위해 임의 변경하지 않는다.

**개발 표준:** 신규 코드는 승인된 영역·분류와 일련번호 자릿수를 사용하고 상수명, 코드, 공개 메시지, 발생 위치와 클라이언트 처리를 함께 등록한다.

### 12.3 표준 실패 예

```json
{
  "header": {
    "guid": "correlation-guid",
    "traceId": "correlation-trace",
    "serviceId": "SV.Sample.read"
  },
  "result": {
    "resultCode": "E0001",
    "resultMessage": "처리 중 오류가 발생했습니다.",
    "errorCode": "E-COM-BIZ-0001",
    "errorMessage": "요청을 처리할 수 없습니다.",
    "errorDetail": null,
    "errorSystemId": "NSIGHT-MP",
    "errorDateTime": "2026-07-28T10:00:00+09:00"
  },
  "body": null
}
```

예제 값은 계약 형태만 보여주며 실제 사용자, 인증정보, 내부 SQL이나 경로를 포함하지 않는다.

## 13. HTTP 상태 정책

| 경로 | 현재 HTTP 상태 | 성공 판정 | 특징 |
| --- | --- | --- | --- |
| 표준 `/online` TCF | 일반적으로 200 | `resultCode == S0000` | 업무·시스템 실패도 표준 Result |
| Web Advice | 200 | `resultCode` | 명시 Handler가 OK 고정 |
| JWT 인증 Filter | 401 | 비표준 `errorCode/message` | TCF·Advice 진입 전 종료 |
| UI Relay | 대상 상태를 Relay 외형에 포함 | Relay 상태와 내부 응답 | 직접 Relay 연결 실패는 502 |
| 하이브리드 REST | Controller별 계약 | 경로별 확인 | TCF 통제를 거치지 않을 수 있음 |
| tcf-eai | 대상 HTTP와 Result | `resultCode == S0000` | 통신 성공과 업무 성공 분리 |

**개발 표준:** 먼저 경로의 HTTP 계약을 확인하고, Body가 표준 전문이면 `resultCode`와 `errorCode`를 추가 판정한다. HTTP 200만으로 업무 성공으로 간주하지 않고, HTTP 4xx·5xx를 표준 JSON이라고 가정하지 않는다.

**개선 권고:** 상태 정책 변경 전 UI, Relay, Gateway와 EAI 호출자의 호환성을 검증한다.
## 14. 로깅·감사·추적성

### 14.1 상관관계와 종료 증적

STF는 Header 검증 후 `guid`와 `traceId`를 생성하고 `TransactionContext`와 MDC에 넣는다. ETF는 Context가 존재할 때 결과별로 다음 증적을 남긴다.

| 증적 | 주요 값 | 목적 |
| --- | --- | --- |
| 거래 로그 | serviceId, guid, traceId, resultCode, errorCode, 처리시간 | 요청 단위 처리 결과와 성능 추적 |
| 감사 로그 | guid, serviceId, transactionCode, userId, branchId, resultCode | 누가 어떤 거래를 실행했는지 감사 |
| 메트릭 | serviceId, resultCode, 처리시간 | 성공률·실패율·지연 모니터링 |
| 시스템 오류 로그 | serviceId, 예외와 Stack Trace | 장애 원인 진단 |

오류 응답을 조사할 때는 공개 `errorMessage`로 원인을 추측하지 않고 `guid → traceId → serviceId → errorCode → 서버 오류 로그` 순서로 연결한다.

### 14.2 Context 정리

[`TCF.process`](../../tcf-core/src/main/java/com/nh/nsight/tcf/core/support/processor/TCF.java)는 `finally`에서 Transaction, Authentication, Timeout Context와 MDC를 정리한다. [`GuidMdcCleanupFilter`](../../tcf-web/src/main/java/com/nh/nsight/tcf/web/entry/web/GuidMdcCleanupFilter.java)도 HTTP 요청 종료 시 MDC와 인증 Context를 정리한다.

**개발 표준:** ThreadLocal·MDC를 추가하면 성공·업무 실패·시스템 실패·MVC 조기 실패를 포함한 모든 종료 경로에서 `clear()` 또는 `remove()`를 보장한다. 비동기 Thread에는 필요한 값만 명시적으로 복사하고 작업 종료 시 정리한다.

### 14.3 로그 수준

- 업무 거절: 반복 빈도와 운영 필요성에 따라 INFO 또는 WARN, Stack Trace는 원칙적으로 생략
- 시스템 장애: ERROR와 원인 Stack Trace
- Timeout: 대상, 단계, 제한시간, 경과시간과 상관관계 ID를 WARN 또는 ERROR로 기록
- 연동 호출: caller·target·resultCode·elapsedMs를 기록하고 요청·응답 전문 전체 로깅은 제한

## 15. 보안과 내부 정보 비노출

### 15.1 클라이언트 응답

클라이언트에 공개할 수 있는 정보는 안정적인 `errorCode`, 사용자가 이해할 수 있는 `errorMessage`, 상관관계 ID와 승인된 지원 정보다. 다음 값은 응답하지 않는다.

- Java 예외 클래스명과 Stack Trace
- SQL, DB 제품 오류와 Table·Column 구조
- 서버 파일 경로, 내부 URL, Host와 Port
- 비밀번호, Access·Refresh Token, Private Key와 Session ID
- Cookie·Authorization 원문
- 주민번호, 계좌번호, 전화번호 등 개인정보 원문

### 15.2 서버 로그

서버 로그도 무제한 저장소가 아니다. Header와 Body 전체를 출력하지 말고 allowlist 필드만 구조화해 기록한다. 인증정보와 개인정보는 마스킹하거나 생략하고, 오류 원인은 상관관계 ID와 별도 보호 로그로 연결한다.

**현재 구현:** TCF의 Console 진단은 요청·응답 Header와 Body를 광범위하게 출력하고 `userId`, `branchId`, `clientIp`, `idempotencyKey`도 출력한다. Audit 로그도 사용자·영업점 식별자를 기록한다.

**개선 권고:** Console 전문 출력은 운영에서 비활성화하고 중앙 마스킹 정책을 적용한다. 감사 목적 필드는 보존기간·접근권한·마스킹 기준을 별도로 관리한다.

### 15.3 오류 Detail

`Result.errorDetail`은 공개 응답 필드이므로 내부 진단용 자유문자열을 넣지 않는다. 현재 ETF와 Web Advice가 기록하는 예외 클래스명·Validation 메시지는 진단 ID 또는 안전한 고정 문구로 대체하는 것이 목표다.

## 16. 현재 구현 정합성 및 개선 권고

| 번호 | 주제 | 현재 구현 | 개발 표준 | 개선 권고 |
| --- | --- | --- | --- | --- |
| 1 | `SystemException` 사용 | Timeout Executor의 중단·실행 실패에서 사용, TCF 일반 catch 처리 | 시스템 의미와 cause 보존 | 기준 문서의 “정의만 존재” 설명을 갱신하고 전용 정책 여부 결정 |
| 2 | ETF와 MVC Advice | ETF는 Context가 있으면 멱등·거래로그·감사·메트릭 종료, Advice는 응답만 변환 | 진입점별 통제 범위를 명시 | MVC 조기 실패의 상관관계·로그 증적 보강 |
| 3 | 시스템 메시지 노출 | 공개 문구는 공통화했으나 `errorDetail`에 예외 클래스·Validation 메시지 포함 | 내부 상세 비노출 | Detail 제거 또는 진단 ID로 대체 |
| 4 | TCF 진입 전 상관관계 | Advice 응답 Header가 `null`이고 STF의 guid·traceId 생성 전일 수 있음 | 모든 실패를 추적 가능하게 함 | Filter 단계 correlation ID 생성과 응답 연계 검토 |
| 5 | Timeout 업무 실패 변환 | 온라인·Transaction·Query Timeout을 `BusinessException`으로 변환 | 처리 불명 상태와 업무 거절을 구별 | Timeout 전용 결과 분류 또는 명확한 재조회 계약 마련 |
| 6 | 하이브리드 REST | 파일 REST가 TCF를 거치지 않고 유사 `header/result/body`를 수동 조립 | 외형과 적용 통제를 일치시킴 | 가능한 경로는 TcfGateway 사용, 불가능하면 누락 통제와 오류 계약 명시 |
| 7 | EAI 코드·메시지 보존 | 대상 resultCode는 보존하지만 Validator가 `result.message`를 읽어 TCF `errorMessage`와 불일치 | 대상 오류 계약을 손실 없이 보존 | `resultMessage`·`errorMessage` 매핑과 호환 테스트 추가 |
| 8 | HTTP와 `resultCode` | 표준·Advice 실패는 주로 HTTP 200, JWT는 401, Relay·REST는 별도 정책 | 전송 상태와 업무 상태를 분리 판정 | 경로별 계약표와 클라이언트 회귀 테스트 유지 |

위 표의 개선 권고는 현재 공개 계약을 즉시 변경하라는 의미가 아니다. 호환성, 배포 순서, 모니터링과 롤백 방안을 갖춘 별도 변경으로 수행한다.

## 17. 신규 예외 체크리스트

- [ ] 예외가 업무 거절, 시스템 장애, Timeout, 연동 실패 중 무엇인지 분류했다.
- [ ] 예외를 발생시킬 책임 계층과 최종 변환 경계를 정했다.

## 18. 예외 변경 체크리스트

- [ ] 변경 전 오류 코드와 응답을 사용하는 UI·Relay·Gateway·EAI 호출자를 찾았다.
- [ ] 코드 삭제·이름 변경·의미 변경의 하위 호환성을 검토했다.
- [ ] `resultCode`, `errorCode`, `errorMessage`, `errorDetail` 변경 범위를 확인했다.
- [ ] ETF, Web Advice, JWT Filter와 하이브리드 REST의 차이를 비교했다.
- [ ] Rollback 규칙과 트랜잭션 경계가 유지되는지 검증했다.
- [ ] 거래 로그·감사·메트릭과 알림 기준을 갱신했다.
- [ ] 민감정보 노출 회귀 테스트를 수행했다.
- [ ] 피호출 서비스 선행 배포 등 호환 배포 순서를 정했다.
- [ ] 이전 오류 계약으로 복원하는 롤백 절차를 정했다.
- [ ] 배포 후 HTTP 상태, resultCode, errorCode, 실패율과 지연을 확인할 증적을 정했다.

## 21. 핵심 원칙 요약

1. 예상 가능한 업무 거절만 `BusinessException`으로 표현한다.
2. 시스템 장애를 업무 오류로 위장하지 않고 원인 예외를 보존한다.
3. Service·Rule이 업무 의미를 판단하고 공통 경계가 응답을 조립한다.
4. 표준 거래 성공은 HTTP 200이 아니라 `resultCode == S0000`까지 확인한다.
5. TCF·ETF 경로와 MVC·JWT·Relay·하이브리드 REST 경로의 차이를 명시한다.
6. Runtime 예외를 트랜잭션 내부에서 삼키지 않고 Rollback 결과를 테스트한다.
7. Timeout은 처리 불명 상태일 수 있으므로 재조회·멱등 확인 후 재시도한다.
8. `guid`, `traceId`, `serviceId`, `errorCode`로 응답과 운영 증적을 연결한다.
9. 클라이언트에는 내부 예외, SQL, Stack Trace, 인증정보와 개인정보를 노출하지 않는다.
10. 오류 코드나 응답 계약 변경은 호출자 호환성, 배포 순서와 롤백 방안을 함께 관리한다.
