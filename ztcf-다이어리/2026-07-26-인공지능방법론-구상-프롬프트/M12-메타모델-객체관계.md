## 이 단계에서 얻는 것

개발모델을 구조화할 **객체·관계·식별자·버전 정책**을 확정한다.  
Model Studio 입력의 뼈대가 된다.

## 지금 이 질문을 붙여 넣으세요

```text
M00을 적용한다. 결과/M0~M11을 인용한다.
코드·최종방법론 본문은 쓰지 마라. 질문 1개씩.

하나의 개발모델이 거래 한 건만 표현하면 충분합니까,
아니면 화면·다중 거래·다중 테이블·외부연계까지 표현해야 합니까?

최소 객체:
Project, BusinessArea, Domain, Screen, ScreenEvent, UseCase,
Service, ServiceId, TransactionCode, RequestModel, ResponseModel,
DTO, ProgramComponent, Rule, Table, Column, Mapper, SqlStatement,
ExternalInterface, SecurityPolicy, OperationalPolicy, TestCase,
DeploymentUnit, Artifact, Evidence, Decision, ChangeRequest

Project → BusinessArea → Domain
  ├ Screen → ScreenEvent → ServiceId

            DAO / Mapper / SQL / OperationalPolicy / TestCase

동기·비동기, 분기, 상태 전이, 보상, Timeout 정책,
버전·호환성, As-Designed vs As-Built

단계 산출물(결과/M12-메타모델-객체관계.md):

- 객체 관계도
```

## 단계 산출물

- 논리 메타모델
- 객체 관계도
- 속성 사전
- 식별자 규칙
- 상태 전이
- 버전·호환성 정책

## 통과 기준

- 모델 범위(단건 거래 vs 복합)가 확정되어 있다.  
- ServiceId 중심 추적 관계가 문장·표로 있다.
