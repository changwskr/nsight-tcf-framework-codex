# NSIGHT-TCF-FRAMEWORK 아키텍처 정의서 대화형 프롬프트 패키지

> **보관·참고용 (초기 생성본)**  
> 실행 기준은 상위 폴더의 [`../README.md`](../README.md) · [`../A-MASTER-대화원칙.md`](../A-MASTER-대화원칙.md) · `A00`~`A18` · [`../결과/`](../결과/) 이다.  
> 본 디렉터리의 `templates/` 는 계속 재사용한다. `prompts/M*`·`MASTER*` 는 이력으로 유지한다.

## 1. 도입 전 안내말

이 패키지는 사용자가 아키텍처 정의서의 모든 내용을 처음부터 알고 있어야 하는 방식이 아니다.
AI가 질문을 한 번에 하나씩 제시하고, 사용자의 답변과 실제 소스·설정·기준문서를 누적하여 최종적으로 **NSIGHT-TCF-FRAMEWORK 아키텍처 정의서**를 완성하도록 구성한다.

```text
질문 1개
→ 사용자 답변
→ 답변 요약 및 사실상태 분류
→ 아키텍처 영향 분석
→ 확정정보 원장 갱신
→ 단계별 Architecture Gate
→ 다음 질문
→ 최종 정의서·ADR·추적성·RACI·검증표 생성
```

본 패키지는 단순 구성도 작성이 아니라 다음 정합성을 최종 결과로 요구한다.

```text
요구사항
↔ 아키텍처 원칙
↔ 논리·물리·런타임 구조
↔ TCF/STF/ETF·ServiceId·Handler
↔ 업무 6계층·데이터·연계
↔ 인증·권한·감사
↔ 용량·가용성·DR
↔ OM·로그·모니터링·장애 대응
↔ CI/CD·자동검증·테스트
↔ 운영전환·변경·폐기
```

## 2. 사용 방법

### 2.1 가장 간단한 사용법

1. `prompts/MASTER_아키텍처정의_대화형_마스터프롬프트.md` 전체를 AI 개발지원 도구에 입력한다.
2. 사용자가 `시작`이라고 입력한다.
3. AI의 질문에 한 번에 하나씩 답한다.
4. 단계가 끝날 때 `확정` 또는 `다음`이라고 입력한다.
5. 최종 단계에서 AI가 `output/architecture-definition/` 아래에 정의서와 부속 산출물을 생성한다.

### 2.2 단계별 통제 방식

대규모 프로젝트나 검토회의에서는 `prompts/M00`부터 `M18`까지 순서대로 사용한다.
각 파일에는 선행단계, 질문, 완료조건, Gate, 결과파일이 정의되어 있다.

### 2.3 권장 명령어

| 명령 | 기능 |
|---|---|
| `시작` | M01부터 인터뷰 시작 |
| `현황` | 확정·가정·미확정·충돌·위험 표시 |
| `근거` | 현재 결정의 소스·문서·사용자 답변 근거 표시 |
| `추천` | 선택 가능한 대안과 권고안 표시 |
| `확정` | 현재 단계 Baseline 확정 |
| `보류` | 현재 항목을 Open Issue로 남기고 다음 질문 진행 |
| `이전` | 직전 질문으로 이동 |
| `수정: 항목=값` | 확정정보 수정 및 영향도 재계산 |
| `재검증` | 실제 소스·설정·산출물과 정의서 정합성 재검사 |
| `최종생성` | M17 최종 산출물 생성 |

## 5. 핵심 설계 원칙

- 실제 소스와 설정이 최우선 기준이다.
- 확인되지 않은 내용은 실제 사실처럼 쓰지 않는다.
- 모든 판단은 `[확정]`, `[가정]`, `[설계 예시]`, `[확인 필요]`, `[충돌]` 중 하나로 표시한다.
- 업무별 Controller를 임의 생성하는 일반 Spring 구조를 NSIGHT 표준보다 우선하지 않는다.
- 온라인 거래는 `OnlineTransactionController → TCF → STF → TimeoutExecutor → Dispatcher → Handler → Facade → Service → Rule/DAO → Mapper → ETF` 흐름을 기준으로 검증한다.
- `ServiceId ↔ Handler ↔ OM Service Catalog ↔ Timeout ↔ 거래통제 ↔ 로그` 정합성을 확인한다.
- 최종 완료는 문서 생성 여부가 아니라 **요구사항·설계·소스·설정·OM·시험·운영 증적의 일치**로 판정한다.
