# 원문 분석 요약

## 1. 문서의 구조

원문은 다음 흐름으로 구성된다.

```text
I. 개요
  → 프로젝트 목적·범위·TO-BE·수립 절차
II. 아키텍처 결정요인 도출
  → 업무 요구·제약·ISO/IEC 9126 품질 요구
III. 아키텍처 전략 정의
  → 품질 요구를 설계 전략·구성요소·원칙으로 전환
IV. 아키텍처 수립
  → Runtime / Module / Allocation View
Appendix
  → 약어
```

## 2. 핵심 아키텍처 특성

| 영역 | 원문 핵심 |
|---|---|
| 온라인 | NEXCORE Online Framework 기반 J2EE 온라인 시스템 |
| 배치 | NEXCORE Batch Framework와 중앙 Scheduler/Agent |
| 연계 | Apache MINA Socket, FTP/NFS 파일 연계 |
| 계층 | Presentation → Command → Business → Infrastructure |
| 업무 구현 | Service Facade(EJB) + Business Unit(POJO) + XSQL/SQL Manager |
| 데이터 | Informix v10 통합 DB, 유지 Oracle/Informix/MS SQL 의존 |
| 보안 | 도메인 쿠키 기반 SSO, URL/화면 식별자 기반 접근통제 |
| 트랜잭션 | XA Driver와 2PC 기반 이기종 DB 트랜잭션 |
| 가용성 | L4, Web, WAS, DB Active-Active 및 Fail-over |
| 구현 | Front/Back Office EAR, Subsystem EJB JAR, WebApp WAR |

## 3. 원문 사용 시 주의사항

1. **역사적 기술 기준**: 기술 제품·버전은 2008년 기준이므로 현재 목표 아키텍처로 자동 적용하지 않는다.
2. **문서 구성 불일치**: 본문 ‘문서 구성’ 설명은 제5장 평가를 언급하지만 실제 목차는 IV까지와 Appendix로 구성된다. 아키텍처 평가 작업은 I.3.4 디렉터리에 유지하고 누락 여부를 별도 확인한다.
3. **표기 오류**: `functionallity`, `usablity`, `Buniess`, `Facde` 등 원문 표기가 존재한다. 추적을 위해 원문명은 보존하되 신규 산출물에서는 정식 용어를 병기한다.
4. **그림 중심 정보**: TO-BE, Runtime, Module, Deployment, Implementation View는 그림과 표의 의미를 함께 검토해야 한다.
5. **사실과 제안 분리**: 원문 사실, 현재 현행값, 목표 설계, 현대화 제안을 별도 상태로 관리한다.

## 4. 권장 결과물 운영 방식

```text
원문 Baseline
  ↓
현행 As-Is 조사
  ↓
Gap/Risk 분석
  ↓
대안 비교·ADR
  ↓
목표 To-Be 설계
  ↓
시험·전환·운영 증적
  ↓
As-Built 및 Drift 관리
```
