# 01. 필요성과 아키텍트

원본 서두: “소프트아키텍처도 모델의 한종류이다…”

## 1. 소프트웨어 모델과 아키텍처

- 소프트웨어 아키텍처는 **소프트웨어 모델의 한 종류**다.
- 아키텍처를 이해하기 전에 **소프트웨어 모델**에 대한 이해가 선행되어야 한다.

## 2. 아키텍처가 나온 이유

가장 큰 이유: **소프트웨어가 크고 복잡해졌기 때문**.

크고 복잡한 시스템을 만들 때 먼저 할 일 = **구조를 정의**하는 것  
(자동차·집도 구조를 먼저 잡는다.)

모델을 그릴지 말지의 기준 = **소프트웨어의 복잡도**.

### “크고 복잡하다”의 실용 기준 (원문 예시)

| 기준 | 예시 |
|------|------|
| 규모 | 총 라인수 **약 10만 라인 이상** |
| 기술 다양성 | 구현 난이도·복잡도 상승 |
| 차세대 | 최소 **30가지 이상** 솔루션 도입·구현 |
| 비용 | 대략 **10억 이상** 규모면 일반적으로 소프트 아키텍처 필요 |
| 기간·비용 | 위 요인으로 프로젝트 기간·비용 증가 |

아키텍처 없이 설계만 진행하면 **후반 문제가 더 많이** 생기는 경우를 자주 봄.  
반대로 **작은 프로젝트**에 아키텍처를 고집할 필요는 없고, **분석모델만으로도 충분**한 경우가 있다.

## 3. 아키텍처의 필요성 (두 가지)

1. **크고 복잡함을 줄이는** 요소  
2. 모든 **이해관계자(stakeholder)** 가 공유할 수 있는 **하나의 그림(블루프린트)**

다양한 이해관계자를 만족시키기 위해 소프트웨어 아키텍처를 그린다.

## 4. 아키텍트에게 필요한 능력

| 능력 | 설명 |
|------|------|
| Communication | 이해관계자를 만족·이해시킬 수 있는 소통 |
| Negotiation | 설득·협상 |
| 기술력 | 필요하나 **이것만으로는 부족** |
| 추상화 | 협상·소통을 어렵게 말하면 **추상화 능력** |

원문 강조:

- 기술력이 다소 낮더라도 **커뮤니케이션·협상이 강한 사람**이 좋은 아키텍트가 될 확률이 높다.
- 모델 그리는 기술적 일보다 **이해관계자 설득에 더 많은 시간**을 쓴다.
- 추상화 = 사물·사건을 **단순화**해 이해관계자가 이해하게 만드는 능력.

아키텍트·아키텍처 모델을 잘하려면 **추상화 능력**을 키워야 한다.
