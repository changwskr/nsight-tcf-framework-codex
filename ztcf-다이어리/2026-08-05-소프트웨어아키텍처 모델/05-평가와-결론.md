# 05. 평가와 결론

## 1. 아키텍처 평가

- 설계를 마친 뒤, 그림·모델이 **제대로인지** 확인하는 단계.
- 여유·기한이 있으면 **프로토타입·구현**으로 평가하는 것도 좋음.

### 팁: Alternative(대안) 비교

- 한 번에 전부 결정하기 어렵고, 시행착오로 **진화**한다.
- **대안 2~3개**를 놓고 비교.
- 동일 품질속성·비기능 기준으로 **+/−** 평가 → 격론·이슈가 의외로 쉽게 정리되는 경우가 많음.

## 2. 결론 (원문)

1. 아키텍처 **결정 요인** = **품질속성을 정확히 정의**하는 것  
2. **전략** = 품질속성별 **구체 아키텍처 솔루션(패턴)** 도출  
3. 전략별로 **뷰 타입**을 정해 설계  
4. 설계의 가장 중요한 포인트 = 비기능·품질 전략이 **모델 그림에 보이는가**  
5. **평가**로 계속 최적화  

## 3. 치트시트

| 주제 | 요지 |
|------|------|
| 언제 필요한가 | 규모·복잡도·다기술·대형 비용 프로젝트 |
| 재료 | 상위 기능 + **비기능(품질·제약)** |
| 시나리오 | Stimulus 계열 6요소 + Response measure |
| 뷰 | SEI 3뷰 권장: Runtime / Module / Allocation |
| 분리 | 기술↔도메인, UI↔로직↔데이터(DAO) |
| 성공 기준 | 품질 해결책이 **뷰에 가시화** |
| 평가 | 시나리오 충족 + 대안 비교 |

## 4. TCF / 다이어리 연결 메모

| 원문 개념 | 로컬 작업과의 느슨한 대응 |
|-----------|---------------------------|
| 비기능 → 아키텍처 | Timeout, 보안(JWT), 가용성, 배치/온라인 분리 |
| Runtime 뷰 | Controller→Service→DAO, TCF STF/ETF 흐름 |
| Allocation | Dev/Staging/운영, 형상·변경관리 환경 승격 |
| Module | `nhnis.mp` / `nhnis.fw.tcf` 패키지 경계 |
| 평가 | harness phase QA, `gradlew test/war` 증적 |

본 문서는 **방법론 강의록**이고, PDMP 계약 SoT는 `tcf-harness-pdmp`·코드베이스를 따른다.
