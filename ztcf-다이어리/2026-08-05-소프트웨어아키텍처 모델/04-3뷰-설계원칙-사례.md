# 04. 3뷰 설계원칙 · 사례

수강신청 시스템을 예로 든 실전 설계 부분.

## 1. 설계전략 수립 (품질 → 패턴)

흐름:

```text
이해관계자 비기능 → 품질속성 시나리오 → 시나리오별 아키텍처 패턴
```

이 구간부터는 **기술·경험 지식**이 필요하다.

| 비기능 예 | 전략(패턴) 예 |
|-----------|----------------|
| 동시 1,000명, 3초 이내 | Memory Cache, Message Queue |
| 다양한 브라우저·권한 | Hybrid Web |
| 주 1회 백업 | Back-End Batch |

→ Memory Cache, Message Queue, Hybrid Web, Backend Batch 등이 **설계 전략(패턴)** 묶음.  
패턴을 많이 아는 아키텍트가 훌륭한 아키텍트에 가깝다(원문).

## 2. Runtime (C&C) 뷰

과제 특성상 **런타임 뷰를 먼저** 그린 예 (순서는 상황별).

### 설계 원칙

**원칙 1 — 기술 vs 도메인(비즈니스) 분리**

| 구분 | 특징 |
|------|------|
| 기술 컴포넌트 | 수강신청이 아니어도 있을 법한 이름 (WAS, Cache, Queue, Login…) |
| 도메인 컴포넌트 | 특정 업무 영역 특성 (수강신청 등) |

**원칙 2 — 도메인을 UI / 로직 / 데이터로 분리**

- UI → 업무 로직 → Data  
- DB 직접 접근 대신 **DAO**로 비즈니스와 데이터 분리  

구조는 **나누고 붙일 때** 생긴다. 하나로 다 만들면 구조가 불필요 → **모노리식(monolithic)**.

### Layer 예 (논리)

UI Layer · User Action Layer · Biz Logic Layer · DAO Layer · Data Layer · External Interface Layer  

- Tier ≈ **물리적** 표현  
- Layer ≈ **논리적** 모습  

런타임을 먼저 그린 이유(이 사례): Memory Queue/Cache, WAS, 로그인(보안), DAO 등 **비기능 패턴이 한 그림에** 다 들어가기 때문.  
경우에 따라 Module 뷰에 비기능 패턴이 더 잘 보이면 Module을 먼저 그려도 된다.

**아키텍처 설계의 핵심:** 뜯고 붙인 그림만 보고도 “비기능·품질을 **이렇게** 해결하는구나”가 보여야 한다.

## 3. Allocation 뷰 (Deployment)

- SW와 Non-SW 관계. 別名 **Deployment Diagram**.
- HW에 SW가 **어떻게 배치**되는지.
- Active-Active, 온라인/배치, DB 서버 등 **시스템 아키텍처 특성** 표현.
- 예: Cache 서버 5대, 주서버 2대, DBMS 2 · WAS 2, Active-Redundancy 등.

성능·안정성(품질속성)이 **이 그림에서 어떻게 해결되는지** 보여야 한다.  
런타임만으로는 비기능을 다 보여준다고 보기 어렵다 → Allocation도 중요.

## 4. Module 뷰

- **비즈니스 특성**이 강할 때 설계 (패키지·클래스 다이어그램).
- 품질속성과 연관이 크면 세부까지, 경우에 따라 **먼저** 그릴 수도 있음.
- 다만 대부분 품질속성은 **Runtime(+Allocation)** 에서 표현됨 → Module은 **생략하는 경우도 많음**.
- Module ≈ **개발용 설계서**에 가깝다(원문).

## 5. “설계” vs “아키텍처 설계”

| | 정의 (원문) |
|--|-------------|
| **아키텍처 설계** | **비기능 요건을 설계로 해결**하겠다 |
| **일반 설계** | 구현을 편하게 하기 위한 설계 |

프레임워크로만 설명하는 것은 부정확할 수 있음(원문).
