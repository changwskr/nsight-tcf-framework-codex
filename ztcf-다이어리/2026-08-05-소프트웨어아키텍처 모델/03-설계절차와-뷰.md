# 03. 설계절차와 뷰

## 1. 전체 요약 (원문 리스트)

1. 소프트웨어 아키텍처도 **소프트웨어 모델** 중 하나 → 모델 이해가 필요  
2. 규모·복잡성 때문에 **구조적 관점**의 아키텍처 설계가 목적  
3. 구조 설계를 위해 먼저 **비기능 요건**을 명확히 정의  
4. **Viewpoint**를 잡고 그 관점으로 설계 → 이해관계자 설득  
5. 마지막으로 아키텍처가 제대로인지 **평가**

## 2. 상세 설계 절차 (4단계)

| 단계 | 내용 |
|------|------|
| 1. 재료 | 기능·비기능 정의. 특히 **품질속성**이 아키텍처 결정 요인 |
| 2. 전략 | 품질속성을 만족할 **솔루션·패턴** (설계 전략) |
| 3. 뷰 작성 | Runtime / Allocation / Module 등 Viewpoint로 **블루프린트** |
| 4. 평가 | 이해관계자 요구(특히 비기능) 만족 여부 확인 |

### 재료 단계 세부

1. **이해관계자 선별** (제안서·요구사항정의서 등)  
2. 시스템을 블랙박스로 두고 연관관계 → **컨텍스트 / 바운더리 다이어그램**  
3. **기능 요구사항 모델링** (유즈케이스 등) — **상위 수준만** (세부 불필요)  
4. **품질속성 도출** · 품질속성 시나리오 · 비기능 모델링 · 이해관계자 매핑  

## 3. Viewpoint (관점)

이해관계자마다 소프트웨어를 보는 **관점이 다르다**.  
아키텍처 설계 시 Viewpoint를 정하는 것이 중요하다.  
직접 정의하기 어려우니 **정해진 뷰 세트**를 쓴다.

### CMU SEI — 3 VIEW (원문 추천)

| 뷰 | 다른 이름 | 보여주는 것 | 주 독자 |
|----|-----------|-------------|---------|
| **C&C** | Runtime View | 소프트웨어가 **동작하는** 모습 | PM 등 이해용 |
| **Module** | — | **정적** 구조, 코드로 가는 모습 | 개발자 |
| **Allocation** | Deployment | SW ↔ Non-SW(HW 등) 배치 | 네트워크·유지보수·HW 설계 |

원문: 보통 **3뷰를 많이 사용**. 간단한 것을 쓰는 것이 좋다.

### OMG — 4+1 View

- UML 진영. Use Case 뷰 + 4가지 뷰.
- 그 외 5뷰 등도 많음 → **프로젝트에 맞게 선택**.

뷰포인트를 잡은 뒤, 그 관점대로 그림을 그리기 시작한다.

## 4. SW 아키텍처 평가란

- “원래 요구한 대로 아키텍처가 만들어졌는가”를 본다.
- 즉 **비기능 시나리오대로** 잘 만들어졌는지 평가.
- 아키텍처는 실제 동작이 아니라 **그림**인 경우가 많아, 제대로 그려졌는지 확인하는 단계가 필요.
