아래와 같이 **“개발단계 아키텍처 의사결정 관리체계”**를 먼저 확정하는 것이 적절합니다. 핵심은 단순한 회의 안건 목록이 아니라, 각 결정사항을 **담당 아키텍처·결정기한·적용 위치·자동검증·예외승인**까지 연결하는 것입니다.

기존 NSIGHT 방법론에서도 아키텍처 의사결정권자, ADR, 예외 승인, Risk·Gap 관리체계를 개발 이전에 확정하도록 하고 있으며, 완료 여부도 문서 작성이 아니라 설계·코드·설정·시험·운영 증적의 정합성으로 판단하도록 정의합니다.

# 1. 도입 전 안내말

농협 상호금융 NSIGHT가 개발단계에 진입하면 업무 개발자는 수많은 세부 판단을 하게 된다.

```text
개인정보는 어디에서 마스킹할 것인가?
전문 필드 암호화는 누가 수행할 것인가?
화면 ID와 ServiceId는 누가 채번할 것인가?
업무 간 호출은 직접 Java 호출인가, MCA·EAI 호출인가?
트랜잭션은 어느 계층에서 시작할 것인가?
Timeout과 재시도는 누가 적용할 것인가?
오류코드와 로그에는 어떤 값을 남길 것인가?
```

이러한 결정을 업무 개발자 개인에게 맡기면 업무별로 서로 다른 구현이 발생한다.

```text
SV 업무는 화면에서만 마스킹
IC 업무는 Service에서 마스킹
PC 업무는 SQL에서 마스킹
일부 업무는 원문을 내려준 뒤 UI에서 마스킹
```

기능적으로는 모두 동작할 수 있지만 다음 문제가 발생한다.

- 개인정보 원문 노출
- 전문과 API 계약 불일치
- 업무별 중복 구현
- 공통 모듈 적용 불가
- 운영로그와 감사로그 불일치
- 성능·장애 처리 방식 혼재
- 유지보수와 변경 영향 분석 곤란
- 보안점검 및 품질검증 기준 부재

따라서 개발단계에서는 다음과 같은 공식 관리체계가 필요하다.

```text
아키텍처 의사결정 TASK 등록
→ 담당 아키텍처 지정
→ 대안과 영향도 분석
→ 권고안 확정
→ ADR 승인
→ 개발표준·가이드 반영
→ 공통모듈 또는 샘플 제공
→ CI/CD 자동검증
→ 예외 승인 및 만료 관리
```

# 3. 의사결정 관리 원칙

## 3.1 책임 기준

모든 의사결정 TASK에는 다음 세 가지 역할을 지정한다.

| 구분     | 의미                                 |
| -------- | ------------------------------------ |
| 주관 `R` | 분석하고 방안을 작성하는 조직        |
| 승인 `A` | 최종 결정을 승인하는 아키텍처        |
| 협의 `C` | 영향 검토와 요구사항을 제공하는 조직 |

하나의 TASK에 주관 조직을 여러 개 지정하지 않는 것이 원칙이다. 공동 주관처럼 보이는 경우에도 최종 문서 작성과 종료 책임은 하나의 조직이 가져야 한다.

## 3.2 우선순위

| 등급 | 적용 기준                                  | 결정기한      |
| ---- | ------------------------------------------ | ------------- |
| `P0` | 이미 개발에 영향을 주며 변경비용이 큰 사항 | 즉시 확정     |
| `P1` | 공통·연계 개발 전에 필요한 사항            | 본격 개발 전  |
| `P2` | 통합·성능·운영시험 전에 필요한 사항        | 통합시험 전   |
| `P3` | 운영 고도화 또는 후속 개선사항             | 운영전환 전후 |

# 6. 핵심 사례별 1차 해결 방향

## 6.1 개인정보 마스킹

### 의사결정

```text
화면 마스킹
= 사용자 표시를 위한 보조 통제

서버 마스킹
= 원문 유출을 차단하는 필수 통제
```

화면에서 마스킹하더라도 서버가 개인정보 원문을 무조건 전송해서는 안 된다.

### 권장 구조

```text
DB 원문 또는 암호화 데이터
  ↓
업무 조회 및 권한 확인
  ↓
서버 개인정보 정책 적용
  ├─ 원문 허용
  ├─ 부분 마스킹
  └─ 필드 제거
  ↓
응답 DTO 생성
  ↓
화면 추가 표시 마스킹
```

### 책임

| 영역 | 책임                                        |
| ---- | ------------------------------------------- |
| DA   | 개인정보 필드와 등급 정의                   |
| SEC  | 등급별 마스킹·원문 허용 정책 승인           |
| AA   | 서버 처리 위치와 권한 연계 설계             |
| FW   | 공통 마스킹 정책·Annotation·Serializer 제공 |
| UI   | 화면 표시와 복사·다운로드 통제              |
| BA   | 어떤 업무·사용자가 원문을 볼 수 있는지 정의 |
| OPS  | 원문 조회·복호화 감사로그 관리              |

### 구현 원칙

- Service마다 문자열을 잘라 마스킹하는 중복 구현은 금지한다.
- 서버 응답 조립 경계에서 공통 정책을 적용한다.
- 사용자 권한·업무 목적·채널에 따라 결과를 결정한다.
- 화면, 엑셀, 파일, 로그에 각각 별도 정책을 적용한다.
- 마스킹된 값을 DB에 재저장하지 않는다.
- 원문 조회는 별도 권한과 감사로그를 남긴다.

---

## 6.2 서버 네이밍 원칙

### 의사결정

네이밍은 AA만의 기준이 아니라 영역별 책임을 통합한 표준이어야 한다.

| 명명 대상            | 주관      |
| -------------------- | --------- |
| 업무코드·도메인      | SA·AA     |
| 화면·이벤트          | UI        |
| ServiceId·거래코드   | FW·AA     |
| 패키지·클래스·메서드 | AA        |
| 전문 필드            | MCA·AA·DA |
| DB 객체·컬럼         | DA        |
| EAI 인터페이스       | EAI       |
| 서버·VM·Tomcat·Port  | TA        |
| 배치·배포 Artifact   | DVO       |

### 권장 구조

```text
업무코드
→ 화면 ID
→ 이벤트 ID
→ ServiceId
→ Handler·Facade·Service
→ DAO·Mapper·SQL ID
→ Table·Column
→ 로그·OM·테스트
```

### 통제방법

- 명명규칙 문서만 배포하지 않는다.
- 프로젝트 생성 템플릿에 규칙을 반영한다.
- Checkstyle·ArchUnit·Gradle Task로 자동검증한다.
- DB 표준용어 검사를 모델링·DDL 단계에 적용한다.
- 예외 명칭은 ADR과 만료일을 등록한다.

## 6.3 전문 필드 암호화

### 의사결정

전문 필드 암호화는 업무 Service가 임의로 암호화 라이브러리를 호출하는 구조보다 공통 보안 경계에서 수행하는 것이 적절하다.

```text
업무 프로그램
  ↓ 평문 또는 도메인 값
암호화 Adapter·공통 보안 모듈
  ↓ 암호문 + 알고리즘·버전·키 식별정보
MCA·EAI·외부 시스템
```

수신 시에는 반대 순서로 처리한다.

```text
암호화 전문
  ↓
암호화 Adapter
  ↓ 복호화·무결성 확인
업무 DTO
  ↓
업무 Service
```

### 책임

| 영역 | 책임                                  |
| ---- | ------------------------------------- |
| SEC  | 알고리즘·키·교체주기·암호화 대상 승인 |
| DA   | 필드의 민감도와 저장 암호화 여부 정의 |
| AA   | 암복호화 경계와 업무 오류 처리 설계   |
| FW   | 공통 암복호화 인터페이스 제공         |
| MCA  | 채널 전문의 암호화 필드 계약          |
| EAI  | 외부 연계 전문의 암호화 계약과 버전   |
| TA   | KMS·HSM·인증서·네트워크 보호          |
| OPS  | 키 교체·장애·복호화 실패 Runbook      |

### 필수 결정값

- 대상 필드
- 암호화 알고리즘
- 암호문 Encoding
- 초기화 벡터 및 Nonce 처리
- 무결성 검증 방식
- Key ID와 Key Version
- 키 교체 시 구·신키 병행기간
- 최대 전문 길이 변화
- 복호화 실패 오류코드
- 로그·Dump의 암호문 기록 허용 여부
- 성능 기준과 대량 처리 방식

### 금지사항

- 암호키를 Java 소스나 `application.yml`에 저장
- UI에서 암호키를 보유
- 업무별로 서로 다른 암호화 규칙 사용
- 암호화 실패 시 평문 전송
- 암호문 전체를 운영로그에 기록
- TLS를 적용했으므로 필드암호화가 불필요하다고 판단
- 필드암호화를 했으므로 TLS를 생략

# 10. 시사점

## 10.1 핵심 아키텍처 판단

첫째, **보안·마스킹·암호화는 화면이나 업무 개발자의 선택사항이 아니라 중앙 정책이어야 한다.**

둘째, **네이밍은 문서 작성 편의가 아니라 화면·ServiceId·프로그램·SQL·운영로그를 연결하는 추적체계다.**

셋째, **MCA·EAI·AA·DA·TA 간 경계가 없는 의사결정은 구현 단계에서 중복되거나 누락된다.**

넷째, **모든 TASK는 최종 주관자 한 명과 승인자를 명확히 지정해야 한다.**

다섯째, **결정사항은 문서에서 끝나지 않고 공통모듈·샘플·CI/CD Gate로 구현돼야 한다.**

## 10.2 주요 위험

- P0 결정 전 업무 개발이 대량 진행되는 것
- 업무팀별 임시 기준이 사실상 표준으로 굳어지는 것
- 화면·MCA·서버가 동일 검증을 서로 다르게 구현하는 것
- 개인정보 원문이 화면·로그·파일로 확산되는 것
- 외부연계 Timeout과 업무 트랜잭션 결과가 불일치하는 것
- 문서는 승인됐지만 공통모듈과 자동검증이 제공되지 않는 것
- 예외 승인이 영구적인 표준 위반으로 남는 것

## 10.3 우선 보완 과제

```text
1순위: P0 20개 의사결정 확정
2순위: 마스킹·암호화·표준 전문 공통모듈
3순위: ServiceId·계층·명명 자동검증
4순위: Timeout·트랜잭션·멱등성 선도거래 검증
5순위: MCA·EAI·업무 WAR 계약 테스트
6순위: 로그·감사·운영진단 연결
```

## 10.4 중장기 발전 방향

향후에는 Architecture Decision Register를 화면·ServiceId·프로그램·DB·테스트·OM 기준정보와 연결해야 한다.

```text
아키텍처 의사결정
  ↓
개발표준
  ↓
모델·템플릿
  ↓
소스코드
  ↓
CI/CD 검증
  ↓
배포
  ↓
운영 증적
  ↓
기준 개선
```

이를 통해 NSIGHT의 아키텍처를 문서 중심의 사전 통제에서 **지속적으로 검증되는 실행 아키텍처**로 발전시킬 수 있다.

# 11. 마무리말

NSIGHT 개발단계에서 가장 위험한 상태는 의사결정을 하지 않은 것이 아니라, 각 업무팀이 서로 다른 결정을 이미 구현하고 있는 상태다.

따라서 지금 필요한 것은 모든 아키텍처 문서를 다시 작성하는 것이 아니다.

```text
개발에 직접 영향을 미치는 P0 의사결정을 먼저 확정하고,
담당 아키텍처를 지정하며,
결정사항을 공통모듈과 자동검증으로 전환하는 것
```

이것이 개발 속도를 늦추는 통제가 아니라, 후반부의 대규모 재개발과 운영 위험을 줄이는 가장 현실적인 개발 아키텍처 관리방안이다.

권장 작성 순서는 **개인정보 마스킹 → 전문 필드 암호화 → 통합 네이밍 → 표준 전문·ServiceId → 트랜잭션·Timeout** 순입니다. 이 다섯 항목이 현재 개발 산출물과 공통 구현에 가장 큰 영향을 줍니다.
