# UI-11 파일 다운로드 전문가 의사결정서

> 문서 등급: **전문가 심의·Baseline 후보**  
> 상태: **제안(Proposed)** · 우선순위: **P0** · 영역: **단말·UI**

## 1. Executive Summary

UI-11는 `권한·마스킹·감사·대용량 처리`를 프로젝트 공통 기준으로 확정하는 의사결정이다. 권고 방향은 **다운로드는 서버 권한·마스킹·감사를 적용한다.**이며, 실행 원칙은 **UI에서 원문을 받은 후 숨기는 방식을 금지한다.**이다. 이 결정은 문서 표준에 머물지 않고 코드·설정·OM 기준정보·시험·CI/CD·운영 증적으로 강제되어야 한다.

전문가 심의의 핵심은 “좋은 방향인가”가 아니라 다음 네 질문에 답하는 것이다.

1. 선택안이 해결하려는 위험과 품질속성이 명확한가?
2. 책임 경계, 계약과 실패 의미가 구현 가능한 수준으로 닫혀 있는가?
3. 준수 여부를 측정·검증하고 위반을 차단할 수 있는가?
4. 기존 구현을 안전하게 전환하고 필요 시 되돌릴 수 있는가?

## 4. Context와 문제 구조

NSIGHT는 Java 21, Spring Boot 3.3.5, Gradle 멀티모듈을 사용하며 `tcf-util → tcf-core → tcf-web → 업무/플랫폼 모듈` 의존 방향과 TCF–Handler–Facade–Service–Rule–DAO/Mapper 흐름을 기본으로 한다.

UI-11의 결정 동인은 **사용성, 서버 보안통제, 오류 회복성, 브라우저 호환성, 대용량 안전성**이다. 표준이 없거나 모호하면 팀별 최적화가 전체 시스템의 불일치로 전환된다. 기능 성공만 확인해서는 계약, 장애, 보안, 운영과 전환 위험을 발견할 수 없다.

## 8. 품질속성 시나리오

대표 시나리오: **사용자가 중복 클릭하거나 입력을 변조해도 서버 정책이 최종 검증하고 예측 가능한 오류와 복구 행동을 제공한다.**

| 요소 | 정의 방법 |
|---|---|
| Source | 사용자, 업무팀, 외부기관, 공격자, 운영자 또는 장애 원인 |
| Stimulus | 정상 요청, 변경, 피크 부하, Timeout, 위변조, 노드·DB·연계 장애 |
| Environment | 평시·피크·배포 중·부분 장애·DR 전환 상황 |
| Artifact | 권한·마스킹·감사·대용량 처리 관련 코드·설정·계약·데이터·운영 절차 |
| Response | 허용·거부·격리·Rollback·재처리·알림·감사·전환 |
| Measure | 초기 로딩·응답시간, UI 오류율, 중복요청률, 접근성 결함, 서버 우회 보안결함 |

승인본에는 최소 정상, 경계, 오류, 보안 우회, 성능 한계, 운영복구 시나리오를 수치와 함께 작성한다.

## 9. 대안 모델

### 대안 A — 중앙 정책과 실행 통제

공통 Framework·Adapter·Registry·Pipeline이 규칙을 실행한다. 편차 위험이 큰 보안·계약·식별자·거래통제에 적합하지만 공통 변경의 Blast Radius와 버전 호환을 관리해야 한다.

### 대안 B — 경계 계약 고정, 내부 구현 자율

입력·출력·오류·관측 계약은 중앙 통제하고 내부 알고리즘은 소유 영역이 결정한다. 팀 자율성과 상호운용성의 균형이 좋지만 계약 밖 중복과 Drift 검사가 필요하다.

### 대안 C — 단계적 전환과 기간 제한 예외

목표 기준은 유지하면서 레거시·외부 제약 범위에 Adapter와 만료 예외를 둔다. 현실적인 전환이 가능하지만 종료 KPI·소유자·제거 버전이 없으면 영구 기술부채가 된다.

## 11. 권고 결정과 Guardrail

**결정 제안:** 다운로드는 서버 권한·마스킹·감사를 적용한다.

**실행 제안:** UI에서 원문을 받은 후 숨기는 방식을 금지한다.

필수 Guardrail:

1. 적용·비적용 대상과 실행 경계를 명시한다.
2. 오류·Timeout·Rollback·재처리의 소유자를 지정한다.
3. 보안은 기본 거부, 최소권한과 최소정보 원칙을 적용한다.
4. 민감정보·Secret·내부 예외를 로그와 응답에 노출하지 않는다.
5. 공개 계약 변경은 버전·병행기간·소비자 전환과 제거일을 갖는다.
6. 예외는 위험·보완통제·책임자·만료일 없이 승인하지 않는다.

## 12. 목표 통제 아키텍처

```text
Policy / ADR Baseline
  → Preventive Control: 템플릿·공통모듈·Schema·설정 제한
  → Detective Control: 정적검사·계약시험·Drift·모니터링
  → Corrective Control: 차단·Rollback·재처리·보상·Runbook
  → Evidence: CI 결과·OM·로그·감사·승인·운영 KPI
  → Feedback: RCA·용량 보정·표준 개정·대체 ADR
```

이 TASK에 필요한 핵심 통제 후보는 **공통 컴포넌트, 서버 재검증, Token 저장정책, origin 검사, 페이징·비동기 파일**이다.

## 13. 정책–메커니즘–증적 분리

| 구분 | 질문 | UI-11 산출물에 기록할 내용 |
|---|---|---|
| Policy | 무엇을 허용·금지·예외로 둘 것인가? | 결정문, 적용범위, 금지사항, 예외조건 |
| Mechanism | 어느 컴포넌트가 어떻게 강제하는가? | 코드·설정·Schema·Pipeline·운영 절차 |
| Evidence | 실제로 준수함을 무엇으로 증명하는가? | 테스트·로그·Metric·OM·승인·배포 결과 |

정책을 특정 구현에 불필요하게 결합하지 않되, 실행 메커니즘이 없는 선언적 정책도 승인하지 않는다.

## 14. 데이터·상태·동시성 검토

- Source of Truth와 쓰기 소유자를 명확히 한다.
- 처리 상태와 전이, 중간상태의 가시성과 복구방법을 정의한다.
- 중복·순서역전·동시변경·부분성공 상황을 모델링한다.
- Transaction 범위와 외부 처리의 원자성 차이를 명시한다.
- 보존·폐기·감사와 비운영 데이터 정책을 연결한다.

해당 없음으로 판단할 때도 N/A 근거와 인접 TASK의 소유권을 기록한다.

## 16. 성능·용량 Budget

성능 요구는 “빠르게”가 아니라 Workload·환경·측정점·Percentile·합격값으로 정의한다. `초기 로딩·응답시간, UI 오류율, 중복요청률, 접근성 결함, 서버 우회 보안결함`를 기본 후보로 사용하고, 다음 Budget 관계를 검증한다.

```text
사용자/채널 Timeout
  > Gateway/MCA Timeout
    > Online Transaction Timeout
      > DB Query·외부호출 Timeout
```

Thread와 Connection Pool은 WAR별 값만 보지 않고 JVM·Tomcat·전체 DB Session 합계를 검증한다. 평균값만으로 승인하지 않고 p95/p99, Stress와 Soak 결과를 함께 본다.

## 18. Observability와 운영 계약

운영자는 GUID·TraceId·ServiceId를 중심으로 Gateway, TCF, Handler, SQL, 연계와 최종 상태를 추적할 수 있어야 한다. 로그는 구조화하되 개인정보·Token·전문 원문을 기록하지 않는다.

필수 운영 계약:

- SLI/SLO와 경보 임계치·지속시간
- 경보 수신자와 첫 조치 Runbook

## 21. KPI·KRI와 운영 Baseline

이 영역의 우선 측정 후보는 **초기 로딩·응답시간, UI 오류율, 중복요청률, 접근성 결함, 서버 우회 보안결함**이다.

각 지표에는 정의, 분모·분자, 수집원, 주기, 임계치, 담당자와 조치 Runbook을 둔다. 초기 값이 없으면 선도 거래로 Baseline을 측정한 후 목표를 승인한다. 측정 불가능한 목표는 Gate 조건으로 사용하지 않는다.

## 22. 전환·배포·Rollback 전략

1. 영향 사용처와 소비자를 전수 식별한다.
2. 목표 계약과 Adapter·병행 운영 필요성을 확정한다.
3. Golden Sample과 자동검증을 먼저 제공한다.
4. 선도 업무에서 정상·오류·부하·복구를 검증한다.
5. 적용률과 예외를 보며 단계적으로 확대한다.
6. 구·신 기준의 Drift와 운영 KPI를 비교한다.
7. Rollback 한계시점 전 실패 시 승인 절차로 원복한다.
8. 완료조건 충족 후 구 기준과 임시 Adapter를 폐기한다.

## 23. 예외·기술부채·잔여위험

예외에는 대상·사유·영향·보완통제·책임자·승인자·시작일·만료일·제거 버전·재검토일이 필요하다. 동일 예외 반복은 표준의 비현실성 또는 이행 실패 신호로 보고 ADR을 재검토한다.

잔여위험은 발생가능성×영향으로 등급화하고 수용·회피·완화·전가 중 전략을 명시한다. Blocker·Critical 위험은 책임자 없는 조건부 승인으로 다음 Gate에 넘기지 않는다.

## 24. 단계별 실행 Roadmap

| 단계 | 주요 활동 | Exit Criteria |
|---|---|---|
| 1. Discover | 현행·사용처·Gap·제약 조사 | 근거 경로와 Gap 원장 완성 |
| 2. Decide | 대안·PoC·영향·잔여위험 심의 | ADR 승인 또는 명시적 재검토 |
| 3. Enable | 표준·샘플·공통모듈·검사 제공 | 선도팀이 독립 적용 가능 |
| 4. Pilot | 대표 거래·환경에서 검증 | Critical Gap 0, Rollback 검증 |
| 5. Scale | 업무팀 확대·적용률·예외 관리 | 대상 적용과 CI Gate 정착 |
| 6. Operate | KPI·Alert·Runbook·RCA 운영 | 운영 Baseline과 소유권 확정 |
| 7. Retire | 구 기준·Adapter·예외 폐기 | 잔여 사용처 0, 대체 링크 완료 |

## 25. ARB 심의 질문

- 이 결정이 해결하는 가장 큰 구조적 위험은 무엇인가?
- 대안의 점수와 가중치를 뒷받침하는 실제 증거는 무엇인가?
- 실패 시 데이터·사용자·외부기관·운영자에게 어떤 결과가 남는가?
- 정책을 강제하는 메커니즘과 준수 증적이 각각 존재하는가?
- 현재 구현과 목표 사이의 Gap을 누가 언제 제거하는가?
- 예외가 만료될 때 서비스가 자동으로 안전해지는가, 수동 조치가 필요한가?
- 목표 TPS·지연·복구시간을 어떤 환경에서 재현했는가?
- 이 결정을 폐기하거나 대체할 Trigger는 무엇인가?

## 26. 최종 승인 체크리스트

- [ ] UI-11 Scope와 비적용 범위가 명확하다.
- [ ] 다운로드는 서버 권한·마스킹·감사를 적용한다.의 선택 근거와 기각안이 있다.
- [ ] UI에서 원문을 받은 후 숨기는 방식을 금지한다.의 구현 위치·책임·계약이 닫혀 있다.
- [ ] 품질속성 시나리오에 수치·환경·측정점이 있다.
- [ ] 보안 Threat, 데이터 상태, 장애·복구와 운영 계약을 검토했다.
- [ ] 다운로드 기준과 코드·설정·OM·테스트가 연결된다.
- [ ] 자동검증, 배포 차단조건과 수동 Gate를 구분했다.
- [ ] Migration·병행기간·Rollback·폐기조건이 있다.
- [ ] 예외·기술부채·잔여위험의 책임자와 만료일이 있다.
- [ ] 업무팀 적용과 운영 Baseline까지 완료 정의에 포함했다.

## 27. 전문가 결론

UI-11의 승인 여부는 문서 분량이 아니라 `권한·마스킹·감사·대용량 처리`에 관한 선택이 실행 가능한 통제와 측정 가능한 증적으로 닫혔는지로 판정한다. 권고안 **다운로드는 서버 권한·마스킹·감사를 적용한다.**을 채택하려면 **UI에서 원문을 받은 후 숨기는 방식을 금지한다.**을 실제 저장소와 운영환경에서 입증하고, Usability·Security·Performance·Accessibility 관점의 실패 시나리오를 통과해야 한다.

승인 후에도 KPI·예외·RCA·기술변화를 정기 검토해 결정의 유효성을 확인한다. 전제가 바뀌면 기존 문서를 조용히 수정하지 않고 새 ADR로 대체관계와 전환·폐기 이력을 남긴다.
