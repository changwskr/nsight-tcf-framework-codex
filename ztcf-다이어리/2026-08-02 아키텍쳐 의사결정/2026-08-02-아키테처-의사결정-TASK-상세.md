# 농협 상호금융 NSIGHT

# 개발단계 아키텍처 의사결정 TASK별 통합 방안서

---

# 1. 도입 전 안내말

본 방안서는 개발단계에서 발생하는 아키텍처 판단을 업무 개발자 개인의 선택에 맡기지 않고, 프로젝트 전체의 공식 기준으로 확정하기 위한 문서다.

각 TASK는 다음 생명주기로 관리한다.

```text
TASK 등록
→ 현행 및 문제 분석
→ 대안 비교
→ 권고안 작성
→ 영향도 및 위험 검토
→ PoC 또는 샘플 구현
→ ARB·ADR 승인
→ 개발표준 반영
→ 공통모듈·템플릿 제공
→ CI/CD 자동검증
→ 업무팀 적용
→ 운영 증적 확인
```

모든 TASK의 완료 기준은 다음과 같다.

```text
문서 승인만 완료
≠ TASK 완료

ADR 승인
+ 소스·설정 반영
+ 샘플 제공
+ 테스트 통과
+ 자동검증 적용
+ 운영관리 등록
= TASK 완료
```

| APP-17 | 공통 Util은 기술 공통 기능만 수용한다.                       | 업무규칙이나 특정 도메인 DTO의 공통 모듈 유입을 금지한다.           | FW·AA             | 공통화 심의기준        |

| APP-20 | 화면부터 DB까지 양방향 추적성을 관리한다.                    | 화면 이벤트–ServiceId–Handler–SQL–Table 매트릭스를 유지한다.        | AA·UI·DA          | 추적성 매트릭스        |

NSIGHT의 기준 처리 흐름은 `OnlineTransactionController → TCF → STF → TimeoutExecutor → Dispatcher → Handler → Facade → Service → Rule·DAO → Mapper → ETF`다.

# 19. 핵심 아키텍처 판단

```text
1. 개인정보 원문은 필요한 사용자와 거래에만 서버에서 제공한다.

2. UI 마스킹은 서버 마스킹을 대체하지 않는다.

3. 전문 암복호화는 업무 Service에 분산하지 않고
   공통 Security Adapter에서 수행한다.

4. 온라인 업무는 공통 Controller와 TCF를 경유한다.

5. 업무 구현은
   Handler → Facade → Service → Rule → DAO → Mapper
   구조를 유지한다.

6. 트랜잭션 경계는 Facade를 기본으로 한다.

7. 다른 WAR와 도메인의 DAO·Mapper·테이블을 직접 사용하지 않는다.

8. 모든 거래는 ServiceId·GUID·TraceId로
   화면·프로그램·SQL·로그·OM과 연결한다.

9. JWT 서명검증은 Gateway 또는 공통 Filter,
   인증문맥 검증은 STF,
   상세 업무권한은 Service·Rule에서 수행한다.

10. 아키텍처 결정은 문서로 끝내지 않고
    공통 구현과 CI/CD Gate로 강제한다.
```

# 20. 마무리말

본 통합 방안서는 개발단계에서 확정해야 할 전체 의사결정 TASK에 대한 1차 권고 기준이다.

실제 적용에서는 각 TASK를 단순 회의 안건으로 다루지 않고 다음 결과물까지 연결해야 한다.

```text
아키텍처 판단
→ ADR
→ 상세 방안서
→ 표준 가이드
→ 공통모듈·샘플
→ 업무 적용
→ 자동검증
→ 시험 증적
→ 운영 기준정보
→ 변경·예외관리
```

특히 P0 TASK는 본격적인 업무 개발이 확대되기 전에 확정해야 한다. P0 기준이 확정되지 않은 상태에서 업무별 구현을 진행하면 이후 공통화가 아니라 대규모 재개발이 발생할 가능성이 높다.
