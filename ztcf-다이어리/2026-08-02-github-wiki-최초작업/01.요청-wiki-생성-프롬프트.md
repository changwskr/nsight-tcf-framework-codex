다음 GitHub 저장소를 기준으로 프로젝트 Wiki를 구축하라.

- 저장소: `changwskr/nsight-tcf-framework-codex`
- Wiki 주소: `https://github.com/changwskr/nsight-tcf-framework-codex/wiki`
- 프로젝트명: 농협 상호금융 NSIGHT TCF Framework
- 문서 형식: GitHub Wiki Markdown
- 주요 독자:
  - 애플리케이션 아키텍트
  - 단말 아키텍트
  - 프레임워크 아키텍트

## 1. 작업 목적

`nsight-tcf-framework-codex` 저장소의 소스와 기존 문서를 분석하여 다음 목적을 달성하는 GitHub Wiki를 구축한다.

1. NSIGHT TCF Framework의 전체 구조를 한눈에 이해할 수 있도록 한다.
2. 개발자가 표준 개발 절차와 구현 규칙을 Wiki에서 바로 확인할 수 있도록 한다.
3. 아키텍처 의사결정을 ADR 형태로 체계적으로 관리한다.
4. ServiceId, 패키지 구조, 전문 처리, 보안, DB, 연동, 운영 표준을 통합한다.
5. 개발·검토·테스트·배포 시 사용할 체크리스트를 제공한다.
6. 소스 코드와 Wiki 문서 간의 추적성을 확보한다.
7. 향후 아키텍처 변경 이력을 지속해서 관리할 수 있는 문서 체계를 만든다.

---

## 2. 작업 원칙

다음 원칙을 반드시 준수한다.

1. 저장소의 기존 소스 코드와 문서를 먼저 조사한다.
2. 실제 소스에서 확인된 내용과 설계 제안을 구분한다.
3. 실제 소스에서 확인되지 않은 클래스, 경로, 설정값은 임의로 확정하지 않는다.
4. 확인되지 않은 내용은 반드시 `설계 예시`, `검토 필요`, `미확인` 중 하나로 표시한다.
5. 기존 README, `docs`, 아키텍처 문서, 개발 가이드, 예제 모듈을 최대한 재사용한다.
6. 동일한 내용을 여러 페이지에 중복 작성하지 않고 링크로 연결한다.
7. 모든 페이지는 GitHub Markdown에서 정상적으로 표시되어야 한다.
8. 각 페이지는 제목, 목적, 적용 범위, 본문, 관련 페이지, 점검 항목 구조를 기본으로 사용한다.
9. 표, 코드 블록, Mermaid 또는 ASCII 구성도를 적극적으로 사용한다.
10. 소스 코드는 변경하지 않고 Wiki 문서만 작성한다.
11. Wiki에 쓰기 권한이 없거나 Wiki 기능이 비활성화되어 있으면 임의로 완료했다고 보고하지 않는다.
12. 작업할 수 없는 항목은 원인과 필요한 조치를 명확히 보고한다.

## 9. 우선 작성할 ADR

최소한 다음 ADR을 작성한다.

### ADR-001: 개인정보 마스킹 처리

결정 방향:

- 화면에서는 사용자 표시를 위한 마스킹을 수행한다.
- 서버 비즈니스 계층에서도 응답 데이터가 외부로 전달되기 전에 마스킹 정책을 적용한다.
- 화면 마스킹만으로 개인정보 보호를 완료한 것으로 간주하지 않는다.
- 로그, 파일, 엑셀 다운로드, 외부 인터페이스에도 동일한 정책을 적용한다.
- 권한에 따라 원문 조회가 필요한 경우 별도의 권한 검증과 감사 로그를 적용한다.

담당 영역:

- 단말 아키텍처
- 애플리케이션 아키텍처
- 프레임워크 아키텍처
- 보안 아키텍처
- 운영 아키텍처

### ADR-002: 서버 개발 명명규칙

결정 방향:

- 모듈, 패키지, 클래스, 메서드, DTO, Mapper, SQL ID, ServiceId, 오류코드에 대한 명명규칙을 정의한다.
- 신규 개발은 표준 명명규칙을 반드시 따른다.
- 예외적인 명칭은 아키텍처 승인 후 사용한다.
- 정적 분석 또는 CI 검증으로 위반 여부를 점검한다.

담당 영역:

- 애플리케이션 아키텍처
- 프레임워크 아키텍처

- 품질 담당자

### ADR-003: 전문 필드 암호화

결정 방향:

- 전문 내 민감정보는 서버 비즈니스 계층 또는 공통 연동 컴포넌트에서 필드 단위로 암호화한다.
- 화면에서 수행한 암호화만으로 서버 보안을 대체하지 않는다.
- 암호화 대상 필드, 알고리즘, 키 관리, 복호화 권한을 명확하게 정의한다.
- 로그에 암호화 전 원문을 남기지 않는다.
- MCA·EAI·대외기관과 암호화 규격을 합의한다.

## 14. Wiki 생성 방법

다음 순서로 작업한다.

### 14.1 Wiki 사용 가능 여부 확인

1. 저장소에 Wiki 기능이 활성화되어 있는지 확인한다.
2. Wiki 첫 페이지가 존재하는지 확인한다.
3. Wiki 저장소에 쓰기 권한이 있는지 확인한다.

Wiki Git 저장소는 일반적으로 다음 형식을 사용한다.

```text
https://github.com/changwskr/nsight-tcf-framework-codex.wiki.git
```

### 14.2 Wiki가 활성화된 경우

1. Wiki 저장소를 Clone한다.
2. 기존 Wiki 페이지를 백업하고 분석한다.
3. 기존 문서와 충돌하지 않도록 페이지를 생성하거나 보완한다.
4. `Home.md`, `_Sidebar.md`, `_Footer.md`를 작성한다.
5. 영역별 Markdown 페이지를 생성한다.
6. 내부 링크를 검증한다.
7. 변경사항을 Commit한다.
8. Wiki 원격 저장소로 Push한다.

### 14.3 Wiki가 비활성화된 경우

다음 내용을 결과 보고서에 명확히 기록한다.

- Wiki 기능이 비활성화되어 있음
- 저장소 관리자 권한이 필요함
- 활성화 경로:

```text
Repository → Settings → General → Features → Wikis
```

Wiki 활성화 전에도 작성 결과를 잃지 않도록 다음 경로에 Wiki 초안을 구성할 수 있다.

```text
docs/wiki/
```

다만, 사용자의 명시적인 승인 없이 소스 저장소에 임의로 커밋하지 않는다.

## 15. 검증 기준

작업 완료 전에 다음 사항을 검증한다.

### 구조 검증

- `Home.md` 존재
- `_Sidebar.md` 존재
- `_Footer.md` 존재
- 모든 상위 영역 페이지 존재

- 필수 ADR 10건 존재
- 체크리스트 페이지 존재

### 링크 검증

- 깨진 내부 링크 없음
- Sidebar의 모든 링크 정상
- Home의 주요 링크 정상
- ADR 관련 문서 링크 정상
- 페이지 이름과 링크 이름 일치

### 내용 검증

- 소스 기반 내용과 설계 예시가 구분됨
- 확인되지 않은 내용을 사실처럼 작성하지 않음
- 각 페이지에 목적과 적용 범위가 있음
- 각 표준에 정상·금지 사례가 있음
- 책임 주체가 명확함
- 검증 방법이 포함됨
- 변경 이력 또는 문서 상태가 포함됨

### Git 검증

- 변경 대상이 Wiki 문서로 제한됨
- 민감정보가 포함되지 않음
- 불필요한 대용량 파일 없음
- Commit 메시지가 작업 내용을 명확하게 표현함
- Push 성공 여부 확인

## 18. 금지사항

다음 행위를 하지 않는다.

1. 저장소를 분석하지 않고 일반적인 내용만 작성하지 않는다.
2. 실제로 존재하지 않는 클래스나 파일을 구현된 것처럼 작성하지 않는다.
3. Wiki Push가 실패했는데 성공했다고 보고하지 않는다.
4. 관리자 권한 없이 Wiki 기능을 활성화했다고 보고하지 않는다.
5. 소스 코드를 임의로 수정하지 않는다.
6. 인증정보, 비밀번호, Token, 개인정보를 Wiki에 기록하지 않는다.
7. 기존 Wiki 문서를 확인하지 않고 전체 삭제하거나 덮어쓰지 않는다.
8. 모든 아키텍처 책임을 개발자에게만 할당하지 않는다.
9. 화면 마스킹만으로 개인정보 보호가 완료된다고 정의하지 않는다.
10. 암호화 키나 민감한 보안 설정값을 Wiki에 직접 기록하지 않는다.
