기존 문서는 **Baseline·Evidence·ADR·검증·Push 통제**가 강점이지만, Wiki의 중심축이 문서 관리 절차에 치우쳐 있습니다. 이를 NSIGHT TCF의 실제 이해 순서인 **아키텍처 → TCF 실행구조 → 애플리케이션 구조 → 개발·구현 → 보안·데이터·연계 → 배포·운영 → 검증·거버넌스**로 재편하는 것이 적절합니다. 기존 문서의 Source Evidence, Architecture Gap, ServiceId Registry, 단계별 Gate는 그대로 유지합니다.

# 1. 새로운 Wiki 설계 방향

```text
기존 구조
Architecture
→ ADR
→ Development Guide
→ ServiceId
→ Security
→ Interface
→ Database
→ Operations
→ Checklist

개선 구조
아키텍처 비전과 원칙
→ 전체 시스템 아키텍처
→ TCF 플랫폼 아키텍처
→ 온라인 거래 실행 아키텍처
→ 업무 애플리케이션 아키텍처
→ 개발·구현 가이드
→ 보안·데이터·연계 아키텍처
→ 배포·인프라·운영 아키텍처
→ ADR·추적성·품질 Gate
```

핵심은 개발 문서와 TCF 문서를 아키텍처와 분리하지 않는 것입니다.

```text
아키텍처 원칙
  ↓
TCF가 실행 원칙을 강제
  ↓
업무 애플리케이션이 표준 계층으로 구현
  ↓
개발가이드가 구현 절차를 제공
  ↓
테스트·운영·Architecture Gate가 준수 여부 검증
```

# 3. 최상위 문서 원칙

## 3.1 아키텍처를 최상위 기준으로 사용한다

개발가이드와 구현예제는 독립된 규칙을 만들지 않는다.

모든 구현 문서는 다음 관계를 명시해야 한다.

```text
상위 아키텍처 원칙
→ 적용되는 TCF 구성요소
→ 업무 프로그램 책임
→ 구현 표준
→ 테스트 및 자동검증
→ 운영 확인 항목
```

예를 들어 트랜잭션 구현 문서는 다음을 연결한다.

```text
트랜잭션 아키텍처 원칙
→ Facade 트랜잭션 경계
→ Service·Rule·DAO 책임
→ Rollback 기준
→ Timeout과의 관계
→ 단위·통합 테스트
→ 거래로그·장애 대응
```

## 3.2 TCF를 실행 아키텍처의 중심에 둔다

TCF는 단순 공통 라이브러리로 설명하지 않는다.

다음 공통 실행 통제의 중심으로 정의한다.

```text
표준 전문 검증
→ 인증 문맥 확인
→ 거래 허용 여부 판단
→ Timeout 정책 적용
→ 중복요청 통제
→ 거래로그 시작
→ ServiceId 기반 Handler 실행
→ 정상·업무 오류·시스템 오류 표준화
→ 거래로그·감사로그·Metric 종료
```

## 3.3 현행과 목표를 구분한다

모든 기술 내용은 다음 상태 중 하나로 표시한다.

| 상태             | 의미                                       |
| ---------------- | ------------------------------------------ |
| 구현 확인        | 기준 Commit 소스·설정·테스트에서 확인      |
| 문서 확인        | 공식 문서에서 확인했으나 소스 검증 미완료  |
| 승인 설계        | ADR 또는 공식 설계로 승인                  |
| 목표 아키텍처    | 향후 적용하기로 승인된 구조                |
| 설계 제안        | 검토 중인 대안                             |
| Architecture Gap | 현행과 승인 기준의 차이                    |
| 미확인           | 근거 부족                                  |
| 폐기·대체        | 더 이상 사용하지 않거나 다른 기준으로 대체 |

자료가 충돌할 경우 다음 우선순위를 적용한다.

```text
1. 기준 Commit의 실행 소스
2. 환경설정·빌드·배포 파일
3. 테스트 코드와 실행 증적
4. 동일 버전 README와 docs
5. 승인된 ADR와 아키텍처 정의서
6. 개발가이드와 과거 설계서
7. 회의자료·메모·설계 제안
```

소스가 승인 아키텍처를 위반하면 소스를 정답으로 처리하지 않는다.

```text

승인된 아키텍처 문서
= 준수해야 할 표준

두 자료의 차이

```
