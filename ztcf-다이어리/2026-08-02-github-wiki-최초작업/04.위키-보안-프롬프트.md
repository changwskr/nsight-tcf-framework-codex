# NSIGHT TCF GitHub Wiki 현행 분석 및 추가 콘텐츠 보강 프롬프트

## 1. 역할

너는 다음 역할을 동시에 수행한다.

- 농협 상호금융 NSIGHT 수석 시스템 아키텍트
- NSIGHT TCF Framework 수석 애플리케이션 아키텍트
- Java·Spring Boot·Gradle·MyBatis·Tomcat 전문가
- Gateway·JWT·SSO·MCA·EAI 아키텍트
- 데이터·보안·운영·DevOps 아키텍트
- AI·LLM 기반 개발자동화 아키텍트
- GitHub Wiki 및 기술문서 정보구조 전문가
- 소스·설계·설정·테스트·운영 증적의 정합성을 검증하는 리뷰어

# 2. 작업 목적

다음 GitHub Wiki와 소스 저장소를 분석하라.

| 항목           | 값                                                             |
| -------------- | -------------------------------------------------------------- |
| 소스 저장소    | `changwskr/nsight-tcf-framework-codex`                         |
| Wiki           | `https://github.com/changwskr/nsight-tcf-framework-codex/wiki` |
| 기본 Branch    | 실제 저장소에서 확인                                           |
| 문서 언어      | 한국어                                                         |
| 기술 식별자    | 실제 소스의 영문 이름 유지                                     |
| 작업 범위      | Wiki 분석·추가 페이지 작성·기존 페이지 보완                    |
| 소스코드 변경  | 금지                                                           |
| 기존 Wiki 삭제 | 별도 승인 없이는 금지                                          |
| Wiki Push      | 사용자의 명시적 승인 이후에만 수행                             |

이번 작업은 새로운 Wiki를 처음부터 다시 만드는 것이 아니다.

현재 Wiki의 모든 페이지를 분석하고, 최신 소스·아키텍처 문서·모듈 README와 대조하여 다음 상태를 판정한 뒤 부족한 콘텐츠를 보완하는 것이 목적이다.

```text
현재 Wiki 조사
→ 저장소 최신 기준선 확정
→ Wiki와 소스·설계 대조
→ 누락·중복·노후·불일치 판정
→ 추가 페이지와 보완 페이지 결정
→ 우선순위별 초안 작성
→ 링크·근거·보안 검증
→ 사용자 승인
→ Wiki 반영
```

# 3. 절대 준수 원칙

## 3.1 Wiki를 먼저 조사한다

문서를 작성하기 전에 Wiki Git 저장소를 별도로 조사한다.

```bash
git clone https://github.com/changwskr/nsight-tcf-framework-codex.wiki.git
```

다음 항목을 수집한다.

- 전체 Markdown 페이지
- `Home.md`
- `_Sidebar.md`
- `_Footer.md`
- 페이지별 제목과 링크
- 마지막 수정 Commit
- 고립된 페이지
- 중복 페이지
- 깨진 내부 링크
- 내용이 거의 없는 페이지
- 구현 근거가 표시되지 않은 페이지

Wiki를 조사하지 않고 추측으로 신규 페이지를 만들지 않는다.

## 3.2 Source Baseline을 고정한다

다음을 기록한다.

| 항목              | 기록값 |
| ----------------- | ------ |
| Source Branch     |        |
| Source Commit SHA |        |
| Commit 일시       |        |
| Wiki Commit SHA   |        |
| Wiki 분석일       |        |
| 소스 분석일       |        |
| 분석 도구         |        |
| 검증 도구         |        |

분석 중 최신 Commit이 바뀌더라도 기준 Commit을 자동 변경하지 않는다.

## 3.3 사실 상태를 구분한다

모든 주요 기술 내용은 다음 중 하나로 표시한다.

| 상태               | 의미                                       |
| ------------------ | ------------------------------------------ |
| `구현 확인`        | 기준 Commit의 소스·설정·테스트에서 확인    |
| `문서 확인`        | 공식 문서에서 확인했으나 구현 검증 미완료  |
| `승인 설계`        | ADR 또는 공식 설계서로 승인                |
| `목표 아키텍처`    | 적용하기로 승인되었으나 구현 진행 중       |
| `설계 제안`        | 검토 중인 방안                             |
| `Architecture Gap` | 구현과 승인 표준이 다름                    |
| `미확인`           | 현재 근거로 판단할 수 없음                 |
| `폐기·대체`        | 더 이상 사용하지 않거나 다른 기준으로 대체 |

## 3.4 근거 우선순위

자료가 충돌하면 다음 우선순위를 적용한다.

```text
1. 기준 Commit의 실행 소스
2. 환경설정·Gradle·배포 스크립트
3. 테스트 코드와 실행 증적
4. 해당 모듈의 최신 README
5. zdocs-1/architecture
6. 승인된 ADR와 공식 설계자료
7. 개발 매뉴얼과 과거 설계서
8. 회의자료·메모·설계 제안
```

실제 소스가 승인 아키텍처를 위반하면 다음처럼 기록한다.

```text
소스 = 현재 구현
공식 설계 = 준수해야 할 기준
차이 = Architecture Gap
```

# 4. 1단계 — 기존 Wiki 전수 분석

모든 Wiki 페이지를 다음 매트릭스로 평가한다.

| Wiki 페이지 | 영역            | 내용 상태      | 최신성    | 소스 근거 | 중복      | 링크 상태 | 처리방안                      |
| ----------- | --------------- | -------------- | --------- | --------- | --------- | --------- | ----------------------------- |
| 페이지명    | Architecture 등 | 충분·부분·빈약 | 최신·노후 | 있음·없음 | 없음·있음 | 정상·오류 | 유지·보완·병합·신규·폐기 후보 |

## 4.1 내용 상태

- `충분`: 목적·구조·흐름·책임·오류·운영·검증이 존재
- `부분`: 개념은 있으나 책임·장애·검증 등이 부족
- `빈약`: 제목과 간단한 설명만 존재
- `노후`: 현재 모듈·패키지·버전·처리구조와 불일치
- `근거 없음`: 소스나 공식 문서 경로가 표시되지 않음
- `중복`: 다른 페이지와 동일 기준을 반복 설명
- `고립`: Home·Sidebar·관련 페이지에서 연결되지 않음

## 4.2 완전성 판정

다음 질문에 답하지 못하는 페이지는 보완 대상으로 분류한다.

```text
왜 필요한가?
현재 구조는 무엇인가?
어떤 문제가 있는가?
목표 구조는 무엇인가?
각 구성요소의 책임은 무엇인가?
정상 거래는 어떻게 흐르는가?
오류·Timeout·장애 시 어떻게 동작하는가?
보안·성능·운영 영향은 무엇인가?
어떻게 테스트하는가?
어떻게 자동검증하는가?
어떤 ADR과 연결되는가?
어떻게 변경·폐기하는가?
```

# 18. 금지사항

1. 기존 Wiki를 조사하지 않고 신규 페이지를 만들지 않는다.
2. 소스를 분석하지 않고 일반론만 작성하지 않는다.
3. 실제 존재하지 않는 모듈·클래스·ServiceId를 구현된 것으로 표시하지 않는다.
4. AI 생성 결과를 승인된 업무 규칙으로 간주하지 않는다.
5. 생성 코드를 테스트 없이 정상 구현으로 표시하지 않는다.
6. GitHub Wiki와 `tcf-help`에 동일 내용을 복사하지 않는다.
7. 현재 구현과 목표 아키텍처를 혼합하지 않는다.
8. 최신 Commit을 확인하지 않고 기술버전을 단정하지 않는다.
9. 업무 WAR와 샘플 프로젝트를 같은 성숙도로 표시하지 않는다.
10. 사용자 승인 없이 기존 Wiki 페이지를 삭제하지 않는다.
11. 사용자 승인 없이 Wiki에 Push하지 않는다.
12. 실행하지 않은 검증을 완료로 보고하지 않는다.
13. 실제 비밀번호·Token·Private Key·개인정보를 기록하지 않는다.
14. Wiki 수정만으로 소스·설정·OM 정합성이 확보됐다고 보고하지 않는다.
15. Architecture Gap을 숨기거나 임의로 정상 처리하지 않는다.
