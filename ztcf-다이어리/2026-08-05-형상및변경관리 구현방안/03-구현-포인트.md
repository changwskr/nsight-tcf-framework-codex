# 03. 구현 포인트

출처: [형상및변경관리-구현방안-검토.png](./형상및변경관리-구현방안-검토.png)

슬라이드가 말하는 **구현 시 잡아야 할 포인트**만 추렸다.

## 1. CM Package를 단위로 설계

| 상태 | 진입 조건 | 비고 |
|------|-----------|------|
| 생성 | 분석/설계·구축방안 정의 완료 | 개발 착수 전 게이트 |
| 진행 | 개발Server 작업·테스트·Staging | 형상 변경과 변경 티켓 연결 |
| 종료 | 운영 이관/배포 완료(또는 폐기 승인) | 패키지 클로즈 |

구현 체크:

- Package ID ↔ 요건/변경 요청 ID ↔ 소스 브랜치·태그 ↔ 배포 이력 연결
- 미종료 Package의 운영 재배포 규칙 명시

## 2. 역할 기반 권한

| 역할 | 허용 예시 | 금지 예시 |
|------|-----------|-----------|
| 현업 | 요청, 인수 승인 | 운영 직접 배포 |
| AM | 요건·이관의뢰 | 임의 소스 커밋(정책에 따름) |
| 아키텍트 | 영향도·아키텍처 승인 | 운영 배포 단독 실행 |
| PM | 구축방안·일정 | 형상 저장소 무단 우회 |
| 개발자 | Check-in/out (개발) | Staging/운영 무단 반영 |
| 변경관리자 | Staging 승격·운영 이관 | 요건 임의 변경 |

## 3. 환경 승격 (Dev → Staging → Prod)

```text
개발Server  (형상관리: 소스 버전 확정)
    │  변경관리 승인
    ▼
Staging     (3자 → 인수)
    │  이관의뢰 + 변경관리자 실행
    ▼
운영Server  (배포 → CM 종료 / ITSM 연계)
```

- 소스 **반입/반출**은 형상관리 경로만
- **서버 간 이동**은 변경관리 승인·증적 필수

## 4. 통합 포인트

| 연계 | 목적 |
|------|------|
| PMS ↔ CM Package | 산출물 등록·추적 |
| 영향도분석 / 모델링 ↔ 설계 게이트 | 현행 아키텍처 확인·모델 등록 |
| 형상관리 ↔ 소스코드점검 | 반입 전/후 품질 게이트 |
| 변경관리 ↔ 테스트 도구 | 단계별 테스트 증적 |
| 운영 ↔ ITSM·통합관제 | 장애/문제관리 핸드오프 |
| iQMS | 전 구간 프로세스·품질 기준 |

## 5. 형상관리 / 변경관리 책임 경계 (구현 계약)

| 관심사 | 담당 |
|--------|------|
| 브랜치, 태그, 빌드 산출물 버전 | 형상관리 |
| 누가 언제 어느 환경에 올렸는가 | 변경관리 |
| 요건·영향도·구축방안 문서 | PMS(+iQMS) |
| 운영 장애 티켓 | ITSM |

이 경계를 한 시스템에 뭉개면 “배포는 됐는데 소스 기준선이 없음” 또는 “소스는 있는데 이관 승인이 없음”이 생긴다.

## 6. 하네스·PDMP와의 느슨한 연결 (참고)

본 슬라이드는 전사 CM/이관 방안이다. 로컬 AI 하네스와는 층이 다르다.

| 전사 CM | 로컬(`tcf-harness-*` / `pdmp-service`) |
|---------|----------------------------------------|
| CM Package · Staging · 운영 이관 | phase·브랜치·PR·로컬 test/war |
| 변경관리자 승인 | 사용자 승인 게이트 |
| 형상 Check-in | Git commit (자동 push 금지 규칙과 정합) |

PDMP 작업 시에도 **“소스 기준선(형상)”과 “환경 반영(변경)”을 문서/증적에서 분리**하면 이 도식과 맞는다.
