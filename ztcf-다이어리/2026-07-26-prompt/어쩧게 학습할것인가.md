NSIGHT-TCF-FRAMEWORK의 프롬프트는 단순히 “코드를 만들어라”라고 지시하는 방식보다, **실제 소스 확인 → 차이 분석 → 설계 판단 → 구현 → 증적 검증**을 강제해야 합니다.

특히 NSIGHT는 요구사항부터 화면·ServiceId·프로그램·SQL·OM·테스트·운영로그까지 연결되는 구조이므로, 프롬프트도 동일한 추적 관계를 유지해야 합니다. 또한 반복 가능한 골격은 자동화하되 업무 규칙·데이터 소유권·트랜잭션·보안·운영 위험은 사람이 판단하도록 구분해야 합니다. 완료 여부도 “문서나 코드가 만들어졌는가”가 아니라 설계·소스·설정·OM·시험·운영 증적이 일치하는지로 판정해야 합니다.

아래는 이 원칙을 반영한 **NSIGHT-TCF 영역별 표준 프롬프트 라이브러리**입니다.

# NSIGHT-TCF-FRAMEWORK 영역별 표준 프롬프트 라이브러리

## 1. 도입 전 안내말

본 프롬프트 라이브러리는 다음 방식으로 사용한다.

```text
P0 공통 마스터 프롬프트
        +
P1~P15 영역별 실행 프롬프트
        +
사용자가 제공하는 업무 입력값
```

예를 들어 신규 업무 모듈을 만들 때는 다음과 같이 조합한다.

```text
P0 공통 마스터 프롬프트
+ P2 신규 업무 모듈 개발 프롬프트
+ 업무코드·도메인·테이블·화면정보
```

CRUD 거래 하나를 만들 때는 다음과 같이 사용한다.

```text
P0 공통 마스터 프롬프트
+ P3 화면·테이블 기반 CRUD 프롬프트
+ 화면 이벤트·입출력·테이블 정의
```

# 21. 핵심 아키텍처 판단

NSIGHT-TCF에서 가장 효과적인 프롬프트는 다음 다섯 가지를 반드시 포함한다.

```text
첫째, 실제 소스를 먼저 확인한다.

둘째, 확인된 사실과 설계 예시를 분리한다.

셋째, 화면에서 운영로그까지 추적한다.

넷째, 정상뿐 아니라 오류·Timeout·장애를 검증한다.

다섯째, 코드 생성이 아니라 증적 확인을 완료기준으로 삼는다.
```

따라서 프롬프트의 최종 구조는 다음과 같아야 한다.

```text
역할
→ 기준자료
→ 입력정보
→ 선행 분석
→ 설계 판단
→ 구현
→ 테스트
→ 운영 검증
→ 완료 증적
→ 변경관리
```

이 라이브러리의 핵심은 `P0`를 고정하고 상황에 따라 `P1~P15`만 결합하는 것입니다. 신규 업무 개발에는 기존 정상 업무 모듈의 실제 파일과 Handler 등록방식을 먼저 확인하도록 강제하는 것이 중요합니다.
