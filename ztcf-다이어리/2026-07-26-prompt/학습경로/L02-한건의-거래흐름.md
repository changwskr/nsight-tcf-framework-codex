## 이 단계에서 얻는 것

`POST /{biz}/online` 한 번이 **어느 클래스 순서로** 실행되는지 끝까지 추적한다.  
TCF의 “공통 파이프라인”이 추상 설명이 아니라 **호출 사슬**이 된다.

## 왜 이 순서인가

지도(L01)만으로는 “실행”이 보이지 않는다.  
한 거래의 정방향 추적이 프레임워크 이해의 척추다.

## 지금 이 질문을 붙여 넣으세요

```text
P0 + P4를 적용한다. 리팩터링/신규코드는 금지. 실제 소스 추적만 한다.

출발점: 업무 모듈의 표준 온라인 진입점 (OnlineTransactionController 또는 동등 클래스)
분석 대상: 현재 Branch, 기준 모듈은 eb-service (없으면 존재하는 업무 WAR 중 하나)

정방향으로만 추적하라.

화면/HTTP 요청
→ 표준 전문
→ Controller
→ TCF.process()
→ STF
→ TimeoutExecutor
→ TransactionDispatcher
→ TransactionHandler
→ Facade → Service → Rule → DAO → Mapper → DB
→ ETF → 표준 응답 → 로그

각 단계마다 표로 적어라:
| 단계 | 파일 경로 | 클래스 | 메서드 | 다음 호출 | 확인 근거 |

추가로:
1. ServiceId가 Dispatcher에서 Handler로 매핑되는 지점을 정확히 찍어라.
2. Timeout이 어디에 걸리는지, 업무 코드가 Timeout을 직접 다루는지 여부를 밝혀라.
3. 오류 시 응답이 어디서 표준화되는지 찾아라.
4. GUID / TraceId / ServiceId가 로그에 남는 위치를 찾아라. (없으면 '확인 불가')

문자열 검색만으로 단정하지 말고, 실제 호출 관계를 교차 검증하라.
최종에 "한 문단 요약 + 내가 암기할 호출 체인 한 줄"을 남겨라.
```

## 읽을 자료 / 열 파일

- `tcf-web` 온라인 컨트롤러·게이트웨이 관련 클래스
- `tcf-core`의 TCF / STF / ETF / Dispatcher / Timeout
- `eb-service`(또는 `av-service`)의 Handler 1개

## 자기 점검

1. Handler는 언제 등장하는가? (파이프라인 앞/뒤)  
2. Facade의 책임은 트랜잭션인가 업무규칙인가?  
3. Timeout을 업무 Service에 넣으면 안 되는 이유는?  

## 통과 기준

- 호출 체인을 보지 않고 한 줄로 말할 수 있다.  
- Dispatcher ↔ serviceId 매핑 위치를 파일로 가리킬 수 있다.
