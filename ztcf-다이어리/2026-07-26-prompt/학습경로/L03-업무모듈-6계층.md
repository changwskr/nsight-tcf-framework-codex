## 이 단계에서 얻는 것

업무 WAR 안의 `entry / application / persistence / client / config / support`  
각 계층이 **무엇을 해도 되고 무엇을 하면 안 되는지**를 책임 언어로 고정한다.

## 왜 이 순서인가

흐름(L02)을 안 뒤에야 “이 코드가 어느 상자에 들어가야 하는지”가 납득된다.  
신규모듈(P2) 실습은 이해 후에(L11) 한다.

## 지금 이 질문을 붙여 넣으세요

```text
P0를 적용한다. 기준 모듈: eb-service (보조로 av-service 비교 가능). 코드 생성 금지.

1. 6계층 패키지 규약을 실제 디렉터리 트리로 보여라. (README + 실제 폴더)
2. Handler / Facade / Service / Rule / DAO / Mapper 각각에 대해:
   - 한 줄 책임
   - 허용 의존
   - 금지 행위
   - eb-service에서 대표 클래스 1개 경로
   를 표로 작성하라.
3. P3 금지사항(업무 Controller 생성, Handler에 업무로직, Service→Mapper 직호출 등)을
   이 저장소의 "위반하면 깨지는 이유"와 연결해 설명해라.
4. DTO가 application / persistence에 나뉘는 이유를 Request·Row 예시로 보여라.
5. "도메인당 Handler 1개, serviceIds()로 다중 거래" 규칙이
   실제 Handler 코드에서 어떻게 표현되는지 인용하라.

마지막에 퀴즈 5문항(정답은 바로 쓰지 말고 힌트만)을 만들어라.
내가 다음에 답하게 하라.
```

## 읽을 자료 / 열 파일

- 루트 README 「업무 WAR 패키지 규약」
- `eb-service/.../entry/handler`, `.../application`, `.../persistence`
- `av-service` 동등 경로 (우리가 만든 샘플)

## 자기 점검

1. Rule에서 DB를 호출하면 무엇이 깨지는가?  
2. DAO에서 업무 메시지를 조립하면 무엇이 깨지는가?  
3. 새 거래 추가 시 새 Handler를 무조건 만드는가?  

## 통과 기준

- 6계층을 역할 문장으로 설명 가능.  
- 금지사항을 “규칙”이 아니라 “부작용”으로 설명 가능.
