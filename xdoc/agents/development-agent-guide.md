# 개발 에이전트 지침

이 문서는 사람과 AI 개발 에이전트가 NSIGHT TCF Framework를 안전하고 일관되게 변경하기 위한 작업 규칙이다.

## 작업 시작 순서

1. 요청 범위와 완료 조건을 확인한다.
2. `git status --short`로 기존 변경을 확인하고 사용자 변경을 보존한다.
3. 루트 `README.md`, 대상 모듈 `README.md`, `build.gradle`을 읽는다.
4. 호출부, 구현부, 설정, 테스트와 문서를 함께 검색한다.
5. 변경 영향이 여러 모듈에 걸치면 실행 계획을 작성한다.

## 탐색 원칙

- 파일 검색은 `rg --files`, 코드 검색은 `rg`를 우선 사용한다.
- 클래스 이름만 보지 않고 Spring Bean 등록, AutoConfiguration과 설정 조건을 확인한다.
- `serviceId` 변경 시 Handler, UI, Service Catalog, 샘플 요청과 문서 사용처를 모두 검색한다.
- 설정 변경 시 `application.yml`, Profile별 설정과 환경변수 사용처를 함께 확인한다.
- 문서 설명보다 코드와 테스트가 우선하되, 불일치는 결과물에 명시한다.

## 변경 원칙

- 요청 범위를 벗어난 대규모 정리나 이름 변경을 섞지 않는다.
- 기존 계층과 패키지 구조를 유지한다.
- 공통 TCF 정책을 업무 모듈에 재구현하지 않는다.
- 다른 작업자가 만든 미커밋 변경을 덮어쓰거나 되돌리지 않는다.
- 생성 파일, 로그, 로컬 DB와 비밀정보를 커밋하지 않는다.
- 코드와 문서는 UTF-8을 유지한다.

## 모듈별 주의점

### `tcf-util`

- Spring 의존성을 추가하지 않는다.
- 범용성 없는 업무 로직을 넣지 않는다.

### `tcf-core`

- 표준 전문과 Handler 계약 변경은 호환성 영향을 평가한다.
- STF/ETF 순서 변경 시 오류와 정리 경로를 함께 검증한다.
- ThreadLocal 또는 MDC 컨텍스트는 항상 정리한다.

### `tcf-web`

- AutoConfiguration 조건과 Bean 중복 가능성을 확인한다.
- DataSource, Transaction Manager와 MyBatis 설정의 조합을 검증한다.
- 외부 입력과 인증 필터 순서를 고려한다.

### 업무 서비스

- 도메인당 Handler 하나와 `serviceIds()` 등록 원칙을 따른다.
- Facade에 트랜잭션 경계를 두고 Service와 Rule의 책임을 분리한다.
- SQL은 Mapper 또는 DAO에 둔다.

### 운영 및 Gateway 모듈

- 인증 우회와 내부 호출 판정 로직은 보안 검토 없이 완화하지 않는다.
- 관리 API 변경 시 UI Relay, 권한과 감사 로그 영향을 확인한다.

## 검증 전략

변경한 가장 작은 단위부터 검증하고 필요에 따라 범위를 넓힌다.

```powershell
# 대상 모듈 테스트
.\gradlew.bat :tcf-core:test

# 대상 모듈 빌드
.\gradlew.bat :sv-service:build

# 전체 빌드
.\gradlew.bat build
```

검증할 수 없는 경우 실패한 명령, 원인과 미검증 범위를 명확히 기록한다.

## 결과 보고

- 무엇이 변경되었는지 먼저 설명한다.
- 변경 파일과 핵심 설계 결정을 짧게 정리한다.
- 수행한 테스트와 결과를 기록한다.
- 기존 미커밋 변경, 위험 요소와 후속 작업을 구분한다.
- 실행하지 않은 테스트를 실행한 것처럼 표현하지 않는다.
