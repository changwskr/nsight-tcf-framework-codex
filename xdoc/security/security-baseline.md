# 보안 기준

## 기본 원칙

- 모든 외부 입력은 신뢰하지 않는다.
- 인증과 권한 검사는 업무 코드에서 임의로 생략하지 않는다.
- 최소 권한과 기본 거부 원칙을 적용한다.
- 비밀정보와 개인정보는 코드, 문서, 로그와 테스트 데이터에 저장하지 않는다.
- 보안 통제를 완화하는 변경은 근거, 영향과 대체 통제를 문서화한다.

## 요청 및 표준 전문

- 필수 Header와 Body 필드를 검증한다.
- Path의 Business Code와 Header 값이 충돌할 때 처리 규칙을 명확히 한다.
- 문자열 길이, 허용 문자, 숫자 범위와 컬렉션 크기를 제한한다.
- 역직렬화된 Map 값을 바로 SQL, 파일 경로 또는 명령에 사용하지 않는다.
- 오류 응답에 내부 클래스명, SQL과 스택 추적을 노출하지 않는다.

## 인증과 권한

- Gateway와 JWT Filter의 검증 결과를 서버 측에서 확인한다.
- 서명 알고리즘, Issuer, Audience와 만료 시간을 검증한다.
- 내부 호출 표식은 외부 사용자가 위조할 수 없는 신뢰 경계에서만 인정한다.
- 인증 면제 목록은 최소화하고 변경 시 회귀 테스트를 추가한다.
- OM 및 관리 기능은 기능 권한과 데이터 권한을 함께 검토한다.

## 세션과 쿠키

- 세션 ID를 로그에 원문으로 출력하지 않는다.
- 운영 쿠키에는 `Secure`, `HttpOnly`와 적절한 `SameSite` 정책을 적용한다.
- 세션 고정, 재사용과 만료 시나리오를 검증한다.
- 로그아웃과 권한 변경 시 세션 무효화 정책을 확인한다.

## 데이터 접근

- MyBatis 파라미터 바인딩을 사용하고 문자열 연결 SQL을 피한다.
- 동적 컬럼이나 정렬 키는 허용 목록으로 검증한다.
- DB 계정은 모듈과 역할에 필요한 최소 권한만 가진다.
- 개인정보 조회와 변경은 감사 가능해야 한다.
- 파일 업로드·다운로드는 경로 순회, 확장자, 크기와 접근 권한을 검증한다.

## 로그와 관측성

다음 값은 원문으로 기록하지 않는다.

- 비밀번호, Access/Refresh Token, Private Key
- 세션 ID와 인증 Cookie
- 주민등록번호, 계좌번호와 카드번호
- 전체 요청·응답 Body에 포함될 수 있는 개인정보

추적에는 GUID, Trace ID, `serviceId`와 비식별 운영 정보를 사용한다. 필요한 개인정보는 승인된 마스킹 규칙을 적용한다.

## 설정과 공급망

- Secret은 환경변수 또는 승인된 Secret Store에서 주입한다.
- 운영 Secret 기본값을 저장소에 두지 않는다.
- 의존성 버전은 Gradle 설정과 BOM에서 일관되게 관리한다.
- 외부 라이브러리 추가 시 필요성, 라이선스와 취약점 영향을 검토한다.
- CI 로그와 빌드 산출물에 Secret이 포함되지 않는지 확인한다.

## 보안 검토 체크리스트

- [ ] 새로운 외부 입력과 신뢰 경계를 식별했다.
- [ ] 인증 및 권한 실패 경로를 테스트했다.
- [ ] SQL, 파일, URL과 명령 주입 가능성을 검토했다.
- [ ] 로그와 오류 응답의 민감정보 노출을 확인했다.
- [ ] Secret 또는 운영 환경값이 커밋되지 않았다.
- [ ] 타임아웃과 자원 제한이 서비스 거부 위험을 완화한다.
- [ ] 보안 관련 설정의 Local/Dev/Prod 차이를 검토했다.
