# 02 — 분석 단계 프롬프트

## 목표

승인된 요건을 기준으로 현행 구조, 영향 범위, 데이터·연계·보안·운영 제약을 분석하고 `docs/work-items/${workItemId}/analysis.md`를 작성한다.

## 필수 입력

- 승인된 `requirement.md`
- `AGENTS.md`, `ARCHITECTURE.md`
- 관련 소스·설정·테스트·DB 정의
- 현재 Branch와 Commit SHA

## 분석 절차

1. 승인된 요건별 분석 질문을 작성한다.
2. 관련 모듈, 패키지, 프로그램, 설정, 테스트를 정방향·역방향으로 탐색한다.
3. 현행 처리 흐름과 책임 경계를 작성한다.
4. 변경 영향 파일과 영향 서비스를 식별한다.
5. 데이터 소유권, 트랜잭션, 외부 연계, 권한, 감사 요구를 분석한다.
6. 기능·성능·보안·운영 위험과 미확정 사항을 등록한다.
7. 구현하지 않고 설계에서 결정해야 할 항목을 분리한다.

## 산출물 구조

```text
1. 도입 전 안내말
2. 문서 개요
3. 문제 정의 및 분석 배경
4. 승인 요건 추적표
5. 현행 구조와 처리 흐름
6. 관련 프로그램·설정·데이터 현황
7. 변경 영향 분석
8. 요구사항과 제약조건
9. 데이터·상태·트랜잭션 분석
10. 보안·개인정보·감사 분석
11. 성능·운영·장애 분석
12. 위험·Gap·미결사항
13. 설계 단계 결정 필요사항
14. 분석 완료 체크리스트
15. 시사점
16. 마무리말
```

## 금지사항

- 설계 대안을 분석 결과처럼 확정하지 않는다.
- 소스에서 확인되지 않은 클래스·테이블을 현행으로 단정하지 않는다.
- 승인 요건을 임의로 확대하거나 축소하지 않는다.

## 완료 Gate

요건별 영향 범위와 설계 결정 필요사항이 추적 가능해야 하며 사용자 수동 승인을 받아야 한다.
