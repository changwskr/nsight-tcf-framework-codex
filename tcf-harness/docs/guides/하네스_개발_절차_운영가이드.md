# 하네스 기반 SI 개발 절차 운영가이드

## 1. 도입 전 안내말

본 하네스는 요건서·분석서·설계서·소스·테스트 로그를 각각 생성하는 도구가 아니다. 하나의 작업 ID를 기준으로 이 산출물들의 선후관계와 승인 상태를 통제하는 최소형 개발 플랫폼이다.

```text
요건이 승인되지 않으면 분석하지 않는다.
분석이 승인되지 않으면 설계하지 않는다.
설계가 승인되지 않으면 구현하지 않는다.
구현이 승인되지 않으면 테스트하지 않는다.
테스트 증적이 승인되지 않으면 완료하지 않는다.
```

## 2. 문서 개요

### 2.1 목적

SI 개발 과정에서 요구사항 누락, 설계–구현 불일치, 무증적 테스트 완료, 에이전트의 과도한 변경을 방지한다.

### 2.2 적용범위

- 신규 기능과 변경 개발
- Java·Spring 기반 업무 애플리케이션
- 사내 DAVIS CODER·Codex CLI·범용 명령형 에이전트
- Git 저장소와 Markdown 중심 프로젝트

### 2.3 대상 독자

아키텍트, 업무분석가, 개발자, 테스트 담당자, PMO, 운영자, 개발 플랫폼 담당자.

### 2.4 선행조건

- Java 21
- Git CLI
- 대상 저장소의 Clean 상태
- Gradle 또는 프로젝트별 빌드도구
- 실행 가능한 에이전트 명령 또는 수동 에이전트 실행 절차

### 2.5 용어 정의

| 용어 | 정의 |
|---|---|
| Work Item | 요건부터 종료까지 추적하는 작업 단위 |
| Gate | 다음 단계 진입을 허용하는 수동 승인점 |
| 기준선 | 승인되어 후속 단계가 임의 변경할 수 없는 산출물 |
| 실행계약 | 에이전트의 `prompt.md`, `context.json`, 결과·로그 파일 집합 |
| 증적 | 명령, 종료코드, 로그, 환경정보, 변경파일, Diff |

## 3. 본문

### 3.1 문제 정의 및 설계 배경

일반적인 SI 절차는 문서상으로 요건·분석·설계·구현·테스트를 구분하지만 실제 개발에서는 단계가 겹치고 승인되지 않은 정보가 코드로 먼저 구현되는 문제가 발생한다. 에이전트 자동화는 이 문제를 해결할 수도 있지만, 통제 없이 적용하면 잘못된 패턴을 더 빠르게 확산시킬 수 있다.

### 3.2 현행 구조와 문제점

| 문제 | 결과 |
|---|---|
| 대화창에만 요건 존재 | 후속 실행에서 문맥 유실 |
| 분석·설계 승인 없이 코드 생성 | 재작업과 범위 확장 |
| 테스트 명령을 에이전트가 임의 선택 | 성공 기준 변형 |
| 실패 로그 미보존 | 원인과 수정 근거 확인 불가 |
| 현재 브랜치 직접 변경 | 기존 개발 작업 오염 |
| 거대한 단일 프롬프트 | 중요 제약 누락과 문서 노후화 |

### 3.3 요구사항과 제약조건

- 가장 단순한 CLI로 시작한다.
- 저장소 내부의 Markdown·JSON을 기준원으로 사용한다.
- 모든 단계에 수동 승인 Gate를 둔다.
- 원격 Push·Merge는 자동화하지 않는다.
- 특정 LLM 제품에 종속되지 않는다.
- Windows와 Linux에서 동작 가능한 Java 기반으로 구성한다.

### 3.4 설계 원칙

1. 작은 진입점과 단계별 문서
2. 승인된 기준선 보호
3. 파일 기반 재현성
4. 명령과 결과의 기계적 증적
5. 자율성보다 안전한 중단 우선
6. 후속 웹 플랫폼 전환 가능한 상태모델

### 3.5 대안 비교 및 의사결정

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Shell CLI | 매우 작음 | Windows·상태관리 취약 | 제외 |
| Python CLI | 구현 용이 | NSIGHT Java 운영체계와 분리 | 대안 |
| Java Spring Boot CLI | 기존 기술체계·확장성 | 초기 의존성 큼 | 선택 |
| 웹 플랫폼 | 가시성 우수 | MVP 범위 과대 | 후속 |

### 3.6 목표 아키텍처

```text
CLI
→ Command Router
→ Lifecycle/Gate Services
→ State·Audit Repository
→ Prompt Contract
→ Command Adapter
→ Source/Test Process
→ Evidence Writer
```

### 3.7 표준 형식

- 작업 ID: `REQ-YYYYMMDD-NNN`
- 작업 브랜치: `harness/{작업ID}-{기능명}`
- 상태파일: `.harness/state/{작업ID}.json`
- 작업문서: `docs/work-items/{작업ID}/`
- 실행계약: `.harness/work/{작업ID}/{단계}/`

### 3.8 구성요소 및 속성

| 구성요소 | 주요 속성 |
|---|---|
| WorkItemState | 작업 ID, Branch, 현재 단계, 단계 상태, 답변, 테스트 명령 |
| GateService | 선행 승인, REVIEW, 수동 결정 |
| PromptService | 마스터·단계 프롬프트 조합, Context 생성 |
| Agent Adapter | 명령 배열, Timeout, stdout·stderr |
| Test Executor | 승인 명령, 최대 3회, 증적 |
| GitService | Clean, Branch, SHA, Diff |

### 3.9 책임 경계와 RACI

| 활동 | 사용자 | 하네스 | 에이전트 |
|---|---|---|---|
| 요건 결정 | A/R | C | C |
| 상태전이 통제 | A | R | I |
| 분석·설계 초안 | A | C | R |
| 코드 변경 | A | C | R |
| 테스트 명령 승인 | A/R | C | I |
| 테스트 실행 | A | R | R |
| 최종 완료 | A/R | C | I |

### 3.10 정상 처리 흐름

```text
init
→ 12문항 답변
→ 요건 REVIEW·승인
→ 분석 생성·승인
→ 설계·실행계획 생성·승인
→ 테스트 우선 구현·승인
→ 승인 명령 테스트
→ 증적 검토·승인
→ 종료보고서
```

### 3.11 오류·Timeout·장애 흐름

| 상황 | 처리 |
|---|---|
| Git Dirty | 초기화 중단 |
| 선행 단계 미승인 | 다음 단계 차단 |
| 에이전트 Timeout | 종료코드 124·로그 보존·사람 검토 |
| 산출물 누락 | REVIEW 전환 금지 |
| 테스트 실패 | 최대 3회 수정 루프 |
| 3회 실패 | `NEEDS_HUMAN_REVIEW` |
| 보안·데이터 위험 | 즉시 중단·에스컬레이션 |

### 3.12 정상 예시

```bash
java -jar harness.jar init --repo . --id REQ-20260802-001 --title "고객 조회"
java -jar harness.jar requirement next --repo . --id REQ-20260802-001
java -jar harness.jar approve --repo . --id REQ-20260802-001 --stage REQUIREMENT --decision APPROVED
```

### 3.13 금지 예시

```text
- main 브랜치에서 직접 구현
- 테스트 실패 후 테스트를 @Disabled 처리
- 설계서 없이 DB 컬럼 변경
- 로그에 Access Token 기록
- 외부 에이전트 성공 메시지만으로 완료 판정
```

### 3.14 연계 규칙

에이전트 제품은 명령어 어댑터로 연결한다. 하네스는 제품별 대화 API를 알지 않으며 입력·출력 파일과 프로세스 종료코드만 계약으로 사용한다.

### 3.15 데이터 및 상태관리

상태는 JSON, 이력은 JSONL, 산출물은 Markdown, 실행증적은 로그·JSON·Patch로 관리한다. 중앙 DB 없이 Git으로 버전관리할 수 있는 형태를 유지한다.

### 3.16 성능·용량·확장성

MVP는 한 번에 한 작업을 로컬에서 처리한다. 후속 단계에서 파일 잠금, 병렬 Work Item, 중앙 이벤트 저장소, 웹 UI를 추가할 수 있다.

### 3.17 보안·개인정보·감사

- Credential은 설정 파일에 직접 기록하지 않는다.
- 실행 명령 인수에 비밀정보를 넣지 않는다.
- 프롬프트에 개인정보 원문을 넣지 않는다.
- 승인·명령·오류·재시도는 감사 JSONL에 기록한다.

### 3.18 운영·모니터링·장애 대응

운영자는 작업 ID로 상태, 실행계약, 테스트 증적, Diff를 조회한다. 프로세스 장애 시 파일 기반 입력으로 동일 단계를 재실행한다.

### 3.19 자동검증 및 품질 Gate

- 상태전이 선행조건
- 작업 ID·Branch 형식
- 필수 산출물 존재
- 승인 테스트 명령 존재
- 실행 종료코드·Timeout
- 변경파일·Diff 생성
- 최대 반복 횟수

### 3.20 테스트 시나리오

1. 상태 JSON 저장·복원
2. 12문항 개수와 순서
3. 요건 미승인 분석 차단
4. Clean 저장소 전용 Branch 생성
5. 프롬프트 계약 파일 생성
6. Gradle 테스트 명령 후보 탐지
7. 3회 실패 후 사람 검토 전환
8. 전체 생명주기 승인 완료

### 3.21 체크리스트

### 3.22 변경·호환성·폐기 관리

상태 스키마와 단계 의미는 공개 계약으로 관리한다. 상태 필드 삭제, 단계 추가, 승인 의미 변경은 마이그레이션과 호환성 검증을 동반한다.

## 4. 시사점

### 4.1 핵심 아키텍처 판단

MVP의 핵심은 LLM의 지능이 아니라 승인된 의도, 구조화된 저장소 지식, 제한된 실행권한, 재현 가능한 검증 루프다.

### 4.2 주요 위험

- 에이전트 명령의 제품별 차이
- 문서와 코드의 드리프트
- 사용자의 형식적 승인
- 임의 Shell 명령 승인에 따른 위험
- 네트워크 차단 환경의 의존성 공급

### 4.3 우선 보완 과제

1. 공식 Gradle Wrapper와 사내 Maven Proxy 적용
2. JSON Schema 자동검증
3. ArchUnit·명명규칙·금지 API 검사
4. 작업별 Git Worktree 격리
5. 에이전트 독립 검토 단계

### 4.4 중장기 발전 방향

CLI 상태모델을 유지한 채 웹 UI, 중앙 승인함, Worktree 실행환경, 로그·Metric·Trace 분석, 주기적 문서 정리 에이전트로 확장한다.

## 5. 마무리말

이 하네스는 에이전트에게 모든 권한을 주는 시스템이 아니다. 에이전트가 빠르게 일해도 요건, 설계, 변경, 테스트, 승인 근거가 사라지지 않도록 만드는 최소 통제 기반이다.
