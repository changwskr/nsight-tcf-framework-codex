# 통합 CRUD 개발 프롬프트 아키텍처 정의서 패키지 설계

## 1. 목적

`nsight-tcf-framework-codex`의 통합 CRUD 개발 프롬프트 패키지를 개발자와 AI 에이전트 운영자가 이해하고 실행·검증·복구할 수 있도록 아키텍처 정의서와 부속 문서를 작성한다.

정의서는 기존 C00~C18 기반 절차를 현재 구조(As-Is)로 설명하고, 단일 진입점과 명시적 상태 계약을 갖는 목표 구조(To-Be), 전환 절차 및 검증 기준을 함께 정의한다.

## 2. 독자

주 독자는 다음과 같다.

- CRUD 프롬프트를 사용해 업무 기능을 개발하는 개발자
- Codex와 Cursor에서 프롬프트 실행을 운영하는 AI 에이전트 운영자

AA, 품질 담당자와 문서 검토자는 보조 독자다. 문서는 추상적 설명보다 실행 계약, 상태 전이, 실패 복구와 검증 증적을 우선한다.

## 3. 범위

### 3.1 포함 범위

- 기존 C00~C18 및 C15 실행 프롬프트의 As-Is 구조
- `MASTER-CRUD-DEVELOPER`, `STANDALONE-CRUD-DEVELOPER`, `CRUD-REQUEST-TEMPLATE`의 To-Be 구조
- 사용자, Codex/Cursor, 저장소, Gradle과 결과 문서의 시스템 Context
- 프롬프트 구성요소와 책임 경계
- 단계별 입력·출력·상태 전이·Gate 계약
- 신규 요구사항과 기존 결과폴더 실행 흐름
- 오류 분류, 안전 통제, 중단과 재개
- 검증, 추적성, 완료 판정과 전환 계획

### 3.2 제외 범위

- NSIGHT TCF Framework 전체 아키텍처 재작성
- 업무 모듈별 상세 설계
- 배포 또는 운영 환경 변경
- 프롬프트 구현 자체
- 기존 C00~C18 자산의 삭제

## 4. 작성 접근법

본문은 C4의 Context·Container·Component 관점을 필요한 수준만 적용하는 C4-lite 구조를 사용한다. 여기에 프롬프트 실행 상태 머신과 단계별 실행 계약을 결합한다.

기존 A00~A18 아키텍처 방법론 전체를 반복하지 않고 다음 항목만 흡수한다.

- 대안과 결정 근거
- 보안과 개인정보
- 운영과 장애 대응
- 요구사항 추적성
- Architecture Gate

## 7. As-Is 아키텍처

현재 흐름은 다음과 같다.

```text
C00~C14 설계 프롬프트
  → 결과 마크다운·확정정보원장
  → 별도 C15 실행 프롬프트
  → 코드 생성
  → C16~C18 검증·추적·완료
```

유지할 자산은 다음과 같다.

- 단계별 상세 질문과 완료 조건
- `_확정정보원장.md`
- C14 설계 Gate
- C15 코드 생성 규칙
- C16~C18 검증·추적성·완료 기준
- 역할별 에이전트 지침

As-Is의 핵심 개선 대상은 다음과 같다.

- 신규 요구사항과 기존 결과폴더 실행 진입점이 분리됨
- 실행 환경이 현재 단계와 승인 상태를 일관되게 복원할 단일 계약이 부족함
- Codex와 Cursor 사이의 중단·재개 및 작업 인계 규칙이 분산됨
- 완료 판정과 오류 복구 규칙이 여러 문서에 나뉨

## 8. To-Be 아키텍처

### 8.1 구성요소

| 구성요소 | 책임 |
| --- | --- |
| `MASTER-CRUD-DEVELOPER` | 저장소 연동형 단일 진입점, 모드 판별과 상태 전이 통제 |
| `STANDALONE-CRUD-DEVELOPER` | 문서 참조가 어려운 환경을 위한 핵심 규칙 내장형 |
| `CRUD-REQUEST-TEMPLATE` | 선택 입력 양식 |
| C00~C18 | 상세 설계·구현·검증 지식의 SoT |
| `_확정정보원장` | 도메인별 확정값, 가정, 충돌과 Open Issue |
| `AGENTS.md`와 역할 문서 | 저장소, 계층, 보안과 검증 규칙 |
| 실제 소스·설정·테스트 | 구현 사실의 근거 |
| Codex/Cursor | 동일 실행 계약을 수행하는 에이전트 환경 |

기존 C15 실행 프롬프트는 삭제하지 않고 호환 진입점으로 유지한다.

### 8.2 우선순위

구성요소 간 정보 우선순위는 다음과 같다.

```text
사용자 현재 지시
→ 범위별 AGENTS.md
→ 승인된 원장과 C00~C14
→ 역할 문서
→ 실제 코드·설정·테스트
→ 프롬프트 기본값
```

원장과 실제 구현이 충돌하면 자동으로 하나를 선택하지 않고 `DESIGN_CONFLICT`로 처리한다.

## 9. 상태 모델

```text
INPUT
  → DISCOVERY
  → DESIGN
  → GATE
  → IMPLEMENT
  → VERIFY
  → TRACE
  → REPORT
```

| 상태 | 입력 | 핵심 처리 | 출력 |
| --- | --- | --- | --- |
| `INPUT` | 자연어 요구사항 또는 결과폴더 | 실행 모드 판별 | 작업 범위 |
| `DISCOVERY` | 작업 범위 | 저장소·유사 구현·변경 조사 | 근거 목록 |
| `DESIGN` | 근거와 요구사항 | 누락 결정만 질의 | C00~C13·원장 |
| `GATE` | 설계 결과 | 정합성·위험 판정 | PASS/CONDITIONAL/FAIL |
| `IMPLEMENT` | 승인된 Gate | C15 구현 | 코드·설정·문서 |
| `VERIFY` | 변경 결과 | C16 테스트·빌드 | 검증 증적 |
| `TRACE` | 요구·설계·변경·시험 | C17 연결 점검 | 추적성 매트릭스 |
| `REPORT` | 모든 증적 | C18 완료 판정 | 최종 보고 |

### 9.1 전이 규칙

- 기존 결과폴더가 충분하면 `DESIGN`을 생략할 수 있다.
- `GATE` 이전에는 업무 소스를 수정하지 않는다.
- `PASS`와 `CONDITIONAL`은 사용자의 `Gate 승인` 후에만 `IMPLEMENT`로 전이한다.
- `FAIL`은 `DESIGN`으로 되돌아간다.
- 구현 결함으로 검증이 실패하면 `IMPLEMENT`로 회귀해 수정하고 재검증한다.
- 외부 환경 또는 필수 결정 문제면 재개 가능한 체크포인트를 기록한다.
- `COMPLETE`는 요청된 동작과 관련 검증이 확인된 경우에만 사용한다.

모든 상태 보고에는 현재 상태, 확정값, 가정, 충돌, Open Issue와 다음 전이 조건을 포함한다.

## 10. 실행 흐름

### 10.1 신규 요구사항

```text
자유 요구사항
→ 입력 모드 판별
→ 저장소와 유사 구현 조사
→ 구현을 바꾸는 누락 결정만 질문
→ 설계와 원장 확정
→ C14 Gate 및 사용자 승인
→ 구현·검증·추적·완료 보고
```

### 10.2 기존 결과폴더

```text
결과폴더 경로
→ 원장·C14·C00~C13 정합성 확인
→ 실제 소스와 충돌 검사
→ 필요한 경우에만 DESIGN 보완
→ Gate 승인
→ 구현·검증·추적·완료 보고
```

## 11. 오류 모델과 안전 통제

| 오류 | 의미 | 처리 |
| --- | --- | --- |
| `DESIGN_CONFLICT` | ServiceId, 업무코드, 테이블 소유권 또는 근거 충돌 | 충돌표와 선택 영향 제시 |
| `WORKTREE_CONFLICT` | 미커밋 변경 또는 보호 경로와 수정 대상 충돌 | 수정 중단 및 사용자 판단 요청 |
| `IMPLEMENTATION_FAILURE` | 컴파일, 테스트, Mapper 또는 계층 계약 위반 | 원인 수정 후 같은 검증 재실행 |
| `ENVIRONMENT_FAILURE` | 외부 DB, 네트워크, 권한 또는 실행 환경 문제 | 명령·오류·미검증·재개법 기록 |

다음 작업은 자동으로 진행하지 않는다.

- DB Schema 또는 공개 계약의 파괴적 변경
- 인증·권한 면제 범위 확대
- 운영 Secret 생성 또는 기록
- 개인정보가 로그·오류 응답·샘플에 노출되는 변경
- 사용자의 미커밋 변경 덮어쓰기 또는 되돌리기

모든 주요 결정은 사용자 답변, 저장소 근거 또는 명시적 가정 중 하나로 출처를 표시한다.

## 12. 운영 Runbook 범위

Runbook은 다음 시나리오의 선행조건, 절차, 성공 조건과 재개 정보를 정의한다.

- 신규 CRUD 작업 시작
- 기존 C00~C14 결과에서 재개
- `CONDITIONAL` Gate 승인
- 보호 경로 추가
- 컴파일·테스트 실패 복구
- 외부 DB 없이 가능한 검증
- Codex에서 Cursor 또는 Cursor에서 Codex로 작업 인계
- 대화 중단 후 원장과 상태 보고로 재개
- 기존 C15 실행 프롬프트를 통한 호환 실행
- 작업 취소와 생성·수정 파일 식별

## 13. 검증과 추적성

다음 항목을 검증한다.

1. 문서 파일, 링크와 참조 경로
2. 저장소 연동형과 독립 실행형의 상태·Gate·완료 기준 일치
3. 신규 요구사항 시나리오
4. 기존 결과폴더 재개 시나리오
5. `PASS`, `CONDITIONAL`, `FAIL` 전이
6. 미커밋 충돌과 환경 실패 복구
7. 요구사항 → 구성요소 → 프롬프트 규칙 → 검증 항목 추적
8. 기존 C00~C18 및 C15 실행 프롬프트 호환성

추적성 문서는 각 요구사항에 고유 ID를 부여하고 기준본 절, 구현 파일, 검증 항목과 상태를 연결한다.

## 14. Architecture Gate

Gate는 두 시점에 사용한다.

### 14.1 구현 전 Gate

- 정의서와 ADR의 결정이 일치함
- 구성요소 책임이 중복되지 않음
- 모든 상태의 입력·출력·전이·실패 처리가 정의됨
- 보안, 보호 경로와 미커밋 변경 정책이 명시됨
- 구현 계획이 To-Be 구성요소와 매핑됨

### 14.2 구현 후 Gate

- 실제 프롬프트와 정의서의 상태·Gate 계약이 일치함
- README에 신규·재개·호환 실행법이 있음
- 대표 정상·조건부·실패 시나리오가 검증됨
- 추적성 매트릭스에 누락이 없음
- 확인되지 않은 사실이 확정값으로 표현되지 않음

## 15. 전환 계획

As-Is에서 To-Be로 다음 순서로 전환한다.

```text
1. 아키텍처 문서 패키지 확정
2. MASTER·STANDALONE·REQUEST TEMPLATE 작성
3. 기존 C00~C18과 링크 및 우선순위 연결
4. README에 신규·재개 실행법 추가
5. 대표 시나리오로 프롬프트 검증
6. 기존 C15 실행 프롬프트를 호환 진입점으로 유지
7. 안정화 후 중복 규칙을 SoT 링크로 정리
```

기존 C15 실행 프롬프트의 제거 여부는 이 범위에서 결정하지 않는다.

## 16. 완료 기준

아키텍처 정의서 패키지는 다음 조건을 모두 만족해야 완료된다.

1. 다섯 문서의 책임이 중복되지 않는다.
2. As-Is, To-Be와 전환 단계가 명확하다.
3. 모든 상태의 입력·출력·전이·실패 처리가 정의된다.
4. 주요 아키텍처 결정이 ADR과 연결된다.
5. Runbook으로 중단 작업을 재개할 수 있다.
