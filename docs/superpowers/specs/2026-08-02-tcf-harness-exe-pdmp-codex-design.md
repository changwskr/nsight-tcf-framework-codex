# tcf-harness-exe-pdmp Codex 병렬 하네스 설계

## 목적

`tcf-harness-exe-pdmp`의 기존 Claude 기반 실행 소스를 변경하지 않으면서, Codex로 `pdmp-service` 개발 작업을 단계적으로 분석·구현·검증할 수 있는 독립 하네스를 추가한다.

## 핵심 제약

- `CLAUDE.md`, `.claude/**`, `scripts/execute.py`, `scripts/test_execute.py`, 기존 `docs/**`의 내용은 변경하지 않는다.
- 기존 phase의 `index.json`, `stepN.md`, `stepN-output.json` 계약을 Codex 실행기에서도 재사용한다.
- 기본 대상은 하네스의 형제 디렉터리인 `../pdmp-service`이며 CLI 옵션 또는 설정으로 변경할 수 있다.
- 자동 커밋과 push는 기본적으로 비활성화한다. 사용자가 명시적으로 활성화한 경우에만 수행한다.
- 저장소의 다른 미커밋 변경은 수정하거나 커밋하지 않는다.

## 선택한 접근

기존 Claude 하네스와 독립된 Codex 하네스를 병렬로 둔다.

- Claude 진입점과 실행기는 그대로 유지한다.
- Codex용 지침, 스킬, 실행기, 검증 도구와 예제 phase를 새 파일로 추가한다.
- 양쪽 실행기는 phase 파일 형식만 공유하며 서로의 구현에 의존하지 않는다.

공통 실행 코어 추출은 기존 실행기 변경이 필요하고, 단순 래퍼는 Claude 전용 명칭과 호출 계약을 누출하므로 채택하지 않는다.

## 구성 요소

### Codex 프로젝트 지침

루트 `AGENTS.md`에 하네스의 목적, 대상 경로 결정 규칙, PDMP 아키텍처, 보안 기준, 승인 게이트와 검증 기준을 정의한다. 하위 스킬은 이 지침을 구체화하되 상충하지 않는다.

### PDMP 스킬

다음 책임을 분리한다.

- 개발 오케스트레이션: 분석 → 사용자 승인 → 구현 계획 → 구현 → 보안 검토 → QA
- CRUD 구현: Controller → Service → DAO → MyBatis XML의 파일 탐색과 변경 규칙
- TCF 적용: `@TcfTransaction`, 거래 동작, 표준 헤더와 MDC 처리 확인
- 보안 검토: 개인정보, 인증·인가, SQL 바인딩, 로그 및 오류 노출 검사
- 품질 검증: 관련 테스트부터 WAR 빌드까지 단계적 검증

각 스킬은 입력, 산출물, 중단 조건과 다음 단계 인계 계약을 명시한다.

### Codex 실행기

`scripts/execute_codex.py`를 새로 추가한다.

- phase와 step 상태를 기존 JSON 계약으로 읽고 기록한다.
- 기본 대상 `../pdmp-service`를 해석하고 `--target`으로 재정의한다.
- Codex CLI를 비대화형으로 호출하며 명령 경로와 추가 인자는 안전하게 구성한다.
- step별 표준 출력, 표준 오류와 종료 코드를 output JSON에 저장한다.
- 완료, 오류, 차단 상태와 타임스탬프를 관리한다.
- 재시도 횟수와 timeout을 제한한다.
- 기존 작업 트리의 사용자 변경을 자동으로 stage하거나 commit하지 않는다.
- `--commit` 또는 `--push`가 명시된 경우에도 하네스가 생성한 것으로 확인된 경로만 대상으로 삼는다.

Codex CLI의 실제 옵션은 구현 전에 로컬 `codex --help`로 확인하고, 확인된 공개 계약에 맞춰 호출한다.

### PDMP 예제 phase

사용자정보관리 CRUD를 예제로 제공한다. 예제는 실제 업무 요구사항을 임의로 구현하지 않고 다음 단계 산출물만 정의한다.

1. 기존 `pdmp-service` 구조와 사용자 관련 구현 분석
2. 요구사항·데이터 계약·보안 요구사항 정리 및 사용자 승인
3. 파일 단위 구현 계획 작성
4. 승인된 범위 구현
5. 개인정보 및 TCF 보안 검토
6. 테스트와 WAR 빌드 검증

## 실행 흐름

1. 사용자가 phase 이름과 선택적 대상 경로를 전달한다.
2. 실행기는 하네스와 대상 경로, phase index 및 step 파일을 검증한다.
3. 실행기는 `AGENTS.md`, 관련 스킬, PDMP 프로젝트 문서와 완료된 step 요약을 프롬프트 컨텍스트로 구성한다.
4. Codex가 현재 step만 수행한다.
5. 실행기는 결과와 상태를 기록하고 성공한 경우 다음 step으로 이동한다.
6. 사용자 승인 step에서는 자동 진행하지 않고 `blocked` 또는 승인 대기 상태로 종료한다.
7. 모든 step이 완료되면 검증 결과를 요약한다.

## 오류 처리와 안전성

- 대상 또는 phase 경로가 없으면 변경 전에 실패한다.
- 잘못된 JSON, 누락된 step, 허용되지 않은 상태 전이는 명확한 오류로 처리한다.
- Codex CLI 부재, timeout, 비정상 종료는 output JSON에 기록한다.
- 대상 경로는 정규화하여 의도한 프로젝트 경계를 벗어난 변경을 방지한다.
- 개인정보, Secret, 토큰과 원문 전문을 프롬프트·로그·output JSON에 불필요하게 포함하지 않는다.
- 자동 push는 원격과 브랜치가 명확하며 앞선 단계가 모두 성공한 경우에만 허용한다.

## 검증 전략

- 기존 보존 대상 파일의 구현 전·후 SHA-256 해시가 동일한지 검사한다.
- Codex 실행기 단위 테스트에서 경로 결정, 명령 구성, 상태 전이, retry, timeout과 output 기록을 모킹해 검증한다.
- 하네스 계약 테스트에서 필수 파일, Markdown 링크, 스킬 인계, PDMP 아키텍처 및 보안 규칙을 검사한다.
- 예제 phase를 dry-run 또는 모킹된 Codex 호출로 끝까지 시뮬레이션한다.
- 로컬 Codex CLI 도움말과 실행기 도움말을 확인한다.
- 대상 `pdmp-service`는 소스 변경이 없는 상태에서도 관련 테스트와 WAR 빌드를 실행해 기준선을 확인한다. Oracle 등 외부 인프라가 필요해 실행할 수 없는 검증은 결과에 별도로 기록한다.

## 완료 기준

- 기존 Claude 하네스 파일의 내용이 변경되지 않는다.
- Claude 진입점과 Codex 진입점이 병렬로 존재한다.
- Codex 실행기가 기본 형제 `pdmp-service` 및 사용자 지정 대상 경로를 지원한다.
- PDMP 사용자정보관리 예제가 승인 게이트를 포함한 전체 개발 흐름을 설명하고 시뮬레이션할 수 있다.
- 하네스 검증과 단위 테스트가 통과한다.
- README 또는 Codex 전용 빠른 시작 문서에서 설치, 실행, 재개와 실패 복구 방법을 확인할 수 있다.

## 비범위

- 기존 Claude 실행기의 리팩터링 또는 제거
- `pdmp-service` 업무 기능 자체의 구현
- Oracle 스키마나 운영 환경 변경
- 사용자 승인 없는 자동 commit, push 또는 배포
