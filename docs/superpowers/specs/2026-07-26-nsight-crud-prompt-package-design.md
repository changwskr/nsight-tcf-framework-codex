# NSIGHT TCF 통합 CRUD 개발 프롬프트 패키지 설계

## 1. 목적

`nsight-tcf-framework-codex`에서 사용자가 자연어 요구사항 또는 기존 CRUD 설계 결과 폴더를 제공하면, Codex와 Cursor가 동일한 절차로 설계·구현·검증하도록 만드는 통합 프롬프트 패키지를 제공한다.

이 패키지는 다음 두 사용 시나리오를 함께 지원한다.

1. 자유 형식 요구사항에서 시작해 누락된 설계를 보완하고 CRUD를 구현한다.
2. 확정된 `C00`~`C14` 결과를 입력받아 Gate 정합성을 확인한 뒤 CRUD를 구현한다.

설계 Gate 승인 전에는 업무 소스를 수정하지 않는다. Gate 승인 후에는 별도의 파일 목록 승인 없이 구현, 테스트, 추적성 확인과 완료 보고까지 자동 진행한다.

## 2. 범위

### 2.1 기본 범위

- Handler, Facade, Service, Rule, DAO/Mapper, DTO와 관련 테스트
- 요청된 CRUD 동작만 구현
- 저장소 조사, 유사 구현 선정과 변경 영향 확인
- C14 설계 Gate, C15 구현, C16 검증, C17 추적성, C18 완료 판정

### 2.2 선택 범위

다음 항목은 사용자 요구사항 또는 실제 저장소 사용처가 있을 때만 포함한다.

- 화면 및 UI 이벤트
- 샘플 요청
- Service Catalog
- 도움말과 색인
- 신규 모듈 설정과 Schema

### 2.3 비범위

- 승인 없는 배포 또는 운영 반영
- 인증·권한 면제 범위 확대
- 요청과 무관한 리팩터링
- 운영 Secret 생성 또는 저장
- C14 `FAIL` 상태에서의 코드 생성

## 3. 산출물 구조

프롬프트 패키지는 기존 CRUD Codegen 작업 공간에 배치한다.

```text
ztcf-다이어리/2026-07-26-Agents/
├─ prompts/
│  ├─ MASTER-CRUD-DEVELOPER.md
│  ├─ STANDALONE-CRUD-DEVELOPER.md
│  ├─ CRUD-REQUEST-TEMPLATE.md
│  └─ C15-실행프롬프트.md
└─ README.md
```

- `MASTER-CRUD-DEVELOPER.md`: 저장소 연동형 기준 진입점이다. **구현됨**
- `STANDALONE-CRUD-DEVELOPER.md`: 관련 문서 접근이 어려운 환경을 위한 핵심 규칙 내장형이다. **구현됨**
- `CRUD-REQUEST-TEMPLATE.md`: 선택적으로 사용하는 입력 템플릿이다. **구현됨**
- 기존 `C15-실행프롬프트.md`는 호환성을 위해 유지한다.
- `README.md`에는 신규·기존 결과 기반 실행법과 파일 간 관계를 추가한다. **갱신됨**

## 4. 기준정보와 우선순위

저장소 연동형 프롬프트는 다음 순서로 정보를 해석한다.

1. 사용자의 현재 지시
2. 대상 경로에 적용되는 `AGENTS.md`
3. `_확정정보원장.md`와 승인된 `C00`~`C14`
4. `xdoc/agents/`의 역할별 지침
5. 실제 코드와 테스트로 검증된 기존 패턴
6. 프롬프트의 기본값

`STANDALONE-CRUD-DEVELOPER.md`도 실제 저장소에서 `AGENTS.md`를 발견하면 내장 규칙보다 해당 지침을 우선한다.

기존 결과 폴더에서는 `_확정정보원장.md`를 설계 결과의 SoT로 사용한다. 단, 실제 코드 또는 다른 C00~C14 결과와 충돌하면 임의로 선택하지 않고 충돌표를 제시한다.

## 5. 상태 모델과 실행 흐름

마스터 프롬프트는 다음 상태를 명시적으로 관리한다.

| 상태 | 책임 | 종료 조건 |
| --- | --- | --- |
| `INPUT` | 입력 유형과 작업 범위를 판별 | 신규 요구사항 또는 결과 폴더 식별 |
| `DISCOVERY` | 저장소, 기존 구현, 설정, 테스트와 문서 조사 | 근거 경로와 유사 구현 확보 |
| `DESIGN` | 누락 정보 질의와 C00~C13 설계 확정 | 구현에 필요한 결정 완료 |
| `GATE` | C14 정합성 및 위험 판정 | 사용자 `Gate 승인` 또는 보완 결정 |
| `IMPLEMENT` | C15 소스·설정·문서 구현 | 요청 범위 구현 완료 |
| `VERIFY` | C16 빌드·테스트·거래 검증 | 실행 결과와 미검증 범위 확보 |
| `TRACE` | C17 요구사항·구현·시험 추적 | 추적 누락 해소 또는 명시 |
| `REPORT` | C18 완료 판정과 결과 보고 | 최종 상태 보고 |

전체 흐름은 다음과 같다.

```text
자유 입력 또는 기존 결과 폴더
  → INPUT
  → DISCOVERY
  → DESIGN (기존 결과가 충분하면 생략)
  → GATE
  → 사용자 승인
  → IMPLEMENT
  → VERIFY
  → TRACE
  → REPORT
```

기존 결과 폴더가 입력되면 확정된 질문을 반복하지 않고 원장, C14와 실제 소스의 정합성만 검증한다.

## 6. 입력 계약

다음 입력 형식을 모두 허용한다.

- 자연어 CRUD 요구사항
- `CRUD-REQUEST-TEMPLATE.md` 형식의 구조화 입력
- 기존 `결과*/` 폴더 경로

최종적으로 확정해야 하는 정보는 다음과 같다.

- 대상 모듈과 기준 모듈
- 업무코드, 도메인, Handler와 ServiceId
- 필요한 등록·조회·수정·삭제 동작
- 테이블, PK, 컬럼, 검색조건, 정렬과 페이징
- 등록·수정 검증과 중복 기준
- 삭제 방식과 참조 데이터 처리
- 트랜잭션 경계와 오류 코드
- 개인정보, 권한과 감사 요구사항
- UI, 샘플 요청, Catalog와 도움말 포함 여부

## 7. 저장소 탐색과 질문 정책

에이전트는 질문 전에 다음을 조사한다.

- `git status --short`
- 루트 및 대상 모듈의 `README.md`, `build.gradle`
- 적용되는 `AGENTS.md`와 역할 지침
- 유사 Handler, DTO, Rule, Mapper/XML, DAO, Service, Facade와 테스트
- ServiceId 사용처, Service Catalog, UI, 샘플 요청과 도움말 색인
- 공통 설정과 Local, Dev, Prod Profile 차이

질문 규칙은 다음과 같다.

1. 저장소에서 확인 가능한 값은 다시 묻지 않고 근거 경로를 기록한다.
2. 외부 동작에 영향을 주지 않는 기본값은 가정 목록에 기록하고 진행한다.
3. 가능한 답에 따라 구현 결과가 달라질 때만 한 번에 하나씩 질문한다.
4. 사용자가 모르는 항목에는 유사 구현을 근거로 권장안을 제시한다.
5. 요청된 CRUD 동작만 생성하며, 동작 범위가 불명확하면 필요한 동작을 질문한다.
6. 설계가 완성되면 추가 질문을 멈추고 C14 Gate를 제시한다.

## 8. C14 설계 Gate

Gate는 다음을 검사한다.

- 업무코드, 도메인, ServiceId, Handler와 대상 모듈의 정합성
- CRUD 동작과 DTO, Rule, SQL, 화면 이벤트의 추적성
- 테이블, PK, 수정 가능 컬럼과 삭제 정책
- 트랜잭션, 오류, 보안과 개인정보 처리
- 기존 구현 및 미커밋 변경과의 충돌
- 테스트 가능성과 Open Issue

판정은 다음 세 값만 사용한다.

- `PASS`: 사용자 승인 후 구현한다.
- `CONDITIONAL`: 가정과 위험을 명시하고 사용자 승인 후 구현한다.
- `FAIL`: 코드를 생성하지 않고 보완 항목만 안내한다.

Gate 보고에는 확정 정보, 가정, Open Issue, 영향 모듈, 예상 생성·수정 파일 범주와 검증 계획을 포함한다. 사용자가 `Gate 승인`을 명시하면 파일 목록 작성부터 검증까지 자동 진행한다.

## 9. 구현 규칙

기본 생성 순서는 다음과 같다.

```text
DTO/Criteria/Row
→ Rule
→ Mapper 인터페이스/XML
→ DAO
→ Service
→ Facade
→ Handler
→ 테스트
→ 선택 범위(UI·샘플·Catalog·도움말)
→ C15 결과와 원장 갱신
```

계층 책임은 다음과 같다.

- Handler: `serviceIds()` 등록과 거래 분기
- Facade: DTO 변환, 유스케이스 조정과 트랜잭션 경계
- Service: 업무 흐름
- Rule: 검증과 계산
- DAO/Mapper: 파라미터 바인딩을 사용한 데이터 접근

도메인마다 Handler 하나를 사용한다. 기존 Handler가 있으면 새 Handler를 만들지 않고 `serviceIds()`와 분기를 확장한다. Handler에 SQL 또는 복잡한 Rule을 넣지 않으며, Service가 Mapper를 직접 호출하지 않는다.

기존 파일은 생성 목록에서 `신규`, `수정`, `보호`, `스킵`으로 구분한다. 사용자의 미커밋 변경을 덮어쓰거나 되돌리지 않는다.

## 10. 자동 진행 중단 조건

다음 조건에서는 사용자 판단 없이 구현을 계속하지 않는다.

- C14 판정이 `FAIL`
- ServiceId 또는 테이블 소유권 충돌
- 사용자의 미커밋 변경과 동일 코드 영역의 충돌
- DB Schema나 공개 계약의 파괴적 변경 필요
- 인증·권한 면제 범위 확대 필요
- 운영 Secret 또는 개인정보 노출 위험
- 선택에 따라 외부 동작이 달라지는 해석 불일치

컴파일 오류나 테스트 실패가 구현 결함으로 판단되면 요청 범위 안에서 원인을 조사하고 수정한 뒤 다시 검증한다. 해결 과정이 요청 범위를 넘어가면 중단하고 사용자 판단을 요청한다.

## 11. 검증 전략

검증은 가장 작은 관련 단위부터 확장한다.

1. 변경 파일 정적 점검
2. Handler, Service, Rule과 Mapper 관련 테스트
3. 대상 모듈 compile 또는 test
4. 영향받는 직접 의존 모듈 빌드
5. 가능한 경우 샘플 요청 또는 Handler 거래 검증
6. ServiceId, Catalog, UI와 도움말 색인 정합성 확인

실패 처리 기준은 다음과 같다.

- 구현 결함: 수정 후 같은 검증을 재실행한다.
- 기존 실패: 요청 변경과의 관련성을 구분한다.
- 환경 또는 외부 DB 문제: 실행 명령, 원인과 미검증 범위를 기록한다.
- 미실행 테스트: 성공으로 표현하지 않는다.

## 12. 명령 체계

최소 명령은 다음과 같다.

- `CRUD 개발 시작: <자유 요구사항>`
- `기존 결과로 개발: <결과폴더>`
- `현황`
- `수정: <항목>=<값>`
- `다음`
- `Gate 승인`
- `보호: <경로>`
- `검증`
- `중단`

일반 자연어도 동일한 의도로 해석한다. `Gate 승인` 전에는 업무 소스를 수정하지 않으며 설계 결과 문서만 작성할 수 있다.

## 13. 완료 보고

최종 보고에는 다음 항목을 포함한다.

- 구현 결과 요약
- 신규·수정·보호·스킵 파일
- 핵심 설계 결정과 가정
- 수행한 명령과 실제 결과
- C00~C18 요구사항 추적표
- 기존 미커밋 변경과의 관계
- 호환성과 롤백 고려사항
- 미검증 항목과 후속 작업
- 최종 판정

최종 판정은 다음과 같다.

- `COMPLETE`: 요청된 동작과 관련 테스트가 검증됨
- `CONDITIONAL`: 구현은 완료됐지만 외부 DB나 운영 환경 등 핵심 검증 일부가 남음
- `BLOCKED`: 필수 결정, 충돌 또는 안전 조건 때문에 완료할 수 없음

파일이 생성됐다는 사실만으로 `COMPLETE`를 사용하지 않는다.

## 14. 수용 기준

구현되는 프롬프트 패키지는 다음 조건을 만족해야 한다.

1. 신규 자유 입력과 기존 결과 폴더 입력을 모두 처리한다.
2. Codex와 Cursor에서 특정 전용 도구명 없이 실행 가능하다.
3. 저장소 연동형과 독립 실행형이 같은 상태, Gate와 완료 기준을 사용한다.
4. 저장소에서 확인 가능한 정보를 불필요하게 질문하지 않는다.
5. C14 승인 전 업무 소스를 수정하지 않는다.
6. 승인 후에는 파일 목록부터 구현·검증까지 자동 진행한다.
7. 요청하지 않은 CRUD 동작과 선택 산출물을 만들지 않는다.
8. 기존 미커밋 변경과 보호 경로를 보존한다.
9. 실제 실행한 검증과 미검증 범위를 구분해 보고한다.
10. 기존 C00~C18 및 C15 실행 프롬프트와의 사용 관계가 README에 설명된다.
