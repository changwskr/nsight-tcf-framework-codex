## 표기 규약 (전 장 공통)

본 문서는 **현재 동작하는 사실**과 **설정에 좌우되는 것**, **소스만 남은 것**을 시각적으로 구분한다.

| 표기 | 의미 | 판단 기준 |
| ---- | ---- | --------- |
| **✅ AS-IS** | 기준일 코드·설정으로 확인된 현재 동작 | 기본 프로파일 `local` 기준 실제 실행 경로 |
| **⚙️ 조건부** | 설정 키 값에 따라 켜지거나 꺼지는 구현 | `@ConditionalOnProperty` 또는 프로파일 분기 |
| **⛔ 비활성** | 소스는 저장소에 있으나 런타임에 로드되지 않음 | `nhnis.fw.tcf.enabled=false` 등 |
| **⚠️ 갭** | 설계 의도와 현재 구현이 어긋나 있는 지점 | [§17.5](#175-확인된-제약과-주의사항) · [부록 I](#부록-i-변경-영향-매트릭스) |

> 같은 설명은 **한 곳에만** 둔다. 다른 장에서는 절 번호로 교차참조한다.
> 상세 색인(서비스 ID·클래스·설정 키·SQL ID·오류 코드)은 본문에서 반복하지 않고 **부록**에 모았다.

# 문서 전면부

## 문서 목적과 대상 독자

### 목적

1. PDMK 세 모듈(`pdmk-fw` / `pdmk-service` / `pdmk-ui`)을 **하나의 실행 스택**으로 정의한다.
2. 요청 한 건이 브라우저에서 DB까지 가는 **실제 경로(AS-IS)** 를 확정하고, 그 위에서 신규 거래를 만드는 **표준 절차**를 제시한다.
3. 소스에 남아 있으나 실행되지 않는 경로(TCF/STF/ETF)를 **명시적으로 분리**하여 혼동을 제거한다.
4. 설계 원칙·금지 패턴·검증 체크리스트를 장 단위로 배치해 **리뷰 기준 문서**로 사용할 수 있게 한다.

### 대상 독자

| 독자 | 이 문서에서 얻는 것 |
| ---- | ------------------- |
| 신규 합류 개발자 | 스택 전체 그림, 요청 흐름, 패키지·네이밍 규칙 |
| 업무(MK) 개발자 | 전문 계약, 계층별 책임, 신규 거래 구현 절차, 페이징·트랜잭션 규칙 |
| 공통(FW) 개발자 | commons 경계, Filter/Interceptor/Resolver 계약, TCF 분리 원칙 |
| 운영·배포 담당 | 프로파일·설정 키, 빌드 산출물, 기동 순서, 환경 전환 |
| 아키텍트·리뷰어 | 설계 원칙, 금지 패턴, 현황 갭, 변경 영향 매트릭스 |

### 이 문서가 다루지 않는 것

- PDMG / PDMP 등 **다른 대구분 앱**의 업무 아키텍처 (`pdmk-fw`를 공유할 수 있으나 별도 스택)
- CI/CD 파이프라인, 컨테이너·오케스트레이션 (저장소에 매니페스트 없음 — [§15.6](#156-was-배포))
- WAS·L4·APIGW 등 **애플리케이션 바깥 인프라**의 상세 구성
- 개별 업무 요건·화면 설계 (업무 설계서 소관)

### 여섯 개의 설계 슬로건

| # | 슬로건 | 근거 절 |
| - | ------ | ------- |
| 1 | **세 모듈 한 스택** — ui는 HTTP, service는 업무, fw는 공통 | [§2.1](#21-모듈별-책임) |
| 2 | **서비스 ID = URL = 메서드 = DTO = SQL ID** — REST 자원 URL 지양 | [§6.1](#61-service-id와-url-규칙) |
| 3 | **commons ON · TCF OFF** — `nhnis.fw.tcf.enabled=false` | [§5.2](#52-현재-설정에서의-활성-여부) |
| 4 | **DB 트랜잭션 경계는 Service** — Filter/Interceptor/Aspect는 TX 경계가 아니다 | [§9.1](#91-spring-트랜잭션-경계) |
| 5 | **전문은 `hdr_nhnis` + `dto`** — 오류도 표준 코드·메시지로 | [§6.2](#62-hdr_nhnis--dto-전문-구조) · [§10.7](#107-표준-오류-응답) |
| 6 | **변경은 영향 표부터** — 세 모듈 파급을 먼저 본다 | [부록 I](#부록-i-변경-영향-매트릭스) |

### 지금 바로 알아야 할 다섯 가지 사실

1. **인증은 Security가 아니라 Filter가 한다.** Spring Security는 `permitAll`이며, 실제 게이트는 `DefaultFilter`의 JWT 검증이다. 단 `local` 프로파일에서는 그 검증도 생략된다. ([§11.1](#111-securityfilterchain)~[§11.3](#113-jwt-검증-경로))
2. **TCF 경로는 실행되지 않는다.** `@TcfTransaction` / `TCFAspect` / `StandardResponseDto`는 PDMK API 계약이 아니다. ([§5](#5-tcfstfetf-아키텍처))
3. **오류 응답 형태가 두 가지다.** Filter 단계 실패는 전문 봉투 없는 HTTP 4xx, 업무 예외는 `{hdr_nhnis, dto:NH_NIS_ERR_DTO}` + HTTP 500이다. ([§10.7](#107-표준-오류-응답))
4. **ImageLog는 업무 트랜잭션과 분리된다.** 업무가 롤백돼도 감사 행은 남을 수 있다. ([§9.5](#95-imagelog와-업무-tx의-관계))
5. **현재 샘플 Service에는 `@Transactional`이 없다.** 신규 거래는 반드시 선언한다. ([§9.3](#93-transactional-적용-규칙) · [§17.5](#175-확인된-제약과-주의사항))

## 1. PDMK 시스템 개요

> **이 장에서 알 수 있는 것**
> - PDMK가 어떤 문제를 풀기 위한 스택인지
> - `pdmk-fw` / `pdmk-service` / `pdmk-ui` 세 모듈이 각각 무엇을 담당하는지
> - 시스템 컨텍스트(외부 경계)와 논리·물리 아키텍처
> - 이후 모든 장이 따르는 다섯 가지 핵심 설계 원칙

### 1.1 PDMK가 해결하는 문제

PDMK는 **서비스 ID 중심 온라인 거래**를 로컬 개발 환경과 폐쇄망에서 동일한 계약으로 검증하기 위한 샘플 스택이다. 해결 대상 문제는 네 가지다.

| 문제 | PDMK의 해법 | 상세 |
| ---- | ----------- | ---- |
| REST 자원 URL과 사내 전문 규격의 불일치 | URL·메서드·DTO·SQL ID를 **하나의 서비스 ID**로 통일 | [§6.1](#61-service-id와-url-규칙) |
| 거래 공통 처리(헤더·GUID·감사)의 업무 코드 침투 | Filter/Interceptor/Aspect로 **횡단 분리**, 업무는 순수 CRUD | [§4](#4-공통-웹-처리-체인) |
| 브라우저에서 사내 API를 시험할 때의 CORS·전문 조립 부담 | `pdmk-ui`가 **서버사이드 릴레이 + 샘플 전문 카탈로그** 제공 | [§3.2](#32-pdmk-ui-relay-처리) |
| 로컬(H2)과 폐쇄망(Oracle) 환경 차이 | 동일 Mapper·동일 전문, **설정 블록 전환**으로 흡수 | [§14.6](#146-local과-배포환경-차이) |

**✅ AS-IS 성격:** PDMK는 운영 원장을 소유한 시스템이 아니라, 공통 프레임워크(`pdmk-fw`)의 계약을 **실제로 실행해 검증하는 참조 구현**이다. 따라서 샘플 거래(`mkcoa5530` / `mkcoa8888` / `mkcoa9999`)는 "업무 요건"이 아니라 "계약 예시"로 읽어야 한다.

### 1.2 pdmk-fw, pdmk-service, pdmk-ui 구성

```text
 ┌─ pdmk-fw ──────────────┐
 │ java-library JAR       │◄── implementation project(':pdmk-fw')
 │ nhnis.fw.commons.*  ✅ │            │
 │ nhnis.fw.tcf.*      ⛔ │            │
 └────────────────────────┘            │
 ┌─ pdmk-service ─────────┐            │

 └────────────────────────┘            │
 ┌─ pdmk-ui ──────────────┐            │
 │ Boot JAR :8090         │────────────┘
 │ nhnis.mk.ui.*          │   ※ pdmk-fw 미의존
 └────────────────────────┘
```

| 모듈 | 성격 | 산출물 | 패키지 루트 | 의존 |
| ---- | ---- | ------ | ----------- | ---- |
| `pdmk-fw` | 공통 프레임워크 라이브러리 (Boot 앱 아님) | `pdmk-fw-0.0.1-SNAPSHOT.jar` | `nhnis.fw.*` | 업무 코드 없음 |
| `pdmk-service` | MK 업무 애플리케이션 | `*.war` | `nhnis.mk.*` | `implementation project(':pdmk-fw')` |
| `pdmk-ui` | 전문 테스트·중계 UI | `pdmk-ui.jar` | `nhnis.mk.ui.*` | HTTP만 |

| -------- | ---- | ------ | ------ |
| `pdmk-service` | **8080** | `*.war` | 로컬 embedded Tomcat(`bootRun`) / 운영 외부 WAS |

### 1.5 핵심 설계 원칙

| # | 원칙 | 구체 규칙 | 위반 시 증상 |
| - | ---- | --------- | ------------ |
| 1 | **서비스 ID 단일 축** | URL·Controller/Service 메서드·DTO·SQL ID·`rms_svc_c`가 동일 | 카탈로그 404, MyBatis 매핑 실패 |
| 2 | **전문 봉투 고정** | 루트는 항상 `hdr_nhnis` + `dto`. 업무 필드를 루트에 두지 않음 | Resolver 바인딩 실패 |
| 3 | **횡단은 fw, 업무는 service** | `nhnis.mk.*` 코드를 `pdmk-fw`에 두지 않음 | FW 재사용 불가, 순환 의존 |
| 4 | **TX 경계는 Service** | Controller·DAO·Filter·Aspect에 `@Transactional` 금지 | 원자성 붕괴, 예상 밖 커밋 |
| 5 | **하나의 실행 경로** | commons 경로만 사용. TCF와 이중 경로 금지 | 응답 스키마 분기, 이중 선후처리 |

> **개발·검증 체크리스트 (§1)**
>
> - [ ] 신규 기능이 세 모듈 중 **어디에 속하는지**를 먼저 결정했는가 (fw=공통 / service=업무 / ui=중계)
> - [ ] 서비스 ID 축(원칙 1)을 깨는 URL·클래스명을 도입하지 않았는가
> - [ ] 전문 루트에 `hdr_nhnis`·`dto` 외 노드를 추가하지 않았는가
> - [ ] 변경이 범위 밖(TCF·PDMG)에 의존하지 않는가
> - [ ] 문서 기준일 이후 변경이면 [§17](#17-현재-구현-현황)과 [부록 I](#부록-i-변경-영향-매트릭스)를 함께 갱신했는가

### 2.2 빌드 의존성과 런타임 통신

```text
 [빌드 시점 — Gradle]                    [런타임 — 프로세스 간]

  pdmk-service/settings.gradle             Browser
    include ':pdmk-fw'                        │ HTTP
    projectDir = ../pdmk-fw                   ▼
        │                                 pdmk-ui :8090
        ▼                                     │ HTTP POST /{서비스ID}
  implementation project(':pdmk-fw')          ▼
        │                                 pdmk-service :8080
        ▼                                     │ JDBC
  WAR 안에 fw 클래스 임베드                    ▼
                                          RDW
  pdmk-ui : fw/service 빌드 의존 없음
```

| 관계 | 종류 | 계약 |
| ---- | ---- | ---- |
| `pdmk-service` → `pdmk-fw` | **빌드 의존** | `settings.gradle`의 `include ':pdmk-fw'` + `implementation project(':pdmk-fw')` |
| `pdmk-ui` → `pdmk-service` | **런타임 HTTP** | `pdmk.ui.target-base-url` (기본 `http://localhost:8080`) |
| `pdmk-ui` ↔ `pdmk-fw` | **없음** | 전문 형식만 service와 공유 (샘플 JSON 동기화 필요) |
| 세 모듈 공통 | 계약 | 서비스 ID · `hdr_nhnis`+`dto` · MK 네이밍 |

**중요:** `pdmk-fw`를 수정하면 `pdmk-service`를 **재빌드**해야 반영된다(프로젝트 의존이므로 WAR 안에 다시 패키징된다). [§15.8](#158-산출물-검증)

### 2.4 허용·금지 의존 방향


### 2.5 배포 단위와 포트

| 배포 단위 | 산출물 | 포트 | 기동 방식 | 필수 여부 |
| --------- | ------ | ---- | --------- | --------- |
| `pdmk-service` | `*.war` (`bootWar` off / `war` on) | **8080** | 로컬 `bootRun` / 운영 WAS 배포 | **필수** |
| `pdmk-ui` | `pdmk-ui.jar` (`bootJar`) | **8090** | `java -jar` 또는 `bootRun` | 선택 (개발·시험용) |
| `pdmk-fw` | `pdmk-fw-*.jar` (`bootJar` off / `jar` on) | — | 단독 기동 **불가** | 라이브러리 |

기동 순서는 **service(8080) → ui(8090)**. UI만 띄우면 릴레이 대상이 없다 ([§15.5](#155-로컬-기동-순서)).

> **개발·검증 체크리스트 (§2)**
>
> - [ ] 새 클래스의 패키지가 `nhnis.mk.{업무}.{세부}.{layer}` 규칙에 맞는가
> - [ ] `pdmk-fw`에 `nhnis.mk.*` 임포트가 생기지 않았는가
> - [ ] `pdmk-ui/build.gradle`에 `pdmk-fw`·MyBatis·Security 의존이 추가되지 않았는가
> - [ ] `pdmk-service/settings.gradle`의 `:pdmk-fw` include 경로가 유효한가
> - [ ] fw 변경 후 service를 재빌드했는가
> - [ ] 8080/8090 포트 충돌이 없는가

## 3. End-to-End 거래 흐름

> **이 장에서 알 수 있는 것**
> - 브라우저 → `pdmk-ui` → `pdmk-service` → `pdmk-fw` → RDW 전 구간 순서
> - UI 릴레이가 하는 일과 하지 않는 일
> - Service 진입 시점의 HTTP 계약
> - 정상 / 업무 오류 / 시스템 오류 세 가지 시퀀스의 분기점

### 3.1 브라우저에서 DB까지의 전체 흐름

```text
 t0  Browser          POST /api/relay/{서비스ID}            [pdmk-ui]
 t1  UI Relay         TransactionRelayService → RestClient
 t2  HTTP             POST /{서비스ID}  { hdr_nhnis, dto }  [pdmk-service]
 t3  DefaultFilter    Body 캐시 · JWT(비-local) · hdr 파싱 · Context/MDC set
 t4  SecurityChain    permitAll 통과
 t5  Interceptor      preHandle — GUID 확정 · 헤더 보강 · ImageLog PRE
 t6  BizAspect        @Before — 업무 공통 선처리 로그(BRC)
 t7  Resolver         dto 노드 → {서비스ID}DTOin
 t8  Controller       @PostMapping("/{서비스ID}") → Service 위임
 t9  Service          검증 · 페이징 계산 · DTO↔Map 변환 · (권장) @Transactional
 t10 DAO/MyBatis      SQL ID 실행 → rdwSqlSessionTemplate → RDW
 t11 Service          Map → DTOSub/DTOout 조립
 t12 BizAspect        @After — 업무 공통 후처리 로그
 t13 Interceptor      postHandle — ImageLog POST
 t14 ResponseAdvice   { hdr_nhnis: Context.header, dto: DTOout }
 t15 Filter finally   ServiceContext remove · ThreadContext.clearAll
 t16 UI               RelayResult(status, elapsedMs, body) → Browser
```

**직접 호출**도 동일하다. `POST http://localhost:8080/{서비스ID}`로 t0~t1, t16을 건너뛴다.

### 3.2 pdmk-ui Relay 처리

`pdmk-ui`는 **브라우저의 CORS 제약을 서버사이드 호출로 회피**하는 얇은 중계 계층이다.

```text
 Browser
   ├─ GET  /api/config          → targetBaseUrl · timeoutMs 등 화면 설정
   ├─ GET  /api/transactions    → TransactionCatalog (거래 목록·샘플 JSON)
   ├─ POST /api/relay/{서비스ID}
   └─ POST /api/imagelog/list | /api/imagelog/delete   (고정 경로 중계)
              │
              ▼
     TransactionRelayService (RestClient)
              │
              ▼
     POST {pdmk.ui.target-base-url}/{서비스ID}
```

| UI 구성요소 | 클래스 | 역할 |
| ----------- | ------ | ---- |
| entry | `PdmkUiHomeController`, `PdmkUiApiController` | 정적 화면 라우팅, `/api/*` |
| application | `TransactionCatalog` | 등록 거래·샘플 요청 JSON (`@PostConstruct` 적재) |
| client | `TransactionRelayService` | `RestClient` HTTP POST 중계 |
| support | `TransactionInfo`, `RelayResult` | 값 객체(상태·소요시간·본문) |
| config | `PdmkUiProperties` | `target-base-url`, `timeout-ms` |

정적 화면: `static/mkcoa5530/`, `static/mkcoa9999/`, `static/imagelog/`, 공통 `_shared/online-single.js`

**⚠️ 갭 2건 (상세 [§17.5](#175-확인된-제약과-주의사항))**

| 갭 | 영향 |
| -- | ---- |
| `RestClient`에 `pdmk.ui.timeout-ms` 미연결 | UI HTTP 타임아웃이 실제로 동작하지 않음 ([§12.7](#127-timeout-설정)) |
| 릴레이가 `Authorization` 헤더를 전달하지 않음 | 비-local 프로파일에서 ui→service 호출이 401 ([§11.3](#113-jwt-검증-경로)) |

**UI가 하지 않는 것:** 페이징 재계산, 전문 헤더 생성/보강, 오류 코드 해석. `dto`를 그대로 넘기고 응답을 그대로 표시한다.

### 3.3 Service HTTP 진입

| 항목 | 규칙 |
| ---- | ---- |
| Method | `POST` 고정 |
| URL | `/{서비스ID}` — 예 `/mkcoa5530S0` |
| Content-Type | `application/json` (multipart는 별도 통과 경로 — [§4.2](#42-defaultfilter)) |
| 요청 루트 | `hdr_nhnis` + `dto` (local 프로파일은 `dto`만으로도 가능) |
| 클래스 `@RequestMapping` | **사용 금지** — 메서드 `@PostMapping`만 |

최소 요청 계약:

```json
{
  "hdr_nhnis": { "sys_comm": { "rms_svc_c": "mkcoa5530S0", "scid": "mkcoa5530" } },
  "dto": { "pageNo": 1, "pageSize": 20 }
}
```

전문 필드 전체와 `sys_comm` 의미는 [§6.2](#62-hdr_nhnis--dto-전문-구조)·[§6.3](#63-sys_comm-필드)을 본다.

### 3.4 업무 계층 실행

```text
 Controller  ── 진입·위임만 (SQL·TX·대량 매핑 금지)
      │ DTOin
      ▼
 Service     ── 업무 규칙 · 페이징 정규화 · DTO↔Map · (권장) @Transactional
      │ Map
      ▼
 DAO         ── SQL ID 호출만 (메서드명 = SQL ID)
      │ MyBatis
      ▼
 Mapper XML  ── rdw.mk.co.a/{식별}-ORA.xml (namespace = DAO FQCN)
      │
      ▼
 RDW
```

계층별 책임·금지는 [§7](#7-업무-계층-아키텍처), SQL·페이징 계약은 [§8](#8-데이터-접근과-페이징)을 본다.

### 3.5 응답 반환과 종료 처리

| 순 | 처리 | 주체 |
| -- | ---- | ---- |
| 1 | Controller가 `{서비스ID}DTOout` 반환 | service |
| 2 | `ResponseBodyArgumentResolver`(ResponseBodyAdvice)가 `{ hdr_nhnis: Context 헤더, dto: DTOout }`로 포장 | fw |
| 3 | 포장 시 `dtoLogicalName`, `fieldPropertyMap`, `*List`/`*Array` 보조 필드 제거 | fw |
| 4 | `BizPrePostAspect.@After` 업무 후처리 로그 | service |
| 5 | `Interceptor.postHandle` ImageLog POST(`RESPONSE_TIME` UPDATE) | fw |
| 6 | `DefaultFilter` finally — `ServiceContextHolder` remove + `ThreadContext.clearAll()` | fw |
| 7 | (UI 경유 시) `RelayResult`로 상태·소요시간과 함께 브라우저 전달 | ui |

**Controller가 `DTOout`만 반환해도 클라이언트는 봉투를 받는다.** 이 점을 모르고 UI/테스트에서 루트 필드를 직접 읽으면 실패한다 ([§6.5](#65-요청-바인딩과-응답-조립)).

### 3.6 정상·업무 오류·시스템 오류 시퀀스

#### (a) 정상 ✅

```text
 Filter ─► Interceptor.pre ─► Aspect.before ─► Controller ─► Service ─► DAO
                                                                   │ commit(쓰기) / 종료(읽기)
        ◄─ Filter finally ◄─ Interceptor.post ◄─ Aspect.after ◄────┘
 응답: HTTP 200 { hdr_nhnis, dto: DTOout }
```

#### (b) 업무 오류 (Service에서 `NhBaseException`)

```text
 Service  throw NhBaseException("FW0001", args, TYPE.COMMON)
    │
    ├─► @Transactional 프록시 : rollback (선언 시)
    │
    ├─► ResponseBodyArgumentResolver.errorProcessor → NH_NIS_ERR_DTO
    │       HTTP 500 + { hdr_nhnis, dto: 에러DTO }
    │
    ├─► Interceptor.afterCompletion(ex) : ImageLog EX UPDATE
    │
    └─► Filter finally : Context/MDC 정리
```

#### (c) 시스템 오류 — Filter 단계 조기 실패

```text
 DefaultFilter
   Body 없음 / JSON 파싱 실패 / hdr_nhnis 없음(비-local)  → sendError(400, "문구")
   Bearer 없음·무효(비-local)                            → sendError(401, "문구")
        │
        └─ 체인 중단. Interceptor·Aspect·Advice **미도달**
 응답: HTTP 4xx, **전문 봉투 없음**
```

| 구분 | HTTP | 봉투 | 포착 지점 | 상세 |
| ---- | ---- | ---- | --------- | ---- |
| 정상 | 200 | ✅ `{hdr_nhnis, dto}` | — | [§3.5](#35-응답-반환과-종료-처리) |
| 업무 오류 | 500 | ✅ `{hdr_nhnis, dto:NH_NIS_ERR_DTO}` | `ResponseBodyArgumentResolver` | [§10.7](#107-표준-오류-응답) |
| Filter 오류 | 400 / 401 | ❌ 없음 | `DefaultFilter.sendError` | [§10.1](#101-예외-처리-전체-흐름) |
| Security 거부 | 401 | ❌ 없음 | `HttpStatusEntryPoint` (현 샘플은 거의 미발생) | [§11.1](#111-securityfilterchain) |

**클라이언트는 이 두 형태를 모두 처리해야 한다.**

> **개발·검증 체크리스트 (§3)**
>
> - [ ] 신규 거래를 `POST /{서비스ID}` 단일 엔드포인트로 노출했는가
> - [ ] 요청 루트가 `hdr_nhnis` + `dto`이고 응답 봉투를 클라이언트가 기대하는가
> - [ ] UI 카탈로그의 서비스 ID가 실제 URL과 일치하는가
> - [ ] 업무 오류와 Filter 오류를 UI/테스트가 각각 처리하는가
> - [ ] 비-local 시험 시 `Authorization` 전달 경로를 확보했는가 (⚠️ UI 릴레이 미전달)
> - [ ] 로그에서 GUID 하나로 t3~t15 구간이 연결되는가 ([§12.4](#124-guidtrace-idmdc))

## 4. 공통 웹 처리 체인

> **이 장에서 알 수 있는 것**
> - 현재 활성화된 처리 경로가 정확히 무엇인지
> - `DefaultFilter` / `ServicePreventionInterceptor` / `BizPrePostAspect` 각각의 책임과 겹치지 않는 이유
> - 요청·응답 Resolver가 전문 봉투를 어떻게 분해·조립하는지
> - 실행 순서와 Spring Order, 그리고 ThreadLocal 정리 규칙

### 4.1 현재 활성 처리 경로

```text
 ┌────────────── Servlet Container ──────────────────────────────┐
 │  FilterRegistrationBean order=1  urlPatterns=/*                │
 │  ┌────────── DefaultFilter  ✅ ─────────────────────────────┐  │
 │  │  multipart 분기 · Body 캐시 · JWT · hdr_nhnis · Context  │  │
 │  └───────────────────────────┬──────────────────────────────┘  │
 │  Spring SecurityFilterChain (앱 SecurityConfig) ✅ permitAll   │
 │                              ▼                                 │
 │  DispatcherServlet                                             │
 │   └─ ServicePreventionInterceptor ✅ (legacy-web)             │
 │        └─ BizPrePostAspect ✅ (@Order 100)                    │
 │             └─ RequestBodyArgumentResolver ✅ → Controller     │
 └────────────────────────────────────────────────────────────────┘

 ⛔ TcfTraceFilter · JwtAuthenticationFilter · TCFAspect — tcf.enabled=true 일 때만
 ⛔ fw commons SecurityConfig — commons.security.enabled=true 일 때만
```

| 구성요소 | 모듈 | 기술 | 활성 조건 | 주 책임 |
| -------- | ---- | ---- | --------- | ------- |
| `DefaultFilter` | fw | Servlet `Filter` | `nhnis.fw.commons.filter.enabled=true` | 전문 파싱·JWT·`ServiceContext` 생성 |
| `ServicePreventionInterceptor` | fw | `HandlerInterceptor` | `nhnis.fw.commons.legacy-web.enabled=true` | GUID 확정·헤더 보강·ImageLog |
| `BizPrePostAspect` | service | Spring AOP | `legacy-web.enabled=true` | Controller 공통 진입/종료 로그 |
| `RequestBodyArgumentResolver` | fw | `HandlerMethodArgumentResolver` | legacy-web | `dto` 노드 → DTOin |
| `ResponseBodyArgumentResolver` | fw | `ResponseBodyAdvice` | legacy-web | 응답 봉투·오류 DTO 조립 |
| `MybatisLogInterceptor` | service | MyBatis Plugin | 항상(Bean) | SQL ID·소요시간 debug 로그 |

등록 주체: `FilterConfiguration`이 Filter를, `WebConfiguration`이 Interceptor·Resolver를 붙인다. Aspect는 컴포넌트 스캔으로 등록된다.

### 4.2 DefaultFilter

**위치:** `nhnis.fw.commons.filter.DefaultFilter`
**역할:** 요청이 Controller에 닿기 전에 **거래 컨텍스트를 만든다.**

```text
                DefaultFilter.doFilter
                          │
        URI 마지막 세그먼트 → serviceId → MDC
        HTTP 헤더 수집
                          │
         content-type = multipart/* ?
          ┌───────────────┴───────────────┐
         Yes                              No
          ▼                                ▼
  X-GUID 헤더로 최소 hdr 구성      CachedBodyHttpServletRequest 래핑
  Context set                      비-local? JWT Bearer 검증 → 실패 401
  doFilter(원본 request)           Body 비어있음? → 400
                                   JSON 파싱 실패? → 400
                                   hdr_nhnis 없음?
                                     · local → syntheticLocalHeader
                                     · 그 외 → 400
                                   sys_comm 보강
                                   MDC(guid/ip/userId/serviceId)
                                   ServiceContextHolder.setInstance
                                   doFilter(wrapper)  ← Body 재읽기 가능
          └───────────────┬───────────────┘
                          ▼
                       finally
        ServiceContext remove + ThreadContext.clearAll
```

| 단계 | 동작 | 실패 시 |
| ---- | ---- | ------- |
| URI → serviceId | path 마지막 세그먼트 | — |
| multipart 분기 | `X-GUID`로 최소 헤더 구성, Body 미파싱 | — |
| JWT (⚙️ 비-local) | `Authorization: Bearer` 필수·유효·Access | 401 `sendError` |
| Body 캐시 | `CachedBodyHttpServletRequest`로 재읽기 가능화 | 빈 Body → 400 |
| `hdr_nhnis` 파싱 | Map → `hdr_nhnis` DTO | 비-local·부재 → 400 |
| 헤더 보강 | `rms_svc_c`, `scid`, IP, `optr_eno`, `tr_sysid` — **비어 있을 때만** | — |
| Context set | `ServiceContextHolder.setInstance` | — |
| finally | Context·MDC 제거 | — |

#### local vs 비-local (⚙️ 조건부)

| 조건 | `local` | 비-`local` |
| ---- | ------- | ---------- |
| JWT | **검증 생략** | Bearer Access Token 필수 |
| `hdr_nhnis` 없음 | 합성 헤더(GUID 신규 채번) 허용 | **400** |
| `optr_eno` 비어 있음 | `"LOCAL"` | 보강 로직 동일(없으면 `LOCAL`) |

**Filter는 DB 트랜잭션 경계를 열지 않는다.** 실패는 예외 전파가 아니라 `sendError`이므로 MVC Advice에 도달하지 않는다.

### 4.3 ServicePreventionInterceptor

**위치:** `nhnis.fw.commons.interceptor.ServicePreventionInterceptor`
**역할:** Filter가 만든 컨텍스트를 **확정**하고, 전문 헤더 기준 **이미지로그**를 남긴다.

| 훅 | 시점 | 처리 |
| -- | ---- | ---- |
| `preHandle` | Handler 매핑 후 · Controller 전 | 시스템 선처리 로그, **GUID 없으면 UUID 강제 채번**, `enrichHeaderFromRequest`, `preImagelog`(INSERT) |
| `postHandle` | Controller 정상 반환 후 · 응답 커밋 전 | 시스템 후처리 로그, `postImagelog`(RESPONSE_TIME UPDATE) |
| `afterCompletion` | 예외 발생 시 | `SystemErrorProcessor` 로그, `exceptionImagelog`, Context 제거, **예외 재던짐** |

#### 헤더 보강 규칙 (`enrichHeaderFromRequest`)

| 필드 | 비어 있을 때 채우는 값 |
| ---- | --------------------- |
| `rms_svc_c` | URI 마지막 세그먼트(서비스 ID) |
| `scid` | `rms_svc_c`에서 `[SD]\d+$` 제거 |
| `tr_trm_ipadr` | `X-Forwarded-For` 또는 `remoteAddr` |
| `optr_eno` | MDC `userId` 또는 `"LOCAL"` |

등록 범위: `/**` (`/error` 제외). multipart 요청은 선/후처리 본문을 건너뛰고 통과한다. `ServiceContext`가 `null`이면 warn 로그 후 통과한다.

### 4.4 BizPrePostAspect

**위치:** `nhnis.mk.co.common.BizPrePostAspect`
**역할:** **업무 Controller** 공통 진입/종료 로그. DB·ImageLog·트랜잭션은 다루지 않는다.

| 항목 | 값 |
| ---- | -- |
| Pointcut | `execution(* nhnis.mk.co..controller..*(..))` |
| Advice | `@Before` / `@After` |
| `@Order` | `100` |
| 조건 | `@ConditionalOnProperty(nhnis.fw.commons.legacy-web.enabled=true)` — 기본 `true` |

| Advice | 로그 (`PdmkTxLog`) | 추가 |
| ------ | ------------------ | ---- |
| `@Before` | `bizPreProcess()` | 인자별 `bizArgumentBefore(BRC)` |
| `@After` | `bizPostProcess()` | 인자별 `bizArgumentAfter(BRC)` |

BRC 추출은 DTO에 `getTrtBrc` / `getBrc` / `getBRC` / `getL5104` getter가 있을 때만 **반사 호출**하며, 없으면 `null`로 남긴다. `@After`는 정상·예외 모두 호출된다.

**하지 않는 것:** DB 접근, 외부 호출, 예외 변환, 응답 조립. Pointcut을 `nhnis.mk..*` 전 계층으로 확대하면 이중 로그·노이즈가 발생한다.

### 4.5 Request·Response Resolver

```text
 [요청]
 JSON Body ─┬─ DefaultFilter ─────────► hdr_nhnis → ServiceContext
            └─ RequestBodyArgumentResolver
                   root.get("dto") → {서비스ID}DTOin
                   ※ 어노테이션은 nhnis.fw.commons.resolver.RequestBody
                     (Spring 표준 @RequestBody 아님)

 [응답]
 Controller return {서비스ID}DTOout
            └─ ResponseBodyArgumentResolver (ResponseBodyAdvice)
                   { "hdr_nhnis": ServiceContext.header,
                     "dto": DTOout }
                   ※ dtoLogicalName · fieldPropertyMap · *List/*Array 제거
                   ※ NhBaseException 시 errorProcessor → NH_NIS_ERR_DTO
```

Controller 시그니처 최소 계약:

```java
@PostMapping("/mkcoa5530S0")
public mkcoa5530S0DTOout mkcoa5530S0(
        @RequestBody mkcoa5530S0DTOin input) throws Throwable { /* Service 위임 */ }
```

> `@RequestBody`는 **`nhnis.fw.commons.resolver.RequestBody`** 를 import해야 한다. Spring 표준 어노테이션을 쓰면 `dto` 노드 추출이 되지 않는다. ([§7.8](#78-금지-구현-패턴))

### 4.6 실행 순서와 Spring Order

| 위치 | 구성요소 | Order / 우선순위 | 근거 |
| ---- | -------- | ---------------- | ---- |
| Servlet Filter | `DefaultFilter` | `FilterRegistrationBean.setOrder(1)` | `FilterConfiguration` |
| Servlet Filter | Spring Security 체인 | Boot 기본 | `SecurityConfig` |
| MVC | `ServicePreventionInterceptor` | `WebConfiguration` 등록 순서 | `/**` except `/error` |
| AOP | `BizPrePostAspect` | `@Order(100)` | Controller 바깥 |
| AOP | `@Transactional` advisor | Spring 기본 | Service 안쪽 |
| MyBatis | `MybatisLogInterceptor` | 플러그인 체인 | AOP 아님 |

`BizPrePostAspect`(Controller **바깥**)와 TX advisor(Service **안쪽**)는 대상이 달라 순서 충돌이 없다.

**self-invocation 주의:** 같은 클래스 내부 메서드 호출은 프록시를 우회하므로 `@Transactional`·AOP가 적용되지 않는다 ([§9.3](#93-transactional-적용-규칙)).

### 4.7 Context 및 ThreadLocal 정리

```text
 Filter 성공
    │ ServiceContextHolder.setInstance(...)
    │ MDC(guid, ip, userId, serviceId)
    ▼
  … Interceptor / Aspect / Controller / Service / DAO …
    ▼
 Filter finally
    │ ServiceContextHolder.remove()
    │ ThreadContext.clearAll()
    ▼
 톰캣 워커 재사용 안전
```

| 저장소 | 보관 내용 | 정리 시점 |
| ------ | --------- | --------- |
| `ServiceContextHolder` | appName, guid, profile, headers, request/response, `hdr_nhnis` | `DefaultFilter` finally (+ Interceptor `afterCompletion` 보조) |
| Log4j2 `ThreadContext` | `guid`, `ip`, `userId`, `serviceId` (+ `sqlId`, `errCode`) | `DefaultFilter` finally |

**정리하지 않으면** 톰캣 워커 재사용 시 이전 거래의 GUID가 다음 거래 로그에 유출된다. Filter 코드 변경 시 `finally` 블록을 반드시 유지한다.

> **개발·검증 체크리스트 (§4)**
>
> - [ ] `nhnis.fw.commons.filter.enabled=true` · `legacy-web.enabled=true`인가
> - [ ] `ClientHttpConnector` Bean이 존재하는가 (`FilterConfiguration` 생성자 주입)
> - [ ] 신규 Controller가 `nhnis.mk.co..controller..*` pointcut에 포함되는가
> - [ ] Controller가 fw `RequestBody`를 import했는가 (Spring 표준 아님)
> - [ ] Filter `finally`의 Context·MDC 정리 코드가 유지되는가
> - [ ] TCF Filter·fw commons Security를 이중 등록하지 않았는가
> - [ ] Aspect 안에서 DAO·외부 호출을 하지 않는가

## 5. TCF/STF/ETF 아키텍처

> **이 장에서 알 수 있는 것**
> - TCF 경로가 원래 무엇을 하려던 설계인지
> - **현재 설정에서 왜 실행되지 않는지**와 그 판단 근거
> - `@TcfTransaction` / `TCFAspect` / STF / ETF의 역할 분담
> - commons(현행) 경로와의 계약 차이, 그리고 혼용 금지 이유
>
> ⛔ **본 장 전체가 비활성 경로다.** PDMK API 계약으로 인용하지 않는다. 신규 거래에 적용하지 않는다.

### 5.1 TCF 경로의 목적

TCF(Transaction Control Framework)는 "**필터는 어떤 거래인지 몰라도 해야 하는 일, AOP는 어떤 거래인지 알아야 할 수 있는 일**"이라는 기준으로 횡단 관심사를 배치한 설계다.

| 지점 | 볼 수 있는 것 | 볼 수 없는 것 |
| ---- | ------------- | ------------- |
| Servlet Filter | HTTP 바이트, URI, 응답 상태 | 어느 거래인지, 역직렬화된 DTO, 업무 예외 |
| Security Filter | 위 + 인증 주체 | 위와 동일 |
| AOP `@Around` | 타입 있는 인자·반환값, 애노테이션 메타, 업무 예외 | HTTP 원문 |
| `@RestControllerAdvice` | 컨트롤러 밖으로 나간 예외 | 필터 내부에서 난 예외 |

그래서 GUID 채번·MDC는 Filter(`TcfTraceFilter`), 헤더 검증·결과 코드 판정·업무 예외 처리는 AOP(`TCFAspect` → STF/ETF)에 두었다.

핵심 원칙은 **Aspect가 로직을 갖지 않는다**는 것이다. Aspect는 STF와 ETF를 순서대로 호출하는 배선 담당이고, 실제 로직은 평범한 `@Component`에 있어 AOP 없이 단위 테스트할 수 있다.

### 5.2 현재 설정에서의 활성 여부

```text
              nhnis.fw.tcf.enabled
                      │
        false ────────┴──────── true
      (PDMK 기본 ✅)          (비권장 · 혼용 금지)
          │                        │
          ▼                        ▼
   commons 경로만            TCFAspect + STF/ETF
   Filter + Interceptor      + commons 이중 경로 위험
   + BizPrePostAspect
```

| 구성요소 | 조건 키 | 현재 값 | 상태 |
| -------- | ------- | ------- | ---- |
| `TCFAspect` | `nhnis.fw.tcf.enabled` | `false` | ⛔ Bean 미생성 |
| `TcfTraceFilter` | `nhnis.fw.tcf.enabled` | `false` | ⛔ |
| `JwtAuthenticationFilter` | Security 체인 **수동** 등록 필요 | 미등록 | ⛔ |
| `STF` / `ETF` / `TcfContext` | `nhnis.fw.tcf.enabled` | `false` | ⛔ |
| `GlobalExceptionHandler`(TCF) | `nhnis.fw.tcf.enabled` | `false` | ⛔ |
| `TcfAuthenticationEntryPoint` | TCF Security 구성 시 | 미구성 | ⛔ |

**판단 근거:** `pdmk-service/src/main/resources/application.yml`의 `nhnis.fw.tcf.enabled: false`. 소스가 `pdmk-fw`에 남아 있어도 **런타임 영향은 없다.**

### 5.3 @TcfTransaction과 TCFAspect

| 항목 | 값 |
| ---- | -- |
| 애노테이션 | `nhnis.fw.tcf.TcfTransaction(serviceId, transactionCode, processingType)` |
| Aspect | `nhnis.fw.tcf.aspect.TCFAspect` — `@Around("@annotation(TcfTransaction)")` |
| 역할 | STF 선처리 → `proceed()` → ETF 성공/업무실패/시스템실패 |
| 반환 타입 | `StandardResponseDto` **고정** |

```java
// ⛔ 참고용 — PDMK 현행 계약 아님
@TcfTransaction(serviceId = "MP.SalesTip.list",
                transactionCode = "MP-INQ-0001",
                processingType = ProcessingType.INQUIRY)
@PostMapping("/list")
public StandardResponseDto<List<XxxDtoOut>> list(
        @RequestBody StandardRequestDto<XxxDtoIn> request) { ... }
```

**기술적 제약:** Spring AOP는 CGLIB 프록시로 동작하므로 프록시 메서드의 선언 반환 타입이 유지된다. 어드바이스가 다른 타입을 반환하면 `ClassCastException`이 난다. 즉 AOP는 성공 응답을 실패 전문으로 **바꿔 끼울 수는 있어도 반환 타입 자체를 바꿀 수는 없다.** 그래서 Controller가 봉투 타입을 선언하고 Body만 채우면 ETF가 `header`·`result`를 완성하는 구조가 되었다.

### 5.4 STF 전처리

`nhnis.fw.tcf.stf.STF.preProcess(request, @TcfTransaction)`

| 순 | 처리 |
| -- | ---- |
| 1 | 표준 헤더 정규화 + 거래 정의(`@TcfTransaction` 메타)로 보완 |
| 2 | `StandardHeaderValidator`로 필수값 검증 |
| 3 | `SecurityContext`에서 userId 보강 → MDC 갱신 |
| 4 | `TcfContext` 생성 (헤더, 시작 시각(nanos), 클라이언트 원본 헤더) |
| 5 | 거래 시작 로그 기록 |

`TcfContextHolder`(ThreadLocal)는 Service에서 guid·userId를 직접 꺼내 쓸 때만 필요하며, 사용 시 **정리 책임**이 따른다.

commons 경로에서 이에 대응하는 것은 `DefaultFilter`의 헤더 파싱·보강 + `ServicePreventionInterceptor.preHandle`이다 ([§4.2](#42-defaultfilter)·[§4.3](#43-servicepreventioninterceptor)).

### 5.5 ETF 응답·오류 처리

`nhnis.fw.tcf.etf.ETF` — 후처리 진입점 + **실패 전문 조립 단독 책임**

| 메서드 | 상황 | 결과 |
| ------ | ---- | ---- |
| `success` | 정상 종료 | `result.resultCode` 성공 코드, 응답 헤더 echo |
| `businessFail` | STF 헤더 검증 실패 / Service 업무 예외(`BizException`) | `result.errorCode` + `errorMessage` |
| `systemError` | 예상 밖 예외 | 시스템 오류 코드 |

공통 후처리: 소요시간·거래 종료 로그, `TcfContext` 정리.

#### 실패 전문이 발생하는 네 지점

| 예외 발생 위치 | 처리 주체 | AOP가 볼 수 있나 |
| -------------- | --------- | ---------------- |
| Trace/JWT 필터 | Security `AuthenticationEntryPoint` | ✗ |
| Jackson 역직렬화 실패 | `GlobalExceptionHandler` | ✗ |
| STF 헤더 검증 | Aspect → `ETF.businessFail` | ✓ |
| Service 업무 예외 | Aspect → `ETF.businessFail` | ✓ |

네 경로가 서로 다른 포맷을 내면 클라이언트가 분기 처리를 해야 하므로, **`GlobalExceptionHandler`와 `AuthenticationEntryPoint`도 ETF를 주입받아** 동일 포맷을 내도록 설계되어 있다. 이것이 ETF가 AOP 전용이 아니라 공용 컴포넌트인 이유다.

메시지 해석은 `ExceptionCodeProperties.message(code, args)`, 인증 실패는 `TcfAuthenticationEntryPoint` → HTTP 401 + `FW0401`.

### 5.6 Trace·MDC·Context

`TcfTraceFilter` (`@Order(HIGHEST_PRECEDENCE)`):

```java
// ⛔ 참고용
long startedAt = System.nanoTime();
try { chain.doFilter(request, response); }
finally { recordTotalElapsed(request, response, startedAt); }
```

- guid/traceId 채번, clientIp 추출, MDC put → **심은 곳에서 지운다**(`finally { MDC.clear(); }`)
- HTTP 총 소요시간 측정: `[TRACE] POST /… status=200 total=3250ms`
- 임계치 초과 시 WARN (`slow-transaction-ms`, 예 3000ms)

TCF는 **두 지점에서 시간을 잰다.** Filter는 총 응답시간(보안 필터 + JSON 변환 + STF + Controller + Service + DB + ETF + 응답), AOP(`TcfContext.elapsedMs()`)는 순수 업무 처리시간. 두 값의 차이가 크면 병목이 업무가 아니라 직렬화·필터에 있다는 진단이 가능하다 ([§12.8](#128-지연-거래와-성능-측정)).

commons 경로의 대응물은 `DefaultFilter`의 MDC 시드 + `PdmkTxLog` 타임라인이며, **총 소요시간 자동 측정·지연 WARN은 없다** ([§17.5](#175-확인된-제약과-주의사항)).

### 5.7 Legacy Commons 경로와의 차이

```text
                       pdmk-fw
             ┌────────────┴────────────┐
             ▼                         ▼
     nhnis.fw.commons.*         nhnis.fw.tcf.*
      Filter / Interceptor        TCFAspect / STF / ETF
      hdr_nhnis + dto             StandardRequestDto / result
      NhBaseException             BizException
             │ enabled=true              │ enabled=false
             ▼                           ▼
        ★ PDMK 런타임 ✅            (소스만 잔존) ⛔
```

| 항목 | commons ✅ | TCF ⛔ |
| ---- | ---------- | ------ |
| 패키지 | `nhnis.fw.commons.*` | `nhnis.fw.tcf.*` |
| 스위치 | `commons.filter.enabled` / `commons.legacy-web.enabled` | `nhnis.fw.tcf.enabled` |
| 요청 전문 | `hdr_nhnis` + `dto` | `StandardRequestDto{header, body}` |
| 응답 전문 | `{hdr_nhnis, dto}` | `StandardResponseDto{header, result, body}` |
| 표준 예외 | `NhBaseException` (checked) | `BizException` (unchecked) |
| 오류 조립 | `ResponseBodyArgumentResolver.errorProcessor` | `ETF.businessFail/systemError` |
| 거래 선언 | 없음 (URL = 서비스 ID) | `@TcfTransaction(serviceId, …)` |
| 선후처리 | Interceptor + `BizPrePostAspect` | `TCFAspect` `@Around` |
| 인증 | `DefaultFilter` + `JwtProvider` | `JwtAuthenticationFilter` + SecurityContext |
| 성능 측정 | 없음 (SQL debug 로그만) | Filter total + AOP business 2구간 |

**혼용 금지 이유**

| 혼용 조합 | 발생 문제 |
| --------- | --------- |
| TCF Filter + `DefaultFilter` JWT | 이중 인증 경로, 401 문구·형식 불일치 |
| `TCFAspect` + `BizPrePostAspect` | 이중 선후처리, 로그 중복 |
| `result.resultCode` + `NH_NIS_ERR_DTO` | 한 API에서 오류 스키마가 갈림 |

**제거 정책:** 제거 여부는 팀 정책에 따른다. 제거 시 `nhnis.fw.tcf.**`와 TCF 전용 `GlobalExceptionHandler`를 함께 정리한다.

> **개발·검증 체크리스트 (§5)**
>
> - [ ] `nhnis.fw.tcf.enabled=false`인지 기동 로그·설정에서 확인했는가
> - [ ] 신규 Controller에 `@TcfTransaction`을 붙이지 않았는가
> - [ ] `StandardRequestDto`/`StandardResponseDto`를 PDMK API 계약으로 문서화하지 않았는가
> - [ ] `BizException`을 commons 경로 Service에서 던지지 않았는가
> - [ ] TCF Filter와 `DefaultFilter`를 동시에 활성화하지 않았는가
> - [ ] TCF 소스 제거 시 예외 핸들러·Security 구성까지 함께 정리했는가

## 6. 서비스와 전문 계약

> **이 장에서 알 수 있는 것**
> - 서비스 ID의 구조와 URL·클래스·SQL로의 전개 규칙
> - `hdr_nhnis` + `dto` 전문 봉투와 `sys_comm` 필드 의미
> - `DTOin` / `DTOout` / `DTOSub` 클래스 규칙
> - 요청 바인딩·응답 조립 경로와 검증 규칙
> - 현재 구현된 거래 목록

### 6.1 Service ID와 URL 규칙

```text
 [대구분2][업무2][세부1][식별번호4][구분자1][순번1]
    mk      co     a      8888       S       0
 → mkcoa8888S0
```

| 요소 | 자릿수 | 값 예 | 설명 |
| ---- | ------ | ----- | ---- |
| 대구분 | 2 | `mk` | 시스템 대구분 |
| 업무 | 2 | `co` | 업무 구분 |
| 세부 | 1 | `a` | 세부 구분 |
| 식별번호 | 4 | `8888` | 프로그램 식별 |
| 구분자 | 1 | `S`/`C`/`U`/`D`/`A`/`R` | 조회/등록/수정/삭제/혼합/리포트 |
| 순번 | 1 | `0`~`9`, 초과 시 `A`~`Z` | 동일 구분자 내 일련 |

#### 서비스 ID의 전개

| 위치 | 값 예 |
| ---- | ----- |
| URL | `POST /mkcoa8888S0` |
| `sys_comm.rms_svc_c` | `mkcoa8888S0` |
| `sys_comm.scid` | `mkcoa8888` (구분자·순번 제거) |
| Controller 메서드 | `mkcoa8888S0(...)` |
| Service 메서드 | `mkcoa8888S0(...)` |
| DTO | `mkcoa8888S0DTOin` / `DTOout` / `DTOSub0` |
| DAO 메서드 = SQL ID | `mkcoa8888S0_S0`, `mkcoa8888S0_S0_count`, `mkcoa8888D0_D0` |
| Mapper XML | `rdw.mk.co.a/mkcoa8888-ORA.xml` |

**클래스는 식별번호 단위, DTO는 서비스 ID 전체.** 동일 식별번호의 `S0`+`D0`는 하나의 Controller/Service/DAO로 묶는다. 클래스명에 구분자(`S0`)를 넣지 않는다.

| 금지 | 영향 |
| ---- | ---- |
| REST `/api/mk/.../list` | Filter·카탈로그·전문 계약 불일치 (`pdmk-ui`의 `/api/relay`는 UI 전용) |
| 클래스 `@RequestMapping` | URL 축이 두 곳으로 갈림 |
| `DtoIn` / `Dao` 등 임의 표기 | 서비스 ID 추적 불가 |
| UI 카탈로그 ID ≠ 서비스 URL | 중계 404 |

명명 세부 규칙의 정본은 [MK-NAMING_CONVENTION.md](./MK-NAMING_CONVENTION.md)이며 **충돌 시 CONVENTION이 우선**한다.

### 6.2 hdr_nhnis + dto 전문 구조

```text
┌──────────────────── 요청 / 응답 JSON ────────────────────┐
│ hdr_nhnis                      ← 공통 헤더 (pdmk-fw 소유) │
│ └─ sys_comm                    ← 시스템 공통 필드          │
│      ├─ std_gbl_id             GUID                       │
│      ├─ rms_svc_c              서비스 ID (= URL)          │
│      ├─ scid                   화면/프로그램 ID           │
│      └─ …                      단말·점·조작자 등          │
│                                                          │
│ dto                            ← 업무 본문 (service 소유) │
│ ├─ [요청] *DTOin  필드                                    │
│ └─ [응답] *DTOout 필드                                    │
│       ├─ *DTOSub0[]            목록 행                    │
│       └─ size/pageNo/totalCount/totalPages                │
└──────────────────────────────────────────────────────────┘
```

| 노드 | Java 타입 | 소유 모듈 |
| ---- | --------- | --------- |
| `hdr_nhnis` | `nhnis.fw.commons.dto.header.hdr_nhnis` | `pdmk-fw` |
| `sys_comm` | `nhnis.fw.commons.dto.header.sys_comm` | `pdmk-fw` |
| `dto`(요청) | `{서비스ID}DTOin` | `pdmk-service` |
| `dto`(응답) | `{서비스ID}DTOout` | `pdmk-service` |

#### local 축소 요청 (⚙️ 조건부)

`spring.profiles.active=local`이면 헤더 없이 본문만 보내도 Filter가 합성 헤더를 만든다.

```json
{ "dto": { "pageNo": 1, "pageSize": 20 } }
```

| 프로파일 | `hdr_nhnis` | Filter 동작 |
| -------- | ----------- | ----------- |
| `local` | 선택 | 없으면 GUID·서비스 ID 등으로 합성 |
| 비-local | **필수** | 없으면 400, JWT도 필요 |

### 6.4 DTOin·DTOout·DTOSub 구조

```text
 서비스 ID  mkcoa5530S0
    ├─ mkcoa5530S0DTOin     ← 요청 dto
    ├─ mkcoa5530S0DTOout    ← 응답 dto
    └─ mkcoa5530S0DTOSub0   ← 목록 1행
```

| 구분 | 클래스 패턴 | 상속 | 필드 표기 |
| ---- | ----------- | ---- | --------- |
| 입력 | `{서비스ID}DTOin` | `DataObject` | camelCase |
| 출력 | `{서비스ID}DTOout` | `DataObject` | camelCase |
| 목록행 | `{서비스ID}DTOSub{순번}` | `DataObject` | camelCase |
| 입출력 겸용 | `{서비스ID}DTOio` | `DataObject` | 필요 시에만 |

`DataObject`는 `com.ims.superspring.*` SuperSpring 호환 stub이다 ([§17.3](#173-stub호환-계층)).

목록 응답 개념도:

```text
 dto (DTOout)
 ├─ mkcoa5530S0DTOSub0 : [ {행0}, {행1}, … ]
 ├─ size               : 현재 페이지 건수
 ├─ pageNo / pageSize  : 적용된 페이징 값
 └─ totalCount / totalPages
```

**DTO는 Service·Controller가 공유하는 전달 객체이며 영속 엔티티가 아니다.** DAO 시그니처에 DTO를 쓰지 않는다(입력 `Map`, 출력 `List<Map>`/`int`) — [§8.5](#85-sql-id와-파라미터-바인딩).

### 6.5 요청 바인딩과 응답 조립

바인딩 경로 자체는 [§4.5](#45-requestresponse-resolver)에 정의되어 있다. 여기서는 **업무 개발자가 지켜야 할 계약**만 정리한다.

| 단계 | 컴포넌트 | 계약 |
| ---- | -------- | ---- |
| 요청 헤더 | `DefaultFilter` | 업무 코드는 `hdr_nhnis`를 직접 파싱하지 않는다 |
| 요청 본문 | `RequestBodyArgumentResolver` | **`dto` 노드만** DTOin으로 변환 |
| 응답 조립 | `ResponseBodyArgumentResolver` | Controller는 `DTOout`만 반환. 봉투는 자동 |
| 어노테이션 | `nhnis.fw.commons.resolver.RequestBody` | Spring 표준 `@RequestBody` 아님 |

응답 JSON 골격:

```json
{
  "hdr_nhnis": { "sys_comm": { "...": "요청과 동일 컨텍스트 헤더" } },
  "dto": {
    "mkcoa5530S0DTOSub0": [],
    "size": 0, "pageNo": 1, "pageSize": 20,
    "totalCount": 0, "totalPages": 0
  }
}
```

| 금지 | 이유 |
| ---- | ---- |
| 루트에 업무 필드 직접 배치 | Filter/Resolver는 `hdr_nhnis`+`dto`만 인식 |
| Spring 표준 `@RequestBody` 사용 | `dto` 노드 추출 실패 |
| Controller에서 봉투를 직접 조립 | Advice와 이중 포장 |
| TCF `StandardRequestDto`·`result.*` 혼용 | 계약 스키마 분기 ([§5.7](#57-legacy-commons-경로와의-차이)) |

### 6.6 검증 규칙

**✅ AS-IS:** 현재 샘플에는 **Bean Validation(`@Valid`) 기반 선언적 검증이 구성되어 있지 않다.** 검증은 Service 진입부의 명시적 분기로 수행한다.

| 검증 대상 | 수행 위치 | 실패 처리 |
| --------- | --------- | --------- |
| 전문 봉투 구조(`hdr_nhnis`·`dto` 존재) | `DefaultFilter` | HTTP 400 `sendError` (봉투 없음) |
| JWT 유효성 (⚙️ 비-local) | `DefaultFilter` | HTTP 401 `sendError` |
| GUID 존재 | `ServicePreventionInterceptor` | 없으면 **UUID 강제 채번** (실패 아님) |
| 필수 업무 입력값 | **Service** | `NhBaseException` 권장 ([§10.2](#102-bizexception)) |
| 페이징 값 범위 | **Service** | 예외 아님 — 정규화(clamp) ([§8.6](#86-oracle-rownum-페이징)) |
| 조회 0건 | **Service** | 예외 아님 — 빈 목록 + `totalCount=0` |

**권장 규칙**

| 상황 | 처리 |
| ---- | ---- |
| 클라이언트가 "실패 전문"으로 받아야 하는 것 | `NhBaseException` throw |
| "성공 전문 + 업무 결과 플래그"로 충분한 것 | `DTOout` 결과 코드 (`RSLT_CD` 등) |
| DB·NPE 등 예상 밖 | `NhExceptionProvider.exceptionBuilder`로 `FW9999` 래핑 |

⚠️ 현재 샘플은 조회 0건·삭제 0건을 결과 코드 필드로 돌려주는 경우가 있다. **시스템·검증 오류는 예외, 업무 정상 분기는 DTOout**으로 나누는 것이 표준이다.

## 7. 업무 계층 아키텍처

> **이 장에서 알 수 있는 것**
> - Controller / Service / DAO / Mapper XML 각각이 "무엇을 하고 무엇을 하지 않는지"
> - DTO ↔ Map 변환을 어디서 수행하는지
> - 조회·등록·수정·삭제 표준 패턴
> - 신규 거래 구현 절차와 금지 패턴

### 7.1 Controller의 책임

| 한다 | 하지 않는다 |
| ---- | ---------- |
| `@RestController` 선언 | 클래스 `@RequestMapping` |
| `@PostMapping("/{서비스ID}")` 단일 매핑 | SQL·DAO 직접 호출 |
| Service 위임 | 트랜잭션 선언(`@Transactional`) |
| 시작/종료 로그 (`PdmkTxLog.controller*` 또는 동등 문자열) | Map↔DTO 대량 매핑 |
| `throws Exception`/`Throwable`로 예외 전파 | 오류 DTO 직접 조립 |

```java
@Slf4j
@RestController
@RequiredArgsConstructor
public class mkcoa5530Controller {

    private final mkcoa5530Service service;

    @PostMapping("/mkcoa5530S0")
    public mkcoa5530S0DTOout mkcoa5530S0(@RequestBody mkcoa5530S0DTOin in) throws Exception {
        return service.mkcoa5530S0(in);      // 진입·위임만
    }
}
```

`NhBaseException`은 **checked**이므로 `throws` 선언이 있어야 Advice까지 전파된다 ([§10.1](#101-예외-처리-전체-흐름)).

### 7.2 Service의 책임

| 한다 | 하지 않는다 |
| ---- | ---------- |
| 업무 규칙·검증 | HTTP 헤더·`HttpServletRequest` 직접 조작 |
| DAO 조합 호출 (목록 + count 등) | `@PostMapping` 등 웹 어노테이션 |
| DTO ↔ Map 변환 | SQL 문자열 조립 |
| 페이징 정규화·offset 계산 | 오류 문구 하드코딩 |
| `@Transactional` 경계 선언 (권장) | ImageLog 직접 기록 |
| 결과 DTOout 조립 | |

메서드명은 **서비스 ID 전체**(`mkcoa5530S0`), 클래스명은 식별번호 단위(`mkcoa5530Service`)다.

### 7.3 DAO의 책임

| 한다 | 하지 않는다 |
| ---- | ---------- |
| MyBatis Mapper 인터페이스 **메서드 선언만** | 업무 if·검증 |
| `@RDWMapper` 부착 | DTO 타입 시그니처 |
| 메서드명 = SQL ID | Controller/Service 참조 |
| `throws Exception` | `@Transactional` |

```java
@RDWMapper
public interface mkcoa8888DAO {
    List<Map<String, Object>> mkcoa8888S0_S0(Map<String, Object> input) throws Exception;
    int mkcoa8888S0_S0_count(Map<String, Object> input) throws Exception;
    int mkcoa8888D0_D0(Map<String, Object> input) throws Exception;
}
```

`@RDWMapper`는 `nhnis.mk.config.RDWMapper` → `@Mapper` 메타 애노테이션이다.

### 7.4 Mapper XML의 책임

| 항목 | 규칙 |
| ---- | ---- |
| 위치 | `src/main/resources/rdw.mk.co.a/mkcoa{식별}-ORA.xml` |
| `namespace` | DAO **FQCN** (`nhnis.mk.co.a.dao.mkcoa8888DAO`) |
| `id` | DAO 메서드명과 **문자 단위 일치** |
| `parameterType`/`resultType` | 명시 (동적·단순 시 `java.util.HashMap`) |
| SQL 주석 | `/* SQL ID */` 포함 (로그 추적용) |
| 바인딩 | `#{…}` 만 사용 (`${…}` 금지 — SQL Injection) |
| 공통 WHERE | `<sql id="…Where">` + `<include>` (목록/count 공유) |
| Alias | 테이블 `T1`, `T2`… / 컬럼 `AS` |

```xml
<mapper namespace="nhnis.mk.co.a.dao.mkcoa8888DAO">
  <select id="mkcoa8888S0_S0" parameterType="java.util.HashMap" resultType="java.util.HashMap">
    SELECT /* mkcoa8888S0_S0 */ … 
  </select>
</mapper>
```

### 7.5 DTO↔Map 변환

```text
 Service
  ├─ DTOin → Map  : 검색조건 + pageNo + pageSize + offset
  ├─ DAO 호출     : {SQLID}_count(param) → totalCount
  │                 {SQLID}(param)       → List<Map> rows
  ├─ Map 행 → DTOSub
  └─ DTOout 조립  : Sub[] + size + pageNo + pageSize + totalCount + totalPages
```

변환 보조 유틸은 `nhnis.mk.common.util.MappingUtil` 등에 둔다.

**⚠️ 키 대소문자 주의:** H2/Oracle/MyBatis 조합에 따라 Map 키가 `GUID` / `guid`로 달라질 수 있다. **Service에서 흡수**하고, DTO 필드는 camelCase를 유지한다.

### 7.6 조회·등록·수정·삭제 패턴

| 구분 | 서비스 ID 구분자 | Service 시그니처 | 트랜잭션 | SQL ID |
| ---- | ---------------- | ---------------- | -------- | ------ |
| 조회(목록) | `S` | `{ID}DTOout {ID}({ID}DTOin)` | `@Transactional(readOnly = true)` | `{ID}_S0` + `{ID}_S0_count` |
| 등록 | `C` | 동일 | `@Transactional` | `{ID}_C0` |
| 수정 | `U` | 동일 | `@Transactional` | `{ID}_U0` |
| 삭제 | `D` | 동일 | `@Transactional` | `{ID}_D0` |

#### 조회(목록) 표준 순서

```text
1. pageNo/pageSize 정규화 (1 / 20 / max 100)
2. offset = (pageNo - 1) * pageSize
3. param Map 구성 (조건 + pageNo + pageSize + offset)
4. totalCount = DAO.{ID}_count(param)
5. rows       = DAO.{ID}(param)         ← ROWNUM 슬라이스
6. DTOSub 매핑 → DTOout(size, pageNo, pageSize, totalCount, totalPages)
```

#### 쓰기(삭제 예) 표준 순서

```text
1. 입력 검증 (guidList 비어 있음 → NhBaseException 또는 결과코드 정책)
2. @Transactional 경계 안에서 DAO.{ID}_D0(param)
3. 영향 행 수(int)로 결과 판단
4. 실패 시 예외 → 전체 rollback
```

| 금지 | 결과 | 대안 |

| Controller/DAO에 `@Transactional` | 경계 이중화·미적용 | Service에만 |
| DAO 메서드명 ≠ XML `id` | MyBatis 매핑 실패 | 문자 단위 일치 |
| DAO 시그니처에 `DTOin`/`DTOout` | Map 계약 위반 | 입력 `Map`, 출력 `List<Map>`/`int` |
| Mapper XML을 `mapper/` 임의 경로에 배치 | `classpath*:rdw.*/*.xml` 스캔 실패 | `rdw.mk.co.a/` |
| namespace에 식별번호만 기재 | FQCN 불일치 | DAO FQCN |
| Controller에서 offset 계산 | 레이어 붕괴 | Service |
| count 없이 `rows.size()`를 totalCount로 | 전체 건수 오류 | count SQL 쌍 |
| 클라이언트가 보낸 `offset` 신뢰 | 조작·불일치 | Service 재계산 |
| Spring 표준 `@RequestBody` | `dto` 추출 실패 | fw `RequestBody` |
| 같은 클래스 내부 호출로 `@Transactional` 기대 | 프록시 우회 | 별 Bean 분리 |
| 업무 조회 결과를 static Map에 캐시 | 정합성 붕괴 | [§13.5](#135-http-client와-connector) 경계 준수 |

> **개발·검증 체크리스트 (§7)**
>
> - [ ] Controller가 진입·위임·로그만 하는가
> - [ ] Service 메서드명이 서비스 ID와 같은가
> - [ ] DAO 메서드명 = XML `id` = SQL ID 인가
> - [ ] Mapper `namespace`가 DAO FQCN인가
> - [ ] `#{}` 바인딩만 사용했는가 (`${}` 없음)
> - [ ] 목록 SQL과 count SQL이 동일 WHERE를 `<include>`로 공유하는가
> - [ ] Map 키 대소문자 차이를 Service에서 흡수했는가
> - [ ] 금지 패턴 표의 항목에 해당하는 코드가 없는가

## 8. 데이터 접근과 페이징

> **이 장에서 알 수 있는 것**
> - RDW DataSource와 관련 Bean 구성
> - H2 로컬과 Oracle 폐쇄망의 차이
> - MyBatis 설정·Mapper 검색 규칙
> - 테이블과 서비스의 매핑, SQL ID·파라미터 계약

### 8.1 RDW DataSource

```text
 RdwDataSourceConfig
 ├─ rdwDataSource          @Primary · HikariCP · @ConfigurationProperties("spring.datasource.rdw")
 ├─ rdwSqlSessionFactory   MyBatis (+ MybatisLogInterceptor 플러그인)
 ├─ rdwSqlSessionTemplate
 └─ rdwTransactionManager  @Primary · DataSourceTransactionManager
        │
        ▼
   동일 DataSource Connection으로 SQL 묶음
```

| Bean | 클래스 | 비고 |
| ---- | ------ | ---- |
| `rdwDataSource` | `HikariDataSource` | `spring.datasource.rdw.*` 바인딩 |
| `rdwSqlSessionFactory` | `SqlSessionFactory` | Mapper XML 로딩 |
| `rdwSqlSessionTemplate` | `SqlSessionTemplate` | DAO 프록시가 사용 |
| `rdwTransactionManager` | `DataSourceTransactionManager` | `@Primary` — `@Transactional` 기본 TM |

`SqlSessionTemplate`과 `TransactionManager`가 **같은 DataSource**를 써야 원자성이 유지된다.

`pdmk-fw`의 `ImageLogHandler`는 `JdbcTemplate`으로 **Primary DS를 별도 사용**하므로 업무 TX와 커밋 단위가 분리된다 ([§9.5](#95-imagelog와-업무-tx의-관계)).

### 8.2 H2 Local과 Oracle 구성

| 항목 | local (H2) | 폐쇄망 (Oracle) |
| ---- | ---------- | --------------- |
| URL | `jdbc:log4jdbc:h2:mem:pdmk;MODE=Oracle;…` | Oracle RDW (`SBMFCRT` 등) |
| 스키마 생성 | `spring.sql.init.schema-locations=classpath:db/h2/schema.sql` | **앱이 생성하지 않음** (DBA/기존 스키마) |
| 시드 데이터 | `classpath:db/h2/data.sql` | 운영 데이터 |
| `spring.sql.init.mode` | `always` | **비활성** |
| 의존성 | `runtimeOnly` H2 | `ojdbc` + `orai18n` (build.gradle 주석 전환) |
| 재기동 | mem DB 초기화됨 | 유지 |

`MODE=Oracle`이므로 **ROWNUM 등 Oracle 문법이 로컬에서도 동작**한다. Mapper XML은 단일(`-ORA.xml`)로 유지한다.

**환경 전환은 세 곳을 함께 바꾼다:** `application.yml` DS 블록 · `build.gradle` JDBC 의존 · `spring.sql.init` ([§15.7](#157-환경-전환)).

### 8.3 MyBatis 설정과 Mapper 검색

| 항목 | 값 |
| ---- | -- |
| `@MapperScan` | `nhnis.mk.**.dao` → `rdwSqlSessionTemplate` |
| XML 스캔 패턴 | `classpath*:rdw.*/*.xml` |
| XML 디렉터리 | `src/main/resources/rdw.mk.co.a/` |
| XML 파일명 | `mkcoa{식별}-ORA.xml` (DB 구분 `ORA`/`MYS`/`MSS`) |
| 플러그인 | `MybatisLogInterceptor` (`@Intercepts` Executor query/update) |

디렉터리명 `rdw.mk.co.a`는 **점(`.`)이 들어간 단일 디렉터리명**이다(패키지가 아니다). 임의 경로(`mapper/` 등)에 두면 스캔되지 않는다.

### 8.4 테이블과 서비스 매핑

```text
                RDW (H2 / Oracle)
  ┌──────────────────────┬───────────────────────────┐
  │ TB_FW_IMAGE_LOG      │ TB_MK_CO_A_5530           │
  │  (FW 감사)           │ TB_CR_AH_SALES_TIP_RACT   │
  └──────────┬───────────┴───────────┬───────────────┘
             │                       │
  fw ImageLogHandler          service MyBatis DAO
  (JdbcTemplate I/U)          (mkcoa8888 / 5530 / 9999)
             └───────────┬───────────┘

                   pdmk-service
                         ▲ HTTP only
                    pdmk-ui (DB 없음)
```

| 테이블 | 구분 | 주 접근 | DML | 비고 |
| ------ | ---- | ------- | --- | ---- |
| `TB_FW_IMAGE_LOG` | FW 공통(감사) | fw `ImageLogHandler` + `mkcoa8888` | I/U(fw), S/D(service) | `GUID` PK |
| `TB_MK_CO_A_5530` | 업무 샘플 | `mkcoa5530` | S | PK `(L5101, L5103)` |
| `TB_CR_AH_SALES_TIP_RACT` | 업무 샘플(공유 원장 형식) | `mkcoa9999` | S | PK 4컬럼 |
| 메시지 번들 테이블 | FW 옵션 | `MessageLoader` | S(기동 시) | ⚙️ H2 스키마 **미포함** |

컬럼 상세는 [부록 D](#부록-d-테이블mappersql-id-매핑)를 본다.

#### 명명·소유

| 패턴 | 의미 | 예 |
| ---- | ---- | -- |
| `TB_FW_*` | 프레임워크 공통 | `TB_FW_IMAGE_LOG` |
| `TB_MK_{업무}_{세부}_*` | MK 샘플·식별 대응 | `TB_MK_CO_A_5530` |

스키마·권한 소유자는 RDW다. **앱은 테이블 오너가 아니다.** 새 MK 전용 테이블은 `TB_MK_…`를 우선하고, 공유 원장은 기존명을 유지한다.

### 8.5 SQL ID와 파라미터 바인딩

```text
 [서비스ID]_[DML][순번]
 [서비스ID]_[DML][순번]_count
```

| 예 | DML | 반환 |
| -- | --- | ---- |
| `mkcoa8888S0_S0` | 목록 SELECT | `List<Map<String,Object>>` |
| `mkcoa8888S0_S0_count` | COUNT | `int` |
| `mkcoa8888D0_D0` | DELETE | `int` (영향 행 수) |

| 규칙 | 설명 |
| ---- | ---- |
| 메서드명 = XML `id` | 문자 단위 일치 |
| 입력 | `Map<String,Object>` — Service가 DTOin에서 구성 |
| 출력 | `List<Map<…>>` 또는 `int` |
| 예외 | `throws Exception` |
| 순번 | `0~9`, 초과 시 `A~Z` |
| 바인딩 | `#{…}` (전치 `${…}` 사용 금지) |
| 동적 SQL | `<if>`, `<foreach>`, `<include>` |

### 8.6 Oracle ROWNUM 페이징

#### 계약 상수

| 항목 | 값 | 처리 |
| ---- | -- | ---- |
| `pageNo` 기본 | **1** | `null` 또는 ≤0 → 1 |
| `pageSize` 기본 | **20** | `null` 또는 ≤0 → 20 |
| `pageSize` 최대 | **100** | 초과 시 100으로 clamp |
| `offset` | `(pageNo - 1) * pageSize` | **Service가 계산**해 Map에 주입 |
| `totalPages` | `ceil(totalCount / pageSize)` = `(totalCount + pageSize - 1) / pageSize` | Service |
| 0건 | 빈 Sub 목록 · `totalCount=0` · `size=0` | **예외 아님** |

#### 전문 필드

**요청 `dto`**

| 필드 | 타입 | 필수 | 설명 |
| ---- | ---- | ---- | ---- |
| `pageNo` | Integer | 선택 | 페이지 번호 |
| `pageSize` | Integer | 선택 | 페이지 크기 |
| (기타) | — | — | 검색 조건 |

**응답 `dto`**

| 필드 | 타입 | 설명 |
| ---- | ---- | ---- |
| `*DTOSub0[]` | 배열 | 현재 페이지 행 |
| `size` | int | **현재 페이지** 건수 (= Sub 길이) |
| `pageNo` / `pageSize` | int | 적용된 값(clamp 후) |
| `totalCount` | long/int | 조건 전체 건수 (count 쿼리) |
| `totalPages` | int | 전체 페이지 수 |

> `size` ≠ `totalCount`. UI 네비게이션은 `totalCount`/`totalPages`를 사용한다.

#### SQL 표준형

```sql
SELECT * FROM (
  SELECT a.*, ROWNUM rnum FROM (
    SELECT /* {서비스ID}_S0 */ …
      FROM T1 …
     WHERE …
     ORDER BY …          -- ★ 안쪽 SELECT에 고정 (페이지 안정성)
  ) a
  WHERE ROWNUM <= #{offset} + #{pageSize}
)
WHERE rnum > #{offset}
```

| 항목 | 규칙 |
| ---- | ---- |
| 엔진 | Oracle / H2 `MODE=Oracle` |
| `ORDER BY` 위치 | 반드시 **안쪽** SELECT |
| WHERE 공유 | `<sql id="…Where">` + `<include>` (목록·count 동일) |
| Keyset/커서 페이징 | 미사용 |
| Spring Data `Pageable` | 미사용 (Map + ROWNUM) |
| 페이징 공통 유틸 | `pdmk-fw`에 **없음** — Service 소유 |

#### 서비스별 현황

| 서비스 | 페이징 | count | 비고 |
| ------ | ------ | ----- | ---- |
| `mkcoa5530S0` | ✅ | ✅ | 안내항목 |
| `mkcoa8888S0` | ✅ | ✅ | 이미지로그 |
| `mkcoa9999S0` | ❌ | ❌ | ⚠️ **전량 반환** — 신규 거래에 복제 금지 |
| `mkcoa8888D0` | — | — | 삭제, 해당 없음 |

UI(`imagelog.js`, `online-single.js`)는 `pageSize` 입력(max 100)과 prev/next를 제공하며, **페이징을 재계산하지 않고** 서버 메타를 그대로 표시한다.

### 8.7 Count·목록 조회 계약

| 규칙 | 이유 |
| ---- | ---- |
| 목록 SQL ID와 count SQL ID를 **쌍**으로 둔다 | 전체 건수 확보 |
| 두 SQL은 **동일 WHERE**를 `<include>`로 공유한다 | 조건 불일치로 인한 페이지 수 오류 방지 |
| count는 `int` 반환 | Service가 `totalPages` 계산 |
| 목록 0건이어도 count는 호출한다 | `totalCount` 일관성 |
| 클라이언트에 `offset`을 노출하지 않는다 | 조작 방지 |

### 8.8 데이터 접근 체크리스트

> **개발·검증 체크리스트 (§8)**
>
> - [ ] `@RDWMapper` + 패키지 `nhnis.mk.**.dao` 인가
> - [ ] Mapper XML이 `rdw.mk.{업무}.{세부}/{식별}-ORA.xml`에 있는가
> - [ ] `namespace` = DAO FQCN 인가
> - [ ] 입력 `Map` / 출력 `List<Map>`·`int` 계약을 지켰는가
> - [ ] `{SQLID}`와 `{SQLID}_count`가 동일 WHERE를 공유하는가
> - [ ] ROWNUM 이중 래핑 + 안쪽 `ORDER BY` 인가
> - [ ] 기본 1 / 20, 최대 100, offset을 **Service**가 계산하는가
> - [ ] 0건을 빈 목록으로 반환하는가 (예외 아님)
> - [ ] 로컬 H2 `schema.sql`/`data.sql`과 Oracle 스키마가 논리적으로 동일한가

## 9. 트랜잭션 처리

> **이 장에서 알 수 있는 것**
> - "업무 거래"와 "DB 트랜잭션"이라는 두 의미의 구분
> - `rdwTransactionManager`와 `@Transactional` 적용 규칙
> - commit/rollback 시점과 예외 전파 순서
> - ImageLog가 업무 TX와 분리되는 이유
> - `ServiceTransactionManager`의 레거시 위치

### 9.1 Spring 트랜잭션 경계

| 용어 | 의미 | PDMK 구현 |
| ---- | ---- | --------- |
| **업무 거래(온라인 트랜잭션)** | `POST /{서비스ID}` 요청 1건의 생명주기 | Filter → Interceptor → Aspect → Controller → Service |
| **DB 트랜잭션** | SQL commit/rollback 단위 | `rdwTransactionManager` + `@Transactional` |

```text
 ┌────────────── 업무 거래 (요청 1건) ──────────────────────┐
 │  DefaultFilter → Interceptor → BizAspect → Controller    │
 │         │                                                │
 │  ┌──────▼──── Service (권장: @Transactional) ─────────┐  │
 │  │  Spring TX Proxy                                   │  │
 │  │     → rdwTransactionManager                        │  │
 │  │     → rdwDataSource → SqlSessionTemplate → DAO SQL │  │
 │  │  정상 → commit(쓰기) / 종료(읽기)                   │  │
 │  │  예외 → rollback                                   │  │
 │  └────────────────────────────────────────────────────┘  │
 │  Interceptor ImageLog PRE/POST — 별도 SQL, TX 분리        │
 └──────────────────────────────────────────────────────────┘
```

| 계층 | 트랜잭션 역할 |
| ---- | ------------- |
| Cross-cutting (Filter/Interceptor/Aspect) | 선후처리·로그. **DB TX 경계 아님** |
| Application (`*Service`) | **DB TX 경계** |
| Persistence (DAO/MyBatis) | Service TX에 참여 |
| Infrastructure (`rdwTransactionManager`) | commit/rollback 실행 |

### 9.2 rdwTransactionManager

| 항목 | 값 |
| ---- | -- |
| 타입 | `DataSourceTransactionManager` |
| 대상 DS | `rdwDataSource` (`@Primary`) |
| 지정 | `@Primary` — `@Transactional`이 별도 지정 없이 사용 |
| 활성화 | `PlatformTransactionManager` Bean 존재 → Boot가 TX 인프라 자동 구성 |

**주의:** TX 인프라가 활성이라는 것과 **경계가 있다는 것은 다르다.** `@Transactional` 선언이 있어야 비로소 경계가 생긴다.

### 9.3 @Transactional 적용 규칙

```java
@Service
@Transactional(readOnly = true)              // 클래스 기본: 조회
public class mkcoaXXXXService {

    public XxxS0DTOout mkcoaXXXXS0(...) { ... }   // 읽기 TX

    @Transactional(timeout = 4)               // 메서드가 클래스 설정을 덮어씀
    public XxxD0DTOout mkcoaXXXXD0(...) { ... }   // 쓰기 TX
}
```

| 용도 | 애노테이션 | 효과 |
| ---- | ---------- | ---- |
| 조회(S) | `@Transactional(readOnly = true)` | 읽기 전용 커넥션 힌트 |
| 등록·수정·삭제(C/U/D) | `@Transactional` (+ `timeout`) | 다중 SQL을 하나의 commit/rollback 단위로 |
| 타임아웃 | `timeout = 초` | 초과 시 DB 작업 경계에서 rollback |

| 규칙 | 이유 |
| ---- | ---- |
| Service에만 선언 | Controller·DAO는 경계가 아님 |
| 다중 DML은 **한 Service 메서드** 안에 | 원자성 확보 |
| self-invocation 금지 | 같은 클래스 내부 호출은 프록시 우회 → TX 미적용 |
| `timeout`은 **확정값만** | 추측값 금지 |
| TCF `@TcfTransaction` 재도입 금지 | DB commit을 하지 않는 별개 개념 ([§5.3](#53-tcftransaction과-tcfaspect)) |

**⚠️ 현재 샘플 상태**

| 항목 | 현재 | 권장 |
| ---- | ---- | ---- |
| `mkcoa*` Service `@Transactional` | **미선언** | 조회 `readOnly=true`, 쓰기 메서드 단위 선언 |
| `mkcoa8888D0` 삭제 | DAO `DELETE` 단건 호출 | 명시적 쓰기 TX |
| fw `ServiceTransactionManager` | 업무 코드에서 호출 없음 | 레거시로만 인지 |

`@Transactional`이 없어도 SQL은 실행된다. 다만 **여러 DAO 호출의 원자성과 예외 시 일괄 rollback은 보장되지 않는다.**

### 9.4 Commit과 Rollback

```text
 INSERT 성공 → UPDATE 실패
        │
        ▼  @Transactional 프록시가 예외 감지
   전체 rollback (INSERT도 취소)
        │
        ▼  예외를 Controller / 응답 Advice로 전파
```

예외 발생 시 처리 **순서**:

```text
 Service 예외
   → ① DB TX rollback         (TX 프록시 — 가장 먼저)
   → ② BizPrePostAspect @After
   → ③ Interceptor.afterCompletion → ImageLog EX
   → ④ ResponseBodyArgumentResolver → NH_NIS_ERR_DTO
   → ⑤ Filter finally → Context/MDC 정리
```

**DB 롤백이 항상 먼저다.** 오류 전문 조립 시점에는 이미 롤백이 끝나 있다.

#### `ttl_ug_ync`와 timeout의 관계

`sys_comm.ttl_ug_ync`는 전문 헤더의 TTL 사용 여부 **플래그**다. **Spring `@Transactional(timeout)`과 자동 연동되지 않는다.** 타임아웃이 필요하면 Service 메서드에 `timeout`을 명시한다. 또한 `timeout`은 **순수 Java sleep을 끊는 wall-clock 타이머가 아니며**, 다음 DB 경계·커밋 시점에 감지된다 ([4초지나면롤백되나.md](./4초지나면롤백되나.md) · [§12.7](#127-timeout-설정)).

### 9.5 ImageLog와 업무 TX의 관계

```text
 Interceptor PRE ── ImageLog INSERT ──── (별도 커넥션·커밋 가능)
        │
 ┌──────▼──── @Transactional Service ───┐
 │  DAO SELECT / DML                     │
 │  commit / rollback                    │
 └──────┬────────────────────────────────┘
        ▼
 Interceptor POST/EX ── ImageLog UPDATE ── (업무 TX와 분리)

 ※ 업무 rollback 후에도 PRE/EX 감사 행이 남을 수 있다.
```

| SQL | 호출 위치 | 업무 TX와의 관계 |
| --- | --------- | ---------------- |
| ImageLog PRE (INSERT) | `preHandle` | Controller/Service **이전** — 별도 커밋 가능 |
| 업무 SELECT/DML | Service → DAO | `@Transactional` 경계 안 |
| ImageLog POST (UPDATE) | `postHandle` | Service **이후** — 분리 |
| ImageLog EX (UPDATE) | `afterCompletion` | 업무는 이미 rollback된 뒤일 수 있음 |

**이것은 버그가 아니라 설계다.** 감사·추적 로그와 업무 원자성을 의도적으로 분리했다. `ImageLogHandler`는 JDBC 실패를 **삼키므로**(예외 미전파) 감사 실패가 거래를 막지 않는다.

> ImageLog 실패가 업무 commit을 막아야 하는지(또는 그 반대) 요구사항이 있다면 **명시적으로 정의**해야 한다. 현재는 "감사 실패는 무시"다.

### 9.6 ServiceTransactionManager의 레거시 역할

| 항목 | 내용 |
| ---- | ---- |
| 위치 | `nhnis.fw.commons.transaction.ServiceTransactionManager`, `InitTransactionManager`, Holder |
| 성격 | ThreadLocal 기반 **레거시 TX 홀더** |
| 현재 사용 | ⛔ 업무 코드에서 호출 없음 |
| 대체 | Service `@Transactional` + `rdwTransactionManager` |
| 정책 | 신규 코드에서 **사용하지 않는다.** 레거시 호환 유틸로만 인지 |

### 9.7 트랜잭션 설계 체크리스트

> **개발·검증 체크리스트 (§9)**
>
> - [ ] 조회 Service에 `@Transactional(readOnly = true)`를 선언했는가
> - [ ] 쓰기 메서드에 `@Transactional`(필요 시 `timeout`)을 선언했는가
> - [ ] 다중 DML이 **하나의** Service 메서드 TX 안에 있는가
> - [ ] Controller·DAO에 `@Transactional`이 없는가
> - [ ] self-invocation으로 TX를 기대하는 코드가 없는가
> - [ ] `timeout` 값이 추측이 아닌 확정값인가
> - [ ] `ttl_ug_ync`를 TX timeout으로 오해하지 않았는가
> - [ ] ImageLog 실패와 업무 commit의 관계를 요구사항으로 명확히 했는가
> - [ ] TCF `@TcfTransaction`을 도입하지 않았는가

## 10. 예외·오류·메시지

> **이 장에서 알 수 있는 것**
> - 예외가 어디서 발생해 어디서 포착되는지 전체 흐름
> - `NhBaseException`과 TYPE 체계
> - 오류 응답을 조립하는 실제 주체
> - 메시지 사전(`exceptionCode.yml` / `MessageCache`)의 우선순위
> - 업무 오류와 시스템 오류의 구분 기준, 표준 오류 응답 형태

### 10.1 예외 처리 전체 흐름

```text
                    예외·오류 발생 지점
                           │
     ┌─────────────────────┼─────────────────────┐
     ▼                     ▼                     ▼
 Filter 단계          Controller 전후        Service / DAO
 (Body·JSON·JWT)      (MVC / Advice)         (업무 로직)
     │                     │                     │
     │ sendError(4xx)      │                     │ throw NhBaseException
     ▼                     ▼                     ▼
 HTTP 상태 + 문구      ResponseBodyArgumentResolver
 (전문 봉투 없음)      .errorProcessor(NhBaseException)
                              │
                              ▼
                      NH_NIS_ERR_DTO 조립 + 메시지 해석
                              │
                              ▼
                      ResponseBodyAdvice
                      { hdr_nhnis, dto: 에러DTO }   HTTP 500
```

#### 포착 지점 (순서대로)

| 순 | 지점 | 조건 | 동작 |
| -- | ---- | ---- | ---- |
| 1 | `DefaultFilter` | Body/JSON/JWT/Header 실패 | `sendError`, **예외 미전파** |
| 2 | Spring TX Proxy | Service `@Transactional` + 예외 | rollback 후 재던짐 |
| 3 | `ResponseBodyArgumentResolver` | `NhBaseException` | `errorProcessor` → 에러 DTO |
| 4 | `Interceptor.afterCompletion` | `ex != null` | ImageLog EX, Context 제거, 재던짐 |
| 5 | `Filter finally` | 항상 | Context·MDC clear |
| — | TCF `TCFAspect` / `GlobalExceptionHandler` | `tcf.enabled=true` | ⛔ 미사용 |

#### 발생 지점별 분기

| 구분 | 예 | 결과 |
| ---- | -- | ---- |
| **[A] Filter 단계** | JSON 파싱 실패, JWT 무효 | `sendError(4xx)` → 체인 중단, MVC Advice 미도달 |
| **[B] Controller 진입 전 MVC** | 바인딩 오류 | 프레임워크 기본 처리 |
| **[C] Service/DAO 업무 예외** | 검증 실패, 대상 없음(정책상) | rollback → Advice → `NH_NIS_ERR_DTO` |
| **[D] 업무 "정상 분기"** | 조회 0건, 삭제 0건 | throw 하지 않음 → `DTOout` 결과코드 |

### 10.2 BizException

> **⚠️ 명칭 주의:** TOC의 이 절이 가리키는 "업무 예외"는, **PDMK 활성 경로에서는 `NhBaseException`이다.** `BizException`은 TCF 전용(⛔)이며 commons 샘플에서 사용하지 않는다.

| 예외 | 패키지 | checked? | PDMK 위치 |
| ---- | ------ | -------- | --------- |
| **`NhBaseException`** | `nhnis.fw.commons.exception` | **Yes** | ✅ commons 표준 업무/공통 예외 |
| `BizException` | `nhnis.fw.exception` | No | ⛔ TCF 전용 |
| `ServiceCommunicationException`, `ServiceHandlerNotFound` | commons | No | 연동·핸들러 부재 |
| `RuntimeException` / NPE 등 | JDK | No | 비권장 — 미래핑 시 컨테이너 기본 오류 |

#### `NhBaseException` 구성

| 필드 | 의미 |
| ---- | ---- |
| `stdErrCode` | 표준 오류 코드 (`FW0001` 등) |
| `errMsgType` (`TYPE`) | 메시지 소스 결정 |
| `messageValue[]` | `MessageFormat` 치환 인자 |
| `stdErrMsgContents` | 이미 완성된 문장이면 그대로 사용 |
| (자동 수집) | 클래스/메서드/파일/라인/스택 |

#### `TYPE`별 메시지 소스

| TYPE | 메시지 소스 | 용도 |
| ---- | ----------- | ---- |
| `RUNTIME` / `COMMON` / `AUTH` | `exceptionCode.yml` (`nhnis.exception.*`) | FW 공통·인증 |
| `SERVICE` / `BIZ` | `MessageCache` (DB 적재) | 업무 메시지 코드 |

사용 예:

```java
// 공통·검증 오류
throw new NhBaseException("FW0001", new String[]{"요청 Body"}, TYPE.COMMON);

// 업무 메시지 코드 (MessageCache)
throw new NhBaseException("MP0404", TYPE.BIZ);
```

#### `NhExceptionProvider` (표준화 유틸)

| 메서드 | 용도 |
| ------ | ---- |
| `nhExceptionBuilder(e, type)` | 이미 `NhBaseException`인 경우 스택·TYPE·MDC `errCode` 보강 |
| `exceptionBuilder(e)` | 임의 예외 → `FW9999` / `TYPE.RUNTIME`. `nhnis` 스택 프레임 우선, cause 메시지 포함 |

업무 Service에서 임의 예외를 삼키지 말고, **경계에서 Provider로 표준화**하는 패턴을 권장한다.

### 10.3 GlobalExceptionHandler

> ⛔ **비활성.** `nhnis.fw.exception.GlobalExceptionHandler`는 **TCF 경로 전용**이며 `nhnis.fw.tcf.enabled=true`일 때만 로드된다. PDMK 활성 경로에서 그 역할을 하는 것은 **`ResponseBodyArgumentResolver`(ResponseBodyAdvice)** 다.

| 항목 | TCF `GlobalExceptionHandler` ⛔ | commons `ResponseBodyArgumentResolver` ✅ |
| ---- | ------------------------------- | ----------------------------------------- |
| 기술 | `@RestControllerAdvice` | `ResponseBodyAdvice` + `@ExceptionHandler(NhBaseException)` |
| 포착 대상 | Jackson 역직렬화 실패 등 컨트롤러 밖 예외 | `NhBaseException` |
| 응답 조립 | `ETF`를 주입받아 `StandardResponseDto` | `NH_NIS_ERR_DTO` + `{hdr_nhnis, dto}` |
| HTTP 상태 | 상황별 | **500** |
| PDMK | 미사용 | 사용 |

**AS-IS 한계:** commons 경로에는 **모든 예외를 포괄하는 전역 핸들러가 없다.** `NhBaseException`이 아닌 예외(NPE 등)를 래핑하지 않으면 컨테이너 기본 오류 페이지가 나갈 수 있다. 그래서 [§10.2](#102-bizexception)의 `NhExceptionProvider` 래핑이 권장된다.

### 10.4 ExceptionCodeProperties

| 항목 | 내용 |
| ---- | ---- |
| 타입 | `ExceptionCodeProperties` — `@ConfigurationProperties("nhnis")` |
| 소스 | `exceptionCode.yml`의 `nhnis.exception.*` |
| import | `spring.config.import: classpath:exceptionCode.yml` |
| **주 소비자** | ⛔ TCF `ETF` (`message(code, args)`) |
| commons 경로 | `SpringContext.getProperty("nhnis.exception." + code)`로 **직접 조회** |

즉 **같은 yml을 두 경로가 다른 방식으로 읽는다.** commons가 활성이므로 실제로는 `SpringContext` 경로가 동작한다.

등록 예:

| 코드 | 메시지 템플릿 |
| ---- | ------------- |
| `FW0001` | `{0} 오류가 발생하였습니다.` |
| `FW0401` | 인증 실패 |
| `FW0403` | 권한 없음 |
| `FW9999` | 예기치 않은 시스템 오류 (기본 폴백) |
| `MP0404` / `MP0409` | 샘플 업무 코드 |

미등록 코드는 `FW9999`로 폴백하거나, 캐시에도 없으면 **코드 문자열 자체**가 메시지로 실린다.

### 10.5 MessageCache와 메시지 조회

```text
 exceptionCode.yml                 MessageCache (ConcurrentHashMap)
 nhnis.exception.{코드}            ← MessageLoader @PostConstruct
        │  (Spring Environment)             │  (DB SELECT)
        └───────────┬───────────────────────┘
                    ▼
        errorProcessor가 TYPE에 따라 선택 → MessageFormat 적용
```

| TYPE | 조회 경로 | 미존재 시 |
| ---- | --------- | --------- |
| `RUNTIME`/`COMMON`/`AUTH` | `SpringContext.getProperty("nhnis.exception."+code)` | `FW9999` 폴백 |
| `SERVICE`/`BIZ` | `MessageCache.getMessage(code, args…)` | **코드 문자열 반환** |

`MessageCache` 상세(적재·설정·갭)는 [§13.1](#131-messagecache)을 본다.

**⚠️ 갭:** 현재 `pdmk-service`의 `application.yml`에 `framework.message.*` 설정이 없다 → `enabled=false` → **캐시가 비어 있는 상태로 기동**한다. 따라서 `TYPE.BIZ`/`SERVICE` 예외의 `stdErrMsgCntn`에 **코드 문자열이 그대로** 실릴 수 있다.

### 10.6 업무 오류와 시스템 오류 구분

| 상황 | 권장 처리 | 현재 샘플 |
| ---- | --------- | --------- |
| 입력 필수값 누락·형식 오류 | `NhBaseException` (`TYPE.COMMON`) | 일부는 Service 내부 분기 |
| 조회 0건이 **정상** | `DTOout` 빈 목록 + `totalCount=0` | 빈 목록·페이징 0 ✅ |
| 삭제 대상 없음 | 정책에 따라 예외 또는 `RSLT_CD` | `RSLT_CD=0001` 등 |
| 권한·인증 실패 | Filter 401 (봉투 없음) | ✅ |
| DB 오류·NPE 등 예상 밖 | `NhExceptionProvider.exceptionBuilder` → `FW9999` | 미래핑 시 기본 오류 |
| 외부 연동 실패 | `NhBaseException` 래핑 권장 | 샘플 없음 |

**판단 기준 한 문장:** 클라이언트가 **"실패 전문"으로 받아야 하면 예외**, **"성공 전문 + 업무 결과 플래그"면 DTOout**.

| 하지 말 것 | 이유 |
| ---------- | ---- |
| Controller에서 오류 DTO를 직접 조립해 반환 | 메시지 사전·스택 수집 누락 |
| 오류 문구를 코드에 하드코딩만 | `exceptionCode.yml`/캐시와 불일치 |
| TCF `BizException` + `result.*`를 commons와 혼용 | 응답 스키마 분기 |
| 예외를 catch 후 로그만 남기고 삼킴 | 실패가 성공 전문으로 나감 |

### 10.7 표준 오류 응답

#### 조립 경로

```text
 NhBaseException
   ├─ stdErrCode / errMsgType / messageValue[]
   └─ 클래스·메서드·파일·라인·스택
        │  errorProcessor
        ▼
 NH_NIS_ERR_DTO
   ├─ stdErrCode          표준 오류 코드
   ├─ stdErrMsgCntn       해석된 메시지
   ├─ addMsgContents      부가 메시지
   ├─ errClassName / errFileName / errMethodName / errLineNo
   ├─ errType             TYPE 값
   └─ stackTrace          상위 15줄
        │  ResponseEntity 500 + beforeBodyWrite
        ▼
 { "hdr_nhnis": {...}, "dto": NH_NIS_ERR_DTO }
```

#### 응답 예

```json
{
  "hdr_nhnis": { "sys_comm": { "std_gbl_id": "…", "rms_svc_c": "mkcoa5530S0" } },
  "dto": {
    "stdErrCode": "FW0001",
    "stdErrMsgCntn": "요청 Body 오류가 발생하였습니다.",
    "errType": "COMMON",
    "errClassName": "…",
    "errMethodName": "…",
    "errLineNo": 0,
    "stackTrace": ["…"]
  }
}
```

#### 오류 응답 형태 요약 (클라이언트 계약)

| 경로 | 활성 조건 | HTTP | 응답 형태 |
| ---- | --------- | ---- | --------- |
| **A. commons 업무 예외** | `legacy-web.enabled=true` | **500** | `{ hdr_nhnis, dto: NH_NIS_ERR_DTO }` |
| **B. Filter 조기 실패** | `filter.enabled=true` | **400 / 401** | 문구만 (봉투 없음) |
| **C. Security 거부** | 앱 `SecurityConfig` | **401** | 봉투 없음 (샘플은 permitAll이라 거의 없음) |
| **D. TCF ETF** ⛔ | `tcf.enabled=true` | — | `StandardResponseDto{result.*}` — **PDMK 미사용** |

> **주의:** 업무 오류가 **HTTP 500**으로 나간다. HTTP 상태만으로 업무 오류와 시스템 장애를 구분할 수 없으므로, 클라이언트는 **응답 봉투의 `dto.stdErrCode`** 를 봐야 한다.

> **개발·검증 체크리스트 (§10)**
>
> - [ ] 공통·FW 코드가 `exceptionCode.yml`에 등록되어 있는가
> - [ ] 업무 코드는 yml / `MessageCache` 중 어느 정책인지 정했는가
> - [ ] 업무 예외를 `NhBaseException` + 적절한 `TYPE`으로 던지는가
> - [ ] `throws` 선언이 있어 checked 예외가 Advice까지 전파되는가
> - [ ] 예상 밖 예외를 `NhExceptionProvider`로 표준화하는가
> - [ ] 클라이언트가 4xx(봉투 없음)와 500(봉투 있음)을 모두 처리하는가
> - [ ] `TYPE.BIZ`/`SERVICE` 응답 문구가 코드 문자열 폴백이 아닌지 확인했는가
> - [ ] TCF `result.*` 스키마를 PDMK 계약으로 문서화하지 않았는가

## 11. 인증·인가와 통신 보안

> **이 장에서 알 수 있는 것**
> - Security 체인이 실제로 무엇을 하고(하지 않고) 있는지
> - local/dev 프로파일에서의 보안 상태 차이
> - JWT 검증이 일어나는 정확한 지점과 그 한계
> - CORS 정책과 UI 릴레이의 관계
> - 시크릿 관리와 외부 입력 검증 경계

### 11.1 SecurityFilterChain

**위치:** `nhnis.mk.config.SecurityConfig` (`pdmk-service`)

| 항목 | 설정 |
| ---- | ---- |
| Session | `STATELESS` |
| CSRF | **disable** (무상태 API 전제) |
| httpBasic / formLogin | disable |
| CORS | `Customizer.withDefaults()` (+ MVC CORS 매핑) |
| authorize | **`anyRequest().permitAll()`** ⚠️ |
| EntryPoint | `HttpStatusEntryPoint(401)` |

```text
 DefaultFilter (fw)          ← 실제 인증 게이트 (⚙️ 비-local JWT)
      │
 SecurityFilterChain (앱)    ← 세션·CSRF·Basic/Form 끄기, permitAll
      │
 DispatcherServlet → Interceptor → Aspect → Controller
```

**함의:** Security 체인만으로는 API가 **열려 있다.** 실인증은 `DefaultFilter`의 JWT 검증에 의존한다.

| 규칙 | 이유 |
| ---- | ---- |
| 앱 `SecurityConfig`만 사용 | fw `commons.configuration.SecurityConfig`는 `commons.security.enabled=true`일 때만 로드 — **동시 활성 금지** |
| TCF `JwtAuthenticationFilter` 미등록 | `DefaultFilter` JWT와 이중 인증 금지 |
| URL·역할 인가가 필요하면 `authorizeHttpRequests` 강화 | permitAll은 샘플 값 |

### 11.2 Local·Dev 보안 상태

| 항목 | `local` | `dev` | 폐쇄망/운영 (권장) |
| ---- | ------- | ----- | ------------------ |
| Filter JWT 검증 | **생략** ⚙️ | **필수** (프로파일이 `local`이 아니므로) | 필수 |
| `hdr_nhnis` 없는 요청 | 합성 헤더 허용 | 400 | 400 |
| Security 인가 | permitAll | permitAll | 강화 필요 ⚠️ |
| `jwt.access-token-expiration` | `180000` ms | `240000` ms | IdP 정책과 일치 |
| DB | H2 mem | (설정에 따름) | Oracle RDW |
| 시크릿 | 커밋된 기본값 (개발 전용) | 동일 ⚠️ | 환경변수 |

**⚠️ 혼동 주의:** `jwt.enabled` 키가 yml에 존재하지만, **commons `DefaultFilter`는 이 키가 아니라 `spring.profiles.active`가 `local`인지로 분기**한다. 따라서 `dev` 샘플에 `jwt.enabled: false`가 있어도 **Filter는 JWT를 요구한다.** 문서·코드 중 한쪽으로 통일이 필요하다 ([§17.5](#175-확인된-제약과-주의사항)).

### 11.3 JWT 검증 경로

```text
 spring.profiles.active
        │
   local │                       그 외 │
        ▼                              ▼
 JWT 검증 생략              Authorization: Bearer <token>
 (Filter 통과)              JwtProvider.validate
                            ├─ 서명·claims(만료 포함) 검증
                            ├─ isAccessToken (type=ACCESS)
                            ├─ getSsoId(subject)
                            │    → request.setAttribute("ssoId", …)
                            └─ 실패 → 401 sendError (봉투 없음)
```

| 항목 | 내용 |
| ---- | ---- |
| 구현 | `nhnis.fw.commons.jwt.JwtProvider` (JJWT, HMAC) |
| 키 | `jwt.secret` (`@Value`), 환경변수 `PDMK_JWT_SECRET`로 덮어쓰기 (≥32바이트) |
| 호출 지점 | `DefaultFilter` **한 곳** |
| 결과 저장 | `request.setAttribute("ssoId", …)` — **SecurityContext에 principal을 심지 않음** |

**⚠️ 한계·갭**

| 항목 | 현황 |
| ---- | ---- |
| 토큰 발급 API | 본 스택에 **없음** (외부 IdP/게이트웨이 전제) |
| UI 릴레이 | `RestClient`가 `Authorization`을 **전달하지 않음** → 비-local에서 ui→service 401 |
| SecurityContext | principal 미설정 → Spring Security 기반 역할 인가 불가 |
| 역할(RBAC) | 미구현 — 필요 시 Service/Interceptor에서 검사 |
| `jwt.enabled` | Filter가 참조하지 않음 (프로파일 분기) |

### 11.4 CORS와 UI Relay

| 경로 | CORS 처리 |
| ---- | --------- |
| 브라우저 → `pdmk-ui`(:8090) → service | UI에 대해 **same-origin**, service 호출은 서버사이드 → **브라우저 CORS 이슈 없음** ✅ |
| 브라우저 → service(:8080) 직호출 | `spring.mvc.cors.allowed-origins`가 **비어 있으면** MVC CORS 미등록 |

| 항목 | 값 |
| ---- | -- |
| 설정 | `spring.mvc.cors.*` → `CorsProperties` → `WebMvcConfig` |
| 샘플 `allowed-origins` | **빈 목록** (자동 CORS 비활성 의도) |
| 매핑 경로 | `/api/**` |
| ⚠️ 주의 | 업무 URL은 `/mkcoa*` 형태이므로 **`/api/**` 매핑에 걸리지 않는다.** SPA가 service를 직접 호출하려면 별도 정책이 필요하다 |

### 11.5 민감정보와 Secret

| 비밀/설정 | 용도 | 운영 권장 |
| --------- | ---- | --------- |
| `jwt.secret` / `PDMK_JWT_SECRET` | HMAC 키 (≥32바이트) | 환경변수·시크릿 저장소. **커밋된 기본값 사용 금지** |
| `PDMK_RDW_PASSWORD` | Oracle DS 비밀번호 | 환경변수 |
| `jwt.access-token-expiration` | 토큰 수명(ms) | 발급기(IdP)와 일치 |
| DB 계정 | RDW 접속 | 최소 권한. ImageLog·업무 테이블 GRANT 분리 검토 |

| 규칙 | 설명 |
| ---- | ---- |
| 평문 시크릿을 운영 yml에 커밋하지 않는다 | 로컬 기본값은 **개발 전용** |
| 비밀번호·토큰을 로그에 남기지 않는다 | MDC에는 GUID·사용자ID만 |
| HTTPS/TLS | 애플리케이션 밖(WAS·LB)에서 종단 처리 |

### 11.6 외부 입력 검증 경계

| 위협 | 현재 완화 | 잔여 위험 |
| ---- | --------- | --------- |
| SQL Injection | MyBatis `#{…}` 바인딩 ✅ | `MessageLoader`의 테이블명은 **설정값 연결** → 설정 신뢰 전제 |
| 대량 Body | `DefaultFilter`가 전체 Body를 **힙에 버퍼** | 크기 상한 정책 없음 → WAS/앱 정책 필요 ([§13.2](#132-request-body-캐시)) |
| 세션 고정/하이재킹 | `STATELESS`, 서버 세션 미사용 ✅ | — |
| CSRF | API + JWT(+릴레이) 전제로 off | 쿠키 세션 도입 시 재검토 |
| 로그 유출 | Filter finally에서 MDC 정리 ✅ | 개인정보 마스킹 정책은 팀 표준 |
| 감사 데이터 삭제 | `mkcoa8888D0` | **별도 관리자 인가 없음** ⚠️ — 네트워크·JWT에만 의존 |

**운영 권장**

| 갭 | 권장 |
| -- | ---- |
| Security `permitAll` | URL·메서드 단위 인가 또는 APIGW 앞단 인증 |
| UI 릴레이 JWT 미전달 | 헤더 전파 구현, 또는 비-local에서 UI 미사용 |
| `jwt.enabled` vs 프로파일 분기 | 코드·문서 통일 |
| ImageLog 삭제 API | 네트워크·인가로 노출 범위 제한 |

> **개발·검증 체크리스트 (§11)**
>
> - [ ] 운영 프로파일이 `local`이 아닌가 (JWT 게이트 동작)
> - [ ] `PDMK_JWT_SECRET`을 환경변수로 주입하고 기본값을 교체했는가
> - [ ] TCF JWT 필터와 `DefaultFilter`가 동시 활성이 아닌가
> - [ ] fw commons `SecurityConfig`가 비활성인가 (앱만 사용)
> - [ ] 직호출이 필요하면 CORS origins가 `/mkcoa*`까지 커버하는가
> - [ ] ui→service 비-local 호출 시 `Authorization` 전달 경로가 있는가
> - [ ] DS 비밀번호·시크릿이 저장소·로그에 평문으로 없는가
> - [ ] ImageLog 조회·삭제 API의 노출 범위를 제한했는가
> - [ ] 모든 SQL이 `#{}` 바인딩인가

## 12. 로그·추적·성능

> **이 장에서 알 수 있는 것**
> - 네 개의 로그 채널과 각각의 저장소·목적
> - 거래 단계 로그의 기호 체계와 읽는 법
> - GUID/MDC로 한 거래를 추적하는 방법
> - ImageLog 컬럼과 기록 시점
> - Timeout 계층과 지연 거래 측정의 현재 한계
> - 장애 추적 표준 절차

### 12.1 로그 체계 개요

```text
 Browser ──(선택)──► pdmk-ui  RelayResult(status, elapsedMs)   ← ④ UI 중계
                        │
                        ▼
             pdmk-service + pdmk-fw
 ┌───────────────────────────────────────────────────────────┐
 │ ① MDC / ThreadContext                                     │
 │    guid · ip · userId · serviceId   (DefaultFilter)        │
 │    sqlId                            (MybatisLogInterceptor)│
 │    errCode                          (NhExceptionProvider)  │
 ├───────────────────────────────────────────────────────────┤
 │ ② 애플리케이션 거래 로그 (Slf4j + PdmkTxLog 메시지)          │
 │    Interceptor → Aspect → Controller → Service             │
 ├───────────────────────────────────────────────────────────┤
 │ ③ 이미지로그 DB  TB_FW_IMAGE_LOG (ImageLogHandler)          │
 │    PRE INSERT → POST UPDATE → EX UPDATE                    │
 ├───────────────────────────────────────────────────────────┤
 │ ④ SQL 로그  MybatisLogInterceptor (debug + MDC sqlId)       │
 └───────────────────────────────────────────────────────────┘
```

| 채널 | 모듈 | 저장소 | 목적 |
| ---- | ---- | ------ | ---- |
| 거래 타임라인 | fw + service | 앱 로그 파일 | 선후처리·Controller/Service 추적 |
| MDC | fw (+ service SQL) | Log4j2 ThreadContext | GUID·서비스·SQL 상관관계 |
| 이미지로그 | fw | `TB_FW_IMAGE_LOG` | 전문 헤더 감사·예외 흔적 |
| SQL | service | SQL 전용 로거(debug) | 쿼리 ID·파라미터·소요(ms) |
| UI 릴레이 | ui | `RelayResult` | HTTP 상태·중계 소요시간 |

로깅 구현은 **Log4j2**다(`spring-boot-starter-logging` exclude, `classpath:log4j2.xml`).

### 12.2 거래 단계 로그

정상 거래 시 순서:

```text
[ServicePreventionInterceptor] SystemPreProcessor Start!      ← fw
[ServicePreventionInterceptor] GUID: <std_gbl_id>
▶▶▶▶▶▶ mpco 업무 공통 선처리 ▶▶▶▶▶▶                          ← service Aspect
[bizPrePostAspect().before()] Argument: BRC : …
▷▷▷▷▷▷▷▷ mkcoa5530 Controller Start!                        ← service
▶▶▶▶▶▶▶▶ mkcoa5530S0 Service Start!
▶▶▶▶▶▶▶▶ mkcoa5530S0 Service End! - Total: n
▷▷▷▷▷▷▷▷ mkcoa5530 Controller End!…
▶▶▶▶▶▶ mpco 업무 공통 후처리 ▶▶▶▶▶▶
[bizPrePostAspect().after()] Argument: BRC : …
[ServicePreventionInterceptor] SystemPostProcessor            ← fw
```

예외 시에는 `[ServicePreventionInterceptor] SystemErrorProcessor` + ImageLog EX가 추가된다.

| 기호/접두 | 출처 | `PdmkTxLog` API |
| --------- | ---- | --------------- |
| `[ServicePreventionInterceptor]` | fw Interceptor | `systemPreProcessorStart`, `systemGuid`, `systemPostProcessor`, `systemErrorProcessor` |
| `▶▶▶▶▶▶` (6개) | service Aspect | `bizPreProcess` / `bizPostProcess`, `bizArgument*` |
| `▷▷▷▷▷▷▷▷` (8개) | Controller | `controllerStart` / `controllerEnd` |
| `▶▶▶▶▶▶▶▶` (8개) | Service | `serviceStart` / `serviceEnd` |

**핵심 규칙:** 메시지 **조립만** `PdmkTxLog`에 두고, `log.info(...)` **호출은 각 계층에서** 한다. 유틸 안에서 Logger를 호출하면 Log4j2 `%C.%M` 패턴이 유틸 위치로 고정되어 운영 로그의 위치 정보가 무의미해진다.

| 계층 | 모듈 | 남기는 로그 |
| ---- | ---- | ----------- |
| `DefaultFilter` | fw | MDC 시드, 오류 시 Filter error 로그 |
| `ServicePreventionInterceptor` | fw | 시스템 선/후/에러 + ImageLog PRE/POST/EX |
| `BizPrePostAspect` | service | 업무 선/후 + BRC 인자 |
| Controller / Service | service | Start/End·건수 |
| `MybatisLogInterceptor` | service | SQL ID·param·elapsed(ms) @ debug |
| `TransactionRelayService` | ui | `RelayResult`(status, elapsedMs) |

### 12.3 요청·응답 전문 로그

**✅ AS-IS:** commons 경로는 **요청/응답 전문 본문(JSON) 전체를 로그 파일에 남기지 않는다.** 전문 관련 흔적은 다음 두 가지다.

| 대상 | 남는 곳 | 범위 |
| ---- | ------- | ---- |
| 전문 **헤더** 핵심 필드 | `TB_FW_IMAGE_LOG` (DB) | GUID·서비스ID·화면ID·조작자·IP·시각 |
| 전문 **본문** | ❌ 미기록 | — |
| 업무 인자 일부(BRC) | 앱 로그 (`BizPrePostAspect`) | `getTrtBrc`/`getBrc`/`getBRC`/`getL5104` 반사 결과만 |
| SQL 파라미터 | 앱 로그 debug (`MybatisLogInterceptor`) | Map 파라미터 문자열 |

> 출처 문서에 전문 본문 로깅 기능에 대한 상세 없음 — **후속 보강**. 필요 시 마스킹 정책과 함께 설계해야 한다(개인정보·비밀번호). 관련 경계는 [§11.6](#116-외부-입력-검증-경계).

### 12.4 GUID·Trace ID·MDC

| 키 | 설정 주체 | 값 |
| -- | --------- | -- |
| `guid` | `DefaultFilter` (없으면 Interceptor가 UUID 채번) | `sys_comm.std_gbl_id` |
| `ip` | `DefaultFilter` | 단말 IP (`X-Forwarded-For` 우선) |
| `userId` | `DefaultFilter` | 조작자 사번 (`optr_eno`, 없으면 `LOCAL`) |
| `serviceId` | `DefaultFilter` | URI 마지막 세그먼트 또는 `rms_svc_c` |
| `sqlId` | `MybatisLogInterceptor` | MyBatis statement ID |
| `errCode` | `NhExceptionProvider` (사용 시) | 표준 오류 코드 |

**추적 방법:** 로그에서 `guid` 하나로 Filter 진입부터 Filter finally까지 전 구간이 연결되고, 같은 `guid`로 `TB_FW_IMAGE_LOG` 행을 조회하면 요청/응답 시각과 예외 정보를 얻는다.

**⛔ 별도 `traceId`는 없다.** `TcfTraceFilter`의 traceId는 TCF 경로 전용이므로 현재 생성되지 않는다. 분산 추적(W3C traceparent 등)은 미구성이다.

`DefaultFilter` finally에서 `ThreadContext.clearAll()`을 반드시 유지한다 ([§4.7](#47-context-및-threadlocal-정리)).

### 12.5 ImageLog

**주체:** `nhnis.fw.commons.imagelog.ImageLogHandler` (JdbcTemplate)

| 컬럼 | 타입(H2) | 매핑 소스 |
| ---- | -------- | --------- |
| `GUID` | VARCHAR(64) **PK** | `sys_comm.std_gbl_id` |
| `SERVICE_ID` | VARCHAR(50) | `rms_svc_c` |
| `SCREEN_ID` | VARCHAR(50) | `scid` |
| `OPTR_ENO` | VARCHAR(20) | `optr_eno` |
| `CLIENT_IP` | VARCHAR(50) | `tr_trm_ipadr` |
| `REQUEST_TIME` | VARCHAR(17) | `tr_dtm` / 서버 시각 |
| `RESPONSE_TIME` | VARCHAR(17) | 후처리 시각 |
| `EXCEPTION_TYPE` | VARCHAR(200) | 예외 클래스명 |
| `EXCEPTION_CODE` | VARCHAR(50) | `NhBaseException` 코드 |
| `EXCEPTION_MSG` | VARCHAR(1000) | 메시지 (1000자 truncate) |

| 시점 | 메서드 | SQL |
| ---- | ------ | --- |
| PRE | `preImagelog` (`preHandle`) | `INSERT` |
| POST | `postImagelog` (`postHandle`) | `UPDATE RESPONSE_TIME` |
| EX | `exceptionImagelog` (`afterCompletion`) | `UPDATE` 예외 컬럼 (행 없으면 INSERT) |
| 조회 | `mkcoa8888S0` | SELECT + count (페이징) |
| 삭제 | `mkcoa8888D0` | `DELETE … WHERE GUID IN (…)` |

**경계:** ImageLog JDBC 실패는 **업무 예외로 전파되지 않는다**(Handler가 삼킴). 업무 `@Transactional`과 커밋 단위가 분리된다 ([§9.5](#95-imagelog와-업무-tx의-관계)).

**금지:** ImageLog 실패로 업무 롤백을 유발하는 구현, 업무 코드에서 ImageLog를 직접 기록하는 구현.

### 12.6 MyBatis·SQL 로그

`MybatisLogInterceptor` (`@Intercepts` Executor `query`/`update`):

```java
long startedAt = System.currentTimeMillis();
try { return invocation.proceed(); }
finally {
    log.debug("{} | param={} | {}ms", sqlId, parameter, System.currentTimeMillis() - startedAt);
}
```

| 기록 항목 | 비고 |
| --------- | ---- |
| MyBatis SQL ID | MDC `sqlId`에도 설정 |
| 파라미터 | Map 문자열 |
| 실행 시간(ms) | debug 레벨 |
| GUID·사용자·서비스 ID | MDC로 자동 결합 |

출력 예:

```text
mkcoa5530S0_S0_count | param={…} | 12ms
mkcoa5530S0_S0       | param={…} | 85ms
```

**⚠️ 한계:** **느린 SQL에 대한 WARN 임계치가 없다.** SQL이 5초 걸려도 debug 실행시간만 남고 경고로 승격되지 않는다.

### 12.7 Timeout 설정

```text
 Browser  (브라우저·네트워크 — 스택 밖)
   ▼
 pdmk-ui       pdmk.ui.timeout-ms = 10000   ⚠️ RestClient 미연결 (값만 존재)
   ▼
 pdmk-service (+ pdmk-fw)
   ├─ jwt.access-token-expiration (ms)   [토큰 수명]
   ├─ @Transactional(timeout = 초)       [DB TX · 권장, 현재 미선언]
   ├─ slow-transaction-ms (WARN)         [성능 경고 ≠ rollback, TCF 계열]
   └─ sys_comm.ttl_ug_ync                [전문 플래그 ≠ Spring TX]
   ▼
 pdmk-fw 연동 (⚙️ 조건부)
   ├─ apigw.connect/response-timeout        (초, 기본 30)
   └─ storage.fos.connect/response-timeout  (초, 기본 -1 무제한)
   ▼
 RDW / 외부 시스템
```

| 층 | 모듈 | 키 | 단위 | 초과 시 | 현재 |
| -- | ---- | -- | ---- | ------- | ---- |
| UI 릴레이 HTTP | ui | `pdmk.ui.timeout-ms` | ms | 클라이언트 타임아웃 | ⚠️ **RestClient 미연결** |
| DB 트랜잭션 | service | `@Transactional(timeout=n)` | **초** | rollback + `TransactionTimedOutException` | ⚠️ `mkcoa*` **미선언** |
| JWT 수명 | service + fw | `jwt.access-token-expiration` | ms | 토큰 무효 → Filter 401 | local 180000 / dev 240000 |
| 전문 TTL 플래그 | fw 헤더 | `sys_comm.ttl_ug_ync` | int | **자동 timeout 없음** | 샘플 `0` |
| APIGW | fw | `apigw.*-timeout` | 초 | 연동 실패 | 기본 30 ⚙️ |
| FOS | fw | `storage.fos.*-timeout` | 초 (`-1`=무제한) | 연동 실패 | 기본 -1 ⚙️ |
| 지연 WARN | (TCF 계열) | `slow-transaction-ms` | ms | 로그만 | ⛔ commons 미적용 |

#### 권장 관계

```text
 UI HTTP timeout-ms
        ≥
 service @Transactional(timeout) × 1000  +  직렬화·필터 여유
        ≥
 개별 SQL / 외부 APIGW·FOS timeout
```

| 관계 | 권장 |
| ---- | ---- |
| UI vs DB TX | UI가 먼저 끊기면 사용자만 실패로 보고 DB TX는 계속될 수 있음 → UI ≥ TX + 여유, 또는 TX를 더 짧게 |
| WARN vs TX | `slow-transaction-ms`(예 3초)를 TX timeout(예 4초)보다 짧게 → 먼저 WARN, 이후 rollback |
| TTL 플래그 | 문서·게이트웨이 정책용. `@Transactional(timeout)`을 대신하지 않음 |

`DefaultFilter`·Interceptor 자체에는 **"요청 절대시간 강제 kill" 타임아웃이 없다.**

### 12.8 지연 거래와 성능 측정

#### 측정 지점 (설계 기준)

| 구간 | 측정 위치 | 포함 범위 |
| ---- | --------- | --------- |
| HTTP 총 시간 | ⛔ `TcfTraceFilter` (TCF 전용) | 보안 필터 + JSON 변환 + STF + Controller + Service + DB + ETF + 응답 |
| 업무 처리 시간 | ⛔ `TcfContext.elapsedMs()` (STF~ETF) | 순수 업무 처리 |
| SQL 실행 시간 | ✅ `MybatisLogInterceptor` | 개별 statement |

두 구간의 차이(예: total 3300ms − business 3100ms = 200ms)가 크면 병목이 업무가 아니라 **직렬화·필터**에 있다는 진단이 가능하다.

#### ✅ commons(현행) 경로에서 실제로 가능한 것

| 항목 | 가능 여부 |
| ---- | --------- |
| SQL별 실행 시간 | ✅ debug 로그 |
| 거래 단계 순서·GUID 상관 | ✅ `PdmkTxLog` + MDC |
| 요청/응답 시각 | ✅ `TB_FW_IMAGE_LOG`의 `REQUEST_TIME`/`RESPONSE_TIME` (초 단위 문자열) |
| HTTP 총 소요시간 자동 측정 | ❌ (UI 경유 시 `RelayResult.elapsedMs`로 간접 확인) |
| 지연 거래 WARN 자동 승격 | ❌ |
| 느린 SQL WARN | ❌ |
| 평균·최대·백분위 통계 / 대시보드 / 알림 | ❌ |
| 트랜잭션 강제 timeout | ❌ (`@Transactional(timeout)` 선언 시에만) |

**현재 수준 한 문장:** "느리면 로그와 ImageLog 시각으로 GUID·serviceId를 따라가 추적하는 단계"이며, 자동 집계·알림을 수행하는 APM 구조는 아니다.

**⚠️ UI `elapsedMs` 해석 주의:** 네트워크·릴레이 시간이 포함되므로 service 성능을 단정하는 근거로 쓰지 않는다.

### 12.9 장애 추적 절차

```text

    │

    ├─ 401? ──────────────► Filter JWT · 프로파일 · Bearer 전달          (§11.2·11.3)
```

#### 표준 절차

| 순 | 행동 | 확인 대상 |
| -- | ---- | --------- |
| 1 | 실패 응답 형태 확인 | HTTP 4xx(봉투 없음) vs 500(`dto.stdErrCode`) → [§10.7](#107-표준-오류-응답) |
| 2 | GUID 확보 | 응답 `hdr_nhnis.sys_comm.std_gbl_id` 또는 로그 MDC `guid` |
| 3 | 앱 로그에서 GUID 필터 | 어느 단계까지 진행했는지 (Filter/Interceptor/Aspect/Controller/Service) |
| 4 | `TB_FW_IMAGE_LOG` 조회 | `mkcoa8888S0` 또는 직접 SELECT — 요청/응답 시각, 예외 타입·코드·메시지 |
| 5 | SQL 로그 확인(debug) | `sqlId` · 파라미터 · 소요시간 |
| 6 | 설정 대조 | 프로파일·스위치 3종(`tcf`/`filter`/`legacy-web`)·DS → [부록 C](#부록-c-설정-키-인덱스) |
| 7 | 재현·격리 | service 직호출(UI 배제) vs UI 경유 비교 |

| 증상 | 1차 확인 |
| ---- | -------- |
| UI만 실패, service 직호출은 성공 | `target-base-url`, 릴레이 로그, (직호출 시) CORS |
| UI 타임아웃이 동작하지 않음 | `timeout-ms` RestClient 미연결 갭 |
| 401, 문구만 오고 봉투 없음 | 프로파일, Bearer 유무, UI 릴레이 미전달 |
| 전문 바인딩 실패 | 루트 구조, fw `RequestBody` import, Content-Type |
| 오류 메시지가 코드 문자열 | `framework.message` 미설정 → 캐시 폴백 ([§13.1](#131-messagecache)) |
| FW Bean 없음 | `scanBasePackages=nhnis`, `:pdmk-fw` include |
| GUID가 다른 거래와 섞임 | Filter finally MDC clear 누락 |

> **개발·검증 체크리스트 (§12)**
>
> - [ ] 시스템·업무 선후처리 로그가 GUID와 함께 남는가
> - [ ] Controller/Service Start·End 패턴이 샘플과 일치하는가

> - [ ] UI `elapsedMs`만으로 service 성능을 단정하지 않는가
> - [ ] 필요한 timeout이 확정값으로 선언되어 있는가

## 13. 캐시와 외부 연동

> **이 장에서 알 수 있는 것**
> - PDMK가 쓰는 "캐시"의 정확한 범위 (분산 캐시는 없다)
> - `MessageCache` 적재·조회·갱신 방식과 현재 갭
> - 요청 Body 캐시의 수명과 메모리 특성
> - API Gateway·FOS 연동 구성과 타임아웃
> - HTTP Client / Connector Bean의 위치

### 13.1 MessageCache

**PDMK는 분산 캐시(Redis 등)·Spring Cache(`@Cacheable`)·MyBatis 2차 캐시를 사용하지 않는다.** 캐시에 해당하는 것은 **프로세스 내 메모리 Map**, **요청 단위 Body 버퍼**, **기동 시 적재 사전**뿐이다.

| 모듈 | 캐시성 저장소 | 수명 |
| ---- | ------------- | ---- |
| `pdmk-fw` | `MessageCache` | JVM 기동 ~ 종료 |
| `pdmk-fw` | `CachedBodyHttpServletRequest` | **요청 1회** |
| `pdmk-fw` / `pdmk-service` | `exceptionCode.yml` → Spring Environment | 기동 시 로드 |
| `pdmk-fw` | `ServiceContextHolder` · MDC | **요청 1회** (컨텍스트이지 캐시 아님) |
| `pdmk-service` | (없음) | — |
| `pdmk-ui` | `TransactionCatalog` 내부 Map | JVM 기동 ~ 종료 |

#### `MessageCache` 구성

| 항목 | 내용 |
| ---- | ---- |
| 클래스 | `nhnis.fw.commons.message.MessageCache` — `ConcurrentHashMap<String,String>` |
| 로더 | `MessageLoader` (`@PostConstruct`) |
| 설정 | `framework.message.*` (`MessageProperties`) |
| 키 / 값 | `CRM_MSG_C` / `MSG_CNTN` |
| 조회 API | `get`, `getMessage(code, args…)` — `MessageFormat` 적용, **미존재 시 코드 문자열 반환** |
| 소비처 | `ResponseBodyArgumentResolver.errorProcessor` (`TYPE.BIZ`/`SERVICE`) |

```text
 framework.message.enabled=true
        ▼
 MessageLoader.init()
   clear → SELECT CRM_MSG_C, MSG_CNTN FROM {tableName[]} (복수면 UNION ALL)
        ▼
 MessageCache.put(code, pattern)
        ▼ (거래 중 예외)
 TYPE.BIZ/SERVICE → messageCache.getMessage(code, args)
```

| 키 | 기본 | 의미 |
| -- | ---- | ---- |
| `framework.message.enabled` | `false` | `true`일 때만 DB 적재. 꺼져 있으면 Loader는 no-op |
| `framework.message.dataSource` | (필수 if on) | Spring `DataSource` Bean 이름 |
| `framework.message.tableName` | 배열 | 메시지 테이블명(들) — 복수면 `UNION ALL` |

**⚠️ 갭 3건**

| 항목 | 현황 | 권장 |
| ---- | ---- | ---- |
| `pdmk-service` yml에 `framework.message` 없음 | `enabled=false` → **캐시 비어 있음** → BIZ/SERVICE 예외에 **코드 문자열 폴백** | 운영 DS·테이블명으로 활성화 |
| 핫리로드 API 없음 | 변경 반영에 **재기동** 필요 | 관리 API 또는 재기동 절차 문서화 |
| 멀티 인스턴스 | 인스턴스별 독립 Map | DB 원본 일치 + 롤링 재기동 절차 |

메시지 테이블은 **로컬 H2 `schema.sql`에 포함되어 있지 않다.**

#### 기동 시 사전·카탈로그 (캐시성)

| 저장소 | 모듈 | 적재 | 갱신 |
| ------ | ---- | ---- | ---- |
| `exceptionCode.yml` → `nhnis.exception.*` | fw + service classpath | Boot `spring.config.import` | **재기동** |
| `MessageCache` | fw | `MessageLoader` `@PostConstruct` | 재기동 |
| `TransactionCatalog` | ui | `@PostConstruct` 샘플 JSON 등록 | ui 재기동 |

#### 의도적으로 캐시하지 않는 것

| 대상 | 이유 |
| ---- | ---- |
| 업무 조회 결과(DAO/Map) | 정합성·동시성. MyBatis 2차 캐시 미설정 |
| JWT / 세션 | 요청마다 검증(또는 local 생략). 토큰 캐시 없음 |
| ImageLog / RDW 행 | 감사·원장성 |
| Spring `@Cacheable` | 스택에 의존성·어노테이션 미사용 |

### 13.2 Request Body 캐시

Servlet `InputStream`은 한 번만 읽을 수 있다. Filter가 JSON을 파싱한 뒤 Resolver·Controller도 Body가 필요하므로 **요청 스코프 바이트 버퍼**를 둔다.

```text
 HTTP Request Body (JSON)
        │ DefaultFilter readAllBytes()
        ▼
 CachedBodyHttpServletRequest (요청 1회 힙 버퍼)
        ├─ Filter JSON 파싱
        └─ RequestBodyArgumentResolver / Controller 재읽기 (동일 바이트)
 ※ multipart 는 래핑하지 않음
```

| 항목 | 내용 |
| ---- | ---- |
| 클래스 | `nhnis.fw.commons.filter.CachedBodyHttpServletRequest` |
| 적재 시점 | `DefaultFilter`가 일반 JSON 요청을 래핑할 때 |
| 조회 | `getInputStream()` / `getReader()` → 동일 바이트 재생 |
| 제외 | `multipart/*` |
| 공유 범위 | 해당 HTTP 요청 스레드만 (분산·공유 없음) |

**⚠️ 대용량 Body는 힙에 전체가 올라간다.** 업로드·대형 전문은 multipart 경로를 쓰거나 크기 상한 정책을 별도로 둔다. Controller에서 Body를 전역 저장소에 별도로 보관하지 않는다.

### 13.3 API Gateway 연동

| 항목 | 내용 |
| ---- | ---- |
| 패키지 | `nhnis.fw.commons.apigw` — `ApiGatewayHandler` + DTO |
| 기술 | WebClient (Reactor Netty `ClientHttpConnector`) |
| 설정 | `apigw.connect-timeout` / `apigw.response-timeout` (초, 기본 **30**) |
| 활성 | ⚙️ 연동 설정 시 |
| PDMK 샘플 | 사용 사례 없음 |

> 출처 문서에 요청 스펙·인증 방식·재시도 정책 등 상세 없음 — **후속 보강**. 도입 시 [§12.7](#127-timeout-설정)의 타임아웃 계층 관계와 [§10.6](#106-업무-오류와-시스템-오류-구분)의 오류 래핑 정책을 함께 정한다.

### 13.4 FOS 객체 저장소

| 항목 | 내용 |
| ---- | ---- |
| 패키지 | `nhnis.fw.commons.fos` — `ObjectStorageHandler`, DTO, enums |
| 설정 | `storage.fos.*` (`connect-timeout` / `response-timeout`, 초, 기본 **-1** = 무제한) |
| 설정 조회 | `SpringContext.getProperty` |
| 활성 | ⚙️ 연동 설정 시 |
| PDMK 샘플 | 사용 사례 없음 |

**⚠️ 기본값 `-1`(무제한)은 위험하다.** 연동을 활성화하면 반드시 유한 값으로 설정한다.

> 출처 문서에 버킷 구조·객체 키 규칙·권한 모델 상세 없음 — **후속 보강**.

### 13.5 HTTP Client와 Connector

| 용도 | 구현 | 위치 | 비고 |
| ---- | ---- | ---- | ---- |
| UI → service 릴레이 | `RestClient` | `pdmk-ui` `TransactionRelayService` | ⚠️ timeout 미연결, `Authorization` 미전달 |
| APIGW 연동 | WebClient + `ClientHttpConnector` | `pdmk-fw` `ClientHttpConnectorConfiguration` | ⚙️ `legacy-web` 조건, `@ConditionalOnMissingBean` |
| FOS 연동 | HTTP 클라이언트 | `pdmk-fw` `fos` | ⚙️ |
| (의존) | httpclient5, gson | `pdmk-fw` `api` 의존 | 소비 앱에 전파 |

**중요:** `FilterConfiguration`이 `ClientHttpConnector` Bean을 **생성자 주입**받는다. 따라서 이 Bean이 없으면 `DefaultFilter` 등록이 실패한다. `legacy-web.enabled=true`로 `ClientHttpConnectorConfiguration`이 활성인지 확인해야 한다.

Netty native 의존(macos/epoll/kqueue)은 빌드에서 **exclude**되어 있다 ([§15.3](#153-모듈별-의존성)).

### 13.6 연결·응답 Timeout

| 연동 | 키 | 단위 | 기본 | 비고 |
| ---- | -- | ---- | ---- | ---- |
| APIGW | `apigw.connect-timeout` | 초 | 30 | |
| APIGW | `apigw.response-timeout` | 초 | 30 | |
| FOS | `storage.fos.connect-timeout` | 초 | **-1** | 무제한 ⚠️ |
| FOS | `storage.fos.response-timeout` | 초 | **-1** | 무제한 ⚠️ |
| UI 릴레이 | `pdmk.ui.timeout-ms` | ms | 10000 | ⚠️ RestClient 미연결 |

전체 타임아웃 계층·권장 관계는 [§12.7](#127-timeout-설정)을 본다.

**설계 규칙:** 외부 연동 timeout은 업무 `@Transactional(timeout)`보다 **짧거나**, 연동 실패 시 업무 롤백 정책이 명시되어 있어야 한다.

> **개발·검증 체크리스트 (§13)**
>
> - [ ] 업무 메시지를 DB로 쓸지 yml로 쓸지 정책을 정했는가
> - [ ] `framework.message.enabled`·`dataSource`·`tableName`이 정책과 일치하는가
> - [ ] BIZ/SERVICE 예외 문구가 코드 문자열 폴백이 아닌지 확인했는가
> - [ ] 대용량 Body에 대한 크기 상한 정책이 있는가
> - [ ] Controller에서 Body를 전역 저장소에 보관하지 않는가
> - [ ] `ClientHttpConnector` Bean이 존재하는가 (Filter 등록 의존)
> - [ ] APIGW/FOS timeout을 유한 값으로 설정했는가 (특히 FOS 기본 -1)
> - [ ] 업무 DAO에 MyBatis cache / `@Cacheable`을 임의 추가하지 않았는가
> - [ ] UI `TransactionCatalog` 변경 후 ui를 재기동했는가

| ---- | ---- | ---- | -------------- |
| `pdmk-service` | `nhnis.mk.PdmkApplication` | `scanBasePackages = "nhnis"` | `@ConfigurationPropertiesScan("nhnis")` |
| `pdmk-fw` | 없음 (`java-library`) | 소비 앱 스캔에 편입 | — |
| `pdmk-ui` | `nhnis.mk.ui.PdmkUiApplication` | 기본(앱 패키지 하위) | `@ConfigurationPropertiesScan` |

```text
 PdmkApplication  scanBasePackages = "nhnis"
      ├─ nhnis.mk.*    ← 업무·config·Aspect
      └─ nhnis.fw.*    ← commons Filter/Interceptor/JWT/Resolver
            └─ nhnis.fw.tcf.*  ← @ConditionalOnProperty로 대부분 미생성 ⛔
```

**⚠️ `scanBasePackages`를 `nhnis.mk`로 축소하면 fw Bean이 전부 누락된다.** Filter·Interceptor·Resolver가 사라져 전문 바인딩 자체가 실패한다.

WAS 배포 시에는 `ServletInitializer`(`SpringBootServletInitializer`)가 동일 `PdmkApplication`을 기동한다 ([§15.6](#156-was-배포)).

### 14.3 Profile 구조

| 프로파일 | 활성화 | 효과 |
| -------- | ------ | ---- |
| `local` | `spring.profiles.active: local` (기본) | H2 + `sql.init`, **Filter JWT 생략**, 헤더 합성 허용, `jwt.access-token-expiration=180000` |
| `dev` | `--spring.profiles.active=dev` | `jwt.access-token-expiration=240000`. **Filter는 JWT 요구**(프로파일이 `local`이 아니므로) |
| (팀 추가) | 환경별 | Oracle DS·시크릿·CORS origins 명시 |

`application.yml`은 공통 블록 + `--- on-profile: local` / `--- on-profile: dev` 구조다.

**⚠️ 반복 경고:** `jwt.enabled` 키와 Filter의 **프로파일명 `local` 분기**는 별개다 ([§11.2](#112-localdev-보안-상태)).

### 14.4 설정 파일 우선순위

```text
 환경변수 / 시스템 프로퍼티            ← 최상위 (시크릿)
      │
 spring.profiles.active = local | dev | …
      │
 application.yml
   ├─ 공통 블록 (profiles · datasource · nhnis.fw · sql.init …)
   ├─ --- on-profile: local   → jwt.*
   └─ --- on-profile: dev     → jwt.*
      │
 spring.config.import
   └─ classpath:exceptionCode.yml   → nhnis.exception.*
      │
 (참고) pdmk-fw application-fw-defaults.yml
   └─ 라이브러리 샘플 — 앱 yml이 덮어씀. 자동 import 아님
```

| 소스 | 모듈 | 역할 |
| ---- | ---- | ---- |
| `pdmk-service/src/main/resources/application.yml` | service | **런타임 정본** |
| `exceptionCode.yml` | service(+fw classpath) | 오류 메시지 사전 import |
| `log4j2.xml` | service | Log4j2 설정 |
| `db/h2/schema.sql`, `data.sql` | service | ⚙️ local `sql.init` |
| `application-fw-defaults.yml` | fw | 개발 참고용 기본값 샘플 (자동 적용 아님) |
| `pdmk-ui/src/main/resources/application.yml` | ui | `server.port`, `pdmk.ui.*` (프로파일 분할 없음) |

**설정 정본은 앱(service/ui) yml이다.** fw defaults만으로 운영하지 않는다.

### 14.6 Local과 배포환경 차이

| 항목 | `local` | 폐쇄망 / WAS |
| ---- | ------- | ------------ |

| 메시지 캐시 | `framework.message.enabled=false` | 정책에 따라 DB 적재 |

### 15.1 독립 Gradle 프로젝트 구조

```text
 nsight-tcf-framework/
 ├─ pdmk-fw/          ← 단독 Gradle 루트 (java-library)
 │    settings.gradle   rootProject.name = pdmk-fw
 │    build.gradle · gradlew.bat · gradle/wrapper (8.10.1)
 │
 ├─ pdmk-service/     ← 단독 Gradle 루트 + fw composite
 │    settings.gradle   include ':pdmk-fw'  (projectDir = ../pdmk-fw)
 │    build.gradle      implementation project(':pdmk-fw')
 │    gradle.properties (UTF-8 JVM args)
 │    script/build.bat · RUN.bat · script/run.bat
 │
 └─ pdmk-ui/          ← 단독 Gradle 루트 (Boot JAR, fw 미포함)
      settings.gradle · build.gradle · script/*.bat
```

| 관계 | 방식 |
| ---- | ---- |
| service → fw | `settings.gradle` include + `projectDir = ../pdmk-fw` + `implementation project(':pdmk-fw')` |
| ui → service/fw | **Gradle 의존 없음** (HTTP만) |
| 모노레포 단일 root | **없음** — 모듈마다 자체 `settings.gradle`과 Wrapper |

`pdmk-fw`만 단독 빌드할 수 있고, `pdmk-service` 빌드 시에는 fw가 **같은 빌드에 포함**된다.

### 15.3 모듈별 의존성

#### `pdmk-fw` (`api`로 소비자에 전파)

- Spring Boot Web / Security / AOP / Autoconfigure / WebFlux
- MyBatis starter, Log4j2 + log4jdbc
- JWT(jjwt), commons-lang3, httpclient5, gson
- `fileTree(libs)` 사내 JAR (있는 경우)
- `spring-boot-starter-logging` **exclude** → Log4j2
- Netty native (macos / epoll / kqueue) **exclude**

#### `pdmk-service`

- `implementation project(':pdmk-fw')` — fw의 `api` 의존을 transitive로 흡수
- Lombok (`compileOnly` + annotationProcessor)
- ⚙️ 로컬 `runtimeOnly` H2 / 폐쇄망 `ojdbc`·`orai18n` (주석 전환)
- `providedRuntime` Tomcat (WAR 시 WAS 제공)
- `fileTree(libs)`, 동일 logging·netty exclude

#### `pdmk-ui`

- `spring-boot-starter-web` + test **만** (경량)
- fw / MyBatis / Security **미포함**

#### 저장소 전환

| 환경 | pluginManagement | repositories |
| ---- | ---------------- | ------------ |
| 로컬 | `gradlePluginPortal()` + `mavenCentral()` | `mavenCentral()` |
| 폐쇄망 | 사내 Nexus `http://19.88.120.152:9010/repository/maven-releases/` (`allowInsecureProtocol`) | 동일 Nexus |

세 모듈 모두 **주석 전환 패턴**이 동일하다. 로컬에서 Nexus 블록을 켜면 해석에 실패할 수 있으므로, DS·JDBC 의존 전환과 **함께** 맞춘다.

### 15.4 JAR·WAR·Boot JAR 산출물

| 모듈 | plugins | bootJar / war | 산출물 | 정책 |
| ---- | ------- | ------------- | ------ | ---- |
| `pdmk-fw` | `java-library`, Boot, dep-mgmt, eclipse | `bootJar` **off** / `jar` **on** | `pdmk-fw-0.0.1-SNAPSHOT.jar` | 앱이 아님 |
| `pdmk-service` | `java`, `war`, Boot, dep-mgmt, eclipse | `bootWar` **off** / `war` **on** | `*.war` | **외부 WAS 배포 전제** |
| `pdmk-ui` | `java`, Boot, dep-mgmt, eclipse | `bootJar` on | `pdmk-ui.jar` | 실행형 JAR |

| 산출물 | 위치 | 포함 내용 |
| ------ | ---- | --------- |
| fw JAR | `pdmk-fw/build/libs/` | `nhnis.fw.*` (transitive 의존은 소비 측에서 해석) |
| service WAR | `pdmk-service/build/libs/` | 업무 + **임베드된 fw** |
| ui JAR | `pdmk-ui/build/libs/pdmk-ui.jar` | UI만 (service/fw 미포함) |

**`bootWar` 비활성은 의도된 결정이다.** service를 실행형 bootJar/bootWar로 바꾸면 WAS 배포 전제가 깨진다(팀 합의 없이 변경 금지).

### 15.5 로컬 기동 순서

```text
 [1] pdmk-fw       gradlew jar
        │
 [2] pdmk-service  script\build.bat  (또는 gradlew clean build) → build/libs/*.war
                   RUN.bat / script\run.bat → bootRun :8080
        │
 [3] pdmk-ui       script\build.bat → build/libs/pdmk-ui.jar
                   RUN.bat / script\run.bat jar → :8090
```

| 목적 | 명령 |
| ---- | ---- |
| FW만 빌드 | `pdmk-fw` → `gradlew jar` |
| Service 빌드 | `pdmk-service` → `script\build.bat` 또는 `gradlew clean build` |
| Service 기동 | `RUN.bat` 또는 `script\run.bat` (`bootRun`) |
| Service 프로파일 지정 | `script\run.bat --args="--spring.profiles.active=dev"` |
| UI 빌드 | `pdmk-ui` → `script\build.bat` |
| UI 기동 | `RUN.bat` 또는 `script\run.bat jar` |
| IDE 클래스패스 | `gradlew writeIdeLaunch` → `../.vscode/launch.json` |

**기동 순서는 service(8080) → ui(8090).** UI만 띄우면 릴레이 대상이 없다.

검증: UI `http://localhost:8090`, API `POST http://localhost:8080/mkcoa5530S0`.

`writeIdeLaunch`(service)는 `dependsOn classes, :pdmk-fw:jar`로, jdt.ls 단독 클래스패스에서 fw가 빠지는 문제를 우회한다.

### 15.6 WAS 배포

| 설정 | 의미 |
| ---- | ---- |
| `bootWar { enabled = false }` | 실행형 Boot WAR 비활성 |
| `war { enabled = true }` | **일반 WAR** (외부 Tomcat 등 WAS 배포) |
| `providedRuntime` Tomcat | WAR 시 WAS 제공 컨테이너 사용 |
| `ServletInitializer` | `SpringBootServletInitializer` → WAS 기동 시 `PdmkApplication` 실행 |

| 항목 | 내용 |
| ---- | ---- |
| service Main | `nhnis.mk.PdmkApplication` (`scanBasePackages="nhnis"`) |
| ui Main | `nhnis.mk.ui.PdmkUiApplication` |
| CORS | ui 서버사이드 릴레이로 브라우저↔service 직접 CORS 회피 |
| 멀티 인스턴스 | ⚠️ 문서화·스크립트 없음. `MessageCache`는 인스턴스 로컬, ImageLog는 공유 DB |
| Docker / Compose / K8s | **저장소에 없음** |
| CI/CD 파이프라인 | 본 문서 범위 밖 (팀 표준) |
| ui 운영 필수 여부 | 개발·시험용. 운영은 API 직호출 가능 |

### 15.7 환경 전환

로컬 → 폐쇄망 전환 시 **다섯 가지를 함께** 바꾼다.

| # | 대상 | 파일 | 작업 |
| - | ---- | ---- | ---- |
| 1 | Gradle 저장소 | `settings.gradle` / `build.gradle` (세 모듈) | Central/PluginPortal → 사내 Nexus |
| 2 | JDBC 의존 | `pdmk-service/build.gradle` | H2 주석 처리 → `ojdbc`·`orai18n` 활성 |
| 3 | DataSource | `application.yml` | `spring.datasource.rdw` Oracle URL·계정 |
| 4 | 초기화 SQL | `application.yml` | `spring.sql.init` **비활성** |

### 16.3 코드 리뷰 체크리스트

#### 계약·네이밍

- [ ] 서비스 ID가 URL·메서드·DTO·SQL ID·`rms_svc_c`에서 동일한가
- [ ] Controller/Service/DAO는 식별번호 단위, DTO는 서비스 ID 전체인가
- [ ] 클래스 `@RequestMapping`·REST 자원 URL이 없는가
- [ ] fw `RequestBody`를 import했는가 (Spring 표준 아님)
- [ ] UI 카탈로그 ID와 샘플 JSON이 동기화되었는가

#### 계층·의존

- [ ] Controller가 진입·위임·로그만 하는가
- [ ] Controller → DAO 직접 호출이 없는가
- [ ] DAO 시그니처가 `Map` 입력 / `List<Map>`·`int` 출력인가
- [ ] `pdmk-fw`에 업무 코드가 추가되지 않았는가
- [ ] `pdmk-ui`에 DB/fw 의존이 추가되지 않았는가

#### 데이터·트랜잭션

- [ ] DAO 메서드명 = XML `id` = SQL ID 인가
- [ ] `namespace` = DAO FQCN 인가
- [ ] 모든 바인딩이 `#{}` 인가 (`${}` 없음)
- [ ] 목록/count SQL이 동일 WHERE를 `<include>`로 공유하는가
- [ ] ROWNUM 이중 래핑 + 안쪽 `ORDER BY` 인가
- [ ] 조회 Service에 `readOnly=true`, 쓰기에 `@Transactional`이 있는가
- [ ] self-invocation으로 TX를 기대하지 않는가

#### 오류·로그·보안

- [ ] 업무 예외가 `NhBaseException` + 적절한 `TYPE` 인가
- [ ] 새 오류 코드가 `exceptionCode.yml`에 등록되었는가
- [ ] 0건을 예외로 만들지 않았는가
- [ ] 로그가 `PdmkTxLog` 포맷을 따르고 호출부에서 `log.info` 하는가
- [ ] 개인정보·비밀번호·토큰이 로그에 없는가
- [ ] 시크릿이 yml에 평문으로 커밋되지 않았는가

#### 비활성 경로

- [ ] `@TcfTransaction` / `StandardResponseDto` / `BizException`을 쓰지 않았는가
- [ ] TCF 필터·fw Security를 활성화하지 않았는가

### 16.4 단위·통합 테스트 범위

**✅ AS-IS:** 현재 저장소에는 Gradle 기본 test 소스셋과 `spring-boot-starter-test` 의존이 구성되어 있으나, **업무 거래에 대한 자동화 테스트 자산은 확인되지 않았다** ([§17.4](#174-테스트-현황)). 아래는 신규 개발 시 **권장 범위**다.

| 계층 | 테스트 종류 | 대상 | 비고 |
| ---- | ----------- | ---- | ---- |
| Service | 단위 (Mockito) | 페이징 정규화, DTO↔Map 변환, 업무 분기, 예외 발생 조건 | DAO는 mock |
| DAO / Mapper | 통합 (`@MybatisTest` 또는 Boot slice) | SQL 문법, 파라미터 바인딩, ROWNUM 슬라이스, count 일치 | H2 `MODE=Oracle` |
| Controller | 통합 (`@SpringBootTest` + MockMvc) | 전문 봉투 바인딩, 응답 포장, 오류 응답 형태 | fw Resolver 포함 필요 |
| 전체 거래 | 수동/스모크 | `pdmk-ui` 화면 또는 `POST /{서비스ID}` 직호출 | GUID·ImageLog 확인 |
| 회귀 | 수동 | 기존 샘플 3거래 정상 동작 | `mkcoa5530/8888/9999` |

**테스트 시 주의**

| 항목 | 주의 |
| ---- | ---- |
| 프로파일 | `local`이면 JWT 생략·헤더 합성 — 비-local 동작은 별도 검증 필요 |
| H2 vs Oracle | Map 키 대소문자·타입 차이 가능 ([§7.5](#75-dtomap-변환)) |
| ImageLog | 테스트 실행마다 `TB_FW_IMAGE_LOG`에 행이 쌓임 |
| MessageCache | 기본 비활성 → BIZ 메시지는 코드 문자열로 나옴 |
| mem DB | 재기동 시 초기화 |

#### 혼동하기 쉬운 개념 5가지

| 혼동 | 사실 |
| ---- | ---- |
| "Security가 인증한다" | ❌ Security는 permitAll. 인증은 Filter JWT (⚙️ 비-local) |
| "`ttl_ug_ync`가 TX timeout이다" | ❌ 전문 플래그일 뿐 Spring TX와 무관 |
| "`@Transactional(timeout)`이 sleep을 끊는다" | ❌ DB 작업 경계에서 감지되는 값 |
| "`size`가 전체 건수다" | ❌ `size`는 현재 페이지 건수, 전체는 `totalCount` |
| "업무 오류면 HTTP 4xx다" | ❌ 업무 오류는 **500** + 봉투. 4xx는 Filter 단계 실패 |
