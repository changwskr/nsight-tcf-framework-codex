결론적으로, Pointcut을 `Service`로 옮긴 실행 로그라면 **업무 선처리와 업무 후처리가 Facade 트랜잭션 안에 포함됩니다.** 의도한 트랜잭션 범위에는 맞습니다.

다만 저장소 현재 소스와 실행 로그가 일치하지 않습니다.

## 로그에서 확인된 실행 구조

첨부 로그에는 다음과 같이 출력됩니다.

```text
[업무 선처리] 호출: mgcoa5530Service.mgcoa5530S0
```

따라서 실행된 애플리케이션의 Pointcut은 Service를 대상으로 합니다.

```text
Handler
→ Facade 프록시
   → @Transactional 시작
   → Service 프록시
      → 업무 선처리
      → Service
      → DAO / SQL
      → 업무 후처리
   → Service 반환
→ Facade 반환
→ Commit
```

시간 순서도 정상입니다.

```text
16:22:07.076 업무 선처리 시작
16:22:07.079 업무처리 시작
16:22:07.080 Service 시작
16:22:07.081 SQL 실행
16:22:07.086 Service 종료
16:22:07.087 업무 후처리 시작
16:22:07.093 업무 후처리 종료
16:22:07.093 Handler 종료
```

Facade의 트랜잭션은 Service 호출 전에 이미 시작되고, Facade 메서드가 반환된 후 Commit되므로 업무 후처리까지 같은 트랜잭션에 포함됩니다.

```text
TX BEGIN
├─ 업무 선처리
├─ Service
├─ DAO
└─ 업무 후처리
TX COMMIT
```

업무 후처리에서 같은 `rdwTransactionManager`를 사용하는 DAO로 `insert/update`하고 예외를 밖으로 전달하면, 앞의 업무 SQL과 함께 Commit 또는 Rollback됩니다.

## 기존 방식과 달라진 점

기존 Facade Pointcut은 Advisor 순서 때문에 다음처럼 동작할 가능성이 있었습니다.

```text
업무 선처리
→ TX 시작
→ Facade / Service / DAO
→ TX Commit
→ 업무 후처리
```

Service Pointcut으로 변경하면 Facade의 트랜잭션 안에서 Service Aspect가 실행되므로 Advisor의 `@Order` 경쟁을 피할 수 있습니다.

```text
Facade TX 시작
→ Service 업무 선처리
→ Service / DAO
→ Service 업무 후처리
→ Facade TX Commit
```

이 점에서는 Service Pointcut이 더 확실합니다.

## 중요한 불일치

현재 워크스페이스의 [BizPrePostAspect.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mg/entry/aspect/BizPrePostAspect.java>)는 아직 다음 Pointcut입니다.

```java
@Pointcut(
    "execution(* nhnis.mg.entry.controller..*(..))"
    + " || execution(* nhnis.mg.entry.facade..*(..))"
)
```

즉:

- 첨부 로그: `Service` Pointcut
- 현재 저장된 소스: `Controller || Facade` Pointcut

실행 중인 클래스와 현재 소스가 서로 다릅니다. 다음 가능성을 확인해야 합니다.

- 변경한 파일이 저장되지 않음
- 애플리케이션 재빌드 또는 재시작이 안 됨
- 다른 작업 폴더에서 실행 중
- IDE가 이전 빌드 산출물을 사용 중
- 첨부 로그 생성 후 Pointcut을 다시 변경함

그리고 요청에는 `pdmk-mg`, `pdmk-fw`라고 되어 있지만, 첨부 로그의 실제 대상은 다음입니다.

```text
업무: pdmg-service / nhnis.mg
프레임워크: pdmg-fw / nhnis.fw
```

저장소에는 `pdmk-mg`라는 모듈이 없습니다. `pdmk-fw`는 이번 `mgcoa5530S0` 로그를 생성한 프레임워크가 아닙니다.

## Service Pointcut 권장 형태

의도대로 유지하려면 현재 파일의 Pointcut은 다음과 같아야 합니다.

```java
@Pointcut("execution(public * nhnis.mg.application.service..*(..))")
public void mgBizBoundary() {
}
```

`public`으로 한정하는 것이 안전합니다.

## 주의할 부작용

Service Pointcut은 트랜잭션 포함에는 유리하지만 다음 특성이 있습니다.

- Facade가 Service를 여러 번 호출하면 선후처리 로그도 여러 번 발생
- 배치나 스케줄러가 같은 Service를 호출해도 선후처리가 실행
- Facade의 DTO 변환에서 실패하면 Service에 도달하지 않아 업무 선처리가 실행되지 않음
- 한 Service가 다른 Service를 호출하면 중복 선후처리가 발생할 수 있음
- 동일 객체 내부의 자기 호출은 Spring 프록시를 통과하지 않아 Aspect가 실행되지 않을 수 있음

거래당 반드시 한 번만 실행해야 한다면 Facade Pointcut이 개념적으로 더 정확하고, 트랜잭션 순서를 별도로 조정해야 합니다. Service 실행 전체를 같은 트랜잭션으로 감싸는 것이 우선이라면 지금 변경한 Service Pointcut이 적절합니다.

또한 로그의 `BRC: null`은 여전히 남아 있습니다. 요청 헤더에는 `tr_brc=10001`이 있으므로 DTO에서 값이 없을 때 `ServiceContext` 헤더 값을 사용하도록 보완할 필요가 있습니다.

이번에는 로그와 소스만 분석했으며 파일 수정이나 테스트 실행은 하지 않았습니다.
