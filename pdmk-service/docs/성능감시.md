현재 성능 감시는 세 구간으로 나눠 진행합니다.

## 1. HTTP 요청 전체 시간

[TcfTraceFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmk-service/src/main/java/nhnis/fw/tcf/web/TcfTraceFilter.java>)가 요청이 서버에 들어온 순간부터 응답이 끝날 때까지 측정합니다.

```java
long startedAt = System.nanoTime();

try {
    chain.doFilter(request, response);
} finally {
    recordTotalElapsed(request, response, startedAt);
}
```

포함되는 시간은 다음과 같습니다.

```text
보안 필터
+ JSON 변환
+ STF
+ Controller
+ Service
+ DB 조회
+ ETF
+ 응답 처리
= total 시간
```

로그 예시는 다음과 같습니다.

```text
[TRACE] POST /api/mp/co/a/9999/list status=200 total=3250ms
```

3초 이상이면 `WARN`, 미만이면 `INFO`로 기록합니다.

## 2. TCF 업무 처리 시간

[STF.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmk-service/src/main/java/nhnis/fw/tcf/stf/STF.java>)가 `TcfContext`를 만들면서 업무 시간 측정을 시작합니다.

[TcfContext.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmk-service/src/main/java/nhnis/fw/tcf/context/TcfContext.java>)에 시작 시간이 저장됩니다.

```java
private final long startedAtNanos;

public long elapsedMs() {
    return (System.nanoTime() - startedAtNanos) / 1_000_000L;
}
```

[ETF.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmk-service/src/main/java/nhnis/fw/tcf/etf/ETF.java>)가 거래 종료 시 시간을 계산합니다.

```java
long elapsedMs = context.elapsedMs();
```

로그 예시는 다음과 같습니다.

```text
[ETF] 거래 종료
serviceId=MP.SalesTip.list
resultCode=S0000
business=3100ms
```

3초 이상이면 다음과 같은 지연 거래 `WARN` 로그도 남깁니다.

```text
[ETF] 지연 거래
serviceId=MP.SalesTip.list
business=3100ms
threshold=3000ms
```

### 전체 시간과 업무 시간의 차이

```text
HTTP 전체 시간: 3300ms
TCF 업무 시간: 3100ms
차이: 200ms
```

200ms는 보안 필터, JSON 변환, 응답 직렬화처럼 TCF 업무 처리 바깥에서 사용된 시간입니다.

## 3. SQL별 실행 시간

[MybatisLogInterceptor.java](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmk-service/src/main/java/nhnis/mp/config/MybatisLogInterceptor.java>)가 MyBatis의 모든 `query`와 `update`를 가로챕니다.

```java
long startedAt = System.currentTimeMillis();

try {
    return invocation.proceed();
} finally {
    long elapsed =
        System.currentTimeMillis() - startedAt;

    log.debug("{} | param={} | {}ms",
        sqlId, parameter, elapsed);
}
```

SQL마다 다음 정보가 기록됩니다.

- MyBatis SQL ID
- 전달된 파라미터
- SQL 실행시간
- 요청 GUID
- 사용자 ID
- 서비스 ID

예시는 다음과 같습니다.

```text
mpcoa9999S0_S0_count | param={...} | 12ms
mpcoa9999S0_S0       | param={...} | 85ms
```

`log4j2.xml`에서 해당 로거가 `DEBUG`로 활성화되어 있어 현재 SQL 시간 로그가 출력됩니다.

## 현재 경고 기준

[application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework/pdmk-service/src/main/resources/application.yml>)에 하나의 공통 기준이 있습니다.

```yaml
nsight:
  tcf:
    slow-transaction-ms: 3000
```

따라서:

```text
HTTP 전체 시간 ≥ 3초 → TRACE WARN
TCF 업무 시간 ≥ 3초 → ETF WARN
SQL 실행 시간         → 시간 기록만 함
```

SQL에는 별도의 느린 SQL 경고 기준이 없습니다. 예를 들어 SQL이 5초 걸려도 `DEBUG` 실행시간은 남지만, `MybatisLogInterceptor` 자체가 `WARN`으로 올리지는 않습니다.

## 현재 감시의 한계

현재는 로그 기반 감시입니다.

- 요청 시간 측정: 있음
- 업무 시간 측정: 있음
- SQL 시간 측정: 있음
- 느린 거래 WARN: 있음
- 느린 SQL WARN: 없음
- 평균·최대·백분위수 통계: 없음
- 실시간 대시보드: 없음
- 임계치 초과 알림: 없음
- 트랜잭션 강제 timeout: 없음

즉, 현재 구조는 “느리면 로그에 표시해서 GUID나 serviceId로 추적하는 단계”입니다. 자동 집계나 알림까지 수행하는 APM 구조는 아직 아닙니다.
