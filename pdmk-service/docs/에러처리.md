# 에러 처리

## 1. 로그 파일명 변경

현재 프로젝트가 `pdmk-service`이고 애플리케이션 이름도 `pdmk`이므로, 프로젝트 식별 목적이라면 `sd`/`pd`보다 `pk`가 더 자연스럽습니다.

### 현재 값

```text
logs/application/sd*framework.log
logs/service/sd_service.log
```

### 변경 후 값

```text
logs/application/pk_framework.log
logs/service/pk_service.log
```

날짜별 압축 파일도 함께 변경해야 합니다.

```text
fileName="${FRAMEWORK_LOG_PATH}/pk_framework.log"
filePattern="${FRAMEWORK_LOG_PATH}/pk_framework_%d{yyyy-MM-dd}.log.gz"
fileName="${SERVICE_LOG_PATH}/pk_service.log"
filePattern="${SERVICE_LOG_PATH}/pk_service_%d{yyyy-MM-dd}.log.gz"
```

다만 `sd`가 사내 통합 로그 수집 규칙에서 요구하는 고정 접두어라면, 변경 전에 운영 설정을 확인해야 합니다. 현재 저장소 안에는 `sd`의 근거나 별도 정의가 없기 때문에, 코드 기준으로는 `pk`로 변경하는 것이 일관적입니다.

## 2. 에러 처리 방식

현재 에러는 발생 위치와 종류에 따라 세 경로로 처리됩니다. 최종 실패 응답은 모두 ETF가 생성합니다.

### 2.1 업무 처리 중 발생한 에러

`@TcfTransaction`이 붙은 Controller 안에서 발생한 오류는 [src/main/java/nhnis/fw/tcf/aspect/TCFAspect.java](../src/main/java/nhnis/fw/tcf/aspect/TCFAspect.java)가 처리합니다.

```java
try {
    context = stf.preProcess(...);
    Object result = joinPoint.proceed();
    return etf.success(context, ...);
} catch (BizException e) {
    return etf.businessFail(context, e);
} catch (Exception e) {
    return etf.systemError(context, e);
} finally {
    TcfContextHolder.clear();
}
```

#### 업무 오류: BizException

사용자 입력 누락이나 조회 결과 없음처럼 예상 가능한 오류입니다.

```java
throw new BizException("FW0001", "요청 Body");
```

[BizException.java](../src/main/java/nhnis/fw/exception/BizException.java)는 `RuntimeException`을 상속합니다.

흐름은 다음과 같습니다.

```text
Service에서 BizException 발생
↓
DB 트랜잭션 rollback
↓
TCFAspect가 catch
↓
ETF.businessFail()
↓
표준 실패 응답
```

응답 예시는 다음과 같습니다.

```json
{
  "result": {
    "resultCode": "E0001",
    "errorCode": "FW0001",
    "errorMessage": "요청 Body 오류가 발생하였습니다."
  },
  "body": null
}
```

#### 예상하지 못한 시스템 오류

`NullPointerException`, DB 접속 오류처럼 일반 `Exception`은 다음 코드로 처리합니다.

```java
catch (Exception e) {
    return etf.systemError(context, e);
}
```

시스템 오류 코드는 고정적으로 `FW9999`를 사용합니다. 또한 실제 예외와 스택 트레이스를 `ERROR` 로그로 기록합니다.

---

### 2.2 Controller에 도착하기 전에 발생한 에러

잘못된 JSON처럼 Controller 메서드가 실행되기 전에 발생한 오류는 Aspect가 볼 수 없습니다.

예시:

- JSON 문법 오류
- JSON 필드 타입 불일치
- 요청 Body 변환 실패
- Controller 매핑 과정의 오류

이 경우 [src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java](../src/main/java/nhnis/fw/exception/GlobalExceptionHandler.java)가 처리합니다.

```java
@ExceptionHandler(BizException.class)
public StandardResponseDto<Object> handleBizException(BizException e) {
    return etf.businessFail(null, e);
}

@ExceptionHandler(Exception.class)
public StandardResponseDto<Object> handleException(Exception e) {
    return etf.systemError(null, e);
}
```

`TcfContext`가 아직 생성되지 않았으므로 `null`을 전달합니다. 대신 Filter가 만든 `guid`와 `traceId`는 MDC에서 가져와 응답에 넣습니다.

---

### 2.3 인증 에러

JWT가 잘못됐거나 만료된 경우에는 Spring Security 필터에서 에러가 발생합니다. 이 에러도 Controller와 Aspect에 도착하기 전이므로 [src/main/java/nhnis/fw/tcf/web/TcfAuthenticationEntryPoint.java](../src/main/java/nhnis/fw/tcf/web/TcfAuthenticationEntryPoint.java)가 직접 처리합니다.

```java
response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
objectMapper.writeValue(response.getOutputStream(), etf.fail("FW0401"));
```

이 경우 HTTP 상태는 실제로 `401 Unauthorized`입니다.

```json
{
  "result": {
    "resultCode": "E0001",
    "errorCode": "FW0401",
    "errorMessage": "인증에 실패하였습니다."
  }
}
```

## 3. 에러 메시지는 어디서 가져오는가

에러 코드별 메시지는 [src/main/resources/exceptionCode.yml](../src/main/resources/exceptionCode.yml)에 정의되어 있습니다.

```yaml
nhnis:
  exception:
    FW0001: "{0} 오류가 발생하였습니다."
    FW0003: "{0} Exception은 {1}로 문의해주세요"
    FW0401: "인증에 실패하였습니다. 다시 로그인해주세요"
    FW0403: "요청한 거래에 대한 권한이 없습니다."
    FW9999: "예기치 않은 시스템 오류가 발생하였습니다."
```

[ExceptionCodeProperties.java](../src/main/java/nhnis/fw/exception/ExceptionCodeProperties.java)가 코드를 메시지로 바꿉니다. 등록되지 않은 코드가 들어오면 `FW9999` 메시지를 대신 사용합니다.

## 4. 최종 실패 응답 조립

[ETF.java](../src/main/java/nhnis/fw/tcf/etf/ETF.java)가 다음 내용을 채웁니다.

```text
header
├─ guid
└─ traceId

result
├─ resultCode: E0001
├─ errorCode
├─ errorMessage
├─ errorDetail
├─ errorSystemId: NSIGHT-MP
└─ errorDateTime

body: null
```

---

## 5. 업무·시스템 에러의 HTTP 상태

현재 TCF 계약에서는 Controller 처리 중 발생한 업무·시스템 오류도 일반적으로 HTTP 200으로 반환합니다.

호출자는 HTTP 상태가 아니라 다음 값을 확인합니다.

- `result.resultCode = S0000` → 성공
- `result.resultCode = E0001` → 실패

다만 인증 실패는 요청 진입 자체가 거절된 것이므로 HTTP 401을 반환합니다.

---

## 6. 전체 흐름

```text
에러 발생
├─ 업무 내부
│  ├─ BizException → ETF.businessFail()
│  └─ 기타 Exception → ETF.systemError()
├─ JSON 변환·Controller 이전
│  └─ GlobalExceptionHandler → ETF
└─ JWT 인증 실패
   └─ AuthenticationEntryPoint → ETF.fail()
```

그리고 DB 쓰기 트랜잭션 안에서 `BizException` 또는 일반 런타임 예외가 발생했다면, 실패 응답을 만들기 전에 Spring 트랜잭션 프록시가 먼저 rollback합니다.
