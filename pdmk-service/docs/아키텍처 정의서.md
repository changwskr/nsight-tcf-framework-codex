## 1. 왜 이렇게 설계했는가

### 1.1 설계 목표

PDMK는 **은행권 온라인 거래 스타일**을 작은 샘플 스택으로 재현한다.

| 목표 | 의미 |
| ---- | ---- |
| 한 스택 | UI·업무·프레임워크를 분리하되 **한 번의 거래**로 이어지게 |
| 서비스 ID | URL·메서드·DTO·SQL이 **같은 이름**으로 연결 |
| 공통 파이프라인 | 헤더·컨텍스트·감사·에러는 **fw commons**에 모음 |
| 업무 경계 | CRUD·TX·페이징은 **service**만 |
| 로컬↔폐쇄망 | 개발은 H2, 운영 전제는 Oracle/WAS |

### 1.2 핵심 결정 (채택 / 기각)

```text
  채택 ★                          기각 ✕
 ─────────                        ─────────
  서비스ID = URL = 메서드          REST /api/업무/list
  hdr_nhnis + dto                 루트에 업무 필드만
  commons Filter/Interceptor      TCF 경로와 이중 혼용
  TX = Service @Transactional     Controller/DAO에 TX
  ui는 HTTP 릴레이만              ui → fw/DAO 직결
  WAR(service) + JAR(fw)          합의 없는 임의 배포 형태
```

| 결정 | 이유 |
| ---- | ---- |
| **commons ON · TCF OFF** | 전문·헤더·ImageLog 경로를 하나로 고정. `nhnis.fw.tcf.enabled=false` |
| **서비스 ID 축** | 레거시 온라인 거래와 동일한 추적·카탈로그·SQL 연결 |
| **세 Gradle 모듈** | 공통/업무/실험UI 변경 영향 분리 |
| **MyBatis Map DAO** | XML·SQL ID를 서비스ID와 1:1로 맞춤 |
| **ui 비의존 fw** | 화면·중계만. 인증·헤더는 service(+fw)에서 처리 |

### 1.3 설계 슬로건

| # | 슬로건 |
| - | ------ |
| 1 | 세 모듈 한 스택 |
| 2 | 서비스 ID = URL = 메서드 |
| 3 | commons ON · TCF OFF |
| 4 | TX는 Service |
| 5 | 전문은 hdr + dto |
| 6 | 변경은 영향 표로 본다 ([§9](#9-소스와-설계가-일치하는지-어떻게-검증하는가)) |

### 1.4 이 장이 답하는 것

- **왜 모듈을 셋으로 쪼갰는가** → 공통/업무/실험 화면의 수명·배포가 다르기 때문  
- **왜 TCF를 켜지 않는가** → commons와 계약·필터가 달라 이중 경로가 됨  
- **왜 REST 자원 URL이 아닌가** → 거래 단위(서비스 ID)가 운영·감사·카탈로그의 키이기 때문

## 2. 전체 시스템은 어떻게 생겼는가

### 2.1 한눈에 보는 스택

```text
 ┌──────────────────────────────────────────┐
 │  Presentation   pdmk-ui :8090            │
 │  정적화면 · 카탈로그 · HTTP 릴레이         │
 └────────────────────┬─────────────────────┘
                      │ POST /{서비스ID}
 ┌────────────────────▼─────────────────────┐
 │  Application    pdmk-service :8080       │
 │  Controller → Service → DAO · BizAspect  │
 └────────────────────┬─────────────────────┘
                      │ implementation
 ┌────────────────────▼─────────────────────┐
 │  Framework      pdmk-fw (commons) JAR    │
 │  Filter · Interceptor · JWT · ImageLog   │
 └────────────────────┬─────────────────────┘
                      │
 ┌────────────────────▼─────────────────────┐
 │  Persistence    RDW (H2 / Oracle)        │
 │  TB_* · MyBatis · DS rdw                 │
 └──────────────────────────────────────────┘
```

| 층 | 구성 | 포트/산출 | 하는 일 | 하지 않는 일 |
| -- | ---- | --------- | ------- | ------------ |

| Application | `pdmk-service` | :8080 · WAR | C→S→DAO · BizAspect | UI 렌더 |
| Framework | `pdmk-fw` | JAR | Filter·헤더·JWT·ImageLog | 업무 CRUD · Boot main |
| Persistence | RDW | H2/Oracle | 테이블·SQL | — |

## 3. 세 모듈은 무엇을 담당하는가

### 3.1 책임 한줄

```text
  pdmk-fw      : 컨텍스트 · 헤더 · JWT · ImageLog · 에러 조립
  pdmk-service : 업무 거래 · TX · DAO · Security 샘플
  pdmk-ui      : 전문 편집 · 카탈로그 · HTTP 릴레이
```

### 3.2 모듈 간 계약

```text
  pdmk-ui                 pdmk-service              pdmk-fw
 ┌─────────┐   HTTP만   ┌─────────────┐  Gradle  ┌─────────┐
 │ :8090   │ ─────────► │ :8080 WAR   │ ◄─────── │ JAR     │
 │ 릴레이  │            │ nhnis.mk.*  │ project  │commons  │
 └─────────┘            └─────────────┘          └─────────┘
      │                        │                      │
      └──────── 서비스ID · hdr_nhnis+dto 계약 ────────┘
      ※ ui ↔ fw 직접 의존 없음
```

| 경계 | 규칙 |
| ---- | ---- |
| ui → service | HTTP만. JSON `hdr_nhnis`+`dto` |
| service → fw | Gradle `implementation` · Bean 스캔 `nhnis` |
| ui → fw | **의존 금지** |
| service/fw → RDW | `rdwDataSource` · MyBatis / ImageLog JDBC |

### 3.3 모듈 × 관심사

| 관심사 | fw | service | ui |
| ------ | -- | ------- | -- |
| Filter / JWT | ● | ○(설정) | — |
| Interceptor / ImageLog | ● | — | — |
| Biz Aspect | — | ● | — |
| Controller·Service·DAO | — | ● | — |
| 전문 DTO / 네이밍 | ○(헤더) | ● | ○(샘플·카탈로그) |
| MyBatis / 테이블 | ○(ImageLog) | ● | — |
| Spring Security | ○(옵션 OFF) | ● | — |
| HTTP 릴레이 | — | — | ● |

### 3.4 패키지·레이어 (service 중심)

```text
 Presentation   Controller (+ ui)
 Application    Service · BizPrePostAspect · @Transactional
 Domain         업무 규칙 · DTO
 Persistence    DAO · MyBatis XML
 Infrastructure fw Filter/Interceptor/Resolver · DS · RDW
```

| 레이어 | 허용 | 금지 |
| ------ | ---- | ---- |
| Controller | 매핑·위임 | SQL · TX · 비즈니스 |
| Service | 규칙·TX·페이징·Map↔DTO | HTTP |
| DAO | SQL ID만 | DTO · 비즈니스 |

### 3.5 commons vs TCF

```text
        pdmk-fw
   ┌──────┴──────┐
   ▼             ▼
 commons★     tcf (OFF)
 hdr+dto      StandardDto
 NhBaseExc    BizException
 Interceptor  TCFAspect
```

| | commons | TCF |
| - | ------- | --- |
| 스위치 | `filter` / `legacy-web` | `tcf.enabled` |
| PDMK | **사용** | **미사용** (`false`) |

### 3.6 하지 말 것 (모듈)

| 금지 | 이유 |
| ---- | ---- |
| ui에 fw/DAO 붙이기 | 경계 붕괴 |
| 업무 코드를 fw에 넣기 | 공통 오염 |
| TCF ON + commons 이중 경로 | Filter/계약 충돌 |
| 한 모듈만 보고 URL·카탈로그 변경 | 계약 어긋남 |

## 4. 거래 1건은 어떻게 흐르는가

### 4.1 UI 경유 통합 경로

```text
 Browser
   → pdmk-ui  (static 또는 POST /api/relay/{서비스ID})
        → TransactionRelayService
             → pdmk-service  POST /{서비스ID}
                  → [§4.2 계층]
```

### 4.2 service + fw 계층

```text
 HTTP POST /{서비스ID}
 Body: { "hdr_nhnis": {...}, "dto": {...} }
       (local: { "dto": {...} } 만으로도 가능)
────────────────────────────────────────────────────────────
 │ ① DefaultFilter                 [Servlet · pdmk-fw]
 │    Body 캐시 · JWT · ServiceContext · MDC
 ▼
 │ ② ServicePreventionInterceptor  [MVC · pdmk-fw]
 │    pre: GUID·헤더보강 · ImageLog PRE
 │    post: ImageLog POST
 │    ex:  ImageLog EX
 ▼
 │ ③ BizPrePostAspect              [AOP · pdmk-service]
 │    @Before / @After  업무 공통 로그 · BRC
 ▼
 │ ④ Controller → ⑤ Service → ⑥ DAO / MyBatis XML
────────────────────────────────────────────────────────────
 응답: *DTOout  →  (ui 경유 시) RelayResult
```

### 4.3 성공 타임라인

```text
 t0  UI relay POST
 t1  DefaultFilter      Body · JWT · Context
 t2  Security           permitAll (샘플)
 t3  Interceptor        GUID · ImageLog PRE
 t4  BizAspect @Before  업무선처리 로그
 t5  Controller → Service → DAO
 t6  BizAspect @After   업무후처리 로그
 t7  Interceptor        ImageLog POST
 t8  Filter finally     Context / MDC clear
 t9  UI ← DTOout
```

### 4.4 삼층 역할

```text
 ┌─ DefaultFilter ──────────┐  Servlet
 │ Body · JWT · Context     │
 └────────────┬─────────────┘
              ▼
 ┌─ ServicePreventionInterceptor ┐  MVC
 │ GUID · 헤더 · ImageLog        │
 └────────────┬──────────────────┘
              ▼
 ┌─ BizPrePostAspect ───────┐  AOP
 │ 업무 선·후처리 로그        │
 └────────────┬─────────────┘
              ▼
         Controller
```

| 구분 | 클래스 | 주 책임 | 스위치 |
| ---- | ------ | ------- | ------ |
| 필터 | `DefaultFilter` | 파싱·JWT·Context | `commons.filter` |
| 시스템 | `ServicePreventionInterceptor` | GUID·ImageLog | `legacy-web` |
| 업무 | `BizPrePostAspect` | Controller 로그 | `legacy-web` |

### 4.5 Filter가 Context를 만드는 이유

거래 전 구간(Interceptor·Advice·업무)이 **같은 GUID·헤더**를 보게 하려고, Servlet 단에서 Body를 한 번 읽고 `ServiceContextHolder` + MDC에 심는다.  
`finally`에서 반드시 지워 **워커 스레드 GUID 누수**를 막는다.

```text
 Filter 성공 → Holder+MDC set → …업무… → finally clear
```

### 4.6 업무 거래 vs DB 트랜잭션

```text
 ┌─ 업무 거래 (요청 1건 생명주기) ──────────────┐
 │ Filter → Interceptor → Aspect → C → S       │
 │         ┌─ DB TX (권장) ─────────────────┐  │
 │         │ @Transactional + rdwTM         │  │
 │         │ DAO SQL commit / rollback      │  │
 │         └────────────────────────────────┘  │
 │ ImageLog PRE/POST/EX 는 업무 TX와 분리 가능  │
 └─────────────────────────────────────────────┘
```

## 5. 서비스/전문 계약은 무엇인가

### 5.1 HTTP · 서비스 ID

| 항목 | 규칙 |
| ---- | ---- |
| Method / URL | `POST /{서비스ID}` (예: `/mkcoa5530S0`) |
| Content-Type | `application/json` |
| UI 중계 | `POST /api/relay/{서비스ID}` → 동일 본문 (UI 전용) |
| 클래스 `@RequestMapping` | 업무에 사용하지 않음 |

```text
 [대구분2][업무2][세부1][식별4][구분자1][순번1]
    mk      co     a     8888      S       0
 → mkcoa8888S0 = URL = 메서드 = rms_svc_c
```

| 위치 | 값 예 |
| ---- | ----- |
| URL | `POST /mkcoa8888S0` |
| `sys_comm.rms_svc_c` | `mkcoa8888S0` |
| `sys_comm.scid` | `mkcoa8888` |
| Controller/Service | `mkcoa8888S0(...)` |
| DTO | `mkcoa8888S0DTOin` / `DTOout` |
| SQL ID | `mkcoa8888S0_S0` |

### 5.2 전문 구조

```text
┌────────────── 요청 / 응답 JSON ──────────────┐
│ hdr_nhnis          ← FW 공통 헤더            │
│  └─ sys_comm       GUID·서비스·단말·조작자   │
│ dto                ← 업무 본문 (서비스별)     │
│  ├─ [요청] *DTOin                            │
│  └─ [응답] *DTOout + *DTOSub0[] + 페이징     │
└──────────────────────────────────────────────┘
```

| 노드 | 소유 | 역할 |
| ---- | ---- | ---- |
| `hdr_nhnis` / `sys_comm` | fw | GUID·서비스·단말·조작자 |
| `dto` 요청 | service `*DTOin` | Resolver 바인딩 |
| `dto` 응답 | service `*DTOout` | Advice가 envelope 조립 |

**핵심 sys_comm:** `std_gbl_id` · `rms_svc_c` · `scid` · `tr_trm_ipadr` · `optr_eno`

### 5.3 바인딩 경로

```text
 [요청] JSON → Filter(hdr→Context) → Resolver(dto→DTOin)
 [응답] DTOout → Advice → { hdr_nhnis, dto }
 [예외] NhBaseException → NH_NIS_ERR_DTO
 [Filter 실패] sendError — envelope 없음
```

| 주의 | 내용 |
| ---- | ---- |
| `@RequestBody` | **Spring 표준이 아니라** `nhnis.fw.commons.resolver.RequestBody` |
| local | `hdr` 없이 `dto`만 가능 → Filter가 합성 헤더 |
| 비-local | `hdr` 필수 + Bearer JWT |

### 5.4 하지 말 것 (계약)

| 금지 | 이유 |
| ---- | ---- |
| 루트에 업무 필드 | Filter/Resolver는 hdr+dto만 |
| Spring `@RequestBody` | `dto` 노드 추출 실패 |
| REST `/api/.../list` 업무 URL | 서비스ID 축 붕괴 |
| TCF `StandardDto` 혼용 | 계약 상이 |

## 6. 업무·DB는 어떻게 구현하는가

### 6.1 Service 책임

```text
 Service
  ├─ DTOin → Map (조건·offset·pageSize·…)
  ├─ @Transactional (조회 readOnly / 쓰기)
  ├─ DAO 호출 (목록 + count)
  ├─ Map → DTOSub / DTOout
  └─ 페이징·검증·결과코드
```

| 용도 | 애노테이션 |
| ---- | ---------- |
| 조회 | `@Transactional(readOnly=true)` |
| 쓰기 | `@Transactional` (± `timeout` 초) |
| 위치 | **Service만** |

### 6.2 DAO · MyBatis

```text
 Service (Map / List·int)
      ▼
 nhnis.mk.co.a.dao.mkcoa{식별}DAO  @RDWMapper
      ▼
 rdw.mk.co.a/mkcoa{식별}-ORA.xml   namespace = DAO FQCN
      ▼
 rdwSqlSessionTemplate → rdwDataSource
```

| 규칙 | 내용 |
| ---- | ---- |
| 메서드명 | = XML `id` = SQL ID |
| 입력/출력 | `Map` / `List<Map>` · `int` |
| DAO에 DTO | **금지** |
| SQL ID 예 | `mkcoa8888S0_S0` · `…_S0_count` · `mkcoa8888D0_D0` |

### 6.3 테이블

```text
                    RDW (H2 / Oracle)
  ┌─────────────────────┬──────────────────────┐
  │ TB_FW_IMAGE_LOG     │ TB_CR_AH_SALES_TIP…  │
  │  (감사 GUID)        │ TB_MK_CO_A_5530      │
  └──────────┬──────────┴──────────┬───────────┘
             │                     │
    fw ImageLogHandler      service MyBatis DAO
    (JdbcTemplate I/U)      (mkcoa8888/9999/5530)
```

| 서비스 | 테이블 | DML |
| ------ | ------ | --- |
| (전 거래) ImageLog | `TB_FW_IMAGE_LOG` | I/U |
| `mkcoa8888S0` / `D0` | 동상 | S / D |
| `mkcoa5530S0` | `TB_MK_CO_A_5530` | S |
| `mkcoa9999S0` | `TB_CR_AH_SALES_TIP_RACT` | S |

### 6.4 페이징

```text
 UI pageNo/pageSize
   → Service normalize (기본 20 · 상한 100) · offset
   ├─ DAO *_count → totalCount
   └─ DAO 목록 (Oracle ROWNUM) → Sub[] + size + totalPages
```

| 서비스 | 페이징 |
| ------ | ------ |
| `mkcoa5530S0` · `mkcoa8888S0` | ○ |
| `mkcoa9999S0` | ❌ 전량 (갭) |

### 6.5 새 거래 추가 (최소 순서)

```text
 ① 네이밍(서비스ID) → ② DTO → ③ C / S / DAO / XML
 → ④ 페이징·TX·테이블 → ⑤ UI Catalog/샘플 → ⑥ fw는 공통만
```

## 7. 보안·로그·에러는 어떻게 공통 처리하는가

### 7.1 보안 계층

```text
 Browser
   │
   ▼
 pdmk-ui :8090          ← 인증 없음 · Bearer 미전달(현황 갭)
   │
   ▼
 pdmk-service :8080
   ├─ DefaultFilter (fw)     ← 비-local: Bearer Access JWT → 401
   ├─ SecurityFilterChain    ← STATELESS · CSRF off · permitAll(샘플)
   ├─ Interceptor / Aspect   ← 인가 아님
   └─ Controller → Service → DAO
```

| 층 | 역할 | 현황 |
| -- | ---- | ---- |
| Filter JWT | 실인증(비-local) | ★ |
| Security | URL 인가 | 샘플 `permitAll` |
| UI | 릴레이 | Authorization 미전달 = 갭 |

`local` 프로파일에서는 JWT 검증을 생략하고 `hdr` 합성을 허용한다. **운영 시크릿·local 설정을 그대로 반입하지 않는다.**

### 7.2 로그 채널

```text
 ┌──────────────────────────────────────────────────────────┐
 │ ① MDC: guid · ip · userId · serviceId  (Filter)         │
 │ ② PdmkTxLog: Interceptor → Aspect → C → S               │
 │ ③ ImageLog DB: PRE INSERT → POST/EX UPDATE              │
 │ ④ SQL: MybatisLogInterceptor (sqlId)                   │
 └──────────────────────────────────────────────────────────┘
```

### 7.3 에러 · 예외

```text
 NhBaseException
   → ResponseBodyArgumentResolver
   → exceptionCode.yml / MessageCache
   → 응답 dto = NH_NIS_ERR_DTO

 Filter 단계 실패 → sendError(401/400) · envelope 없음
```

| 상황 | 권장 |
| ---- | ---- |
| 시스템·검증 | `NhBaseException` |
| 업무 정상 분기(0건 등) | DTOout 결과코드 |
| TCF `BizException` | **미사용** |

### 7.4 AOP · 타임아웃 경계

```text
 Filter → Security → Interceptor → BizAspect → Controller
 → @Transactional → MyBatis Plugin
 (OFF) TCFAspect
```

```text
 UI timeout-ms (설정 존재 · RestClient 미연결 = 갭)
   ≥  DB @Transactional(timeout 초) + 여유
 ttl_ug_ync ≠ Spring TX timeout (자동 연동 없음)
```

## 9. 소스와 설계가 일치하는지 어떻게 검증하는가

### 9.1 검증의 목적

문서가 **희망 사항**이 되지 않도록, 샘플 소스·설정과 **대조 가능한 질문**으로 검증한다.

### 9.2 빠른 대조 체크리스트

| # | 설계 주장 | 소스/설정에서 볼 곳 | 기대 |
| - | --------- | ------------------- | ---- |
| 1 | commons ON · TCF OFF | `nhnis.fw.tcf.enabled` | `false` |
| 2 | Filter·Interceptor 활성 | `commons.filter` / `legacy-web` | `true` |
| 3 | 서비스ID = URL | `*Controller` `@PostMapping` | `/mkcoa…` |
| 4 | hdr+dto | Filter · commons `@RequestBody` | dto 노드만 바인딩 |
| 5 | TX=Service | `*Service` | `@Transactional` (권장 전부) |
| 6 | DAO=SQL ID | DAO 메서드 · `*-ORA.xml` id | 문자 일치 |
| 7 | ui≠fw | `pdmk-ui` build | fw 의존 없음 |
| 8 | JWT 비-local | `DefaultFilter` | Bearer / local 스킵 |
| 9 | ImageLog | Interceptor · `TB_FW_IMAGE_LOG` | PRE/POST/EX |
| 10 | 에러 | `NhBaseException` · `exceptionCode.yml` | NH_NIS_ERR_DTO |

### 9.3 샘플 거래로 끝단 검증

| 서비스 | 검증 포인트 |
| ------ | ----------- |
| `mkcoa5530S0` | 페이징 ○ · `TB_MK_CO_A_5530` |
| `mkcoa8888S0`/`D0` | ImageLog 조회/삭제 |
| `mkcoa9999S0` | 목록 · **페이징 갭** 인지 |

```text
 UI Catalog.id ──► /api/relay/{id} ──► POST /{id}
 ──► Filter → Interceptor → Aspect → C→S→DAO ──► DTOout
```

### 9.4 현황 갭 (설계와 소스의 차이)

```text
  [데이터] mkcoa9999 전량 SELECT
  [UI]     timeout-ms ↔ RestClient 미연결
  [보안]   Authorization 미전달 · permitAll 샘플
  [TX]     일부 @Transactional 미명시
  [FW]     TCF 소스 잔존(런타임 OFF)
  [배포]   컨테이너 없음
```

갭은 **버그 목록이 아니라 문서화된 현재 상태**다. 해소 시 이 절과 상세 보충(copy §26.0)을 같이 고친다.

### 9.5 변경 영향 매트릭스

| 변경 | fw | service | ui |
| ---- | -- | ------- | -- |
| 서비스ID · DTO · DAO | — | ● | ● |
| 헤더(`sys_comm`) | ● | ● | ● |
| Filter / JWT | ● | ○ | ○ |
| 테이블 | ○ | ● | — |
| 페이징 계약 | — | ● | ● |
| Gradle / Boot | ● | ● | ● |
