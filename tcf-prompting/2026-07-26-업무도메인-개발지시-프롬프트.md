현재 저장소 기준으로 업무 WAR는 `eb-service`와 같은 6계층 구조를 사용하고, ServiceId는 `{업무코드}.{업무명}.{처리유형}` 형식을 따릅니다. 업무 메인 클래스는 `NsightWarBootstrap`을 상속하며, Handler는 도메인 단위로 여러 ServiceId를 `serviceIds()`에 등록하는 방식입니다. ([GitHub][1])

신규 모듈은 `settings.gradle`의 `include`, 루트 `build.gradle`의 `businessModules`, 모듈 자체 `build.gradle`에 모두 반영해야 합니다. `eb-service/build.gradle`은 Spring Boot·WAR 플러그인, TCF 의존성, MyBatis, H2, 외부 Tomcat용 `providedRuntime`과 WAR 파일명을 정의합니다. ([GitHub][2])

아래 프롬프트에서 `8088`은 현재 문서화된 업무 포트 목록에 없는 **AV 권장 임시 포트**입니다. 실제 적용 전 저장소 전체와 실행 환경에서 충돌 여부를 다시 확인하도록 구성했습니다. 패키지·프로그램 책임은 기존 NSIGHT 패키지 및 프로그램 설계기준을 반영했습니다.

# 3. 미확정 필수 입력정보 처리

현재 다음 정보는 아직 확정되지 않았다.

| 미확정 항목        | 필요한 내용                                        |
| ------------------ | -------------------------------------------------- |
| DB 테이블          | 자산평가 조회 대상 테이블 또는 View                |

| 개인정보           | 고객번호·주소 등 개인정보 포함 여부                |
| 권한               | 조회 가능 사용자·지점·조직 범위                    |

| 감사대상           | 중요 정보 조회 감사로그 대상 여부                  |

운영용 SQL과 DB 객체를 임의로 만들어서는 안 된다.

구현 실행 시 위 정보가 제공되지 않았다면 다음 원칙을 적용하라.

1. 실제 운영 테이블명과 컬럼명을 추측하지 않는다.
2. `AV_ASSET_VALUATION` 같은 이름을 확정된 객체처럼 사용하지 않는다.
3. 필요한 입력을 한 번에 표로 요청한다.
4. 사용자가 DB 정보를 제공하기 전에는 운영 SQL을 생성하지 않는다.
5. 구조 검증이 필요하면 `local` Profile에 한정한 **설계 예시 H2 테이블**을 사용할 수 있다.
6. 설계 예시 객체에는 주석으로 다음 문구를 명시한다.

```text
설계 예시:
실제 DB 테이블·컬럼 정의가 확정되면 교체해야 하며
운영 적용 대상으로 간주하지 않는다.
```

7. 운영 Profile에서 설계 예시 H2 객체가 자동 생성되지 않도록 한다.

# 5. 6계층 패키지 및 호출 규약

## 5.1 논리 처리 흐름

반드시 다음 방향으로만 호출한다.

```text
entry/handler
    ↓
entry/facade
    ↓
application/service
    ↓
application/rule
    ↓
persistence/dao
    ↓
persistence/mapper
    ↓
Mapper XML
    ↓
DB
```

간략히 표현하면 다음 6계층이다.

```text
Handler → Facade → Service → Rule → DAO → Mapper
```

## 5.2 계층별 책임

| 계층    | 책임                                     | 금지사항                      |
| ------- | ---------------------------------------- | ----------------------------- |
| Handler | ServiceId 등록, 요청 진입, Facade 분기   | SQL, 트랜잭션, 업무규칙 구현  |
| Facade  | 유스케이스 조립, 트랜잭션 경계, DTO 변환 | Mapper 직접 호출              |
| Service | 조회 절차와 업무 처리 조정               | 요청 전문 직접 파싱, SQL 작성 |
| Rule    | 요청 검증, 조회조건 생성, 업무 판단      | DB·외부 API 호출, 상태 변경   |
| DAO     | Mapper 호출과 데이터 접근 추상화         | 업무 판단, 응답 전문 조립     |
| Mapper  | MyBatis Statement 계약                   | 업무 로직, 예외 메시지 결정   |

## 5.3 금지 호출

다음 구조는 생성하지 마라.

```text
업무별 Controller → Service
Handler → Mapper
Handler → DAO
Facade → Mapper
Service → Mapper
Rule → DAO
Rule → Mapper
DAO → 다른 도메인 Service
다른 업무 WAR Java 클래스 직접 참조
```

업무별 온라인 Controller를 별도로 만들지 마라. 온라인 요청은 기존 공통 `OnlineTransactionController`와 TCF Dispatcher를 통해 처리한다.

# 6. ServiceId 설계

## 6.1 형식

ServiceId는 반드시 다음 형식을 따른다.

```text
{업무코드}.{업무명}.{처리유형}
```

AV 최초 거래는 다음과 같이 고정한다.

```text
AV.AssetValuation.inquiry
```

| 구간     | 값               | 의미              |
| -------- | ---------------- | ----------------- |
| 업무코드 | `AV`             | 자산평가 업무 WAR |
| 업무명   | `AssetValuation` | 자산평가 도메인   |
| 처리유형 | `inquiry`        | 조회 처리         |

## 6.2 Handler 설계

`AvAssetValuationHandler`는 자산평가 도메인 단위 Handler로 구현한다.

```java
private static final String INQUIRY =
        "AV.AssetValuation.inquiry";
```

`serviceIds()`를 사용하여 지원 ServiceId를 등록한다.

```java
@Override
public Collection<String> serviceIds() {
    return List.of(INQUIRY);
}
```

`doHandle()`에서는 `TransactionContext`의 Header에서 ServiceId를 읽고 Facade 메서드로 분기한다.

지원하지 않는 ServiceId는 다음 기준으로 처리한다.

```text
ErrorCode.SERVICE_NOT_FOUND
+ Handler명
+ 입력 ServiceId
```

향후 다음 조회 거래가 추가되더라도 동일 도메인 Handler에 등록할 수 있게 설계한다.

```text
AV.AssetValuation.inquiry
AV.AssetValuation.inquiryDetail
AV.AssetValuation.inquiryHistory
AV.AssetValuation.inquiryList
```

다만 실제 요구사항 없이 위 ServiceId를 미리 구현하거나 OM에 등록하지 않는다.

# 10. DTO 설계

## 10.1 요청 DTO

`AssetValuationInquiryRequest`는 표준 전문의 `body`를 업무 요청으로 변환한다.

DB 정보가 미확정된 현재 단계의 설계 예시는 다음과 같다.

```text
assetId
valuationBaseDate
customerId
valuationStatus
pageNo
pageSize
```

실제 요구사항이 확정되면 필요 필드만 남긴다.

다음 메서드를 기존 EB DTO 패턴에 맞춰 구현한다.

```java
public static AssetValuationInquiryRequest fromMap(
        Map<String, Object> body)
```

필수 필드 누락과 타입 변환 오류는 표준 업무 오류로 변환한다.

## 10.2 조회조건 DTO

`AssetValuationSearchCriteria`는 화면 요청 DTO를 그대로 Mapper로 전달하는 객체가 아니다.

Rule에서 정규화·검증한 조회조건만 포함한다.

```text
문자열 trim
날짜 형식 변환
상태코드 검증
조회범위 제한
페이지 크기 상한 적용
권한에 따른 지점·조직 조건 추가
```

## 10.3 응답 DTO

`AssetValuationInquiryResponse`는 DB Row를 화면에 그대로 노출하지 않는다.

다음 정보를 구분한다.

```text
처리 결과
조회 건수
조회 데이터
페이징 정보
업무 메시지
```

개인정보가 포함되면 Service 또는 응답 조립 단계에서 마스킹 정책을 적용한다.

# 11. Rule 구현

`AvAssetValuationRule`은 부작용 없는 업무 판단만 수행한다.

기본 메서드는 다음과 같이 구성한다.

```java
void validateInquiry(AssetValuationInquiryRequest request);

AssetValuationSearchCriteria buildSearchCriteria(
        AssetValuationInquiryRequest request,
        TransactionContext context);
```

검증 대상은 실제 요구사항에 따라 확정하되 다음을 검토한다.

```text
요청 Body null 여부
필수 조회조건 존재 여부
평가기준일 형식
조회 시작일·종료일 관계
허용 평가상태 코드
페이지 크기 상한
사용자·지점·조직 조회범위
개인정보 접근 권한
```

Rule에서는 DAO, Mapper, 외부 Client를 호출하지 않는다.

# 12. Service 및 Facade 구현

## 12.1 Facade

`AvAssetValuationFacade`는 다음 책임을 가진다.

```text
Map Body → 업무 Request DTO 변환
트랜잭션 경계
Service 호출
업무 Response DTO → Map 변환
```

조회 거래이므로 다음 기준을 적용한다.

```java
@Transactional(readOnly = true)
```

현재 프레임워크가 Facade에 고정 Timeout을 사용하면 EB 기준을 유지하되, OM의 Service Timeout 정책과 중복·충돌하지 않는지 확인한다.

## 12.2 Service

`AvAssetValuationService` 처리 흐름은 다음과 같다.

```text
Rule.validateInquiry()
→ Rule.buildSearchCriteria()
→ DAO 조회
→ 조회 결과 업무 DTO 변환
→ Response 생성
```

Service는 `StandardRequest<Map<String,Object>>`를 직접 받지 않는다.

Service에서 HTTP Header나 JWT 문자열을 직접 파싱하지 않는다. 필요한 사용자·지점·채널 정보는 `TransactionContext`를 통해 사용한다.

# 13. DAO·Mapper·SQL 구현

## 13.1 DAO

`AvAssetValuationDao`는 Mapper 호출을 감싸는 데이터 접근 계층이다.

```java
@Repository
public class AvAssetValuationDao {

    private final AvAssetValuationMapper mapper;

    public AvAssetValuationDao(
            AvAssetValuationMapper mapper) {
        this.mapper = mapper;
    }

    public List<AssetValuationRow> selectAssetValuations(
            AssetValuationSearchCriteria criteria) {
        return mapper.selectAssetValuations(criteria);
    }
}
```

반환 건수 제한과 결과 없음 처리 기준을 명확히 한다.

## 13.2 Mapper Interface

```java
@Mapper
public interface AvAssetValuationMapper {

    List<AssetValuationRow> selectAssetValuations(
            AssetValuationSearchCriteria criteria);
}
```

## 13.3 Mapper XML

Namespace는 Mapper Interface의 FQCN과 정확히 일치해야 한다.

```xml
<mapper namespace=
 "com.nh.nsight.marketing.av.persistence.mapper.AvAssetValuationMapper">
```

Statement ID는 인터페이스 메서드명과 일치시킨다.

```xml
<select id="selectAssetValuations">
```

운영 SQL은 DB 정의가 제공된 후 작성한다.

다음은 금지한다.

```text
SELECT *
문자열 치환 ${}
조건 없는 전체 테이블 조회
업무코드와 무관한 테이블 직접 접근
다른 도메인 소유 테이블 UPDATE
개인정보 원문 로그
무제한 목록 조회
Mapper XML에 업무 판단 로직 과다 구현
```

동적 조건에는 `#{}` 바인딩을 사용하고, 목록 조회에는 페이징 또는 최대 건수 제한을 적용한다.

## 19.4 Timeout

테스트 Profile에서만 지연을 주입하여 Online·TX·DB Query Timeout 동작을 검증한다.

운영 코드에 `Thread.sleep()`를 남기지 않는다.

검증사항:

```text
Timeout 응답 표준화
업무 처리 중단 여부
DB Transaction Rollback 여부
거래로그 TIMEOUT 상태
GUID·TraceId 추적 가능
```

# 21. 금지사항

다음을 절대 수행하지 마라.

```text
1. eb-service 소스를 직접 AV 업무로 변경
2. EB 전용 클래스명·설정·테이블을 AV에 남김
3. 업무별 Online Controller 신규 생성
4. Handler에서 DAO·Mapper 직접 호출
5. Service에서 Mapper 직접 호출
6. Rule에서 DB 또는 외부 API 호출
7. 실제 DB 정의 없이 운영 SQL 추측
8. SELECT * 사용
9. 비밀번호·JWT·Private Key 하드코딩
10. ServiceId를 URL이나 클래스명만으로 대체
11. OM Catalog 미등록 상태로 완료 판정
12. 테스트 없이 BUILD SUCCESSFUL만 보고 완료 판정
13. 응답 성공만 확인하고 거래로그를 확인하지 않음
14. 다른 업무 WAR의 Java 클래스를 직접 Import
15. 운영 Profile에서 H2 schema.sql 자동 실행
16. 실제 실행하지 않은 명령을 성공했다고 보고
```

# 23. 최종 완료조건

다음 문장을 증명할 수 있을 때만 작업을 완료했다고 보고하라.

```text
av-service가 Gradle 멀티모듈에 정상 등록되었고,
NsightWarBootstrap 기반 Spring Boot WAR로 기동되며,
AV.AssetValuation.inquiry ServiceId가
AvAssetValuationHandler에 유일하게 등록되어 있고,
Handler → Facade → Service → Rule → DAO → Mapper 계층을 거쳐
표준 응답을 반환하며,
bootRun 포트에서 POST /av/online 호출이 성공하고,
거래로그·GUID·TraceId·OM 기준정보까지
End-to-End로 추적할 수 있다.
```

DB 테이블·조회조건·응답 필드가 확정되면 이 프롬프트의 **3번과 10~13번 입력값만 교체**하고 나머지 아키텍처 지시는 그대로 사용할 수 있습니다.
