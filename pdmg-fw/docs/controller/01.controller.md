PDMG의 Controller는 HTTP 거래의 진입점으로, 표준 요청 전문에서 업무 DTO를 전달받아 Service를 호출하고 결과 DTO를 반환합니다.

Controller 자체는 업무 로직을 수행하기보다 다음 역할만 담당하는 구조입니다.

```text
HTTP URL 매핑
  → 요청 DTO 수신
  → Service 호출
  → 결과 DTO 반환
```

## 1. 전체 처리 흐름

```text
클라이언트 요청
  │
  ▼
DefaultFilter
  ├─ JWT 검증
  ├─ hdr_nhnis 추출
  ├─ 요청 본문 캐싱
  └─ ServiceContext 생성
  │
  ▼
ServicePreventionInterceptor.preHandle()
  └─ 시스템 사전 처리
  │
  ▼
RequestBodyArgumentResolver
  └─ JSON의 dto를 입력 DTO로 변환
  │
  ▼
BizPrePostAspect.before()
  └─ 업무 사전 처리
  │
  ▼
Controller
  └─ Service 호출
  │
  ▼
BizPrePostAspect.after()
  └─ 업무 사후 처리
  │
  ▼
ResponseBodyArgumentResolver
  └─ hdr_nhnis + dto 형태로 응답 조립
  │
  ▼
클라이언트 응답
```

## 2. Controller 기본 구조

현재 Controller 예시는 다음과 같습니다.

[mgcoa5530Controller.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mk/co/a/controller/mgcoa5530Controller.java>)

```java
@Slf4j
@RestController
public class mgcoa5530Controller {

    @Autowired
    private mgcoa5530Service mgcoa5530Service;

    @PostMapping("/mgcoa5530S0")
    public mgcoa5530S0DTOout mgcoa5530S0(
            @RequestBody mgcoa5530S0DTOin input)
            throws Throwable {

        mgcoa5530S0DTOout output =
            mgcoa5530Service.mgcoa5530S0(input);

        return output;
    }
}
```

각 요소의 역할은 다음과 같습니다.

| 구성              | 역할                                |
| ----------------- | ----------------------------------- |
| `@RestController` | 반환 객체를 JSON 응답으로 변환      |
| `@PostMapping`    | HTTP URL과 Controller 메서드 연결   |
| `@RequestBody`    | 표준 전문의 `dto`를 입력 DTO로 변환 |
| `DTOin`           | Controller 입력 데이터              |
| `Service`         | 실제 업무 흐름 수행                 |
| `DTOout`          | 업무 처리 결과                      |
| `return output`   | 응답 Resolver에 결과 전달           |

## 3. URL 매핑

```java
@PostMapping("/mgcoa5530S0")
```

다음 요청을 처리합니다.

```http
POST /mgcoa5530S0
Content-Type: application/json
```

현재 주요 매핑은 다음과 같습니다.

| URL            | Controller            | 기능          |
| -------------- | --------------------- | ------------- |
| `/mgcoa5530S0` | `mgcoa5530Controller` | 목록 조회     |
| `/mgcoa8888S0` | `mgcoa8888Controller` | ImageLog 조회 |
| `/mgcoa8888D0` | `mgcoa8888Controller` | ImageLog 삭제 |
| `/mgcoa9999S0` | `mgcoa9999Controller` | 샘플 조회     |

일반적으로 서비스 ID의 마지막 문자는 거래 성격을 나타냅니다.

```text
S0 → Select/조회
D0 → Delete/삭제
```

`DefaultFilter`는 요청 URI의 마지막 부분을 서비스 ID로 사용합니다.

```text
/mgcoa8888D0
      └─ serviceId = mgcoa8888D0
```

## 4. 요청 전문 형식

PDMG Controller에 전달되는 요청은 일반 Spring JSON 구조가 아니라 표준 전문 구조입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "202608090001",
      "rms_svc_c": "mgcoa5530S0",
      "scid": "mgcoa5530",
      "optr_eno": "USER01"
    }
  },
  "dto": {
    "brc": "001",
    "searchDate": "20260809"
  }
}
```

Controller의 입력 DTO에는 `dto` 부분만 전달됩니다.

```java
public mgcoa5530S0DTOout mgcoa5530S0(
    @RequestBody mgcoa5530S0DTOin input
)
```

변환 결과:

```text
전체 요청 JSON
 ├─ hdr_nhnis → ServiceContext.header
 └─ dto       → mgcoa5530S0DTOin input
```

## 5. PDMG 전용 `@RequestBody`

여기서 사용하는 `@RequestBody`는 Spring 표준 어노테이션이 아닙니다.

```java
import nhnis.fw.commons.resolver.RequestBody;
```

즉 다음과는 다른 어노테이션입니다.

```java
// PDMG 전용
import nhnis.fw.commons.resolver.RequestBody;

// Spring 표준
import org.springframework.web.bind.annotation.RequestBody;
```

PDMG 전용 어노테이션은 표준 전문 안의 `dto` 필드만 추출하기 위해 사용합니다.

처리 구현:

[RequestBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/RequestBodyArgumentResolver.java>)

## 6. 입력 DTO 변환 과정

ArgumentResolver는 PDMG 전용 `@RequestBody`가 붙은 파라미터를 처리합니다.

### 적용 여부 확인

```java
return parameter.hasParameterAnnotation(
    RequestBody.class
);
```

Multipart 요청에는 적용하지 않습니다.

```java
if (contentType.startsWith("multipart/")) {
    return false;
}
```

### JSON 본문 읽기

```java
String requestBody =
    request.getReader()
           .lines()
           .collect(Collectors.joining());
```

`DefaultFilter`가 `CachedBodyHttpServletRequest`로 감쌌기 때문에 필터가 먼저 본문을 읽었어도 Resolver가 다시 읽을 수 있습니다.

### `dto` 노드 추출

```java
JsonNode root = objectMapper.readTree(requestBody);
JsonNode bodyNode = root.get("dto");
```

요청이 다음과 같으면:

```json
{
  "hdr_nhnis": {},
  "dto": {
    "brc": "001"
  }
}
```

Resolver는 다음 부분만 가져옵니다.

```json
{
  "brc": "001"
}
```

### DTO 객체 생성

```java
Class<?> dtoClass = parameter.getParameterType();

return objectMapper.treeToValue(
    bodyNode,
    dtoClass
);
```

결과적으로 Controller는 이미 변환된 객체를 받습니다.

```java
mgcoa5530S0DTOin input
```

알 수 없는 JSON 필드는 현재 무시됩니다.

```java
FAIL_ON_UNKNOWN_PROPERTIES = false
```

따라서 요청에 DTO에 없는 필드가 들어와도 일반적으로 오류가 발생하지 않습니다.

## 7. `dto`가 없을 때

요청에 `dto`가 없으면 빈 JSON 객체를 사용합니다.

```java
if (bodyNode == null || bodyNode.isNull()) {
    bodyNode = objectMapper.createObjectNode();
}
```

즉 다음 요청도 빈 DTO로 변환될 수 있습니다.

```json
{
  "hdr_nhnis": {}
}
```

```text
dto 없음
  → {}
  → 모든 필드가 null 또는 기본값인 DTO
```

필수 입력값 검증은 Resolver가 아니라 Controller 이후의 Rule 또는 Service에서 수행해야 합니다. Bean Validation을 사용하려면 Resolver가 검증을 연동하는지 별도 확인과 구현이 필요합니다.

## 8. Controller 내부 처리

Controller가 입력 DTO를 받은 후 Service 메서드를 호출합니다.

```java
mgcoa5530S0DTOout output =
    mgcoa5530Service.mgcoa5530S0(input);
```

Controller의 권장 책임은 다음과 같습니다.

- URL 매핑
- 입력 DTO 수신
- Facade 또는 Service 호출
- 출력 DTO 반환

Controller에 넣지 않아야 할 내용:

- SQL 실행
- 복잡한 업무 계산
- 업무 트랜잭션 직접 처리
- 중복 공통 로그 처리
- 표준 헤더 조립
- JWT 검증

현재 저장소 아키텍처 원칙상 이상적인 호출 방향은 다음과 같습니다.

```text
Controller/Handler
  → Facade
    → Service
      → Rule
        → DAO/Mapper
```

현재 PDMG Controller는 Service를 직접 호출하고 있으므로, 유스케이스 조정이나 DTO 변환·트랜잭션 경계가 복잡해지면 중간에 Facade를 두는 것이 적절합니다.

## 9. Controller 반환 처리

Controller는 업무 DTO만 반환합니다.

```java
return output;
```

예:

```java
mgcoa5530S0DTOout
```

하지만 클라이언트에는 DTO만 바로 전송되지 않습니다. [ResponseBodyArgumentResolver.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/resolver/ResponseBodyArgumentResolver.java>)가 표준 응답 형식으로 감쌉니다.

Controller 반환값:

```json
{
  "resultCode": "0000",
  "items": []
}
```

실제 최종 응답:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "202608090001",
      "rms_svc_c": "mgcoa5530S0"
    }
  },
  "dto": {
    "resultCode": "0000",
    "items": []
  }
}
```

응답 구성 원리는 다음과 같습니다.

```text
ServiceContext.header
        +
Controller 반환 DTO
        ↓
{
  "hdr_nhnis": {...},
  "dto": {...}
}
```

응답 과정에서 내부 변환용 필드는 제거됩니다.

- `dtoLogicalName`
- `fieldPropertyMap`
- 이름이 `List` 또는 `Array`로 끝나는 일부 보조 필드

## 10. Controller 예외 처리

현재 Controller 메서드는 다음과 같이 선언되어 있습니다.

```java
throws Throwable
```

Service에서 예외가 발생하면 Controller에서 처리하지 않고 상위로 전달합니다.

`NhBaseException`이면 `ResponseBodyArgumentResolver`의 `@ExceptionHandler`가 오류 DTO로 변환합니다.

```java
@ExceptionHandler(NhBaseException.class)
public ResponseEntity<NH_NIS_ERR_DTO> errorProcessor(
        NhBaseException e) {
    ...
}
```

오류 응답에도 표준 구조가 적용됩니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "..."
    }
  },
  "dto": {
    "stdErrCode": "...",
    "stdErrMsgCntn": "...",
    "errType": "BIZ"
  }
}
```

다만 현재 예외 DTO에 내부 파일명, 클래스명, 스택 트레이스 일부가 포함될 수 있습니다. 운영 응답에서는 내부 구현정보가 외부에 노출되지 않도록 제한하는 것이 필요합니다.

또한 `throws Throwable`은 범위가 너무 넓습니다. 일반적으로는 다음 중 하나가 더 적절합니다.

```java
throws NhBaseException
```

또는 Controller에서 `throws`를 생략하고 Runtime Exception을 전역 예외 처리기가 담당하게 합니다.

## 11. Controller 전후 AOP

Controller가 호출되면 `BizPrePostAspect`가 자동으로 감쌉니다.

```text
업무 사전처리
  → GUID
  → 서비스 ID
  → Controller 메서드
  → BRC
Controller 실행
업무 사후처리
  → 반환 DTO 로그
```

추가로 `PdmgBizTxFlowAspect`가 Controller·Service·DAO의 진입과 종료를 기록합니다.

따라서 Controller에 다음 로그를 중복해서 넣을 필요는 크지 않습니다.

```java
log.info("Controller Start");
log.info("Controller End");
```

현재 Controller에 있는 Start/End 로그는 공통 Aspect 로그와 중복될 수 있습니다.

## 12. 신규 Controller 작성 예시

현재 방식에 맞춘 최소 Controller는 다음과 같습니다.

```java
@RestController
@RequiredArgsConstructor
public class CustomerInquiryController {

    private final CustomerInquiryService service;

    @PostMapping("/customerInquiryS0")
    public CustomerInquiryOutput inquiry(
            @RequestBody CustomerInquiryInput input) {

        return service.inquiry(input);
    }
}
```

요청:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "customerInquiryS0"
    }
  },
  "dto": {
    "customerNumber": "C00001"
  }
}
```

처리:

```text
dto.customerNumber
  → CustomerInquiryInput.customerNumber
  → Controller
  → Service
  → CustomerInquiryOutput
  → 최종 응답의 dto
```

## 13. 현재 구조에서 주의할 점

- Spring 표준이 아니라 PDMG 전용 `@RequestBody`를 import해야 합니다.
- 입력 데이터는 JSON 루트가 아니라 `dto` 안에 있어야 합니다.
- 표준 헤더는 Controller DTO가 아닌 `ServiceContext`에서 조회합니다.
- `dto`가 없으면 빈 DTO가 만들어지므로 필수값 검증이 필요합니다.
- Controller는 `nhnis.mg.co..controller`에 있어야 현재 업무 Aspect가 적용됩니다.
- 반환 DTO 전체 로그에는 개인정보 마스킹이 필요합니다.
- 필드 주입보다 생성자 주입이 테스트와 안정성 측면에서 좋습니다.
- Controller에 업무 로직이나 SQL을 직접 작성하지 않는 것이 좋습니다.
- 공통 Start/End 로그는 Aspect와 중복될 수 있습니다.

정리하면 PDMG Controller는 표준 요청의 `dto`만 입력 객체로 받고, Service 결과 DTO만 반환합니다. `hdr_nhnis` 분리, `ServiceContext` 생성, 업무 전후 로그, 표준 응답 조립은 프레임워크 계층에서 자동으로 처리합니다.
