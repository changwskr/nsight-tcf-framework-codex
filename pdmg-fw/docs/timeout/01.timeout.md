현재 PDMG의 타임아웃 관리를 점검한 결과, 일부 설정은 존재하지만 실제 업무 요청 전체를 제한하는 통합 타임아웃은 없습니다.

핵심 상태는 다음과 같습니다.

| 영역                    |              설정 존재 |                        실제 적용 |
| ----------------------- | ---------------------: | -------------------------------: |
| PDMG 업무 요청 전체     |                      X |                                X |
| Service/트랜잭션        |                      X |                                X |
| MyBatis SQL             |                      X |                                X |
| DB Connection Pool 대기 |    PDMG 명시 설정 없음 |                 Hikari 기본 동작 |
| APIGW 외부 호출         |              코드 존재 |         현재 연결·주입 문제 있음 |
| FOS 외부 호출           |              설정 존재 | PUT 일부 적용, GET/DELETE 미적용 |
| PDMG UI Relay           |     `timeout-ms=10000` |      실제 HTTP Client에는 미적용 |
| Gradle 다운로드         | `networkTimeout=10000` |                    빌드에만 적용 |

## 1. PDMG 업무 요청 타임아웃

`pdmg-service`에는 HTTP 요청 전체를 제한하는 설정이나 실행 코드가 없습니다.

확인되지 않은 항목:

```yaml
spring:
  mvc:
    async:
      request-timeout: ...
```

또한 다음과 같은 요청 타임아웃 Filter나 Interceptor도 없습니다.

```java
Future.get(timeout)
CompletableFuture.orTimeout(...)
TimeoutException
```

따라서 Controller/Service/DAO가 오래 실행되면 애플리케이션 내부에서 정한 시간에 강제로 종료되지 않습니다.

```text
요청
  → DefaultFilter
  → Interceptor
  → Controller
  → Service
  → DAO가 끝날 때까지 대기
  → 응답
```

앞단에 API Gateway, Load Balancer 또는 WAS 타임아웃이 있다면 클라이언트 연결만 먼저 종료될 수 있습니다. 이 경우 서버의 업무 처리는 계속될 가능성이 있습니다.

## 2. 트랜잭션 타임아웃

현재 Service에는 `@Transactional` 자체가 없습니다.

따라서 다음과 같은 트랜잭션 타임아웃도 없습니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    timeout = 30,
    rollbackFor = Exception.class
)
```

`TransactionManagerHolder`에도 타임아웃을 설정하는 코드가 없습니다.

```text
TransactionDefinition.setTimeout(...)
```

수동 트랜잭션을 사용하더라도 현재 구현대로라면 시간 제한 없이 DB 처리가 끝날 때까지 기다립니다.

트랜잭션을 적용한다면 다음처럼 초 단위 타임아웃을 지정할 수 있습니다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    timeout = 30,
    rollbackFor = Exception.class
)
public Output execute(Input input) throws Exception {
    ...
}
```

단, `@Transactional(timeout=30)`은 HTTP 요청 전체가 아니라 해당 트랜잭션 구간의 제한입니다.

## 3. MyBatis SQL 타임아웃

[RdwDataSourceConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mk/config/RdwDataSourceConfig.java>)에는 MyBatis 쿼리 타임아웃이 설정되어 있지 않습니다.

현재 설정:

```java
Configuration mybatisConfig = new Configuration();

mybatisConfig.setJdbcTypeForNull(JdbcType.NULL);
mybatisConfig.setCallSettersOnNulls(true);
```

다음 설정은 없습니다.

```java
mybatisConfig.setDefaultStatementTimeout(...);
```

Mapper XML에도 `timeout` 속성이 없습니다.

```xml
<select id="..." timeout="30">
```

따라서 느린 SQL이 발생하면 JDBC Driver 또는 DB 측 제한이 발생할 때까지 기다릴 수 있습니다.

공통 설정 예:

```java
mybatisConfig.setDefaultStatementTimeout(30);
```

특정 SQL 설정 예:

```xml
<select id="selectCustomers"
        timeout="10"
        resultType="java.util.HashMap">
```

보통 공통 기본값을 설정하고, 장시간이 정당한 특정 SQL에만 별도 값을 주는 방식이 관리하기 좋습니다.

## 4. DB Connection Pool 타임아웃

현재 DataSource는 HikariCP입니다.

```java
DataSourceBuilder.create()
    .type(HikariDataSource.class)
    .build();
```

그러나 `application.yml`에는 PDMG가 명시적으로 관리하는 다음 설정이 없습니다.

```yaml
spring:
  datasource:
    rdw:
      connection-timeout: ...
      validation-timeout: ...
      max-lifetime: ...
```

여기서 `connection-timeout`은 SQL 실행 시간이 아니라 Pool에서 Connection을 얻기 위해 기다리는 최대 시간입니다.

```text
Connection Pool에 여유 있음
  → 즉시 Connection 획득

Connection Pool 소진
  → connection-timeout까지 대기
  → 초과 시 Connection 획득 실패
```

SQL 실행 시간 제한과는 다른 개념입니다.

## 5. APIGW 타임아웃

[ApiGatewayHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/apigw/ApiGatewayHandler.java>)에는 다음 설정이 있습니다.

```java
@Value("${apigw.connect-timeout:30}")
private static int CONNECT_TIMEOUT;

@Value("${apigw.response-timeout:30}")
private static int RESPONSE_TIMEOUT;
```

적용 의도:

```java
HttpClient.create()
    .option(
        ChannelOption.CONNECT_TIMEOUT_MILLIS,
        CONNECT_TIMEOUT * 1000
    )
    .responseTimeout(
        Duration.ofMillis(RESPONSE_TIMEOUT * 1000)
    );
```

설정값을 초 단위로 보고 밀리초로 변환하는 구조입니다.

그러나 현재 구현에는 문제가 있습니다.

### `static` 필드에 `@Value`

```java
@Value(...)
private static int CONNECT_TIMEOUT;
```

Spring은 일반적인 방식으로 static 필드에 `@Value`를 주입하지 않습니다. 따라서 의도한 설정값이 들어가지 않을 수 있습니다.

다음처럼 인스턴스 필드로 바꿔야 합니다.

```java
@Value("${apigw.connect-timeout:30}")
private int connectTimeout;
```

### Spring Bean 등록 확인 불가

클래스에 다음 어노테이션이 없습니다.

```java
@Component
@Service
@Configuration
```

검색상 생성하거나 호출하는 사용처도 발견되지 않았습니다. 현재는 실제 업무 실행 경로에 연결되지 않은 코드로 판단됩니다.

### Connector 초기화 문제

`call()`은 다음 값을 사용합니다.

```java
.clientConnector(clientHttpConnector)
```

하지만 `clientHttpConnector`가 반드시 초기화된다는 보장이 없습니다. Bean 생성 구조를 정리하고 생성자에서 설정된 WebClient를 주입받는 방식이 안전합니다.

따라서 APIGW 타임아웃은 “코드는 존재하지만 현재 유효하게 적용된다고 보기 어려운 상태”입니다.

## 6. 공통 ClientHttpConnector

[ClientHttpConnectorConfiguration.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/configuration/ClientHttpConnectorConfiguration.java>)는 기본 Connector를 생성합니다.

```java
return new ReactorClientHttpConnector(
    HttpClient.create()
);
```

여기에는 다음 설정이 없습니다.

- 연결 타임아웃
- 응답 타임아웃
- Read/Write 타임아웃
- Connection Pool 대기 타임아웃

`DefaultFilter`와 `ResponseBodyArgumentResolver`가 이 Connector를 주입받지만 현재 외부 호출에는 사용하지 않고 예약 필드로만 보유합니다.

## 7. FOS 타임아웃

[ObjectStorageHandler.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/fos/ObjectStorageHandler.java>)에는 다음 설정이 있습니다.

```java
@Value("${storage.fos.connect-timeout:-1}")
private int connectTimeout;

@Value("${storage.fos.response-timeout:-1}")
private int responseTimeout;
```

기본 설정:

[pdmg-fw/application-fw-defaults.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/resources/application-fw-defaults.yml>)

```yaml
storage:
  fos:
    connect-timeout: -1
    response-timeout: -1
```

`-1` 또는 0 이하는 사실상 타임아웃 비활성 의도입니다.

### PUT 요청

PUT에는 RequestConfig를 설정합니다.

```java
RequestConfig requestConfig = getRequestConfig();
request.setConfig(requestConfig);
```

따라서 PUT에는 일부 타임아웃이 적용됩니다.

### GET/DELETE 요청

GET과 DELETE에서는 `request.setConfig(...)`를 호출하지 않습니다.

따라서 현재 구현상 FOS 타임아웃 설정은 GET과 DELETE에 적용되지 않습니다.

### 연결 타임아웃 명칭 문제

현재 구현:

```java
.setConnectionRequestTimeout(...)
```

`ConnectionRequestTimeout`은 외부 서버에 TCP 연결하는 시간이 아니라 HTTP Connection Pool에서 Connection을 빌리는 대기시간입니다.

실제 서버 연결 제한은 별도의 Connect Timeout 설정이 필요합니다.

### 단위 문제

현재 코드는 다음과 같습니다.

```java
(connectTimeout * 1000),
TimeUnit.MICROSECONDS
```

예를 들어 설정값이 `30`이라면:

```text
30 × 1,000 마이크로초
= 30,000 마이크로초
= 30밀리초
```

설정 의도가 30초라면 단위가 잘못된 것입니다.

Response Timeout은 다음과 같습니다.

```java
(responseTimeout * 1000),
TimeUnit.MILLISECONDS
```

`30`이면 30초가 되므로 두 설정의 단위 처리도 일관되지 않습니다.

## 8. PDMG UI 타임아웃

[pdmg-ui/application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-ui/src/main/resources/application.yml>)에는 다음 값이 있습니다.

```yaml
pdmg:
  ui:
    target-base-url: http://localhost:8080
    timeout-ms: 10000
```

[PdmgUiProperties.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-ui/src/main/java/nhnis/mk/ui/config/PdmgUiProperties.java>)에도 값이 매핑됩니다.

```java
private int timeoutMs = 10000;
```

하지만 [TransactionRelayService.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-ui/src/main/java/nhnis/mk/ui/client/TransactionRelayService.java>)의 `RestClient`에는 이 값이 설정되지 않습니다.

```java
this.restClient = RestClient.builder()
    .defaultHeader(...)
    .build();
```

즉 현재 `timeout-ms=10000`은 `/api/config` 응답으로 화면에 전달될 뿐, Java `RestClient` 요청을 10초 후 중단시키지 않습니다.

```text
timeout-ms 설정 존재
  → 화면 설정 조회에는 노출
  → Relay HTTP Client에는 미적용
```

프런트엔드에서 해당 값으로 요청을 취소하는 코드도 검색상 확인되지 않았습니다.

## 9. Gradle Network Timeout

다음 설정은 애플리케이션 업무 타임아웃과 관계없습니다.

```properties
networkTimeout=10000
```

위치:

```text
gradle/wrapper/gradle-wrapper.properties
```

이는 Gradle Wrapper 다운로드 네트워크 제한입니다.

```text
Gradle 설치 파일 다운로드 → 10초 제한
PDMG 업무 요청             → 영향 없음
```

## 10. 현재 전체 실행 모습

현재 PDMG 요청은 사실상 다음과 같습니다.

```text
UI Relay
  → 명시적인 HTTP timeout 없음

pdmg-service HTTP 요청
  → 전체 request timeout 없음
  → Controller timeout 없음
  → Service timeout 없음
  → Transaction timeout 없음
  → MyBatis query timeout 없음
  → DB 또는 외부 시스템 응답까지 대기
```

따라서 지연 시 앞단 Proxy나 클라이언트만 먼저 끊어지고, 서버 작업이나 SQL은 계속 실행되는 상황이 발생할 수 있습니다.

## 11. 권장 타임아웃 계층

타임아웃은 바깥쪽이 안쪽보다 길도록 설정하는 것이 일반적입니다.

```text
클라이언트/UI       35초
  └─ Gateway       32초
      └─ 서비스 요청 30초
          ├─ 트랜잭션 25초
          ├─ DB SQL  20초
          └─ 외부호출 10초
```

숫자는 예시이며 실제 SLA에 맞춰야 합니다.

핵심 원칙:

```text
외부 호출/SQL 제한
  <
업무 트랜잭션 제한
  <
서비스 요청 제한
  <
Gateway/클라이언트 제한
```

그래야 내부에서 오류와 Rollback을 완료한 뒤 클라이언트에 명확한 오류 응답을 줄 수 있습니다.

## 12. 우선 보완 순서

1. MyBatis 기본 Statement Timeout 설정
2. 변경 Service에 Transaction Timeout 설정
3. UI `RestClient`에 `timeout-ms` 실제 적용
4. APIGW Handler를 Spring Bean으로 정리하고 static `@Value` 제거
5. FOS PUT/GET/DELETE에 동일한 타임아웃 적용
6. FOS 연결 타임아웃 종류와 단위 수정
7. Hikari Connection Pool 대기시간 명시
8. Timeout 예외를 표준 오류코드로 변환
9. Timeout 발생 시 거래 GUID와 대상 시스템 기록
10. 타임아웃과 트랜잭션 Rollback 통합 테스트

결론적으로 현재 PDMG는 부분적인 타임아웃 설정만 존재하고, 업무 요청부터 DB와 외부 연계까지 이어지는 일관된 타임아웃 정책은 적용되지 않은 상태입니다. 특히 UI의 `timeout-ms`, APIGW 설정, FOS 기본값은 실제 보호 기능으로 작동하는지 재구현 또는 보완이 필요합니다.
