`ServiceContext`는 HTTP 요청 한 건의 공통 정보를 모아두는 요청 단위 저장소입니다. `DefaultFilter`에서 생성하여 `ThreadLocal`에 저장하고, 같은 요청을 처리하는 Interceptor·Aspect·Resolver·Service에서 꺼내 사용합니다.

```text
HTTP 요청
  → DefaultFilter
      ├─ 요청/헤더 분석
      ├─ ServiceContext 생성
      └─ ServiceContextHolder(ThreadLocal)에 저장
  → Interceptor
  → Controller / Service / Aspect
  → Response Resolver
  → 요청 종료
      └─ ServiceContextHolder 제거
```

## 1. ServiceContext 위치

[ServiceContext.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/context/ServiceContext.java>)

현재 저장하는 정보는 다음과 같습니다.

```java
public class ServiceContext {
    private String applicationName;
    private String guid;
    private String active;
    private HttpHeaders requestHeaders;
    private HttpServletRequest httpServletRequest;
    private HttpServletResponse httpServletResponse;
    private hdr_nhnis header;
    private Map<String, Object> userContext = new HashMap<>();
    private String requestBody;
}
```

| 속성                  | 의미                                 |
| --------------------- | ------------------------------------ |
| `applicationName`     | `spring.application.name`            |
| `guid`                | 요청 추적용 고유 ID                  |
| `active`              | 활성 Spring 프로파일                 |
| `requestHeaders`      | 전체 HTTP 요청 헤더                  |
| `httpServletRequest`  | Servlet 요청 객체                    |
| `httpServletResponse` | Servlet 응답 객체                    |
| `header`              | PDMG 표준 헤더 `hdr_nhnis`           |
| `userContext`         | 요청 처리 중 사용할 임시 업무 데이터 |
| `requestBody`         | 원본 JSON 요청 문자열                |

## 2. 생성 위치

ServiceContext는 [DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java>)에서 생성합니다.

일반 JSON 요청의 개념적인 코드는 다음과 같습니다.

```java
ServiceContext serviceContext = new ServiceContext(
    applicationName,
    guid,
    active,
    requestHeaders,
    cachedRequest,
    response,
    header
);

serviceContext.setRequestBody(requestBody);

ServiceContextHolder.setInstance(serviceContext);
```

생성 순서는 다음과 같습니다.

1. HTTP 헤더를 `HttpHeaders`로 복사
2. 요청 JSON에서 `hdr_nhnis` 추출
3. GUID, 서비스 ID, IP 등 보정
4. 요청 본문을 문자열로 저장
5. `ServiceContext` 생성
6. `ServiceContextHolder`에 저장
7. 다음 Filter·Interceptor·Controller로 요청 전달

Multipart 요청도 최소한의 `hdr_nhnis`를 구성하여 별도의 `ServiceContext`를 생성합니다.

## 3. 저장 방식

[ServiceContextHolder.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/context/ServiceContextHolder.java>)

```java
public class ServiceContextHolder {

    private static ThreadLocal<ServiceContext> INSTANCE =
        new ThreadLocal<>();

    public static void setInstance(ServiceContext serviceContext) {
        INSTANCE.set(serviceContext);
    }

    public static ServiceContext getInstance() {
        return INSTANCE.get();
    }

    public static void removeInstance() {
        INSTANCE.remove();
    }
}
```

`ThreadLocal`을 사용하기 때문에 요청마다 독립적인 Context가 보관됩니다.

```text
요청 A 처리 Thread → ServiceContext A
요청 B 처리 Thread → ServiceContext B
요청 C 처리 Thread → ServiceContext C
```

동시에 여러 사용자가 요청하더라도 서로 다른 스레드라면 Context가 섞이지 않습니다.

## 4. 기본 활용 방법

업무 코드에서는 다음과 같이 가져옵니다.

```java
ServiceContext context = ServiceContextHolder.getInstance();

if (context != null) {
    String guid = context.getGuid();
    String profile = context.getActive();
    hdr_nhnis header = context.getHeader();
    String requestBody = context.getRequestBody();
}
```

`ServiceContext`에 Lombok `@Getter`가 있으므로 모든 필드에 getter가 생성됩니다.

```java
context.getApplicationName();
context.getGuid();
context.getActive();
context.getRequestHeaders();
context.getHttpServletRequest();
context.getHttpServletResponse();
context.getHeader();
context.getUserContext();
context.getRequestBody();
```

다만 Holder가 없는 실행 환경도 있으므로 null 검사를 권장합니다.

```java
ServiceContext context = ServiceContextHolder.getInstance();

if (context == null) {
    throw new IllegalStateException(
        "ServiceContext가 초기화되지 않았습니다."
    );
}
```

## 5. 표준 헤더 사용

```java
ServiceContext context = ServiceContextHolder.getInstance();
hdr_nhnis header = context.getHeader();
```

예를 들어 시스템 공통 헤더를 사용한다면 DTO가 제공하는 getter를 통해 접근합니다.

```java
String guid = context.getGuid();
var systemHeader = context.getHeader().getSys_comm();
```

실제 `hdr_nhnis`와 `sys_comm`의 정확한 getter 이름은 DTO 필드 정의를 기준으로 사용해야 합니다.

표준 헤더 자체를 교체할 수도 있습니다.

```java
context.setHeader(newHeader);
```

그러나 Response Resolver도 이 헤더를 사용하므로, 업무 코드에서 임의로 교체하면 최종 응답 헤더가 달라질 수 있습니다.

## 6. 사용자 정의 데이터 사용

`userContext`는 요청 처리 단계 사이에서 부가 정보를 공유하는 Map입니다.

저장:

```java
ServiceContext context = ServiceContextHolder.getInstance();

context.getUserContext().put("customerId", customerId);
context.getUserContext().put("authorizationLevel", "MANAGER");
```

조회:

```java
String customerId = (String) context.getUserContext()
    .get("customerId");
```

타입 캐스팅을 안전하게 하려면 확인 후 사용합니다.

```java
Object value = context.getUserContext().get("customerId");

if (value instanceof String customerId) {
    // customerId 사용
}
```

문자열 키가 여러 곳에 흩어지는 것을 방지하려면 상수로 관리하는 편이 좋습니다.

```java
public static final String CTX_CUSTOMER_ID = "customerId";
```

중요한 업무 데이터나 영속 데이터 저장소로 사용하기보다는, 한 요청 안에서 필요한 임시 부가 정보에만 사용하는 것이 적절합니다.

## 7. 요청 본문 사용

필터가 원본 JSON을 저장하므로 다음과 같이 가져올 수 있습니다.

```java
ServiceContext context = ServiceContextHolder.getInstance();
String requestJson = context.getRequestBody();
```

현재 실제 사용처 중 하나인 `ServicePreventionInterceptor`도 Context와 요청 본문을 활용합니다.

원본 요청 본문에는 개인정보나 인증정보가 있을 수 있으므로 전체 문자열을 그대로 로그에 기록하는 것은 피해야 합니다.

## 8. HTTP 요청 정보 사용

헤더 조회:

```java
String authorization = context.getRequestHeaders()
    .getFirst(HttpHeaders.AUTHORIZATION);
```

Servlet Request 사용:

```java
String ssoId = (String) context.getHttpServletRequest()
    .getAttribute("ssoId");

String requestUri = context.getHttpServletRequest()
    .getRequestURI();
```

응답 정보 사용:

```java
context.getHttpServletResponse()
    .setHeader("X-GUID", context.getGuid());
```

다만 Service 계층에서 Servlet 객체에 직접 의존하면 웹 계층과 결합되므로, 가능하면 Facade나 Interceptor에서 필요한 값만 추출해 Service에 전달하는 편이 좋습니다.

## 9. 현재 제공되는 set 메서드

현재 명시적인 setter는 세 개입니다.

```java
context.setGuid(guid);
context.setHeader(header);
context.setRequestBody(requestBody);
```

나머지는 생성 시 결정되고 setter가 없습니다.

```java
new ServiceContext(
    applicationName,
    guid,
    active,
    requestHeaders,
    request,
    response,
    header
);
```

사용자 정의 값은 `userContext` Map을 이용합니다.

```java
context.getUserContext().put("key", value);
```

## 11. 종료 처리

`DefaultFilter`의 `finally`에서 반드시 제거합니다.

```java
finally {
    ServiceContextHolder.removeInstance();
    ThreadContext.clearAll();
}
```

Servlet Container의 작업 스레드는 재사용됩니다. 제거하지 않으면 이전 요청 정보가 다음 요청에 남을 수 있습니다.

```text
요청 A: 사용자 A의 Context 저장
  → 제거하지 않음
요청 B: 같은 Thread 재사용
  → 사용자 A의 정보가 노출될 가능성
```

업무 Service에서는 일반적으로 `removeInstance()`를 호출하면 안 됩니다. 생성과 제거의 책임은 요청 경계를 관리하는 `DefaultFilter`에 두는 것이 안전합니다.

## 12. 비동기 처리 주의사항

일반 `ThreadLocal`은 새로운 스레드로 자동 전달되지 않습니다.

다음 환경에서는 `ServiceContextHolder.getInstance()`가 `null`일 수 있습니다.

- `@Async`
- `CompletableFuture`
- 별도 Thread Pool
- Scheduler
- 메시지 소비자
- 배치 작업

```java
@Async
public void execute() {
    ServiceContext context = ServiceContextHolder.getInstance();
    // 일반적으로 null
}
```

비동기 작업에는 Context 전체를 전달하지 말고 필요한 값만 명시적으로 전달하는 것이 안전합니다.

```java
String guid = context.getGuid();
String ssoId = (String) context.getHttpServletRequest()
    .getAttribute("ssoId");

asyncService.execute(guid, ssoId);
```

정리하면 `DefaultFilter`가 Context의 생성자, `ServiceContextHolder`가 요청 스레드 저장소, Interceptor·Aspect·Resolver가 주요 소비자입니다. 업무 코드에서는 `getInstance()`로 조회할 수 있지만, null 가능성·개인정보 로깅·비동기 전파·요청 종료 정리를 특히 주의해야 합니다.
