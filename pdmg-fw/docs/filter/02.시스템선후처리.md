PDMG의 “시스템 전후 처리”는 모든 Controller 업무가 실행되기 전후에 공통 처리를 자동 적용하는 방식입니다. 현재는 Spring MVC의 `HandlerInterceptor`인 `ServicePreventionInterceptor`가 담당합니다.

핵심 목적은 다음과 같습니다.

- 요청 추적용 GUID 보장
- 표준 헤더 보정
- 요청 전문 로그
- 거래 시작·종료 기록
- ImageLog DB 기록
- 예외 거래 기록
- `ServiceContext` 활용

## 1. 전체 실행 흐름

```text
HTTP 요청
  │
  ▼
DefaultFilter
  ├─ JWT 검증
  ├─ 요청 본문 캐싱
  └─ ServiceContext 생성
  │
  ▼
ServicePreventionInterceptor.preHandle()
  ├─ 시스템 사전처리 시작
  ├─ 표준 헤더 보정
  ├─ GUID 보장
  ├─ 요청 전문 로그
  └─ Pre ImageLog 기록
  │
  ▼
BizPrePostAspect.before()
  └─ 업무 사전처리
  │
  ▼
Controller / Service / DAO
  │
  ▼
BizPrePostAspect.after()
  └─ 업무 사후처리
  │
  ▼
응답 변환 및 표준 응답 생성
  │
  ▼
ServicePreventionInterceptor.postHandle()
  │
  ▼
ServicePreventionInterceptor.afterCompletion()
  ├─ 정상: Post ImageLog 기록
  └─ 예외: Exception ImageLog 기록
  │
  ▼
DefaultFilter.finally
  ├─ ServiceContext 제거
  └─ MDC 제거
```

시스템 전후 처리와 업무 전후 처리는 범위가 다릅니다.

| 구분             | 구현                           | 역할                               |
| ---------------- | ------------------------------ | ---------------------------------- |
| 시스템 전후 처리 | `ServicePreventionInterceptor` | 모든 HTTP 거래의 공통 처리         |
| 업무 전후 처리   | `BizPrePostAspect`             | 특정 Controller의 업무 로그        |
| 요청 경계 처리   | `DefaultFilter`                | 인증, 요청 캐싱, Context 생성·제거 |

## 2. 적용 방식

### 활성화 설정

[pdmg-service/application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml>)에서 다음 설정으로 활성화됩니다.

```yaml
nhnis:
  fw:
    commons:
      legacy-web:
        enabled: true
```

`legacy-web.enabled=true`이면 [WebConfiguration.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/configuration/WebConfiguration.java>)가 활성화됩니다.

```java
@Configuration
@ConditionalOnProperty(
    name = "nhnis.fw.commons.legacy-web.enabled",
    havingValue = "true",
    matchIfMissing = true
)
public class WebConfiguration implements WebMvcConfigurer {
}
```

### URL 적용 범위

현재 등록 범위는 다음과 같습니다.

```java
registry.addInterceptor(servicePreventionInterceptor)
        .addPathPatterns("/**")
        .excludePathPatterns("/error");
```

따라서:

- 모든 Controller 요청에 적용
- `/error`만 제외
- Controller에 별도 어노테이션을 붙일 필요 없음
- 정적 자원이나 관리 URL도 MVC Handler로 처리되면 영향을 받을 수 있음

실제 구현:

[ServicePreventionInterceptor.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/interceptor/ServicePreventionInterceptor.java>)

## 3. 시스템 사전 처리

`preHandle()`은 Controller 호출 전에 실행됩니다.

```java
@Override
public boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler) throws Exception {

    return preHandleInternal(request, response, handler);
}
```

`true`를 반환하면 Controller로 진행하고, `false`를 반환하면 처리를 중단합니다. 현재 구현은 정상적으로 `true`를 반환합니다.

### 3.1 시스템 사전 처리 로그

```java
LOGGER.info(PdmgTxLog.systemPreStart());
```

거래 로그에서 시스템 사전 처리 구간의 시작과 종료를 식별할 수 있게 합니다.

```text
시스템 사전처리 시작
  → 공통정보 보정
  → 요청 전문 기록
  → ImageLog 기록
시스템 사전처리 종료
```

### 3.2 Multipart 처리

Multipart 요청은 일반 JSON 전문 처리를 생략합니다.

```java
if (contentType != null &&
        contentType.startsWith("multipart")) {
    return true;
}
```

따라서 파일 업로드 요청에서는:

- JSON 요청 전문 출력 생략
- 일반 Pre ImageLog 처리 생략
- Controller 호출은 계속 진행

파일 업로드도 거래 이력 관리가 필요하다면 Multipart 전용 처리 정책을 별도로 추가해야 합니다.

### 3.3 ServiceContext 조회

```java
ServiceContext ctx =
    ServiceContextHolder.getInstance();
```

`DefaultFilter`가 먼저 생성한 Context를 가져옵니다.

Context가 없다면 경고만 남기고 요청은 계속 진행합니다.

```java
if (ctx == null) {
    LOGGER.warn(PdmgTxLog.systemContextNull());
    return true;
}
```

즉 현재는 Fail-open 방식입니다. Context가 없어도 업무 Controller가 실행됩니다.

거래 통제 관점에서 `ServiceContext`가 반드시 필요하다면, 경고 후 진행할 것인지 요청을 차단할 것인지 정책 결정이 필요합니다.

### 3.4 표준 헤더 보장

Context에 `hdr_nhnis`나 `sys_comm`이 없으면 생성합니다.

```java
hdr_nhnis header = ctx.getHeader();

if (header == null) {
    header = new hdr_nhnis();
    ctx.setHeader(header);
}

if (header.getSys_comm() == null) {
    header.setSys_comm(new sys_comm());
}
```

이 처리로 이후 업무 코드가 표준 헤더를 사용할 때 NullPointerException이 발생할 가능성을 줄입니다.

### 3.5 GUID 생성 및 동기화

표준 헤더에 GUID가 없으면 새로 생성합니다.

```java
guid = UUID.randomUUID()
        .toString()
        .replace("-", "");
```

생성한 GUID는 세 군데에 동기화합니다.

```java
sysComm.setStd_gbl_id(guid);
context.setGuid(guid);
ThreadContext.put("guid", guid);
```

```text
hdr_nhnis.sys_comm.std_gbl_id
              =
ServiceContext.guid
              =
Log4j2 ThreadContext.guid
```

이렇게 하면 애플리케이션 로그, ImageLog, 요청·응답 전문을 같은 GUID로 추적할 수 있습니다.

### 3.6 표준 헤더 보정

헤더 값이 비어 있으면 HTTP 요청 정보로 채웁니다.

| 필드                    | 보정 값                             |
| ----------------------- | ----------------------------------- |
| 서비스 ID `rms_svc_c`   | 요청 URI의 마지막 경로              |
| 화면/서비스 코드 `scid` | 서비스 ID에서 접미사 제거           |
| 단말 IP `tr_trm_ipadr`  | `X-Forwarded-For` 또는 `remoteAddr` |
| 조작자 번호 `optr_eno`  | MDC 사용자 ID 또는 `LOCAL`          |

예:

```text
요청 URI: /api/customer/CustomerInquiryS01
rms_svc_c: CustomerInquiryS01
scid: CustomerInquiry
```

단, `X-Forwarded-For`는 신뢰하는 Proxy나 Gateway를 통해 들어오는 요청에서만 신뢰해야 합니다.

### 3.7 요청 전문 로그

요청 본문은 다음 우선순위로 찾습니다.

```text
1. ServiceContext.requestBody
2. request attribute의 PDMG_REQUEST_BODY
3. CachedBodyHttpServletRequest.cachedBody
4. 없으면 "(empty-request-body)"
```

이를 통해 `DefaultFilter`에서 읽은 본문을 Interceptor가 다시 사용할 수 있습니다.

다만 현재 구현은 원본 요청 전문을 INFO 로그에 기록합니다. 다음 정보가 요청에 포함될 수 있으므로 마스킹이 필요합니다.

- 비밀번호
- 주민등록번호
- 계좌번호
- 인증 토큰
- 개인정보
- 고객 식별정보

운영에서는 전문 전체 출력보다 필드 마스킹과 로그 크기 제한을 적용하는 것이 안전합니다.

### 3.8 Pre ImageLog 기록

```java
imageLogHandler.preImagelog(header, null);
```

거래 시작 시점에 ImageLog DB 레코드를 생성합니다.

주요 기록 항목은 다음과 같습니다.

- GUID
- 서비스 ID
- 화면 ID
- 사용자 또는 조작자 번호
- 클라이언트 IP
- 요청 시각

이 기록은 거래가 시작됐지만 종료되지 않은 장애 상황도 추적할 수 있게 합니다.

## 4. Controller 실행 이후 처리

### `postHandle()`

`postHandle()`은 Controller가 정상 실행된 다음 호출됩니다.

현재 구현에서는 별도의 업무 로직 없이 흐름 추적만 수행합니다.

```java
@Override
public void postHandle(...) throws Exception {
    HandlerInterceptor.super.postHandle(
        request,
        response,
        handler,
        modelAndView
    );
}
```

응답 전문 조립과 출력은 별도의 응답 Resolver/Advice 계층에서 담당하도록 역할을 분리한 구조입니다.

`@ResponseBody` 응답은 메시지 변환 시점과 `postHandle()` 호출 순서가 복잡하므로, 응답 본문을 `postHandle()`에서 직접 수정하는 것은 적절하지 않습니다.

## 5. 시스템 사후 처리

실질적인 시스템 사후 처리는 `afterCompletion()`에서 수행됩니다.

```java
@Override
public void afterCompletion(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        Exception ex) throws Exception {
}
```

이 메서드는 요청 처리가 끝난 후 실행되며 정상과 예외를 구분합니다.

### 정상 종료

예외가 없으면 Post ImageLog를 기록합니다.

```java
imageLogHandler.postImagelog(
    ServiceContextHolder.getInstance().getHeader(),
    null
);
```

거래 시작 시 생성한 동일 GUID의 레코드에 다음 정보를 갱신합니다.

- 응답 시각
- 처리 종료 여부
- 최종 상태

개념적으로는 다음과 같습니다.

```text
preImagelog()
  → INSERT: 요청 시각, GUID, 서비스 정보

postImagelog()
  → UPDATE: 응답 시각, 정상 종료
```

### 예외 종료

예외가 전달되면 다음을 수행합니다.

```java
imageLogHandler.exceptionImagelog(
    header,
    null,
    ex
);
```

기록 대상은 다음과 같습니다.

- 예외 유형
- 예외 코드
- 예외 메시지
- GUID
- 서비스 ID
- 거래 종료 시각

그 후 현재 구현에서는 Context를 제거하고 예외를 다시 던집니다.

```java
ServiceContextHolder.removeInstance();
throw ex;
```

최종적으로 `DefaultFilter.finally`에서도 다시 제거합니다. `ThreadLocal.remove()`는 반복 호출해도 큰 문제는 없지만, Context 생명주기 소유권은 Filter로 통일하는 편이 구조적으로 명확합니다.

## 6. 업무 전후 처리와의 관계

시스템 전후 처리 안쪽에서 [BizPrePostAspect.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mk/co/common/BizPrePostAspect.java>)가 업무 전후 로그를 처리합니다.

현재 Pointcut은 다음과 같습니다.

```java
@Pointcut(
    "execution(* nhnis.mg.co..controller..*(..))"
)
```

즉 `nhnis.mg.co` 아래 `controller` 패키지의 메서드에만 적용됩니다.

업무 사전 처리에서는 다음을 기록합니다.

- GUID
- 서비스 ID
- 호출 Controller와 메서드
- BRC 값
- 업무 처리 시작

업무 정상 종료 시에는 다음을 기록합니다.

- 업무 처리 종료
- 업무 사후 처리 시작·종료
- 반환 DTO

현재 `@AfterReturning`만 있으므로 Controller가 예외를 던지면 업무 사후 Aspect는 실행되지 않습니다. 예외 기록은 시스템 `afterCompletion()` 및 전역 예외 처리 계층이 담당합니다.

## 7. 활용 측면

### 거래 추적

사용자가 오류를 신고했을 때 GUID 하나로 전체 흐름을 추적할 수 있습니다.

```text
GUID
 ├─ 요청 전문 로그
 ├─ 시스템 사전처리 로그
 ├─ 업무 사전·사후 로그
 ├─ SQL 또는 외부 연계 로그
 ├─ 응답 전문 로그
 └─ ImageLog DB
```

### 성능 분석

Pre ImageLog의 요청 시각과 Post ImageLog의 응답 시각 차이로 처리 시간을 계산할 수 있습니다.

```text
응답시각 - 요청시각 = 전체 거래 처리시간
```

이를 이용하여:

- 지연 거래 조회
- 서비스별 평균 응답시간
- 시간대별 TPS
- 장시간 미종료 거래
- 장애 시간대 분석

등에 활용할 수 있습니다.

### 장애 분석

정상 종료는 없고 Pre 기록만 존재하는 거래를 찾으면 다음 상황을 조사할 수 있습니다.

- 서버 프로세스 강제 종료
- DB 연결 지연
- 외부 서비스 타임아웃
- 예외 처리 누락
- 네트워크 연결 종료

Exception ImageLog를 통해 GUID별 오류 종류와 발생 서비스를 연결할 수 있습니다.

### 공통 정책 적용

`preHandle()`에 공통 정책을 추가할 수도 있습니다.

예:

- 거래 차단
- 점검 시간 통제
- 사용자 권한 확인
- 요청 헤더 필수값 검증
- 중복 요청 방지
- 서비스별 Rate Limit
- 서비스 타임아웃 초기화

다만 JWT 인증은 현재 `DefaultFilter`, 업무 검증은 Service/Rule 계층에서 담당하므로 역할이 중복되지 않도록 해야 합니다.

## 8. 기능을 추가할 때 기준

| 추가 기능              | 적합한 위치                          |
| ---------------------- | ------------------------------------ |
| JWT 서명 검증          | `DefaultFilter` 또는 Spring Security |
| GUID 및 공통 헤더 보정 | 시스템 `preHandle()`                 |
| 거래 시작 기록         | 시스템 `preHandle()`                 |
| 업무 입력값 검증       | Rule 또는 Service                    |
| Controller 공통 로그   | 업무 Aspect                          |
| 응답 표준 전문 조립    | Response Resolver/Advice             |
| 거래 종료 기록         | `afterCompletion()`                  |
| 예외 공통 응답 변환    | 전역 Exception Handler               |
| Context 생성·정리      | `DefaultFilter`                      |

시스템 Interceptor에 업무 로직이나 DB 트랜잭션을 넣으면 모든 거래가 영향을 받으므로 피해야 합니다.

## 9. 수정 시 주의할 점

- `preHandle()`에서 오류가 발생하면 모든 Controller 요청이 막힐 수 있습니다.
- ImageLog 저장 실패가 본 업무 실패로 연결될지 정책을 명확히 해야 합니다.
- 원본 전문 로그에는 개인정보 마스킹이 필요합니다.
- `/actuator`, Swagger, 정적 자원, 인증 URL의 제외 여부를 결정해야 합니다.
- Multipart도 거래 추적이 필요하면 별도 처리가 필요합니다.
- 비동기 처리에서는 `ServiceContext`가 자동 전달되지 않습니다.
- 정상·예외·클라이언트 연결 종료 모두에서 사후 처리가 수행되는지 테스트해야 합니다.
- `DefaultFilter`와 Interceptor 사이에서 Context 제거 책임을 한 곳으로 통일하는 것이 좋습니다.

정리하면 현재 시스템 전후 처리는 Controller에 코드를 반복해서 넣지 않고, 모든 거래에 GUID·표준 헤더·전문 로그·ImageLog를 일괄 적용하는 구조입니다. 업무 개발자는 이 기반 위에서 Controller와 Service를 작성하고, 공통 거래 정책 변경은 `ServicePreventionInterceptor`와 관련 설정에서 관리하면 됩니다.
