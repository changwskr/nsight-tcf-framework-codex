`DefaultFilter`는 Controller 진입 전에 요청을 검증하고, PDMG 업무 처리에 필요한 `ServiceContext`를 생성하는 공통 진입 필터입니다.

현재 구성에서는 `TCF` 대신 기존 Legacy Web 처리 경로의 핵심 역할을 합니다.

```text
HTTP 요청
  → DefaultFilter
     ├─ 요청 본문 캐싱
     ├─ JWT 검증(Non-local)
     ├─ hdr_nhnis 검증/생성
     ├─ ServiceContext 생성
     └─ MDC 로그 정보 설정
  → ServicePreventionInterceptor
  → ArgumentResolver
  → Controller / Service
  → Response 처리
  → ServiceContext 및 MDC 정리
```

## 1. 현재 실행 환경

[pdmg-service/application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml>)의 주요 설정은 다음 의미입니다.

```yaml
spring:
  profiles:
    active: local

nhnis:
  fw:
    tcf:
      enabled: false
    commons:
      legacy-web:
        enabled: true
      filter:
        enabled: true
```

| 설정                     | 현재 상태 | 의미                               |
| ------------------------ | --------: | ---------------------------------- |
| `tcf.enabled`            |   `false` | 신규 TCF 처리 경로를 사용하지 않음 |
| `legacy-web.enabled`     |    `true` | 기존 Interceptor/Resolver 활성화   |
| `filter.enabled`         |    `true` | `DefaultFilter` 활성화             |
| `spring.profiles.active` |   `local` | JWT와 표준 헤더를 완화하여 처리    |

필터는 [FilterConfiguration.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/configuration/FilterConfiguration.java>)에서 다음 조건으로 등록됩니다.

- `nhnis.fw.commons.filter.enabled=true`일 때만 등록
- URL 패턴: `/*`
- 실행 순서: `order=1`

따라서 현재는 거의 모든 요청이 `DefaultFilter`를 거칩니다.

## 2. DefaultFilter가 하는 일

구현은 [DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java>)에 있습니다.

### 요청 기본정보 추출

요청 URI의 마지막 경로를 `serviceId`로 사용합니다.

예:

```text
/api/member/selectMember
                  └─ serviceId = selectMember
```

또한 다음 값을 로그 컨텍스트인 Log4j2 `ThreadContext`에 저장합니다.

- GUID
- 서비스 ID
- 사용자 ID
- 클라이언트 IP

이 값들은 업무 로그와 거래 추적에 사용됩니다.

### 요청 본문 캐싱

Servlet 요청 본문은 원래 한 번만 읽을 수 있습니다. 필터에서 JSON을 읽으면 Controller가 다시 읽지 못하기 때문에 [CachedBodyHttpServletRequest.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/CachedBodyHttpServletRequest.java>)로 감쌉니다.

```text
원본 Request
  → 전체 body를 byte[]로 보관
  → 필터에서 JSON 파싱
  → Controller/Resolver에서 다시 읽기 가능
```

현재 전체 본문을 메모리에 올리므로 대용량 요청에서는 주의가 필요합니다.

### JWT 검증

현재 코드는 `jwt.enabled`가 아니라 활성 프로파일을 기준으로 JWT 검증 여부를 결정합니다.

| 프로파일         | Authorization 헤더 | JWT 검증 |
| ---------------- | ------------------ | -------- |
| `local`          | 없어도 됨          | 생략     |
| `dev`, `prod` 등 | `Bearer` 토큰 필수 | 수행     |

Non-local에서는 다음을 검사합니다.

1. `Authorization: Bearer {token}` 존재
2. JWT 서명 및 유효기간
3. Access Token인지 검사
4. 토큰 Subject를 `ssoId` 요청 속성에 저장

JWT 처리는 [JwtProvider.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/security/JwtProvider.java>)가 담당합니다.

중요한 점은 `dev` 설정에 `jwt.enabled: false`가 있어도 현재 `DefaultFilter`는 이를 보지 않는다는 것입니다. `spring.profiles.active=dev`이면 JWT를 요구합니다. 설정과 구현이 불일치하므로 운영 전 정리가 필요합니다.

### 표준 헤더 처리

일반 JSON 요청에는 다음 구조가 있다고 가정합니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "guid": "...",
      "rms_svc_c": "...",
      "scid": "...",
      "tr_sysid": "..."
    }
  },
  "body": {}
}
```

`local`에서는 `hdr_nhnis`가 없어도 다음 기본값을 생성합니다.

- `guid`: UUID
- `rms_svc_c`: URI의 마지막 경로
- `scid`: 서비스 ID에서 특정 접미사 제거
- 사용자 ID: `LOCAL`
- 송신 시스템 ID: `spring.application.name`
- IP: `X-Forwarded-For` 또는 `remoteAddr`

Non-local에서는 `hdr_nhnis`가 없으면 `400 Bad Request`로 거절합니다.

### ServiceContext 생성

필터가 추출한 요청 정보를 가지고 `ServiceContext`를 생성하고 `ServiceContextHolder`에 넣습니다.

개념적으로는 다음과 같습니다.

```java
ServiceContext serviceContext =
    new ServiceContext(request, response, hdrNhnis);

serviceContext.setRequestBody(requestBody);
ServiceContextHolder.setInstance(serviceContext);
```

이후 Controller, Aspect, Interceptor 등에서는 다음 방식으로 접근합니다.

```java
ServiceContext context = ServiceContextHolder.getInstance();
```

주요 사용처는 다음과 같습니다.

- `ServicePreventionInterceptor`: 요청 본문과 거래 컨텍스트 사용
- `BizPrePostAspect`: GUID와 서비스 ID 기반 업무 로그 기록
- `ResponseBodyArgumentResolver`: 요청 헤더를 이용해 표준 응답 구성

### Multipart 요청

Multipart 요청은 JSON 본문 파싱을 생략합니다.

- `X-GUID` 헤더에서 GUID 추출
- 최소한의 `hdr_nhnis` 및 `ServiceContext` 생성
- 파일 업로드 처리를 계속 진행

### 종료 시 정리

성공하거나 예외가 발생하더라도 반드시 실행됩니다.

```java
finally {
    ServiceContextHolder.removeInstance();
    ThreadContext.clearAll();
}
```

ThreadLocal/MDC를 정리하지 않으면 다음 요청이 이전 요청의 사용자나 GUID를 사용하는 심각한 문제가 생길 수 있으므로, 이 부분은 수정할 때 반드시 유지해야 합니다.

## 3. 오류 처리

현재 주요 응답은 다음과 같습니다.

| 상황                           |  응답 |
| ------------------------------ | ----: |
| Non-local에서 Bearer 토큰 없음 | `401` |
| JWT가 유효하지 않음            | `401` |
| Access Token이 아님            | `401` |
| 요청 본문이 비어 있음          | `400` |
| JSON 형식 오류                 | `400` |
| Non-local에서 `hdr_nhnis` 없음 | `400` |
| 필터 내부 일반 예외            | `400` |

현재 내부 구현 오류까지 모두 `400`으로 반환할 수 있습니다. 개선할 경우 사용자 입력 오류는 `400`, 서버 내부 오류는 `500`으로 구분하는 것이 좋습니다.

## 4. 수정할 때 함께 확인할 부분

### JWT 정책을 변경하는 경우

다음 파일을 함께 확인해야 합니다.

- [DefaultFilter.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/filter/DefaultFilter.java>)
- [JwtProvider.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-fw/src/main/java/nhnis/fw/commons/security/JwtProvider.java>)
- [SecurityConfig.java](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/java/nhnis/mk/config/SecurityConfig.java>)
- [application.yml](<C:/Programming(23-08-15)/nsight-tcf-framework-codex/pdmg-service/src/main/resources/application.yml>)

현재 Spring Security는 `anyRequest().permitAll()`이고 실질적인 JWT 검증은 `DefaultFilter`가 담당합니다. 필터만 끄면 인증되지 않은 요청이 그대로 통과할 가능성이 있습니다.

추천 방식은 프로파일 문자열 비교 대신 명시적인 설정을 사용하는 것입니다.

```yaml
jwt:
  enabled: true
```

```java
@Value("${jwt.enabled:false}")
private boolean jwtEnabled;
```

### 표준 헤더를 변경하는 경우

다음을 함께 수정해야 합니다.

- `hdr_nhnis`, `sys_comm` DTO
- `DefaultFilter`의 기본 헤더 생성 로직
- `ServiceContext`
- 요청/응답 ArgumentResolver
- UI의 API 요청 공통 모듈
- 샘플 JSON과 아키텍처 문서

필드 하나만 필터에 추가하고 응답 Resolver나 UI를 수정하지 않으면 요청과 응답의 표준 헤더가 달라질 수 있습니다.

### URL 또는 제외 경로를 변경하는 경우

현재 `/*`에 등록되어 빈 본문 요청도 검사합니다. 따라서 다음 요청도 영향을 받을 수 있습니다.

- Health check
- 정적 파일
- Swagger
- 단순 GET
- 로그인 또는 토큰 발급 API

이런 요청은 `FilterConfiguration`에서 제외하거나, `DefaultFilter` 내부에서 `shouldNotFilter` 성격의 조건을 두는 것이 좋습니다. 구조를 다듬는다면 `Filter`보다 `OncePerRequestFilter`가 관리하기 편합니다.

### 요청 본문 처리를 변경하는 경우

다음을 같이 검토해야 합니다.

- `CachedBodyHttpServletRequest`
- `DefaultFilter` JSON 파싱
- `RequestBodyArgumentResolver`
- Controller DTO
- 최대 요청 크기

현재 `readAllBytes()`를 사용하므로 요청 크기 제한을 두는 것이 안전합니다.

### TCF 방식으로 전환하는 경우

Legacy 경로와 TCF 경로를 동시에 켜면 중복 검증이나 컨텍스트 중복 생성이 발생할 수 있습니다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    commons:
      legacy-web:
        enabled: false
      filter:
        enabled: false
```

단, 실제 전환 전에는 TCF가 JWT, 표준 헤더, `ServiceContext`, 응답 조립을 모두 대체하는지 먼저 확인해야 합니다.

## 5. 수정 후 반드시 확인할 테스트

현재 `DefaultFilter` 전용 테스트는 확인되지 않으므로 수정 시 추가하는 것이 좋습니다.

최소한 다음 시나리오가 필요합니다.

- Local에서 `hdr_nhnis` 없이 기본 헤더가 생성되는지
- Non-local에서 토큰이 없으면 `401`인지
- 유효하지 않은 토큰이 `401`인지
- Access Token이 아니면 거절되는지
- 올바른 토큰의 Subject가 `ssoId`로 전달되는지
- 잘못된 JSON이 `400`인지
- Multipart 요청이 정상 통과하는지
- Controller에서 `ServiceContext`와 요청 본문을 사용할 수 있는지
- 성공과 예외 모두에서 `ServiceContextHolder`가 정리되는지
- Health check와 GET 요청의 필터 적용 정책이 올바른지

핵심적으로는 현재 `DefaultFilter`가 단순 로깅 필터가 아니라 인증, 표준 전문 검증, 요청 캐싱, `ServiceContext` 초기화를 모두 담당하고 있습니다. 따라서 수정할 때는 필터 하나만 보지 말고 Security, Interceptor, Resolver, 표준 DTO, UI 요청 형식까지 하나의 계약으로 함께 검토해야 합니다.
